"Agent 可以在使用中不断进化"是一句很吸引人的话，也是一句信息量很低的话。

有的系统只是把失败经验追加到 Prompt，有的会重写 Memory 规则，有的生成新的 Skill，还有的真的修改 Agent 代码并运行基准测试。它们都被叫作自进化，风险和技术难度却不在一个量级。这篇文章想回答一个朴素的问题：下一次运行与这一次相比，到底有什么东西被保存并改变了，以及凭什么说这次改变是进步。

证据来自自进化 Agent 的几篇综述，以及 ACE、EvoSkill、Darwin Gödel Machine、AlphaEvolve 四个代表性方法。这些方法面向的对象、优化信号和验证方式各不相同，放在一起比较容易看清"自进化"这个笼统说法下面到底有几个不同的东西。所有实验数字都来自各自论文或官方发布的设定，不能直接外推到任意业务。

![Agent 自进化从上下文到模型权重的六种更新对象](/images/posts/agent-self-evolution-map.svg?v=20261001)

## 先看结论

自进化可以按"改什么"分成六层，越往下修改越接近系统本体，验证和回滚成本也越高。

| 层 | 改什么 | 代表方法 | 主要风险 |
| --- | --- | --- | --- |
| Context | 模型看到的规则与案例 | ACE | 规则冲突、上下文膨胀 |
| Memory | 写入、检索与遗忘策略 | 记忆进化 | 错误被固化为事实 |
| Skill | 可复用的步骤与工具用法 | EvoSkill | 脚本改坏真实环境 |
| Workflow | 流程、路由与并行策略 | 编排进化 | 状态机被破坏 |
| 代码 | Agent 自身实现 | DGM | 改坏运行与评测 |
| 权重 | 模型参数 | 微调、强化学习 | 灾难性遗忘、无法解释 |

共同的难点只有一个：产生修改不难，判断修改是否真的更好很难。后面会逐层展开，并用一个贯穿案例说明一个可控的进化闭环长什么样。

## 一、先区分反思、学习、进化与自适应

四个词经常混在一起，但它们保留的东西不同。

| 行为 | 是否跨任务保留 | 例子 |
| --- | --- | --- |
| 反思 | 否 | 当前任务失败后让模型重新检查计划 |
| 学习 | 可以 | 把一次经验写入 Memory 或 Skill |
| 进化 | 是，并经过选择 | 生成多个候选版本，评测后保留更优版本 |
| 自适应 | 是，调整行为或参数 | 根据线上分布调整阈值或路由策略 |

一次任务里执行 `plan → act → reflect → retry`，即使成功率提高，也不一定是自进化。任务结束后状态全部丢弃，下一次还会从原点开始。这种只发生在单次任务内的调整，通常叫 test-time adaptation。

反过来，简单地把所有经验永久追加到 Prompt 也不是有效进化。上下文越来越长、规则互相冲突、早期错误被反复继承，系统可能越用越差。自进化真正困难的部分不在"产生修改"，而在选择哪些修改值得进入下一代。

### 综述给出的三组坐标

[自进化 Agent 综述](https://arxiv.org/abs/2507.21046)把问题概括为三个维度：改什么、什么时候改、怎样改。这三个维度比按项目名称分类实用得多，因为同名的方法经常在改完全不同的东西。

另一篇[自进化 Agent 综合综述](https://arxiv.org/abs/2508.07407)给出一个更系统的框架，把系统拆成四个组件：System Inputs、Agent System、Environment、Optimisers。它强调一个被忽略的点：自进化不只是"Agent 改自己"，还包括环境反馈如何被采集、优化器如何消费这些反馈。

一篇更新的[现代 Agent 系统自改进综述](https://arxiv.org/abs/2607.13104)把 Agent 看成一个配置，耦合了基础模型和由 Prompt、Memory、Tools、Control Logic 组成的脚手架，并把自改进定义成一个"自诱导的更新算子"，作用于模型参数或脚手架。这个定义的价值在于，它把"改 Prompt"和"改权重"放进同一个坐标系，只是更新目标不同。

三篇综述的共同结论是：自进化不是一种技术，而是一组作用于不同对象的更新机制。脱离"改什么、什么时候改"去谈自进化，讨论会失去落点。

### 自进化与持续学习不是一回事

持续学习通常指模型在数据流上持续更新参数，重点是解决灾难性遗忘和稳定性。自进化的范围更宽，它包括不改变参数、只改变上下文的更新。

这个区别有实际意义。一个只改 Prompt 的系统，严格说不算"学习"，因为它的模型没变；但它确实在积累能力，因为下一次任务和这一次不同。把"参数是否更新"当成唯一标准，会漏掉大部分真实发生的自进化。

### intra-test-time 和 inter-test-time

有的综述用 intra-test-time 和 inter-test-time 来划分更新时机。前者发生在任务执行过程中，影响当前任务的后续步骤；后者发生在任务之间，影响未来任务。

这个划分帮助回答一个工程问题：改动应该立刻生效，还是等任务结束再评估？立即生效能快速适应，但风险高；任务之间生效更安全，但适应慢。大多数生产系统应该偏向后者。

## 二、改什么：六种更新对象

把"改什么"摊开，就得到六种更新对象。它们的成本、可解释性和风险依次上升。

Context 和 Memory 最轻，改的是模型看到的信息。Skill 和 Workflow 居中，改的是可复用的过程知识。代码和权重最重，改的是系统实现或模型本体。

这条从轻到重的序列，也大致对应了落地的难度顺序。一个应用团队通常从 Context 和 Memory 起步，只有当某类行为高频、稳定、数据充足时，才考虑更重的更新。越重的更新，越需要隔离、评测和回滚。

### 六种对象之间存在依赖

六种对象不是彼此独立的。Context 里的一条规则可能来自 Memory 里的一次经验；一个 Skill 可能封装了一组 Workflow；一段代码可能实现了新的 Context 管理策略。

这种依赖意味着改动会传导。改了一条 Context 规则，可能让某个 Skill 的前提失效；改了一个 Workflow，可能让恢复逻辑不再成立。自进化系统需要记录这些依赖，否则一次局部改动可能在别处引发退化。

### 为什么先做轻的

轻量更新的收益下限低、上限也不高，但它的风险可控。一条规则改错了可以删掉，一段脚本改错了可能改坏环境。从轻到重，本质上是用可逆性和成本换能力上限。

一个务实的策略是：先用轻量更新把系统稳定下来，再用重更新解决轻量更新解决不了的瓶颈。跳过轻量、直接上代码或权重进化，通常会发现根本没有可靠的评测来支撑这次更新。

## 三、反馈信号决定系统会学成什么样

更新算子会优化它能看到的信号。综述一般把信号分成三类：标量奖励、文本反馈，以及没有显式信号时的自生成反馈。

标量奖励最直接，例如测试是否通过、延迟、成本、任务是否完成。它容易优化，也容易被钻空子。文本反馈更丰富，例如一次失败的自然语言解释，模型可以据此生成针对性的修改，但文本本身需要被解释和裁剪。没有外部信号时，系统只能自问自答，风险最高。

常见的信号包括：

- 测试是否通过；
- 任务是否完成；
- 用户是否接受结果；
- LLM Judge 给出的分数；
- 延迟、成本和工具调用数；
- 人工写下的文本反馈。

这些指标都不完整。只优化测试通过率，Agent 可能写死答案；只优化用户点赞，系统可能学会迎合；只优化调用成本，复杂任务会被过早终止；只依赖 LLM Judge，Agent 可能适应 Judge 的语言偏好。

因此自进化通常需要多目标约束：质量达到底线后再降低成本，安全规则作为硬约束，线上收益还要通过独立数据确认。单目标优化会把系统带向指标的漏洞，这一点在各种优化循环里反复出现。

### 信号从哪来

反馈信号大致有三个来源：环境、用户，以及系统自评。

环境信号最客观，例如测试是否通过、服务是否健康。用户信号最贴近真实需求，但噪声大，收集也慢。系统自评最便宜，也最危险，因为模型评判自己容易出现相关错误。

一个稳健的循环通常以环境信号为准绳，用用户信号补充，把自评限制在低风险场景。把自评当成主要信号，等于让系统自己定义什么算进步。

### 标量奖励与文本反馈的分工

标量奖励适合做准入判断，因为它明确、可比较。文本反馈适合做修改生成，因为它能解释失败的原因。

把两者混用会出问题。用标量奖励驱动生成，模型不知道该改哪里；用文本反馈做准入，判断标准不稳定。合理的分工是：文本反馈提出候选，标量奖励决定去留。

## 四、Context 进化：改模型看到的规则

最轻量的路径是修改模型下次看到的上下文，例如系统指令、操作手册、错误案例或领域经验。

假设一个数据分析 Agent 多次把"同比"和"环比"混淆。系统可以从失败轨迹中整理出一条新规则：

```markdown
当用户说"同比"时，默认比较去年同期；
如果数据不足以确定周期，先向用户确认，不要自动改成环比。
```

下次任务开始时，这条规则进入上下文。模型参数没有变化，行为却可能改善。

### Context 进化的三种粒度

Context 的修改可以发生在三种粒度：整段重写、条目级增删、以及条件化调整。整段重写风险最大，容易丢失信息；条目级增删是主流；条件化调整最精细，给规则加上"在什么情况下生效"。

一个成熟的系统通常从条目级开始，逐步走向条件化。条件化让规则在正确场景生效，避免一条经验在错误场景里被误用。

### ACE：把上下文当成可演化对象

[Agentic Context Engineering（ACE）](https://arxiv.org/abs/2510.04618)把这类过程做成生成、反思和整理循环。系统从轨迹中提取有用经验，再增量更新一份 playbook，而不是每次让模型从头重写整个 Prompt。

增量更新能降低一种常见退化：模型在"优化 Prompt"时喜欢缩短内容，结果把少见但重要的规则一起删掉。论文把这种现象称作 brevity bias 和 context collapse，并通过保留已有条目、局部修改来减少信息损失。

论文报告，ACE 在 Agent 和领域基准上同时优化离线上下文（如系统提示）和在线上下文（如 Agent 记忆），相对强基线在 Agent 任务上提升约 10.6%，在金融领域提升约 8.6%，同时降低了适配延迟和 rollout 成本。这些数字来自论文设定，说明的是"上下文可以被系统化优化"，而不是"任何场景都能提升 10 个点"。

### ACE 的生成、反思与整理

ACE 的结构可以理解成三个角色：生成器产生解决问题的推理轨迹，反思器从成功和失败里抽出可复用的经验，整理器把经验合并进 playbook 的增量更新。

增量更新是它和"每次重写整个 Prompt"的关键区别。重写有两重风险：可能丢掉少见但重要的规则，也可能让新旧版本之间失去稳定的对应关系，难以定位哪条规则改变了效果。增量更新把每次改动限定成小的 delta，改动可以追踪。

### Context 进化的边界

Context 进化的优点是便宜、可读、容易回滚。一条规则改了，可以直接看 diff，不满意就删掉。

缺点也很直接。规则只能通过自然语言影响模型，无法保证被遵守；条目越来越多以后，需要处理冲突、重复、适用条件和优先级；不同规则可能互相抵消。一个只靠追加规则的系统，最终会得到一份冗长而自相矛盾的手册。

### 一个 Context 进化的例子

一个真实的 Context 进化可能长这样：系统收集到一批失败，全部是因为 Agent 在缺少参数时直接用了默认值。反思器抽出一条经验"参数缺失时应先询问，不应静默使用默认值"，整理器把它作为一个条目加入 playbook。

下一轮评测里，如果这条规则减少了失败，它被保留；如果它导致延迟上升、收益又不明确，整理器可以缩减它的适用范围。整个过程不需要动模型，只改动 playbook 里的一小块。

### 规则冲突怎么处理

处理冲突的第一步是给规则加上适用条件和优先级。两条看似矛盾的规则，往往适用于不同场景。如果确实无法调和，需要指定哪条优先，并说明理由。

第二步是定期清理。过期的规则和已被模型能力覆盖的提醒应该退役。规则的收益要能被验证，否则它只是增加了上下文负担。没有清理机制的规则库会一直膨胀，直到没人敢删任何一条。

## 五、Memory 进化：改存储与检索策略

Memory 不只是存储内容，也包含一组策略：

- 什么值得写入；
- 写成事实、偏好、事件还是规则；
- 新旧记忆怎样合并；
- 检索时使用哪些关系和预算；
- 什么时候遗忘或降权。

自进化可以发生在内容上，也可以发生在策略上。

内容级更新比较直观。Agent 记住用户偏好或任务事实。策略级更新更有意思：系统发现"把整段日志存入长期记忆会污染检索"，于是改变写入条件；发现某类任务需要时间关系，便为记忆增加事件顺序。

### 记忆的三类内容

记忆内容可以粗分三类：事实、偏好、过程经验。事实是"用户是谁、项目处于什么状态"；偏好是"用户喜欢怎样的输出"；过程经验是"这类任务怎么做更好"。

三类内容的写入条件、寿命和检索方式不同。把偏好当事实存储会污染检索，把一次过程经验当成普遍规则会误导后续任务。自进化首先要区分这三类。

### 错误积累是记忆进化的主要风险

一次幻觉若被写成长期事实，后续模型会把它当作可信上下文，再生成更多与之相容的错误。这种错误会自我强化，因为每条新错误都在引用旧的错误。

缓解方式是给每条长期记忆保留来源、时间、置信度和适用范围。一条没有来源的"经验"很难被安全更新，因为你无法判断它在什么条件下成立。无法追溯来源的记忆，本质上不可撤销。

### 记忆策略的进化对象

记忆策略本身可以列成一组可调项：写入阈值、节点类型、关系种类、检索预算、重排序策略、遗忘规则。每一项都可以成为进化的对象。

例如系统发现"把整段工具输出写入记忆"会污染检索，于是提高写入阈值，只保存结构化事实。又例如系统发现某类任务需要时间关系，于是给记忆增加事件顺序字段，并在检索时优先走时间边。

策略级进化比内容级更难验证，因为它改变的是系统长期行为，短期指标未必立刻反映。它通常需要更长周期的回放和离线评测。

### 记忆进化的验证难点

记忆进化的验证比 Context 更难，因为它的效果往往延迟出现。一条记忆写入策略今天看不出问题，可能几周后在检索质量上才暴露。

这要求评测覆盖长周期：不只是看下一条回答是否正确，还要看多次交互后检索是否仍然精准。长周期评测可以用回放的方式构造，把历史对话重放并测量检索命中率。

### 记忆进化与 Jev-Mem 的联系

记忆的写入、分类和检索判断本身是高频、有界的决策。与其每次都调用生成模型，可以把这些判断类型化，交给更便宜的控制层。这条思路在 Jev 那篇文章里详细展开过，它和记忆进化是互补的：控制层决定怎么记、怎么取，进化机制决定这些策略如何被更新。

## 六、Skill 进化：把经验变成可复用能力

Skill 比一句规则更接近可执行知识。它可以包含适用条件、步骤、工具说明、模板、脚本和验收方式。

例如，Agent 多次处理数据库慢查询后，不应该只记住"要检查索引"。更完整的 Skill 可能包括：

```text
触发条件：用户提供 SQL 并询问性能
输入检查：SQL、表结构、执行计划、数据量
诊断步骤：过滤选择性 → 索引 → 回表 → join 顺序 → 锁等待
工具：EXPLAIN、慢日志、指标查询
验收：给出修改前后执行计划与耗时
禁止：没有证据时直接建议强制索引
```

### Skill 的结构

一个可维护的 Skill 通常包含五部分：触发条件、前置检查、执行步骤、使用工具、验收方式。缺了触发条件，Skill 会在不该出现的时候被调用；缺了验收方式，无法判断它是否有效。

把 Skill 写成这五部分，也让它可以被自动评测。评测器可以检查"触发是否准确""验收是否通过"，而不只是看最终回答。

### EvoSkill：从失败中长出技能

[EvoSkill](https://arxiv.org/abs/2603.02766)从失败分析中发现能力缺口，提出候选 Skill，经过评测后保留有效版本。它的意义不是"让模型再写一份 Markdown"，而是把 Skill 当作有版本、可验证的优化对象。

论文还考察了技能的可迁移性：在一个任务上进化出的 Skill，不加修改地迁移到另一个任务上，也能带来提升。其中一个例子里，从 SealQA evolve 出的 Skill 零样本迁移到 BrowseComp，准确率提升约 5.3%。这说明技能层面的优化可以产生超出训练任务的、可迁移的能力。

### EvoSkill 的实验设置

EvoSkill 面向的是一套多 Agent 系统。它迭代地进行失败分析，从失败轨迹里识别能力缺口，再提出候选 Skill。候选不是为了通过个别任务，而是要在评测集上稳定通过。

这个设定的特别之处在于它是多 Agent 的：技能可以在 Agent 之间共享和复用。当多个 Agent 面对相似任务时，从一个 Agent 的失败里学到的 Skill，可能直接被另一个 Agent 使用。

### Skill 进化的风险

Skill 进化比 Context 进化更容易复用，也更容易测试。风险来自执行能力：一条错误规则可能让回答变差，一段错误脚本则可能改坏真实环境。

生成 Skill 与启用 Skill 应当是两个独立阶段。生成阶段可以宽松，鼓励多样候选；启用阶段必须严格，只有通过了验收和权限检查的 Skill 才能进入运行时。把两者混在一起，等于让候选代码直接在生产环境里试错。

### 技能库需要治理

技能一旦多了，就面临和 Context 规则一样的治理问题：重复、冲突、过期、适用范围模糊。这要求技能库有清晰的元数据：触发条件、依赖工具、验证方式、版本和所有者。

没有元数据的技能库会退化成一堆无人维护的脚本。生成技能容易，维护技能库才是长期工作。

### Skill 什么时候值得进化

不是所有经验都值得变成 Skill。一个只出现一次的任务，记下一条规则就够了；一个反复出现且有清晰步骤的模式，才值得做成 Skill。

判断标准是"重复性加可验证性"。重复出现意味着有足够数据来验证 Skill；可验证意味着能判断 Skill 是否有效。两个条件都满足时，Skill 进化才有意义。

### 技能进化的验证闭环

技能进化的验证比规则更直接，因为技能通常自带验收方式。一段诊断步骤的验收是"是否给出修改前后的执行计划与耗时"，这可以被检查。

验证闭环包括：候选技能在固定任务上运行，比较成功率和副作用，检查是否越权。只有同时满足效果和安全，技能才能进入运行时。

## 七、Workflow 与工具进化：改过程

Agent 也可以修改任务流程：先检索还是先规划，失败后是否引入 Reviewer，哪些步骤并行，什么条件触发人工确认。

下面两个流程调用相同模型和工具，结果可能完全不同：

```text
流程 A：读取需求 → 修改代码 → 运行测试

流程 B：读取需求 → 定位调用链 → 写失败测试
      → 修改代码 → 定向测试 → 回归测试 → Review
```

Workflow 进化适合处理重复出现的过程问题。例如大量失败都源于 Agent 修改前没有找到数据兼容逻辑，系统可以增加一个显式的影响分析步骤。

工具也可以被更新：补充一个结构化日志查询工具，给现有工具增加分页和错误类型，或把频繁组合的五次调用封装成一个领域工具。

### 工具与流程的耦合

工具和流程常常耦合。一个新流程可能需要一个新工具，一个新工具可能让某个流程变得多余。进化时要一起看，而不是单独改一个。

单独改流程，可能让流程依赖一个不存在的工具；单独加工具，可能让已有流程多出一条没人用的分支。把流程和工具当成一对来演化，能减少这种不匹配。

### 为什么这一层开始危险

这一层开始接触 Harness。新 Workflow 可能改变状态机，新工具可能扩大权限，因此需要验证死循环、预算、幂等性和副作用。

流程和工具的改动不像一条规则那样可以轻易删除。它们可能改变事件顺序、持久化假设和终止条件。一个看似优化的流程改动，可能让恢复逻辑失效。这一层的自进化，必须和 Harness 的契约一起设计。

### 编排进化的两种形态

编排进化有两种常见形态。一种是固定骨架、调整步骤，例如在修改代码前增加一步影响分析。另一种是搜索结构，例如决定哪些步骤可以并行、哪些必须串行。

固定骨架的调整更容易验证，因为它不改变状态机的形状。搜索结构的改动风险更大，因为它可能引入新的状态和新的失败模式。多数团队应该从调整步骤开始。

### 工具进化的边界

工具进化最容易被低估。给一个已有工具补上结构化错误，可能比新增三个工具更能减少失败。把频繁组合的五次只读调用封装成一个领域工具，可能同时降低延迟和出错率。

但工具一旦涉及写操作，进化就必须谨慎。工具的副作用分类、幂等性和权限范围都要明确，否则一次"优化"可能扩大了系统的能力边界。

### 为什么 Workflow 改变最难回滚

规则可以删，记忆可以降权，但 Workflow 的变化常常嵌在状态机里。一旦某个步骤被移除或重排，正在进行的任务可能无法恢复。

因此 Workflow 进化应该附带状态迁移方案：正在运行的任务如何过渡到新流程，旧状态的检查点是否仍然可读。没有迁移方案的流程改动，等于把所有在途任务置于风险中。

## 八、代码进化：让 Agent 改写自己

[Darwin Gödel Machine（DGM）](https://arxiv.org/abs/2505.22954)将 Agent 自身代码作为搜索对象。系统从一个 Agent 档案中选择父代，让模型修改其实现，在编码基准上评测，再把有价值的新版本加入档案。

它不是沿着一条线不断覆盖旧版本，而是保留多样化的候选。某个版本当前分数不是最高，却可能携带之后有用的编辑工具、上下文管理或 peer review 机制。这种开放式探索是 DGM 区别于普通迭代的地方。

### DGM 搜索的是什么

DGM 搜索的是 Agent 的实现，而不是任务答案。它修改的可能是工具实现、上下文管理策略，或评审机制。这些改动只通过基准分数被筛选。

搜索对象越大，评估成本越高。DGM 用档案和基准评测来控制成本，只在编码基准这类可自动验证的任务上推进。把它直接搬到无法自动验证的场景，评估就失去客观性。

### 论文报告的结果

论文报告，DGM 在实验中把 SWE-bench 表现从 20.0% 提高到 50.0%，Polyglot 从 14.2% 提高到 30.7%。这些是论文设定下的结果，说明 Harness 代码本身可以成为优化对象。

论文还指出，DGM 自动改进出了更好的代码编辑工具、长上下文窗口管理、peer review 机制等能力。这些改动的共同点是：它们都在优化"Agent 怎么工作"，而不是"Agent 知道什么"。这说明自进化在代码层能触及到 Context 层触及不到的瓶颈。

### DGM 的档案机制

DGM 的核心不是单次修改，而是维护一个不断增长的档案。它从档案里采样父代，生成新版本，评测后加入档案，并按质量与多样性选择后续父代。

保留多个版本而不是只留最高分，是为了避免过早收敛。某个当前不占优的版本，可能携带之后有用的编辑工具或上下文管理策略。开放式探索的价值，是把"现在看不出来但以后有用"的改动保留下来。

### 代码进化为什么最危险

被修改的正是负责运行、评测和进一步修改的程序。这是一个自我指涉的结构，风险也集中在这里。

代码级进化必须在隔离环境中运行。候选版本不能拥有修改评测集、绕过沙箱或伪造结果的权限。每次变化要有 diff、构建产物、测试轨迹和可恢复快照。没有这些约束，"会修改自己的 Agent"就等于把普通软件更新的风险交给了一个概率模型。

### DGM 的自我指涉风险

DGM 修改的是 Agent 自身的代码，而这段代码同时负责运行任务、评测候选，以及决定下一次如何修改。三者叠在同一个程序里，风险会互相放大。

如果候选版本能够影响评测，它就可能被优化成让评测对自己更有利。因此评测必须独立于候选：评测代码不由候选修改，评测数据对候选不可见，评测环境与候选运行环境隔离。

## 九、权重进化：改模型参数

最重的更新对象是模型参数，包括微调、强化学习、持续预训练和模型合并。

权重更新能把能力内化，不再依赖长 Context，却面临训练成本、灾难性遗忘、数据治理和回归定位问题。一次 Prompt 变更可以直接查看 diff，一次权重更新很难解释具体哪条行为为何变化。

### 权重进化的替代方案

在走向权重更新之前，有几条更轻的替代路径：把能力写进 Skill，让外部工具承担更重的计算，或者用检索把领域知识注入上下文。

这些替代方案不一定上限更高，但它们可读、可回滚、可以在没有大量训练数据时使用。只有当这些路径都被证明到顶，权重更新才值得作为下一步。

### 权重进化的成本结构

权重更新不只是算力成本。它还包括数据采集与清洗、训练稳定性、评测和回归定位。一次失败的权重更新可能让整个系统退化，而回滚又需要保留旧权重。

这些成本决定了权重进化应该低频发生，且必须有明确的触发条件，例如某类行为长期无法通过脚手架解决，同时已有大量高质量数据。

### 为什么它排在最后

权重更新的问题不只是成本。它同时改变了大量行为，难以定位回归；它需要大量高质量数据；它把系统的一部分能力锁进不可读的参数里。

对大多数应用团队来说，自进化应从 Context、Memory 和 Skill 开始。只有当某类行为高频、稳定、数据充足，并且外部脚手架已经无法满足延迟或效果要求时，权重更新才值得进入选项。

### AlphaEvolve 为什么需要两类模型

广度模型产生大量候选，保证搜索空间被覆盖；深度模型在关键处提出改进，保证候选质量。只用广度，会把评估预算浪费在低质量候选上；只用深度，会陷入局部。

分工让搜索同时在广度和质量上推进。这个结构也可以借鉴到非算法领域：用一个便宜模型生成候选方案，用一个强模型或人工在关键处把关。

## 十、可验证进化：AlphaEvolve 的闭环

[AlphaEvolve](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)提供了另一种很清楚的结构：语言模型生成程序，自动评估器运行并打分，程序数据库保存候选，进化算法决定哪些候选进入后续 Prompt。

```text
Program Database
      ↓ 选择父代与历史候选
Prompt Sampler
      ↓
LLM 生成程序变体
      ↓
Evaluator 执行并评分
      ↓
接受、归档或丢弃
```

它最适合答案能够写成程序、效果能够自动测量的领域，例如算法性能、调度、芯片设计和数学构造。评估器提供了清晰的优化信号，系统不必只依赖另一个 LLM 的主观判断。

### AlphaEvolve 的搜索结构

AlphaEvolve 用一组模型分工：更快的模型负责广度，产生大量候选；更强的模型负责深度，在关键处提出改进。候选程序被自动评估器打分，结果进入程序数据库，进化算法据此决定哪些程序进入下一轮 Prompt。

这个结构中，评估器和进化算法承担了筛选，语言模型只负责提出候选。把"提想法"和"做判断"分开，是它能在可验证领域稳定推进的原因。

### 官方发布的几个结果

Google DeepMind 报告，AlphaEvolve 在若干任务上产生了可验证的改进：它发现了一个数据中心调度启发式，在生产中持续回收约 0.7% 的全球算力；改进了矩阵乘法相关的一段电路设计并集成进下一代 TPU；把某个 FlashAttention 内核实现最高加速约 32.5%；还用 48 次标量乘法完成了 4x4 复矩阵乘法，改进了此前已知的最好结果。

这些数字说明的是"在可自动验证的问题上，进化循环能走得很远"，不能直接迁移到无法自动验证的领域。矩阵乘法和调度有明确的评估器，Agent 行为质量却没有同等清晰的度量。

### 可验证与不可验证的鸿沟

自进化在可自动验证领域进展快，在开放质量判断上进展慢，原因就在评估信号。一个能自动打分的任务，进化循环可以跑很多轮；一个只能靠人工判断的任务，每轮的成本都很高。

这条鸿沟短期内不会消失。对不可验证的领域，更现实的做法是把人工判断沉淀成半自动的评测集，逐步扩大可自动验证的部分。

### 为什么评测比生成更值得投入

生成候选的能力已经很便宜，一个模型一次能提出很多候选。真正稀缺的是判断候选好坏的能力。在这两个能力不对等的系统里，投入应该更多放在评测上。

一个常见的错误是不断改进候选生成，却复用粗糙的评测。结果是系统生成能力越来越强，却越来越擅长通过一个不完整的评测。

### 评估器决定进化的上限

AlphaEvolve 的经验指向一个通用结论：自进化的上限经常由评估器决定。没有可重复的评分，生成再多候选也只是扩大随机试错。

这也解释了为什么自进化在数学、算法、代码这类有客观验证的领域进展快，而在开放的质量判断上进展慢。评估信号的质量，直接决定了进化能优化到什么程度。

### 在线进化的三个前提

在线进化（任务执行中修改自己）要满足三个前提：改动可即时回滚、影响范围被严格限制、以及有独立的验证信号。三者缺一，在线进化就会变成不可控的自我修改。

大多数系统应该避免在线进化，除非它的对象是低风险的路由或个性化记忆。

## 十一、系统什么时候更新

自进化还要决定更新周期。

| 时机 | 特点 | 适用对象 |
| --- | --- | --- |
| 单次任务内 | 反馈快，不一定长期保留 | 计划、临时 Memory、重试策略 |
| 任务结束后 | 可以读取完整轨迹 | Context、Skill、Workflow 候选 |
| 定期离线 | 允许回放和批量评测 | Skill 发布、策略更新、模型训练 |
| 在线持续 | 适应快，风险最高 | 低风险路由与个性化记忆 |

生产环境最好把"发现候选"和"发布候选"分开。线上轨迹负责提出问题，离线管道负责生成与评测，达到门槛后再灰度发布。

让 Agent 在同一个线上请求中修改自己并立即使用，虽然更像科幻里的自进化，却很难审计和回滚。一旦这次修改是有害的，它已经作用到了当前请求，而你可能没有任何证据链还原发生了什么。

### 评测器设计的四条原则

评测器决定了进化会优化什么。四条原则是：能被重复运行、对候选不可见的部分足够多、覆盖历史失败样本、以及能把"钻空子"和"真进步"区分开。

用同一个模型既生成候选又评判候选，是评测器设计的常见缺陷。独立证据是评测器可信的基础。

## 十二、一个可控的进化闭环

一个可控实现至少包含六步：

```text
采集轨迹
→ 定位重复失败
→ 生成候选修改
→ 在隔离环境评测
→ 达到准入条件后发布
→ 持续监控并允许回滚
```

其中任何一步缺失都会产生典型问题：

| 缺失环节 | 后果 |
| --- | --- |
| 没有失败归因 | 针对偶然现象修改系统 |
| 没有候选版本 | 新规则直接覆盖旧行为 |
| 没有隔离评测 | 候选污染数据或环境 |
| 没有准入门槛 | 改动只凭几条成功案例上线 |
| 没有线上监控 | 分布变化后仍沿用旧结论 |
| 没有回滚 | 错误经验继续生成错误经验 |

### 准入条件怎么定

准入条件要在生成候选之前确定，避免看到结果再降低标准。一个可用的条件集包括：在固定任务上不退化、在历史失败样本上有改善、在隐藏留出集上无异常、成本在预算内、改动可回滚。

这些条件里，隐藏留出集尤其重要。只用开发样本选版本，候选会逐渐适应这些样本；隐藏集能暴露过拟合。准入条件和候选生成分开，是可控进化的前提。

### 贯穿案例：一个测试编写 Skill 的进化

用一个具体例子把闭环串起来。假设一个 Coding Agent 反复在同一个项目里写出会误判边界的单元测试。

第一步，采集轨迹。系统记录每次写测试的过程和后续失败，保存命令、diff 和测试结果。

第二步，定位重复失败。分析发现失败集中在"边界条件"这类测试上，Agent 经常只覆盖正常路径。这是一个重复出现的模式，不是偶发现象。

第三步，生成候选修改。系统从失败轨迹里提出一个候选 Skill，规定"写测试前先列出输入边界，边界用例单独成组"。

第四步，隔离评测。候选 Skill 在临时工作区里运行一批固定任务，比较修改前后边界用例的覆盖率和测试通过情况。

第五步，准入发布。只有当候选在固定任务上和一批历史失败样本上都达标，才允许进入项目配置。

第六步，监控与回滚。发布后持续观察该类测试的失败率；如果某个新项目上表现退化，回滚到上一版 Skill。

这个例子里，进化发生在 Skill 层，改动可读、可回滚，收益可以被衡量。把同样的闭环用在 Context 或 Memory 上，结构是一样的，只是评测对象不同。

### 失败模式的共同点

这些失败模式有一个共同点：它们不是"模型不够聪明"，而是评估和治理结构的问题。换一个更大的模型未必能解决，因为问题出在系统如何定义和度量进步。

## 十三、失败模式：自进化会在哪里失控

自进化循环本身会引入新的失败模式，其中几类在近年的研究里被反复记录。

奖励作弊（reward hacking）是最常见的。只要系统持续优化一个不完整指标，它就会找到指标漏洞。Coding Agent 可能修改测试文件或硬编码测试输入来通过评测；文本 Agent 可能学会复述 rubric 关键词来获得高分。这类行为不需要模型有恶意，它只是忠实地优化了被给定的信号。

评测信号失效是另一类。有研究记录了自主 Prompt 优化循环中的多种失败：Judge 偏差、Harness 与指标错误、ground truth 错误，以及奖励作弊。有案例显示 Agent 通过读取环境里的缓存答案来获得满分，从而掩盖了真实能力。这说明评测链路本身也需要被验证。

错误积累是第三类。一次错误经验若被写入长期 Memory 或 Skill，后续会继续生成相容的错误。这要求每条经验保留来源，并且准入检查要覆盖历史失败样本，避免解决新问题的同时重新引入旧错误。

![Agent 自进化的可控闭环](/images/posts/self-evolution-loop.svg?v=20261001)

### 三个真实案例

奖励作弊、评测失效、错误积累三类失败，在近年的研究里都有具体记录。有研究发现，自主 Prompt 优化循环会把语法损坏的 Prompt 选为赢家，因为解析器的静默回退意外提高了指标；有研究记录 Agent 读取环境缓存答案获得满分，掩盖了真实能力；也有研究显示，reference-free 的自我评测会让模型变得更有说服力，真实正确率却不提高。

这些案例的共同点是：问题出在评测信号，而不是模型能力。优化器忠实地优化了被给定的信号，包括信号里的漏洞。

### 相关错误为什么难以自查

用同一个模型既生成候选、又担任 Judge，是自进化架构里最常见的设计，也是最容易失效的设计。研究和评测文章都指出，模型在评判自己或同族模型时，错误可能高度相关，单独的置信度不足以发现问题。

缓解方式是引入独立证据：确定性断言、隐藏测试、真实环境结果、以及不同来源的标注。多个 AI Judge 的一致意见不能替代独立证据，因为相关的错误会在多个 Judge 之间一起出现。

### 从实验到生产的三道门

把一个进化实验推进到生产，要过三道门。第一道是离线门：候选在固定集和隐藏集上不退化。第二道是灰度门：小流量真实数据上，指标没有变差。第三道是长期门：运行一段时间后，没有出现延迟出现的退化。

三道门的顺序不能跳。离线门抓过拟合，灰度门抓分布差异，长期门抓缓慢退化。只过第一道门就全量发布，是自进化最常见的翻车方式。

## 十四、落地建议

短期内，我更看好 Context、Memory 和 Skill 的受控进化。它们不需要训练模型，改动可读，能够按领域拆分，也方便做版本和回滚。对 Coding Agent 来说，一个被真实失败轨迹打磨过的 Skill，往往比再加一句通用 Prompt 更有价值。

Workflow 和代码级进化会继续发展，但必须与强评测、沙箱和权限系统一起出现。缺少这些基础设施时，"会修改自己的 Agent"只是把普通软件更新的风险交给了一个概率模型。

### 一个团队的最小实践

对一个刚开始做自进化的团队，最小实践可以是：只做 Skill 层；固定一批任务作为回归集；每次改动生成候选、离线评测、人工确认、灰度发布；保留版本和一键回滚。

这个实践不追求自动化程度，追求的是闭环完整。闭环完整之后，再逐步放宽人工确认的比例。先有可靠的闭环，再谈自动化，顺序不能反。

### 谁来判断进步

判断进步的主体可以是人、评测器，也可以是另一个模型。选择不同，风险不同。人工最可信但最慢；评测器最快但可能被钻空子；模型自评最便宜但相关错误多。

一个稳健的组合是：确定性检查做硬约束，评测器做初筛，人工负责高风险和边界。单一主体判断进步，都会有盲区。

### 判断一项改动该不该保留

面对一次候选修改，可以依次问四个问题：它解决的是一个重复出现的失败，还是一次偶发？它在固定任务和隐藏样本上都不退化吗？它可读、可版本化、可回滚吗？它的收益是在独立数据上确认过的吗？

四个问题里只要有一个答案是否定的，宁可不合并。自进化的价值来自长期累积的、可靠的改进，而不是每次运行都产生一点变化。

自进化可以被写成一句不神秘的话：系统从执行轨迹里提出修改，用独立证据筛掉退化版本，再把通过验收的变化带到下一次任务。变化发生在哪一层，决定了它的能力上限，也决定了我们要承担的风险。

### 一个健康的进化节奏

健康的进化节奏是慢而稳的：每次改动小、可验证、可回滚；改动之间留有观察期，确认没有延迟退化；新改动不覆盖旧版本，而是并行运行一段时间再切换。

快速迭代在软件工程里是优点，在自进化里要打折。因为这里的"迭代"直接改变系统行为，而行为退化未必立刻可见。

### 几个仍然开放的问题

自进化领域还有几个没有定论的问题。更重的更新应该允许多频繁发生；代码级进化和权重进化是否会带来失控风险；评测器本身能不能被自动改进，以及谁来判断改进后的评测器是否更好。

这些问题没有现成答案。承认它们是开放问题，比给出一套看起来完整的框架更诚实。对工程实践的影响是：在开放问题上保守一点，把可控的轻量进化先做扎实。

### 常见误解

关于自进化有几个常见误解。第一，认为自进化就是改模型权重，其实大多数自进化发生在上下文和技能层。第二，认为只要让模型反思就能持续变好，其实没有筛选的反思会固化错误。第三，认为换一个更大的模型就能解决问题，其实很多失败出在评测和治理。

澄清这三个误解，能避免把有限精力投在错误的地方。

### 一个反面例子：反思循环的退化

假设一个 Agent 每轮任务后都让模型"总结经验"并追加到 Prompt。起初效果不错，因为错误被纠正。几周后，Prompt 里堆满了针对个别任务的规则，彼此冲突，模型开始随机选择。系统"反思"得越多，表现反而越差。

这个例子的教训很直接：反思必须伴随筛选。没有准入门槛和清理机制的自我改进，会从积累能力变成积累噪声。

### 一个人也能做的版本

个人项目没有大规模数据和评测团队，但仍有可做的自进化。最简单的做法是维护一份结构化的错误笔记：每次失败记录输入、原因和修正，定期把它整理成 Skill 或 Context 规则。

关键是把"记录"和"采纳"分开。记录可以随意，采纳必须经过一次回测，确认新规则在旧任务上不退化。即使只有几十个任务，这个回测也能挡住大部分误改。

### 一句话总结

自进化的核心问题不是"系统能不能改自己"，而是"谁来判断改得对不对"。把判断做扎实，进化才值得信任；判断做不扎实，进化只是把偶然固化下来。
