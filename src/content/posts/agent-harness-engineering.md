大模型擅长生成文字。要让 Agent 完成一个跨越多轮操作的任务，程序还得帮它读取环境、调用工具、保存状态、处理失败，并在达到验收条件时停下来。

这套位于模型之外的程序与配置通常被称为 Agent Harness。可以把模型看作发动机，把 Harness 看作方向盘、仪表盘、刹车和道路规则。模型决定能力上限，Harness 决定系统能不能稳定地用好这份能力。

我从概念的来历和模型的结构限制讲起，再沿着一个最小 Agent Loop，把实际工程中会遇到的故障逐层展开。阅读时可以一直追三个问题：失败发生在哪里，哪一层负责处理，以及怎样验证处理确实有效。

## 先看结论

一句很短的总结是：

> If you're not the model, you're the harness.

模型本身只负责生成下一段内容。打开文件、执行命令、保存进度、检查结果、判断何时停止，这些都发生在模型之外。你在聊天窗口和编辑器之间复制报错、运行代码、再把结果贴回去时，你自己就是那个 Harness。

下面八层各自补上一种模型做不好的工作：

| 层 | 防什么问题 | 少了它的样子 |
| --- | --- | --- |
| 循环 | 你手动来回贴结果 | 你自己变成那个循环 |
| 工具契约 | 输出撑爆窗口、报错没法用 | 模型对着 `Error: failed` 瞎猜 |
| 规划 | 十步任务做三步跑偏 | 修着修着忘了最初要干什么 |
| 上下文 | 窗口塞满、关键决策被压没 | 两小时后写出和自己决定矛盾的代码 |
| 记忆 | 会话一关全忘 | 新会话失忆上岗 |
| Hook 与权限 | 危险命令、越界改文件 | 写在 Prompt 里的禁令被无视 |
| 验证回路 | 假完成 | “已修复”三个字没有证据 |
| 隔离与编排 | 中间过程污染主 Context | 读五个文件的垃圾全留在窗口里 |

后面的正文会解释每一层为什么出现、挂在 Agent Loop 的什么位置，以及该怎样验证它有没有用。

## 一、Harness 这个词解决了什么问题

Harness 原本指马具，也出现在软件测试里的 test harness：控制输入、驱动被测对象运行、观察结果，再决定下一步。Agent Harness 延续了同一思路，只是被控制的对象换成了大模型。

这个词流行得很晚，背后的工程问题却很早就存在。早期的 AutoGPT、BabyAGI 已经能让模型循环调用工具，但停止条件、状态恢复和结果验证都很薄。演示时看起来很聪明，任务一长就容易陷入重复操作、任务漂移或假完成。

随着模型能力提升，问题的重心也在变化：最初大家关心模型能不能回答，后来关心如何给它正确的上下文，现在更常见的问题是它能不能长期、稳定并且可控地完成任务。模型能生成更好的候选动作，却不能替运行环境处理授权、持久化和外部验收。

Workflow 和 Harness 也不完全相同。Workflow 预先规定步骤，适合审批、发布等确定流程；Harness 主要规定边界、反馈和协作协议，让模型在边界内选择具体路径。实际系统往往混用两者：关键步骤走固定流程，调查和修复阶段允许 Agent 动态决定工具。

还要区分两个容易混用的说法：Agent Harness 是已经搭好的运行系统，Harness Engineering 是设计、评估和持续调整这套系统的过程。前者像工具和场地，后者更接近工程方法。

### 为什么这个词在最近才变得常见

Agent 工程经历过几轮关注点迁移。2023 年前后，很多工作集中在 Prompt：怎样让模型按格式回答，怎样通过 few-shot 示例稳定输出，怎样减少角色和语气跑偏。随后检索增强、长上下文与工具调用逐渐普及，Context Engineering 开始成为独立问题：有限窗口里到底放哪些材料，什么时候检索，工具结果怎样组织。

模型能处理的任务越来越长后，新的故障开始反复出现。单次回答没问题，连续执行几十轮却会忘记目标；工具调用格式正确，真实动作却可能越权；代码已经写完，模型没有足够证据判断需求是否满足。问题从“这一轮回答准不准”转向“整条执行轨迹能不能负责”。Harness Engineering 给这批分散的做法提供了一个统一名字。

几个概念的时间顺序很容易造成误解。Prompt、Context 和 Harness 并不是旧技术被新技术淘汰。一个成熟 Agent 仍然需要清楚的指令，也需要准确的 Context。区别在于研究对象逐渐扩大：从一句输入，扩大到一次调用可见的全部信息，再扩大到跨多轮运行的系统。

早期 Workflow 编排尝试解决过一部分问题。开发者把业务理解画成一张流程图，模型只负责其中几个节点。这样做确定性很强，也容易审计，但开放任务很难提前穷举路径。排查一个线上故障时，下一步取决于刚刚看到的日志；修复一个陌生仓库时，所需文件要在阅读过程中才能确定。Harness 保留了动态决策，同时把权限、预算和验收留在程序手里。

### 两类 Harness 不要混在一起

Agent harness 服务于执行，让一个具体任务能够持续运行。Evaluation harness 服务于评测，负责批量运行任务、保存轨迹、隔离环境和计算分数。两者都会调用模型和工具，但目标不同：一个交付结果，一个测量能力。

实际项目往往同时需要两套系统。生产 Harness 新增一条工具错误语义后，评测 Harness 应拿固定任务集比较修改前后的错误完成率、成本和成功率。只做生产系统而没有评测，很难知道规则是否真的有效；只做评测而没有可靠运行时，得到的高分也未必能转化为可控的线上任务。

“Harness”也有不同口径。有人强调它像马具，重点是控制；有人把它理解为工作空间，重点是给模型趁手工具；还有一种口径强调约束执行，认为模型是系统里最不稳定的部件。工程实现通常会混合三者：给模型可用的观察和行动能力，同时把风险限制在可接受范围内。

## 二、模型的结构限制

模型一次调用做的事情很单一：根据当前输入生成下一段内容，内容可以是回答，也可以是工具调用请求。连续对话看起来像模型记得上一轮，实际是运行时把历史重新放进了输入。

这种工作方式留下了几类长期存在的问题：

- 模型不会自行保存跨会话状态，需要外部持久化；
- 模型只看到当前 Context，很难持续维护全局一致性；
- 让执行者自己判断何时停止，容易提前收尾或持续空转；
- 生成和自检使用同一套判断过程，关键验收不能只靠模型自评；
- 工具调用会产生真实副作用，超时之后不能像普通回答那样直接重试。

这些能力会随着模型升级而改善，但系统责任不会因此消失。文件到底有没有修改、部署是否生效、付款是否重复、用户是否授权，都需要模型之外的事实和记录。

因此有一条很实用的原则：能由程序确定判断的规则，尽量交给程序；需要语义理解和开放判断的部分，再留给模型。Harness 保留模型的决策空间，同时让这段执行过程可观察、可恢复、能验收。

### 从回答到行动，责任发生了变化

聊天模型给出一段错误建议，用户可以不采用。Agent 拿到工具后，建议会变成真实动作：文件被覆盖、分支被推送、通知被发送、数据库被修改。一次文本生成失败通常可以重新请求，一次外部动作超时却可能已经在远端生效。

因此工具调用至少要区分三种状态：明确成功、明确失败和结果未知。结果未知常见于客户端超时或进程崩溃。此时继续重试可能重复扣款、重复部署或重复发消息。可靠系统需要业务幂等键、执行回执或状态查询，先核实外部世界发生了什么。

模型协议里的 `call_id` 只能关联一轮工具请求与返回。模型下一轮重新提出相同业务动作时，通常会产生新的 `call_id`。业务幂等键需要绑定逻辑动作，例如“任务 T 对订单 O 的这次退款”，同时校验同一个键是否对应相同参数。

### 为什么 Prompt 代替不了程序规则

Prompt 改变模型输出的概率。它可以让模型更倾向于先测试、更倾向于少改文件，却无法提供确定性保证。上下文变长、指令冲突或模型版本变化后，遵守概率也会变化。

程序条件则有明确语义。`score > 60` 在代码里满足或不满足；“只有分数超过 60 才继续”写进 Prompt 后，还要依赖模型正确读取分数、理解规则并在后续步骤持续记住。高风险边界若只存在于文字中，相当于把检查与被检查的动作放进同一个不稳定过程。

这并不意味着所有规则都要写成代码。代码适合判断路径、参数、资源范围和测试结果；架构取舍、命名风格和模糊需求仍需要语义判断。工程上的关键是找到责任边界：模型提出解释和候选动作，程序控制动作何时发生、影响哪些资源、如何记录以及怎样验收。

### 约束怎样变成能力

完全开放的工具和文件系统看起来给了模型最大自由，实际也扩大了无效搜索空间。模型需要在大量目录、命令和操作组合里分配注意力，正确路径只占其中很小一部分。

好的约束会删掉明显无效或危险的路径。例如工具参数 Schema 可以阻止模型凭空传字段，目录白名单可以避免误改无关文件，验收标准可以让循环知道何时收尾。它们没有替模型预先写好答案，而是让计算预算更多地落在有效轨迹上。

约束过多也会反噬。把每一个历史 Review 意见都写进常驻 Prompt，会挤占 Context，并产生互相冲突的规则。Harness Engineering 需要不断做减法：规则有对应故障、有可检查收益才保留；已经被模型能力、类型系统或更可靠机制覆盖的提醒应当退役。

## 三、先分清模型、Prompt、Context 和 Harness

模型、Prompt、Context 和 Harness 处在不同层次，解决的问题也不同。

| 层次 | 关注的问题 | 典型故障 |
| --- | --- | --- |
| Prompt | 当前指令如何表达 | 回答偏离目标、格式不符合要求 |
| Context | 本次调用实际能看到什么 | 信息缺失、噪声过多、关键证据被淹没 |
| Harness | 整个任务如何持续执行并接受约束 | 越权、无限重试、状态丢失、假完成 |

Prompt 是 Context 的一部分。Context 还包括对话历史、工具定义、检索结果、文件内容和环境反馈。Harness 位于更外层，负责筛选进入 Context 的信息、执行模型提出的动作，并把结果组织成下一轮 Context。

![Prompt、Context 与 Harness 的层次关系](/images/posts/harness-layers.svg)

一次模型调用只会产生回答或候选动作。执行权在 Harness 手里：动作能否执行、使用什么权限、结果怎样保存、任务是否完成，都由它判断。

可以把一个 Agent 粗略写成：

```text
Agent = Model + Harness
```

这个表达式能把许多看似“模型不够聪明”的现象拆成具体的工程问题：

- 模型没有看到图片，需要补观察通道，继续改 Prompt 没有用；
- 工具只返回 `failed`，需要改错误契约，让模型多猜几次也得不到新信息；
- 模型说“已完成”却没有测试证据，需要增加验收回路；
- 新会话忘记进度，需要持久化状态。

## 四、从最小 Agent Loop 开始

用聊天模型解决问题时，人往往就在充当 Harness：复制报错、执行代码、把结果贴回对话框，再判断是否继续。把这套往返过程搬进程序，就得到了最小 Agent Loop。

```python
def run_agent(task, tools):
    messages = [make_user_message(task)]

    for step in range(MAX_STEPS):
        response = ask_model(messages, tools)
        messages.append(response)

        calls = read_tool_calls(response)
        if not calls:
            return read_final_text(response)

        for call in calls:
            name, args, call_id = validate_call(call)
            result = TOOL_IMPL[name](**args)
            messages.append(make_tool_result(call_id, result))

    raise RuntimeError("Agent 超过最大步数，已停止")
```

这段代码里，模型只出现在 `ask_model`。其余工作都属于 Harness：保存消息、校验参数、执行工具、回传结果以及限制最大步数。

这个循环能运行，但还有一批问题没有处理：

- 模型拒答、输出截断或接口超时时怎么办；
- 工具参数不合法、工具不存在或权限不足怎么办；
- 写操作超时后，远端究竟有没有执行成功；
- 模型不再调用工具，是已经完成还是需要用户补充信息；
- 进程崩溃后，如何知道上次执行到了哪里；
- 模型说测试通过，依据来自哪里。

生产系统除了维护 `messages`，还需要一份独立的任务状态。

```text
RUNNING → WAITING_TOOL → RUNNING
RUNNING → VERIFYING → COMPLETED
                   → RUNNING      # 验证失败，仍可修复
RUNNING → NEEDS_INPUT
RUNNING → CANCELLED
RUNNING → BUDGET_EXHAUSTED
WAITING_TOOL → RESULT_UNKNOWN     # 副作用已发出，但结果未确认
```

![Agent Harness 运行循环](/images/posts/harness-runtime.svg)

`RESULT_UNKNOWN` 很容易被忽略。只读查询超时后通常可以有限重试；发送通知、支付、部署等操作超时后，远端却可能已经成功。直接重放会产生重复副作用。此时要用业务幂等键、执行回执或状态查询核对结果。模型协议里的 `call_id` 只负责关联消息，代替不了业务幂等键。

## 五、Harness 的八层机制

下面八层分别对应一类常见故障。项目遇到哪类问题，就补哪一层，不需要照着清单堆满组件。

| 层 | 防止的问题 | 最小机制 |
| --- | --- | --- |
| 运行循环 | 人工搬运、无限执行、错误重试 | 模型与工具交替执行，预算与退出状态 |
| 工具契约 | 参数乱传、结果难懂、输出撑爆窗口 | Schema、分页、结构化错误、权限声明 |
| 规划 | 做着做着偏离原目标 | 当前步骤、任务边界、验收条件 |
| 上下文 | 关键信息被历史和日志淹没 | 按需读取、结果落盘、裁剪与摘要 |
| 记忆 | 新会话失忆、旧结论被误当事实 | 检查点、来源、适用范围、失效机制 |
| Hook 与权限 | 规则只靠模型自觉 | 执行前拦截、最小权限、沙箱 |
| 验证回路 | “执行过”被当成“完成了” | 外部检查、证据要求、失败反馈 |
| 隔离与编排 | 子任务污染上下文或互相覆盖 | 独立上下文、结果契约、资源归属 |

### 1. 运行循环：把失败送到正确的处理层

“再试一次”只适合少数异常。Harness 要先区分失败类型，再选择处理策略：

| 故障 | Harness 的动作 | 模型应该看到什么 |
| --- | --- | --- |
| 模型接口限流 | 有次数上限的退避重试 | 重试耗尽后的明确原因 |
| 工具参数不合法 | 不执行，返回字段错误 | 如何修正参数 |
| 权限不足 | 保持权限边界并记录拒绝 | 被拒绝的动作与替代路径 |
| 只读查询超时 | 在预算内有限重试 | 超时，而不是“没有数据” |
| 写操作超时 | 查询状态或核对幂等键 | 结果未知，不能声称成功或失败 |
| 连续重复动作 | 检查是否产生新证据，必要时熔断 | 已尝试范围和停止原因 |

除最大步数外，还要限制单次调用时长、任务总时间、工具调用次数、Token 和费用。任一预算耗尽时，Harness 都要写下明确的退出状态并保存进度。

### 2. 工具契约：给下一步提供可用信息

工具是 Harness 提供给模型的一份合约，不能简单地把底层函数原样暴露出去。合约至少要说明：

- 什么时候应该使用；
- 参数格式与允许范围是什么；
- 会不会修改外部状态；
- 能否并发；
- 输出过大时如何分页或落盘；
- 失败属于哪一类，是否值得重试。

例如，日志查询工具不应只返回一段字符串：

```json
{
  "status": "ok",
  "query_scope": {
    "service": "order-service",
    "window": "2026-09-30T10:00:00+08:00/2026-09-30T10:10:00+08:00"
  },
  "items": [
    {"evidence_id": "E1", "message": "downstream timeout"}
  ],
  "truncated": true,
  "next_cursor": "opaque-cursor",
  "artifact_ref": "artifact:logs-001"
}
```

`truncated: true` 会改变结论能说到什么程度。模型可以说“当前返回记录里出现了下游超时”，却没有依据声称“全部日志只有这一类问题”。

错误也需要结构化。`not_found`、`permission_denied`、`timeout` 和 `unknown_result` 对应不同的后续动作。如果把权限不足包装成空数组，模型很可能把“无法读取”误解成“业务对象不存在”。

文件工具同样需要契约：

- `read` 支持 `offset` 和 `limit`，超长时返回下一段位置；
- `bash` 限制输出量，完整内容写入临时文件；
- `edit` 使用精确旧文本与新文本，修改后返回 diff；
- 写入前核对文件版本，防止覆盖并发修改；
- 写入过程采用原子替换，避免留下半个文件。

工具设计还会遇到两个容易被忽略的问题。

第一个是并发修改。模型读完文件、推理几轮再写回去时，文件可能已经被用户或另一个任务改过。`edit` 可以要求旧文本唯一匹配，写入前再核对内容版本或修改时间。原子替换只能避免产生半个文件，不能避免覆盖别人的更新，两者处理的故障不同。

第二个是工具数量。工具越多，定义占用的 Context 越大，名称和适用范围也更容易互相混淆。可以先向模型提供能力目录，命中后再加载完整描述和 Schema。Skill 的按需加载也是同一思路。渐进披露减少了常驻输入，但需要单独评测工具发现率，避免为了节省 Token 把正确工具藏得太深。

命令执行工具的风险更高。检查 shell 命令时，不能只看第一个词：管道、重定向、命令替换以及 `env`、`timeout` 等包装命令都会改变实际执行内容。检查器解析到的命令必须与最终 shell 执行的内容一致；无法确定时，安全策略应拒绝执行或请求人工确认。

工具错误本身也是下一轮输入。只抛出 `failed`，模型只能猜；返回错误类别、失败字段和可行的修正方向，模型才有机会恢复。运行时异常和可修正的业务错误也要分开：前者可能要求任务停止，后者适合转成结构化工具结果交回模型。

#### `read`、`bash`、`edit` 为什么不能只是函数包装

`read` 如果直接返回整个文件，大日志和生成文件很快就会占满窗口。更合适的接口支持 `offset`、`limit` 或行号范围，并在截断时告诉模型剩余内容在哪里。二进制、图片和敏感路径需要走单独的观察能力，不能假装它们都是普通文本。

`bash` 的问题是输出不可预测。一条测试命令可能打印上万行，真正有用的错误只在末尾。Harness 可以限制行数，将完整结果写进临时文件，同时返回退出码、运行时长、截断信息和文件位置。长时间任务还要支持后台运行与增量读取，避免一次工具调用占住整个 Agent Loop。

`edit` 若允许模型重写整个文件，一行修改也会变成几百行生成，成本高且容易夹带无关变化。精确的 `oldText` / `newText` 补丁能缩小写入范围；要求 `oldText` 唯一匹配，可以在文件版本变化时让操作明确失败。修改完成后返回 diff，下一轮才知道实际改了什么。

下面是一种更完整的工具返回结构：

```json
{
  "status": "error",
  "error": {
    "type": "invalid_argument",
    "field": "time_range",
    "message": "结束时间早于开始时间",
    "retryable": true,
    "retry_hint": "交换开始与结束时间，并保留原时区"
  },
  "side_effect": "none",
  "artifact_ref": null
}
```

这里的 `retryable` 表示修改参数后值得再次尝试，不代表原样重放。`side_effect` 告诉运行时是否需要核对外部状态。错误信息的读者是模型，但仍要避免把密钥、Cookie、完整堆栈和内部路径直接放进 Context。

#### 工具描述也是路由规则

模型选择工具时主要依赖名称、描述、Schema 和示例。只写“用于搜索”的描述边界太宽，代码搜索、文档搜索和互联网搜索会互相抢任务。描述需要说明适用场景，也要说明不适用场景。

真实调用示例可以展示参数之间的关系，例如时间范围是否闭区间、分页游标怎样续读、多个过滤条件怎样组合。反例同样重要：查当前天气不该调用历史数据工具，修改文件不该用只读搜索接口。示例的目标是减少选择歧义，而非把所有可能调用都列一遍。

工具粒度也需要权衡。`run_ripgrep` 暴露了底层实现，`search_code` 表达了 Agent 的目标，未来可以替换搜索引擎；但“自动排查并修复所有问题”又太粗，证据和副作用都被藏在黑盒里。一个好工具应该让意图清楚、结果可解释、失败能定位。

#### 渐进披露不是免费优化

几十个工具的完整 Schema 常驻 Context，会同时增加 Token 和选择难度。渐进披露先给能力名称，需要时再加载详细说明，调用前才提供完整 Schema。MCP server、Skill 和文档目录都可以使用这种模式。

代价是发现阶段可能漏掉正确能力。工具检索需要自己的评测集：给出一批真实任务，观察正确工具是否进入候选、错误工具是否被排除，以及检索多花了多少轮。只比较节省的 Token，很容易得到“Context 更短，但任务更差”的优化。

有些中间结果还可以留在执行环境里。比如模型生成一段过滤脚本处理大量 JSON，只将最终统计和原始文件引用返回 Context。这样能显著减少数据搬运，但过滤代码本身必须可检查，查询条件、数据范围和截断情况也要保留，否则模型只看到结论，无法知道哪些证据被丢掉。

#### Shell 工具的检查边界

Shell 是最难安全暴露的工具之一。`timeout 10 <command>`、`env KEY=value <command>`、管道和命令替换都会把真实动作藏在外壳后面。按空格切分字符串并检查第一个单词，无法形成可靠边界。

比较稳妥的方案是优先提供目标明确的工具，例如 `run_tests`、`git_status`、`search_code`，只在确实需要开放命令时使用 Shell。检查器要解析每个管道段和重定向目标，识别包装命令；解析失败时请求批准或拒绝，而不是默认安全。

静态检查仍不是沙箱。即使命令文本通过检查，脚本文件、解释器参数和运行时下载的内容也可能改变行为。高风险任务还需要文件权限、网络目标限制、低权限用户和隔离环境共同约束。

### 3. 规划：保存目标与边界

复杂任务经常在执行过程中偏离原目标。工具结果不断进入 Context，最新的报错会吸走注意力，调查范围也会跟着扩大。

计划用来固定目标、边界和验收条件：

```yaml
goal: 定位指定接口在指定时间段超时的原因
scope:
  allowed: 读取日志、Trace 和指标
  forbidden: 修改线上配置或重启服务
acceptance:
  - 结论关联到可复查证据
  - 区分已验证事实、推测和缺失信息
budget:
  max_tool_calls: 30
  deadline_minutes: 15
stop_when:
  - 达成验收
  - 缺少必要权限或定位标识
  - 预算耗尽
```

重规划需要说明新证据是什么、旧计划哪里不再成立，以及下一步怎样接近验收。没有新证据却持续扩大范围，通常意味着任务已经漂移。

计划不必很重。短任务可以只有当前步骤和验收条件；长任务再增加依赖、阻塞原因和检查点。关键在于把“动作做过”与“目标达成”分开。例如“查过数据库指标”只是一条操作记录，只有观察范围足够、证据支持结论时，才能写成“已排除数据库问题”。

重规划也需要留下理由。如果任务从检查下游延迟切换到检查发布记录，至少要记录是哪条新证据触发了切换。否则上下文压缩或会话恢复后，下一轮很可能重复已经排除的路线。

#### 一个任务怎样从第三步开始跑偏

假设任务只是解决一处合并冲突。Agent 先正确读懂 `base`、`ours` 和 `theirs`，随后发现合并结果触发了 Lint。它开始尝试修改 import、增加忽略注释、调整 Lint 配置，接着又因为依赖问题重装包。每一步单独看都能解释，整条轨迹却早已离开“保留双方正确改动并解除冲突”的目标。

最新错误会天然吸走注意力。工具结果不断追加后，最初目标离当前生成位置越来越远。模型容易把“让眼前命令通过”当成新目标，却忘记这个命令为什么会被运行。

一个简单的 TODO 工具就能改善这种情况。列表保存当前步骤、完成项和阻塞原因，同一时刻只允许少量任务处于 `in_progress`。连续多个工具轮次没有更新计划时，Harness 可以在工具结果后追加提醒。提醒靠近当前生成位置，比只写在很早的系统指令里更容易起作用。

TODO 也有容量限制。七八条短任务还能充当工作记忆，几十条带依赖的任务应该落到状态文件或任务图中。每条任务可以记录 `blockedBy`、验收条件和证据引用，跨会话继续读取。

#### 强目标比长流程更有用

“把接口性能优化一下”无法告诉 Agent 何时结束，也无法判断修改有没有价值。更强的任务约定会写明目标指标、测量方法、允许范围、预算、停止条件和完成证据，例如：

```yaml
goal: 将指定接口的 p95 延迟降到约定阈值以下
measurement: 使用仓库中的 bench 脚本连续运行三次
scope: 只允许修改 service/cache 与对应测试
budget: 最多两轮实现与验证
stop_when:
  - 达到指标且回归测试通过
  - 两轮都没有改善
evidence:
  - 修改前后的同环境结果
  - 相关测试输出
```

阈值必须来自具体任务，这个示例不提供通用数值。重点是让计划围绕可验证目标工作。Agent 可以改变实现路线，却不能自行修改指标、扩大目录或把测量脚本换成更容易通过的版本。

计划模式也有成本。简单修改先写长计划，会增加延迟和阅读负担；开放调查完全不计划，又容易漂移。是否启用计划应看依赖关系、任务时长、失败成本和恢复需求，而不是看改动行数。

### 4. 上下文：它是预算，也是状态的一份视图

Context 是当前决策所需信息的集合，不负责保存永久历史。系统指令、工具定义、文件内容、命令输出和检索结果都会占用窗口。

一个实用的保留顺序是：

1. 当前目标与用户约束；
2. 已确认的决策、理由与关键证据；
3. 最近的操作与结果；
4. 可以重新读取的旧工具输出。

系统最好同时保存两份信息：完整记录用于追溯，本轮 Context 用于决策。

```text
事件记录 + 证据文件 + 任务状态 + 项目知识
                    ↓ 按当前目标筛选
Context = 目标 + 约束 + 当前步骤 + 关键证据 + 必要历史
```

大结果优先落盘，Context 只保留摘要、截断信息和引用。需要压缩时，要留下架构决策及理由、已修改文件、验证状态、待办和精确标识符。模型可以生成摘要，程序仍需校验结构和引用是否存在。

“可重新获取”不等于所有操作都能重跑。历史日志可能过期，环境可能变化，带副作用的命令也不能为了恢复上下文再次执行。

### 上下文为什么会失控

Context 里既有固定开销，也有任务运行时产生的内容。系统指令、工具定义和常驻 Skill 属于固定开销；文件、日志、命令输出和子任务结果会随着执行不断增长。窗口变大只能推迟上限，不能解决注意力稀释、偏向最近内容和中间信息被忽略的问题。

常见的失控形态包括：错误结论进入历史后被反复引用，旧动作持续干扰当前判断，工具太多导致选择混淆，以及并行结果互相冲突。治理时要围绕当前决策组织本轮输入，而非完整复制历史。

一个成本较低的压缩顺序是：先限制工具输出，再把大结果落盘并保留定位信息，随后清理可恢复的旧结果，最后才调用模型生成摘要。摘要属于有损操作，必须保留目标、约束、决策及理由、证据位置、已完成事项和待办。UUID、哈希、端口等精确标识不能让模型自行改写。

固定前缀还会影响缓存。稳定的系统指令和工具定义适合放在前面，动态结果追加在后面。但缓存只影响成本与延迟，不能改善无关信息对推理的干扰。为了命中缓存而保留大量无关工具，可能省了计费却降低任务成功率。

压缩的时机同样重要。调试中途往往依赖零散线索，贸然摘要会迫使 Agent 从头调查。更稳妥的做法是在任务闭合点压缩，并在接近上限之前主动保存证据和状态，而不是等窗口耗尽后仓促收尾。

#### 一条可执行的压缩 Pipeline

可以先把压缩做成确定性流程，再在最后一步使用模型摘要：

1. 单个工具结果超过上限时落盘，只保留路径、范围和短预览；
2. 历史消息太多时保存完整 transcript，Context 保留开头约束和最近交互；
3. 已被消费的旧工具结果替换成一行引用，工具请求与结果必须成对处理；
4. 前三步仍无法控制长度时，再生成结构化摘要；
5. 摘要完成后校验证据引用和精确标识符，再进入下一轮。

工具调用与工具结果不能只删除一半。许多模型 API 要求二者配对，残缺历史会直接导致协议错误。即使 API 接受，模型也会看到一条没有结果的动作，误以为任务仍在执行。

摘要最容易丢的是“为什么”。“决定使用 POST，因为数据量大且请求体不适合放在 URL”若被压成“使用 POST”，后续 Agent 可能把它当成随时可以推翻的个人偏好。决策、理由、证据和适用范围需要一起保留。

#### 状态栏与 Context 的关系

长任务可以在 Context 尾部维护一段短状态栏：当前目标、已经确认的事实、正在执行的步骤、待办和硬约束。它靠近模型下一次输出，能降低早期目标被稀释的问题。

状态栏应由运行时代码根据任务状态生成。让模型自己改状态栏，容易把推测升级成事实，或者在想结束时提前把任务标成完成。模型可以提出更新，程序负责校验允许变化的字段。

压缩后还可能丢失角色和任务身份。运行时可以在恢复或消息极少时重新注入任务 ID、角色、授权范围和证据入口。模型看到的连续性，本质上是 Harness 每一轮重新拼装出来的。

### 5. 记忆：事实、解释与规则不能混在一起

模型不会自行保留跨会话状态。需要长期保存的信息应写进任务检查点、项目文档或 Git。

```json
{
  "task_id": "incident-20260930",
  "revision": 7,
  "status": "waiting_tool",
  "goal": "定位接口超时",
  "current_step": "核对下游耗时",
  "completed_steps": ["确认时间范围", "获取样本调用链"],
  "pending_actions": [
    {"action_id": "action-3", "kind": "read_metrics", "status": "running"}
  ],
  "evidence_refs": ["artifact:trace-001"],
  "open_questions": ["是否存在同时间窗的服务端排队"],
  "next_action": "读取指标结果并更新假设"
}
```

恢复任务时，不能只把这段 JSON 塞回模型。运行时要先核对在途动作是否完成，尤其要处理这种崩溃窗口：工具已经执行成功，结果却还没来得及落盘。

记忆中还要区分：

- “接口返回 403”是观察事实；
- “可能是权限不足”是解释；
- “以后永远不用这个接口”是一条规则。

这三类信息不能在摘要里合并成一句话。重要记忆最好记录来源、时间、适用范围和验证状态；信息过期后需要重新核对。

执行记录、任务状态和长期知识也应该分开保存。执行记录用于审计和恢复，任务状态描述当前目标与下一步，长期知识才用于跨任务复用。把一次故障的临时结论直接升级成永久规则，会让错误归因稳定地影响后续任务。

团队知识适合进入仓库或共享文档，个人偏好可以放在个人记忆中。仓库里的知识能审计、能评审，也能被其他 Agent 使用。入口文档不必塞满所有规则，可以只做目录地图，让具体领域文档按需加载。

一个检查点是否合格，可以用冷启动来验证：新会话能否在很短时间内知道上次完成了什么、为什么这样决定、还缺什么证据，以及下一步准备做什么。只留下聊天摘要而没有在途动作和证据引用，恢复时仍可能重复产生副作用。

#### 跨会话交接需要留下什么

一个可恢复的代码任务通常需要几类交接物：初始化环境的脚本、当前进度、结构化功能清单、验证结果和描述清楚的 Git 提交。新会话不应该依赖上一段聊天才能启动，仓库本身要能解释当前状态。

功能清单适合使用结构化格式。自由文本容易在模型更新进度时顺手改掉验收描述；JSON 或 YAML 可以只开放 `status`、`evidence` 等字段，测试定义和需求文本保持只读。例如：

```json
{
  "feature": "支持失败任务恢复",
  "acceptance": [
    "进程中断后能够恢复任务",
    "已经成功的外部动作不会重复执行"
  ],
  "status": "in_progress",
  "evidence": ["artifact:recovery-test-003"]
}
```

检查点还需要版本号。两个执行者同时更新状态时，可以通过条件写入发现冲突，而不是后写覆盖先写。状态结构升级后也要有迁移逻辑，否则旧任务恢复时会被新运行时误读。

#### 记忆的来源等级与失效

长期记忆至少要区分用户明确陈述、运行时观察、外部验证和模型自我总结。不同类型的权威性与适用范围不同。用户对个人偏好最有权威性；系统是否健康则应以当前监控和实际调用为准。

每条记忆可以记录：

- 原始来源或证据引用；
- 写入时间与最后复查时间；
- 适用的项目、环境和版本；
- 它是事实、假设、偏好还是规则；
- 发现冲突时如何处理。

记忆不是越多越好。过期信息一旦被模型高度信任，会持续产生稳定错误。比如“测试服务暂时不可用”若没有失效时间，几周后的 Agent 仍可能跳过验证。动态状态更适合实时查询，记忆只保存查询入口和当时结论。

#### 项目文档也是 Agent 之间的接口

一个 Agent 的完整轨迹可能有几万字，下一个 Agent 不需要重读全部聊天。经过评审的设计决策、操作步骤和证据索引，是更稳定的交接接口。

入口文档适合保持短小，只说明仓库结构、关键约束和需要按需读取的资料位置。架构决策、领域规则和故障手册分别维护。代码已经能直接表达的信息不必重复写进文档，文档重点保存代码看不出来的原因、边界与跨模块契约。

项目知识和个人记忆不能混在一起。团队约束放在仓库里才能被所有执行者读取、评审和更新；个人偏好可以只对自己的 Agent 生效。把团队规范存在某个人的私有记忆中，会让不同成员的 Agent 对同一个项目持有不同规则。

### 6. Hook 与权限：把口头规则变成执行检查

写在 Prompt 里的“不要删除文件”仍要靠模型遵守。能由程序判断的规则，应放到模型之外：

- 权限规则决定动作是 `allow`、`deny` 还是 `ask`；
- PreTool Hook 在动作发生前检查参数与风险；
- PostTool Hook 在修改后立即运行格式、语法或类型检查；
- 沙箱限制动作真正执行后能够影响的范围；
- CI 在合并前执行最终门禁。

决定一条规则放在哪里时，可以检查四件事：能否写成代码判定、违反一次的代价、出现频率和反馈速度。

| 规则 | 更合适的位置 |
| --- | --- |
| 命名与解释风格 | 项目指令或 Skill |
| 模块 A 不得依赖模块 B | 静态检查与 CI |
| 不得读取特定目录 | 文件权限或沙箱 |
| 某类动作必须得到批准 | 工具执行前的权限检查 |
| 结果必须包含证据 | 输出校验与验收器 |

授权必须来自可信的运行时记录。网页、文档和工具结果里即使写着“用户已经批准”，也只是外部数据；模型总结出的“已获授权”同样无效。执行前要核对获批的动作、目标和关键参数是否与即将执行的操作一致。

Hook 通常挂在几个位置：模型调用前、工具执行前、工具执行后，以及循环准备退出时。执行前 Hook 可以阻止动作；执行后 Hook 只能报告问题，因为副作用已经发生。比如写入代码后立刻运行语法检查，能在错误继续扩散前把反馈送回循环。

Skill、Hook、权限和沙箱的作用也不同：

| 机制 | 解决的问题 | 强制程度 |
| --- | --- | --- |
| Skill / 项目文档 | 告诉模型应该怎样做 | 依赖模型理解与遵守 |
| Hook | 在特定事件前后运行检查 | 命中路径时强制执行 |
| 权限 | 决定动作允许、拒绝还是询问 | 在工具入口形成边界 |
| 沙箱 | 限制动作真正能影响的资源 | 操作系统或执行环境级限制 |

Git worktree 只能隔离代码目录，不等于进程沙箱；容器与虚拟机的隔离强度也不同。设计时要明确自己在防什么，而不是看到“独立目录”就默认风险已经被隔离。

规则还可以按反馈时机分层。类型和 API 误用会影响后续代码，适合尽早由 Linter 报出；提交格式可以在提交前拦截；覆盖率和完整构建适合放在 CI。反馈越晚，Agent 在错误前提上继续工作的时间越长，返工也越多。

另一方面，不知道项目里已有 `formatDate` 属于知识缺失，并不是权限问题。把认知问题全部写成硬规则，会让约束越来越多，却没有补上模型缺少的信息。先判断它是“不知道怎么做”还是“知道但不能被允许这样做”，再选择文档、Skill 或强制机制。

#### Hook 的四个常见挂点

不同产品的名称和协议不一样，抽象位置大致相同：

| 挂点 | 适合做什么 | 做不到什么 |
| --- | --- | --- |
| 用户输入进入模型前 | 补充任务状态、过滤明显无关输入 | 不能验证尚未发生的动作 |
| 工具执行前 | 参数校验、权限判断、危险动作拦截 | 看不到真实执行结果 |
| 工具执行后 | 运行语法检查、记录审计、整理结果 | 已发生的副作用无法自动撤销 |
| 循环准备退出时 | 检查验收证据、要求继续修复 | 不能无限阻止用户取消或预算结束 |

执行后检查越靠近写入动作，反馈越快。模型刚改完 Python 文件就运行语法检查，比几十轮后统一跑 CI 更容易定位哪次修改引入了错误。CI 仍然需要保留，它负责统一环境和最终门禁，两者不是替代关系。

Hook 自身也会失败或超时。安全边界检查不可用时，通常应默认拒绝；格式化建议失败时，可以记录警告并继续。默认行为需要按规则风险配置，不能让所有 Hook 都“失败即放行”或“失败即终止”。

#### `allow`、`ask`、`deny` 的三态权限

只读且范围明确的操作可以直接允许；会修改文件、访问网络或影响外部状态的动作通常需要按目标和参数决定是否询问；删除关键数据、读取禁止目录等动作应直接拒绝。

`deny` 的优先级应高于 `allow`，子任务不能获得超过父任务的权限。一次批准要绑定具体动作和关键参数：用户批准部署到测试环境，不能自动扩展成部署生产；批准发送一封邮件，也不是永久发送权限。

权限还要关注组合风险。单独读取私有文件和单独向外部网站发送公开文本都可能合理，但二者组合后可能形成数据外泄。运行时可以按数据来源、目标域名和工具能力做分区，限制敏感内容从读取工具流向外部发送工具。

#### 权限、沙箱与数据层防线

权限决定动作能不能开始，沙箱限制开始之后能影响多大范围。工作目录和 Git 分支只隔离代码状态，无法阻止进程读取主机上的其他文件。容器共享宿主机内核，microVM 和虚拟机提供更强隔离，但启动和维护成本也更高。

再往下一层是资源本身的权限，例如数据库行级安全、云资源 IAM 和只读凭据。即使模型受提示注入影响，只要请求在数据层被拒绝，损失仍能被限制。最后一道防线要建立在被约束者无法修改的数据和策略上。

安全配置也不能交给同一个 Agent 随意修改。允许执行者编辑自己的 `deny` 列表或关闭沙箱，相当于没有边界。策略变更需要独立权限、审计和必要的人工批准。

### 7. 验证回路：在验证前，“完成”只是一句声明

可靠验收要同时检查结果、执行过程和交付质量：

| 维度 | 代码任务 | 排障任务 |
| --- | --- | --- |
| 结果 | 原问题是否消失，相关测试是否通过 | 是否定位原因，或明确证据为何不足 |
| 过程 | 是否越过授权范围、修改无关文件 | 是否查错环境、扩大时间范围 |
| 质量 | 兼容性、性能、可维护性 | 证据是否支持结论，是否过度推断 |

确定性检查优先交给测试、类型系统、Linter 和契约。需要主观判断的部分，可以交给独立上下文中的评审 Agent 或人工处理。分开实现者与评审者，能减少“自己写、自己判”带来的宽松倾向，独立评审仍代替不了可执行测试。

验收失败后的反馈要能指导下一步，只有一个总分没有多少帮助：

```json
{
  "accepted": false,
  "issues": [
    {
      "criterion": "结论有对应证据",
      "finding": "报告称连接池耗尽，但引用证据只显示下游超时",
      "required_action": "补充直接证据，或将该结论降为待验证假设"
    }
  ]
}
```

如果 Agent 可以修改验收标准、删除失败测试或降低阈值，它就可能通过改考卷让自己通过。验收基线需要独立保存，修改基线也要单独审核。

结束信号和完成状态必须分开。模型没有继续调用工具，可能意味着已经完成，也可能是拒答、输出截断、信息不足或预算焦虑。运行时要先识别响应状态，再根据验收条件决定完成、暂停、失败或继续有限修复。

验证器还需要被验证。可以准备一组已知缺陷：引用了错误环境、把权限不足写成没有异常、修改了禁止路径、结论没有证据，然后确认验证器能否拒绝；同时放入正常样本测误报。一个永远拒绝的验证器也没有实际价值。

连续几轮出现同类失败却没有新证据时，应停止自动修复并保留诊断信息。验证回路利用失败反馈缩小下一轮的搜索空间，同时受修复次数和资源预算限制。

#### 什么证据才能支持“完成”

不同任务需要不同证据。修复代码至少要看到原问题复现用例通过、相关回归测试通过，并确认改动没有越过允许范围。页面任务除了截图，还可能需要点击交互和状态变化；截图能证明视觉结果，不能证明按钮真的连接了业务逻辑。

排障任务的验收方式不同。它可以在证据不足时合理结束，但必须明确已确认事实、仍是推测的候选原因、无法访问的证据以及下一步建议。为了给出唯一根因而把“下游超时”扩写成“数据库连接池耗尽”，属于错误完成。

验证结果最好附带覆盖范围。测试通过了哪些模块，哪些平台没有运行；日志查询覆盖哪个环境和时间段，是否被截断。没有范围的“全部通过”会给读者一种不存在的确定性。

#### 反馈要能驱动修复

综合分数适合做报表，不适合直接反馈给执行 Agent。`72 分` 无法说明下一步该做什么。可操作反馈应指出验收项、实际发现、证据位置和需要采取的动作。

```json
{
  "criterion": "修改不得改变公开 API",
  "finding": "response.userId 被改为 response.user_id",
  "evidence": "contract-test:api-response-12",
  "required_action": "恢复字段名，或提交经过批准的 API 迁移方案"
}
```

修复预算也要有限。Agent 连续两次用相同方法处理同一失败，没有新增证据时，继续运行通常只会产生更多噪声。运行时应记录失败指纹，检测重复轨迹，并在合适时转成 `needs_input` 或明确未完成。

#### 独立评审怎样保持独立

评审 Agent 可以不接收实现者的自我解释，只读取需求、约束、最终 diff 和真实检查结果，减少被“我已经修好了”这种叙述影响。但它仍需要必要背景，否则会把有意设计当成缺陷。

独立上下文不要求一定使用不同模型。不同模型可能带来互补，也可能增加格式差异和成本。更重要的是评审标准、证据输入和产物权限独立。评审者不应悄悄修改实现或降低阈值，再宣布通过。

验证器同样需要回归测试。准备已知好坏样本，测量缺陷检出率和正常样本误报率。模型升级、规则变化或项目结构调整后重新运行，防止一个曾经有效的验证器逐渐变成只会制造循环的门禁。

### 8. 子 Agent 与编排：先隔离上下文

子 Agent 适合独立搜索、读取大量文件或执行专项检查。它在自己的 Context 中处理细节，主任务只接收结论、证据位置、覆盖范围和不确定项。

```yaml
subtask: 核查下游服务是否出现排队
input:
  window: 与主任务一致的时间窗
  evidence: [E1, E2]
  constraints: 只读，不得扩大环境范围
output:
  status: completed / blocked / failed
  findings: 结论与证据引用
  coverage: 实际检查范围
  uncertainties: 尚未排除的问题
  artifacts: 可复查结果位置
```

上下文隔离并不会自动隔离文件系统。多个 Agent 仍可能同时修改一个文件，因此需要明确写入归属、使用独立工作区，或让单一执行者统一落盘。

增加子 Agent 前，先看它能否带回主模型当前拿不到的信息。如果只是让几个相同模型换角色讨论，没有新的工具结果、界面观察或独立证据，通常只会增加 Token 和协调成本。

多 Agent 系统还会引入传统分布式系统的问题：消息重复、结果丢失、共享文件冲突、父任务不知道子任务已经结束，以及子任务递归扩散。需要给消息和结果稳定 ID，明确文件写入归属，设置总预算、并发上限和派生深度。

并行也必须尊重数据依赖。日志检索与配置历史阅读可以同时进行；拿到 Trace ID 之后才能查询调用链，这类步骤不能为了并行而提前。调度依据应来自数据和资源依赖，而不是任务标题看起来是否不同。

短期子任务通常只需要“派发、等待、收结果”。只有确实需要长期驻留、互相通信和持续接单时，邮箱、队友和复杂调度才值得引入。否则系统很可能花大量代码解决自己制造出的协作问题。

#### 隔离与并行是两种不同收益

子 Agent 即使不并行也可能有价值。主任务把“阅读五十个文件并定位认证入口”交给独立上下文，最后只接收结论、覆盖范围和文件位置，可以避免大量中间内容污染主 Context。

并行收益则要求任务互相独立。两个子任务如果都要修改同一文件，执行速度可能更快，合并成本和冲突风险也会增加。可以让子任务只读分析，由单一执行者落盘；或者使用独立工作区，并在合并前检查变更重叠。

#### 子任务的结果要像接口返回

一句“检查过了，没问题”无法支持父任务决策。结果契约至少包含状态、发现、证据、覆盖范围和不确定项。`blocked` 与 `failed` 也要区分：缺少权限属于阻塞，工具实现崩溃属于失败。

父任务派发时要提供最小充分上下文。排查日志至少需要环境、时间窗、服务和只读约束；让子 Agent “看看数据库有没有问题”会得到一个范围不清的结论，即使内容本身看起来专业。

#### 多 Agent 的消息与预算

父子任务之间的消息要有稳定 ID，消费端需要处理重复到达。子任务完成后，结果应持久化，父任务超时或重启后仍能查询。用户在等待期间补充信息时，也要明确由哪个任务接收并怎样传播。

预算必须从根任务向下分配。若每个子 Agent 都拥有完整预算，递归派生会迅速放大 Token、工具调用和外部请求。总预算、单任务预算、并发上限和最大派生深度应由运行时统一控制。

多 Agent 还会放大授权问题。父任务只有只读权限，子任务不能通过换角色获得写权限；用户批准某个子任务执行特定动作，也不能自动授权其他任务复用这次批准。

选择单 Agent 还是多 Agent，最终要看相同任务上的质量、时间和成本。角色数量不是能力指标。一个上下文清楚、工具合适的 Agent，可能比五个互相复述背景的角色更可靠。

## 六、用一次排障任务串起来

用一个排障任务把前面的机制连起来。用户给出的任务是：“某接口在十分钟内大量超时，帮我定位原因。”

### 第一步：建立任务边界

Harness 保存接口、环境、时间范围、只读权限和最大预算。缺少必要定位信息时，状态进入 `needs_input`，模型不应自行猜测环境。

### 第二步：取得现象证据

日志工具返回 E1，显示错误率上升。Trace 工具返回 E2，请求耗时主要集中在下游调用。此时只能确认“下游阶段贡献了较多耗时”，还不足以判断根因来自数据库、网络还是连接池。

### 第三步：把结论拆成假设

模型提出网络等待、下游排队和数据库访问变慢这几个候选原因。Harness 将假设与待查证据写入状态文件。这样即使上下文被压缩或会话重启，系统仍知道每一步在查什么。

### 第四步：正确解释工具失败

数据库指标查询返回 `permission_denied`，说明这个分支还没有被查证，不能据此得出“数据库没有异常”。如果工具只返回空数组，后面的推理很可能从这里开始跑偏。

### 第五步：形成有边界的结论

新证据 E3 显示，同一时间窗内的下游排队时间明显上升。报告可以写“现有证据支持超时主要发生在下游排队阶段”。若要继续追到“某次发布导致排队”，还需要变更时间、实例对照或其他因果证据。

### 第六步：交给验收器

验收器核对每个结论对应的环境、时间和证据，检查是否把无权限误写成正常，以及执行过程有没有越过只读范围。如果证据不足，结果应写明“尚无法定位”并列出缺失信息，不必为了给出唯一答案而编造根因。

这类任务可以没有确定答案，但结论强度必须与证据强度一致。

### 一个更接近生产环境的循环

最小 Loop 只有十几行，真正的运行时需要把状态恢复、授权、结果未知和验收放进同一条控制流。下面是架构伪代码，函数名表达组件职责，不对应某个具体 SDK：

```python
def run_task(task_id, runtime):
    state = runtime.restore_and_reconcile(task_id)
    # 恢复后先核对在途动作，不能直接重放

    while state.is_runnable():
        if runtime.should_stop(state):
            return runtime.stop_and_checkpoint(state)

        runtime.collect_background_results(state)
        context = runtime.build_context(state)
        response = runtime.ask_model_bounded(context)
        runtime.record_response(state, response)

        if response.is_interrupted_or_invalid():
            runtime.handle_model_failure(state, response)
            continue

        if response.needs_user_input():
            return runtime.pause_for_input(state, response)

        calls = response.tool_calls
        if not calls:
            report = runtime.verify(state, response)
            if report.accepted:
                return runtime.complete(state, response, report)
            runtime.record_verification_failure(state, report)
            continue

        for call in calls:
            if runtime.should_stop(state):
                return runtime.stop_and_checkpoint(state)

            decision = runtime.validate_and_authorize(state, call)
            if decision.requires_user:
                return runtime.pause_for_approval(state, call, decision)
            if decision.denied:
                runtime.record_tool_result(state, call.id, decision.result)
                continue

            action = runtime.record_action_intent(state, call)
            result = runtime.execute_with_policy(action)
            runtime.record_tool_result(state, call.id, result)
            runtime.checkpoint(state)
```

这里有四个不能混在一起的职责：模型提出候选动作，`validate_and_authorize` 判断能否执行，`execute_with_policy` 处理超时、幂等和结果状态，`verify` 检查任务是否完成。把它们合并成一句“请谨慎执行并自行测试”，系统就失去了确定的责任边界。

### 常见翻车轨迹分别缺了哪一层

最终回答往往只留下“成功”或“失败”，真正有用的信息藏在中间轨迹里。下面几种表现看起来都像模型能力不足，修复位置却完全不同。

| 翻车轨迹 | 更可能缺少的机制 | 优先检查 |
| --- | --- | --- |
| 同一条命令重复执行，结果没有变化 | 循环与停滞检测 | 是否产生新证据、剩余预算 |
| 日志返回 403，报告写成系统正常 | 工具错误契约 | 权限不足是否被包装成空结果 |
| 修复一个警告时修改了十个无关文件 | 规划与任务范围 | 当前目标、允许目录、diff |
| 长任务后推翻早期架构决定 | Context 与记忆 | 决策理由是否在压缩时丢失 |
| 删除文件前没有请求批准 | 权限与执行前 Hook | 动作分类、资源目标、授权记录 |
| 模型说测试通过，实际没有运行 | 验证回路 | 命令记录、退出码、测试证据 |
| 子任务都说完成，主任务无法合并 | 结果契约与资源归属 | 文件冲突、覆盖范围、不确定项 |

#### 无限重试并不总是循环问题

Agent 反复查询同一个接口，可能是循环没有重复检测，也可能是工具错误没有告诉它查询条件错了。只增加最大步数能让任务更早失败，却没有增加恢复能力。要查看每轮是否获得新证据：参数完全相同、结果指纹相同、计划也没有变化时，才适合熔断。

如果错误是临时限流，运行时可以退避重试，并且不必把每次底层失败都塞给模型。若错误是权限不足，退避没有意义；循环应保留权限边界，向模型返回可用替代路径或暂停请求用户处理。

#### “测试通过”可能只是语言模型的陈述

模型有时会根据代码看起来合理而写出“测试应该通过”，也可能引用很早之前的成功结果。验收器需要关联本次修改后的真实命令、退出码和环境。测试结果要带时间与代码版本，不能拿旧提交的绿灯证明新提交。

测试命令本身也可能只覆盖一小部分。改动影响前后端协议时，只跑单元测试不能证明联调正常。验证计划应从需求推导，而不是看到仓库里哪个命令最容易运行就执行哪个。

#### 修改验收条件是一种特殊变更

Agent 遇到失败测试后，可能认为测试已经过时并顺手修改。这个判断有时是对的，但它改变了考卷，必须单独说明理由并经过评审。实现修改和验收修改混在一个无人检查的步骤里，系统就无法区分修好了功能还是放宽了标准。

同样，关闭 Linter、增加忽略规则、降低覆盖率阈值都可能让命令变绿，却没有解决原问题。验证器应关注检查配置的变化，并要求更高权限或单独批准。

#### 多 Agent 的“都完成了”为什么仍无法交付

两个子任务可能分别正确修改同一个配置文件，合并后却互相覆盖。也可能一个任务升级依赖，另一个仍按旧版本生成代码。各自局部通过并不能推出整体通过。

父任务需要在汇总阶段重新运行集成验收，并检查变更之间的数据依赖。子任务结果中的 `coverage` 和 `artifacts` 能帮助定位冲突，但最终组合产物仍要作为一个新状态重新验证。

## 七、如何判断 Harness 改动是否有效

规则不断累积后，Harness 很容易变得臃肿。新增组件最好对应一次真实失败，并记录它要改善的问题、引入的成本、验证方式和复查时间。

可以用下面的流程评测改动：

1. 从真实失败中整理固定任务集；
2. 冻结旧版与新版 Harness；
3. 固定模型、任务输入和主要环境；
4. 每次只修改一个组件；
5. 对同一道题多次运行，做逐题比较；
6. 记录失败轨迹，而不只看最终总分。

评测时同时关注这些指标：

| 指标 | 说明 |
| --- | --- |
| 任务成功率 | 端到端是否交付 |
| 错误完成率 | 没做成却报告成功的比例 |
| 证据支持率 | 结论是否真的被引用证据支持 |
| 自我恢复率 | 收到有效反馈后能否纠正 |
| 人工介入次数 | 哪些地方仍需要人处理 |
| 单任务耗时与费用 | 资源效率与每个成功任务成本 |
| 权限违规与近失事件 | 是否突破执行边界 |

成功率不变但成本下降，改动仍可能有价值。成功率上升却伴随更多越权，则说明改动没有达到目标。

消融实验会暂时关闭某个组件，观察效果怎样变化。一次分数不变，只能说明当前样本没有检出收益，不能证明组件永远无用。权限和安全机制往往低频但损失很高，也不能因为小样本里“没有出事”就删除。

评测本身也会失真，例如题面泄露答案、模型能读取标准答案、外部服务状态变化、执行环境不一致或裁判标准不稳定。修改 Harness 前，先检查考卷和验证器。

例如要验证“结构化工具错误是否减少错误归因”，任务集不能只有成功查询，还要包含查无数据、权限不足、超时和结果未知。旧版与新版使用相同模型、输入和主要环境，每道题运行多次，再逐题比较：

| 用例 | 旧版表现 | 新版表现 | 结论 |
| --- | --- | --- | --- |
| 查询权限不足 | 宣称没有异常 | 说明证据不可访问 | 错误语义改善 |
| 查询确实无结果 | 重复相同查询 | 检查范围后停止 | 无效调用减少 |
| 正常查询 | 正确定位 | 正确定位但调用翻倍 | 质量不变，成本退化 |

总分可能掩盖这些差异。按任务难度、失败原因和工具类型分层，通常更容易定位 Harness 改动到底改善了什么，又让哪里变差。

### 单次成功和稳定完成不是一回事

很多 Agent 演示只展示一次最好的运行结果。只要允许反复尝试，一个成功率不高的系统也可能偶尔跑出漂亮答案。生产任务关心的却是另一件事：同样的输入再次出现时，系统能否保持结果、权限和成本都在可接受范围内。

可以用两个方向相反的指标理解这种差别。假设一次独立运行的成功概率是 `p`，运行 `k` 次后“至少成功一次”的概率近似为：

```text
Pass@k = 1 - (1 - p)^k
```

它适合描述允许多次采样、最后挑选一个结果的场景。另一种要求是连续 `k` 次全部成功：

```text
Pass^k = p^k
```

这个数字会随运行次数快速下降，更接近定时任务、批量迁移和无人值守流程对稳定性的要求。若单次成功率为 90%，十次里至少成功一次几乎没有悬念，但连续十次全部成功只有大约 35%。这解释了为什么一次 Demo 看起来已经很好，放进每天执行的流水线仍会频繁需要人工收尾。

真实运行并不完全独立：相同服务故障会同时影响多次任务，缓存、限流和上下文污染也会制造相关性。因此公式适合帮助理解，评测仍应保留真实轨迹。至少要记录运行批次、环境版本、模型版本、工具版本和随机性配置，避免把环境差异误当成 Harness 改进。

对有副作用的任务，还要把“成功”拆开。结果正确但多发了一封邮件，不应算完全成功；代码测试通过但修改了禁止目录，也不应与合规完成等价。可以把一次运行拆成任务结果、边界遵守、证据完整和资源消耗四个维度，再根据场景设定门槛。

稳定性评测也不等于无休止地烧 Token。先选择少量高价值用例，每题运行三到五次，已经能发现偶现的格式错误、工具选择漂移和假完成。只有在准备无人值守或改动影响很大时，才需要更大的样本。对比时最好保留逐题结果，而不是只报告一个平均分。

### 从失败轨迹建立回归集

通用基准能比较模型能力，却不一定覆盖自己的工具和业务边界。更实用的评测集通常来自真实失败：把当时的任务输入、允许权限、关键环境和期望证据保存下来，去除敏感数据后变成可重复运行的用例。

每个用例至少需要四部分：任务说明、初始状态、验收器和禁止行为。只保存一句“修复登录问题”无法复现；还要保存相关代码版本、错误样本、允许修改范围，以及怎样判断登录真正恢复。禁止行为也应显式列出，例如不能关闭鉴权、不能改测试来通过、不能访问生产数据。

失败用例需要定期维护。代码接口变化后，旧任务可能无法启动；线上服务状态变化后，原来的正确答案也可能失效。用例失效时应标记原因，而不是让模型在一套坏考卷上不断调参。评测系统本身同样是需要版本控制、Review 和监控的工程资产。

## 八、所有机制都挂在同一个循环上

一个成熟的 Agent 看起来组件很多，主循环本身却没有神秘之处：调用模型、读取候选动作、检查并执行工具、记录结果、继续或退出。规划、Context、权限、验证和子 Agent 都挂在这几个位置上。

```text
恢复任务状态
    ↓
构建本轮 Context ← 计划、记忆、项目知识
    ↓
调用模型，得到回答或工具请求
    ↓
校验参数与授权 ← Hook、权限、沙箱
    ↓
执行工具并记录结果 ← 超时、幂等、审计
    ↓
满足验收吗？ ─ 否 → 反馈具体问题并继续
    │
    是
    ↓
保存最终状态与证据
```

这也是为什么 Harness 往往从痛点中长出来。Agent 反复选错工具，就改工具描述和发现方式；长任务丢决策，就加状态与压缩；改完代码经常假完成，就补测试和验收；出现越权风险，再把权限从文字提醒移到工具入口。

运行时之外，仓库边界、测试稳定性、日志关联、环境复现和文档版本也会影响 Agent 是否容易观察和验证结果。

| 项目缺口 | 对 Agent 的影响 | 更值得先做的改进 |
| --- | --- | --- |
| 测试不稳定 | 无法区分代码回归与环境故障 | 建立可重复的测试入口 |
| 日志没有关联标识 | 多个请求被拼成错误证据链 | 贯通 Trace ID 与时间范围 |
| 架构边界只靠口头约定 | 局部修改破坏整体依赖 | 文档化决策并加机械检查 |
| 启动依赖个人电脑 | 新任务反复卡在配置 | 提供可复现环境与初始化脚本 |
| 业务知识互相矛盾 | 模型随机采用旧结论 | 指定权威来源和维护责任 |

因此团队采用现成 Agent 运行时后，未必需要重写 Loop。很多时候，更有效的投入是完善项目知识、可观测性和验收入口。Agent-friendly 的工程基础同时也会改善人类开发者的体验。

模型增强后，Harness 也不会简单变薄。教模型输出 JSON、修格式的适配层可能消失，但更强的模型会被交付更长、更复杂、权限更高的任务，状态、授权和验证反而更重要。每次模型或项目升级后，都应该重新做消融和回归测试，删除被新能力覆盖的规则，保留仍承担系统责任的机制。

## 九、从最小实现到可维护系统

个人项目没必要一次搭齐所有机制，可以根据风险和遇到的故障逐步增加。

### 阶段一：先跑通，并看清失败

先建立最小循环、少量工具、执行日志和资源预算，记录模型请求、实际执行、工具结果与退出原因。这一阶段先保证失败可以重现，不急着把系统做得完整。

### 阶段二：补工具契约与任务验收

区分参数错误、查无数据、权限不足、超时和结果未知，限制工具输入输出，并给关键任务写清验收条件。有副作用的动作还要同时建立授权与幂等机制。

### 阶段三：让长任务能够恢复

把任务状态和证据放到模型上下文之外，增加检查点、在途调用核对和 Context 裁剪。可以主动模拟程序在几个关键位置崩溃，检查恢复后是否重复执行、丢失证据或错误宣告完成。

### 阶段四：根据瓶颈增加分工

出现独立且耗时的调查分支时，再引入子 Agent；需要长期协作时，再增加消息与调度。每个新角色都要明确输入、输出、权限、预算、超时和失败归属。

### 阶段五：持续评估与清理

把真实失败整理成回归用例，记录每次组件调整的收益与代价。模型或项目升级后，重新检查旧假设，删除已经被模型能力或其他可靠机制覆盖的规则。

从后端工程的视角看，Harness 处理的许多问题并不陌生：

| Agent 机制 | 后端工程中的对应问题 |
| --- | --- |
| 工具调用超时 | 分布式调用的结果未知、幂等与补偿 |
| 检查点恢复 | 持久化、崩溃窗口和状态重放 |
| 多 Agent 通信 | 消息重复、乱序与消费确认 |
| 工具并发 | 数据依赖、锁、限流与资源调度 |
| 权限检查 | 服务端鉴权、资源范围和审计 |
| 完成验证 | 业务验收、质量门禁与基线对比 |

新的难点来自模型本身：动作和解释由概率系统动态生成，所以协议、状态和反馈需要比传统程序更明确。

## 十、什么时候不需要复杂 Harness

原型、一次性脚本和低风险小改动通常不值得搭建重流程。判断一层机制是否值得保留，可以看同一种错误再次出现时，它能否自动挡住问题。

可以先按任务风险做判断：

| 任务情况 | 适合的机制 |
| --- | --- |
| 只读、几分钟完成、结果容易人工检查 | 最小循环、工具限流和明确退出状态 |
| 修改本地代码，但可以用 Git 恢复 | 文件版本检查、测试、diff 与预算 |
| 跨会话长任务 | 检查点、证据引用、Context 治理 |
| 会发送消息、部署或修改线上数据 | 明确授权、幂等、状态核对和审计 |
| 多个独立调查分支 | 子 Agent、结果契约和总预算 |

有些反对意见也值得保留。Harness 代码会变多，维护成本是真实存在的；规则可能限制新模型发挥；评测无法覆盖全部线上情况；多 Agent 可能把单体问题变成协调问题。这些都不是停止建设的理由，但要求每一层机制能说明自己在防什么、代价多大，以及是否仍然有效。

### 几个需要认真回答的反对意见

#### 模型再强一点，还需要 Harness 吗

需要区分两类机制。一类是在弥补模型暂时不擅长的事情，例如反复提醒固定输出格式、把一个长说明拆成模型更容易遵循的小提示。模型能力增强后，这些适配层可能变薄，甚至可以删除。

另一类承担的是系统责任。工具有没有权限、动作是否真的执行、任务如何从崩溃中恢复、邮件是否重复发送、测试是否来自本次代码，这些事实不能只由模型声明。模型越强，用户越可能把更长、风险更高的任务交给它，确定性的状态、权限和验证反而会承受更大压力。

因此升级模型后不应默认保留所有旧规则，也不应把运行时一起扔掉。更合适的做法是重新跑回归集：删除只为旧模型补课的提示，保留负责边界和事实的机制，再观察是否出现新的失败类型。

#### Harness 会不会把模型限制得太死

会，尤其是把某一次成功轨迹硬编码成唯一流程时。模型本来可以先读配置再查日志，Harness 却强制所有任务按十个固定步骤运行，不但浪费调用，还会让新情况无法进入正确分支。

好的边界限制结果和风险，给推理过程留出空间。例如规定“只能读取测试环境、写操作需要批准、结论必须引用证据”，比规定“第一步必须调用 A，第二步必须调用 B”更耐用。确有数据依赖时再约束顺序，例如必须先获得 Trace ID 才能查询调用链。

判断限制是否过度不能只靠感觉。对同一组任务比较完成率、违规率、费用和轨迹长度。如果一条规则没有降低已知风险，却持续增加步骤或阻止合法方案，它就应该被修改或移除。

#### 代码越多，故障点也越多，为什么不让人处理

低频、高风险、每次情况都不同的任务，人工处理可能就是更好的方案。Harness 并不天然优于值班工程师。它的收益来自重复使用：同一类任务次数足够多，工具契约、审计、恢复和验收的成本才能被摊薄。

自动化也会产生运行负担。要维护凭证、SDK、沙箱、评测集和告警，还要处理外部 API 变化。把这些成本算进去后，如果一年只运行几次，做一个清晰的人工 Runbook 可能更划算。可以先让 Agent 只读分析和整理证据，保留最后的执行与审批给人，等失败模式稳定后再扩大权限。

另一种实用做法是设置自动化边界。常规、可恢复、证据清楚的分支由 Agent 完成；无法分类、涉及高价值资源或超过预算的情况转交人工。这样 Harness 的目标不是消灭人在回路中，而是让人只处理真正需要判断和承担责任的部分。

#### 评测覆盖不了线上，分数还有什么意义

评测无法证明系统在所有情况下安全可靠，但它能防止已经见过的问题悄悄回来。单元测试也不能覆盖线上一切，工程团队仍会维护它，因为稳定的回归信号能缩小不确定范围。

离线评测之外，还需要逐步放量、运行审计和事故反馈。高风险动作可以先在模拟环境执行，随后进入只读模式，再允许少量白名单任务。上线后记录停滞率、人工接管、权限拒绝和近失事件，把新失败补回回归集。

不要为了分数训练出“会做考卷”的 Harness。若规则只对几个固定任务有效，换个文件名就失效，说明它记住了题面而没有改善机制。保留一部分从未参与调试的任务，并按时间滚动加入新样本，可以降低这种自我欺骗。

#### 多 Agent 是不是只是在堆 Token

很多时候是。把同一任务发给五个角色，让它们在相同上下文里各写一段观点，再由第六个角色总结，通常只增加成本。角色名字不同不会自动带来新的信息，也不会消除共同盲点。

多 Agent 值得使用的条件通常很具体：任务分支可以并行；每个分支能访问不同工具或独立证据；大量中间材料需要隔离；或者需要一个不能修改实现的独立评审者。缺少这些条件时，单 Agent 配合清晰的检查点往往更简单。

即使满足条件，也要比较端到端收益。并行节省了十分钟，却增加二十分钟合并和复核，就没有实际提速；发现数量上升但误报翻倍，也不能只报“召回更高”。多 Agent 的产物仍需要统一验收，因为几个局部正确的结论可能互相冲突。

### 明天开始做，应该先配哪一层

不需要先画一个完整平台架构。观察手头任务最常出现的症状，从对应位置增加最小机制，再用真实任务验证。

| 当前症状 | 优先增加的机制 | 暂时不用急着做 |
| --- | --- | --- |
| 人工在模型与命令行之间复制结果 | 最小 Loop、执行日志、明确退出状态 | 多 Agent 调度 |
| 工具输出太大，报错又看不懂 | 输入输出 Schema、分页、结构化错误 | 长期记忆 |
| 做着做着改了无关文件 | 当前目标、范围约束、计划与 diff 检查 | 复杂知识图谱 |
| 长任务忘记早期决定 | 外部状态、检查点、Context 压缩摘要 | 无限上下文 |
| 写操作可能重复或越权 | 服务端权限、执行前批准、幂等键 | 让 Prompt 反复提醒小心 |
| 模型说完成但没有证据 | 可执行验收、命令记录、独立检查 | 再加一个负责总结的角色 |
| 有多个独立且耗时的调查分支 | 只读子任务、结果契约、资源归属 | 自由递归派生 |
| 同类失败反复出现 | 固定回归用例与逐题轨迹比较 | 只看一次总分 |

如果只能用一天做第一个版本，可以按以下顺序推进：

1. 选一个真实、可重复、失败代价不高的任务，不从万能助手开始；
2. 记录模型输入、工具请求、真实执行结果、退出原因和耗时；
3. 为每个工具定义成功、无数据、参数错误、权限不足、超时和结果未知；
4. 写一个模型无法自行修改的验收器，并保存验收证据；
5. 给循环设置步数、时间、费用和重复动作上限；
6. 连续运行几次，把第一类重复失败变成下一项工程改动。

第二天是否继续增加组件，要看第一天的轨迹。若主要问题是工具选错，先改工具描述和发现方式；若结果正确但经常越权，先强化权限；若总在长任务后丢失目标，再做状态和 Context。按失败顺序建设，通常比照着某个成熟产品抄齐功能更快得到可靠系统。

### 一份最小上线检查表

准备把 Agent 从本地 Demo 放进真实工作流前，可以逐项确认：

- 任务有明确的完成、失败、等待输入和取消状态；
- 每个有副作用的工具都有服务端鉴权，并能识别目标资源；
- 超时后不会未经核对就重放未知结果的动作；
- Context 可以追溯来源，旧信息不会无期限保持最高优先级；
- 最终结论引用了本次运行产生的证据；
- 验收器无法被执行 Agent 随意关闭或改低阈值；
- 日志能串起模型请求、工具调用、授权决定和状态变化；
- 达到预算、重复动作或停滞阈值后会安全停止；
- 用户中途取消、程序崩溃和重启都做过演练；
- 至少有一组来自真实失败的回归任务，并保留逐题轨迹。

这份清单不要求每个个人项目都做成企业级平台。它的作用是暴露被 Demo 隐藏的问题。只读小工具可以把许多项目标为“不适用”；会部署、发消息或改线上数据的 Agent，则不能跳过权限、幂等和恢复。

最容易走偏的是从名词出发搭平台。更实际的顺序是从失败轨迹出发：

1. 先记录模型看到了什么、调用了什么、为什么退出；
2. 找到重复发生且代价最高的一类失败；
3. 判断它属于信息、工具、状态、权限还是验收问题；
4. 在对应挂点增加最小机制；
5. 用同一组任务比较改动前后的效果、成本与风险；
6. 没有收益的规则及时删除，低频高损失的安全边界单独评估。

模型升级后，一部分“教模型如何做事”的提示会失去价值。状态持久化、权限隔离、外部验证和不可逆操作前的确认则更稳定。Harness 应当允许裁剪，每个组件都能独立关闭、比较和删除。

规则放进 Prompt 还是变成程序机制，取决于它需不需要模型灵活判断。需要判断的规则适合写进文档和 Skill；模型不应有机会违反的规则，更适合交给类型系统、Linter、权限、Hook 与 CI。

持续改进 Harness 的方式，是把重复出现的问题变成工程资产：

- 缺失的信息变成项目文档与观察接口；
- 反复出现的 Review 意见变成静态检查；
- 看不见的失败变成结构化信号；
- 口头提醒变成真正的执行边界；
- 线上事故变成可以重复运行的评测用例。

Agent 出错后，除了修正当前产物，还要回到运行环境中寻找缺失的能力、边界或反馈。随着这些机制逐渐齐全，工程师可以少参与具体步骤，把精力放在目标、协议、约束和验证回路上。

我目前对 Harness Engineering 的理解是：让模型负责需要创造和判断的部分，把权限、状态和验收尽可能交给确定性的系统。

### 术语速查

| 术语 | 含义 |
| --- | --- |
| Agent Loop | 模型与工具交替执行的主循环 |
| Tool contract | 工具的输入、输出、权限、副作用与错误语义 |
| Context | 当前一次模型调用可见的全部信息 |
| Checkpoint | 可用于恢复任务的结构化状态快照 |
| Hook | 在模型或工具生命周期特定位置执行的程序检查 |
| Verification | 用外部证据判断任务是否达到验收条件 |
| Evaluation harness | 批量运行任务、记录轨迹并评分的评测系统 |
| Agent harness | 让 Agent 实际运行、受控执行并持续改进的系统 |
