大模型擅长生成下一段文字，但一个能持续完成任务的 Agent 还需要更多东西：它要读取文件、调用工具、保存状态、处理失败，并在真正完成后停下来。

这些位于模型之外、负责让任务稳定推进的程序与配置，可以统称为 **Agent Harness**。如果把模型看作发动机，Harness 就是方向盘、仪表盘、刹车和道路规则。发动机决定能力上限，Harness 决定这份能力能否被可靠地使用。

## Prompt、Context 和 Harness 的区别

这三个概念不是互相替代的三代技术，而是由内向外的三层系统：

| 层次 | 解决的问题 | 常见故障 |
| --- | --- | --- |
| Prompt | 如何表达当前指令 | 回答偏离目标 |
| Context | 这一次调用应该看到什么 | 信息不足或噪声太多 |
| Harness | 整个任务如何持续运行 | 越权、失控、假完成、状态丢失 |

Prompt 是一次调用中的指令，Context 是模型本轮能看到的全部信息，而 Harness 会根据模型的输出执行动作，再把环境结果组织成下一轮 Context。换句话说，Harness 每运行一轮，都在为下一轮生产上下文。

## 一个 Agent 最小需要什么

最小的 Agent 循环并不复杂：

```text
把任务放入消息列表

在最大步数以内循环：
  调用模型
  如果模型给出最终答案，则结束
  校验模型请求的工具和参数
  执行工具
  将结果写回消息列表

超过步数上限则停止
```

模型只负责判断下一步做什么，真正的文件读写、命令执行和结果回传都由运行时完成。一个工程化 Harness，就是不断补齐这段循环没有覆盖的异常、边界和反馈机制。

这里有一个很重要的区分：**循环结束不等于任务成功**。生产系统至少要区分 `completed`、`needs_input`、`failed`、`cancelled` 和 `budget_exhausted`。对于有副作用的调用，还可能出现 `result_unknown`：请求已经发出，但客户端在拿到结果前超时，远端究竟有没有执行成功并不确定。

## Harness 的八个组成部分

### 1. 运行循环

循环负责连接“思考”和“行动”：接收模型请求、执行工具、返回结果，再判断是否继续。它还必须有最大轮次、超时、费用上限和连续失败熔断。只靠模型说“我完成了”来停止，本质上仍然是一个没有可靠退出条件的循环。

不同失败应由不同层处理：模型服务限流可以有限重试；参数错误应返回给模型修正；权限拒绝不能通过重试放宽；预算耗尽则必须保存进度并停止。尤其是发消息、支付、部署这类动作，超时后不能直接重放，需要幂等键或状态查询。模型协议中的 `call_id` 只负责关联请求与结果，不等于业务幂等键。

### 2. 工具契约

工具不是简单地把底层函数暴露给模型，而是一份面向模型的合约。一个合格的工具需要说明：

- 什么时候应该使用；
- 参数允许什么、不允许什么；
- 成功结果如何精简返回；
- 失败后是否可以重试；
- 是否会修改数据，以及是否能够并发执行。

例如读取大文件时必须支持分页和截断；命令输出过长时应保存到文件，只返回摘要与路径；编辑文件时应尽量基于精确片段修改，并把 diff 返回给模型确认。

工具错误也不应只是一句 `failed`。错误信息要告诉模型失败类型、关键原因和可行的下一步，因为每一次工具结果都会成为下一轮提示的一部分。

工具返回还应明确区分 `not_found`、`permission_denied`、`timeout` 和 `unknown_result`。如果把“没有权限读取”包装成空数据，模型很可能进一步得出“业务对象不存在”的错误结论。Harness 不仅要把动作执行出来，还要确保模型能正确理解执行结果。

### 3. 计划与任务状态

复杂任务容易在工具调用中逐渐偏离最初目标。计划的作用不是替模型决定每一步，而是让它始终知道：当前目标是什么、已经做了什么、接下来做什么。

短任务可以维护一份小型 Todo；长任务则应把计划、依赖关系和阻塞项写入文件。任务本身也需要明确边界：允许修改的范围、禁止事项、验收证据和停止条件。

### 4. 上下文治理

上下文窗口更像预算，而不是永久历史。系统指令、工具定义、文件内容和命令输出都会消耗它。窗口越大，也不代表所有内容都应该塞进去。

一个实用的优先级是：

1. 当前目标和用户约束；
2. 已确认的架构决策与关键证据；
3. 最近的操作与结果；
4. 可重新读取的旧工具输出。

大段日志和文件应优先落盘，只在对话中留下摘要与位置；真正需要压缩历史时，要保留决策理由、已修改文件、验证状态和未完成事项。不要在排查问题进行到一半时压缩，因为最容易被丢掉的往往正是尚未串起来的线索。

更准确地说，Context 应该是完整状态的一份**可控视图**。完整事件、原始证据和任务状态用于追溯；本轮上下文只装当前目标、有效约束、关键证据和近期交互。这样，“清理上下文”就不等于“删除历史”，模型需要细节时仍能通过引用重新读取。

### 5. 外部记忆

模型本身没有跨会话记忆。对话结束后仍需要保留的内容，应写进仓库里的文档、状态文件和 Git 提交。

项目知识与个人偏好要分开：团队都应遵循的架构决策、运行方式和约束进入仓库；个人使用习惯才进入个人记忆。记录事实时还应保留来源，避免把模型的一次猜测固化成下一次会话里的“已知事实”。

长期状态里还要分清三类内容：工具观察到的事实、模型给出的解释，以及系统最终采用的规则。例如“接口返回 403”是事实，“可能是权限不足”是解释，“以后永远不要调用这个接口”则是一条新规则。三者不能在摘要时被压成同一句话。

### 6. 权限、Hook 与隔离

写在提示词里的“不要删除文件”只是一条建议，不能充当安全机制。能够由程序判断的规则，应尽量放到模型之外：

- 权限规则决定某类动作是允许、拒绝还是需要确认；
- PreTool Hook 在动作发生前拦截危险命令；
- PostTool Hook 在修改后立即运行格式、语法或类型检查；
- 沙箱限制即使动作被执行，最多能影响哪些资源。

安全规则还要建立在模型无法自行修改的层面。否则让 Agent 自己维护禁止列表，就像让被检查者自己决定检查标准。

授权也必须来自可信的运行时记录。网页、文档或工具结果里即使写着“用户已经同意”，也只是不受信任的数据；模型自己总结出的“已获批准”同样不是批准。真正执行前，系统需要核对用户授权的动作、目标和关键参数是否与即将执行的操作一致。

### 7. 验证回路

在验证之前，“已经修复”只是一句声明。可靠的完成状态至少要能回答：

- 产生了哪些明确改动；
- 运行了哪些相关测试；
- 测试结果是否成功；
- 有没有无关修改；
- 无法验证的部分是什么。

验证最好同时覆盖结果、过程和质量。确定性的检查交给测试、类型系统、Linter 和契约；需要主观判断的部分，可以交给独立的评审 Agent 或人工检查。实现者和评审者应尽量使用独立上下文，避免“自己写、自己判”带来的宽松倾向。

这三个维度缺一不可：结果验证任务是否办成，过程验证有没有越过授权范围，质量验证性能、可维护性和代码风格是否达标。测试全绿只能证明测试覆盖到的部分，不能自动证明需求全部满足。

### 8. 子 Agent 与编排

子 Agent 的首要价值是上下文隔离，其次才是并行。例如为了确认项目使用哪套测试框架，子 Agent 可以读取多个配置文件，最终只把一句结论返回主会话，中间过程不会长期占用主上下文。

但子 Agent 并不天然等于沙箱。它可能仍与主 Agent 共享进程、工作目录和文件改动。并发规模较大时，需要进一步使用独立工作区、分支甚至容器隔离。

是否需要增加一个 Agent，可以问一个简单问题：它能否带回主模型当前拿不到的新信息？如果只是让两个相同模型换个角色反复讨论，往往只增加成本，并没有增加证据。

## 从哪里开始搭建

对个人项目来说，不需要一次把所有机制配齐。更合理的顺序是：

1. 先限制高风险动作，并设置最大步数和超时。
2. 把高频、可判定的规则从提示词迁移到 Linter、Hook 或测试。
3. 建立统一验收命令，让“完成”必须附带测试与检查结果。
4. 把关键决策、进度和未验证事项写入项目文件。
5. 保存一组真实失败案例，每次只修改一个 Harness 组件并重新评测。

只有当单 Agent 的运行循环、状态和验证已经稳定，再考虑多 Agent 编排。复杂架构无法弥补基础反馈回路的缺失，反而会让问题更难定位。

## 怎么判断一次改动有没有用

Harness 很容易越做越复杂，因此每个新增机制都应该对应一个真实失败，并回答三个问题：它准备改善什么、付出了什么成本、如何证明有效。

比较时尽量固定模型、任务集合和执行环境，每次只改变一个组件。除了成功率，还要同时记录错误完成率、人工介入次数、耗时、费用和权限违规。成功率不变但成本下降可能仍有价值；成功率提升但越权增多，则不能视为改进。

可以通过消融实验暂时关闭某个组件，观察它对结果的影响。但一次分数不变，只能说明当前样本没有检出收益，不能证明组件永远无用，尤其不能据此删除低频高损失的安全机制。

从后端工程视角看，Harness 并不是一套完全陌生的技术：工具超时对应分布式调用的结果未知，检查点对应故障恢复，多 Agent 通信对应异步消息，权限检查对应服务端鉴权，完成验证对应质量门禁。模型带来的新难点，是动作和解释都由概率系统动态生成，因此协议、状态与反馈必须设计得更加明确。

## Harness 不是越厚越好

原型、一次性脚本和低风险的小改动，往往不值得搭建重型流程。Harness 的意义来自复用：同一种错误第二次出现时，系统能否自动避免它。

模型升级后，部分“教模型如何做事”的规则会失去价值；但状态持久化、权限隔离、独立验证和不可逆操作前的确认不会消失。好的 Harness 应当可以裁剪，每个组件都能单独关闭、比较和删除。

最终目标不是让规则越来越多，而是把重复出现的问题逐渐变成可靠机制：缺失的信息变成文档，反复出现的评审意见变成检查规则，看不见的失败变成可观测信号，口头提醒变成真正的执行边界。

当 Agent 做错时，与其每次手动修改它的产物，不如修正让它工作的环境。工程师也由此从每一步都参与执行，转向设计目标、边界与反馈回路。
