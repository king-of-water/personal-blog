大模型擅长生成下一段文字，但一个真正能完成任务的 Agent 还需要读取环境、调用工具、保存状态、处理失败，并在满足验收条件后停下来。

这些位于模型之外、让任务能够持续且受控地推进的程序与配置，可以统称为 **Agent Harness**。如果把模型看作发动机，Harness 就是方向盘、仪表盘、刹车和道路规则。模型决定能力上限，Harness 决定这份能力能否被稳定地使用。

这篇文章从最小 Agent Loop 出发，逐层解释一个 Harness 如何长成可靠系统。重点不是记住八个名词，而是建立一条分析路径：**失败发生在哪里，应该由什么机制处理，又该如何验证这个机制真的有效。**

## 一、先分清模型、Prompt、Context 和 Harness

这三个概念不是互相替代的三代技术，而是三个不同层次的对象。

| 层次 | 关注的问题 | 典型故障 |
| --- | --- | --- |
| Prompt | 当前指令如何表达 | 回答偏离目标、格式不符合要求 |
| Context | 本次调用实际能看到什么 | 信息缺失、噪声过多、关键证据被淹没 |
| Harness | 整个任务如何持续执行并接受约束 | 越权、无限重试、状态丢失、假完成 |

Prompt 是 Context 的一部分。Context 还包括对话历史、工具定义、检索结果、文件内容和环境反馈。Harness 则位于更外层：它负责选择哪些信息进入 Context，执行模型提出的动作，再把执行结果组织成下一轮 Context。

![Prompt、Context 与 Harness 的层次关系](/images/posts/harness-layers.svg)

模型在一次调用中只负责输出回答或候选动作。真正的执行权一直掌握在 Harness 手里：它决定动作能否执行、以什么权限执行、结果怎样保存，以及任务是否真的完成。

可以把一个 Agent 粗略写成：

```text
Agent = Model + Harness
```

这个表达式的价值，是把很多“模型不够聪明”的问题重新拆成工程问题：

- 模型没有看到图片，应该补观察通道，而不是继续改 Prompt；
- 工具只返回 `failed`，应该改错误契约，而不是让模型多猜几次；
- 模型说“已完成”但没有测试证据，应该补验收回路，而不是要求它更认真；
- 新会话忘记进度，应该持久化状态，而不是指望模型自己记住。

## 二、从最小 Agent Loop 开始

早期使用聊天模型解决问题时，人其实承担了 Harness 的角色：复制报错、执行代码、把结果贴回对话框，再判断是否继续。把这套人工往返搬进程序，就得到最小 Agent Loop。

```python
def run_agent(task, tools):
    messages = [make_user_message(task)]

    for step in range(MAX_STEPS):
        response = ask_model(messages, tools)
        messages.append(response)

        calls = read_tool_calls(response)
        if not calls:
            return read_final_text(response)

        for call in calls:
            name, args, call_id = validate_call(call)
            result = TOOL_IMPL[name](**args)
            messages.append(make_tool_result(call_id, result))

    raise RuntimeError("Agent 超过最大步数，已停止")
```

这段代码里，模型只出现在 `ask_model`。其余工作都属于 Harness：保存消息、校验参数、执行工具、回传结果以及限制最大步数。

它可以运行，但距离可靠还很远。至少有这些问题没有解决：

- 模型拒答、输出截断或接口超时时怎么办；
- 工具参数不合法、工具不存在或权限不足怎么办；
- 写操作超时后，远端究竟有没有执行成功；
- 模型不再调用工具，是已经完成还是需要用户补充信息；
- 进程崩溃后，如何知道上次执行到了哪里；
- 模型说测试通过，依据来自哪里。

所以生产系统不能只维护一串 `messages`，还要维护独立的任务状态。

```text
RUNNING → WAITING_TOOL → RUNNING
RUNNING → VERIFYING → COMPLETED
                   → RUNNING      # 验证失败，仍可修复
RUNNING → NEEDS_INPUT
RUNNING → CANCELLED
RUNNING → BUDGET_EXHAUSTED
WAITING_TOOL → RESULT_UNKNOWN     # 副作用已发出，但结果未确认
```

![Agent Harness 运行循环](/images/posts/harness-runtime.svg)

这里最容易忽略的是 `RESULT_UNKNOWN`。一次只读查询超时，通常可以有限重试；但发送通知、支付、部署等动作超时，远端可能已经成功。此时直接重放会制造重复副作用。需要使用业务幂等键、执行回执或状态查询来核对，而模型协议中的 `call_id` 只负责消息关联，不能代替业务幂等键。

## 三、Harness 的八层机制

下面八层不是固定产品清单。每一层都对应一种真实故障，项目缺什么就补什么。

| 层 | 防止的问题 | 最小机制 |
| --- | --- | --- |
| 运行循环 | 人工搬运、无限执行、错误重试 | 模型与工具交替执行，预算与退出状态 |
| 工具契约 | 参数乱传、结果难懂、输出撑爆窗口 | Schema、分页、结构化错误、权限声明 |
| 规划 | 做着做着偏离原目标 | 当前步骤、任务边界、验收条件 |
| 上下文 | 关键信息被历史和日志淹没 | 按需读取、结果落盘、裁剪与摘要 |
| 记忆 | 新会话失忆、旧结论被误当事实 | 检查点、来源、适用范围、失效机制 |
| Hook 与权限 | 规则只靠模型自觉 | 执行前拦截、最小权限、沙箱 |
| 验证回路 | “执行过”被当成“完成了” | 外部检查、证据要求、失败反馈 |
| 隔离与编排 | 子任务污染上下文或互相覆盖 | 独立上下文、结果契约、资源归属 |

### 1. 运行循环：把失败送到正确的处理层

不能把所有异常都处理成“再试一次”。不同失败需要不同策略：

| 故障 | Harness 的动作 | 模型应该看到什么 |
| --- | --- | --- |
| 模型接口限流 | 有次数上限的退避重试 | 重试耗尽后的明确原因 |
| 工具参数不合法 | 不执行，返回字段错误 | 如何修正参数 |
| 权限不足 | 保持权限边界并记录拒绝 | 被拒绝的动作与替代路径 |
| 只读查询超时 | 在预算内有限重试 | 超时，而不是“没有数据” |
| 写操作超时 | 查询状态或核对幂等键 | 结果未知，不能声称成功或失败 |
| 连续重复动作 | 检查是否产生新证据，必要时熔断 | 已尝试范围和停止原因 |

除了最大步数，还应考虑单次调用超时、任务总截止时间、工具调用次数、Token 和费用预算。任何一项触发都应该形成明确退出状态，并保存当前进度。

### 2. 工具契约：让结果真正指导下一步

工具不是把底层函数直接暴露给模型，而是一份面向模型的合约。它至少要回答：

- 什么时候应该使用；
- 参数格式与允许范围是什么；
- 会不会修改外部状态；
- 能否并发；
- 输出过大时如何分页或落盘；
- 失败属于哪一类，是否值得重试。

一个日志查询工具，不应该只返回一段字符串：

```json
{
  "status": "ok",
  "query_scope": {
    "service": "order-service",
    "window": "2026-09-30T10:00:00+08:00/2026-09-30T10:10:00+08:00"
  },
  "items": [
    {"evidence_id": "E1", "message": "downstream timeout"}
  ],
  "truncated": true,
  "next_cursor": "opaque-cursor",
  "artifact_ref": "artifact:logs-001"
}
```

`truncated: true` 会直接改变结论强度：模型只能说“当前返回记录里出现了下游超时”，不能说“全部日志只有这一类问题”。

错误也需要结构化。`not_found`、`permission_denied`、`timeout` 和 `unknown_result` 不是一回事。如果把权限不足包装成空数组，模型很可能把“无法读取”错误解释成“业务对象不存在”。

文件工具同样需要契约：

- `read` 支持 `offset` 和 `limit`，超长时返回下一段位置；
- `bash` 限制输出量，完整内容写入临时文件；
- `edit` 使用精确旧文本与新文本，修改后返回 diff；
- 写入前核对文件版本，防止覆盖并发修改；
- 写入过程采用原子替换，避免留下半个文件。

### 3. 规划：保存目标，而不是限制全部路径

复杂任务最常见的问题不是每一步都错，而是做着做着忘了最初要解决什么。工具结果不断进入 Context，最新报错会吸走注意力，任务范围随之扩大。

计划的作用是保存目标与边界：

```yaml
goal: 定位指定接口在指定时间段超时的原因
scope:
  allowed: 读取日志、Trace 和指标
  forbidden: 修改线上配置或重启服务
acceptance:
  - 结论关联到可复查证据
  - 区分已验证事实、推测和缺失信息
budget:
  max_tool_calls: 30
  deadline_minutes: 15
stop_when:
  - 达成验收
  - 缺少必要权限或定位标识
  - 预算耗尽
```

合理的重规划应说明：出现了什么新证据、旧计划哪里不成立、下一步为什么更接近验收。没有新证据却不断扩大范围，通常就是任务漂移。

### 4. 上下文：它是预算，也是状态的一份视图

Context 不是永久历史，而是当前决策需要的信息集合。系统指令、工具定义、文件内容、命令输出和检索结果都会消耗窗口。

一个实用的保留顺序是：

1. 当前目标与用户约束；
2. 已确认的决策、理由与关键证据；
3. 最近的操作与结果；
4. 可以重新读取的旧工具输出。

更准确地说，系统应保存两份信息：完整记录用于追溯，本轮 Context 用于决策。

```text
事件记录 + 证据文件 + 任务状态 + 项目知识
                    ↓ 按当前目标筛选
Context = 目标 + 约束 + 当前步骤 + 关键证据 + 必要历史
```

大结果优先落盘，在 Context 中保留摘要、截断信息和引用。必须摘要时，应保留架构决策及理由、已修改文件、验证状态、待办与精确标识符。摘要可以由模型提出，但程序仍应校验结构和引用是否存在。

不要把“可重新获取”理解成所有内容都能重跑。历史日志可能过期，环境可能变化，带副作用的命令更不能为了恢复上下文而再次执行。

### 5. 记忆：事实、解释与规则不能混在一起

模型没有跨会话状态。需要长期保留的信息，应写入任务检查点、项目文档和 Git，而不是依赖聊天历史。

```json
{
  "task_id": "incident-20260930",
  "revision": 7,
  "status": "waiting_tool",
  "goal": "定位接口超时",
  "current_step": "核对下游耗时",
  "completed_steps": ["确认时间范围", "获取样本调用链"],
  "pending_actions": [
    {"action_id": "action-3", "kind": "read_metrics", "status": "running"}
  ],
  "evidence_refs": ["artifact:trace-001"],
  "open_questions": ["是否存在同时间窗的服务端排队"],
  "next_action": "读取指标结果并更新假设"
}
```

恢复时不能只把这段 JSON 塞回模型。运行时需要先核对在途动作是否已经完成，尤其要处理“工具成功执行，但结果尚未来得及落盘时进程崩溃”的窗口。

记忆中还要区分：

- “接口返回 403”是观察事实；
- “可能是权限不足”是解释；
- “以后永远不用这个接口”是一条规则。

三者逻辑距离很远，不能在摘要里合并成一句话。每条重要记忆最好带来源、时间、适用范围和验证状态；过期信息应重新核对，而不是永久生效。

### 6. Hook 与权限：把口头规则变成执行检查

写在 Prompt 里的“不要删除文件”只是一条建议。能够由程序判断的规则，应该落到模型之外：

- 权限规则决定动作是 `allow`、`deny` 还是 `ask`；
- PreTool Hook 在动作发生前检查参数与风险；
- PostTool Hook 在修改后立即运行格式、语法或类型检查；
- 沙箱限制动作真正执行后能够影响的范围；
- CI 在合并前执行最终门禁。

一条规则放在哪里，可以问四个问题：能否写成代码判定、违反一次的代价多高、多久出现一次、需要多快反馈。

| 规则 | 更合适的位置 |
| --- | --- |
| 命名与解释风格 | 项目指令或 Skill |
| 模块 A 不得依赖模块 B | 静态检查与 CI |
| 不得读取特定目录 | 文件权限或沙箱 |
| 某类动作必须得到批准 | 工具执行前的权限检查 |
| 结果必须包含证据 | 输出校验与验收器 |

授权必须来自可信的运行时记录。网页、文档和工具结果里即使写着“用户已经批准”，也只是外部数据；模型自己总结出的“已获授权”同样不能算数。执行前应核对批准的动作、目标和关键参数是否与即将执行的操作一致。

### 7. 验证回路：在验证前，“完成”只是一句声明

可靠验收至少包含三层：

| 维度 | 代码任务 | 排障任务 |
| --- | --- | --- |
| 结果 | 原问题是否消失，相关测试是否通过 | 是否定位原因，或明确证据为何不足 |
| 过程 | 是否越过授权范围、修改无关文件 | 是否查错环境、扩大时间范围 |
| 质量 | 兼容性、性能、可维护性 | 证据是否支持结论，是否过度推断 |

确定性检查应优先交给测试、类型系统、Linter 和契约。需要主观判断的部分，可以由独立上下文中的评审 Agent 或人工完成。实现者和评审者分开，能降低“自己写、自己判”的宽松倾向，但独立评审仍不能替代可执行测试。

验收失败时，反馈要能指导下一步，而不是只给一个总分：

```json
{
  "accepted": false,
  "issues": [
    {
      "criterion": "结论有对应证据",
      "finding": "报告称连接池耗尽，但引用证据只显示下游超时",
      "required_action": "补充直接证据，或将该结论降为待验证假设"
    }
  ]
}
```

如果 Agent 能修改验收标准、删除失败测试或降低阈值，它就可能通过改变考卷获得通过。验收基线应独立保存，变更验收本身需要单独审核。

### 8. 子 Agent 与编排：隔离是第一价值

子 Agent 适合独立搜索、读取大量文件和执行专项检查。它在自己的 Context 中处理细节，主任务只接收结论、证据位置、覆盖范围和不确定项。

```yaml
subtask: 核查下游服务是否出现排队
input:
  window: 与主任务一致的时间窗
  evidence: [E1, E2]
  constraints: 只读，不得扩大环境范围
output:
  status: completed / blocked / failed
  findings: 结论与证据引用
  coverage: 实际检查范围
  uncertainties: 尚未排除的问题
  artifacts: 可复查结果位置
```

上下文隔离不等于文件系统隔离。多个 Agent 仍可能修改同一个文件，需要明确写入归属、使用独立工作区，或由单一执行者统一落盘。

是否值得增加一个 Agent，可以先问：它是否能带回主模型当前拿不到的新信息？如果只是让多个相同模型换角色讨论，却没有新的工具结果、界面观察或独立证据，往往只增加 Token 和协调成本。

## 四、用一次排障任务串起来

假设用户给出任务：“某接口在十分钟内大量超时，帮我定位原因。”

### 第一步：建立任务边界

Harness 保存接口、环境、时间范围、只读权限和最大预算。缺少必要定位信息时，状态进入 `needs_input`，而不是让模型猜环境。

### 第二步：取得现象证据

日志工具返回 E1：错误率上升；Trace 工具返回 E2：请求耗时主要出现在下游调用。此时只能确认“下游阶段贡献了较多耗时”，还不能直接断言数据库、网络或连接池是根因。

### 第三步：把结论拆成假设

模型提出三个候选：网络等待、下游排队、数据库访问变慢。Harness 将假设与待查证据写入状态文件，确保上下文压缩或会话重启后仍知道每一步调查的目的。

### 第四步：正确解释工具失败

数据库指标查询返回 `permission_denied`。这表示该分支尚未查证，不能被解释成“数据库没有异常”。如果工具只返回空数组，整个推理链可能从这里开始跑偏。

### 第五步：形成有边界的结论

新的证据 E3 显示同一时间窗内下游排队时间明显上升。报告可以写“现有证据支持超时主要发生在下游排队阶段”。如果要进一步声称“某次发布导致排队”，还需要变更时间、实例对照或其他因果证据。

### 第六步：交给验收器

验收器核对每个结论的环境、时间与证据，确认没有把无权限写成正常，也没有越过只读范围。如果证据不足，合理结果应是“尚无法定位，并列出缺失信息”，而不是为了给出唯一答案而编造根因。

这条轨迹说明，可靠 Agent 不要求每次都给出确定答案，而要求**结论强度与证据强度一致**。

## 五、如何判断 Harness 改动是否有效

Harness 很容易在不断加规则后变得臃肿。每个新增组件都应该来自一个真实失败，并记录：它准备改善什么、成本是什么、怎样验证、什么时候复查。

一个可落地的评测流程是：

1. 从真实失败中整理固定任务集；
2. 冻结旧版与新版 Harness；
3. 固定模型、任务输入和主要环境；
4. 每次只修改一个组件；
5. 对同一道题多次运行，做逐题比较；
6. 记录失败轨迹，而不只看最终总分。

至少同时关注这些指标：

| 指标 | 说明 |
| --- | --- |
| 任务成功率 | 端到端是否交付 |
| 错误完成率 | 没做成却报告成功的比例 |
| 证据支持率 | 结论是否真的被引用证据支持 |
| 自我恢复率 | 收到有效反馈后能否纠正 |
| 人工介入次数 | 哪些地方仍需要人处理 |
| 单任务耗时与费用 | 资源效率与每个成功任务成本 |
| 权限违规与近失事件 | 是否突破执行边界 |

成功率不变但成本下降，可能仍然是有价值的改进；成功率上升但越权增多，则不能算成功。

消融实验可以暂时关闭某个组件，观察效果变化。但一次分数不变，只能说明当前样本没有检出收益，不能证明它永远无用。低频高损失的权限与安全机制，更不能仅凭小样本中“没有出事”就删除。

评测本身也可能失真：题面泄露答案、模型能读取标准答案、外部服务状态变化、执行环境不一致、裁判标准不稳定。修改 Harness 前，先确保考卷和验证器没有坏。

## 六、从最小实现到可维护系统

个人项目没有必要一次搭齐全部机制，可以按风险和真实故障逐步推进。

### 阶段一：先跑通，并看清失败

建立最小循环、少量工具、执行日志和资源预算。记录模型请求、实际执行、工具结果与退出原因。目标不是马上做到完美，而是让每次失败可以重现。

### 阶段二：补工具契约与任务验收

区分参数错误、查无数据、权限不足、超时和结果未知；限制工具输入输出；给关键任务写清验收。对有副作用的动作同步建立授权与幂等机制。

### 阶段三：让长任务能够恢复

外置任务状态与证据，增加检查点、在途调用核对和 Context 裁剪。主动模拟程序在几个关键位置崩溃，检查恢复后是否重复执行、丢失证据或错误宣告完成。

### 阶段四：根据瓶颈增加分工

确实存在独立且耗时的调查分支，再引入子 Agent；真正需要长期协作，再增加消息与调度。每个新角色都需要明确输入、输出、权限、预算、超时和失败归属。

### 阶段五：持续评估与清理

把真实失败沉淀为回归用例，记录每次组件调整的收益与代价。模型或项目升级后，重新检查旧假设，删除已经被模型能力或更可靠机制覆盖的规则。

从后端工程视角看，Harness 并不是完全陌生的新技术：

| Agent 机制 | 后端工程中的对应问题 |
| --- | --- |
| 工具调用超时 | 分布式调用的结果未知、幂等与补偿 |
| 检查点恢复 | 持久化、崩溃窗口和状态重放 |
| 多 Agent 通信 | 消息重复、乱序与消费确认 |
| 工具并发 | 数据依赖、锁、限流与资源调度 |
| 权限检查 | 服务端鉴权、资源范围和审计 |
| 完成验证 | 业务验收、质量门禁与基线对比 |

模型带来的新难点在于：动作和解释都由概率系统动态生成，因此协议、状态和反馈必须比传统程序设计得更加明确。

## 七、Harness 不是越厚越好

原型、一次性脚本和低风险小改动，通常不值得搭建重流程。Harness 的长期价值来自复用：同一种错误第二次出现时，系统是否能自动避免它。

模型升级后，一部分“教模型如何做事”的提示会失去价值；但状态持久化、权限隔离、外部验证和不可逆操作前的确认不会轻易消失。好的 Harness 应当可以裁剪，每个组件都能独立关闭、比较和删除。

判断一条规则应该写进 Prompt 还是变成机制，可以问：这件事应该由模型理解并灵活决定，还是根本不应该给模型违反的机会？前者适合文档和 Skill，后者适合类型系统、Linter、权限、Hook 与 CI。

最终目标不是让规则越来越多，而是把重复出现的问题转化成可靠的工程资产：

- 缺失的信息变成项目文档与观察接口；
- 反复出现的 Review 意见变成静态检查；
- 看不见的失败变成结构化信号；
- 口头提醒变成真正的执行边界；
- 线上事故变成可以重复运行的评测用例。

当 Agent 做错时，我们不再只是手动修正这一次产物，而是回到运行环境中寻找缺失的能力、边界或反馈。工程师的角色也由每一步都参与执行，逐渐转向设计目标、协议、约束与验证回路。

这正是我目前对 Harness Engineering 的理解：**把模型的不确定性留在需要创造和判断的地方，把权限、状态和验收尽可能交给确定性的系统。**
