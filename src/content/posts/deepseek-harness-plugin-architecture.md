大多数 Agent 框架允许我们添加工具，少数框架还能替换模型或提示。DeepSeek Harness（DSH）往前走了一步：Agent Loop、Session、模型服务、工具、Hook、UI，乃至运行时扩展本身，都放进同一套插件组合机制。官方把这套原则写成一句话：Everything is a Plugin。

这句话很容易被理解成"插件特别多"。真正的区别在于，DSH 不把插件当作主程序外围的附件，而是用插件装配主程序。产品启动时看到的那个 Agent，只是某一组服务在当前 Scope 中组合出来的结果。理解这一点，才理解 DSH 和普通框架差在哪里。

本文基于 DeepSeek Harness 官方仓库、官方架构文档和 Cordis 论文分析。项目目前处于开发者预览阶段，接口仍可能发生破坏性变化，所以本文关注的是设计方法，不把当前包名当作长期稳定 API。

## 一、普通插件系统为什么不够

常见插件系统有一个稳定主程序：核心负责全部流程，插件在预先留好的位置注册命令、菜单或工具。这种结构适合功能扩展，却很难改变主流程。插件可以增加一个搜索工具，却不能替换 Agent Loop；可以订阅工具调用事件，却不能接管 Session 的保存方式；可以加一块 UI，却未必能让某个子任务拥有不同的一组服务。

Agent 系统偏偏经常需要改变这些"核心"部分：主 Agent 与子 Agent 使用不同工具，评测环境换成可回放的模型服务，Web 产品和命令行产品装配不同 UI，高风险任务临时挂载审计和审批能力，某个实验只替换 Loop 而其余组件保持不变。

如果所有变化都依赖主程序里的条件分支，系统很快会出现一棵庞大的配置树。每个新场景都往主函数里加一个判断，最终没人说得清哪个分支在什么条件下生效。这个问题在需要派生子任务、做评测回放、支持多宿主的 Agent 上尤其明显，因为这些需求天然要改变"核心"。

### 从扩展点到可装配的能力

普通插件系统的扩展点是静态的：主程序在启动时声明了十个钩子，插件只能挂在这十个位置。这个模型的问题在于，扩展点本身也是产品的一部分，而 Agent 需要改变的东西经常正好是扩展点之外的。

DSH 的思路是把扩展点反过来：不是"主程序暴露位置，插件填进去"，而是"先有能力和契约，再由 Scope 把 Provider 装配给 Consumer"。主程序不再是一个装满逻辑的壳，而是一组能力契约和一套装配机制。

这个反转的后果很直接。你想替换模型服务，就换一个 Provider；想让子 Agent 用只读文件系统，就为它创建覆盖了文件能力的子 Scope；想做评测，就挂一个回放 Provider；想换控制策略，就替换 Loop。每一项都不需要改主循环。

### 一个具体的失败案例

设想一个团队在普通框架里加"子 Agent"。最初需求是子 Agent 只能读。他们在工具注册处加了个条件：如果调用来自子 Agent，就不挂写工具。

需求很快变多：某个子 Agent 需要写，但只能写临时目录；评测时子 Agent 用回放模型；某个客户的部署里子 Agent 根本不能用网络。每个需求都往主程序的工具注册函数里加分支。半年后，这个函数有十几层嵌套，没有人敢动它。

根因不是需求刁钻，而是"谁拥有什么能力"被写死在了主程序的控制流里。DSH 用 Scope 把这个问题移出来：能力集合由 Scope 表达，子 Agent 的能力差异是 Scope 的差异，而不是条件分支的差异。

## 二、Cordis：组合运行时的三个概念

DSH 构建在 Cordis 之上。Cordis 不是 Agent 模型，也不是工具协议，它是一套应用组合运行时，负责插件生命周期、服务发现、作用域和上下文传播。理解 DSH，先理解 Cordis 的三个角色。

| 角色 | 含义 | 例子 |
| --- | --- | --- |
| Service Definition | 一种能力的类型与契约 | LLM 服务、文件系统、会话存储 |
| Service Provider | 在某个 Scope 内提供具体实现 | 远端模型、本地模型、回放器 |
| Service Consumer | 声明并使用这种能力 | Agent Loop、UI、Hook、工具 |

以模型调用为例，Agent Loop 不应该直接引用某个具体模型客户端。它消费的是 LLM 服务；OpenAI、DeepSeek、本地模型或回放器都可以成为 Provider。评测时挂回放 Provider，线上运行时挂真实模型 Provider，Loop 本身不变。

### 它和依赖注入的差别

传统依赖注入也能替换实现，所以有人会问 Cordis 和容器有什么不同。区别主要在两点。

第一是生命周期。依赖注入容器通常关心对象在进程启动时怎么构造，Cordis 关心的是能力在运行过程中如何挂载、替换、卸载，以及卸载时怎样撤回它带来的副作用。第二是作用域的表达。依赖注入的作用域多用于请求级隔离，Cordis 的 Scope 更接近一个可以继承、覆盖、临时创建和销毁的能力边界，它不是为了让对象活得久一点，而是为了让"某段任务拥有某组能力"成为可描述、可回收的事实。

### 一次服务解析

当一个 Consumer 请求某项能力，运行时先在当前 Scope 查，找不到就向上级 Scope 查，直到根 Scope。查到的 Provider 就是这次调用要用的实现。

这个向上查找的语义，决定了子 Scope 的"覆盖"其实是"遮蔽"：子 Scope 提供自己的实现，上级的实现仍然存在，只是对子 Scope 内的 Consumer 不可见。因此"临时降级模型"不会破坏父 Scope 的配置，子 Scope 销毁后，父级实现重新可见。

服务解析还要处理缺失和降级。一个 Consumer 声明需要审计能力，但当前 Scope 没有提供，运行时可以给一个空实现，或显式报告能力缺失。降级策略应该由装配决定，而不是由每个 Consumer 自己判空；把"缺了怎么办"也作为装配的一部分，Consumer 才能保持简单。

## 三、时间维度的可组合：可逆副作用

Cordis 论文把"时间可组合"定义成：一个组件被移除后，它的副作用能被完全撤回。这个定义比"能热插拔"严格得多，也更有用。

在普通运行时里，挂载一个插件可能打开文件句柄、注册监听器、启动后台任务。卸载时如果没有一条清晰的逆操作，这些副作用会泄漏。Cordis 的形式化做法是给每个上下文变换保存一个逆变换：运行时持有这个逆，卸载时执行它，于是组件的副作用可以局部地、确定地撤回。

```ts
const openDatabase = (config) => {
  const pool = createPool(config);
  return {
    value: new DatabaseProvider(pool),
    inverse: () => pool.close(),
  };
};
```

运行时挂载时执行函数本体，把返回值放进上下文，同时保存逆操作；卸载时执行逆操作。关键不是"关闭连接池"这行代码本身，而是运行时把"如何撤回"当成一等数据保存下来，不依赖调用方记得清理。

![DSH Scope 的装配、运行与可逆卸载](/images/posts/dsh-scope-lifecycle.svg?v=20261001)

### 清理顺序也是组合的一部分

Provider 之间常有依赖。一个查询 Provider 依赖一个连接池 Provider：查询 Provider 的逆操作是"等待在途查询完成"，连接池的逆操作是"关闭所有连接"。正确的卸载顺序是先卸载查询 Provider，再卸载连接池。

如果顺序反过来，先关连接池，在途查询会失败，查询 Provider 就永远等不到"在途查询完成"。运行时若维护了依赖图，就能按逆拓扑顺序卸载；没有依赖图，就只能靠运气或写死顺序。这张活的依赖关系，才是"可组合"和"能堆到一起"的分界线。

副作用的粒度也直接影响撤回的精度。如果整个 Provider 只有一个大逆操作，撤回时只能整体关闭；如果每个资源都有独立的逆操作，撤回时可以选择性释放。粒度也不是越细越好，打开二十个连接却给每个都记录逆操作，运行时就要维护二十条记录；合适的粒度是把"一个逻辑动作"作为单位，打开一个连接池是一个副作用，池里的单个连接由池自己管理。

### 热替换与配置协调

Cordis 还提供了一个声明式组件加载器，带配置协调和热模块替换能力。热替换不只是把新代码塞进去，还要处理新旧配置的差异：哪些配置是新增的，哪些被删除，哪些值发生了变化。

举个具体例子。一个模型 Provider 从 v1 升级到 v2，v2 把 `temperature` 字段改名为 `sampling`。加载器不能只把新代码换上去，还要把配置里的 `temperature` 映射成 `sampling`，或者显式报告这个字段已经废弃。若不做协调，v2 代码读不到 `sampling`，会退回默认值，行为变化就说不清是代码升级还是配置丢失造成的。

热替换在长任务里还有隐蔽风险：一个 Provider 运行到一半被替换，正在使用它的 Consumer 该怎么办。运行时至少要有两个选择，等当前批次结束后再替换，或立刻替换并让旧 Provider 走完逆操作。选择取决于能力的性质：模型 Provider 可以等本轮结束再换，副作用小；文件系统 Provider 若被替换，在途的读写必须要么完成要么被明确中止。热替换没有一键生效的通用答案，它需要按能力类型决定过渡方式。

## 四、空间维度的可组合：Scope 与依赖

论文把"空间可组合"定义成：组件之间的依赖能够被声明，并被反应式地管理。通俗地说，组件不只声明"我能提供什么"，也声明"我需要什么，以及这些依赖变化时我该怎么办"。当 Scope 里的某项能力发生变化，依赖它的组件会被自动重新评估。

```text
Application Scope
├── Main Agent Scope
│   ├── Full Filesystem
│   └── Strong Model
└── Subagent Scope
    ├── Read-only Filesystem
    └── Cheap Model
```

这比全局单例更贴近 Agent 的执行模型。权限、模型和工具集合本来就该跟随任务边界，而不是跟随进程。子 Agent 不需要复制整套应用，只需在自己的 Scope 中覆盖差异。

依赖还能驱动激活和停用。一个审计 Provider 声明它需要文件写能力，并且只有在写能力存在时才激活；某个 Scope 移除了写能力，审计 Provider 就被停用。反过来，一个只读缓存 Provider 声明它依赖数据库读能力，当数据库 Provider 被替换成另一个实现，缓存 Provider 收到这个变化，清空旧缓存并重新激活。组件不需要轮询，运行时根据声明在上下文变化时主动通知。

### Scope 表达的是权限边界

Scope 的父子关系不只是代码复用，它直接对应权限。子 Scope 继承父级服务，也能覆盖其中一部分。一个只读文件系统的子 Scope，即使父 Scope 拥有写权限，子任务看到的也只是只读版本。

这个能力对 Agent 尤其重要。Agent 经常派生子任务做调查、检索或代码评审，这些子任务不需要主任务的完整权限。用 Scope 表达权限，权限就跟着任务走，而不是跟着进程走。

继承不是复制，而是引用加遮蔽。子 Scope 不会把父 Scope 的所有 Provider 复制一份，它只在需要时覆盖；改父 Scope 的一个 Provider，所有没有覆盖它的子 Scope 都会看到变化。覆盖则是局部生效：子 Scope 覆盖了文件系统，父 Scope 里的其他兄弟 Scope 不受影响。这个语义让"全局默认"和"局部例外"可以同时存在。

还需要区分依赖声明和权限声明。依赖声明的是"没有它我就不激活"，权限声明的是"即使有更多能力我也只用这些"。前者解决可用性，后者解决边界；运行时要同时检查两者，只检查其一，要么组件在不满足依赖时被错误激活，要么组件在权限范围内被错误放行。

### 统一上下文与可观察等价

论文进一步把副作用上下文和依赖上下文统一成一个上下文类型，让每次变化都通过它中介，这个设计被称作上下文范式。统一之后得到一个可观察等价：不同组件的变化可以交错，只要它们不通过这个统一的上下文互相干扰，行为就等价。

为什么统一上下文关键？分开的两套状态会让运行时维护两份账，两份之间如何同步就成了糊涂账；统一成一份之后，挂载产生的副作用和组件声明的依赖都落在同一份状态上，中介逻辑只有一处。落到工程上，"可观察等价"这句话的意思是：一个 Provider 挂了或卸载了，只要它的副作用被正确撤回，就不该影响其他 Provider 的观察结果。这是隔离的保证，也是"卸载后系统状态一致"能被推理的前提。

论文还给出一套组件演算，让这些性质能从单个组件推广到整个系统：只要每个组件都满足局部的可逆副作用和响应式依赖性质，整个系统就能保持组合可观察。对要承载大量第三方插件的运行时来说，可检查比可宣称重要得多，这也是为什么这套形式化值得一篇长论文。

## 五、DSH 的包地图与依赖方向

官方把代码按能力族组织。主要分组包括：`core` 是产品能力的脊柱，负责 Session、Prompt、Tool、Agent 服务和具体 Loop；`api` 负责远程装配与 RPC 网关；`boot` 是共享启动装配；`host` 是 Web GUI 的宿主服务、目录选择、插件清单和遥测；`client` 是浏览器端的 shell、wire、对象服务、slots 和各类 UI 插件；此外还有 `runtime-diagnostics` 做不变量检查和报告，`test-support` 提供回放、测试工具和 smoke test，`util` 放低层通用工具。

包多并不自动代表架构先进。DSH 有价值的地方是依赖方向受到约束：扩展插件依赖服务定义，而不依赖某个具体 Provider；可替换的 Agent Loop 通过 Agent 服务与其他组件交互；UI、Hook 与工具消费稳定能力，而不是穿透到内部实现。如果插件名义上独立、实际却引用主程序的内部对象，它仍然只是分散的模块。插件化的质量取决于能力接缝是否稳定。

依赖图本身也被当作架构的一部分。官方会生成依赖图并在持续集成里做新鲜度门禁，这一步看起来是工具性细节，其实是防线：如果某个插件偷偷依赖了不该依赖的模块，依赖图会暴露它。类型能挡住错误调用，挡不住错误的依赖方向。

### 发布预期与能力接缝

官方把包分成产品级、支持级和实验级：产品级有稳定接口承诺，实验级没有稳定性或支持保证。这个分类不是文档措辞，它决定了下游能不能放心依赖。一个插件作者如果依赖实验级包，就要接受它随时变化；把稳定能力和实验能力在发布层面分开，能避免"崩溃之后才发现"。

能力接缝要按变化的来源来切，而不是按模块名来切。一个经常变化的能力，最好拆成三类包：定义、提供者和消费者，只有当这三者可能独立演进时才拆。判断标准是变化的来源：模型供应商会换、评测需要回放、不同宿主需要不同实现，所以模型调用值得拆；一个只在单进程内使用的配置读取函数，拆成服务反而增加间接层。

接口设计有两个常见的病。接缝太宽，消费者会绕过接口去读内部状态，比如 LLM 服务的接口里直接暴露一个原始字段，消费者就会读它，实现细节于是泄漏到所有调用方；接缝太窄，接口里塞满无关细节，任何实现变化都会扩散到所有消费者。好的接缝落在"能力的最小稳定语义"上，既足够抽象以允许多种实现，又足够具体以阻止消费者绕过它。

## 六、可替换的 Agent Loop

很多框架把 Loop 写死为"模型输出工具调用，执行后继续"。现实中的 Loop 存在大量策略差异：一次允许并行执行多少工具，何时压缩上下文，是否先生成计划，工具失败后重试、反思还是退出，子 Agent 怎样调度，用户中断何时生效，达到预算后如何降级。

DSH 让 Agent Loop 成为可替换部分，意味着研究者可以替换控制策略，而不必复制 Session、UI 和工具生态。拿两个具体策略对比：一个面向代码评审的 Loop，可能每轮只允许一次工具调用，先让模型读完差异再决定；一个面向批量重构的 Loop，可能并行跑多个只读检索，再串行落盘。两者共享同一套 Session、工具和 UI，却需要不同的推进策略；如果 Loop 被写死，这两类产品就得各分叉一份运行时。

### 可替换 Loop 的契约

可替换也带来风险。Loop 是状态推进的中心，更换它可能破坏事件顺序、持久化假设和终止条件。所以稳定的 Agent 服务需要规定可观察行为：什么叫一次 Turn，工具调用怎样记录，取消后有哪些保证，结束状态有哪些类型，预算耗尽时的行为是什么。少了任何一条，替换 Loop 都可能破坏依赖它的 Session 或 UI。

这也是为什么 Agent 服务要放在脊柱里。Loop 可以换，但它换的时候必须遵守 Agent 服务定义的稳定语义，否则"可替换"就成了"可破坏"。插件自由度越高，对契约和不变量的要求越高；一个能随便替换的 Loop，如果连"工具结果何时回到 transcript"都没定义清楚，替换它就等于把整个系统的行为交给一个未约束的实现。

## 七、Extensions：运行时自修改与治理

DSH 的扩展机制里还有一部分更激进：它允许检查当前插件和服务，并由模型生成挂载或卸载操作。Agent 不只调用业务工具，还能查看自己当前拥有什么能力，再为任务装配新的能力。

一种理想流程是：任务需要数据库诊断，Agent 查询当前服务清单，找到只读数据库插件，请求用户授权挂载，在子 Scope 中运行诊断，任务结束后卸载插件。整个过程里，能力不是写死在启动配置里，而是随任务动态装配。

如果缺少治理，这也会变成供应链和权限问题。运行时自修改至少需要插件来源和版本锁定、安装前的权限清单、代码签名或可信发布渠道、Scope 级最小权限、完整的挂载调用卸载审计，以及失败时恢复到已知装配。模型可以提出装配方案，但不应该自行扩大权限；装一个插件会改变系统能力集合，而调用一个工具只在已有能力内行动，两者的区别是本质性的。

权限清单是这里最硬的一道门槛。它必须在挂载前可读、可审计：要哪些文件、哪些网络、哪些环境变量，是否要提升权限。它不是给模型看的提示，而是给运行时和人的检查点；模型可以解释"为什么需要这个插件"，但最终能否挂载，由清单和授权策略决定。

审计也要覆盖挂载、调用和卸载三段。谁在什么时刻请求挂载哪个版本、授权依据是什么；插件被调用时传了什么参数、产生了什么副作用；卸载时逆操作是否执行、有没有残留。三段合起来，才能回答"这个插件现在还在不在、刚才做了什么"。缺了卸载审计，系统可能以为自己已经卸载了某个插件，实际它的连接还活着。

## 八、端到端：一个任务穿过 DSH

用一个具体任务把前面的机制串起来。主 Agent 要修一个登录超时缺陷，怀疑是数据库连接问题，派一个子 Agent 去查数据库。

第一步，应用启动时，启动层和宿主层装配出主 Scope，挂载 Session、Prompt、Tool、Agent 服务和具体 Loop。模型 Provider 指向真实模型，文件系统 Provider 拥有完整权限。启动日志里，运行时诊断检查不变量，确认装配一致。

第二步，主 Agent 走完几轮循环，判断需要独立的数据库调查。它不是直接扩大自己的工具集，而是请求创建一个子 Scope。

第三步，子 Scope 继承主 Scope，但覆盖两个能力：模型 Provider 换成更便宜的模型，数据库能力换成只读 Provider。子 Agent 在这个 Scope 里运行，看不到写权限。

第四步，调查完成，子 Agent 返回结论和证据，运行时卸载子 Scope 里的只读数据库 Provider。因为 Cordis 记录了逆操作，连接被正常释放，没有句柄泄漏。卸载按依赖的逆序进行：先停在途查询，再关闭连接。

第五步，同一个任务放进评测环境时，测试支持层挂载回放 Provider 替换真实模型。Loop、工具和 Session 都不变，只有模型服务的实现变了。评测器记录轨迹和结果，结束后销毁评测 Scope。

```text
scope.create(child)                 → 创建子 Scope
child.provide(model, cheapModel)    → 覆盖模型 Provider
child.provide(db, readonlyDb)       → 覆盖数据库能力
turn.start                          → 子任务开始
tool_call(read_db, args)            → 模型发起查询
tool_result(evidence)               → 结果回到 transcript
turn.complete                       → 子任务结束
child.unmount(db)                   → 卸载数据库 Provider
child.dispose()                     → 销毁 Scope，执行逆操作
```

这个例子里，没有一步需要改主循环，变化的都是 Provider 和 Scope。事件里的"创建 Scope"和"开始 Turn"是两个层次：Scope 管能力边界，Turn 管任务推进；把两者混在一个事件流里，就无法回答"这个工具调用是在哪个能力边界内发生的"。

子任务的结果回到父任务时，还要注意边界。父任务和子任务运行在不同 Scope，看到的能力不同，事件不能直接拼接。子任务的结果应该作为一个结构化对象回到父 transcript：状态、发现、证据、覆盖范围、不确定项。父任务据此决定继续、换方案还是停止，并且要核对子任务有没有越出它的 Scope、结论有没有对应证据。

## 九、失败模式与常见误解

插件化把灵活性交给运行时，也把新的失败模式带进来。

| 失败模式 | 更可能缺少的机制 |
| --- | --- |
| 卸载后连接仍被占用 | 可逆副作用与清理顺序 |
| 子 Agent 意外继承父级写权限 | Scope 覆盖与最小权限 |
| 热替换后新旧配置混用 | 配置协调 |
| 插件偷偷依赖具体 Provider | 依赖方向约束 |
| 卸载仍在使用的服务 | 生命周期与依赖管理 |
| 模型挂载了不该挂载的插件 | 来源锁定、签名与授权 |
| 评测和线上用了不同装配 | 可重放与装配快照 |

一次典型的卸载事故可以这样还原：一个子 Agent 正在查询数据库，主任务因为超时决定取消子任务。如果运行时只把子 Scope 标记为"取消"而没有正确卸载，数据库连接会继续占用；如果卸载顺序错误，在途查询先收到断连，错误会被误写成"数据库不可用"。正确路径是先停止新的查询请求，再等待在途查询结束，最后关闭连接。这个顺序不是业务代码想出来的，而是依赖图和逆操作机制提供的。

### 配置错误与运行时错误的分界

插件化系统的故障里，很多其实是配置错误，却容易被当成运行时错误。一个工具没生效，可能是 Provider 没挂对 Scope；一个模型不对，可能是子 Scope 覆盖错了实现。排查时先回答"当前 Scope 里到底有哪些 Provider、优先级如何"，再去看代码逻辑。运行时诊断和服务清单的价值就在这里：它们把装配状态显式化，让"配置错了"和"逻辑错了"能被分开定位。

### 几个常见误解

第一个误解是"插件化就是插件多"。真正决定质量的是能力接缝是否稳定、依赖方向是否受约束，而不是插件数量。第二个误解是"插件化必然更灵活"，实际上过早插件化会产生大量间接层，调试成本比业务收益更早到来。第三个误解是"可替换等于可随便换"，可替换的前提是有清晰的契约和不变量，没有契约的可替换只是把行为交给未约束的实现。

还有一个误解是把 DSH 当成适合所有团队的选择。它还在开发者预览阶段，官方明确会有兼容性破坏的变化；如果你的系统只有单一模型、单一宿主、单一 Loop，插件化收益很小，反而要多维护一套装配机制。DSH 更像一份"Agent 运行时可以被组合到什么程度"的研究样本，用它来学设计，比直接把它塞进生产更稳妥。

## 十、怎样判断插件架构是否成立

可以用一组问题检查一套插件架构：消费者是否只依赖定义，插件升级是否必须同步修改所有调用方；Provider 是否有明确生命周期，文件句柄、连接和监听器会不会泄漏；Scope 是否表达权限边界，子 Agent 会不会意外继承全部能力；事件是否有稳定顺序，UI、持久化和评测看到的是不是同一份事实；装配是否可观测，线上能不能解释某个能力来自哪个插件；版本是否可重放，同一个 Session 能不能恢复原运行环境；卸载是否安全，仍在运行的任务会不会突然失去依赖。

每一问都对应一种真实故障。插件系统的目标不是让任何东西都能替换，而是让变化发生在可描述、可检查、可恢复的边界内。

### 从单进程到组合运行时的迁移路径

如果要从一个单进程 Agent 迁移到组合运行时，不要一次重构。可以先从最容易变化的能力开始：把模型服务抽成定义和 Provider，让评测能回放；再把文件系统能力抽出来，让子任务能只读；等真的出现第二种 Loop 或第二种宿主，再抽 Loop 和 UI。

每一步都要先有真实需求。没有需求就抽服务，只是把一处写死的逻辑搬到另一处写死，还多了一层间接。组合运行时的收益，只在变化真实发生时才兑现。一张按触发条件组织的迁移表可以帮助排序：评测需要回放时引入定义与 Provider 分离；子任务需要更小权限时引入 Scope；出现第二种宿主时让客户端与宿主分离；出现第二种 Loop 时引入可替换 Loop 与稳定 Agent 服务；需要热替换时引入可逆副作用与配置协调；需要运行时自修改时引入权限清单、审计与回滚。

### 可重放性：装配快照

插件化系统最后要面对一个现实问题：线上某次运行能不能被重新制造出来。可重放性要求记录的不只是模型输出，还有当时的装配：每个 Provider 的版本、配置和 Scope 结构。

```text
run_snapshot:
  harness: dsh@0.x.y
  model_provider: remote@1.2.0
  tools: [read@2.0.0, bash@1.1.0]
  scopes:
    subagent:
      filesystem: readonly@1.0.0
```

如果只记录提示和模型输出，下次想复现时，工具版本变了、模型 Provider 变了、Scope 配置变了，复现就无从谈起。装配快照是可重放性的前提，也是评测可信的前提。对还在预览阶段的 DSH，这一点尤其重要：接口会变，只有把每个实验的装配完整记录下来，版本升级后的行为对比才有意义。

没有快照时，复现会以一种很隐蔽的方式失败。设想一个评测跑在两周前的装配上，模型 Provider 是 1.2.0、某个工具是 2.0.0；两周后工具升到 2.1.0，改了默认行为。此时重跑同一批任务，结果变了，却无法判断是模型还是工具升级造成的。快照的价值就在这里，它能区分"系统变了"和"结果漂了"。

## 十一、Pi、DSH 与 Codex 的位置不同

把 DSH 放在同类系统里比较，位置会更清楚。

| 系统 | 适合观察什么 | 主要扩展边界 |
| --- | --- | --- |
| Pi | 最小 Agent Loop 和可嵌入运行时 | 工具、扩展、技能、包 |
| DSH | 整个 Agent 应用如何被插件装配 | 服务、Provider、Scope、Loop、UI |
| Codex | 工业产品如何处理协议、审批、沙箱与恢复 | 工具、MCP、技能、客户端协议 |

Pi 抽象的是最小运行时，回答一个 Agent 怎么跑；DSH 抽象的是组合，回答一个 Agent 应用怎么装配；Codex 抽象的是产品与安全，回答一个 Agent 怎么在真实环境里受控执行。三者的抽象层次不同，不能直接比较谁更强。学习顺序上，先读 Pi 理解循环，再读 DSH 理解组合，最后读 Codex 理解产品边界，是比较自然的路径。

### 这份设计对普通框架的启示

即使不采用 Cordis，DSH 也给出几个可以迁移的判断：能力接缝要按变化来源来切，而不是按模块名；权限边界最好跟着任务走，而不是跟着进程走；卸载必须能撤回副作用，否则热插拔就是幻觉；可重放性依赖装配快照，而不是只记录输入输出。

这些判断不依赖任何具体库。一个普通框架也可以先做一件小事：把模型调用从 Loop 里抽成接口，让评测能挂回放。这一步带来的可测试性，往往比一堆插件机制更早产生价值。

## 十二、我对 DSH 的理解

DSH 值得研究的地方，不是它用了多少插件，而是它把"组合"做成了运行时的一等能力。它回答了一个其他框架很少正面回答的问题：当 Agent 应用需要随时替换模型、隔离子任务、回放评测、甚至让模型修改自己的运行时时，这套系统该怎么组织。

Cordis 的贡献是把这个问题从工程直觉提升到可以推理的机制：可逆的副作用、响应式的依赖、统一的上下文、可推广的组件演算。这些概念听起来抽象，但它们对应的是非常具体的问题：卸载会不会泄漏、依赖变化会不会漏通知、子任务会不会越权、系统能不能还原到某次运行。把这些回答清楚，插件化才不只是把代码拆碎。

它对使用者的启示是：插件化的价值在边界，不在数量。真正需要的是稳定的契约、清晰的 Scope、可撤回的副作用和可重放的装配，而不是尽可能多的可插拔点。做到这些，无论用不用 Cordis，你都已经在写一个更可靠的 Agent 运行时。
