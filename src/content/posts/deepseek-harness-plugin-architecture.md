大多数 Agent 框架允许我们添加工具，少数框架还能替换模型或 Prompt。DeepSeek Harness（DSH）往前走了一步：Agent Loop、Session、模型服务、工具、Hook、UI，乃至运行时扩展本身，都放进同一套插件组合机制。官方把这套原则写成一句话：Everything is a Plugin。

这句话很容易被理解成"插件特别多"。真正的区别在于，DSH 不把插件当作主程序外围的附件，而是用插件装配主程序。产品启动时看到的那个 Agent，只是某一组 Service Provider 在当前 Scope 中组合出来的结果。理解这一点，才理解 DSH 和普通框架差在哪里。

本文基于 [DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)、[官方架构文档](https://deepseek-harness.github.io/deepseek-harness/)和 [Cordis 论文](https://arxiv.org/abs/2608.25512)分析。项目目前处于 Developer Preview，接口仍可能发生破坏性变化，所以本文关注的是设计方法，不把当前包名当作长期稳定 API。

![DSH 从 Cordis Scope 到 Agent 能力的插件化装配](/images/posts/dsh-plugin-harness.svg?v=20261001)

## 先看结论

DSH 把一个 Agent 应用看成一组能力在具体 Scope 和生命周期中的装配结果。它用三个角色表达能力：

| 角色 | 含义 | 例子 |
| --- | --- | --- |
| Service Definition | 一种能力的类型与契约 | LLM Service 的流式接口 |
| Service Provider | 在某个 Scope 内提供具体实现 | 远端模型、本地模型、回放器 |
| Service Consumer | 声明并使用这种能力 | Agent Loop、UI、Hook |

两个维度决定组合的质量。时间维度回答"挂载和卸载时，副作用能否完全撤回"；空间维度回答"不同 Scope 之间的依赖如何声明并反应式地管理"。DSH 的价值在于把这两个维度做成了显式的运行时机制，而不是靠约定和文档。

后面正文会先讲普通插件系统为什么不够，再拆 Cordis 的时间与空间两个维度，然后落到 DSH 的包地图、能力接缝、可替换 Loop 和运行时自修改，最后用一个真实任务串起来，并说清楚插件化最容易在哪里翻车。

## 一、普通插件系统为什么不够

常见插件系统有一个稳定主程序：核心负责全部流程，插件在预先留好的位置注册命令、菜单或工具。

```text
Main Program
├── Plugin: Tool A
├── Plugin: Tool B
└── Plugin: UI Panel
```

这种结构适合功能扩展，却很难改变主流程。插件可以增加一个搜索工具，却不能替换 Agent Loop；可以订阅工具调用事件，却不能接管 Session 的保存方式；可以加一块 UI，却未必能让某个子任务拥有不同的一组服务。

Agent 系统偏偏经常需要改变这些"核心"部分：

- 主 Agent 与子 Agent 使用不同工具；
- 评测环境换成可重放的模型服务；
- Web 产品和命令行产品装配不同 UI；
- 高风险任务临时挂载审计和审批能力；
- 某个实验只替换 Loop，其余组件保持不变。

如果所有变化都依赖主程序里的条件分支，系统很快会出现一棵庞大的配置树。每个新场景都往主函数里加一个 `if`，最终没人说得清哪个分支在什么条件下生效。DSH 选择让核心能力也通过服务和插件提供，把"改什么"从主程序里搬出来。

### 从"扩展点"到"可装配的能力"

普通插件系统的扩展点是静态的：主程序在启动时声明了十个钩子，插件只能挂在这十个位置。这个模型的问题在于，扩展点本身也是产品的一部分，而 Agent 需要改变的东西经常正好是扩展点之外的。

DSH 的思路是把扩展点反过来：不是"主程序暴露位置，插件填进去"，而是"先有能力和契约，再由 Scope 把 Provider 装配给 Consumer"。主程序不再是一个装满逻辑的壳，而是一组能力契约和一套装配机制。

这个反转的后果很直接。你想替换模型服务，就换一个 Provider；想让子 Agent 用只读文件系统，就为它创建覆盖了文件能力的子 Scope；想做评测，就挂一个 Replay Provider。每一项都不需要改主循环。

### 一个具体的失败案例

设想一个团队在普通框架里加"子 Agent"。最初需求是子 Agent 只能读。他们在工具注册处加了个条件：如果调用来自子 Agent，就不挂写工具。

需求很快变多：某个子 Agent 需要写，但只能写临时目录；评测时子 Agent 用回放模型；某个客户的部署里子 Agent 根本不能用网络。每个需求都往主程序的工具注册函数里加分支。半年后，这个函数有十几层嵌套，没有人敢动它。

这个案例的根因不是需求刁钻，而是"谁拥有什么能力"被写死在了主程序的控制流里。DSH 用 Scope 把这个问题移出来：能力集合由 Scope 表达，子 Agent 的能力差异是 Scope 的差异，而不是 if 的差异。

### 从 if 分支到 Scope 的一个对照

同样一个"子 Agent 只能读"的需求，普通写法和 Scope 写法的差别很直观。普通写法把判断放进工具注册：

```ts
function toolsFor(caller: 'main' | 'subagent') {
  if (caller === 'subagent') return [readFile, listDir];
  return [readFile, writeFile, editFile, bash];
}
```

Scope 写法把能力集合挂在边界上，注册逻辑不变：

```ts
const subagentScope = parentScope.child();
subagentScope.provide(filesystem, readonlyFilesystem);
```

两种写法都能跑，但后者的"只读"是一条边界，前者是一个散落在注册函数里的条件。当子 Agent 的权限需求再变一次，Scope 写法改的是 Scope 配置，if 写法改的是主程序逻辑。边界和逻辑的分开，正是插件化要解决的问题。

### 条件分支为什么会指数级失控

条件分支的问题不在于第一个 if，而在于 if 之间会组合。工具集、模型、文件权限、网络访问，每一项都是一个维度，每加一个维度，条件组合就翻一倍。两个维度是四种组合，五个维度是三十二种，而且多数组合从未被测试。

Scope 的继承和覆盖把这从"枚举组合"变成"覆盖差异"。子 Scope 只需要声明和父级的差异，剩下的继承。系统要维护的是差异，而不是全组合。

## 二、Cordis：组合运行时的三个概念

DSH 构建在 Cordis 之上。Cordis 不是 Agent 模型，也不是工具协议，它是一套应用组合运行时，负责插件生命周期、服务发现、作用域和上下文传播。理解 DSH，先理解 Cordis 的三个角色。

```text
Service Definition  定义一种能力的类型和契约
Service Provider    在某个作用域内提供具体实现
Service Consumer    声明并使用这种能力
```

以模型调用为例，Agent Loop 不应该直接 import 某个具体模型客户端。它消费的是 LLM Service；OpenAI、DeepSeek、本地模型或回放器都可以成为 Provider。评测时挂 Replay Provider，线上运行时挂真实模型 Provider，Loop 本身不变。

### 传统依赖注入差在哪

传统依赖注入也能替换实现，所以有人会问：Cordis 和 DI 容器有什么不同。区别主要在两点。

第一，生命周期。DI 容器通常关心对象在进程启动时怎么构造，Cordis 关心的是能力在运行过程中如何挂载、替换、卸载，以及卸载时怎样撤回它带来的副作用。

第二，作用域的表达。DI 的作用域多用于请求级隔离，Cordis 的 Scope 更接近一个可以继承、覆盖、临时创建和销毁的能力边界。它不是为了让对象活得久一点，而是为了让"某段任务拥有某组能力"成为可描述、可回收的事实。

### 一次服务解析发生了什么

当一个 Consumer 请求某项能力，运行时先在当前 Scope 查，找不到就向上级 Scope 查，直到根 Scope。查到的 Provider 就是这次调用要用的实现。

这个向上查找的语义，决定了子 Scope 的"覆盖"其实是"遮蔽"。子 Scope 提供自己的实现，上级的实现仍然存在，只是对子 Scope 内的 Consumer 不可见。因此"临时降级模型"不会破坏父 Scope 的配置，子 Scope 销毁后，父级实现重新可见。

### 服务缺失时的降级路径

服务解析不只是"找到或找不到"。真实运行时还需要处理缺失和降级。一个 Consumer 声明需要审计能力，但当前 Scope 没有提供，运行时可以给一个 no-op Provider，或显式报告能力缺失。

降级策略应该由装配决定，而不是由 Consumer 自己到处判空。把"缺了怎么办"也作为装配的一部分，Consumer 才能保持简单：它假定契约被满足，装配层负责满足它，或明确告知不满足。

### 上下文如何在 Scope 间传播

Provider 的配置、身份、租户信息这些上下文，也需要在 Scope 间传播。子 Scope 继承父级的上下文，但可以覆盖其中一部分，例如换一个租户或换一个环境标签。

上下文传播和依赖注入的区别在于，上下文是随调用链流动的环境信息，不是某个 Consumer 的构造参数。它让子任务天然带上"我是从哪个父任务派生出来的"这类信息，而不需要每个调用方显式传递。

## 三、时间维度的可组合：可逆 effect

论文把"时间可组合"定义成：一个组件被移除后，它的副作用能被完全撤回。这个定义比"能热插拔"严格得多，也更有用。

在普通运行时里，挂载一个插件可能打开文件句柄、注册监听器、启动后台任务。卸载时如果没有一条清晰的逆操作，这些副作用会泄漏。Cordis 的形式化做法是给每个 context 变换保存一个逆变换：运行时持有这个逆，卸载时执行它，于是组件的副作用可以局部地、确定地撤回。

```text
mount provider   → 副作用进入 context，运行时记录 inverse
run task         → 在带副作用的 context 中执行
unmount provider → 执行 inverse，撤回副作用
```

这个机制的意义不是"让插件更安全"这么泛。它解决的是一个具体问题：Agent 任务频繁创建和销毁子 Scope，如果每次销毁都留下连接、句柄或后台进程，长任务会慢慢把环境拖垮。

![DSH Scope 的装配、运行与可逆卸载](/images/posts/dsh-scope-lifecycle.svg?v=20261001)

### effect 与 inverse 的代码形状

"可逆 effect"用代码表达，大致是给每个挂载操作配一个逆操作：

```ts
const openDatabase = (config) => {
  const pool = createPool(config);
  return {
    value: new DatabaseProvider(pool),
    inverse: () => pool.close(),
  };
};
```

运行时挂载时执行函数本体，把 `value` 放进 context，同时保存 `inverse`。卸载时执行 `inverse`。关键不是"关闭连接池"这行代码本身，而是运行时把"如何撤回"当成一等数据保存下来，不依赖调用方记得清理。

这也解释了为什么可组合的插件系统常常要求 Provider 显式声明销毁逻辑。如果每个 Provider 都自己兜底清理，运行时就无法在正确的时机、以正确的顺序统一撤回。

### effect 的粒度决定撤回的精度

effect 的粒度直接影响撤回的精度。如果整个 Provider 只有一个大 inverse，撤回时只能整体关闭；如果每个资源都有独立的 inverse，撤回时可以选择性地释放。

粒度也不是越细越好。一个 Provider 打开二十个连接，给每个连接都记录 inverse，运行时就要维护二十条记录。合适的粒度是把"一个逻辑动作"作为单位：打开一个连接池是一个 effect，池里的单个连接由池自己管理。

### 热替换在长任务里的风险

热替换在长任务里有个隐蔽风险：一个 Provider 运行到一半被替换，正在使用它的 Consumer 该怎么办。运行时至少要有两个选择：等当前批次结束后再替换，或立刻替换并让旧 Provider 走完 inverse。

选择取决于能力的性质。模型 Provider 可以等本轮结束再换，副作用小；文件系统 Provider 若被替换，在途的读写必须要么完成要么被明确中止。热替换没有"一键生效"的通用答案，它需要按能力类型决定过渡方式。

### 清理顺序也是组合的一部分

Provider 之间常有依赖。一个数据库 Provider 可能依赖一个连接池 Provider。卸载时，顺序错了就会出问题：先关连接池，正在使用的数据库 Provider 就悬空；先关数据库，连接池还能正常释放。

运行时需要保证服务何时可用、退出时按什么顺序清理。插件化不是简单地把函数放进数组，它要维护一张活的依赖关系。这张关系才是"可组合"和"能堆到一起"的分界线。

### 清理顺序的一个反例

假设一个查询 Provider 依赖一个连接池 Provider。查询 Provider 的 inverse 是"等待在途查询完成"，连接池的 inverse 是"关闭所有连接"。正确的卸载顺序是先卸载查询 Provider，再卸载连接池。

如果顺序反过来，先关连接池，在途查询会失败，查询 Provider 的"等待在途查询完成"就永远等不到。运行时若维护了依赖图，就能按逆拓扑顺序卸载。没有依赖图，就只能靠运气或写死顺序。

### 热替换与配置协调

Cordis 还提供了一个声明式组件加载器，带配置协调和热模块替换能力。热替换不只是把新代码塞进去，还要处理新旧配置的差异：哪些配置是新增的，哪些被删除，哪些值发生了变化。

配置协调之所以重要，是因为 Provider 的行为由配置决定。如果只替换代码、不协调配置，新代码可能拿到旧配置，产生难以复现的行为。把"协调"作为加载器的一等能力，说明可组合不只是空间上的拼装，也包括时间上的平滑过渡。

举个具体的例子。一个模型 Provider 从 v1 升级到 v2，v2 把 `temperature` 字段改名为 `sampling`。加载器不能只把新代码换上去，还要把配置里的 `temperature` 映射成 `sampling`，或者显式报告这个字段已经废弃。若不做协调，v2 代码读不到 `sampling`，会退回到默认值，行为变化就说不清是代码升级还是配置丢失造成的。

## 四、空间维度的可组合：响应式 coeffect

论文把"空间可组合"定义成：组件之间的依赖能够被声明，并被反应式地管理。形式化工具是 coeffect：一次 context 变化会根据组件的 coeffect 说明来驱动它的激活或停用。

通俗地说，组件不只声明"我能提供什么"，也声明"我需要什么，以及这些依赖变化时我该怎么办"。当 Scope 里的某项能力发生变化，依赖它的组件会被自动重新评估。

```text
Application Scope
├── Main Agent Scope
│   ├── Full Filesystem
│   └── Strong Model
└── Subagent Scope
    ├── Read-only Filesystem
    └── Cheap Model
```

这比全局单例更贴近 Agent 的执行模型。权限、模型和工具集合本来就该跟随任务边界，而不是跟随进程。子 Agent 不需要复制整套应用，只需在自己的 Scope 中覆盖差异。

### coeffect 如何驱动激活与停用

"响应式"具体指什么，可以用一个例子说明。一个审计 Provider 声明它需要文件写能力，并且只有在写能力存在时才激活。当某个 Scope 移除了写能力，审计 Provider 的 coeffect 说明被重新检查，运行时把它停用。

反过来，一个只读缓存 Provider 声明它依赖数据库读能力。当数据库 Provider 被替换成另一个实现，缓存 Provider 收到这个变化，清空旧缓存并重新激活。组件不需要轮询，运行时根据 coeffect 说明在 context 变化时主动通知。

### Scope 表达的是权限边界

Scope 的父子关系不只是代码复用，它直接对应权限。子 Scope 继承父级服务，也能覆盖其中一部分。一个只读文件系统的子 Scope，即使父 Scope 拥有写权限，子任务看到的也只是只读版本。

这个能力对 Agent 尤其重要。Agent 经常派生子任务做调查、检索或代码评审，这些子任务不需要主任务的完整权限。用 Scope 表达权限，权限就跟着任务走，而不是跟着进程走。

### 继承与覆盖的语义细节

Scope 的继承不是复制，而是引用加遮蔽。子 Scope 不会把父 Scope 的所有 Provider 复制一份，它只在需要时覆盖。这样改父 Scope 的一个 Provider，所有没有覆盖它的子 Scope 都会看到变化。

覆盖则是局部生效。子 Scope 覆盖了文件系统，父 Scope 里其他兄弟 Scope 不受影响。这个语义让"全局默认"和"局部例外"可以同时存在：大多数子任务用父级的模型和工具，少数子任务单独降级模型，或单独收紧文件权限。

### coeffect 与权限声明不是一回事

coeffect 声明的是依赖，权限声明的是限制，两者容易混。一个 Provider 声明 coeffect"需要数据库读能力"，是在说"没有这个依赖我就不激活"；它声明权限"只读数据库"，是在说"即使有更多能力我也只用这些"。

coeffect 解决可用性，权限解决边界。运行时要同时检查两者：依赖不满足就停用，权限越界就拦截。只检查其一，要么组件在不满足依赖时被错误激活，要么组件在权限范围内被错误放行。

## 五、context paradigm：把两个维度统一

论文进一步把 effect context 和 coeffect context 统一成一个 context 类型，让每次 effect 和 coeffect 都通过它中介。这个设计被称为 context paradigm。

统一之后得到一个可观察等价：不同组件的 effect 可以交错，只要它们不通过这个统一的 context 互相干扰，行为就等价。这个性质让组合的元理论可以从单个组件推广到整个系统。

### 为什么统一 context 很关键

分开的 effect 和 coeffect 会让运行时维护两套状态，两套状态之间如何同步就成了一笔糊涂账。统一成一个 context 后，挂载产生的副作用和组件声明的依赖都落在同一份状态上，中介逻辑只有一处。

对使用 DSH 的人来说，这个形式化结论意味着：只要组件的副作用和依赖都经过 context，运行时就能给出"卸载后是否能完全撤回""依赖变化后是否已重新激活"这类问题的确定答案。可组合性从一种模糊的工程感觉，变成了可以推理的性质。

### 可观察等价对使用者的意义

"可观察等价"听起来抽象，落到工程上是一句话：两个组件只要不通过共享 context 互相干扰，它们的行为就等价于各自独立运行。这意味着一个 Provider 挂了或卸载了，只要它的 effect 被正确撤回，就不该影响其他 Provider 的观察结果。

这个性质是隔离的保证。没有它，"卸载后系统状态一致"就无从谈起，因为任何组件都可能通过隐藏的共享状态影响别的组件。Cordis 把共享状态收敛到 context，才让隔离可以被推理。

### 从单个组件到整个系统的推广

论文给出一套组件演算，让时空可组合性可以从单个组件推广到整个系统。它的核心是：只要每个组件都满足局部的可逆 effect 和响应式 coeffect 性质，整个系统就能保持组合可观察。

这个推广的价值在于可扩展性。如果只能保证单个组件正确，系统一变大就失去保证；如果能证明组合保性质，新增组件不会破坏已有组件的隔离。对一个会长出大量插件的运行时，这比逐例验证更可靠。

### 为什么要花一篇论文去形式化

Cordis 论文有九十多页，有人会问值不值得。原因是"可组合"这个词在工程里用得太随意：能把组件堆到一起，不等于它们的副作用能互相隔离。

形式化的价值是给出一个可判定的标准：什么样的 effect 可逆，什么样的 coeffect 会触发重新激活，组合之后哪些性质保持。没有这套标准，"可组合"就只能靠作者宣称，无法被检查。对要承载第三方插件的运行时，可检查比可宣称重要得多。

## 六、DSH 的包地图与依赖方向

[官方 Packages 地图](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/README.md)把代码按能力族组织。主要分组包括：

| 分组 | 责任 |
| --- | --- |
| `core` | Session、Prompt、Tool、Agent Service 和具体 Loop |
| `api` | 远程 BFF 装配与 RPC 网关 |
| `boot` | 应用启动与共享装配逻辑 |
| `host` | Web GUI 的宿主服务与插件清单 |
| `client` | 浏览器端 shell、wire、object service 和 UI 插件 |
| `runtime-diagnostics` | 运行时不变量检查与诊断 |
| `test-support` | Replay、测试工具和 smoke tests |
| `util` | 低层通用工具 |

包多并不自动代表架构先进。DSH 有价值的地方是依赖方向受到约束：扩展插件依赖 Service Definition，而不依赖某个具体 Provider；可替换的 Agent Loop 通过 Agent Service 与其他组件交互；UI、Hook 与工具消费稳定能力，而不是穿透到内部实现。

如果插件名义上独立，实际却 import 主程序的内部对象，它仍然只是分散的模块。插件化的质量取决于能力接缝是否稳定。

### 依赖图是架构的一部分

官方会生成依赖图（`pnpm run gen-module-graph`）并在 CI 里做新鲜度门禁。这一步很容易被当成工具性细节，但它其实是架构的防线：如果某个插件偷偷依赖了不该依赖的模块，依赖图会暴露它。

把依赖图、package README 和运行时诊断都当成架构的一部分，说明 DSH 认识到插件系统不能只靠 TypeScript 类型。类型能挡住错误调用，挡不住错误的依赖方向。

### host 与 client 的边界

`host` 和 `client` 分别代表 Web GUI 的两半。`host` 在服务端，负责目录选择、应用启动、插件清单和产品遥测；`client` 在浏览器端，负责 shell、wire、对象服务、slots 和各类 ui-* 插件。

这条边界说明 DSH 连"界面"也纳入了插件组合。一个 UI 插件消费的是对象服务，而不是直接读写服务端的内部状态。界面的组件和业务能力通过契约连接，于是同一套后端能力可以配上不同的前端，甚至命令行前端。

### release expectations 的意义

官方把包分成产品级、support 级和 experimental 级。产品级有稳定 API 承诺，experimental 没有稳定性或支持保证。这个分类不是文档措辞，它决定了下游能不能放心依赖。

一个插件作者如果依赖 experimental 包，就要接受它随时变化。这个边界让"稳定能力"和"实验能力"在发布层面就分开，而不是在崩溃后才被团队发现。

### core 里的 spine 是什么

`core` 被官方称为 Product API spine，负责 Session、Prompt、Tool、Agent Service 和具体 Loop。spine 这个词很准确：它是产品能力的脊柱，别的组挂在这条脊柱上。

区分 spine 和扩展很重要。spine 是必须稳定、少而正交的那几块；扩展是可以增减的那部分。把 Session 放进 spine，是因为所有插件都要读写会话；把某个具体工具放进扩展，是因为它只是众多能力之一。spine 越小，运行时越稳；但 spine 少到连 Loop 都不稳定，插件就没了可依赖的主干。

### runtime-diagnostics 抓什么

`runtime-diagnostics` 做包级的不变量检查和报告。它能抓的典型问题包括：两个 Provider 声称提供同一个能力却没有明确的优先级，一个插件声明依赖的能力在目标 Scope 里不存在，卸载顺序违反了依赖图。

这类问题在类型层面常常不报错，只在运行时表现为诡异的行为。把它们做成显式的不变量检查，相当于给"装配是否正确"加了一道确定性防线。装配错误越早暴露，越不会被误判成模型或业务逻辑的问题。

### api 层为什么单独存在

`api` 负责远程 BFF 装配和 RPC 网关。单独一层的原因很实际：浏览器端的 client 不能直接接触服务端的内部 Provider，它需要一个稳定的远程边界。

BFF（Backend for Frontend）把服务端能力重新组织成适合前端消费的形状，RPC 网关负责跨进程调用。把这两件事放进独立的 api 组，说明"能力"和"能力的远程暴露"是两个问题：内部 Scope 怎么组合，和外部怎么访问，不该混在一起。

## 七、能力接缝怎样设计

一个经常变化的能力最好拆成三类包：定义、提供者和消费者。以模型调用为例：

```ts
// definition
interface LlmService {
  stream(request: ModelRequest): AsyncIterable<ModelEvent>;
}

// provider
class RemoteLlmProvider implements LlmService {
  async *stream(request) { /* 调用真实模型 */ }
}

// consumer
class AgentLoop {
  constructor(private llm: LlmService) {}
}
```

设计接缝时要回答四个问题：

1. 能力的最小稳定语义是什么；
2. Provider 何时创建和销毁；
3. Consumer 在服务暂时不可用时怎么办；
4. 哪些事件必须跨插件传播。

接口太小，消费者会绕过接口读取内部状态。接口太大，任何实现变化都会扩散。DSH 把 package README、依赖图和运行时诊断当作架构的一部分，就是因为插件系统只靠 TypeScript 类型还不够。

### 何时拆出三个角色

不是每项能力都需要 Definition、Provider、Consumer 三个包。只有当这三者可能独立演进时才拆。一个稳定的内部函数不需要包成服务，一个永远只有一种实现的模型调用也不需要 Provider 抽象。

判断标准是变化的来源。模型供应商会换、评测需要回放、不同宿主需要不同实现，所以模型调用值得拆。反过来，一个只在单进程内使用的配置读取函数，拆成服务反而增加间接层。

### 接缝过宽与过窄的两种病

接缝定义得太宽，消费者会绕过接口去读内部状态。比如 LLM Service 的接口若只暴露一个 `raw` 字段，消费者就会直接读 raw，Provider 的实现细节于是泄漏到所有调用方。

接缝定义得太窄，接口里塞满无关细节，任何实现变化都会扩散到所有消费者。好的接缝要落在"能力的最小稳定语义"上：它足够抽象以允许多种实现，又足够具体以阻止消费者绕过它。

### 事件契约也是接缝

能力的稳定语义不只有方法签名，还有它发出的事件。一个模型 Provider 的事件顺序、一个工具 Provider 的进度回调，都是契约的一部分。

如果只约束方法、不约束事件，两个 Provider 的调用结果看起来一样，实际事件顺序不同，下游 UI 和持久化就会看到不同事实。事件契约要明确：事件按什么顺序到达，哪些事件保证有，哪些事件可以省略。

## 八、为什么 Agent Loop 也应该可替换

很多框架把 Loop 写死为"模型输出工具调用，执行后继续"。现实中的 Loop 存在大量策略差异：

- 一次允许并行执行多少工具；
- 何时压缩上下文；
- 是否先生成计划；
- 工具失败后重试、反思还是退出；
- 子 Agent 怎样调度；
- 用户中断何时生效；
- 达到预算后如何降级。

DSH 让 `dsh-agent-loop` 成为可替换部分，意味着研究者可以替换控制策略，而不必复制 Session、UI 和工具生态。

### 可替换 Loop 的契约

可替换 Loop 也带来风险。Loop 是状态推进的中心，更换它可能破坏事件顺序、持久化假设和终止条件。因此稳定的 Agent Service 需要规定可观察行为：什么叫一次 Turn，工具调用怎样记录，取消后有哪些保证，结束状态有哪些类型。

插件自由度越高，对契约和不变量的要求越高。一个能随便替换的 Loop，如果连"工具结果何时回到 transcript"都没定义清楚，替换它就等于把整个系统的行为交给一个未约束的实现。

### 几个真实的 Loop 策略差异

拿两个不同的 Loop 看差异有多大。一个面向代码评审的 Loop，可能每轮只允许一次工具调用，先让模型读完 diff 再决定；一个面向批量重构的 Loop，可能并行跑多个只读检索，再串行落盘。

两者共享同一套 Session、工具和 UI，却需要不同的推进策略。如果 Loop 被写死，这两类产品就得各 fork 一份运行时。DSH 把 Loop 变成可替换的能力，正是为了让"策略差异"不升级成"代码分叉"。

### 可替换 Loop 的最小契约清单

一个 Loop 要能被安全替换，至少要在契约里写清：Turn 的边界、工具调用的记录方式、取消的保证、结束状态的类型、预算耗尽的行为。少了任何一条，替换 Loop 都可能破坏依赖它的 Session 或 UI。

这也是为什么 DSH 把 Agent Service 放在 spine 里。Loop 可以换，但它换的时候必须遵守 Agent Service 定义的稳定语义，否则"可替换"就成了"可破坏"。

## 九、Extensions：运行中的 Agent 修改运行时

DSH 的 packages 地图还列出 `extensions`：它允许检查当前插件和服务，并由模型生成挂载或卸载操作。

这是"Everything is a Plugin"最激进的一部分。Agent 不只调用业务工具，还能查看自己当前拥有什么能力，再为任务装配新的能力。一种理想流程是：

```text
任务需要数据库诊断
→ Agent 查询当前 Service Inventory
→ 找到只读数据库插件
→ 请求用户授权挂载
→ 在子 Scope 中运行诊断
→ 任务结束后卸载插件
```

### 运行时自修改需要治理

如果缺少治理，这也会变成供应链和权限问题。运行时自修改至少需要：

- 插件来源和版本锁定；
- 安装前的权限清单；
- 代码签名或可信发布渠道；
- Scope 级最小权限；
- 完整的挂载、调用和卸载审计；
- 失败时恢复到已知装配。

模型可以提出装配方案，但不应该自行扩大权限。这一点和普通工具调用有本质区别：装一个插件会改变系统能力集合，而调用一个工具只在已有能力内行动。

### 权限清单为什么是硬门槛

运行时自修改最危险的一步，是模型请求挂载一个新插件。插件清单必须在挂载前可读、可审计：它要哪些文件、哪些网络、哪些环境变量，是否要提升权限。

权限清单不是给模型看的提示，而是给运行时和人的检查点。模型可以解释"为什么需要这个插件"，但最终能否挂载，由清单和授权策略决定，不由模型自述决定。少了这一步，自修改就等于给模型开了一个绕过沙箱的后门。

### 审计要覆盖挂载、调用和卸载

治理不只是挂载前检查一次。完整的审计要覆盖三段时间：谁在什么时刻请求挂载哪个版本、授权依据是什么；插件被调用时传了什么参数、产生了什么副作用；卸载时逆操作是否执行、有没有残留。

三段时间的审计合起来，才能回答"这个插件现在还在不在、刚才做了什么"。缺了卸载审计，系统可能以为自己已经卸载了某个插件，实际它的连接还活着。对运行时会自我修改的系统，这份审计记录是唯一能事后还原真相的依据。

### 模型查询 inventory 的边界

模型能查询当前 Service Inventory，但这个查询本身也要受约束。它只能看到自己有权查看的能力，不能通过 inventory 枚举出系统里所有插件，更不能据此推断其他 Scope 的配置。

inventory 暴露给模型的范围，应该和模型所在 Scope 的权限一致。否则，一个低权限子 Agent 通过枚举 inventory 就能摸清整个系统的能力布局，这本身就是一种信息泄漏。

## 十、端到端：一个任务穿过 DSH

用一个具体任务把前面的机制串起来：主 Agent 要修一个登录超时 bug，怀疑是数据库连接问题，派一个子 Agent 去查数据库。

### 第一步：装配主 Agent Scope

应用启动时，boot 与 host 装配出主 Scope，挂载 Session、Prompt、Tool、Agent Service 和具体 Loop。模型 Provider 指向真实模型，文件系统 Provider 拥有完整权限。启动日志里，`runtime-diagnostics` 检查不变量，确认装配一致。

### 第二步：主 Agent 判断需要子任务

主 Agent 走完几轮 Loop，判断需要独立的数据库调查。它不是直接扩大自己的工具集，而是请求创建一个子 Scope。

### 第三步：子 Scope 覆盖能力

子 Scope 继承主 Scope，但覆盖两个能力：模型 Provider 换成更便宜的模型，数据库能力换成只读 Provider。子 Agent 在这个 Scope 里运行，看不到写权限。

### 第四步：子任务结束，卸载 Provider

调查完成，子 Agent 返回结论和证据。运行时卸载子 Scope 里的只读数据库 Provider。因为 Cordis 记录了逆操作，连接被正常释放，没有句柄泄漏。

### 第五步：评测时换成 Replay Provider

同一个任务放进评测环境时，`test-support` 挂载 Replay Provider 替换真实模型。Loop、工具和 Session 都不变，只有模型服务的实现变了。评测器记录轨迹和结果，结束后销毁评测 Scope。

### 事件在子任务间如何传递

子任务结束后，结论和证据要回到父任务。这里有一个容易忽略的问题：父任务和子任务运行在不同的 Scope，它们看到的能力不同，事件不能直接拼接。

子任务的结果应该作为一个结构化对象回到父 transcript：状态、发现、证据、覆盖范围、不确定项。父任务据此决定继续、换方案还是停止。事件边界和 Scope 边界一致，才能避免"子任务在只读 Scope 里看到的东西，被父任务误当成完整事实"。

### 一次完整的事件序列

把这次任务的运行时事件按时间排开，能看到装配和执行为什么必须分开：

```text
scope.create(child)                 → 创建子 Scope
child.provide(model, cheapModel)    → 覆盖模型 Provider
child.provide(db, readonlyDb)       → 覆盖数据库能力
turn.start                          → 子任务开始
tool_call(read_db, args)            → 模型发起查询
tool_result(evidence)               → 结果回到 transcript
turn.complete                       → 子任务结束
child.unmount(db)                   → 卸载数据库 Provider
child.dispose()                     → 销毁 Scope，执行逆操作
```

事件里的 `scope.create` 和 `turn.start` 是两个层次。Scope 管能力边界，Turn 管任务推进。把两者混在一个事件流里，就无法回答"这个工具调用是在哪个能力边界内发生的"。

### 子任务结果的验收

子任务结束，不等于父任务可以无条件采信。父任务至少要核对：子任务有没有越出它的 Scope，结论有没有对应的证据，覆盖范围是否和任务一致。

如果子任务说"数据库没问题"，但它的证据只有一条只读查询，父任务就不该把这个结论当成全面排查。验收把子任务的结果重新放进证据标准里，而不是把"子 Agent 说完了"当成"问题查清了"。

这个例子里，没有一步需要改主循环。变化的都是 Provider 和 Scope。

## 十一、失败模式：插件化最容易在哪翻车

插件化把灵活性交给运行时，也把新的失败模式带进来。

| 失败模式 | 更可能缺少的机制 |
| --- | --- |
| 卸载 Provider 后连接仍占用 | 可逆 effect 与清理顺序 |
| 子 Agent 意外继承父级写权限 | Scope 覆盖与最小权限 |
| 热替换后新旧配置混用 | 配置协调 |
| 插件偷偷依赖具体 Provider | 依赖方向约束 |
| 卸载仍在使用的服务 | 生命周期与依赖管理 |
| 模型挂载恶意插件 | 来源锁定、签名与授权 |
| 评测和线上用了不同装配 | 可重放与装配快照 |

每一条都对应 DSH 的一个设计决策。插件化不是免费的，它把"配置错误"从启动时的一次性检查，变成了运行中需要持续治理的状态。

### 一次卸载事故的还原

一个子 Agent 正在查询数据库，主任务因为超时决定取消子任务。如果运行时只把子 Scope 标记为"取消"而没有正确卸载，数据库连接会继续占用；如果卸载顺序错误，在途查询先收到断连，错误会被误写成"数据库不可用"。

正确路径是：先停止新的查询请求，再等待在途查询结束，最后关闭连接。这个顺序不是业务代码想出来的，而是依赖图和 inverse 机制提供的。事故还原的意义，是让我们看到"卸载"不是一个动作，而是一个有顺序的过程。

### 如何测试插件化运行时

插件化运行时的正确性很难靠手工验证。值得建立的测试包括：挂载再卸载后，环境状态是否回到挂载前；卸载顺序反转时，是否能被运行时拒绝；依赖变化的通知是否真的到达了订阅者。

这些测试针对的是运行时机制本身，而不是某个具体 Provider。它们保证了"可组合性"这个承诺真的成立，而不是只停留在文档里。

### 配置错误与运行时错误的分界

插件化系统的故障里，很多其实是配置错误，却容易被当成运行时错误。一个工具没生效，可能是 Provider 没挂对 Scope；一个模型不对，可能是子 Scope 覆盖错了实现。

排查时先回答"当前 Scope 里到底有哪些 Provider、优先级如何"，再去看代码逻辑。runtime-diagnostics 和 inventory 的价值就在这里：它们把装配状态显式化，让"配置错了"和"逻辑错了"能被分开定位。

## 十二、怎样判断插件架构是否真的成立

可以用下面这组问题检查：

| 检查项 | 失败时的症状 |
| --- | --- |
| Consumer 是否只依赖定义 | 插件升级必须同步修改所有调用方 |
| Provider 是否有明确生命周期 | 文件句柄、连接和监听器泄漏 |
| Scope 是否表达权限边界 | 子 Agent 意外继承全部能力 |
| 事件是否有稳定顺序 | UI、持久化和评测看到不同事实 |
| 装配是否可观测 | 线上无法解释某能力来自哪个插件 |
| 版本是否可重放 | 同一 Session 无法恢复原运行环境 |
| 卸载是否安全 | 仍在运行的任务突然失去依赖 |

插件系统的目标不是让任何东西都能替换，而是让变化发生在可描述、可检查、可恢复的边界内。

### 过早插件化的代价

如果要自己实现一个内部 Agent 平台，我不会第一天就复制 DSH 的全部插件体系。更合理的顺序是：先把模型、工具、状态和 UI 分层；当第二种 Loop、第二种宿主或子任务隔离真实出现时，再引入 Scope 和 Service Definition。

过早插件化会产生大量间接层，调试成本比业务收益更早到来。一个只跑单进程、单模型、单 UI 的系统，用插件体系去解耦，往往是在解决还没出现的问题。DSH 的价值，是当你确实需要这些变化时，可以参考它怎么做。

### 从单进程到组合运行时的迁移路径

一个单进程 Agent 要迁移到组合运行时，不要一次重构。可以先从最容易变化的能力开始：把模型服务抽成 Definition 和 Provider，让评测能回放；再把文件系统能力抽出来，让子任务能只读；等真的出现第二种 Loop 或第二种宿主，再抽 Loop 和 UI。

每一步都要先有真实需求。没有需求就抽服务，只是把一处写死的逻辑搬到另一处写死，还多了一层间接。组合运行时的收益，只在变化真实发生时才兑现。

### 一张迁移检查表

| 触发条件 | 值得引入的机制 |
| --- | --- |
| 评测需要回放模型 | Definition 与 Provider 分离 |
| 子任务需要更小权限 | Scope 与继承覆盖 |
| 出现第二种宿主或 UI | 能力接缝与 client/host 分离 |
| 出现第二种 Loop 策略 | 可替换 Loop 与稳定 Agent Service |
| 需要热替换或平滑升级 | 可逆 effect 与配置协调 |
| 需要运行时自修改 | 权限清单、审计与回滚 |

这张表的原则是"变化驱动引入"。每一项机制都对应一个真实出现的变化，而不是抽象的"更解耦"。

## 十三、Pi、DSH 与 Codex 的位置不同

| 系统 | 适合观察什么 | 主要扩展边界 |
| --- | --- | --- |
| Pi | 最小 Agent Loop 和可嵌入 Runtime | Tools、Extensions、Skills、Packages |
| DSH | 整个 Agent 应用如何被插件装配 | Service、Provider、Scope、Loop、UI |
| Codex | 工业产品如何处理协议、审批、沙箱与恢复 | Tools、MCP、Skills、Apps 与客户端协议 |

三者不是简单的功能强弱关系。Pi 适合从小处理解循环，DSH 适合研究运行时组合，Codex 适合研究产品边界和安全执行。

### 什么时候不该选 DSH

DSH 还在 Developer Preview，官方明确说会有兼容性破坏的变化。下面这些情况要慎重：

- 你需要稳定的长期 API，而不是快速迭代的设计实验；
- 你的系统只有单一模型、单一宿主、单一 Loop，插件化收益很小；
- 你需要开箱即用的产品，而不是一套需要自己装配的运行时；
- 你的团队对运行时组合还不熟悉，直接上 Scope 和 Provider 会让排查更难。

DSH 更像一份"Agent 运行时可以被组合到什么程度"的研究样本。用它来学设计，比直接把它塞进生产更稳妥。

### 这份设计对普通框架的启示

即使不采用 Cordis，DSH 也给出几个可以迁移的判断：能力接缝要按"变化来源"来切，而不是按模块名；权限边界最好跟着任务走，而不是跟着进程走；卸载必须能撤回副作用，否则热插拔就是幻觉。

这些判断不依赖任何具体库。一个普通框架也可以先做一件小事：把模型调用从 Loop 里抽成接口，让评测能挂回放。这一步带来的可测试性，往往比一堆插件机制更早产生价值。

### 三者分别抽象了什么

Pi 抽象的是"最小运行时"，回答一个 Agent 怎么跑；DSH 抽象的是"组合"，回答一个 Agent 应用怎么装配；Codex 抽象的是"产品与安全"，回答一个 Agent 怎么在真实环境里受控执行。三者的抽象层次不同，所以不能直接比较谁更强。

对学习顺序，我会建议先读 Pi 理解循环，再读 DSH 理解组合，最后读 Codex 理解产品边界。这个顺序从最小开始，每一步都建立在上一步之上。

### 选型时先问三个问题

面对 Pi、DSH、Codex 这类选择，与其比 star 数，不如问三个问题：你要改变的东西是模型、循环、宿主，还是权限边界；你需要的是可嵌入的骨架，还是可装配的运行时，还是带安全边界的完整产品；你的团队能承受多少运行时复杂度。

前两个问题决定技术匹配，第三个问题决定落地成本。一个只需要最小循环的小项目，选 DSH 反而把简单的需求做复杂；一个需要多宿主、多 Loop 的平台，选 Pi 就要自己补上整套组合机制。

## 十四、配置、版本与可重放性

插件化系统最后要面对一个现实问题：线上某次运行能不能被重新制造出来。可重放性要求记录的不只是模型输出，还有当时的装配：每个 Provider 的版本、配置、Scope 结构。

```text
run_snapshot:
  harness: dsh@0.x.y
  model_provider: remote@1.2.0
  tools: [read@2.0.0, bash@1.1.0]
  scopes:
    subagent:
      filesystem: readonly@1.0.0
```

如果只记录 Prompt 和模型输出，下次想复现时，工具版本变了、模型 Provider 变了、Scope 配置变了，复现就无从谈起。装配快照是可重放性的前提，也是评测可信的前提。

对还在 Developer Preview 的 DSH，可重放性尤其重要：接口会变，只有把每个实验的装配完整记录下来，版本升级后的行为对比才有意义。

### 没有快照时的复现失败

设想一个评测跑在两周前的装配上：模型 Provider 是 1.2.0，某个工具是 2.0.0。两周后工具升到 2.1.0，改了默认行为。此时重跑同一批任务，结果变了，却无法判断是模型还是工具升级造成的。

快照的价值就在这里：它能区分"系统变了"和"结果漂了"。没有快照，任何跨版本对比都建立在不可靠的基础上。

### "Everything is a Plugin"真正改变了什么

回到开头那句话。它改变的不是技术词汇，而是判断框架：一个 Agent 应用不是"一个程序加若干功能"，而是"一组能力在时间和空间上的装配"。

这个说法如果只是换个词，没有意义。它有意义的地方，是逼出了三个具体问题。

第一，变化发生在哪个层次。是 Provider 换了，还是 Scope 变了，还是 Loop 被替换了。层次不同，风险和契约都不同。第二，变化能不能撤回。挂载产生的一切副作用，卸载时能不能干净地收回。第三，变化能不能被看到。当前的装配是什么、每个能力来自哪里、依赖是否满足。

能回答这三个问题，插件化才不是装饰；不能回答，插件就只是把代码拆得更碎。DSH 和 Cordis 的贡献，是把这三个问题从"靠人自觉"变成"运行时机制"。

对要做 Agent 的工程师来说，这套思路的结论并不激进：先把模型、循环、工具、宿主这些真正会独立变化的东西分开，给它们稳定的契约，再让组合发生在可描述、可检查、可撤回的边界内。做到这些，无论用不用 Cordis，你都已经在写一个更可靠的 Harness。

这套标准也适用于任何会长期演进、需要第三方扩展的软件，不只是 Agent。边界清楚、变化可撤回、装配可观察，是插件化真正要解决的三件事。
