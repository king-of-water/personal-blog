订单代码只写一行 `stockClient.reserve("O100", "S42", 1)`，库存却在另一台机器上减少了一件。中间发生了什么？这篇始终跟着订单 O100 的库存预占走：先看完整路线，再把每一站拆开。

## 先看全程：本地入口、网络请求、远端执行、结果返回

订单 O100 想预占商品 S42 一件。库存服务里原本有十件，成功后变成九件，并保存 O100 的预占记录。先只看这一次成功调用，按下面四步走完：

![四步走完库存预占：本地代理组织请求，远端执行，结果返回本地](/images/posts/rpc-call-mainline.svg)

1. 订单代码调用本地的 `stockClient.reserve(...)`，进入客户端代理；代理负责代替业务代码组织通信。
2. 代理把“调用库存预占方法”和 O100、S42、数量 1 编成请求，发给库存服务。
3. 库存服务读懂请求，找到自己的预占方法，提交减库存与预占记录的事务。
4. 库存服务发回结果，本地代理解析结果，让等待中的方法返回。

这种通过本地方法入口，请求另一个进程执行操作的方式，叫远程过程调用，英文简称 RPC。“像调用本地方法”来自本地代理提供的方法入口，真正的库存代码仍在另一个进程执行。后面前四节就按这四步展开；先把正常流程走通，再看响应丢失、超时和重试。涉及具体协议时，以 gRPC 与 Protocol Buffers 官方文档为依据。

## 一、本地代理：先接住这行方法调用

如果订单与库存都在一个进程，可以直接持有库存对象并调用它。库存独立部署后，订单进程里没有那个对象，于是需要一个提供相同调用入口、内部负责网络通信的本地对象。这个对象就是客户端代理。

`stockClient.reserve("O100", "S42", 1)` 先进入代理，并不会让运行时直接跳到另一台机器。下面看代理究竟接住了什么。

### 本地真正执行的是哪个对象

在一个 Java 应用内，如果写 `StockService stock = new StockServiceImpl()`，那么调用 `stock.reserve(...)` 时，运行时根据这个对象找到本进程的方法实现，建立方法调用栈，把参数交给该方法。返回值沿着同一进程的调用栈回到调用处。对象参数传递的是引用值，被调用方法可以通过这个引用访问本进程中的对象。

拆成两个进程后，订单服务的内存里没有那个库存实现对象。即使两个进程部署在同一台机器上，它们通常也拥有各自的地址空间；订单服务中的一个对象引用，不能直接用来定位库存进程中的对象。RPC 要跨过的就是这个边界。

解决办法是让订单服务持有另一个实现相同接口的对象：客户端代理，也叫调用桩（stub）。它的 `reserve` 方法不减库存，负责把调用变成请求。下面是手写代理的结构示意，`RpcTransport` 是假设的通信组件，代码省略了具体编码、连接和错误类型，不是某个框架的可直接运行 API：

```java
interface StockService {
    ReserveResult reserve(String orderId, String sku, int quantity);
}

final class StockClientProxy implements StockService {
    private final RpcTransport transport;

    StockClientProxy(RpcTransport transport) {
        this.transport = transport;
    }

    public ReserveResult reserve(String orderId, String sku, int quantity) {
        ReserveRequest request = new ReserveRequest(orderId, sku, quantity);
        return transport.unaryCall(
            "stock.v1.StockService/Reserve", request, ReserveResult.class);
    }
}

StockService stockClient = new StockClientProxy(transport);
ReserveResult result = stockClient.reserve("O100", "S42", 1);
```

编译器只需要知道 `stockClient` 提供这个方法，以及参数和返回值的类型。真正调用时，先进入 `StockClientProxy.reserve`，再由 `transport` 发出请求。业务代码可以保持方法调用的写法，是因为有人在本地实现了这样一个方法入口。

框架可以在构建时生成代理类，也可以在运行时用动态代理拦截调用。后者把接口上的方法和参数交给统一处理器，再转换成网络请求；Java 的具体拦截机制可看[动态代理：JDK 代理与 CGLIB](/posts/java-dynamic-proxy-jdk-cglib/)。RPC 不要求必须使用 JDK 动态代理：gRPC Java 就会生成调用桩。代理也不需要持有远端业务对象的 Java 引用，只需要接口描述和通信能力。

## 二、网络请求：把方法和参数交给库存服务

上一步代理接到的是本地方法和参数，这一步要把它们转换成远端能读懂的请求。双方事先约定服务名、方法标识、请求字段和返回类型；客户端知道如何编码，服务端才知道如何解析。比如双方都把 O100 理解成订单号，把数量 1 理解成一件，不能一端按件、另一端按箱。

这份约定叫接口契约。先记住它保证“同一组数据在两端有共同的解释”，具体的接口定义文件留到第八节。现在沿着请求往前走：找到目标、编码参数、发送完整消息。

### 先确定发到哪里，再把数据编码成消息

代理拿到 O100、S42 和数量 1 后，还需要目标地址。最简单的做法是配置一个固定主机和端口；实例变多后，可以把逻辑服务名解析成可用地址列表，再按负载均衡策略选择实例。名字解析解决“有哪些地址”，负载均衡解决“这次选哪一个”；请求也可能先发给代理或网关，由它选择后端。

假设当前解析得到库存实例 `10.0.0.8:9000` 和 `10.0.0.9:9000`，本次选了前一个。它们是部署信息，和方法标识 `stock.v1.StockService/Reserve` 分工不同：地址把数据送到某个进程，方法标识告诉那个进程该执行哪项操作。注册中心是服务发现的一种实现；固定地址、DNS 也能支持 RPC，并非每次调用都必须先请求注册中心。gRPC 就支持通过不同名字解析器获得地址。[gRPC 名字解析说明](https://grpc.io/docs/guides/custom-name-resolution/)

接着，客户端把参数对象转换为双方约定格式的字节，这叫序列化；服务端从字节还原出可用字段，叫反序列化。网络发送的是 O100 等字段的表示，不是客户端对象地址，也不是方法的机器指令。远端收到字段后创建自己的请求对象，因此修改远端请求对象不会自动修改客户端对象。

一次调用在逻辑上至少需要方法标识、参数，以及把响应对应回本次调用的办法。下面用 JSON 展示一个**自定义教学协议**的可读结构，实际发送时仍需编码成字节；它不是 gRPC 的报文格式：

```json
{
  "requestId": "A1",
  "method": "stock.v1.StockService/Reserve",
  "timeoutMs": 2000,
  "body": { "orderId": "O100", "sku": "S42", "quantity": 1 }
}
```

这里 A1 识别一次网络尝试，O100 标识订单业务。框架还可能传递身份凭证、链路追踪信息等元数据；`timeoutMs` 表示调用预算，服务端仍需结合耗时和取消检查决定是否继续处理。具体字段及其位置取决于协议，不能把这张 JSON 当成所有框架都必须照搬的信封。

### 传输协议如何识别完整请求

客户端通过连接发送消息，服务端在约定端口监听并读取。实际系统通常会复用连接，避免每调用一次就重新建连；配置加密通信时，连接还涉及 TLS 握手和身份验证。连接复用只是在复用通信通道，不是在让两个进程共享对象。

还要解决一个容易忽略的问题：以 TCP 字节流为例，一次写入不保证对应一次读取。服务端可能先读到半条请求，也可能一次读到多条请求的字节。通信层必须知道消息边界，例如先读固定大小的长度字段，再按长度读完整内容，并限制允许的消息大小。否则连参数有没有收全都无法判断。

gRPC 在 HTTP/2 上组织调用，用请求路径标识服务和方法；消息本身带有压缩标志和长度前缀。HTTP/2 的流把同一连接上的不同调用区分开。因此 gRPC 不需要照搬上例的 JSON `requestId` 字段，也不是靠“第一个响应一定对应第一个请求”来配对结果。[gRPC HTTP/2 协议说明](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)

序列化和传输协议解决不同问题。Protocol Buffers 说明一个消息内部各字段怎样编码；外层协议说明消息怎样传输、如何标识方法、如何结束本次调用。只会把对象转成字节，还不能组成一个完整的 RPC 系统。

## 三、远端执行：从方法标识找到业务代码，再提交库存

### 收到请求后，先找到本进程的处理入口

库存服务启动时，需要把允许对外调用的方法登记到分发表。可以把它理解为一张表：键是 `stock.v1.StockService/Reserve`，值是已登记的处理入口及请求解析规则。收到调用后，框架根据方法标识查表，把完整消息解析成请求对象，再交给对应处理入口。

这个入口有时被称为服务端骨架（skeleton）：它把协议层接收到的请求衔接到本地业务实现。下面仍是教学伪代码，实际框架可能在不同拦截器和线程中完成这些步骤：

```text
启动时：
  handlers["stock.v1.StockService/Reserve"] = reserveHandler

收到一次完整调用时：
  检查消息大小、调用身份与方法访问权限
  handler = handlers.lookup(method)
  找不到方法 -> 返回方法不存在，结束本次调用
  按约定类型解码请求；失败 -> 返回参数/格式错误
  校验订单、商品和数量；通过后交给业务执行器
  reply = stockServiceImpl.reserve(orderId, sku, quantity)
  编码 reply，并返回本次调用的完成状态
```

这里的 `stockServiceImpl` 才是库存进程里的业务对象。网络没有让它隔空执行；库存进程自己的代码读懂了请求，再发起一次普通的本地调用。服务端可以通过生成的分发代码或事先绑定的处理器调用它，不必每次都用反射搜索任意类和方法，更不应让外部请求随意指定类名来执行。

请求解析成功也不代表业务已经执行。权限检查可能拒绝，请求可能在执行队列等待，业务线程也可能因数据库锁阻塞。两端接口版本不一致时，甚至会在方法查找或解码阶段结束。这些阶段留下的证据不同，后面分析失败时需要分开看。

![服务端按方法标识查找处理入口，解析校验通过后调用库存方法；不认识的方法直接拒绝](/images/posts/rpc-server-dispatch.svg)

图中的“找到方法”只意味着找到了执行入口。下面才开始改变库存，成功的确认点要放在事务提交之后。

### 处理 O100 时，数据库发生了什么

订单服务首先准备 O100、S42 和数量 1。它发出请求，库存服务收到完整请求，解析参数，检查身份和接口权限，然后把请求交给业务处理代码。

“收到完整请求”和“开始处理业务”之间可能还有排队。服务端的连接线程接收了数据，不代表数据库操作已经开始。繁忙时，请求可能在工作队列里等几百毫秒。

业务代码开始执行后，需要确认 O100 是否已经预占过库存。没有预占过，才尝试减少可用库存，并写入预占记录。这两项写入应当在库存服务自己的一个数据库事务里完成。

假设减库存成功，写入记录也成功，事务提交。到这里，数据库里才留下可恢复的业务事实：S42 的可用库存是九件，O100 对应一件预占库存。

库存服务随后组织成功响应，带上 O100 和预占结果，发回订单服务。订单服务解析完整响应，才拿到代码里的 ReserveResult。

![订单服务、库存服务和数据库完成一次库存预占的步骤](/images/posts/rpc-stock-call-sequence.svg)

这里有几个先后关系不能颠倒。服务端应该先确认事务提交，再返回“预占成功”。如果先返回成功、稍后才写数据库，客户端已经继续创建订单，库存事务却可能失败。

只减少库存、不写 O100 的预占记录，也有问题。下次重试时，服务端无法判断 O100 是否已经减过库存；事后释放库存也缺少明确依据。

本例把减少库存与预占记录放在同一个本地事务里，是为了让它们一起成功或一起回滚。远程调用只负责把请求与结果送到双方，这个数据库边界仍然需要业务代码实现。

## 四、结果返回：让等待中的本地方法继续执行

### 等待中的调用如何被唤醒

库存业务完成以后，服务端把结果对象编码回字节，通过本次调用对应的通道返回。客户端接收完整响应，确认协议层的结束状态，再解析为本地结果对象。远端的结果对象和客户端的结果对象是两份数据，客户端拿到的是按约定重建的内容。

对于前面的自定义协议，可以在发送前为 A1 建立一个“等待结果的占位对象”，通常叫 Future，并存入 `pending[A1]`。接收线程收到带 A1 的完整响应后，找到该 Future，填入结果或错误；同步代理等待的 Future 完成后，`reserve` 才能返回。异步代理可以先把 Future 交给业务方，稍后再通过回调处理结果。

先登记等待项、再发送请求，是为了避免响应过快时接收线程找不到等待者。超时、断连、正常完成都需要清理等待项，还要处理“超时和响应同时到达”的竞争：一次本地调用只能完成一次。迟到响应不能误交给另一次调用。gRPC 在自己的调用与流状态中处理对应关系，不要求业务方自己维护这张 `pending` 表。

因此，同步写法里的“等一个方法返回”，底下可以是接收线程不断读网络，再通知业务线程继续执行。业务线程不需要自己循环读取 socket；网络上的请求和响应也不要求按发出顺序完成。同步与异步 API 改变的是调用方怎样等待，不改变远端业务仍由另一个进程执行这个事实。

![本地代理编码调用，服务端分发执行，响应完成等待；超时后保留订单号查证](/images/posts/rpc-proxy-wire-flow.svg)

顺着图读 O100：本地进入代理，代理封装方法和参数；网络送达后，服务端找到已登记的处理器，执行库存方法；事务提交后返回响应，客户端重建结果并结束等待。如果等不到完整结果，图中的超时分支进入查询或原编号重试，而不能直接判断库存没有变化。

## 五、正常路径之外：成功、拒绝和结果未知怎样区分

RPC 框架可以把远端错误转换成本地异常，但不会把远端异常对象原样搬进本地内存。双方必须约定错误状态和允许返回的详情。库存不足可以是正常响应中的 `REJECTED`，网络中断则是通信错误；两者不能仅凭“都抛异常”就认定业务效果相同。

gRPC 还用调用状态表达完成情况。HTTP 层拿到 200 不足以证明这次 gRPC 成功，应读取 gRPC 状态；即使通信完成且状态为 OK，是否预占成功还要看业务响应和接口承诺。例如返回了 `REJECTED`，只能说明这次拒绝结果成功传回，不能继续按库存已预占处理。[gRPC 调用生命周期](https://grpc.io/docs/what-is-grpc/core-concepts/#rpc-life-cycle)

| 观察点 | 同进程方法调用 | 远程方法调用 |
| --- | --- | --- |
| 方法入口 | 本进程对象上的实现 | 本地代理，最终请求另一进程 |
| 参数与返回值 | 在本进程按语言规则传递 | 需要按契约编码，并在另一端重建 |
| 耗时来源 | 本地计算，也可能有锁、I/O 等等待 | 另加编码、连接、网络和远端排队等耗时 |
| 上下文 | 可使用当前线程已有的上下文 | 身份、追踪等要显式传播并在服务端校验 |
| 事务范围 | 可让本地操作加入同一个事务 | 调用方本地事务不会自动覆盖远端数据库 |
| 等不到结果 | 取决于本地操作和运行时的具体行为 | 远端可能没执行、正在执行，也可能已提交 |

例如订单服务开启本地数据库事务，再调用库存 RPC。库存已经提交后，即使订单服务后来回滚，库存也不会跟着回滚。需要协调两项业务效果时，另行设计补偿或分布式事务；代理只负责通信。同样，远端修改参数不会自动改本地对象，远端代码也不能自动读取调用方线程里的用户身份。

在设计接口时，应把需要一起完成的操作做成有明确业务含义的一次请求。若把 `getStock`、`setStock` 等细碎操作机械地逐个远程化，调用方不仅多付出网络往返，还会在“读库存”和“写库存”之间引入竞争窗口。让服务端提供 `reserve`，才能在拥有库存数据的一侧实现条件更新、去重和事务。

到这里，一行方法调用背后的两次本地调用就接上了：订单服务调用本地代理，库存服务调用本地业务实现；连接两者的是有契约的请求和响应。接下来再把数据库提交放进这条链，就能判断每一种“成功”到底确认到了哪里。

### 把中断放回调用链上看

先看请求尚未发送的情况。订单服务在本地发现数量为零，直接拒绝；或者客户端能确认本次请求在发出之前就失败了。这些证据可以说明，这一次尝试没有触发远端业务。

但要确认框架或中间层有没有其他尝试。某个连接建立失败，只说明这次连接没成功；如果之前已经向另一个实例发过请求，就不能把整个业务操作认定为从未执行。

第二种，请求已发出，但调用方没有收到结果。字节可能还在网络中，也可能已经到达库存服务，甚至库存服务已经处理完了。订单服务单凭“发送完成”，无法分辨这些位置。

客户端把字节交给自己的网络系统，不等于远端业务线程已经读取；远端机器收到字节，也不等于数据库已经提交。哪怕传输层确认收到数据，它确认的仍是传输范围内的事情。

第三种，库存服务已经开始执行，却在事务提交之前崩溃。若这个本地事务最终回滚，库存仍是十件。但客户端没有直接看到数据库回滚，只能先保留结果未知。需要通过业务查询或原编号重试确认。

第四种，库存事务已经提交，服务端在发送响应前崩溃，或者响应在网络中断掉。库存实际上已经是九件，O100 的预占记录也存在。订单服务看到的依然可能是超时。

最后一种，完整成功响应已经到达订单服务。按照我们前面定义的接口，订单服务可以据此确认库存预占已提交。但这个成功不能扩展为“支付也成功了”或者“用户整笔订单都已完成”，因为那些操作还没发生。

![请求发送、业务执行、事务提交与响应返回之间的失败窗口](/images/posts/rpc-failure-windows.svg)

这张图不是让调用方凭超时猜阶段。恰恰相反，阶段相邻，调用方又看不见远端的完整过程，所以同一个错误可能覆盖多个阶段。阶段用于帮助服务端记录证据、设计恢复方式，不能给客户端制造不存在的确定性。

如果库存服务执行过程中先调用了另一个外部服务，再操作本地数据库，本地回滚也无法证明外部操作没有发生。本文简单例子的结论依赖“业务效果都在这一个本地事务内”，换了边界就要重新分析。

### 收到的确认覆盖哪一步

现在设想接口返回“成功”，却没有说成功是什么意思。库存服务可能想表达“请求已接收”，订单服务却理解成“库存已预占”。双方都觉得自己写得没错，业务却会继续走错。

接口需要明确确认点。对于本例，成功表示库存服务已提交预占事务，可以按 O100 查询到对应记录。它不只是请求进了队列，也不只是处理函数开始执行。

如果业务确实采用异步处理，可以先返回“任务已接收”，但应给出任务编号和后续查询方式。这个响应只能允许订单服务进入等待确认状态，不能直接把订单标成库存已预占。

持久化任务以后，进程崩溃时还可以恢复。只把任务放进内存队列，就立即向外承诺可靠接收，重启后任务可能消失。这个接收承诺到底覆盖哪一步，也应写清楚。

返回错误也要看承诺。库存不足，是库存服务经过业务检查得出的结果；网络连接被重置，是调用方观察到通信中断。两者都可能让代码进入异常分支，但只有前者直接表达了业务拒绝。

如果接口约定“库存不足时没有产生预占记录”，订单服务就可以提示购买失败。若业务代码已经完成部分不可回滚动作后才返回错误，就需要描述这些部分效果和恢复方式，不能只给一个笼统的失败。

可以给本例约定三个业务结果：

```text
RESERVED：O100 的预占事务已经提交
REJECTED：明确拒绝本次预占，没有形成预占
NOT_FOUND：本次查询暂时没有看到 O100 的预占记录
```

这些名称要有上面的具体含义才有用。NOT_FOUND 尤其不能被扩大为“原请求以后也不会执行”。原请求还在排队时，查询同样可能返回没有记录。

调用方的“结果未知”不必成为库存业务状态。服务端可以明确知道已经 RESERVED，调用方却因响应丢失而未知。给双方强行共用一套状态，会把问题越画越复杂。

## 六、超时与取消：本地停止等待，远端未必停止执行

假设订单服务给库存调用设置两秒超时。超过两秒，本地结束等待，返回超时错误。这能避免一个请求永远占住调用方的资源。

但库存服务可能只用了四百毫秒接收和排队，然后在数据库上等锁一千六百毫秒。两秒刚到时，业务操作也许还没结束。调用方不等了，不会让这段代码自动从世界上消失。

框架可以发送取消信号，让服务端停止不再需要的工作。服务端需要检查信号，停止后续步骤，并清理自己创建的任务。数据库正在做的操作是否中止、事务是否回滚，还要看数据库驱动和具体业务实现。[gRPC 取消处理说明](https://grpc.io/docs/guides/cancellation/)

已经提交的预占不会因为取消而自动释放。若业务决定不再保留它，应发起明确的释放操作，并让释放操作自身支持结果确认和重复请求。取消等待不能充当释放库存的业务接口。

还有一个常见误区：订单服务已经花了一秒八百毫秒，却再给库存服务两秒。这样下游可能认真做完了工作，入口却早已超时。总预算需要沿链路扣减，给下游的是剩余时间，并留出回传结果的空间。

服务端收到请求后，如果发现剩余时间连基本处理都来不及，可以在开始业务前拒绝，减少无效工作。处理过程中发现取消，也应尽早停止尚未执行的步骤。是否能够中止已经发生的业务效果，要单独判断。

gRPC 默认不设置截止时间，调用方需要明确选择合理的截止时间。它的文档也区分了框架取消一次调用与应用停止自己启动的工作，不能只配置一个超时参数就假定两端都已经停下。[gRPC 截止时间说明](https://grpc.io/docs/guides/deadlines/)

超时配置只能限制等待，结果确认仍然要靠业务证据。把超时调到十秒可能减少误报，但响应仍然可能在第九秒丢失；没有确认接口，这个根本问题不会消失。

## 七、结果未知以后：保留 O100，沿原操作确认

第一次调用超时后，订单服务保留 O100，查询库存服务：“O100 有没有预占 S42 一件？”

查到已预占，就继续后续订单流程。明确查到拒绝记录，并且接口保证不会再执行这次请求，就结束这次购买。如果暂时没有记录，订单服务不能立即判断库存尚未扣减，更不能用 O101 再预占一次。

可以按照约定继续查询，或者用 O100 重试原来的预占请求。重试安全的前提是库存服务把 O100 当成同一项业务，而不是看到一条新 RPC 就再减一件。

库存服务可以给预占记录建立订单号的唯一约束，把“记录该订单的预占”和“减少库存”放在同一个事务里。重复调用发现原预占已经存在，检查商品、数量等参数后返回原结果。

关于唯一约束为什么能挡住并发请求、提交时断连怎样处理，前一篇已经详细展开：[超时后怎样安全重试](/posts/timeouts-retries-idempotency-exactly-once/)。这里需要记住的是，RPC 框架不会自动替业务设计这个约束。

有些客户端配置了自动重试。库存服务必须把每次尝试携带的 O100 看成同一笔业务；否则业务代码虽然只调用一次方法，框架内部已经发出多次请求，照样可能多减库存。

重试次数和等待时间也要受总预算限制。如果库存服务已经拥堵，订单服务无限重试会让它更难恢复。一次同步等待结束以后，可以留下待确认记录，由后续流程继续查询，但这又要求待确认记录可恢复，有明确负责人推进。

查询接口要校验身份和访问权限，不能拿任意订单号就读取别人的业务。还应明确查询读取什么数据源；读取延迟副本时，“暂未找到”尤其不能用来证明原请求没执行。

如果库存预占后来会释放，查询也要反映这个后续状态。重复到达的旧预占请求不能在订单已取消之后偷偷重新占库存。实际接口需要保留足够的业务状态和约束，让同一个订单的预占、释放遵循允许的顺序。

## 八、接口契约：让两端对同一次操作有相同理解

前面已经走完正常调用和恢复路径。现在补上请求能被双方理解的约定：通信字段、业务编号、结果含义。先看接口如何描述，再看业务必须约定什么。

### 用一份定义描述方法与消息

本地接口让编译器知道怎样调用，还需要让网络两端知道怎样理解请求。假设订单服务把数量写成第一个整数，库存服务却把它理解成订单编号，即使字节一模一样地送达，业务仍然会出错。

因此要先定义接口契约：服务叫什么、能调用哪些方法、请求有哪些字段、各字段是什么类型、响应表示什么。接口定义语言（IDL）就是把这些约定写进一份机器可读文件，再由工具为两端生成代码。gRPC 常用 `.proto` 文件描述服务与消息，例如：

```proto
syntax = "proto3";
package stock.v1;
option java_multiple_files = true;

service StockService {
  rpc Reserve (ReserveRequest) returns (ReserveReply);
}

message ReserveRequest {
  string order_id = 1;
  string sku = 2;
  int32 quantity = 3;
}

message ReserveReply {
  string order_id = 1;
  string sku = 2;
  int32 quantity = 3;
  ReserveStatus status = 4;
}

enum ReserveStatus {
  RESERVE_STATUS_UNSPECIFIED = 0;
  RESERVED = 1;
  REJECTED = 2;
}
```

`order_id = 1` 里的 1 是编码时识别字段的编号，不是订单号的默认值；数量 1 是调用时填写的数据。Protocol Buffers 根据字段编号和类型编码消息，接收方用相应定义读取。字段编号一旦使用，就不能随意改作别的含义；旧版本删除字段时还应保留其编号，避免新旧服务误读。[Protocol Buffers 字段编号与兼容性规则](https://protobuf.dev/programming-guides/proto3/#assigning-field-numbers)

从同一份定义可以生成 Java 消息类、Java 客户端调用桩和服务端基类；也可以为其他支持的语言生成代码。于是 Java 订单服务和另一种语言实现的库存服务可以遵守同一份线上协议，无需共享 Java 对象布局。库存算法仍由开发者实现，编译工具只生成通信接口及其相关代码。[gRPC Java 代码生成说明](https://grpc.io/docs/languages/java/basics/#generating-client-and-server-code)

IDL 解决的是表达与解析的一致性，不会验证所有业务语义。两个版本都把 `quantity` 声明为整数，却分别理解成“件”和“箱”，仍然会算错。上面的 `RESERVED` 也需要业务约定为“预占事务已经提交”，工具无法替双方决定确认点。

### 业务编号、参数和结果需要什么约束

一个可以恢复的远程接口，至少要把“操作是谁、做了什么、怎样查结果”表达出来。

先区分两个编号。订单 O100 是业务编号，重试时保持不变；第一次网络尝试 A1、第二次 A2 是尝试编号，可以不同。前者用于防重复和确认业务，后者帮助排查哪一次网络请求出了问题。

如果两者混成一个编号，每次为了追踪新请求而换号，就破坏了幂等；如果所有尝试都不留区分，也不容易看出某次请求是第一次调用还是重试。

其次，成功响应应包含足以确认的业务信息。本例可以返回订单号、商品、预占数量和结果。不能只返回“OK”，却让调用方再猜这是接收成功还是提交成功。

查询接口应当只读结果，不能“查询一下，没找到就顺便再执行”。否则原本用于确认的操作又产生新副作用，调用方无法判断自己究竟在查证还是重新申请。

参数变化也要处理。同一 O100 从预占一件变成两件，不能算普通重试。服务端应拒绝编号复用，或设计明确的修改操作，让修改也有自己的业务规则。

对于“明确拒绝”的结果，需要决定是否持久化。若库存不足的请求稍后重试可能成功，接口就不能承诺它已经永久结束；若业务要求拒绝后不再执行，服务端要有能够挡住迟到请求的记录。这是业务约定，不是某个状态码自动提供的保证。

最后，业务编号和结果保留多久必须明确。调用方过了重试窗口还拿旧编号提交，服务端是拒绝、查询历史，还是可能当作新操作，需要在设计时说清楚。记录一删，原来的防重复保证就可能随之失效。

## 九、排查时，把证据放回这条调用链

假设订单服务在 12:00:00 发出 O100 的预占请求，12:00:02 超时。库存服务记录它在 12:00:01.700 已经提交事务，响应却在稍后返回时失败。

此时调用方日志里是失败，库存服务日志里是成功，数据库里的可用库存是九件。它们并不矛盾：调用方记录“没在两秒内收到结果”，库存服务记录“已经提交预占”，描述的是不同位置。

排查时先拿 O100 找数据库里的预占记录，再结合各次尝试的日志，还原请求有没有到达、什么时候开始处理、什么时候提交、响应有没有成功送出。只搜索异常堆栈，很容易漏掉已经发生的业务效果。

没有日志也不等于没有执行。进程可能提交后崩溃，日志还没刷出；采集系统也可能漏掉一段。确认业务事实应依靠能够恢复的业务记录，而不是依靠“搜不到成功日志”。

还要注意中间层。网关返回一个错误，可能是它连接库存服务失败，也可能是库存服务已经完成工作但网关没有拿到完整响应。中间层知道的事情同样有限，不能把所有 502 都翻译成库存没有预占。

不同机器的时钟可能有偏差，不能只靠几行日志的毫秒时间判断绝对先后。业务编号、数据库提交结果、同一次尝试内的耗时，往往比跨机器直接比较时间更可靠。

代码里的远程方法调用，可以保持简洁。业务处理不能因此只剩一个成功分支和一个失败分支。对于 O100，真正需要回答的是：库存预占已经确认、已经明确拒绝，还是仍需查证？有了这个区分，订单服务才知道该继续、结束，还是保留原编号等待确认。
