今天构建一个有三个 Worker 的 Agent 系统，最难的部分不是让三个 Agent 各自运行。那一部分已经很容易了，框架、协议和基础设施都到位了。真正让产出质量上不去的，是任务被直接拆开扔下去之后发生的事：数据侧 Agent 踩到了一个缓存侧也会碰到的坑，但它不知道有这种情况；Leader 发现了，只能在 Worker 都跑完以后再告诉所有人。已经投入的 Token 预算买来的是重复劳动和事后返工。

这是一个关于信息流的问题，不是关于并行计算的问题。Leader-Worker 架构把 Worker 之间的通道切断了，系统的每一个 Agent 只能向上汇报、等待指令，没法横向告诉队友"我这里出了一个你大概也会遇到的情况"。

本文不再重复介绍怎样拆任务、怎样用 Subagent 并行推进——那些内容在《[Subagent 与多 Agent：任务拆分、通信与结果汇总](/posts/subagents-and-multi-agent-orchestration/)》里已经完整覆盖。这里处理一个更前置的问题：**Leader-Worker 架构的协作机制缺了哪几块，补上之后系统会发生什么变化。**

## 先看结论

用一张表把五个机制和它们各自解决的问题放在一起：

| 机制 | 解决的问题 | 如果缺失 |
| --- | --- | --- |
| 启动协议（讨论先于执行） | 执行层约束在规划阶段不可见 | 做到一半才发现方案行不通 |
| 横向通信 | Worker 之间信息孤岛 | 踩过的坑队友不知道，重复发生 |
| OKR 协商 | 目标由 Leader 单方面分配 | Worker 无法在制定阶段说"这个做不到" |
| 集体复盘 | 经验停留在个体层面 | 团队不会积累协作层面的知识 |
| Mission 与核心宗旨 | 无人拍板时无方向锚点 | 多目标并发时各 Agent 推理出互相冲突的结论 |

后面的正文会解释每一项为什么出现在列表里、它改变了哪个环节，以及什么情况下可以先跳过它。

## 一、基础设施已经够了，瓶颈在协作机制

2026 年，多 Agent 的基础设施问题已经基本有了答案。A2A 和 ANP 协议提供了 Agent 之间直接通信的标准层；Matrix 协议（在 AgentTeams 等工业系统里被用作通信总线）让 Agent 和人类可以共用一条消息通道；MCP 标准化了工具接入方式；共享文件系统、凭据隔离、可观测性日志——这些问题都有了工程方案。

能不能让消息发出去，答案已经是"能"。

问题转移到了另一层：**该说什么、怎么达成共识、说完之后如何沉淀。** 这是协作机制层的问题，不是基础设施层的问题。消息通道存在，并不意味着团队知道要对齐什么、用什么方式决策分歧、把这次任务的教训存在哪里让下次能用到。

2025–2026 年的研究开始认真对待这个问题。Meta-Team（arXiv:2605.29790）和 EvoChamber（arXiv:2605.11136）分别从协作演化和群体共进化角度，给出了当 Agent 拥有协作机制后系统表现提升的实验证据。EvoChamber 的消融实验里有一个值得直视的数字：关掉协作进化机制之后，20 个 Agent 的群体和 1 个 Agent 的表现没有统计显著差异。多 Agent 的价值不来自数量，来自机制。

把这个结论反过来读：**在协作机制到位之前，增加 Agent 数量不产生任何收益。**

## 二、Leader-Worker 能做到什么，做不到什么

当前主流多 Agent 框架大多采用 Leader-Worker 架构。CrewAI 的官方文档对 hierarchical process 的描述是：manager agent "coordinates the workflow, delegates tasks, and validates outcomes"——协调工作流、委派任务、验证产出。这个描述准确，也说明了它的边界：Leader 是一个分发器加验收器，不是一个能和 Worker 共同讨论方案的角色。

这套架构能稳定解决的问题有几类：把一个大任务切成有依赖关系的小块、按 Worker 的能力分配工作、在 Worker 完成后检查结果是否符合预期、在某个 Worker 失败时触发重试或替换。对于规则清晰、依赖关系固定的流程，这已经够用。

它做不好的部分，集中在三个地方。

第一是**执行层的可行性在规划阶段不可见**。Leader 把方案制定完再拆给 Worker 执行，Worker 到了实际操作层面才发现某个假设是错的——比如"这个表我拿不到"、"这个服务的 API 不支持批量更新"。这时候已经消耗了大量上下文，方案需要改，但改动往往只改了出问题的那一条，没有重新检查其他 Worker 的任务是否受到影响。

第二是**Worker 之间没有信息通道**。每个 Worker 只能向 Leader 汇报，不能直接告诉其他 Worker 自己的发现。这不只是沟通效率的问题，更是知识损耗的问题：一个 Worker 在执行中发现了一个对整体架构有影响的约束，在当前结构里没有路径把它传递给需要知道这件事的队友。

第三是**任务结束后没有团队层面的积累**。个体 Agent 的自进化机制（见《[Agent 自进化：它究竟在修改什么](/posts/self-evolving-agents-overview/)》）改变的是"我怎么把某类任务做得更好"。团队层面的问题是另一个：这个组合、这套协作方式怎么做得更好。这是不同粒度的问题，需要不同的存储和触发机制。

![Leader-Worker 星型结构与 Agent Team 信息流对比](/images/posts/agent-team-vs-leader-worker.svg)

Leader-Worker 架构没有错。它把已有的工程问题解决得相当完整：任务分发、能力匹配、结果验收——这些都是真实的需求，这些机制都值得保留。需要补的是它有意裁掉的那些通道：向上汇报和等待指令之外的横向关系。

## 三、五个机制，补上 Leader-Worker 留下的空白

![Agent Team 的七个协作机制](/images/posts/agent-team-mechanism-map.svg)

### 启动协议：讨论先于执行

Leader-Worker 的默认流程是 Leader 给出方案，Worker 执行。这个流程的问题不在 Leader 的能力，而在信息结构：Leader 在制定方案时，每个 Worker 的局部约束信息并不在 Leader 的上下文里，而 Worker 在执行时才能看到这些约束。

启动协议把这一步提前。Leader 给出初版方案之后，不立即进入执行，而是让每个 Worker 从自己的角度给出可行性反馈：资源约束、权限缺口、替代路径、与其他任务的依赖冲突。这些反馈汇总之后，Leader 整合修订，形成最终的 OKR，各方确认后才开始执行。

![把执行层约束提前到规划阶段](/images/posts/agent-team-startup-phases.svg)

这不是开会，而是一次信息同步。关键约束是：Worker 的反馈必须是具体的——"这个接口不支持分页，我只能全量拉取"，而不是"感觉有风险"。模糊的反馈进不了方案修订，等于没有发生。

实现上，启动协议需要一个结构化的反馈格式。每个 Worker 的回应包含三个字段：可行性判断（能做 / 需要条件 / 做不到）、具体约束或条件，以及替代建议（如果有）。Leader 的整合步骤是把这些约束写回 OKR 的每个 KR 条款旁边，然后让受影响的 Worker 确认。这个过程的代价是 2–3 轮额外的通信，收益是在执行阶段减少中途返工。

```yaml
# Worker 启动反馈格式（结构化，非自由文本）
worker_id: data-agent
task_ref: KR-1  # 采集过去 30 天的接口调用分布
feasibility: conditional  # 能做 / conditional / cannot
constraints:
  - "服务 B 的调用日志只保留 7 天，当前方案窗口不够"
  - "需要 read 权限访问 log-store/service-b"
alternative: "改用 APM 平台的接口调用聚合数据，覆盖 90 天"
```

这个格式的关键不是字段名，而是"可行性"必须是枚举而不是模糊描述，"constraints"里必须是可核查的事实而不是感受。Leader 收到这份回应之后，能直接判断方案是否需要修订，不需要再追问。

启动协议在两种情况下可以跳过：任务足够小，且 Leader 对每个 Worker 的执行边界足够熟悉；或者这是一个已经被团队多次执行过的标准流程，可行性已知。

### 横向通信：Worker 之间需要说话

补上 Worker 之间的通道之后，需要立刻回答另一个问题：什么时候说、说什么，以及说话的成本由谁承担。

不加限制的全连接是最直觉的方案，也是代价最高的方案。N 个 Worker 的全连接通道是 O(N²) 的，每个 Worker 的上下文都要处理来自所有队友的消息。在 Worker 数量超过四五个之后，上下文成本会迅速失控，而大多数消息对大多数接收方并不重要。

实用的设计是**按能力路由加通信预算**。通信分三类：广播（发现了一个对整体有影响的约束，需要告知所有人）、定向查询（我需要某类信息，谁能提供）、求助升级（我遇到了超出自己能力范围的情况，需要 Leader 或有该能力的 Worker 接入）。Leader 在岗位描述里声明每个 Worker 的能力标签，定向查询通过能力路由找到目标，而不是广播给全体。

通信预算的作用是给每个 Worker 一个轮次内可以发出的通信量上限，超出时必须向 Leader 申请。这不是限制沟通，而是让代价可见：如果一个 Worker 需要频繁超预算，说明它的任务边界划得不对，或者它缺少某种能力需要补充到工具池里。

横向通信的另一个设计点是消息格式。Worker 之间传递的消息不应该是对话体——"我觉得这里有个问题"——而是结构化的事实载体：我发现了什么、它影响了哪些任务、我的建议是什么。Anthropic 在多 Agent 工程实践的公开资料里反复强调这一点：Agent 之间传递的应该是事实和决策，不是思维过程。

```yaml
# Worker 横向通信消息格式
from: data-agent
to: migration-agent   # 定向，不广播；能力路由确定目标
type: constraint_notice
finding: >
  service-c 的接口 /v1/settle 在当前采样窗口调用量为 0，
  但代码中有 feature flag 条件调用（flag: PAY_NEW_FLOW）。
  在 flag 未开启的环境下不发出请求，不等于接口已废弃。
affects_kr: [KR-3]  # 迁移侧的 KR
recommendation: "为条件调用接口单独加标注字段，不按调用量判断废弃"
requires_response: false  # 通知类，不需要回复；查询类设为 true
```

`requires_response: false` 是一个设计细节：不是所有横向通信都需要对方回复，只有查询类消息才需要等待。把二者混在一起会让接收方的上下文里充满不需要处理的消息。

### OKR 由协商产生

OKR-Agent（arXiv:2311.16542）是目前唯一直接把 OKR 机制引入 Agent 系统的研究工作。它验证了一件事：OKR 的层级分解——把顶层目标拆成子目标和可量化的 Key Result，再分配给专门的 Agent——放到 Agent 系统里是可行的。这是有价值的，但它本身的设计是单个 Meta-Agent 递归分解，Worker 是目标的接收方，不参与制定。

这个设计的局限在实际工程里很常见：Leader 分下来的 KR 在执行层面不可测量、验收条件不清晰、或者依赖一个 Worker 没有权限访问的资源。如果 Worker 不能在制定阶段说出来，这些问题就只能在执行中暴露。

协商产生的 OKR 和单方面分配的 OKR 的差别，不在目标的内容，在验收条件的质量。每个 KR 需要有四个字段：要达成什么、怎样测量、谁负责验证、依赖什么资源或权限。其中"怎样测量"和"依赖什么资源"这两个字段，在没有执行层参与的情况下，很难由 Leader 单独写准确。

```yaml
# 经过协商的 KR 条款示例
kr_id: KR-2
objective: "完成全量旧接口调用方的识别"
measure: "在 call-inventory.json 中列出所有调用位置，覆盖率由 cache-agent 交叉核验"
owner: data-agent
verifier: cache-agent  # 独立验证，不由 owner 自我报告
depends_on:
  - resource: "log-store/service-b"
    permission: read
    status: pending  # 启动时标记为待申请
milestone: "data-agent 完成后推送事件，触发 schema-agent 启动"
escalation: "超过预计时间 2h 未推进度，由 Leader 接入"
```

`verifier` 和 `depends_on.status` 这两个字段是协商才能产出的：前者需要知道谁有能力做交叉核验，后者需要执行层确认权限是否已经就绪。

进度跟踪是 OKR 的另一半。里程碑触发检查，而不是定时轮询：数据侧完成采集时主动推送一条进度更新，触发依赖它的 KR Owner 更新状态。如果某个 KR 在预期时间内没有推送，Leader 的进度模型应该主动标记为"待确认"而不是静默等待。偏离预警的阈值和升级路径需要在 OKR 制定阶段就写清楚，而不是等出问题了再决定怎么处理。

### 集体复盘：三层，非对称流

Agent 自进化处理的是个体层面的问题：一个 Agent 下次能否把同类任务做得更好。集体复盘处理的是团队层面的问题：这个组合、这套协作方式下次能否更流畅。两者是不同粒度的议题，需要分开设计。

Meta-Team 的三层演化给出了一个有用的分层框架。任务过程中，Agent 层发生微复盘：Agent 主动向队友索取"我的输出对你的决策产生了什么影响"这类反馈，更新自己对协作关系的理解。阶段交付后，交互层发生中盘：回顾这一阶段各 Worker 之间的通信，更新对彼此能力和沟通方式的理解，写成可以在下一个任务里参考的队友画像。任务结束或周期性，团队层发生总复盘：讨论组织本身是否合理——岗位划分是否带来了不必要的边界，是否需要引入某个新能力，现有规则里哪条造成了反复摩擦。

![团队复盘与演化的三个层次](/images/posts/agent-team-evolution-levels.svg)

复盘要产出三类资产，而不是一份流水账叙述。方法论是这次成功或失败的关键因素抽象成的可复用原则，例如"遇到跨服务约束时，先让受影响的 Worker 同步，再由 Leader 拍板修订方案"。协作模式是哪种 Worker 组合和通信方式在这类任务上有效，形成 team playbook。反模式是踩过的坑和走过的弯路，作为下次的提前规避清单。

这三类资产分两个层次存储：团队共享知识库（所有 Worker 都能检索）和角色专属经验（只对当前岗位有意义的细节）。知识流向上，EvoChamber 的 CoDream 机制引入了非对称转移的设计：把洞察从高表现的 Agent 路由到表现低于中位数的 Agent，而不是向所有人对称广播。这样做强化了专精而不是把所有人拉平稀释。

对知识流向的控制是有意义的设计，不是优化细节。如果把所有人的经验都向所有人广播，接收方会淹没在大量与自己岗位无关的信息里，反而降低信噪比。

### Mission 与核心宗旨：无人拍板时的锚点

OKR 回答"这个季度我们具体做什么"，Mission 回答"我们为什么存在、什么时候牺牲速度换质量"。二者不是同一层面的东西，但现有的多 Agent 系统设计里，Mission 这一层几乎是缺席的。

对 Agent Team 来说，Mission 的作用在于让团队在 Leader 不下场的情况下自主做取舍。遇到多任务抢占同一资源、遇到"快但脏"和"慢但净"两种方案、遇到两个 KR 之间产生冲突——如果没有共同目标做锚点，每个 Agent 只能从自己的局部视角推理，推出的结论会不一致，而且都有各自的局部合理性，最终还是需要人来拍板。有了 Mission，团队应该能在内部自洽地收敛出一个方向，而不是把每一个中等规模的分歧都上升到人工决策。

Mission 还是 Leader 鼓励 Worker "放开尝试"时的语义基底。"放开尝试"如果没有边界，对 Agent 来说是一个处理不了的指令；有了 Mission 和宗旨，Agent 知道什么值得为之承担成本、什么是不能越过的边界，能动性才不会变成不受控制的随机行为。

## 四、用一次 API 迁移走完整个协作流程

数据平台有一组旧版 REST 接口需要迁移到新版 GraphQL。旧接口有二十多个调用方，分布在三个服务里，需要同时更新调用方和接口层。这个任务交给一个 Agent Team：数据侧负责摸清所有调用方和调用频率，接口侧负责设计新 GraphQL schema，迁移侧负责生成适配代码和迁移脚本。

**启动阶段**：Leader 给出初版方案——三个 Worker 并行启动，数据侧先摸底，接口侧同步设计 schema，迁移侧在另外两个就位后生成代码。数据侧 Worker 回应：服务 B 的调用日志只保留七天，如果按这个时间窗口采样，会遗漏低频但高风险的接口。接口侧 Worker 回应：GraphQL schema 的设计需要知道哪些字段是调用方必须有的，不能在数据侧完成之前并行推进。Leader 修订方案：数据侧先完整摸底，接口侧在拿到数据后开始，迁移侧依赖接口侧产物，串行改为依赖触发。这个调整把原计划节省的并行时间还了回去，但代价是可以接受的，因为如果不调整，接口侧的 schema 设计会在后面被推翻重做。

**执行阶段**：数据侧在采集日志时发现，服务 C 有一处调用在调用之前会先做一次 feature flag 检查，只在 flag 开启时才发出请求。这意味着在当前采样窗口里，这个接口的调用量是零，但它并没有废弃。数据侧通过横向通信告知迁移侧：这个接口不能按"无调用 = 可废弃"的规则处理，需要单独标记。迁移侧在生成适配代码时对这个接口加了例外标注，并在 OKR 里把"feature flag 条件接口处理"标记为一个独立验收项，等接口侧确认 schema 覆盖了这种情况。这件事如果没有横向通信通道，只能在迁移侧生成代码、接口侧检查输出时才被发现，代价是一轮返工。

**收尾与复盘**：任务完成后，团队层复盘产出两条方法论：第一，有 feature flag 控制的接口不能用采样窗口内的调用量判断是否废弃，摸底阶段应该先检查代码里有没有条件调用；第二，并行执行计划里的依赖关系应该在启动阶段让受影响的 Worker 过一遍，不能只由 Leader 从外部判断。这两条写进了团队的 playbook，下次同类任务的启动协议里会把它们作为检查项。

这个例子的价值不在于流程图上看起来更严密，而在于两个具体的节点：数据侧发现的约束在当前轮次内传递给了迁移侧，而不是等到迁移侧自己碰到才处理；这次任务里的系统性认知被写成了规则，而不是停留在执行这次任务的 Agent 的个人记忆里。

## 五、现有研究怎样验证这些机制

上面描述的五个机制不是纯粹的工程推演，它们在最近两年的研究里都有对应的实验验证。这一节把研究证据和工程机制对应起来，帮助读者判断哪些结论是有实验支撑的，哪些是在特定条件下成立的。

**关于协作机制的必要性**：EvoChamber（arXiv:2605.11136，2026 年 5 月）提出了 CoDream（Collaborative Dreaming）机制，在任务完成后触发五阶段循环（Reflect、Contrast、Imagine、Debate、Crystallize），并采用非对称知识转移——把洞察从高表现 Agent 路由到低于中位数的成员，而不是对称广播。消融实验的结果是：去掉 CoDream 机制之后，20 个 Agent 的群体表现和 1 个 Agent 没有统计显著差异。这是目前最直接的证据，说明协作机制本身是多 Agent 价值的来源，而不是 Agent 数量。

**关于团队演化的层次**：Meta-Team（arXiv:2605.29790，2026 年 5 月）设计了三层协作演化，并报告在测试集上优于不进化的多 Agent 基线。它还附带了一个值得注意的负面发现：初始手工设计的多 Agent 系统在部分测试里的表现不如单个 Agent，说明多 Agent 的优势必须通过协作机制才能解锁，而不是默认就有。

**关于个体经验积累**：Experiential Co-Learning（arXiv:2312.17025，ACL 2024）在软件开发任务上验证了从历史轨迹中提取"捷径经验"、用 RAG 在新任务里复用的机制，并报告了任务质量的显著提升。这个结果说明个体经验积累是有效的，但它积累的是角色内部的经验，不是团队级别的协作模式。这正是集体复盘要补的位置。

**关于分工结构的选择**：2025 年 1 月的综述（arXiv:2501.06322）对多 Agent 系统做了多维度的分类，涵盖协作类型、协调策略、通信结构和动态性等维度。其中有一个结论和本文的设计方向一致：越是需要灵活交互、频繁横向求助的场景，全连接或部分连接的结构比严格层级结构更合适。这支持了横向通信机制的设计选择，但同时也说明设计需要和具体场景的交互模式匹配，没有普适答案。

## 六、失败模式与适用边界

这五个机制不是越多越好，引入每一个都有代价。

**启动协议的代价**是延迟执行。如果任务足够小、Leader 对 Worker 的边界足够熟悉，启动协议的额外通信轮次会让总成本更高而不是更低。经验法则：任务预计需要五个以上工具调用轮次，或者跨越两个以上不同能力边界，才值得走完整的启动协议。

**横向通信最常见的失败方式**是变成广播洪水。如果没有通信预算和能力路由，每个 Worker 发现的任何信息都倾向于广播给全体，接收方的上下文被大量无关信息填满，反而降低了推理质量。设计横向通信时，发送方的责任是判断这条信息需要谁知道，而不是让 Leader 来筛选所有消息。

**OKR 协商最常见的失败方式**是形式化的参与。Worker 在启动阶段给出反馈，但反馈是模糊的，Leader 把它解读成"没有问题"然后继续。这比不走协商流程更危险，因为系统认为执行层的约束已经被纳入考量，实际上并没有。解决方式是要求 Worker 的反馈必须回答具体字段：可行性判断、依赖条件、验收标准，而不是自由文本。

**集体复盘的失败模式**是每次任务都产出方法论，但方法论从未被检索和使用过。存进去的知识如果不经过索引和触发机制，就等于没存。复盘的价值取决于两件事：知识以可检索的形式存储，以及在相关任务启动时有机制把它们带入上下文。如果这两点没有，复盘只是一个仪式。

**Mission 和宗旨在短生命周期任务里是过度设计**。一次性的批量数据处理任务不需要 Mission，因为它不会遇到原则冲突的场景。Mission 的价值在持续运行、反复决策的系统里才体现出来：当团队面临互相竞争的目标，或者需要在无人监督的情况下持续优化某个方向时，Mission 作为共识基底才真正在用。

一个更根本的边界条件：这五个机制假设 Agent 之间的协调成本低于它们各自独立执行的效率损耗。如果每次任务都只有两个 Worker、执行时间不到五分钟，协调机制本身的开销就占了总成本的大部分。规模越小，这套机制的收益越低。EvoChamber 的实验用了相对较大的 Agent 池；Experiential Co-Learning 的结论在重复执行同类任务的场景下最显著。这些场景条件需要对应到实际任务里才能判断适用性。

## 七、从一个最小改动开始

如果现在的系统是一个标准的 Leader-Worker 架构，已经能稳定完成任务，在此基础上引入协作机制，不需要一次把五个机制全部加进去。

最小的起点是**给启动协议加一轮反馈环**。Leader 给出初版方案之后，让每个 Worker 在开始执行之前用结构化格式回应一次：可行性判断、依赖条件、已知约束。这一步不需要修改现有的任务执行架构，只需要在 Leader 分发任务之后、Worker 开始执行之前插入一轮通信。代价是额外的 Token 消耗，收益是把执行阶段最常见的"做到一半发现方向不对"提前到规划阶段处理。

第二步是**给 Worker 加一个定向查询通道**，允许 Worker 在执行中向另一个 Worker 发出查询，格式是"我需要某类信息，你那边有吗"，目标由能力路由决定而不是广播。这比全连接横向通信的代价低得多，已经能覆盖最常见的信息孤岛场景。

第三步，**在任务结束后加一次结构化复盘**，输出三个字段：这次成功的关键因素、这次的反模式、下次相同类型任务应该改变的一件事。把这些结果存进可检索的知识库，并在下次同类任务启动时把最相关的几条带入 Leader 的 Context。

这三步里的每一步都可以独立评估：加了之前和加了之后，任务完成质量、返工频率、总上下文消耗各是多少。不需要等到五个机制都就位才能判断方向是否正确。

关于是否应该采用完整的团队机制，有一个简单的判断起点：如果在当前系统里，一个 Worker 踩到的坑超过一次被另一个 Worker 独立踩到，那么横向通信的收益就已经覆盖了它的成本。如果任务结束之后，下次启动时团队表现没有任何提升，那么复盘机制没有有效地把知识带回执行层。这两个信号都不需要复杂的度量体系，从任务日志里就能看出来。
