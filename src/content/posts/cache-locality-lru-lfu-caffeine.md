商品 A、B 经常有人查看，商品 X、Y 只在一次批量浏览中出现。缓存装满以后，应该留下谁？只看“刚访问过”，容易让一次性数据挤掉热点；只看累计次数，又容易让已经冷下来的商品长期占位。

Caffeine 是 Java 进程内的缓存库。它的容量淘汰策略把近期访问和访问频率结合起来：**新数据先进入一个小窗口，离开窗口时再竞争主缓存的位置；留下的数据通过试用和保护两个区域继续流转。** 这套组合叫 Window TinyLFU，简称 W-TinyLFU。[官方策略说明](https://github.com/ben-manes/caffeine/wiki/Efficiency)

![Caffeine 容量淘汰主线：新数据进窗口，超出窗口后竞争主缓存，留下的数据按访问晋升或降级](/images/posts/caffeine-eviction-mainline.svg)

先读上面的正常路径，再看被淘汰的分支。全文都用商品缓存说明机制；先忽略到期和并发，把对象看成等大小条目，最后再补实现中的近似与边界。具体源码细节沿用 Caffeine 3.1.8，不把示意过程当作每个版本的逐次执行记录。

## 一、先看 LRU 和 LFU 各自解决了什么

缓存有用，是因为一部分数据会被再次访问。假设缓存只能保存三个商品，我们希望有限的位置尽量留给接下来还会被查看的商品。淘汰策略无法提前知道未来，只能从过去的请求里寻找线索。

LRU 的中文含义是“最近最少使用”：优先移除最久没有被访问的数据。常见实现用哈希表定位商品节点，用双向链表记录访问先后；每次命中就把节点移到最近端，容量不足时从最旧端删除。

例如缓存从最旧到最新为 A、B、C，再访问 A，顺序就变成 B、C、A。此时加载 X，LRU 删除 B。它关心的是最后一次访问的先后，不关心 A 之前访问过一次还是一万次。

这个规则很容易适应新热点，也容易受到扫描影响：A、B、C 原本都经常使用，突然有人依次查看 X、Y、Z。每个新商品都挤到最近端，三个旧热点依次被删除。接着用户回来看 A、B、C，又要查询数据库。这就是扫描污染：一次性访问占用了原本能产生重复命中的位置。

LFU 的中文含义是“最不经常使用”：优先移除访问频率低的数据。用最直观的累计计数模型看，A 访问了 100 次，X 只访问了 1 次，保留 A 很合理。但如果 A 的访问都发生在昨天，今天的热点已经变成 X，旧计数反而会阻碍替换。实际 LFU 可以增加衰减等机制，所以这个问题针对的是不让历史减弱的累计模型。

| 策略 | 主要依据 | 优点 | 容易遇到的问题 |
| --- | --- | --- | --- |
| LRU | 最近一次访问的先后 | 新热点较快进入缓存 | 一次性扫描可能挤掉旧热点 |
| 不衰减的累计 LFU | 过去累积的访问次数 | 能识别长期反复使用的数据 | 旧热点降温后，计数仍然很高 |

这两个反例引出了 Caffeine 要处理的矛盾：既要保留近期机会，也要识别持续复用，还要让过时的历史逐渐失去影响。下面沿着一个新商品 X 的去留，依次看这些工作由谁完成。

## 二、窗口区：让新商品先获得一段机会

商品 X 第一次被请求，缓存没有它，应用从数据库加载数据，再交给缓存。X 先进入窗口区 Window。窗口按 LRU 管理，命中会更新访问位置；它只占整个缓存的一部分。

为什么不直接比较访问次数？如果 X 刚出现就必须战胜长期热门商品，新商品天然吃亏。即使 X 接下来会成为热门，也可能在第二次访问之前就被拒绝，连续请求都要回源。

窗口让 X 先留在缓存里。如果用户紧接着反复查看 X，这些请求可以命中，它也会积累被保留的依据。如果 X 只出现一次，后续新商品逐渐进入，X 就会走到窗口的最旧端。

窗口超出预算时，最旧的条目被选为离开窗口的候选。注意，这个候选不一定是刚刚加载的商品：Y 的到来，可能把更早进入的 X 推向主缓存。因此，“新数据先住窗口”和“窗口最旧者去竞争主缓存”是两个连续动作。

这里的“窗口”指一块有容量预算的缓存区域，不是“每个商品保证停留十秒”。X 能留多久，取决于区域大小和后续访问。主缓存还有空位时，候选可以留下；真正需要腾位置时，才要比较谁更值得保留。

窗口也会承受扫描压力。一次性商品仍可能把窗口里的其他条目挤出去，但它们不会仅凭一次新访问，就无条件替换主缓存的旧热点。这个隔离使大范围扫描的影响更容易被限制在一部分空间内。

## 三、TinyLFU：离开窗口后，比较谁值得留下

假设整个缓存已经满了。X 从窗口出来，想继续留下；主缓存中最久未访问的试用条目 A，则成为待淘汰者。此时需要作出的判断是：保留 X、删除 A，是否比保留 A、删除 X 更划算？

这一步叫“准入”，即决定候选者是否值得占用主缓存位置。TinyLFU 是用少量统计信息估算近期访问频率的准入机制。它不需要把全部商品按次数排序，而是比较选出来的两个对象。[TinyLFU 原始论文](https://arxiv.org/abs/1512.00727)

![窗口候选 X 与主缓存待淘汰者 A 比较估算频率，决定谁离开缓存](/images/posts/caffeine-admission-choice.svg)

例如 X 的估算频率是 1，A 是 6，通常保留 A，删除 X。这次读取 X 的用户已经获得商品数据，删除缓存条目并不会让请求失败；它影响的是下一次访问是否还需要回源。

如果 X 在窗口里多次被访问，估算频率变成 7，而 A 是 3，就倾向保留 X，删除 A。**窗口提供积累热度的机会，TinyLFU 决定这份热度是否足以换取主缓存的位置。** 两者各自处理一部分问题。

频率更高的候选通常胜出，相同频率通常倾向保留原有条目，以减少没有明确收益的替换。3.1.8 的实现还为防御哈希碰撞攻击保留了小概率随机放行，因此不能把这个主规则写成对每次执行都成立的严格公式。

从实现上说，3.1.8 会先把窗口候选移动到试用区，再在总容量超限时比较和删除节点。图中的“准入关口”描述逻辑结果，不表示源码里还有一个独立的等待队列。对应方法是 `evictFromWindow`、`evictFromMain` 和 `admit`。[3.1.8 源码](https://github.com/ben-manes/caffeine/blob/v3.1.8/caffeine/src/main/java/com/github/benmanes/caffeine/cache/BoundedLocalCache.java)

## 四、主缓存：试用区和保护区怎样升降

X 赢得比较后，也没有获得永久席位。主缓存内部还要区分“刚留下的数据”和“留下后又被使用的数据”。为此，它采用分段 LRU，也就是把条目分成两个按最近访问排序的区域。

**试用区 Probation** 放置刚从窗口转来的条目，也接收从保护区降级的条目。X 留在这里后，如果再次命中，就可以晋升到保护区的最近端。这个额外的访问说明：它在离开窗口之后仍然有复用。

**保护区 Protected** 给这些已经表现出复用的条目更多保留机会。命中保护区里的商品，也会把它移到最近端。若保护区超出预算，最久没访问的条目降回试用区的最近端，而不是立刻从整个缓存删除。

![试用区命中后晋升，保护区超预算后降级，试用区最旧者参与淘汰竞争](/images/posts/caffeine-main-segments.svg)

比如 X 在试用区再次被查看，晋升到保护区。此时保护区装不下了，最旧的 B 被降回试用区。B 后面若再次被访问，还可以重新晋升；若一直没人使用，就会逐渐走到试用区的最旧端，成为下一轮竞争的待淘汰者。

这也回答了“已经保护起来的数据怎么淘汰”：近期持续访问让它留在保护区；长期不访问，其他复用条目逐渐占据保护区，它就会降级，再面对淘汰。保护描述的是相对优先级，没有跳过容量约束。

区域内的移动主要依靠节点和链表，不需要每次读取都对全部商品按频率排序。LRU 负责选出较久没用的对象，TinyLFU 再判断替换价值。两种信号因此在同一次决策中协作。特殊情况下候选不足，淘汰路径也会继续查看其他区域，不能把“优先从试用区选”理解成“只能淘汰试用区”。

## 五、频率草图：怎样记热度，又怎样忘掉旧热点

前面反复提到“估算频率”，因为永久保存所有历史商品的精确计数也会耗尽内存。即使商品被删除，如果计数表一直增长，缓存的容量限制就失去了意义。

Caffeine 使用频率草图 FrequencySketch：一块由很多小计数器组成的统计结构。一个商品 key 经哈希计算找到四个计数位置，记录访问时递增这些计数，查询热度时取四个值的最小值。

例如 X 对应的四个计数值是 5、8、5、6，估算频率取 5。不同 key 可能共享某些位置，导致计数被别人抬高；取最小值可以降低局部碰撞的影响，但仍然可能误判。因此这些数适合辅助缓存去留，不适合充当业务访问量或排行榜的精确数据。

![X 映射到四个小计数器，取最小值估算频率，并在采样达到阈值后衰减](/images/posts/caffeine-frequency-aging.svg)

3.1.8 使用四位计数器，单个计数最高到 15，达到上限后不再继续增长。采样推进到阈值时，计数整体减半并向下取整，让旧访问的影响逐渐减弱。[FrequencySketch 源码](https://github.com/ben-manes/caffeine/blob/v3.1.8/caffeine/src/main/java/com/github/benmanes/caffeine/cache/FrequencySketch.java)

回到商品缓存：A 曾经很热，但后来没有新访问，旧计数会随着衰减降低；X 持续被访问，一边经历衰减，一边获得新计数。这样，新热点就不必永久背负“上线时间晚”的劣势。

衰减由采样推进触发，不是精确统计“过去五分钟”，也不是到点删除商品。它只改变后续比较的依据；条目是否仍能读取，还取决于是否被淘汰、是否到期等规则。缓存条目消失后，对应计数位置也未必立即归零，这些共享位置会继续携带一部分历史，再逐渐老化。

## 六、把一个商品的去留连起来看

现在固定同一个初始状态：缓存已满，X 在窗口里，A 是主缓存试用区最旧的条目，B 是保护区最旧的条目。下面取普通的频率比较路径，忽略碰撞、衰减和并发带来的变化，观察每一步分别改变什么。

| 步骤 | 发生的访问或决策 | 条目怎样移动 |
| --- | --- | --- |
| 1 | 用户反复查看 X | 窗口内命中，X 移到最近端，积累热度 |
| 2 | 后续商品进入，X 最终成为窗口最旧者 | X 离开窗口，成为主缓存候选 |
| 3 | X 估算频率为 7，A 为 3 | 删除 A，X 留在试用区 |
| 4 | 用户再次查看 X | X 从试用区晋升到保护区 |
| 5 | 保护区超出预算 | B 降回试用区，尚未被删除 |
| 6 | B 长期没有新访问 | 逐渐成为试用区最旧者，参与后续淘汰竞争 |

如果把第三步改成 X 只有一次访问、A 有六次，通常就会删除 X，后面的晋升路径也不会发生。一次性数据能获得窗口机会，但没有因此获得长期占位的保证。

这里没有一步要求先在全部条目中找“访问次数最少的那个”。队列顺序负责提供候选，频率摘要负责比较，分区负责让反复复用的条目更难被一次性访问影响。理解这个分工，比记住一个算法缩写更容易推导实际行为。

## 七、自适应与并发维护，补上实际实现的边界

窗口应该多大，没有一个比例能适合所有请求。窗口大一些，突发新热点有更多停留机会；同时主缓存能保护的旧热点就变少。窗口小一些，更有利于保留稳定热点，也可能让新商品过早离开。

Caffeine 会观察一段访问的命中表现，尝试调整窗口与主缓存的容量划分，再根据效果继续调整方向。这种方法叫爬山调整，核心是沿着表现变好的方向试探，而不是预先知道最优比例。所以常见资料里的区域百分比只能结合版本和初始设置理解，不能当成整个运行期间不变的结构。[官方 Design 文档](https://github.com/ben-manes/caffeine/wiki/Design)

另一个实际问题是并发。如果每次命中都争抢同一把锁来移动链表，维护策略本身就会拖慢读取。Caffeine 把业务数据访问和策略维护分开：读请求取得值后，通过缓冲记录访问事件，维护路径再批量调整队列和频率。

竞争下允许丢失部分读事件，因为少记一次访问影响的是预测精度；这不意味着把已经查到的商品值随机丢掉。写入和删除涉及结构一致性，不能按相同方式随意丢弃。维护也可能由调用线程参与，不能把它理解成所有工作都由一个固定后台线程完成。[官方并发维护说明](https://github.com/ben-manes/caffeine/wiki/Design)

因此，正文图示表达的是策略主线，真实并发运行未必呈现严格的逐次 LRU 顺序；写入后的队列维护与容量收敛也可能稍后发生。容量预算用于约束缓存，不等于为整个 JVM 堆提供精确到每一时刻的内存上限。

最后还要守住两条边界。第一，W-TinyLFU 主要回答容量不足时保留谁；过期回答数据何时失效，刷新回答怎样加载新版本。热门商品同样可能到期，未到期商品也可能先被淘汰。[官方 Eviction 文档](https://github.com/ben-manes/caffeine/wiki/Eviction)

第二，Caffeine 是进程内缓存。多个服务实例分别统计各自看到的访问，重启会失去本地热度，扩容后也要重新积累。请求几乎不重复、活跃商品远多于容量，或者热点变化快于策略适应时，它仍然可能频繁回源。容量策略能改善保留决策，无法创造重复访问，也无法替代跨实例的数据一致性协议。
