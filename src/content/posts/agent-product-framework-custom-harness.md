要做一个排障 Agent，有一个很直接的问题：Codex、Claude Code 已经能读代码、调用工具、连续调查，为什么还要用 Spring AI 再开发一套？把公司里的日志查询、配置查询和代码检索接给它们，外面加上自己的任务管理，不就可以了吗？

可以。封装成熟 Agent 是一条完整的开发路线，不能因为它最初面向编程，就把它排除在业务 Agent 的候选方案之外。能否用来排障，要看它能否接到需要的工具、能否满足数据与权限要求，以及执行方式是否适合任务。

这里比较三种实现：复用 Codex、Claude Code 的执行系统；使用 Spring AI 这样的开发框架组织模型与工具；自己实现模型调用、工具调度和任务恢复这套运行程序。第三种通常叫自建 Harness，也就是自建模型外面的执行框架，不涉及训练大模型。

最容易混淆的地方是可观测性。成熟 Agent 并不意味着只能看到最后一句答案。它们有程序接口、事件和扩展点，可以记录执行过程，也能干预部分操作。Spring AI 的优势需要具体到“我要在哪个位置插入什么代码”，不能只说“框架更透明”。

下面一直用一个排障任务比较。产品接口能力依据官方文档；业务架构、故障处理和选择建议属于工程设计推演，不代表已经在某个公司项目里验证过。接口会随版本变化，接入时仍要核对实际使用的版本。

## 一、先固定任务：我们究竟要做什么

假设用户提出一个问题：“某个用户完成任务了，为什么奖励没有到账？”

系统已有任务记录、奖励流水、服务日志和代码仓库。Agent 可以查询这些信息，但不能发放奖励，不能修改生产配置，也不能访问与当前问题无关的用户数据。最终需要返回一个有证据的解释：问题停在哪一步，哪些记录支持这个判断，还有什么信息没有拿到。

初始状态很明确：只知道用户、任务编号和大致时间，根因未知。排障可能沿着任务完成记录、奖励请求、支付结果、补偿记录往下查，也可能中途发现输入错了，先向用户补问。下一步取决于刚查到的信息，因此不能把所有路径都写成一个固定流程。

无论选哪条路线，都需要几个业务能力：创建任务、识别用户身份、检查查询范围、调用内部系统、保存证据、展示进度、判断是否可以结束。这些不会因为用了某个框架就自动出现。

三条路线的区别集中在调查过程：谁负责把已有信息组织成下一次模型输入，谁接住模型提出的工具调用，谁决定继续、等待还是停止。

| 实现方式 | 已经拿到的东西 | 仍要自己开发的东西 |
| --- | --- | --- |
| 封装成熟 Agent | 已有连续执行循环、会话机制和一组工具能力 | 业务入口、内部工具、授权、证据保存和验收 |
| 使用 Spring AI | 模型调用、工具接入等可组合能力 | 业务流程，以及所需的任务状态、上下文和恢复逻辑 |
| 自建 Harness | 自己选择复用的模型客户端和基础库 | 自己定义循环、事件、调度、状态与恢复协议 |

“自己开发”并不意味着每一行都从零写。自建也可以复用模型 SDK、数据库和现成工具；使用框架也可能自己写循环。要比较的是接手了哪段执行逻辑。

## 二、在 Codex、Claude Code 上封装，到底怎么封装

这里只讨论通过程序接口接入运行能力，不讨论自动点击聊天窗口、复制答案。后者很难可靠地关联任务、处理取消和捕获结构化结果。

封装后，用户仍然使用你的排障页面。后端先创建自己的任务，再启动或续接一个 Agent 会话，把问题、允许范围和必要证据交给它。查询日志、读取配置、查奖励流水这些能力，由你通过受支持的工具接口提供。Agent 决定何时调用，真正的查询由你的工具服务执行。

你可以把成熟 Agent 想成后端里的一个调查执行器。网页、业务数据库、员工身份、任务编号都不需要交给它管理。它接收调查任务，在给定能力范围内行动，把执行事件和候选结论返回给你的服务。

![封装成熟 Agent 时，业务服务和执行器怎样协作](/images/posts/agent-wrapper-investigation-flow.svg)

图里的权限检查放在工具服务上。Agent 提出“查这个用户的流水”，工具服务根据服务端绑定的身份和任务范围决定是否允许。不能直接相信模型传过来的员工 ID，也不能因为提示词写着“只查当前用户”就省掉后端检查。

本地维护上下文也可行。比如任务库长期保存完整证据，启动调查时只交给 Agent 问题摘要和证据索引。需要详细日志时，再由工具返回一段相关内容。这能避免每次把所有材料一次性塞进去。

不过，“证据保存在本地”和“模型完全没有看到证据”是两回事。返回给 Agent 的工具结果通常会进入后续模型输入。即使工具服务、运行进程都在内网，调用外部模型时仍要检查哪些信息会离开内网。使用 Spring AI 或自建循环也一样，本地框架不会自动解决模型请求的数据边界。

这条路线的好处很具体：通用的连续调查能力已经存在，团队可以把精力用在内部工具和业务规则上。特别是需要读代码、检索文件、运行受限命令的调查，不必重新拼装这些能力。但生产权限必须按需要收窄，不能把日常编程环境里的全部权限直接搬过去。

## 三、成熟 Agent 的日志不是黑箱

以 Codex App Server 为例，它把执行过程组织为会话、轮次和执行项。会话关联一段历史，轮次对应一次用户请求驱动的执行，执行项可以是工具调用、命令执行或消息。

客户端能接收执行项开始和结束等事件。自定义工具调用会带出工具名和参数，客户端执行工具并返回结果；命令执行也有状态和输出字段。具体字段和可用性以 [Codex App Server 官方接口](https://learn.chatgpt.com/docs/app-server)为准。接入时应保存最终事件，不要只拼接流式文字来推断成功。

Claude Agent SDK 提供另一种干预方式：Hook，也就是在指定执行时机调用你写的回调。工具执行前，可以检查参数和权限、拒绝操作，或修改支持修改的输入；工具执行后，可以记录结果。它的 [Hooks 文档](https://code.claude.com/docs/en/agent-sdk/hooks)包含这些能力，但每类事件允许返回的控制字段不同，不能把某个回调的能力推广到所有事件。

因此，以下需求本身不足以排除成熟 Agent：

- 展示调查进度，记录调用过哪些工具；
- 保存查询条件、返回证据和失败信息；
- 在内部工具入口检查身份和参数；
- 把执行轨迹关联到业务任务。

事件接口提供素材，接入代码负责落库和展示。还要补齐日志的保留、脱敏、大小限制和访问权限。“支持事件”不等于你的服务已经具备完整审计。

可以设计一份自己的工具执行记录，不直接把供应方对象当成业务表结构：

```json
{
  "taskId": "diagnosis-1042",
  "attemptId": "attempt-2",
  "runtimeSessionId": "runtime-session",
  "runtimeCallId": "call-17",
  "tool": "query_reward_ledger",
  "scope": {"userId": "user-7", "taskId": "reward-task-9"},
  "status": "succeeded",
  "evidenceIds": ["evidence-31"],
  "error": null
}
```

这是应用自己的示例协议，不是 Codex 或 Claude 的原生格式。业务任务、执行尝试和运行会话分开，服务才能说明“同一个问题重试了两次，每次查到了什么”。

如果连接中断，只收到开始事件，没有结束事件，应先记为结果未确认。它可能没有执行，也可能已经执行但回执丢失。事件缺失不能直接变成“工具失败”，更不能自动变成“可以重试”。

## 四、执行日志、模型思考和每轮输入，要分开看

“能看所有步骤”有几种不同含义，混在一起会得出错误结论。

第一种是动作轨迹：调用了什么工具，参数是什么，返回了什么，是否报错。它对排障和审计最有用，成熟 Agent、框架和自建系统都可以围绕它建设记录。

第二种是模型公开输出的推理内容。某些模型提供推理文本或摘要，某些不提供。它取决于模型和服务接口，Spring AI 不会因为是框架，就自动获得模型内部完整思考。模型写出的“我打算先查流水”也是一段输出，不能证明它一定会照着做。

第三种是发送给模型的完整请求：系统指令、历史消息、工具定义、证据和调用参数。开发者在自己组装请求时，比较容易记录应用这一侧实际发送了什么。接入成熟运行时后，外部会话记录未必等于它每轮组装后的精确模型请求，能否拿到要查对应接口和实现，不能靠界面里的聊天记录猜。

即便记录了请求，也只能解释模型当时获得了哪些信息，不能保证重复请求会走相同路径。外部数据、模型版本和生成过程都可能变化。保存轨迹有助于追查故障，但“可追查”与“逐步确定重放”是两个要求。

在排障任务里，优先保存的是原始证据和动作回执。如果 Agent 说“奖励请求根本没发出去”，你要能找到任务记录和查询结果来核对。无论它输出了多长的思考，都不能替代这份证据。

## 五、能观察执行，不等于能随意改内部循环

这是封装成熟 Agent 和自己组织模型调用最有区分度的地方。

假设只想规定“查流水前必须检查身份”。放在自己的工具服务里即可。即使模型绕着提示词尝试多次，工具服务每次都会检查。也可以配合运行时提供的审批与回调。

再假设想规定“查询超过十分钟必须停止”“重复查询没有新增证据时要提醒或结束”。可以在外层统计调用、限制工具请求，并通过受支持的取消接口结束执行。需要区分取消请求已接收、运行轮次已结束、外部工具已停止，这几个状态不一定同时发生。

更深一层的要求是：每次模型调用之前，必须按自己的算法裁剪历史，只允许某几类证据进入本轮；某个工具失败后，必须保留原始输出、执行一次特定查询，再换一个模型继续；多个工具要按自己的资源预算调度。

这些要求涉及内部执行循环。成熟 Agent 的配置、工具接口和 Hook 可能覆盖其中一部分。覆盖不到时，就需要改它的运行程序、重组任务边界，或接受它已有的执行规则。不能凭“有插件”就假定每个内部步骤都能替换，也不能凭“是成熟产品”就假定什么都改不了。

如果采用 Spring AI，并由应用自己掌握循环，这段规则可以直接落在调用模型之前、执行工具之后。具体版本可能同时支持自动工具执行和用户控制执行。官方 [Tool Calling 文档](https://docs.spring.io/spring-ai/reference/api/tools.html)区分这些模式；退出默认循环后，原有观测和回调组合也需要重新检查，不能以为所有框架能力都会原样保留。

所以需要写清楚的是一个插入位置：“我要在每轮模型请求之前重新挑选证据”。如果只是说“我想控制上下文”，封装成熟 Agent 也能通过初始材料和查询工具做到很多事情，还不足以说明必须换路线。

## 六、用 Spring AI，具体多得到什么、少得到什么

Spring AI 比较适合把模型调用融入已有 Java 服务。任务状态、数据库访问、身份校验和业务规则继续使用团队熟悉的代码组织方式，模型与工具成为这些服务中的一部分。

排障系统可以先由普通代码查询任务记录，发现已经到账就直接返回；只有出现无法由规则判断的状态，才进入模型调查。模型提出查日志的请求后，应用校验范围、执行查询、保存结果，再决定是否进行下一轮。这种安排能减少不必要的开放调查。

自己控制调用循环时，可以精确决定这一轮提供哪些工具。例如查明某个用户不在授权范围内，下一轮就不给相关查询能力；拿到订单编号后，再开放订单查询工具。也能在不同阶段使用不同模型。能否这样组织、怎样保持流式输出和观测，仍取决于实际框架版本和应用实现。

下面是执行顺序示意，不是可直接运行的 Spring AI API：

```text
读取任务状态和调用者身份
如果缺少必要编号：保存 WAITING_INPUT，返回补问
根据当前阶段挑选证据和可用工具
发送模型请求，并记录应用发出的输入
如果模型请求工具：
    校验范围，保存动作记录
    执行工具，保存结果或“结果未知”
    根据结果决定下一轮、等待或失败
如果模型提交结论：
    检查引用的证据和完成条件
    通过后保存完成状态，否则补查或转人工
```

这份控制权也意味着更多工作。Spring AI 不会直接给你一套完整的排障产品，不会替你保存任务恢复点，也不会自动获得成熟 Coding Agent 的代码探索体验。读取大型仓库、执行命令、管理工作空间，以及把错误反馈组织成可继续调查的消息，仍需选择组件并集成。

如果只是想记录工具调用，重做整段循环可能不划算。假如需求是每轮都要使用业务专用的证据筛选策略，而且已有 Java 服务承载任务和权限，框架路线则比较顺手。它的收益来自复用已有业务工程体系，同时更直接地组织模型调用。

## 七、自建 Harness 和使用框架也有重叠

自建 Harness 指团队自己定义执行闭环：模型请求格式怎样统一，工具调用怎样排队，失败怎样分类，事件怎样编号，任务怎样恢复。它仍然可以使用 Spring AI 的某些组件。

因此，“用了 Spring AI”和“自建了 Harness”有时同时成立。比如模型适配和工具注册复用 Spring AI，但任务状态机、工具调度、证据存储和整个循环自己写。选型记录应该写到组件层面，避免为了归类硬把项目塞进一个互斥选项。

完全自建的优势是修改位置由自己安排。想在模型请求之前检查预算，就在那一行加检查；想将工具结果分为确定成功、确定失败和结果未知，就在协议里定义；想支持跨版本恢复，就自己设计快照和迁移。这些规则能围绕业务对象直接表达。

代价是错误也归自己处理。流式响应断了怎么办，模型同时提出多个工具怎么办，取消时哪些任务还能继续跑，恢复旧状态时怎样兼容新代码，都需要长期维护。保存了一份 messages 列表，并不等于完成了恢复系统。

“想深入理解 Agent 底层”是合理的学习目标，可以写一个小循环研究消息如何往返。但它不能单独证明生产系统应该全部自建。学习用的实现可以很小；线上实现需要明确维护人员和故障处理能力。

如果只是缺一个特殊查询工具，三条路线都能接，没有必要因此自建。只有需要改动的执行规则反复超出已有接口，而且值得持续维护时，收回那部分运行逻辑才有明确收益。也可以只替换一个调度器或上下文模块，无需一次性重做整个系统。

## 八、同一个问题，三条路线怎样走完

回到奖励未到账。假设查询后发现：任务完成记录存在，奖励流水显示业务确认失败，补偿状态正在等待处理。还没有证据表明需要重新发放，也不允许 Agent 执行发放。

封装成熟 Agent 时，后端先保存任务和查询范围，启动一个调查会话。Agent 调用任务查询工具，看到任务已完成；再调用奖励流水工具，得到确认失败的记录；随后查看补偿状态和对应日志，形成候选解释。每次工具调用都经过你自己的服务，原始证据存到任务库。

Agent 返回“当前停在业务确认后的补偿处理阶段”后，业务服务检查它引用的证据编号是否存在、记录是否属于当前用户、时间是否匹配。通过后展示结论；如果只拿到一条失败日志却没有补偿状态，就展示待确认或要求继续查询。运行时说“完成了”，不能自动替应用完成验收。

Spring AI 路线可以让前两步由程序确定执行：先查任务，再查流水。发现确认失败之后，把相关记录、工具定义和问题交给模型，请它决定要查哪条日志。拿到日志后，应用保存证据，再组织下一轮请求。这种实现把已知路径写成代码，把不确定调查留给模型。

自建 Harness 路线的正常路径可能看起来相同。区别更多在自己定义的状态与事件：每个动作先生成编号，保存请求，再交给执行器；执行器返回结果后，状态机决定下一轮；预算、暂停和恢复都使用自己的协议。它带来的价值需要在特殊规则或故障处理中体现，正常查询路径不能单独证明自建更好。

三种实现都可以保留相同的工具服务和结论验收器，也都可能得出同一个答案。不能把某条路线完成得好，直接归因于框架名称。真正影响结果的还有模型、证据质量、工具设计和调查指令。

比如成熟 Agent 已经善于读代码，但奖励流水工具只返回一个数字状态，没有解释其含义，它仍可能误判。框架路线准确提供了字段说明，就可能表现更好；把同样的说明补给成熟 Agent，也可能消除差距。对比时要先看差异出在哪一层。

## 九、工具超时和任务恢复，是封装后仍要负责的事

假设查询补偿状态时工具超时。只读查询通常可以在限制次数和时间的条件下重试，但第二次查询的数据可能已经变化，要保存查询时间，不能把不同时间的记录当成同一张快照。

如果工具有副作用，情况更复杂。比如以后允许提交人工补偿工单，远端已创建成功，但客户端没收到结果。这时直接重试可能创建重复工单。模型提供的调用编号通常只标识一次工具调用，不能自动标识同一个业务动作的全部重试。

应用需要把逻辑动作绑定到自己的幂等键，并在工具服务中核对相同键对应相同参数。超时之后先用该键查询执行记录或外部回执；明确未执行才可以重试，无法确认就等待或转人工。这套规则可以放在成熟 Agent 外面的工具服务中，同样适用于框架和自建方案。

![工具超时后，先确认外部结果，再决定是否重试](/images/posts/agent-wrapper-timeout-recovery.svg)

图中“确认未执行”不能只靠本地没收到成功事件。需要工具服务或远端协议提供足够依据，否则仍属于结果未知。

再考虑后端重启。业务任务已经有证据，但运行会话是否还在执行并不确定。恢复时要先检查已有运行状态，避免又启动一个调查造成并行重复。找不到旧会话时，可以基于已保存证据建立新的执行尝试，而不是把状态重置成从未调查。

任务状态和会话状态要分开。任务可以处于等待用户补充，即使本轮 Agent 已结束；会话可以结束，但结论没有通过验收，任务仍未完成。二者强行共用一个“完成”字段，就会出现模型提前结束、页面却显示排障成功的问题。

取消也有相同边界。中断 Agent 能阻止后续决策，但已经发到远端的工单请求可能仍在处理。应用需要标记取消后尚未确认的动作，并继续核对回执，不能把它们直接丢弃。

这些都是封装方案的工程工作，但不构成“必须自建循环”的证据。只要外层任务管理和工具服务可以承接，就可以继续复用成熟运行时。

## 十、哪些限制才真的足以改变路线

首先是所需的内部控制点没有接口。比如要求每轮发送给模型的历史都严格按自己的规则重建，而当前运行时无法满足。可以评估改源码，也可以用框架掌握请求构建。改源码后需要跟进上游变化，这时封装的维护成本会增加。

其次是部署与模型接入不匹配。工具在内网并不必然排除成熟 Agent，可以通过合规的网络和工具接入；但如果指定模型、运行环境或数据要求无法兼容，就会形成实际限制。框架和自建也要核对模型、依赖和外部调用，不能把“Java 服务”当成“完全离线”。

还有并发运行和身份隔离。需要明确一个员工的凭证、工作目录、会话和预算如何与另一个员工隔离。成熟运行时能否配合应用的部署方式，要按具体接口判断。自己开发也要真正落实隔离，不能因为有一个 taskId 就声称已经安全。

长期维护同样影响选择。封装要维护适配层和版本兼容；框架要维护业务编排、状态与依赖升级；自建还要维护整个执行协议。哪条路线更省，不只是比较初始代码行数，要看团队在哪一层已经有成熟能力。

有时三个方案都不值得。对于“任务成功且流水到账就返回成功”这样的确定判断，普通代码更清楚。可以先做规则查询，把难以枚举的调查部分交给 Agent，不必让模型接管每个数据库查询。

## 十一、用几个具体需求做选择

| 你真正需要的能力 | 可以先考虑什么 | 需要确认的边界 |
| --- | --- | --- |
| 接日志、配置、流水工具，展示调查进度 | 封装成熟 Agent | 工具接入、事件字段、数据权限 |
| 本地保存任务、证据与跨会话历史 | 外层任务服务加成熟 Agent | 任务和会话映射、续接与取消 |
| 固定规则查询加开放式代码调查 | 普通流程加成熟 Agent | 两部分之间的输入、结果和验收 |
| 每轮精确重建上下文、按业务阶段改变执行逻辑 | 框架加应用控制循环 | 版本接口、观测、状态和恢复 |
| 多处内部执行规则无法通过已有接口表达 | 局部自建，必要时自建 Harness | 长期维护范围和升级成本 |

自定义状态、审计、权限、长任务这些词不能单独决定路线。先找实现位置：能在外层任务服务做的，就不必改内部循环；能在工具入口检查的，就不必让模型承担；必须影响每轮模型请求和调度的，再检查运行时扩展点。

框架也不是天然更透明。默认自动循环里发生什么，要阅读实际代码与事件；要精确掌握每轮过程，应用需要选择合适的控制方式，并自己补充记录。自建代码同样可能缺日志、缺恢复，拥有源码不自动等于容易排查。

我会把封装成熟 Agent 留在候选里，尤其是工具齐全、只读调查、代码探索占比较高的系统。如果它满足需要的控制点，就没有充分理由只为了“用了自己的框架”重做通用能力。

对于已经用 Spring AI 做出的排障 Agent，也不用因此推翻。应说明它实际承担了什么：哪些步骤由 Java 代码固定执行，怎样挑选每轮证据，如何记录和恢复任务。若这些控制确实更适合现有业务体系，选框架有依据；如果只是连接几个工具并保存日志，封装成熟 Agent 同样可能满足要求。

三条路线最终可以共存：应用管理任务和权限，固定路径由普通代码执行，开放调查交给 Codex 或 Claude Code，某些专用模型调用继续用 Spring AI。把输入、证据和动作协议保持独立，之后才能只替换调查执行器，不必连业务系统一起重写。
