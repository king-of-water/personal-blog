我们经常记住三句话：Redis 的大 ZSet 用跳表，InnoDB 索引用 B+ 树，HashMap 的长冲突桶会变成红黑树。

但只记住这三句话，很难回答接下来的问题：它们到底在解决什么？为什么这里用跳表，那里用树？换一种能不能做？

用一个积分排行榜来看会更容易。用户完成任务后涨分，打开页面要看到前十名，也要知道自己排第几；页面还要显示昵称和头像，后台要保存积分记录。看起来都是“查用户”，但这些操作需要找的东西不同，数据放的位置也不同。

这篇沿这个例子把原因讲开。源码细节限定在 Redis 7.2.5、OpenJDK 17.0.12，数据库说明采用 MySQL 8.4 文档。涉及“换一种结构会怎样”的部分，是根据读写过程作出的分析，不是三种结构的跑分结果。红黑树能做排行榜，B+ 树也能做内存索引，不能把某个系统当前的实现理解成唯一答案。

## 一、同一个排行榜，其实在问几种不同的问题

先把数据缩到五个人，方便看清过程。A、B、C、D、E 的分数依次是 10、20、30、40、50。实际活动可以有上百万人，这里只画其中几个。

如果问“C 的分数是多少”，给出的条件是用户 C。只要有一份“用户 → 分数”的对应关系，找到 C 就能拿到 30。Java 里可以用 Map，Redis 里可以用字典一类的哈希结构。

如果问“谁的分数在 20 到 40 之间”，给出的条件变成了分数。按用户名字查得再快，也不能直接回答。没有另外维护积分顺序，就得检查所有人的分数。

如果问“前十名是谁”，同样需要积分顺序。只有五个人时，临时排一下很简单；每次打开页面都给一百万人重新排序，工作量就不同了。可以维护一个已经有序的集合，读取时从高分那一端拿结果。

如果问“C 排第几”，还要知道有多少人排在 C 前面。能找到 C 的位置，不一定能立刻知道它前面有多少人。这个区别后面会解释，它正是跳表里的跨度要解决的问题。

最后还有一个操作：C 从 30 分变成 55 分。资料里把 30 改成 55 很容易，榜单里却必须把 C 从 B、D 之间移到 E 后面。否则“按用户查分数”已经是 55，“按积分读榜”却仍把 C 放在原位置。

| 这次要做什么 | 给了什么条件 | 需要保存什么 |
| --- | --- | --- |
| 查 C 的分数或昵称 | 用户 ID | 用户到信息的对应关系 |
| 找 20 到 40 分的人 | 分数上下界 | 按分数排列的顺序 |
| 取前十名 | 榜单的一端 | 可以直接连续读取的有序结果 |
| 查 C 的名次 | 用户 C | 找到 C，还知道前面有多少人 |
| 把 C 改成 55 分 | 用户 C、新分数 | 同时改分数和它的排序位置 |

这些东西可以放在同一个系统里，但不能指望一份只按用户 ID 组织的数据，自动满足全部需求。多维护一份顺序，读取会更方便，更新时也就多了一份要修复的东西。

在这个例子里，我们让 Redis ZSet 服务实时榜单，数据库保存活动记录，应用中的 HashMap 用来按 ID 配上用户资料。这是为了说明各自的工作，不是说所有排行榜都必须用这三个组件。

## 二、先试数组和链表，就知道为什么需要更复杂的结构

最直接的办法，是把分数存在一个数组里：

```text
10、20、30、40、50
```

如果没有排序，找到某个分数只能挨个检查。先排好序，就可以从中间比较：目标比中间值大，去右半边；比中间值小，去左半边。每次排除一半，这就是二分查找。

问题出在更新。现在插入 35，要把 40、50 往后挪，给它空出位置。只挪两个数没什么，百万个元素中间插一个，就可能移动后面很大一段。改分数也可能先移走旧位置，再为新位置腾地方。排序数组容易读，持续更新则可能很贵。

把数组换成有序链表，元素之间用链接连起来：

```text
10 → 20 → 30 → 40 → 50
```

已经找到 30 和 40 时，插入 35 只要把链接接成 `30 → 35 → 40`，后面的元素不用搬。

但我们怎么找到 30 和 40？链表不能像数组那样用下标直接拿到中间元素，只知道当前节点的下一个在哪里。通常还是要从前往后走。它省下了移动元素的成本，却没有解决找到位置的问题。

哈希表又是另一个方向。它根据用户 ID 算出一个位置，快速缩小查找范围，适合找 C 的资料；哈希分布不保留积分大小关系，找到了 C，也不能顺手知道谁比 C 高分。因此它适合保留，但还要配一份有序结构。

跳表和平衡搜索树就是在补这个缺口：既能跳过大批不相关元素，又能在更新时避免搬动整个集合。跳表给链表增加跨过一段元素的链接；搜索树通过比较大小选择左边或右边，再用规则限制树不要长歪。

### 为什么同样是 O(log N)，仍然不能说速度一样

`O(log N)` 大致表达的是：数据越来越多时，查找所需步骤增长得比较慢。它没有告诉我们，每一步到底有多贵。

数组中的下一次比较，可以计算出元素地址；树和跳表要沿链接找下一个节点；数据库中的下一页如果还没进内存，就得先从存储读取。这些都算“往下走一步”，代价却不同。

而且，内存也不是没有区别。CPU 会把附近的一小块数据一起读入硬件缓存，通常称为缓存行。数组里的相邻元素挨在一起，读到一个，附近的数据可能也到了；节点各自分散分配时，下一次沿指针访问的地方，未必已经在缓存里。对象大小、比较函数和内存分配方式也会影响结果。

所以，几十个元素连续扫描，可能比“先算哈希、再找桶、再追节点”更划算。小数据用简单结构并不奇怪，重要的是总工作量。

还要算返回结果的成本。找区间起点很快，不意味着把区间里的十万个人返回也很快。`O(log N + M)` 中的 M，就是还要读取的结果数量；读取、编码和网络传输都不会因为起点找得快而消失。

## 三、跳表怎样让 ZSet 既能改分，又能读榜

ZSet 给每个成员一个分数。成员叫 member，分数叫 score。我们的成员可以是用户 C，score 是 30；同一个成员只能出现一次，但不同成员可以同分。同分时，Redis 再按成员字符串的字节顺序决定先后。

对较大的 ZSet，Redis 7.2.5 保存两份查找结构：一份字典按成员找到分数，一份跳表按分数和成员维护顺序。两者引用共享的成员字符串，不必把字符串内容复制两遍。[Redis ZSet 源码](https://github.com/redis/redis/blob/7.2.5/src/t_zset.c)

![ZSet：按用户查分数，与按分数读榜是两条路径](/images/posts/storage-zset-paths.svg)

问“C 多少分”，先走字典，得到 30；问“20 到 40 分有哪些人”，走按分数排列的跳表。只留字典，区间查询要扫描；只留按分数排列的结构，手里只有 C 的名字，又不知道旧分数，就缺少沿分数查找的条件。

### 给链表加几条能跳远一点的链接

先看一个稍长的有序链表：

```text
底层：10 → 20 → 30 → 40 → 50 → 60 → 70
高层：10 ─────────→ 40 ─────────→ 70
```

底层保留所有元素，高层只在部分节点之间建立链接。查找 55 应该插在哪里，可以先在高层到 40。下一跳是 70，超过 55，就降到底层，从 40 到 50，发现下一项 60 已经太大。插入边界是 50 和 60 之间。

如果元素更多，可以再有更高、更稀疏的层。查找先走高层，下一跳会超过目标时就下降，直到找到底层位置。它节省的是定位过程中没必要逐个看的元素。

新节点有几层链接，由随机过程决定。插入时记录查找途中各层的前一个节点，把新节点接进去；删除时把对应链接接回去。它不用像红黑树一样旋转，但要维护多层链接，也要为这些链接付内存成本。

随机层级通常能形成比较好的分布，得到期望的对数查找成本。这里的“期望”是概率意义上的保证：不意味着每一张跳表、每一次查找都严格走很短的路径。极端分布下仍可能退化，实际实现也会限制最高层数。

### 已经按顺序排好了，为什么排名还要另做处理

底层现在是 A、B、C、D、E。找到了 D，我们知道它在 C 后、E 前，但如果链接里没有记录数量，要知道 D 是第几个，仍可能从头数。

Redis 的跳表为链接保存一个数：这次往前跳，跨过了多少个底层位置。这个数叫跨度，也就是 span。

例如从表头直接跳到 D，跨过四个位置；D 再到 E，跨过一个位置。把经过链接的跨度加起来，能得到 E 在从一开始计数时的位置 5。Redis 对外返回的 rank 从零开始，因此正向排名是 4。这是计数方式不同，不是少算一个人。

反过来，想找第几个元素，也可以用跨度判断这一跳会不会越过目标位置。只要不越过，就往前；会越过，就降一层继续。带跨度的跳表因此既能按分数找，也能按位置找。

插入一个新成员后，跨过插入点的链接覆盖的底层元素多了一个，跨度也要改。新节点接入某一层时，还要把原链接的跨度分配到新的两段。删除时做对应调整。排名查询少数很多步，是因为更新时已经维护了这些数量。

红黑树也能做同样的事，只需为节点记录它下面有多少个元素。B+ 树也能增加子树计数。普通有序结构只保存前后顺序，不会自动获得精确排名能力。

### C 从 30 分变成 55 分，会改哪些东西

原顺序是 A10、B20、C30、D40、E50。C 改成 55 后，应该变成 A10、B20、D40、E50、C55。

字典先找到 C，取得旧分数；有序结构移除 C 的旧位置，把它接到新的位置；相关跨度也要修复，字典中的分数引用要指向正确的结果。Redis 还会检查新分数能否保留在原位置：例如一个节点的分数变化后仍位于原相邻节点之间，可能直接修改，不必每次都移动。[Redis 的改分实现](https://github.com/redis/redis/blob/7.2.5/src/t_zset.c)可对照 `zslUpdateScore`。

这说明字典和跳表不是两个互不相关的东西。它们共同描述同一份集合，一次改分要把两边都改对。ZSet 把这件事放在一条命令内部处理；应用自行用一个 Hash 和另一份排序结构，分两条命令更新，就要自己处理两者不一致的窗口。

单次 ZSet 命令内部维护好，也不代表数据库已经同步，更不代表同一条积分事件重复到达时不会重复加分。这些属于后面的业务写入问题。

### 那为什么不用红黑树，或者直接用 B+ 树

换红黑树可以做。按 `(score, member)` 比较，能找分数区间；记录子树元素数，能查排名；再配字典，能按成员查旧分数。找到区间起点后，也能沿树的后继元素继续读取，不必每条结果都从树根重新查。

区别是维护方式。红黑树要维护父子关系、颜色规则，必要时旋转；加了排名计数，旋转和增删时也要修复数量。跳表改成维护各层链接和跨度，底层前后链接直接用于正向、反向读榜。两种结构都要做更新工作，不能把“跳表不旋转”理解成“跳表更新没有成本”。

Redis 的选择与它实现的这组能力相匹配：按分数定位、连续读取、反向读取、计算排名。这里能说明跳表怎样满足需要，但没有给出与某棵红黑树的性能对照，所以不能断言跳表一定更快。跳表可能用于并发结构，也不证明 Redis 是为了并发修改同一张跳表才采用它。

内存 B+ 树同样是候选。一个节点集中放许多键，可能让 CPU 一次读到更多有用数据。不过要决定节点大小，处理节点内移动、满节点的分裂，以及排名计数更新。Redis 这条索引主要操作内存中的对象，没有 InnoDB 那样强的“尽量少从存储取得页”的压力，是否值得换成多键节点，要看具体实现的收益。

如果榜单基本不更新，排序数组也可以考虑：构建时排好，之后二分找起点、连续读结果。每秒都有人涨分的榜单，与每天结算一次的静态名单，未必需要相同结构。

### 只有几个人时，Redis 也不急着用跳表

字典的桶、跳表的节点和多层链接，都要占空间。只有 A、B、C 几个人时，为了省下几次扫描就分配这些结构，可能不划算。

Redis 可以把小 ZSet 的成员和分数紧凑地放在一段内存里，按序扫描或移动。这种编码叫 Listpack。读到下一对成员和分数，不必追到另一个独立节点；元素很少时，有限的扫描和搬移可以接受。

常见默认配置给出的限制是 128 个成员、成员长度 64 字节，即 `zset-max-listpack-entries` 与 `zset-max-listpack-value`。具体使用哪种编码，要看版本、数据和配置，不能说所有 ZSet 都一定走跳表。把阈值调大，会让更多操作保留在线性扫描和移动路径里。[Redis 内存优化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

## 四、InnoDB 为什么关心“一次读到多少”，而不只关心比较几次

数据库要把活动记录长期保存。索引和数据可能远大于内存，有些记录现在不在缓存里。找它们时，就需要从存储取得数据。

InnoDB 不会只为一个整数读取四个字节，它按页组织索引，默认索引页大小是 16KB。页可以理解成存储引擎管理的一整块数据：取得一页后，里面会有多条记录和管理信息。具体页大小在实例初始化时确定。[InnoDB 索引物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

因此，一次取得的页能帮我们判断多少事情，会直接影响查找成本。只用到里面一个小节点，随后又去另一页，与在这一页里完成很多导航比较，不是同一种效率。

### B+ 树把很多导航键放在同一页

二叉搜索树的一个节点主要把范围分成左、右两边。B+ 树的内部页则放许多分隔键，把范围分成很多段；比较这些键后，选择其中一个子页继续查。一个节点能连多少个子节点，这个数量叫扇出。

可以把一个导航页想成目录页：它不只写“去左边还是右边”，而是列出许多范围分别去哪里。读到这张目录，就能决定下一步进入哪段数据。

用一组假设数字算一下：根页能连 200 个内部页，每个内部页再连 200 个叶页，每个叶页保存 100 条记录。三层最多覆盖：

```text
根页 → 内部页 → 叶页
200 × 200 × 100 = 4,000,000 条记录
```

它说明多分支能让树比较浅，不是说 MySQL 任意一棵树三层都能装四百万行。键越长、行或索引记录越大，一页能放的条目就越少；页也不会永远塞满。真正的容量取决于这些条件。

普通红黑树若要覆盖百万个键，即使接近完全平衡，也大约有二十层，红黑树实际高度还可能更大。沿二十个独立节点找下去，如果它们分散在不同的未缓存页里，就可能取得很多页。这里不是说红黑树必然读二十次磁盘：节点可能共页，页面也可能早就在缓存中。问题是普通二叉节点没有天然利用好一整页的空间。

![InnoDB：导航页负责找路，叶页保存记录并继续读取范围](/images/posts/storage-bplus-pages.svg)

普通跳表也有类似问题。链接让它跳过元素，却不保证下一个节点就在刚取得的页里。直接把内存节点搬到磁盘，依然可能到处读页。可以重新把元素分成块，建立适合块的导航，但那就需要另外设计存储布局，不能原样照搬普通跳表。

B+ 树适合 InnoDB 的原因是：索引要查单条，也要取范围，而这些工作围绕页进行。高扇出减少导航层数，叶层负责读取有序结果。其他结构能保留顺序，但要想成为替代品，还得解决如何分块、如何利用页空间和如何更新页。

### 为什么记录放在叶子，范围查询又怎样往下读

B+ 树的内部页主要用来指路，叶页保存索引记录。内部页不塞完整行数据，就能把更多空间用于导航。找到叶层的一条记录后，再按叶层的顺序继续取后面的记录。

例如要找 20 到 40 分的人，先找到第一条满足条件的记录，再读下一条、下一条，直到超过 40。当前叶页读完了，可以沿叶页之间的链接继续，不必每读一条结果都从根开始找。

教科书里的 B 树允许内部节点也存数据条目，查到那里就可以返回；B+ 树把索引记录集中到叶层，更方便把查找和连续读取分开组织。实际哪种实现更合适，还要看键宽度和存储布局，不能只凭一个加号比较所有树。

MySQL 官方文档称这类索引为 B-tree；本文用 B+ 树解释它的内部页导航、叶页记录这种布局。不要因为文档少一个加号就把它当成另一种完全不同的实现。空间索引用的是 R-tree，也不在本文比较的普通索引范围内。

叶页按顺序连接，指的是逻辑顺序。相邻叶页不保证在磁盘上也紧挨着，读取时仍可能取得不同位置的页。减少重复导航，不等于所有范围读取都变成物理上的连续读。

### 找到索引记录，为什么有时还要“回表”

假设用户表的主键是 user_id，行里还有昵称、头像等字段。InnoDB 的主键索引把行数据放在叶记录中，按主键找到叶记录，就能拿到这行。这种组织叫聚簇索引。

再建一个按积分排列的二级索引，叶记录通常保存索引列和对应主键值。按积分找到用户 C，只拿到积分和 C 的主键，未必有昵称。如果还需要昵称，就拿主键再去聚簇索引找到 C 的完整行。这个多走一次主键查找的过程叫回表。[MySQL 聚簇与二级索引文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

如果查询只要 user_id 和 score，而所用索引里已经包含它们，就可以直接取得需要的字段，不必为这些字段再找完整行，这叫覆盖索引。

这也解释了两个常见现象。主键很长，多个二级索引都要携带较长的主键，可能让一页放不下那么多条目；查询只要 ID 和积分，却使用 `SELECT *`，可能为了本来不需要的大字段增加回表和传输。优化时先看是不是多取了东西，比直接讨论“换一种树”更具体。

### 写入时，B+ 树也要为保持顺序付钱

叶页还有空间时，可以把新记录放进去；页放不下，可能要分裂，把部分记录放到新页，并更新上层导航。如果上层也满了，变化可能继续向上传。

所以它也不是只有好处。插入可能移动页内记录、分配新页，还要配合日志和并发控制。少读几层页的收益，伴随着维护页结构的写入成本。

递增主键的新记录经常落在索引的一端，通常比到处随机插入更集中；但并发写同一片区域，也可能带来竞争。随机主键把位置打散，却可能接触更多页、影响缓存和页分裂。不能只用“顺序一定快”或“随机能分散压力”一句话判断。

另外，一页在内存里与不在内存里，成本不同。InnoDB 用 Buffer Pool 缓存页面，命中时无需为这次访问从存储重新取得页。它是数据库的页缓存，与前面 CPU 按缓存行工作的硬件缓存不是一回事。[MySQL Buffer Pool 文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

B+ 树负责组织和找到记录，不负责凭空提供事务和断电恢复。日志用于恢复写入，MVCC 让读取按照事务规则看到相应版本，锁等机制处理并发限制。这些由存储引擎一起完成，单独实现一棵 B+ 树，并不等于实现了 InnoDB。

## 五、HashMap 为什么只给拥挤桶加红黑树

假设应用已经加载了一批用户资料，用 `HashMap<用户ID, 用户资料>` 保存它们。现在要查用户 C 的昵称。这里给出的条件只有用户 ID，不需要知道谁的积分更高，也不需要把所有用户排成一个榜单。

### 查一个用户，先找桶，再在桶里找 Key

HashMap 内部有一个数组，数组的每个位置称为一个桶。可以把它理解成一排抽屉：先根据 Key 算出放在哪个抽屉，再在里面找对应记录。实际实现先调用 `hashCode()`，处理得到的哈希值，再结合数组长度算出桶下标；桶本身是数据结构中的位置，不是另一张业务表。

不同 Key 可能算出同一个桶下标，这叫哈希冲突。落在同一个桶，不代表两个 Key 相等，也不代表它们完整的哈希值一定相同。HashMap 还需要判断 Key 是否匹配，通常涉及引用相同判断或 `equals()`，才能返回正确资料。

例如下面是一个假设的分桶结果，箭头表示桶内链表的下一节点：

```text
桶 0：用户 A
桶 1：用户 B → 用户 C
桶 2：用户 D
桶 3：空
```

查 C 时，哈希计算先把请求带到桶 1，不必检查 A 和 D；桶内再检查 B、C，直到找到匹配的 Key。这就是两步查找：第一步缩小到一个桶，第二步在桶内确定目标。

正常情况下桶很短，第二步只检查少量节点，用简单链表就够了。但如果许多 Key 挤到同一个桶，仍用链表时，查末尾元素可能要逐个检查很久。树化是在这个时候，把该桶内的查找结构改成红黑树；其他桶仍保持原来的轻量结构。外层哈希数组没有被换掉。

### 红黑树解决的是长桶内的查找

树怎样减少检查？先看一个简化的搜索树。假设桶内的几个键可以按下面的数值标记比较大小；数字只用于说明比较方向，不表示实际 HashMap 按用户 ID 建树。这里也省略节点颜色，不模拟 JDK 的具体树形。

```text
        40
       /  \
     20    60
    / \    / \
   10 30  50 70
```

查 50，先比较 40，发现目标更大，只去右边；再比较 60，发现目标更小，只去左边；最后找到 50。比较一次就能排除不可能包含目标的一部分节点，因此不用沿链表把前面的元素逐个看完。HashMap 的实际树节点主要先比较哈希值，哈希值相同且 Key 有适用的比较关系时，再利用该关系判断方向。

普通二叉搜索树还有问题：按 10、20、30、40 的顺序插入，可能一直往右接节点，变成 `10 → 20 → 30 → 40`。这时虽然名字叫树，查找仍像走链表。红黑树通过节点颜色规则约束树的形状；插入、删除后，必要时调整局部父子关系并重新着色，使它不会因插入顺序一直长成单边链。调整局部父子关系、同时保留比较顺序的操作叫旋转。

这里使用红黑树，是为了让拥挤桶内的搜索路径保持较短。它不负责把整个 Map 排序：两个 ID 相邻的用户可能在不同桶中，桶内树的顺序也主要由哈希值决定。直接遍历 HashMap，仍得不到按用户 ID 或积分排列的结果。

### 为什么只改拥挤桶，不统一换成其他结构

先看“整个 Map 都换成一棵树”。在上面的例子里，查 A 原本算出桶 0，再检查一个节点就能找到。如果改用覆盖所有 Key 的搜索树，A 也要从树根开始比较。数据规模变大时，所有正常访问都会进入树的路径。HashMap 的任务是按 Key 找值，没有要求全局顺序；它保留哈希定位，只给拥挤桶增加树，避免所有桶都承担树节点和维护的额外成本。

再看“把拥挤桶换成跳表”。可以实现，因为跳表也能跳过不相关的节点。但这里用不上 ZSet 的精确排名、积分区间和反向读榜能力。普通随机跳表要保存多层链接，查找路径长短还受随机生成的层级影响；红黑树则通过平衡规则限制树高。前者通常能得到较短路径，后者的树高有确定的上界。这是两种不同的代价与保证，并不能直接推导红黑树在每种负载下都更快。

最后看“把拥挤桶换成 B+ 树”。它也能保存并查找这些键。但是，InnoDB 面临的是数据可能不在内存、需要取得整页的情况，B+ 树把很多导航键放进同一页，可以充分利用一次读页。普通 HashMap 的桶节点主要在内存里，没有同样的冷页读取需求。换成多键节点之后，还要设计节点内移动、节点满后的分裂等规则，是否值得要结合实现和负载判断。

| 方案 | 解决什么 | 在 HashMap 这个场景里的取舍 |
| --- | --- | --- |
| 短桶用链表，长桶用红黑树 | 保留哈希定位，改善拥挤桶的搜索 | 树节点更重，只在需要的桶使用 |
| 整个 Map 换成搜索树 | 维护所有 Key 的全局比较顺序 | 正常访问也走树路径，放弃原来的哈希定位 |
| 桶内换成普通随机跳表 | 为桶内键提供跳跃查找 | 多层链接和随机层级，需要另做实现与比较 |
| 桶内换成 B+ 树 | 把多个键集中放进节点 | 要设计移动和分裂，缺少 InnoDB 那样强的读页动机 |

因此，能从当前实现解释的是：红黑树适合承担长桶中的平衡搜索，轻量节点适合保留在正常桶中。跳表和 B+ 树也能设计成替代方案；这里的分析没有证明 JDK 必须用红黑树，更没有给另外两种结构作出普遍更慢的结论。

### 树化的条件与它没有解决的问题

先遇到长桶，也不一定立即树化。桶数组还小时，可以先扩容成更多桶，利用更多哈希位把原来挤在一起的 Key 分开。如果这些 Key 的完整哈希值都相同，扩容就无法靠增加桶数分开它们。扩容尝试改善分布，树化改善桶内查找，是不同的处理方式。

OpenJDK 17.0.12 的三个相关常量是：`TREEIFY_THRESHOLD = 8`，用于链表插入时判断是否尝试树化；`MIN_TREEIFY_CAPACITY = 64`，数组容量小于它时优先扩容；`UNTREEIFY_THRESHOLD = 6`，用于扩容拆分树桶后判断是否转回链表。它们不能压缩成“第八个一定树化、第六个一定退化”：普通 `putVal` 的链表追加路径通常在已有八个节点、再追加一个时触发树化尝试，删除时转回链表还有结构性判断。需要核对细节时，可看源码中的 `putVal`、`treeifyBin` 和 `TreeNode.split`。

树高受限制，也不代表每一种 Key 都能沿一条路径找到。当两个不同 Key 的完整哈希值相同，又无法通过适用的比较关系判断左右时，查询为了找出 `equals()` 匹配的目标，可能还要搜索多个分支。前面的 50 示例假设能判断大小，不能无条件套到任意 Java 对象上。[OpenJDK HashMap 实现说明](https://github.com/openjdk/jdk17u/blob/jdk-17.0.12%2B7/src/java.base/share/classes/java/util/HashMap.java)明确给出了这些适用条件和树节点的额外开销。

树化也不会修复错误的 `equals()` 约定，或插入后修改 Key 的哈希字段。它没有提供自动过期、容量限制和线程安全；这些需求要由其他容器或缓存机制承担。[Java HashMap API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html)说明了其顺序和同步边界。

回到排行榜，ZSet 决定前十名有哪些人、按什么顺序返回；应用里的 HashMap 按这些人的 ID 找昵称和头像。页面仍沿 ZSet 的结果排列，不能改成 HashMap 的遍历顺序。ZSet 的有序索引处理榜单顺序，HashMap 的桶内树处理局部冲突，这是它们在同一条请求中各自承担的工作。

## 六、让三种结构一起完成一次请求

回到原来的五个人。C 从 30 分变成 55 分，用户刷新榜单，想看到新的前几名和自己的名次。

为了让同分也有明确顺序，这个例子约定分数越高越靠前，同分按成员字符串的逆字节序排列。用户 ID 使用固定宽度编码，例如 `user:0003`。这只是一种规则；如果业务要求先达到分数的人靠前，就要另外保存时间并设计排序，不能期待 Redis 默认替我们做到。

先只看 ZSet 的接口。下面展示从原状态到新状态会发生什么，不要求读者运行测试：

```text
原分数：A=10、B=20、C=30、D=40、E=50

ZSCORE ranking user:0003
结果：30

ZADD ranking 55 user:0003
结果：C 的分数改成 55

ZRANGE ranking 0 2 REV WITHSCORES
结果：C55、E50、D40

ZREVRANK ranking user:0003
结果：0，表示降序榜的第一名

ZRANGE ranking 20 40 BYSCORE WITHSCORES
结果：B20、D40
```

大集合的改分会维护字典与跳表的位置和跨度；读前三名，从高分那一端取结果；查自己的名次，用维护好的数量信息定位。只有五个人的小集合，内部可能走 Listpack，这段展示的是命令语义，不是声称它已经在使用跳表。[ZRANGE 命令说明](https://redis.io/docs/latest/commands/zrange/)

应用得到 C、E、D 的 ID 后，批量加载它们的昵称和头像。资料返回可能是 D、C、E，顺序不一定与榜单一致。把这些资料放进 HashMap，再按榜单给出的 C、E、D 逐个取，就能保持正确顺序。HashMap 在这里帮忙配资料，没有参与积分排名。

数据库可以保留一份活动当前积分。下面是一个表与查询的例子：

```sql
CREATE TABLE activity_score_demo (
  activity_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  score BIGINT NOT NULL,
  PRIMARY KEY (activity_id, user_id),
  KEY idx_rank (activity_id, score DESC, user_id DESC)
) ENGINE=InnoDB;

SELECT user_id, score
FROM activity_score_demo
WHERE activity_id = 7
ORDER BY score DESC, user_id DESC
LIMIT 10;
```

主键按活动和用户组织，适合问“活动 7 中 C 多少分”。idx_rank 则先按活动分组，在组内按积分和用户 ID 排列，适合取这个活动的前十名。一次积分更新可能要改动这两份索引，各自让一种查询更方便，也各自占空间、付更新成本。

这里的同分规则是数值 user_id 降序。要与 ZSet 中的字符串规则对齐，ID 编码应保证相应的字符串顺序与数值顺序一致，不能让 `user:10` 排在 `user:2` 的直觉顺序与实际字节顺序相混。

查询只要 user_id 和 score，是因为这两个字段可以由合适的索引提供，争取不再查整行。优化器实际选择哪条路径还受统计信息等条件影响，建了索引并不保证所有查询都使用它。

### 数据结构改对了，为什么榜单仍可能错

数据库提交了 C=55，应用还没更新 Redis 就退出，数据库与榜单会暂时不一致；先把 Redis 改成 55，数据库却提交失败，又会出现榜单虚高。问题不在于跳表没有排序，而在于两个系统没有一起完成这次业务更新。

一种处理方式，是数据库保存积分结果时，在同一个事务里记下“这次结果还要通知榜单”。后台读取待通知记录，更新失败就按原事件继续处理，成功后记录进度。这样应用退出后还能找到没有完成的工作。这类办法常叫事务发件箱。它仍需要处理重复通知，不能因为会重发，就放心地每次再加一次分。

例如同一个完成任务事件让 C 增加 25 分，重复执行两次增量加分就变成增加 50 分。业务要识别同一事件已处理，而不是依赖跳表判断这次分数变化是不是合法。

用绝对分数也有问题。两次通知分别是“C=55”和“C=60”，后者先到，前者迟到，如果都直接覆盖，分数会退回 55。可以把事件版本和结果一起保存，只有比当前更新的版本才应用；版本判断与写分数必须一起完成，例如通过受控的 Redis 脚本检查并更新。只在应用里先查版本、再单独写分数，两个请求仍可能在中间交错。

通知长期失败时，需要告警和恢复；重建榜单时，需要依据可信的积分记录，而不能只把错误的 Redis 值再复制一遍。具体方案可继续看[消息可靠投递](/posts/message-queue-reliable-delivery-no-loss/)和[缓存一致性](/posts/cache-consistency-write-invalidate-races/)。这里先保留边界：结构帮我们把数据放到合适位置，业务协议负责保证放进去的是正确结果。

## 七、几个容易误以为“有了结构就自动解决”的问题

### 按分数找得到，不等于能直接跳到第十万名

带跨度的跳表知道一次跳过了多少个元素，因此可以按排名定位到后面的某个位置。普通 InnoDB 索引按键排列，却没有给每条记录保存一份可直接使用的精确名次。

因此，数据库执行 `LIMIT 10 OFFSET 100000`，通常仍要让执行器处理前面的记录，再跳过十万条。最终只返回十条，不能说明整个过程只看了十条。

如果用户是在一页一页往后翻，可以记住上一页最后一条的积分和用户 ID，下一页从这个边界继续，而不是每次从头数。对于降序榜，假设上一页最后一项是 score=1000、user_id=42：

```sql
SELECT user_id, score
FROM activity_score_demo
WHERE activity_id = 7
  AND (score < 1000 OR (score = 1000 AND user_id < 42))
ORDER BY score DESC, user_id DESC
LIMIT 10;
```

先看积分，比 1000 低的在后面；同为 1000 分时，比 42 小的 ID 在后面。这就是把“从上一页往后读”写成查询条件，通常称为游标分页或 keyset pagination。不能只保存分数，否则同分用户的边界不完整。具体执行计划仍需要确认，OR 条件不应被当作固定速度承诺。

翻页期间有人改分，还可能跨过分页边界，导致重复或遗漏。如果要导出一份稳定的获奖名单，可以冻结榜单版本，或按数据库一致性读规则取得快照；后者也要考虑长事务成本。分页方式减少扫描，与多页结果是否来自同一份数据，是两个不同问题。

### score 能存数字，不等于能无损塞进任意大整数

Redis score 使用双精度浮点数。它能连续精确表示的整数范围到 `2^53`；超过这一范围，有些相邻整数会被表示成同一个值。[ZADD 文档](https://redis.io/docs/latest/commands/zadd/)说明了这个边界。

例如 9007199254740992 与 9007199254740993，按常用的舍入规则转为双精度数值，会得到同一个数。客户端如果先把精确整数转成这种数值类型，低位就在发送之前丢了，Redis 收到后无法知道原来是哪一个整数。

因此，把积分、时间戳和用户 ID 拼成一个很大的整数 score，要检查总范围和客户端的数值类型。不同人的原值一旦变成同一个分数，跳表只能根据它实际收到的分数排序，不会恢复丢失的信息。货币金额也要按精度需求建模，例如在确定范围内使用整数最小单位，并检查转换链路。

### 一个 ZSet 很大，不等于会自动拆到很多机器上

Redis Cluster 根据 Key 决定分片。一个排行榜 Key 即使包含百万个成员，也不会因为成员多，就自动把这些成员分散给所有节点。

读榜、改分和大范围返回仍可能集中在负责这个 Key 的节点。把榜单拆成多个分榜可以分散负载，但全局排名要重新计算：每个分榜的第一名，不一定足以回答任意用户在所有分榜中排第几。精确全局排名与一致更新会变成新的问题。

同样，找到十万个结果的起点很快，也无法省掉返回十万个结果的读取与传输。结构选择之外，还要限制一次返回量、考虑热点和实际响应时间。

## 八、最后把“换成另一种”放回具体问题

到这里，可以用三个问题检查自己是否理解了选型。

如果 ZSet 不用跳表，换红黑树，能不能做？能。需要保留按成员查找的字典，再让树按分数排列、保存子树元素数量，并在增删和旋转时修复数量。更换的是维护顺序和计数的方法，不是失去排行榜能力。

如果 InnoDB 把页式 B+ 树换成普通红黑树或跳表，能不能有序？也能。但普通节点和链接没有自然地利用整页读取，可能经过更多未缓存页。要成为合适的数据库索引，还得设计分块、页布局、并发更新和恢复，不能只把指针结构换一个名字。

如果 HashMap 的拥挤桶换成跳表或 B+ 树，能不能查 Key？仍然可以设计。只是这里不需要 ZSet 的排名能力，也没有 InnoDB 那样强的冷页压力。我们要解决的是哈希定位后，桶内怎样少检查一些节点；JDK 选择红黑树，并不证明其他 Map 实现一定不能用别的结构。

| 场景 | 先解决哪件事 | 采用的结构帮在哪里 | 付出的成本 |
| --- | --- | --- | --- |
| 大 ZSet | 经常改分，还要读顺序和名次 | 字典找成员，跳表找顺序，跨度数位置 | 两份查找结构、多层链接、跨度更新 |
| InnoDB 普通索引 | 数据按页管理，尽量少取页并方便范围读取 | 一页放很多导航键，叶层保存有序记录 | 页内更新、分裂以及日志和并发协作 |
| HashMap 长桶 | 按哈希找到桶后，别再沿长链逐个找 | 红黑树限制桶内搜索高度 | 树节点更大，更新要维护树的规则 |

选择随工作变化也很正常。只有几十个元素，紧凑数组或 Listpack 可能够用；每天批量生成、之后只读的榜单，可以考虑排序数组；只按用户 ID 查值，不需要顺序，则先从哈希映射开始。

遇到类似选型，可以先写下实际操作：用什么条件查，是否要连续读一段结果，更新是否频繁，数据是不是已经在内存里。然后沿一次查找和一次更新走完，看看哪里在扫描、哪里在搬动元素、哪里需要取得新页。需要减少哪一部分工作，才是选结构的依据。
