一个接口处理完请求，创建的对象是不是就能被回收？如果接口每秒创建大量对象，GC 很频繁，是不是内存泄漏？换成低停顿收集器，为什么请求还是会卡？

这些问题需要一起看对象的引用关系、回收方式和程序运行时的资源。只记住“新生代复制、老年代整理”“G1 低停顿、Parallel 高吞吐”，很难从线上现象反推原因。

本文围绕一个订单查询接口展开：请求创建查询结果和序列化缓冲，有些数据随请求结束失去引用，有些被缓存保留，还有些被异步队列延长了生命周期。我们沿着这条链解释 GC 为什么能收、为什么收不掉，以及回收为何影响业务。一般行为以 HotSpot JDK 17 为基础；CMS 作为历史设计讨论，分代 ZGC 单独标注 JDK 21 及之后的变化。机制与版本依据来自官方文档，业务场景用于解释因果，不作为收集器性能排名的证据。

## 一、为什么需要 GC：请求结束和对象死亡是两件事

如果让业务代码手动管理内存，分配一个查询结果之后，就必须知道所有调用方何时不再使用它。对象被缓存、回调或另一个线程拿走后，这个问题很难由最初创建它的方法独自回答。释放过早会让别人访问已经失效的内存，忘记释放又会不断占用空间。

GC 把这部分责任交给运行时：从仍然有效的访问入口出发，找出程序还能到达的对象，保留它们；把不再需要保留的对象所占空间交回分配器。开发者仍然要管理引用的生命周期。缓存是否过期、队列是否有上限、线程上下文何时清理，都属于业务责任。

这里的“活着”有一个严格含义：对象仍然可以通过运行时认可的引用路径被访问。GC 不理解“这张订单已过期”或“这个请求已完成”。一个不用的订单结果挂在静态 Map 下，仍然是存活对象。

看一个简化例子：

```java
static final Map<String, byte[]> CACHE = new HashMap<>();

static void query(String orderId) {
    byte[] response = new byte[128 * 1024];
    CACHE.put(orderId, response);
    // 方法返回后，CACHE 仍然持有 response。
}
```

在这个模型中，`response` 的局部绑定结束了，数组却仍能从 `CACHE` 找到。如果每个订单 ID 都插入一条且没有淘汰，换收集器无法解决增长。对 GC 来说，删除这些数组反而会破坏程序语义。

可达性分析从 GC Roots 出发遍历引用图。HotSpot 的根来源包括线程栈及寄存器中的有效对象引用、JNI 全局引用和运行时维护的入口等；已加载类的静态字段也是重要的持有路径。并不是“栈上的每个槽永远都算引用”，运行时需要在扫描点识别哪些位置实际保存有效引用。

这也解释了为什么循环引用不等于泄漏：A 引用 B、B 引用 A，只要它们都没有来自根的可达路径，追踪式 GC 仍能回收这个环。简单引用计数会被环困住，可达性分析关心的是整个访问路径。

![请求结束后，对象是否仍可从根到达](/images/posts/gc-request-lifetime.svg)

图中缓存和异步任务是两条独立路径。只删除缓存条目，如果排队的任务仍然捕获整个结果，对象就还活着。排查时应检查所有持有者，而不能把某一次 `remove` 当成回收已经完成。

局部变量的源码作用域也不能精确决定 GC 时点。JIT 可以在最后一次使用之后不再把某个引用报告为根，即使方法尚未返回；反过来，其他持有者又可能让对象继续存活。设为 `null` 只会断开一条引用，不保证立刻触发收集，更不保证立刻把内存归还操作系统。Java 对可达性层次的定义见 [java.lang.ref 文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/ref/package-summary.html)。

## 二、强弱引用与资源释放：哪些事不能交给 GC

平时使用的字段、数组元素和集合条目通常是强引用。只要存在强可达路径，对象就必须保留。Java 另外提供软引用、弱引用和虚引用，让程序表达不同的保留与通知语义。

| 引用 | 对目标对象的作用 | 使用时要注意什么 |
| --- | --- | --- |
| 强引用 | 保证强可达对象存活 | 过期条目和无限队列会延长整个对象图的生命周期 |
| `SoftReference` | 允许 GC 按内存压力等策略清理 | 不是明确的容量、过期时间或命中率策略 |
| `WeakReference` | 不阻止弱可达对象被清理 | `get()` 可能返回 null；引用包装对象本身仍须被管理 |
| `PhantomReference` | 配合队列感知特定的回收阶段 | `get()` 始终返回 null，不能借它继续访问目标对象 |

软引用常被解释成“内存不够时才回收”，但不能据此设计确定的缓存行为。你无法像配置容量上限那样精确控制清理时机；大量引用处理本身也可能增加 GC 开销。一个需要稳定延迟的订单缓存，通常应先明确容量、TTL、淘汰和加载策略。

弱引用同样不会让整个数据结构自动变得无泄漏。[ThreadLocal 那篇](/posts/java-threadlocal-memory-leak/)已经给出一个具体例子：Entry 弱引用 key，却强引用 value。key 被清理与 value 的强路径断开之间，还隔着 ThreadLocalMap 的条目清理。

GC 的空间回收也不等于外部资源释放。数据库连接、文件描述符、网络连接都有自己的使用协议和数量限制。即使 Java 包装对象最终能回收，等待一个不确定的时点再归还连接，也可能先耗尽连接池。明确关闭的资源应使用 `try-with-resources` 或框架规定的生命周期；不要把 `finalize` 或 Cleaner 当成正常的及时释放路径。

最后要分清三种内存数值：堆中已使用空间、JVM 已提交的堆空间、进程的实际内存占用。对象回收后，原来的位置可以再分配，不代表 JVM 必须马上缩小已提交堆。进程还包含元空间、线程栈、直接内存、代码缓存等。RSS 没下降，单独看这一条不能认定 GC 没工作。

## 三、清除、复制、整理：到底在处理哪些内存

假设一段空间里依次放着 A、B、C、D，只有 A 和 C 还活着。回收需要先获得存活信息，再决定如何把 B、D 的空间变成可用空间。基础算法描述的是这个空间处理方式，不直接规定线程数量、是否分代或是否暂停业务。

标记-清除（mark-sweep）保留 A、C 原来的位置，把 B、D 所占区域交给分配器。它不必搬动存活对象，但得到的空闲空间可能不连续。分配器要通过空闲列表等结构寻找合适位置。若大对象需要一段连续空间，总空闲量足够，也可能找不到合适的块。

复制（copying）把 A、C 搬到另一块可用空间，更新引用，再整体释放原来的区域。新的排列紧凑，分配器可以使用类似指针递增的方式分配。回收成本与需要扫描、复制的存活数据密切相关：如果多数对象很快死亡，只搬少数幸存者很划算；如果大部分数据还活着，就必须准备足够的目标空间，并承担大量搬迁。

教科书里的半空间复制，把两块相等空间轮流作为来源和目标，所以同一时间只有一半用于分配。但“复制需要目标空间”和“所有实际复制收集器固定浪费一半堆”不是同一句话。分代复制和 Region 疏散都可能采用不同的空间组织。

标记-整理（mark-compact）根据存活结果把 A、C 紧凑排列，更新它们的引用，再把一段连续空间释放出来。它同样要处理对象移动，但目标布局可以位于原来的堆范围内。实现中还需要计算目标地址、解决移动顺序与引用修正，不能只理解成“把垃圾擦掉”。

![同一组对象在清除、复制与整理后的空间变化](/images/posts/gc-space-reclamation.svg)

这张图刻意使用同一组对象。比较时追两件事：存活对象是否换地址，以及空闲空间是否连续。图中的目标区只是说明复制需要另一个位置，不表示实际 JVM 必须预留一半堆。

现代收集器经常组合这些思路。G1 将选中 Region 的存活对象疏散到其他 Region，局部看是复制，整体获得整理效果；CMS 的老年代主要做标记-清除；Serial 和 Parallel 的老年代采用整理。说某个收集器用了哪种算法，是解释它如何处理空间的起点，不能靠这一句话推出它一定快或一定慢。

对象移动后，原本指向旧位置的引用必须仍然有效。暂停期间统一修正是一种办法；并发移动时，通过屏障与转发信息处理访问又是另一种。搬迁过程是否与业务重叠，是后面 G1 和 ZGC 的一个重要区别。

## 四、分代为什么有效：少看长期对象，少搬短命对象

订单接口通常会创建解析结果、临时列表、序列化缓冲。很多对象在请求完成后就失去引用。另一些对象，例如缓存结果、配置、排队任务，会活得更久。分代收集利用这种寿命分布，把回收工作集中在短命对象较多的区域，减少每次都扫描整个长期存活集合的成本。

这是经验假设，不是 Java 语义保证。请求积压、批量加载、对象池和长生命周期缓存都可能改变幸存比例。分代机制的收益要由应用实际的分配与存活行为决定。[Oracle 的分代说明](https://docs.oracle.com/javase/8/docs/technotes/guides/vm/gctuning/generations.html)解释了这一假设及其性能边界。

在传统 Eden 加两个 Survivor 的模型中，新对象通常先进入 Eden。一次新生代回收把 Eden 和当前 Survivor 中的幸存对象搬到另一个 Survivor，或晋升到老年代。复制结束后，来源空间可以再使用，两个 Survivor 交换角色。

假设用 8:1:1 说明布局，Eden 和一个 Survivor 可以使用，另一个 Survivor 作为复制目标。它对应的是这个简化模型里约十分之一的保留目标空间，并非“一半堆闲置”。比例、目标容量和年龄策略都可能受收集器与运行时自适应影响，不能当成所有 JVM 的固定布局。

晋升也不只由“年龄达到 15”决定。Survivor 容量、年龄分布和分配策略都会影响对象去向；目标区不足时，一些对象会更早进入老年代。G1 使用 Region 承担 Eden、Survivor、Old 角色，分代仍然存在，但不要求每个代是一块固定连续地址。

只扫描新生代又带来一个问题：如果老年代缓存引用一个刚创建的年轻对象，扫描线程根时未必会重新遍历整个缓存。漏掉这条老到新的边，就会把仍在使用的年轻对象误判为垃圾。

为此，收集器通过写屏障记录某些引用更新，使用卡表、记忆集等结构跟踪跨代或跨 Region 的入口。回收年轻区域时，除了线程等根，也要扫描这些外部入口。屏障是运行时插入的少量辅助代码，用于维护回收所需的信息；GC 据此寻找需要扫描的入口，避免每次遍历整个老年代。

所以新生代 GC 的耗时不只取决于“有多少垃圾”。存活数据的复制量、根扫描、跨区引用、引用对象处理和 CPU 资源都会影响停顿。如果订单服务下游变慢，任务排队时间变长，原本短命的结果活过多次回收，晋升与搬迁压力就可能同时上涨。先处理积压，比单纯加大年轻代更贴近原因。

日常提到的 Minor GC 通常指年轻代回收；Full GC 通常指整堆回收，具体阶段仍由收集器决定。Major GC 的用法并不统一，有资料指老年代回收，也有资料用于整堆回收，因此不能只靠这个称呼判断暂停范围。看 G1 日志时，直接区分 Young、Mixed、并发标记周期与 Full 更准确。年轻代分配不足、老年代占用阈值、显式 GC 请求，都可能触发不同的活动；不能把“调用 System.gc()”或“发生老年代回收”一律等同于同一种 Full GC。

## 五、为什么会停顿：并行与并发分别解决什么

如果业务线程继续修改引用，而 GC 正在扫描和移动对象，运行时必须处理两类变化：标记结果如何保持正确，访问者如何找到被移动后的对象。最直接的协调办法是暂停业务线程，让回收在稳定的状态下执行。

Stop The World（STW）指相关阶段暂停应用线程。HotSpot 通常通过安全点机制协调进入这种状态。一次较长的安全点事件可能包含等待线程到达安全点的时间和实际执行操作的时间，且安全点操作不全是 GC。排查时应把 GC 日志与安全点日志对齐，避免把所有暂停都归给垃圾回收。

并行（parallel）是多个 GC 线程一起执行同一阶段。业务可能仍然全部暂停，只是回收工作完成得更快。Serial 与 Parallel 的核心差别之一就在这里：前者单个 GC 线程，后者让多个 GC 线程分担工作。

并发（concurrent）是部分 GC 工作与应用执行重叠。CMS 并发标记与清除，G1 并发标记，ZGC 还把对象重定位等大量工作移到并发阶段。并发阶段仍要占用 CPU、带宽和内存，不能把“应用没暂停”理解为“GC 免费”。

以 G1 的 SATB 为例，标记开始后，业务删掉某条旧引用，运行时通过写屏障保留相关信息，让本轮标记仍能按开始时的视角正确完成。这可能把本轮期间刚变成垃圾的对象再保留一段时间。它是保证安全的保守处理，和业务永远不清理条目造成的泄漏不同。更细的三色标记模型留给[下一篇](/posts/java-tricolor-marking-cms-g1/)。

吞吐与停顿还应分开测量。纯 STW 的简化模型中，GC 占用 1 秒、应用运行 9 秒，可以说应用运行时间占比为 90%；对于并发收集器，墙钟时间与 CPU 消耗互相重叠，这个比例已经不能充分描述效率。生产对比应直接观察完成请求数、请求延迟、总 CPU、内存占用和回收行为。

短暂停顿也可能放大队列延迟：如果系统已经接近容量上限，暂停期间积累的请求恢复后还要竞争线程和下游连接。GC 停顿 20ms 不代表每个受影响请求只多等待 20ms。同样，日志中的 GC 停顿 P99 与接口延迟 P99 是两个分布，不能直接互相替代。

## 六、Serial、Parallel、CMS：不同目标留下的设计

Serial 用一个 GC 线程执行回收，应用在相关回收阶段暂停。年轻代复制、老年代整理。对于小存活集合或有限 CPU 的程序，较少的线程协调成本有价值；不能因为“单线程”就认为它在任何小容器里都最慢，也不能仅凭容器小就认定它一定最合适。

Parallel 使用多个 GC 线程执行年轻代和老年代回收，仍以 STW 为主。它偏向通过集中完成回收来维持吞吐，常是批处理和吞吐敏感任务的候选。如果多个 GC 线程得到足够 CPU，回收阶段可以加速；若容器 CPU 配额很紧或机器已经过载，增加线程也可能只增加竞争。所谓“吞吐量最高”必须带具体负载和资源条件，不能当作通用排名。

CMS 的目标是减少老年代回收造成的长暂停。一次典型过程包括初始标记、并发标记、重新标记和并发清除；初始标记与重新标记仍需要停顿。它通常配合 ParNew 处理年轻代，ParNew 是并行的年轻代收集器，不是另一个单线程 Serial。

CMS 的取舍来自并发与清除：业务在回收期间继续分配，必须留出余量；清除不把所有存活对象整理成连续区域，容易产生碎片；并发阶段刚失去引用的对象，也可能要留到后续周期处理。如果老年代在回收完成前耗尽可用空间，可能出现 concurrent mode failure，转入代价更大的停顿回收路径。减少暂停的同时，运行时需要承担并发协作与空间余量的成本。[CMS 官方说明](https://docs.oracle.com/javase/8/docs/technotes/guides/vm/gctuning/cms.html)给出了这些失败模式。

CMS 在 JDK 9 被标记弃用、JDK 14 移除，因此这里主要帮助读懂旧系统与设计演进。新部署不应照着旧文章添加 `UseConcMarkSweepGC`。迁移也不应把 CMS 的代大小参数照搬给 G1；不同收集器的自适应机制和内存组织并不相同。

这些设计没有形成一条“新型号总是全面胜过旧型号”的直线。Serial、Parallel、G1 和 ZGC 仍然分别提供不同取舍。选择时更有用的问题是：应用愿意付出多少并发 CPU 和内存余量，换取多短的暂停，以及这个代价是否改善了业务指标。

## 七、G1：并发判断老年代存活，暂停搬迁选中的区域

G1 的 Region 是等大小的堆管理单元，可以承担年轻代、老年代等角色。它既是分代收集器，也使用分区布局。Region 让老年代空间回收可以分摊到多次暂停中，而不必每次集中搬动整个老年代。

普通 Young GC 的 collection set（回收集合）主要包含年轻代区域。暂停期间，G1 从根和记忆集记录的外部入口出发，把存活对象复制到 Survivor 或 Old 区域，再释放成功疏散的来源 Region。年轻代不是任意挑几个最脏的 Region 就结束，垃圾最多也不是唯一的选择依据。

老年代逐步增长后，G1 根据自适应阈值等因素启动并发标记。Concurrent Start 通常搭载在一次年轻代暂停上，随后并发扫描；Remark 与 Cleanup 等协调阶段得到本轮存活与候选区域信息。完成标记，不代表所有仍有活对象的老年代 Region 已经释放，后面还要执行空间回收。

Mixed GC 将年轻代与部分老年代候选 Region 放入回收集合，在暂停中疏散存活对象。候选区域的垃圾比例、复制成本、跨区引用和回收进度都影响选择。G1 用历史观测预测成本，尽量让一次暂停接近 `MaxGCPauseMillis` 的目标；这个参数是软目标，不是实时系统的硬上限。[G1 的回收集合与阶段说明](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html)可以对照这些动作阅读。

![G1 从年轻代回收到并发标记和 Mixed 回收的流程](/images/posts/gc-g1-cycle.svg)

图中特意分开“统计谁存活”和“搬迁并释放区域”。这是读日志时很重要的区别：并发标记结束只说明这一轮分析推进了，不代表空间压力立即消失；Mixed 回收发生时，复制仍然可能造成可观的暂停。

如果疏散目标空间不足，日志可能出现 `to-space exhausted` 或相关 evacuation failure 信息。部分对象无法完成移动，后续如果仍不能维持分配，G1 可能使用 Full GC 整堆整理。这类问题要检查存活集合、晋升速度、并发周期是否及时完成和剩余空间，不能只把暂停目标从 200ms 改成 50ms。

G1 还有 Humongous 对象的专门路径。判断依据是对象实际占用大小相对于 Region 大小；接近半个 Region 的边界时，还须考虑对象头和对齐，不能只看数组载荷。Humongous 对象直接占用老年代中连续的 Region，最后一个 Region 的尾部可能无法用于其他普通对象。

这会带来连续区域需求和空间浪费，但不等于每个 Humongous 分配必然 Full GC。一些死的基本类型数组可以被提前回收。遇到问题，应先看日志中的 Region 大小、Humongous 区域数量与分配模式，再判断是否需要分块处理或调整布局。大对象是否真的需要一次完整驻留，是比“把 Region 调大”更早的问题。

G1 自适应调整年轻代大小来控制暂停，因此不要默认给它固定 `-Xmn` 或固定年轻代比例。减小年轻代可能减少单次复制量，却增加回收频率；更早结束 Mixed 回收可能缩短暂停，却留下更多老年代压力。任何调整都应同时观察回收进度与业务吞吐。[G1 调优指南](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-garbage-collector-tuning.html)将这些取舍分别讨论。

## 八、ZGC：把搬迁也并发化，但分配仍需要余量

G1 的主要疏散工作在暂停中进行，低停顿目标会受到需要复制的存活量影响。ZGC 将标记、重定位及相关引用处理的大量工作与业务执行重叠，保留较短的协调暂停。

它通过引用中的元信息、屏障和重定位信息，让业务在对象地址变化时仍能获得有效引用。屏障可以在访问路径上处理需要修正的引用，从而避免把整个堆的搬迁都放入一个长 STW 阶段。分代 ZGC 还使用写屏障跟踪相应信息。具体屏障职责随版本变化，不能把早期的“着色指针加读屏障”当成所有版本的完整实现。

低停顿是设计目标，不能写成对每次请求的亚毫秒保证。业务可能因为 CPU 争用、内存分配等待、操作系统调度或下游依赖继续变慢。特别是分配速度超过并发回收进度时，线程可能遇到 allocation stall（分配等待）。这与一条很短的 STW 日志可以同时出现。

ZGC 需要同时容纳存活数据和回收期间的新分配，还要处理搬迁所需空间。若存活集合已经占满可用堆，再低的协调暂停也无法创造空间。它适合纳入严格延迟目标的对比实验，并不要求先把堆扩大到 TB 级才能考虑。

版本边界应明确记录：

| JDK 版本 | ZGC 的变化 | 配置时的含义 |
| --- | --- | --- |
| 11 | 以实验特性引入 | 不是后续分代实现；支持平台也要核实 |
| 15 | 转为生产特性 | 仍应验证实际 JDK 构建支持情况 |
| 21、22 | 引入并可显式启用分代模式 | 使用 `UseZGC`，另加 `ZGenerational` 启用分代 |
| 23 | 分代成为 ZGC 的默认模式 | 不是整个 JVM 默认收集器改为 ZGC |
| 24 及之后 | 非分代模式移除 | 不再按旧非分代教程配置 |

版本依据分别是 [JEP 333](https://openjdk.org/jeps/333)、[JEP 377](https://openjdk.org/jeps/377)、[JEP 439](https://openjdk.org/jeps/439)、[JEP 474](https://openjdk.org/jeps/474) 和 [JEP 490](https://openjdk.org/jeps/490)。部署记录应写出完整 JDK 版本、发行版和启用模式；只写“用了 ZGC”会丢失重要条件。JDK 21 的分代启用方式也可对照 [Java 团队的说明](https://inside.java/2023/10/09/sip084/)。

Shenandoah 也是并发低停顿收集器，但采用自己的引用与搬迁协议，而且是否可用取决于发行版和平台。这里不展开另一套实现。如果目标 JVM 提供它，可以作为实际对比的候选，而不能只凭收集器名字估计结果。

## 九、从 GC 日志找证据：高频、长暂停和泄漏不是一回事

把订单接口放在一个明确场景中：流量上涨后，接口 P99 恶化，年轻代 GC 更频繁，老年代占用也上涨。现在还不能决定换收集器。应先对齐流量、并发请求、下游耗时、队列长度、CPU 和 GC 时间，确认这些变化先后发生的顺序。

下面是 JDK 17 G1 的日志配置示例。容量只是示意，要按容器预算设置，日志目录要存在且允许写入：

```text
-Xmx2g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M
```

`Xms` 决定初始堆，`Xmx` 决定最大堆。固定相等可以减少运行期堆伸缩，并配合预触摸把部分内存工作前移，但增加启动与内存驻留成本，不是所有部署都必须如此。进程的堆外内存还需要预算，不能把容器限额全部给 `Xmx`。JDK 9 起优先使用统一日志；旧参数可能被兼容映射或在某些版本移除，不能一概写成“被忽略所以没有日志”。

一行用于解释格式的示例日志如下，数值仅用于说明字段：

```text
[12.345s][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 512M->128M(2048M) 18.432ms
```

`GC(42)` 是事件标识，同一个周期可能有多条不同阶段日志，不是“一条日志等于一次完整回收”。`512M->128M` 是此次事件前后堆占用，括号中是当时堆容量，不能直接当成物理 RSS 或始终不变的最大堆。`18.432ms` 是这条暂停事件的耗时。

Young GC 没有扫描回收整个老年代，所以回收后的 128M 也不等于“整个进程只有这些活对象”。其中可能包含尚未被本轮处理的老年代垃圾。比较趋势时，应把收集器、事件类型、负载和回收覆盖范围保持可比。

| 现象 | 优先核查 | 暂时不能下的结论 |
| --- | --- | --- |
| Young GC 很频繁，但回收后基线稳定 | 分配速率、年轻代容量、单次暂停与总开销 | 有泄漏；或频繁就一定需要调优 |
| 老年代基线随积压增长，队列消退后下降 | 下游变慢、在途对象、晋升和缓存预热 | 所有长期对象都属于泄漏 |
| 可比的完整回收周期后仍持续增长 | 存活对象类型、保留路径、容量与过期策略 | 必须换一个“更强”的收集器 |
| G1 出现疏散失败、Full GC | 目标空间、存活集合、晋升、并发进度、Humongous 分配 | 只要缩小暂停目标就能解决 |
| ZGC 协调暂停短，接口依然慢 | allocation stall、CPU 配额、调度、锁与下游 | GC 对请求完全没有影响 |

如果 CPU 时间不高但暂停墙钟时间很长，应检查 CPU 限流、机器竞争和内存页分配；如果 Object Copy 阶段突出，应看存活量与晋升；如果引用扫描或引用处理阶段突出，应看跨区连接、根集合或大量 Reference 对象。阶段名会随 JDK 改变，先按实际日志解释，不要机械套用旧截图。

需要进一步取证时，可以先读取目标进程实际参数和堆概况：

```text
jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> help GC.heap_dump
```

不要在繁忙生产进程上顺手执行 live dump。`GC.heap_dump` 的影响可能很高，默认还可能请求一次 Full GC；`-all` 等选项的含义应按目标 JDK 的帮助确认。导出需要预留磁盘，快照也可能包含用户数据和业务敏感信息。应在有权限、可接受暂停的窗口操作，必要时先摘流实例。[jcmd 官方手册](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html)标注了各命令的影响与选项。

堆分析工具中的 dominator tree（支配树）和到根的路径，可以帮助回答“谁在保留这些对象”。单个数组本身占多少空间是 shallow size；如果一个缓存入口让整组对象都必须保留，retained size 更接近这条入口造成的保留影响。最后应把根路径对应回代码中的容量、删除、取消或清理动作，泄漏判断才有业务含义。

## 十、回到订单接口：先改生命周期，再做收集器选型

假设下游耗时先上涨，工作线程处理不过来，异步队列开始堆积。队列中的任务捕获查询结果和响应缓冲，这些数组不能随入口方法返回而回收。它们活过多次年轻代回收，逐渐进入老年代；G1 启动并发标记，随后执行 Mixed 回收，但大部分结果依然被队列持有，可释放的空间就有限。

这里可能同时看到 Young GC 变频繁、复制暂停增长和老年代基线上升。串起事件后，原因是任务生命周期拉长，而不是 GC 忽然“失灵”。如果队列消退后基线回落，说明此前保留主要来自在途工作；如果队列已经清空，结果却仍挂在一个无界缓存下，就要继续沿缓存路径检查。

累计分配量和持续保留量也不同。接口累计分配数百 MiB，只要多数临时对象失去引用、空间被重复使用，就不要求始终拥有数百 MiB 堆；固定保留的那批结果即使经历多次 GC，也不能被回收。调参前应先分清，是分配速度太高，还是存活集合太大。

回到订单接口，调整的次序可以根据证据决定。如果队列无限增长，应先做容量、限流和超时取消，并检查取消后引用是否真的移除；如果缓存过期不清理，应修复淘汰；如果基线稳定但临时数组制造大量分配，可以考虑流式处理、合理批量或减少中间拷贝。盲目加入对象池可能延长存活期，也增加同步和清理负担。

当应用生命周期合理，GC 停顿仍然成为主要瓶颈，再考虑收集器与资源配置。在线服务可以先以 G1 为基线，吞吐敏感任务把 Parallel 纳入候选，严格延迟场景考虑目标版本的 ZGC；小负载和有限 CPU 场景也可以评估 Serial。JDK 9 起 G1 在服务器配置中成为默认，但实际使用什么仍以启动日志和 `VM.flags` 为准。

比较时保持请求组成、并发、CPU 配额、堆预算、预热和测量窗口一致，每次只改变一个主要变量。至少记录吞吐、接口 P95/P99、最大暂停、GC 频率、并发周期、CPU、堆及进程内存；对于 ZGC 再留意分配等待。一次短测无法覆盖缓存预热、周期任务和持续积压，结果应放在预期的生命周期内判断。

选型最终落在三个具体问题上：对象是谁保留的，回收在做什么工作，以及这份工作是否超出了应用的资源和延迟预算。能从日志与引用路径回答它们，才知道该删除一个过期条目、限制一个队列，还是更换回收方式。
