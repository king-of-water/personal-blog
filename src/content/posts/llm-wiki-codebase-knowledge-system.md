接手一个陌生仓库时，我通常先找 README，再看目录、启动入口和几个核心模块。README 如果只写了安装命令，后面的理解几乎都靠搜索：某个接口从哪里进入，数据在哪一层落库，缓存何时失效，模块之间为什么这样依赖。

Coding Agent 也在做同一件事，只是速度更快，代价更隐蔽。它可以不停地 `list`、`grep` 和 `read`，每一步都在消耗上下文。仓库缺少结构化说明时，人要重复理解，Agent 也要重复探索。

LLM Wiki 想把这部分成本提前支付：读取仓库，恢复代码结构，生成一套有目录、有交叉链接、有图、有源码引用的说明。开发者可以浏览，Agent 也可以按需检索。DeepWiki、DeepWiki-Open、RepoAgent 和 CodeWiki 都属于这条路线，只是产品形态和技术重点不同。

这篇文章讨论的是 LLM Wiki 这一类系统，不局限于某个具体产品。我更关心四个问题：它和普通文档生成有什么区别，页面怎样从代码中长出来，代码变更后怎样保持可信，以及它如何同 RAG、FastCode 组成一套代码知识系统。

![LLM Wiki 从代码仓库到可追溯知识页的生成流水线](/images/posts/llm-wiki-pipeline.svg)

## 一、LLM Wiki 解决的是重复理解，不是缺少文字

代码仓库里从来不缺文字。类名、函数名、注释、提交记录和 README 都是文字。真正短缺的是可复用的解释。

比如一个订单系统有这些文件：

```text
api/order_controller.py
application/create_order.py
domain/order.py
domain/pricing.py
infra/order_repository.py
infra/event_publisher.py
workers/order_timeout.py
```

逐文件摘要可以准确描述每个文件，却未必回答新人最关心的问题：创建订单经历哪些步骤，价格在哪个阶段确定，失败如何回滚，超时关闭和支付回调会不会竞争。

这些答案需要跨文件恢复一条业务链路。好的 Wiki 页面围绕读者问题组织，而不是照着目录逐个复述源码。它可能生成“订单创建流程”“价格计算规则”“订单状态机”“事件发布与补偿”四页，并把相关文件作为证据挂在页面下面。

因此，LLM Wiki 的输入是仓库，输出不是一批摘要，而是一套**稳定的知识视图**：

- 页面边界来自架构、领域和流程，不等同于文件边界；
- 页面中的结论能够回到代码符号和仓库版本；
- 页面之间有明确关系，读者能从总览进入细节；
- 代码变化后，系统知道哪些页面需要重新检查。

如果生成结果无法追溯来源，也无法随着代码更新，它只是一份长摘要。第一次阅读或许有帮助，几周后就会变成新的信息噪声。

### 重复理解的代价

一个新成员理解陌生仓库，往往要重复别人已经做过的调查：入口在哪、模块怎么分、某段逻辑为什么这样写。这些结论如果没有沉淀，每个人都要重新走一遍。

LLM Wiki 的价值是把这个调查过程沉淀成可检索、可追溯的产物，让下一个人从结论出发，而不是从零开始。它节省的不是写文档的时间，是重复理解的时间。

### 与知识管理的区别

知识管理关注"存下来"，LLM Wiki 关注"能用起来"。能查、能引、能更新，才算可用。

单纯把资料集中到一个地方，不等于知识可被使用。可检索、可引用、可更新，才是 Wiki 和资料堆的区别。

## 二、它也是知识库，但知识形态和 RAG 不同

把 LLM Wiki、RAG 和 FastCode 放在一起看会更清楚。三者都在建设模型外部知识，也都试图控制 LLM 最终看到的内容。

区别在交付形态。

LLM Wiki 把代码事实加工成可阅读页面。目录、标题、图和交叉链接给读者建立整体认知，适合“我先系统了解这个仓库”。

RAG 根据当前问题即时召回证据。它不要求提前为每个问题写好页面，适合“我现在有一个具体问题”。

FastCode 进一步利用符号、调用、依赖和继承关系做结构导航，在有限 Token 下选择最值得读取的代码，适合“我需要定位实现、还原链路或分析影响范围”。

![LLM Wiki、RAG 与 FastCode 在代码知识系统中的分工](/images/posts/code-knowledge-system-layers.svg)

它们可以共享同一套底层事实：源码、AST、符号表、调用关系、文档、Git 版本和权限。上层分别生成 Wiki 页面、RAG 检索结果和面向 Agent 的最小代码上下文。

这也是我更愿意把它们放进「RAG 与知识库」专栏的原因。它们都在回答同一个工程问题：怎样把仓库中的事实组织成模型和人能够稳定使用的外部知识。

### Wiki 和 RAG 的分工

RAG 解决"给定问题去找相关片段"，Wiki 解决"这个仓库整体长什么样"。前者面向查询，后者面向理解。

两者互补：Wiki 提供结构化的入口和结论，RAG 在需要细节时下钻到原文。把 Wiki 当成 RAG 的替代，会丢掉下钻能力；把 RAG 当成 Wiki 的替代，会丢掉全局视图。

## 三、逐文件总结为什么做不好仓库 Wiki

最容易实现的方案是遍历文件，把每个文件交给 LLM 总结，再拼成页面：

```python
for path in repository.files():
    source = read(path)
    summary = llm.generate(SUMMARY_PROMPT, source)
    save_markdown(path, summary)
```

这个版本很快就能跑起来，也会很快遇到四类问题。

### 1. 局部代码缺少调用背景

一个函数的真实角色取决于谁调用它、它调用谁、参数从哪里来、结果流向哪里。只把函数正文交给模型，它可能正确解释算法，却误判这个函数在系统中的职责。

例如 `calculate_price()` 看起来负责计算价格，实际可能只是实验分流后的一个实现。页面如果不包含调用方、开关配置和兜底路径，就会把局部实现写成系统规则。

### 2. 文件结构不是读者的知识结构

目录通常服务于构建系统、依赖管理和团队分工。读者更关心入口、流程、状态、边界和常见改动。一个业务流程可能横跨 controller、service、domain、repository 和 worker，按文件生成文档会把这条链路切碎。

### 3. 摘要会在向上汇总时失真

很多实现采用“先总结函数，再总结文件，再总结模块，最后总结系统”的树形压缩。每一层都可能丢掉条件、例外和不确定性。到架构总览时，原始证据已经经过几轮改写，读起来连贯，事实却难以核对。

### 4. 全量重写让 Wiki 越更新越不可信

一次提交只改了支付超时策略，如果系统重新生成整个 Wiki，未受影响的页面也会改变措辞，甚至引入新的解释偏差。评审者无法从庞大的文档 diff 中判断哪些变化来自代码，哪些只是模型换了一种说法。

因此，仓库 Wiki 需要先建立结构模型，再规划页面，并把每一条结论和证据、版本、更新范围绑定起来。

### 逐文件总结的另一种失败：术语不一致

逐文件总结时，每个文件由不同上下文生成，同一个概念可能被叫成不同名字，同一个名字可能指不同东西。

术语不一致比错误更难发现，因为它看起来都合理。Wiki 需要一层术语表，统一概念和命名，让不同页面在说同一件事时用同一个词。

## 四、第一层：把仓库编译成知识模型

LLM Wiki 的离线阶段很像编译器前端。系统先解析仓库，得到比原始文本更适合推理的中间表示。

### 代码实体有哪些

代码实体包括：模块、类、函数、接口、类型、配置项、命令行参数、环境变量、数据表、消息主题。

抽取实体是构建知识模型的第一步。实体清单决定了 Wiki 能引用什么，也决定了页面能组织到什么粒度。

### 1. 解析代码实体

基础实体至少包括：

```text
Repository
  └─ Package / Module
       └─ File
            ├─ Class / Interface
            ├─ Function / Method
            ├─ Type / Constant
            └─ Configuration
```

Tree-sitter、语言编译器 API 或 LSP 能帮助识别符号、签名、注释和引用。不同语言的可解析程度并不一致，框架生成代码、宏、动态导入和反射还会制造额外困难，所以解析结果要保留语言和解析器置信度。

### 关系怎么定义

常见关系包括：调用、继承、实现、依赖、读写同一状态、发布订阅、配置影响、测试覆盖。

关系让 Wiki 能回答"改这里会影响什么"这类问题，而不只是"这是什么"。只有实体没有关系，Wiki 就退化成一个名词表。

### 2. 提取关系

页面质量很大程度取决于关系。常见关系包括：

- 文件导入与包依赖；
- 函数调用与反向调用；
- 接口实现与类继承；
- API 路由到处理函数；
- 数据模型到表、消息或序列化结构；
- 配置项到读取位置；
- 测试到被测符号；
- 文档到代码路径和符号引用。

静态分析无法完整恢复运行时行为。依赖注入、消息路由、反射和配置驱动逻辑往往需要框架适配器、运行时 Trace 或人工补充。知识模型应该允许“不确定关系”，而不是把所有边都伪装成确定事实。

### 版本绑定为什么重要

代码在变，Wiki 如果不对应版本，很快就会误导人。每个结论都要绑定它对应的 commit 或分支。

版本绑定让 Wiki 能显示"这条结论基于哪个版本"，并在代码变化时把它标记为待更新。没有版本，Wiki 就不知道自己什么时候过期了。

### 3. 绑定版本与来源

每个实体和关系都应携带版本信息：

```json
{
  "id": "symbol:domain.order.Order.confirm",
  "kind": "method",
  "path": "domain/order.py",
  "lines": [84, 121],
  "commit": "8f2a7c1",
  "language": "python",
  "references": [
    "symbol:application.confirm_order.handle",
    "symbol:domain.order.OrderStatus.CONFIRMED"
  ]
}
```

页面引用这个对象时，就能显示对应文件、行号和 commit。用户查看旧版本 Wiki 时也能回到当时的代码，而不是跳到已经变化的主分支。

### 页面规划的三类决策

页面规划要决定三件事：有哪些页面、页面之间怎么组织、每个页面的入口在哪。

好的规划让人能从一个入口走进来，按需要下钻，而不是面对一堆平级的页面。规划是 Wiki 从"一堆文档"变成"一个结构"的关键一步。

### 页面类型怎么定

页面类型可以按读者的问题分：概览页回答"这是什么"，模块页回答"这部分怎么工作"，流程页回答"一次请求怎么走"，决策页回答"为什么这样设计"，排障页回答"出错时看哪里"。

按问题分类型，比按目录分更贴近使用场景。读者找的是答案，不是目录结构。

### 入口页与导航

入口页是 Wiki 的门面。它应该给出仓库的用途、主要模块、常见任务入口，以及阅读顺序建议。

没有稳定入口的 Wiki，即使页面很多，也很难用起来。使用者需要知道从哪开始，以及下一步去哪。

### 解析要按语言

不同语言有不同的解析方式：静态类型语言可以利用类型信息，动态语言需要处理运行时，多语言仓库要分别解析再用统一模型合并。

解析质量决定知识模型的上限。解析不准，后面全是错的。宁可先支持少数语言并做到准确，也不要贪多而处处出错。

### 解析到什么深度

解析可以只到文件级，也可以到函数级、调用级。深度越深，成本和精度要求越高。

从模块级和文件级开始，逐步深入到关键流程的函数级，是更现实的路径。一开始就要求全仓库到调用级，往往做不完。

### 从仓库到页面的映射

从仓库到页面不是一对一映射。一个实体可能出现在多个页面，一个页面可能聚合多个实体。

映射由读者的问题决定，而不是由代码结构决定。先想清读者要问什么，再决定页面怎么组织。

### 为什么要先建模型再写页面

如果直接写页面，模型会在每个页面里重新理解代码，结论之间可能不一致。先建统一的模型，所有页面引用同一份实体和关系，才能一致。

模型是页面之间一致性的来源。跳过模型直接生成，得到的是一堆看起来相关、实际互相矛盾的文章。

### 模型要不要包含私有逻辑

知识模型应该覆盖可共享的部分。私有逻辑如果要入模型，需要权限标注。

把私密和公开分开，避免 Wiki 成为泄露源。哪些实体、哪些关系可以被谁看到，应该在模型层就定好。

### 知识模型的可视化

把知识模型画出来，能帮助人发现遗漏：哪些实体还没有页面，哪些关系还没有被描述。

可视化也是规划页面的输入。看着结构图规划，比对着实体列表规划更容易发现空白。

### 知识模型的数据结构

一个最小的知识模型可以是一组实体加一组关系：实体有 id、类型、名称和位置，关系有源、目标、类型。

```json
{"entities":[{"id":"svc.order","type":"module","path":"src/order"}],
 "relations":[{"from":"svc.order","to":"svc.pay","type":"calls"}]}
```

数据结构简单一点更好维护。过于复杂的 schema，往往因为没人愿意维护而退化。

### 解析结果的置信度

自动解析的结果不总是可靠，尤其是动态语言和反射。解析结果可以带置信度，低置信的部分标出来。

带置信度能让下游知道哪些结论更可靠，也能把人工评审集中到低置信区域。

### 知识模型的版本

知识模型也要版本化。模型变了，页面要重新生成或更新。

模型和页面版本绑定，才能追溯。否则你会遇到"页面看着新，其实基于旧模型"的情况。

### 知识模型的最小字段

实体至少需要 id、type、name、location 四个字段；关系至少需要 from、to、type 三个字段。

字段够用就行，多了维护不动。先把最小字段跑通，再按需要扩展。

### 知识模型的更新触发

更新可以由 commit、定时任务或人工触发。不同触发器适合不同场景：commit 触发最及时，定时任务最省事，人工触发最可控。

多数团队用定时加按需触发：日常定时增量更新，重大改动手动触发全量重建。

### 一个完整页面的结构

一个模块页可以是这样的结构：一句话职责，主要接口，依赖关系，关键流程，测试，相关决策，相关排障。

结构固定之后，读者知道每一页能去哪里找什么，而不是每页都要重新摸索。

### 页面很多但没人能导航

页面很多、没有入口、没有分类，用户根本找不到需要的那一页。

导航和入口比页面数量更重要。一个有条理的小 Wiki，比一个杂乱的大 Wiki 有用。

## 五、第二层：先规划页面，再生成正文

仓库里有几万个符号，不代表 Wiki 需要几万个页面。页面规划决定哪些知识值得形成稳定入口。

一个实用的页面体系通常包含四类内容。

| 页面类型 | 回答的问题 | 常用证据 |
| --- | --- | --- |
| 系统总览 | 这个项目解决什么问题，主要边界是什么 | README、入口、顶层模块、部署配置 |
| 模块说明 | 某个模块负责什么，对外暴露什么 | 包结构、公开接口、依赖关系 |
| 关键流程 | 一个请求、任务或事件怎样流动 | 路由、调用图、状态变化、消息关系 |
| 核心概念 | 领域对象、规则和约束如何定义 | 类型、校验、状态机、ADR、测试 |

页面规划可以结合三类信号：

1. **结构信号**：目录、包、依赖簇、中心符号和入口点。
2. **语义信号**：README 标题、代码注释、类和方法命名。
3. **使用信号**：提交频率、故障记录、搜索日志和人工指定的重点。

依赖聚类能给出候选模块，模型负责给模块命名并判断是否值得单独成页。模型生成的目录仍需约束，否则容易把同一主题拆成几页近义内容，或者生成“核心功能”“主要模块”这种难以维护的空泛标题。

页面规划最好产出一份可以验证的 manifest：

```yaml
pages:
  - id: order-lifecycle
    title: 订单生命周期
    type: flow
    root_symbols:
      - domain.order.Order
      - application.create_order.handle
      - workers.order_timeout.handle
    required_questions:
      - 订单有哪些状态
      - 哪些事件触发状态变化
      - 并发更新如何处理
```

这样做的好处是，页面生成失败时可以定位到页面规划、证据召回或正文合成中的某一层，而不是只看到一篇“写得不太对”的文章。

### 证据包包含什么

一个页面的证据包包含：相关的代码片段、它们的文件路径和行号、相关的调用关系、相关测试，以及版本信息。

证据包是页面正文的依据。正文的每个关键结论都应该能追到证据包里的某一条。没有证据的结论，就是一段无法核对的描述。

### 证据的时效

证据要带时效。代码更新后，旧证据可能失效。证据包记录每个片段的版本，页面更新时只替换变化的证据。

没有时效标记的证据，会让页面看起来还有效，实际已经过期。时效是证据可信度的一部分。

### 页面规划的输入

页面规划的输入是知识模型加使用场景。知识模型给出有什么，使用场景决定先写哪些。

规划不是把实体一对一变成页面，而是按读者的问题重组。同一个模块，可能既出现在"架构概览"里，也出现在"排障指南"里。

### 规划的两种策略

规划有两种策略：自顶向下（先定分类，再填页面）和自底向上（先聚类实体，再命名页面）。

自顶向下结构清晰但可能遗漏，自底向上贴近实际但结构可能松散。两者结合更稳：先用自顶向下定骨架，再用自底向上补内容。

### 页面之间的引用

页面之间要互相引用：模块页引用流程页，流程页引用决策页，排障页引用模块页。

引用让知识形成网络，而不是一堆孤立页面。断掉的引用是 Wiki 腐烂的信号。

### 页面模板

每类页面用固定模板：概览页有用途、模块、入口；模块页有职责、接口、依赖、测试；流程页有触发、步骤、失败点。

模板让生成稳定，也让读者知道每一页该有什么。没有模板，每页结构都不一样，读者要重新适应。

### 入口的三种

入口可以是目录页、搜索框，或者编辑器里的悬浮提示。不同入口服务不同场景。

最有用的是集成到工作流的入口，例如在代码旁边显示相关结论。放在开发者必经路径上的 Wiki，才会被真正使用。

### 摘要与细节的平衡

页面开头给一段摘要，回答"这页讲什么"，正文展开细节。

摘要是给快速浏览的人，细节是给深入阅读的人。两者都要有，缺任何一个都会让一部分读者流失。

### 页面命名的规范

页面命名要一致：按模块名、按功能、按问题，各有一套命名规则。

命名混乱会让搜索和引用变难。统一的命名规则是 Wiki 可用性的基本功。

## 六、第三层：为每一页组装证据包

模型不应该直接面对整个仓库。生成某一页前，系统要围绕页面目标构建证据包。

以“订单生命周期”为例，证据包可以包含：

- `OrderStatus` 枚举和 `Order` 聚合根；
- 修改状态的方法及其调用方；
- 订单创建、支付回调、取消和超时任务；
- 乐观锁或事务代码；
- 对应单元测试和状态转换测试；
- 描述状态含义的 ADR 或产品规则。

证据选择不能只靠向量相似度。符号引用、调用图、依赖关系和测试映射提供更稳定的结构信号；关键词与向量检索用于补充注释、文档和命名不一致的实现。

每个证据片段还需要记录用途：

```json
{
  "page": "order-lifecycle",
  "claim_scope": "payment transition",
  "source": "application/payment_callback.py:61-104",
  "commit": "8f2a7c1",
  "relation": "calls Order.confirm",
  "confidence": 0.93
}
```

正文生成时，Prompt 要求模型只根据证据包写作，并为架构结论、流程步骤和约束附上引用。没有证据的猜测可以单独标成“待确认”，不能混进确定叙述。

### 分层生成与一次性生成的区别

一次性生成是把整个仓库塞进一次调用，让它写出所有页面。分层生成是先建模型、再规划页面、再逐页组装证据、最后生成。

分层的价值在可控性。每一层都能单独检查和修正，出错时能定位到是哪一层的问题。一次性生成出错，你只知道结果不对，不知道哪一步错了。

### 一致性检查

生成完成后要检查一致性：同一概念在不同页面是否命名一致、图与正文是否矛盾、页面之间的引用是否有效、结论是否都有证据。

一致性检查是 Wiki 可用的前提。一堆各自正确但互相矛盾的页面，比没有页面更容易误导人。

### 生成提示怎么写

生成每页的提示要包含：页面类型、目标读者问题、证据包、术语约束、引用格式和禁止事项。

提示越具体，输出越稳定。让模型自由发挥，会得到风格统一但内容发散的结果。

### 引用校验

生成后要校验引用：每条引用指向的文件和行号是否存在，引用的片段是否真的支持该结论。

引用校验能挡住一部分幻觉，但挡不住"引用存在却不支持结论"的情况，后者需要抽样人工检查。

### 术语表怎么建

术语表从知识模型里的实体抽取，统一同一概念的不同叫法，并给每个术语一个定义和首选写法。

术语表是跨页面一致的基础。没有它，不同页面会用不同的词描述同一个东西。

### 怎么处理矛盾证据

遇到矛盾证据时，不要随意选一个，而是把矛盾暴露出来，标注两个来源和差异。

矛盾往往是代码或文档本身不一致的信号，值得人工介入。掩盖矛盾，会让 Wiki 传达一个错误的确定感。

### 生成质量的下限

生成质量有下限：事实准确、引用有效、术语一致。达不到下限的内容不应该发布。

下限比上限更重要。一篇平淡但准确的页面，比一篇漂亮但错误的页面有用得多。

### 证据包的裁剪

证据包不能无限大。按结论需要裁剪，每页只放相关证据。

裁剪本身是一次检索，可以借用 FastCode 或 RAG 的思路：先定位相关实体，再取其证据。

### 生成失败的恢复

生成失败（超时、格式错）时，要能重试或跳过，不影响其他页面。

批处理要有失败隔离。一个页面失败，不应该让整批生成中断。

### 一个最小的工作流示例

```text
1. 解析代码      → 知识模型
2. 规划页面      → 页面清单
3. 组装证据      → 每页证据包
4. 生成正文      → 草稿
5. 自动校验      → 引用、术语、一致性
6. 人工评审      → 发布
7. 代码变化      → 增量更新
```

这个流程每一步都能单独跑。哪一步质量差，都会在后面的步骤里暴露，但至少能定位。

### 页面草稿与发布

草稿和发布分开。草稿可以自由改写，发布要经过校验。

分开之后，未完成的页面不会污染正式内容，读者看到的始终是校验过的版本。

### 知识模型与代码搜索的区别

代码搜索找的是"哪里有这个字符串"，知识模型回答的是"这属于哪个模块、和谁有关系"。

两者服务于不同问题。搜索适合已知目标，知识模型适合理解和导航。

## 七、分层生成不是反复总结

大型仓库无法一次放进上下文，分层生成不可避免。问题在于怎样减少信息经过多轮改写后的漂移。

RepoAgent 的思路是先分析全局结构，再为代码对象生成文档，并利用 Git 变化维护文档。CodeWiki 更进一步，把仓库级文档拆成层次结构，通过递归 Agent 生成文字和可视化内容。DocAgent 则把分层处理用于上下文感知的 docstring 生成。

这些工作共同说明：局部内容需要全局结构，上一层也需要能够重新访问底层证据。

一个较稳妥的分层方式是：

```text
代码事实层
  ↓
符号卡片：职责、签名、引用、证据位置
  ↓
模块页：公开能力、内部协作、依赖边界
  ↓
流程页：跨模块调用、状态变化、失败路径
  ↓
系统总览：模块地图、关键入口、部署边界
```

上层页面不只读取下层摘要，还能沿引用回到原始符号。模型写“订单服务通过消息队列通知库存服务”时，系统应当提供发布代码、Topic 配置和消费入口。只有模块摘要而没有底层证据时，这个结论很容易把计划中的设计写成已经运行的事实。

生成顺序也可以根据依赖关系安排。先处理被大量依赖的基础模块，再处理调用它们的上层模块，后续页面会得到更稳定的背景。遇到循环依赖时，可以先生成实体卡片，再以依赖簇为单位完成模块说明。

### 图应该回答什么问题

Wiki 里的图应该回答结构问题：模块如何分层、一次请求如何流过、数据如何流转、哪些部分耦合紧密。

为每个模块画一张装饰性架构图没有意义。图要有明确的问题，并且答案只能靠图说清楚，而不是靠一段文字。

### 图与正文的一致性

图如果和正文分开生成，很容易矛盾。图应该从同一份知识模型生成，正文和图共享实体和关系。

把图和正文绑在同一份模型上，是保证一致的最简单办法。分开生成的图，早晚会和正文对不上。

### 一个最小的生成提示示例

```text
页面类型：模块页
读者问题：这个模块负责什么，和谁交互
证据包：见下方代码片段、调用关系和测试
要求：每个关键结论后附引用；不确定的内容标注"待确认"
禁止：不得编造未出现在证据里的行为
```

提示把"页面目的"和"约束"写清楚，模型才有稳定的输出边界。

### 排障页怎么生成

排障页按故障现象组织：现象、可能原因、排查步骤、验证方式。它的证据来自代码里的错误分支、日志和测试。

排障页价值很高，但需要真实故障数据。没有真实数据的排障页，只是猜测清单。

### 从生成到人工确认的工作流

工作流可以是：模型生成草稿，自动检查通过后进入待审，人工确认后发布。

分级发布：低风险页面自动发布，高风险页面人工确认。自动化的比例应该随信任度提高，而不是一开始就全自动。

### 一个常见误区：追求全自动

全自动听起来省事，但高风险内容的错误代价高，半自动加人工确认通常更稳。

把人工放在关键位置，而不是追求零人工。零人工的系统，一旦出错也没有人在回路里拦截。

### 生成的批量与单页

批量生成快但难以精细控制，单页生成慢但可控。可以批量生成初稿，再对重点页面单独精修。

混合策略兼顾效率和重点。全部精修太慢，全部批量太粗。

### 引用与行号的稳定性

代码变化会让行号失效。引用可以绑定到实体 id 或符号，而不是固定行号。

符号级引用比行号更稳定。行号一改就错，符号级引用能容忍代码移动。

### 一个常见的过度设计

有些团队一开始就上知识图谱、多模态、实时更新。结果基础没做好，系统复杂且不可用。

从最小可用开始，按真实需求增加复杂度。先把模型、规划、证据做扎实，再考虑花哨的部分。

## 八、图不是装饰，它应该回答结构问题

自动 Wiki 很喜欢生成大量流程图，但图多并不代表解释清楚。每张图应当回答一个确定问题。

| 问题 | 合适的图 |
| --- | --- |
| 系统有哪些边界和外部依赖 | C4 Context / Container 图 |
| 请求经过哪些组件 | 时序图或请求路径图 |
| 对象怎样改变状态 | 状态机 |
| 模块之间怎样依赖 | 依赖图 |
| 数据从哪里产生、流向哪里 | 数据流或事件流图 |

图中的节点最好来自已经解析出的实体，边来自静态分析、配置或 Trace。让模型凭正文自由生成图，常见问题是节点名称与源码不一致、箭头方向错误、把同一模块画成几个不同组件。

一个可验证的生成过程应先得到结构化图数据：

```json
{
  "nodes": [
    {"id": "api", "label": "Order API", "source": "api/order_controller.py"},
    {"id": "app", "label": "Create Order", "source": "application/create_order.py"},
    {"id": "repo", "label": "Order Repository", "source": "infra/order_repository.py"}
  ],
  "edges": [
    {"from": "api", "to": "app", "type": "calls"},
    {"from": "app", "to": "repo", "type": "writes"}
  ]
}
```

渲染器只负责布局与样式。这样既能更换图形引擎，也能单独验证节点是否存在、边是否有依据。

### 知识模型的存储格式

知识模型可以用图数据库、关系库或 JSON 文件存储。小规模用 JSON 就够，规模上来后才需要图数据库。

存储选择影响查询能力。需要复杂关系查询时，图结构更方便；只需要按 id 取实体时，普通键值存储就够。先用最简单的存储把流程跑通，再按查询需求升级。

### 页面粒度怎么定

页面太粗，一页塞进太多内容；太细，页面数量爆炸。合适的粒度是一页回答一个主要问题。

一个检验方式：如果一页里有两个不相关的问题，就该拆开；如果两页总是一起被搜到，可以考虑合并。

### 变化检测

变化检测可以基于 commit diff、文件哈希或实体哈希。哈希粒度越细，更新越精确，但计算越多。

从文件级哈希开始通常够用；需要更精确时，再下沉到实体级。

### 更新流水线

更新流水线包括：检测代码变化、定位受影响实体、确定受影响页面、重组证据、重建或局部更新页面。

每一步都能单独运行。全量重建是更新流水线的一个特例，不是默认选项。

### 页面更新的一致性

更新一页时，可能影响其他页面的引用。更新要检查反向引用，看看哪些页面引用了被改动的实体。

孤立的页面更新，会让 Wiki 内部产生新的矛盾。更新是全局操作，不是单页操作。

### 什么时候重新规划

当仓库架构大改，或者使用场景变化时，要重新规划页面。规划不是一次性的。

定期审视页面结构，能避免 Wiki 结构僵化。旧结构可能还在，但已经不再匹配现在的代码。

### 更新时的冲突

同一实体被多个页面引用时，更新要同步所有页面，否则会产生不一致。

维护反向索引能快速找到所有引用。没有反向索引，更新只能靠人记住哪些页面受影响。

### 页面的生命周期

页面有生命周期：创建、更新、废弃。废弃的页面要归档，而不是留在主目录。

生命周期管理避免 Wiki 无限膨胀，也避免读者看到已经废弃的内容。

### 什么时候用人工精写

核心架构决策、对外接口、安全相关的政策适合人工精写，自动生成只做初稿。

人工精写保证质量，自动生成保证覆盖。两者分工，才能既广又准。

### 生成风格过于统一的问题

自动生成的页面容易读起来一样，缺少重点。可以在模板里加入"这一页最重要的三件事"这样的字段。

强制指定重点，能打破千篇一律，也让读者更快抓住关键。

### 怎么避免 Wiki 变成"另一个没人看的知识库"

让它出现在开发者已经在用的地方：IDE、PR、搜索，而不是要求他们主动去访问。

降低使用成本，比增加内容更重要。一个需要专门打开、登录、搜索的系统，使用率注定很低。

## 九、更新能力决定 Wiki 能活多久

初次生成很容易让人惊艳，长期维护才是难点。代码每天变化，自动 Wiki 必须回答三个问题：

1. 哪些知识实体受到影响；
2. 哪些页面引用了这些实体；
3. 页面中哪些结论需要重写或重新确认。

RepoAgent 使用 Git 追踪代码变化，并根据受影响对象和双向引用更新最小范围文档。这个方向比定时全量重建更适合真实仓库。

一次增量更新可以这样执行：

```text
Git diff
  ↓
识别新增、修改、移动、删除的符号
  ↓
更新邻接关系与索引
  ↓
查找引用这些实体的页面和结论
  ↓
重建受影响段落与图
  ↓
检查悬空链接、冲突结论和置信度下降
  ↓
生成可评审的文档 diff
```

删除比新增更难处理。一个函数消失后，页面可能仍然描述旧流程；一次重命名可能被误识别为删除加新增；公共接口变化还会影响调用方页面。实体要有尽量稳定的身份标识，更新算法也要结合路径、签名和代码相似度识别移动与重命名。

文档 diff 应尽量小。未受代码变化影响的段落不要重新生成，否则评审者会被措辞变化淹没。模型和 Prompt 版本也要记录，因为换模型可能让相同证据产生不同叙述。

### 增量更新的三种粒度

更新有三种粒度：整页重建、片段更新、结论级更新。整页重建最省心但最贵；片段更新只改变化的部分；结论级更新最精细，但需要判断哪条结论受影响。

选择取决于更新频率和页面稳定性。频繁变化的模块适合片段更新，稳定的概览页可以整页重建。

### 失效与删除

代码删掉后，Wiki 里的对应内容要标记失效或删除。残留的失效内容会误导人，而且很难发现。

处理方式有两种：标记为"已失效"并保留历史，或者直接移除并在变更记录里留下痕迹。选择取决于是否有审计需求。

### 怎么判断一个结论可信

一个结论可信，需要满足三条：有证据支持、证据是当前版本的、证据和结论之间没有跳跃。

任何一条不满足，结论就应该标为待确认。可信度是每条结论的属性，而不是整篇页面的属性。

### 敏感信息

Wiki 可能包含内部逻辑、密钥引用、业务流程。生成和发布要考虑权限和密级。

把内部 Wiki 和公开 Wiki 分开，是最简单的边界。混淆两者，可能把内部信息暴露到公开环境。

### 多仓仓库

一个团队往往有多个仓库，它们之间有依赖。跨仓的 Wiki 需要把多个知识模型合并，并标注跨仓关系。

跨仓关系是理解系统全貌的关键，也是最容易被忽略的部分。只写单仓，看不到系统整体的耦合。

### 评测的基线

先建立一个基线：当前 Wiki 的准确度、覆盖度和新鲜度。之后每次改动都对比基线。

没有基线，无法判断改动是否真的改进。基线不需要完美，但需要一致。

### 一个可选的评测指标表

| 指标 | 测什么 | 怎么测 |
| --- | --- | --- |
| 事实准确度 | 结论是否成立 | 抽样人工核对 |
| 覆盖度 | 重要实体是否被写 | 模型实体对比页面引用 |
| 新鲜度 | 是否对应当前代码 | 版本绑定检查 |
| 可读性 | 是否好读 | 读者反馈 |

### 常见疑问：自动生成会不会错

会。任何自动生成都会错。关键是让错误可发现、可修正、可隔离。

把错误控制在可修正的范围内，是自动生成可用的前提。追求零错误不现实，追求可控才现实。

### 评测的样本量

评测不需要覆盖全部页面，抽样即可。关键在于样本要覆盖不同类型的页面和高风险区域。

样本少但选得准，比样本多但随机更有信息量。

### 页面质量的抽检方法

抽检：随机选页面，随机选页面里的结论，回到代码验证是否成立。

抽检频率和风险挂钩，高风险页面抽得更密，稳定页面抽得稀疏。

### 评测结果的解读

准确度、覆盖度、新鲜度三个指标要一起看。准确度高但覆盖度低，说明能查到的都准，但很多查不到。

单看一个指标会误判。三个指标共同描述 Wiki 的健康状况。

### 评测与线上问题

线上问题可以作为评测来源：用户找不到某内容、引用点开发现过期，都进入评测集。

真实问题比想象的问题更值得评测。它反映的是系统在真实使用中的短板。

### 评测的三条线

准确度、覆盖度、新鲜度，各设一条最低线。低于线就触发维护，而不是等出问题。

把维护变成有触发条件的动作，比靠人的自觉更可靠。

## 十、可信度不能只看文章是否流畅

LLM 很擅长把零散代码写成连贯说明，流畅恰好会掩盖错误。评测需要拆成几层。

### 1. 事实准确度

- 页面引用的文件、类和函数是否存在；
- 参数、返回值、异常和配置项是否与代码一致；
- 调用与依赖关系是否有静态或运行时证据；
- 页面版本是否对应正确 commit。

这部分尽量用确定性检查完成，不要再让另一个 LLM 全权裁判。

### 2. 覆盖度

- 关键入口、核心模块和主要流程是否有页面；
- 页面是否遗漏失败分支、权限检查和异步路径；
- 架构图是否覆盖实际部署组件；
- 重要术语是否能从索引进入对应解释。

### 3. 可用性

- 新人能否根据 Wiki 找到修改入口；
- Agent 能否借助页面减少文件读取和无效搜索；
- 用户提问后能否得到带来源的答案；
- 页面是否在合理步数内从总览导航到实现。

### 4. 新鲜度

- 代码提交后多久更新相关页面；
- 受影响页面召回率是多少；
- 是否存在指向已删除符号的链接；
- 文档版本落后主分支多少个提交。

还要专门设计拒答样本。仓库中没有证据时，系统应明确说不知道，不能为了补齐页面结构而生成一个合理故事。

### 怎么测事实准确度

事实准确度可以抽样人工核对：随机选页面里的陈述，回到代码确认是否成立。

抽样能给出一个估计，不需要逐条检查。准确度低于某个阈值，说明生成质量有问题，需要回头改知识模型或证据组装。

### 怎么测覆盖度

覆盖度衡量 Wiki 覆盖了多少重要实体和关系。可以对比知识模型里的实体总数和 Wiki 里被引用的实体数。

覆盖度低，说明很多代码没有被写进 Wiki，使用者会遇到"查不到"的情况。覆盖度是 Wiki 是否有用的前提。

### 人工评审放在哪

人工评审应该放在高风险或高价值的页面上，而不是平均分配。核心模块、易错逻辑、关键决策值得人工过一遍。

把人工放在最有用的地方，比追求全量评审更现实。全量评审既慢，又容易因为疲劳而流于形式。

### 评测周期

Wiki 需要定期评测：每月抽样检查准确度、覆盖度和新鲜度，观察是否退化。

定期评测让 Wiki 保持可信，而不是上线后慢慢腐烂。没有评测的 Wiki，会在几个月内失去参考价值。

### Wiki 的版本管理

Wiki 本身也要版本管理。每次更新生成一个新版本，保留历史，能回滚。

把 Wiki 和代码版本绑定，能让人知道某一版 Wiki 对应哪一版代码。没有版本绑定，Wiki 的时效性无从判断。

### Wiki 的搜索

Wiki 需要一个好的搜索：按术语、按模块、按问题都有入口。

搜索是 Wiki 的常用入口。没有搜索，多页面 Wiki 很难用起来。

### 与 RAG 结合的使用场景

用户问一个具体问题，先用 RAG 找片段；如果片段属于某个模块，再跳到 Wiki 的模块页看全局。

Wiki 给背景，RAG 给细节。两者结合，比任何单独一个都更完整。

### 与 onboard 的关系

新成员的上手最需要 Wiki。给一个"从这里开始"的路径，能显著缩短上手时间。

入口页可以跟着 onboarding 需求设计：新人最常问什么，入口就先回答什么。

### 如何让 Wiki 被搜索到

加入站内搜索，把 Wiki 和代码仓库关联，在 PR 里链接相关页面。

被搜索到才可能被使用。藏在角落里的 Wiki，写得再好也没人看。

## 十一、LLM Wiki 和 RAG 应该怎样连接

Wiki 页面本身可以进入 RAG，但不能只索引最终文章。更好的做法是保留三个检索层次。

### 第一层：页面索引

用于寻找“订单状态机”“权限模型”这类稳定主题。它有清晰标题和完整上下文，适合先确定知识位置。

### 第二层：结论与证据索引

把页面中的关键结论拆成带来源的记录。查询命中结论后，可以一起返回支持它的代码片段、版本和关系边。

### 第三层：原始代码索引

当页面没有覆盖新问题，或者 Agent 要执行修改时，继续搜索符号和代码正文。FastCode 一类结构导航工具适合承担这一层。

一次查询可以按下面的顺序路由：

```python
def query_code_knowledge(question):
    page = wiki_index.search(question)
    if page.confidence >= 0.85 and page.is_fresh:
        return answer_with_citations(question, page)

    evidence = claim_index.search(question)
    if evidence.coverage >= 0.75:
        return answer_with_sources(question, evidence)

    return fastcode.scout_and_read(question)
```

阈值只是示意，重点是查询路径。系统先利用已经沉淀的稳定解释，证据不足时再下钻到代码结构和正文。Agent 不必每次从目录开始重新认识仓库。

### 三层索引怎么衔接

页面索引支持"我大概想知道什么"，结论索引支持"这个具体结论在哪"，原始代码索引支持"给我看原文"。

三层从粗到细，使用者按需要下钻。缺任何一层，都会让某类查询落空。

### 和 FastCode、Repo Map 的关系

FastCode 侧重"给定任务找到最小充分上下文"，Repo Map 侧重"快速给出仓库结构地图"，LLM Wiki 侧重"把仓库编译成可读的知识页"。

三者都在解决代码理解，但产物不同：一个是上下文，一个是地图，一个是知识库。它们可以叠加，而不是互相替代。

### 与手工文档的关系

LLM Wiki 补充而不是取代手工文档。核心决策、对外接口适合手工精写，大量模块说明适合自动生成。

两者分工：手工写"重"的、稳定的内容，自动生成"广"的、变化的内容。

### 与代码评审的关系

代码评审时，如果改动影响 Wiki，可以在评审里提示"相关 Wiki 需要更新"。

把 Wiki 更新纳入评审流程，才能跟上代码变化。靠事后补更新，几乎一定会漏。

### 与需求、Issue 的连接

把 Wiki 页面和需求、Issue 连接，能形成"需求到代码到知识"的链路。

这条链路让追溯更容易：从一个需求出发，能看到它落到哪些代码，以及这些代码的说明在哪里。

### 术语表的维护

术语表需要维护：新术语加入，旧术语更新，冲突术语仲裁。

术语表是活的，不是一次性文档。没有维护的术语表，很快会和代码里的实际命名脱节。

### 一个反例：把源码注释当 Wiki

源码注释是给读代码的人，Wiki 是给需要全局理解的人。两者目标不同，结构也不同。

把注释汇总当 Wiki，得到的是一堆碎片。碎片拼不出全局视图，也无法回答"改这里会影响什么"。

### 与外部文档的连接

Wiki 可以链接到外部文档、规格、设计稿，形成更完整的背景。

链接让 Wiki 不必重复所有内容，只负责组织和指向。它把分散的资料串联起来。

## 十二、Wiki 还需要吸收代码之外的知识

只读取源码，系统能解释“现在怎么做”，很难准确解释“为什么这样做”。很多重要知识并不在代码中：

- 架构决策记录中的方案取舍；
- 故障复盘中的真实失效模式；
- 产品规则中的边界和例外；
- 迁移文档中的临时兼容逻辑；
- 团队 Skills 中的修改方法和验证清单。

这些材料应当和代码事实分开标记。代码可以证明某个分支存在，ADR 可以解释为什么保留它，测试可以证明哪种行为受到保护。模型生成页面时要区分事实来源，遇到冲突时显示版本和时间，而不是自动把几份材料揉成一个结论。

权限也必须在索引阶段执行。私有文档、敏感配置和跨团队代码不能先进入统一上下文，再依赖 Prompt 要求模型保密。页面缓存、向量索引、问答历史和生成结果都要继承原始数据的访问边界。

### 非代码知识的来源

代码之外的知识包括：设计决策、业务规则、历史 bug、外部依赖约定、运维流程。这些往往存在于文档、Issue、聊天记录和人脑里。

把这些知识纳入 Wiki，需要来源和确认机制。没有确认的推测，不应写成结论，只能标为待确认。

### 决策记录怎么进 Wiki

设计决策适合用 ADR 的形式记录：背景、决策、理由、后果。它回答的是"为什么这样设计"。

把 ADR 和代码实体关联，能让人在读到某段代码时，找到它背后的决策。代码说明"怎么做"，决策记录说明"为什么这么做"。

### 成本估算

主要成本是生成和更新。全量生成贵，增量更新便宜。按仓库变化频率规划更新。

把成本和变化频率挂钩，能避免不必要的全量重建。一个每月才变几次的仓库，不需要每天全量重生成。

### 从文档到可执行检查

有些 Wiki 结论可以转成可执行检查，例如"模块 A 不能依赖模块 B"可以变成静态检查。

能转成检查的结论价值更高，因为它不依赖人记住。把可检查的结论沉淀成规则，是 Wiki 的高阶用法。

### 一个团队的分工

知识模型的维护、页面生成、人工评审可以由不同角色承担。

分工明确，Wiki 才能持续维护。一个人既做大模型又做评审，很快就会停下来。

## 十三、一套可落地的最小实现

如果要在团队内部试做，我会把第一版控制在下面这条链路：

```text
Git 仓库
  ↓
Tree-sitter / LSP 提取文件、符号、引用
  ↓
关键词索引 + 向量索引 + 简单依赖图
  ↓
人工指定 5 到 10 个高价值页面
  ↓
为每页构建可追溯证据包
  ↓
LLM 生成 Markdown 与结构图数据
  ↓
静态检查 + 人工评审
  ↓
Git diff 驱动增量更新
```

第一版不要急着自动发现全部页面。选一个边界清楚、日常会被问到的仓库，先覆盖系统总览、两个关键流程、两个核心概念。每页保留源码链接、commit 和生成时间。

验收也可以很具体：找三名不熟悉仓库的开发者，让他们分别完成定位入口、解释流程和判断改动影响的任务；再让 Coding Agent 在有 Wiki 和没有 Wiki 的条件下执行同一组问题，比较文件读取次数、Token、引用准确率和最终结论。

效果稳定后再增加自动页面规划、更多语言适配、运行时 Trace 和跨仓库关系。过早追求“一键生成整个公司代码百科”，会把精力耗在页面数量和模型成本上，忽略最重要的可信度与更新链路。

### 最小实现的组件

一个最小实现需要：代码解析器、知识模型存储、页面规划器、证据组装器、生成器、一致性检查器、更新器。

这些组件可以先用脚本实现，不必一开始就做成平台。先把流程跑通，再按需要把重复的部分抽成工具。

### 从哪个仓库开始

选一个有代表性、但不至于太大的仓库开始。最好是团队熟悉、有真实问题、有明确使用者的仓库。

从太小的玩具仓库开始，测不出真实问题；从太大的仓库开始，第一版就做不完。

### 一个可选的目录结构

```text
wiki/
├── index.md          # 入口
├── glossary.md       # 术语表
├── modules/          # 模块页
├── flows/            # 流程页
├── decisions/        # 决策记录
└── troubleshooting/  # 排障页
```

目录结构反映页面类型。清晰的目录让人一眼看出 Wiki 的组织方式。

### 与 CI 集成

把 Wiki 生成和更新放进 CI：代码合并后触发增量更新，检查一致性和引用有效性。

集成到 CI，Wiki 才会持续更新，而不是靠人记得。没有 CI，Wiki 会在几周内落后于代码。

### 谁来维护

Wiki 需要所有者。没有所有者，页面会过期，术语会漂移，评测会停。

所有者不一定是专职，但要有明确的人负责定期评测和更新策略。

### 一个失败案例

一个团队用模型自动生成了五百个文件页，看起来很多。使用时却发现没有入口、术语混乱、半数页面基于旧分支。

问题不在生成数量，而在缺少模型、规划和版本绑定。这个案例说明，Wiki 的质量不取决于生成了多少，而取决于结构是否清楚、结论是否可信。

### 从 Wiki 到团队共识

Wiki 的一个隐藏价值，是它逼团队把"默认知道"的东西写下来。写下来才能讨论，讨论才能形成共识。

从这个角度看，Wiki 是团队对齐的工具，而不只是文档。它把隐性的理解变成显性的、可讨论的资产。

### 从知识到行动

Wiki 的最终价值是支持行动：改代码前的评估、排障、onboarding、评审。

如果 Wiki 不能支持具体行动，它就只是装饰。每一页都应该能回答"读者看完之后能做什么"。

### 一条判断是否值得做的标准

如果团队经常重复问同样的问题，或者新人上手很慢，LLM Wiki 值得做。

反过来，如果仓库很小、团队很熟悉，或者代码变化快到来不及维护，就可以先不做。工具要匹配问题，而不是为了做而做。

## 十四、几个容易忽略的失败模式

### 1. 页面正确，却对应错误分支

用户在看 release 分支，Wiki 来自主分支。两边内容都正确，结合起来就是错误答案。页面上必须显示仓库、分支和 commit，检索时也要把版本作为过滤条件。

### 2. 图和正文各自生成，互相矛盾

流程图显示 A 调用 B，正文写 B 通过事件触发 A。图与正文应共享同一份结构化事实，不能各写一遍 Prompt。

### 3. 生成页面很多，却没有稳定入口

自动目录如果每次更新都改变页面层级和标题，外部链接、团队记忆和 Agent 引用都会失效。页面 ID 应保持稳定，标题变化通过重定向处理。

### 4. Wiki 代替了源码验证

Wiki 是导航和解释层。Agent 真正改代码前仍要读取相关实现、测试和配置，并执行验证。页面可能过期，也可能遗漏动态行为。

### 5. 把“没有写下来”误判成“不存在”

静态分析没找到调用，不等于线上没有调用。反射、插件、脚本和外部消费者都可能绕开可见关系。页面需要说明分析边界，并允许维护者补充人工关系。

### 安全：Wiki 也是攻击面

Wiki 内容会进入模型上下文，可能被注入。生成和消费时都要区分"资料"和"指令"。

内部 Wiki 里的敏感信息也要限制在授权范围内，避免通过检索泄露。

## 十五、我对 LLM Wiki 的理解

LLM Wiki 可以看成一种面向代码仓库的知识编译器。

源码、文档和版本历史是原材料。解析器恢复符号与关系，页面规划确定知识边界，检索为每页准备证据，LLM 把证据编排成人能读懂的解释。Git diff 和验证器负责让这份解释继续跟得上代码。

这套系统同时服务两类读者。人通过目录和图建立心智模型，Agent 通过页面索引、结论索引和源码关系图取得上下文。Wiki 负责沉淀稳定解释，RAG 负责按问题取证，FastCode 负责在代码结构中继续下钻。三者共享底层事实时，代码知识才不会被重复生成、重复索引和重复理解。

如果只记住一个判断标准，我会选这个：**一条 Wiki 结论能否回到对应版本的代码证据，代码变化后系统又能否找到并更新它。**

能做到这两点，LLM Wiki 才是一套可以长期使用的代码知识库。

### 一个端到端案例

用一个中等规模仓库把流程串起来：解析出实体和关系；规划出概览、模块、流程、决策四类页面；组装证据；生成正文和图；一致性检查发现术语不一致并修正；发布后按代码变化做增量更新。

每一步都能单独检查。Wiki 的质量来自这些可检查的步骤，而不是某一次生成的效果。

### 常见问题：Wiki 没人看

Wiki 没人看，通常是因为入口不明显、结论不具体，或者没集成到工作流。解决方法不是写更多，而是把它放到开发者的必经路径上。

### 结语

LLM Wiki 的目标是让理解可以积累。它把对代码的调查变成可追溯、可更新的知识，让下一个人站在前人的结论上。做到这一点，Wiki 才不是负担，而是资产。

### 三件事决定 Wiki 能不能活

模型准不准、更新跟不跟得上、人用不用。三者缺一，Wiki 就会腐烂。

准确是基础，更新是维持，使用是目的。三件事都要有人负责，Wiki 才是长期资产，而不是一次性的产出。

### 一个实践建议

先把一个模块做透，作为样板。样板立起来之后，其他模块按同样的模式扩展。

一次性铺开所有模块，往往因为质量参差而失去信任。一个高质量的样板，比十个半成品更有说服力。

### 一个团队引入 LLM Wiki 的节奏

第一周选一个模块做样板；第二周补自动化；第三周接 CI 和搜索；第四周做第一批评测。

节奏从窄到宽，每一步都有可验收的产出。一上来就全仓库铺开，几乎一定会因为质量不齐而失败。

### 一个可选的页面清单模板

```text
- 概览：这个仓库做什么
- 模块：每个模块做什么
- 流程：关键流程怎么走
- 决策：为什么这样设计
- 排障：出错时看哪里
```

清单不用一次填满，但结构先定下来。结构定了，后续生成和更新才有落点。

### 与个人笔记的区别

个人笔记服务个人理解，Wiki 服务团队共享。Wiki 需要统一的术语、结构和引用。

把个人笔记直接当 Wiki，会有大量只有作者能看懂的缩写和跳跃。共享内容需要更完整的表达。

### 一个常见问题：Wiki 和代码不一致

Wiki 和代码不一致时，以代码为准，并触发生成更新。代码是事实来源，Wiki 是解释。

把这条规则写清楚，能避免在评审里争论"到底哪个对"。事实永远以代码为准，Wiki 负责跟上。

### 结语：把理解变成资产

代码会变，人会走。留下的如果只是代码，下一个人还得重新理解。LLM Wiki 把理解本身沉淀下来，让团队少走重复的路。

### 一个可选的更新策略

按变化频率分层：高频模块每周增量更新，低频模块每月更新，概览页每季度重审。

分层更新把维护成本控制在可承受范围。所有内容用同一频率更新，要么过度，要么不足。

### 常见问题：生成太慢

生成慢通常是证据包太大，或者用了过强的模型。可以先缩小证据包，再用更快的模型做初稿，强模型只做精修。

### 一个判断页面是否值得写的标准

如果一页不能回答读者的一个具体问题，就不值得单独成页。页面的存在理由是回答问题，而不是凑数量或让目录显得完整。

### 关于维护成本的提醒

自动化降低了生成成本，但没有降低维护成本。维护需要人，人需要时间。规划时要把维护算进去。低估维护成本，往往是知识库项目失败的原因，而不是生成能力不够。
