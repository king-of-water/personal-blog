第一次写这篇文章时，我把 LLM Wiki 几乎等同于“把代码仓库生成成文档”。这个说法没有完全错，却把它说窄了。

代码仓库只是很适合做 Wiki 的一种知识源。真实团队里的知识还散落在 PRD、接口文档、数据字典、运维手册、事故复盘、会议决议、工单和结构化业务记录中。只读代码，可以知道系统现在怎样执行，却未必知道业务为什么这样规定；只读 PRD，可以知道产品想实现什么，却未必知道线上真正跑成了什么。

更准确地说，LLM Wiki 是一种**知识编译系统**：它把多种原始资料解析成统一的知识对象，再按读者的问题生成有结构、有引用、有版本的页面。人可以顺着页面建立整体认识，Agent 也可以检索这些页面和底层证据。

这里的“LLM Wiki”不是某个固定标准或唯一产品名。不同产品的实现差别很大，本文讨论的是这类系统共同面对的工程问题。

## 一、它要解决的不是资料存放，而是重复理解

假设一个新同学要弄清“退款为什么有时原路退回，有时退到账户余额”。资料可能分散在下面几处：

- PRD 写着当前产品规则；
- 接口文档说明支付渠道支持哪些退款方式；
- 代码里有真实的路由条件和补偿逻辑；
- 数据表记录退款单状态；
- 事故复盘说明某个边界为什么不能再改；
- 群聊里还有一次没有正式沉淀的口头决定。

把这些资料集中到一个文件夹，只解决了“放在哪里”。读者仍然要自己搜索、判断版本、识别冲突，再拼出完整结论。下一个人来时，还要重新做一遍。

LLM Wiki 想沉淀的是这段理解过程。最终页面不只是列出资料，而是直接回答：

1. 退款方式由哪些条件决定；
2. 一次退款从受理到完成经过哪些系统；
3. 哪些结论来自产品规则，哪些来自当前代码；
4. 两个来源冲突时，以哪个为准；
5. 这页对应哪个版本，最近为什么发生变化。

因此，判断一套系统是不是可用的 Wiki，不能只看它生成了多少页。更重要的是，读者能否从页面回到证据，资料变化后页面能否及时失效或更新。

### 普通文档、RAG 和 LLM Wiki 分别做什么

普通文档适合由作者主动表达判断。作者知道读者是谁，也知道哪些背景可以省略。它的优势是准确、有取舍，弱点是覆盖和更新依赖人。

RAG 面向一次具体查询。问题来了，系统从资料中找若干相关片段，把证据交给模型。它很适合回答“退款单有哪些状态”，但几个片段通常不会天然组成一套稳定的阅读结构。

LLM Wiki 面向反复理解。它会预先生成“退款总览”“状态流转”“渠道差异”“异常恢复”等页面，建立导航和交叉引用。读者不需要先想出精确问题，也可以从入口逐层读下去。

三者可以共存。高质量手写文档是重要知识源；Wiki 页面可以进入 RAG 索引；RAG 发现的高频问题也能反过来提示 Wiki 缺哪一页。

## 二、先把“来源”拆开，别把所有资料当纯文本

多源知识系统的第一步不是切块，而是识别每类来源能证明什么。不同来源包含的结构、权限和时效都不一样，不能统一转成纯文本后就当作同一种材料。

### 文档源：保留层级、作者与生效范围

需求文档、设计文档、操作手册和事故复盘至少要保留：

- 标题和章节层级；
- 作者、负责人和更新时间；
- 文档状态，例如草稿、已生效、已废弃；
- 所属产品、系统和适用版本；
- 原始链接与访问权限；
- 文档之间的引用关系。

如果只保留正文，一段三年前的草案和一份昨天生效的规范在检索时可能具有同样权重。模型能找到两段文字，却不知道哪段仍然有效。

### 代码源：保留符号、依赖与版本

代码不能只按固定字数切块。类、函数、接口、调用、继承、配置引用和测试覆盖本身就是结构。代码解析器需要抽取：

- 仓库、模块、目录和文件；
- 类、函数、接口、配置项和数据结构；
- 调用、依赖、实现、读写与发布订阅关系；
- 测试、提交版本和变更历史。

这也是代码 Wiki 看起来更成熟的原因：Git 天然提供版本，语法树和符号系统又给了稳定结构。但这只说明代码是一类优质输入，不代表 Wiki 只能处理代码。

### 结构化来源：保留字段语义，不要先写成散文

数据库 schema、OpenAPI、配置中心、工单和资产目录已经有字段与关系。系统应该直接读取这些结构，而不是先转成一大段自然语言再让模型猜回来。

例如退款状态表中的 `status`、`updated_at` 和 `channel_refund_no` 是字段事实；“退款完成后不可重新发起”则是业务约束。前者可以由 schema 或代码确认，后者可能来自产品规范和实现共同证明。两者需要进入不同类型的知识对象。

### 会话和会议：默认只能当线索

聊天记录和会议纪要能补充背景，却经常缺少明确的生效状态。除非有负责人确认或后续正式文档，否则更稳妥的做法是把它们标为“候选结论”或“决策线索”，不要直接当成当前规则。

这条边界很重要。自动化系统最危险的情况不是找不到知识，而是把一句讨论中的建议写成了正式规定。

## 三、统一的不是文本格式，而是知识模型

各类来源经过解析后，需要进入一套共同的知识模型。这里的模型不是大模型参数，而是一组可查询的数据结构。

一个实用的最小模型可以包含六类对象：

```text
Source       原始来源：文档、代码、表结构、工单
Entity       实体：系统、模块、接口、业务概念、状态
Claim        可验证结论：退款成功后订单进入 REFUNDED
Relation     关系：调用、依赖、属于、影响、替代
Evidence     证据：具体章节、代码符号、字段或记录
Version      生效时间、来源版本、过期状态与权限
```

页面不是事实源，它只是这些对象的一种展示。把结论和页面直接绑死，页面一改就很难判断其他页面是否也要改；把结论独立出来，一条 Claim 发生变化，系统就能找到所有引用它的页面。

### 每条结论至少回答四个问题

一条可用的结论需要知道：

1. **说了什么**：例如“退款完成以渠道回执和本地状态都成功为准”；
2. **证据在哪**：产品规范第几节、哪个代码符号、哪张表；
3. **何时有效**：对应哪一版规则、哪个 commit 或哪个发布日期；
4. **谁可以看到**：公开、团队内、特定项目或敏感级别。

还可以增加置信度，但置信度不能代替证据。一个模型给出的 0.95 只是计算结果，不是事实本身。读者真正需要的是可核对的来源。

### 来源冲突必须显式存在

假设 PRD 写着“失败后自动重试三次”，代码却只重试一次。系统不应该擅自把两者揉成“会自动重试”，而要保留冲突：

```text
产品期望：最多重试 3 次
当前实现：最多重试 1 次
状态：待负责人确认
证据：PRD v4.2 §6.1 / RetryPolicy.java@8f31c2
```

冲突本身就是知识。它可能意味着代码缺陷、文档过期，也可能表示灰度规则尚未同步。强行生成一个流畅答案，只会把真正需要处理的问题藏起来。

## 四、从知识模型规划页面，而不是照着来源目录抄

最省事的生成方式，是每个文件写一份摘要。它通常也最不好用。

读者关心的是“新用户优惠怎样计算”“退款失败后如何恢复”，不是“`RefundService.java` 写了什么”。一个业务问题可能横跨 PRD、接口、三个模块和两张表；按文件生成，读者仍然要自己拼接。

页面规划应从读者任务出发。常见页面类型包括：

- **概览页**：这个领域有哪些系统、角色和核心概念；
- **流程页**：一次操作从入口到结果怎样流动；
- **规则页**：一条业务约束在什么条件下成立；
- **接口页**：上下游怎样交互，失败和重试边界在哪；
- **决策页**：为什么采用当前方案，替代方案为何没选；
- **排障页**：看到某个现象后先查什么，如何恢复。

代码仓库也可以生成模块页和符号页，但不应让文件树控制整个 Wiki 的目录。

### 页面要有稳定入口

入口页至少告诉读者三件事：这个知识空间覆盖什么、从哪里开始读、遇到不同任务应该去哪一页。页面之间还要有明确的下钻关系，例如：

```text
支付域总览
  ├─ 收款流程
  │    ├─ 渠道路由规则
  │    └─ 支付结果确认
  ├─ 退款流程
  │    ├─ 退款状态机
  │    └─ 失败补偿
  └─ 关键决策
       └─ 为什么以本地流水作为恢复基准
```

一页最好回答一个主要问题。太粗会塞满无关信息，太细会产生大量必须来回跳转的小页面。

## 五、页面生成的核心是证据包

页面规划完成后，系统要为每页组装证据包。证据包不是“向量检索返回的前十段”，而是围绕当前页面问题组织的一组材料。

以“退款失败如何恢复”为例，证据包可能包含：

- PRD 中对用户承诺的退款时限；
- OpenAPI 中渠道查询和退款接口；
- 退款状态机代码与重试配置；
- 本地退款流水表字段；
- 一次历史事故中的失败路径；
- 上述材料的版本、权限和引用锚点。

生成器只能基于证据包写作。关键结论没有证据就不发布，来源相互冲突就显式标记，证据不足时写“当前资料无法确认”，而不是靠模型补齐。

### 不同来源需要不同锚点

文档适合引用章节、段落和原始链接；代码适合引用仓库、commit、文件和符号；结构化数据适合引用 schema 版本、表和字段；工单适合引用单号和状态。

行号不是稳定锚点。代码插入几行，旧链接就可能偏移。更稳妥的是优先绑定符号和提交版本，行号只用来帮助阅读。

### 先写局部页，再汇总总览

总览页需要依赖多个局部结论。合理顺序是先生成规则页、流程页和接口页，校验后再汇总总览。若先让模型凭一大包资料写总览，页面容易完整得像真的，却混入无法定位的推断。

生成结束后还要做机械校验：引用是否存在、页面链接是否断开、同一术语是否统一、同一 Claim 在不同页面中有没有互相矛盾。这些检查不需要大模型自由发挥，规则和图查询往往更可靠。

## 六、一个完整例子：把退款资料编译成知识空间

初始状态如下：

- `退款产品规则 v4.2` 写了用户承诺和渠道差异；
- OpenAPI 描述渠道退款、查询和回调；
- `refund-service` 仓库包含状态机、补偿任务和测试；
- MySQL schema 定义退款流水；
- 两份事故复盘记录过超时与重复退款问题；
- 一份旧版 PRD 仍能被搜索到。

系统按下面流程工作：

```text
接入来源
  ↓ 解析结构、权限与版本
抽取实体、关系、结论与证据
  ↓ 发现“重试次数”存在冲突
把冲突交给负责人确认
  ├─ 确认旧 PRD 已废弃 → 标记失效
  └─ 确认代码少实现两次 → 创建待办，页面保留差异
  ↓
生成退款总览、状态流转、渠道差异、失败恢复页面
  ↓
校验引用、链接、术语与页面间一致性
  ↓
发布给人阅读，同时进入 RAG 索引供 Agent 查询
```

这时读者打开“失败恢复”页面，会先看到正常流程，再看到每个失败点的判断与动作：渠道请求超时后先查渠道结果；渠道已成功而本地未落库时，依据退款流水推进本地状态；无法确认时进入人工队列。每个动作都能回到接口、状态机和事故复盘。

后来代码把重试从一次改成三次。增量更新不需要重写整站：

1. Git diff 找到变化的配置和调用者；
2. 受影响的 Claim 被标记为待重算；
3. “失败恢复”和“渠道差异”两页进入更新队列；
4. 重新组装证据并生成变化段落；
5. 引用校验通过后发布新版本；
6. 旧版本仍可追溯，但默认不再参与当前问答。

这才是“可维护”的含义。不是每次全量重写，而是知道什么变了、影响哪些结论、哪些页面需要更新。

## 七、更新、删除和权限比第一次生成更难

演示通常只展示第一次生成，生产系统真正困难的是第二次以后。

### 增量更新要沿关系传播

来源变化后，不能只更新同名页面。一个接口字段变化，可能影响接口页、流程页、排障页和总览页。系统需要从变化的 Source 或 Entity 沿着 Claim 和页面引用关系传播，得到受影响范围。

传播也要有限制。若任何底层变化都重建整个 Wiki，成本和页面漂移都会失控。可以按关系类型、页面重要度和风险等级设置更新边界，高风险页面要求人工确认，低风险描述允许自动发布。

### 删除不是从索引里消失就结束

来源被删除或权限收回后，要同时处理：

- 底层证据是否仍可访问；
- 依赖该证据的 Claim 是否还有其他来源；
- 页面应删除、降级为不确定，还是保留历史版本；
- RAG 索引、缓存和搜索摘要是否同步清理。

否则页面正文已经删了，旧片段仍可能从向量库中被检索出来。

### 权限必须贯穿整条链路

访问控制不能只做在网页入口。解析、索引、生成、缓存和检索都要携带权限标签。一个用户无权访问事故复盘时，系统既不能向他展示原文，也不能通过自动摘要间接泄露其中内容。

跨来源页面尤其要小心。页面由五份材料生成，而读者只对其中四份有权限时，最稳妥的方案通常是生成权限隔离的不同视图，或者不展示依赖敏感证据的结论。

## 八、怎样判断 Wiki 值不值得信

“页面看起来不错”不是评测标准。至少应分别测四件事：

### 事实正确

随机抽取关键结论，检查证据是否真的支持它。不是检查文字是否通顺，而是检查有没有把推测写成事实、把旧规则写成现状。

### 覆盖任务

拿真实任务检验：新人能否找到系统入口，开发能否判断改动范围，值班同学能否按页面定位失败点。Wiki 页数很多，不代表覆盖了读者最关心的问题。

### 更新及时

统计来源变化到页面完成更新的时间，以及过期页面被用户看到的比例。一个很准但两个月才更新一次的 Wiki，不适合解释快速变化的系统。

### 引用可用

引用能否打开，是否指向正确版本，读者是否有权访问，删除来源后是否及时失效。引用只是装饰时，系统仍然不可审计。

还可以观察搜索后继续点击率、页面被 Agent 使用后的任务成功率，以及“页面无答案”是否比错误自信更常见。好的 Wiki 应该敢于承认资料不足。

## 九、它与 RAG、Skills、Repo Map、FastCode 怎样分工

LLM Wiki 的核心产物是**稳定页面**。RAG 的核心产物是**当前问题的证据片段**；Skill 保存的是**做事规则与验收方法**；Repo Map 提供**紧凑的仓库结构导航**；FastCode 围绕当前编码任务进行**动态代码侦察和上下文组装**。

它们不是五个互相替代的知识库产品。一个团队完全可以让它们共享底层解析结果：

- 文档解析、代码符号和权限元数据进入共同事实层；
- LLM Wiki 从事实层生成可阅读页面；
- Wiki 页面和原始证据一起进入 RAG；
- Repo Map 给出仓库骨架；
- FastCode 沿骨架为当前任务选择代码；
- Skill 告诉 Agent 本项目必须遵守哪些规则、怎样验证完成。

如果只想回答几类明确问题，先做 RAG 通常更轻；如果 Agent 经常违反稳定业务规则，应先补 Skill；如果主要痛点是大仓库定位，Repo Map 或 FastCode 更直接；如果新人、跨团队协作和 Agent 都在反复重建整体认识，LLM Wiki 才开始显示价值。

更完整的横向比较见[《代码知识工程怎么选：RAG、Skills、Repo Map、FastCode 与 LLM Wiki》](/posts/code-knowledge-engineering-selection/)。

## 十、一套可以落地的最小版本

不要从“接入全公司所有资料”开始。选一个边界清楚、变化适中、确实有人反复理解的领域，先做四类页面：概览、核心流程、关键规则、排障入口。

第一版可以按以下顺序：

1. 接入一类权威文档和一个核心代码仓库；
2. 为来源补齐版本、负责人、权限和原始链接；
3. 抽取系统、模块、接口、业务规则和证据关系；
4. 人工确认十到二十条最关键的 Claim；
5. 围绕真实读者问题规划页面；
6. 生成页面并强制关键结论带引用；
7. 建立变更检测和受影响页面队列；
8. 用真实任务评测，再决定是否扩来源。

这套最小版本不需要先做复杂知识图谱。关系可以存在普通数据库中，页面也可以是 Markdown。先证明“少数页面真的减少了重复理解”，再增加自动规划、图检索和多权限视图。

### 哪些情况暂时不值得做

以下情况做 LLM Wiki 往往投入大于收益：

- 项目很小，核心成员随时可以当面解释；
- 来源缺少负责人，错误资料没人确认；
- 系统变化极快，页面还没审核就过期；
- 主要需求只是精确查询若干文档片段；
- 团队没有维护更新链路的预算。

此时可以先做搜索、RAG 或一份手写入口文档。Wiki 不是知识工程成熟度的必经等级，它只是针对“整体理解被反复重建”这一类成本的解法。

## 十一、我现在对 LLM Wiki 的理解

LLM Wiki 最容易被做成一个漂亮的文档生成演示：输入仓库，几分钟后出现目录、说明和架构图。但页面生成只是最后一步。

真正的系统从来源治理开始。它要知道每份材料是什么、谁负责、何时生效、谁能访问；随后把不同来源里的实体、关系和结论统一起来；页面生成时保留证据，来源变化后再沿关系准确更新。

代码仓库仍然是其中很重要的一类输入。它结构明确、版本清楚，也最能反映真实执行。但一套能帮助团队理解业务的 Wiki，不能停在代码里。产品规则解释承诺，接口和数据解释边界，代码解释执行，复盘解释失败，决策记录解释为什么。把这些材料放进同一套可追溯的知识结构，才是 LLM Wiki 更完整的形态。
