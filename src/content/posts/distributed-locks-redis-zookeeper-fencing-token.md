商品 S42 的缓存过期了。此时三个请求分别落到三台应用机器，每台机器都发现缓存不存在，于是同时查询数据库、计算商品详情、写回缓存。

如果重建很昂贵，我们希望三台机器先商量一下：这一轮先让一个实例来做，其他实例等结果或者返回可接受的旧数据。分布式锁就是实现这种多进程协调的一种办法。

先讲这个场景，是因为它能够把锁的作用和边界分清楚：锁用来减少并发重建，偶尔重复重建可以接受。如果业务是扣款或抢最后一件库存，还要保护真正的账务、库存记录，不能照搬缓存重建的安全要求。

本文主要讲 Redis 锁：怎样抢到，怎样释放，持有者崩溃时怎么办，任务超过过期时间又怎么办。ZooKeeper 和 Fencing Token 放在后面，用来补充 Redis 锁尚未解决的问题。

## 一、为什么本地锁不够用，分布式锁在协调谁

在一台应用机器内，两个线程同时重建 S42 的缓存，可以用同一个本地锁，让它们轮流执行。Java 的 synchronized、ReentrantLock 都能处理这种线程之间的协调。

但应用部署在三台机器上，每个进程都有自己的内存和锁对象。A 机器拿到了自己的本地锁，B 机器完全不知道这件事，仍然能拿到 B 的本地锁。两个请求就同时开始重建。

哪怕三台机器上的锁变量名字相同，也不会自动变成同一把锁。要协调它们，需要一个大家共同访问的地方，记录“当前谁有资格处理 S42”。

如果使用 Redis，可以约定一个键：lock:product:S42。A、B、C 都先尝试在这个键上登记自己，登记成功的实例进入重建逻辑，其他实例不能把失败当作成功，继续做同一件事。

这个规则只能约束遵守它的代码。如果另一个服务直接写商品缓存，从来不检查锁，Redis 不会主动拦住它。锁的位置和所有参与者是否遵守同一协议，需要一起看。

锁的粒度也要与资源对应。S42 和 S43 的缓存通常可以并行重建，所以按商品分别加锁。把整个商品服务都锁住，会让无关商品也排队；为每次请求生成不同锁名，又会让大家根本没抢同一把锁。

拿不到锁以后怎么做，取决于业务。缓存重建可以短暂等待，再读缓存；能接受旧数据时也可以返回旧值。不能一直占着请求线程等待，更不能默认“没拿到也没关系”然后同样开始重建。

## 二、最基础的 Redis 加锁，为什么不能先查再写

一个直观写法是先 GET 锁键，发现不存在，再 SET 自己的名字。问题与“先查订单不存在，再插入订单”相似：两次操作之间存在空隙。

A 查询时锁不存在，B 查询时也不存在。随后 A 写入，B 又写入，两边都认为自己抢到了锁。这段逻辑无法把并发竞争变成只有一个成功。

需要让 Redis 在执行写入时检查：只有键不存在，才允许创建。SET 的 NX 选项就是这个条件。同时用 PX 指定存活时间，单位是毫秒：

```text
SET lock:product:S42 owner-A-7f92 NX PX 30000
```

这条命令表达的是：如果键不存在，就写入本次持有者标识，并设置三十秒过期时间；如果键已经存在，就不覆盖。

在处理这一条命令的 Redis 实例上，检查与写入是一个原子操作。A 得到成功结果后，B 再执行同样的条件写入，会发现键存在，无法抢到。不能把没有抢到与通信失败混在一起：明确返回未成功，才是正常竞争失败。[Redis SET 命令说明](https://redis.io/docs/latest/commands/set/)

过期时间为什么要同时写进去？假设先用 SET NX 成功，再另发一条设置过期的命令。A 在两条命令之间崩溃，锁就可能没有过期时间，其他实例一直无法接手。

把“创建锁”和“指定过期时间”放进同一条命令，避免了这个窗口。三十秒只是本文的例子，不是所有任务都应该设置三十秒。选择多久需要看重建耗时，以及持有者消失后允许其他实例等多久。

![Redis 锁协调缓存重建：抢到才处理，没抢到短暂等待后重新读取](/images/posts/redis-lock-acquire-release-flow.svg)

还有一个需要加的检查：拿到锁以后，再读一次缓存。A 重建完成并释放锁后，B 才抢到，缓存可能已经存在；如果 B 不检查就重建，虽然没有并发执行，仍然重复做了一轮工作。

锁解决“能不能同时进入”，缓存二次检查解决“轮到我时还需不需要做”。两者配合，才符合这个场景的目标。

## 三、过期时间为什么必要，又为什么不能保证任务停下来

假设 A 抢到锁后，进程崩溃了，释放锁的代码根本不会执行。没有过期时间，B 可能永远等不到机会。

设置过期时间后，Redis 会让这个键到期失效，其他实例就能再次尝试加锁。这种“只能在一段有效期内持有”的机制，也叫租约。它给持有资格设了期限。

但 Redis 只能让键失效，不能让 A 的业务线程停下来。A 可能没有崩溃，只是数据库查询太慢、进程长时间暂停，或者网络断了一会儿。等 A 恢复运行时，锁已经过期了。

此时 B 可以拿到新锁，开始重建。A 的代码也从暂停位置继续执行，于是出现两个实例同时干活。Redis 没有违反“当前键只能有一个持有者”的规则，旧线程却已经不再受这份有效期约束。

在缓存重建里，这可能只是多查一次数据库，也可能出现旧结果晚写回、覆盖新结果。具体能接受哪种情况，要看缓存数据是什么、更新路径如何设计。

在库存扣减或扣款里，后果更重。不能把“设置了三十秒过期”解释成“业务一定只执行一次”。过期是为了让其他实例能够恢复接手，也因此会产生旧任务还没停、新任务已经开始的可能。

把过期时间设置得特别长，只是减少正常情况下提前过期的概率，同时延长崩溃后的等待。设置得特别短，又容易让正常任务失去锁。有限的时间参数无法覆盖任意长暂停，需要后面讲的续期或资源侧保护。

## 四、释放锁为什么一定要检查本次持有者

如果 A 完成重建后直接 DEL 锁键，看起来很合理，但考虑下面这个时间顺序：

A 抢到锁，持有者标识为 owner-A-7f92。A 处理太久，锁到期。B 抢到同一个键，值变成 owner-B-3c18。随后 A 完成工作，执行 DEL，把 B 的锁删掉了。

这时 C 也可能抢到锁，B 和 C 又开始同时工作。A 本来只想释放自己的资格，却误删了别人的资格。

所以锁值不能只放“已上锁”这样一个固定值。需要为每次成功获取生成一个足够难碰撞的持有者标识，并在释放时检查：当前键的值是不是我这一次持有的值。

为什么强调“这一次”？同一进程可能先后拿锁。如果只使用固定机器名或线程名，迟到的旧释放动作可能把同一进程后来拿到的新锁删掉。每次获取要能被区分。

但“先 GET 检查相等，再 DEL”也不安全。A 检查时值确实属于自己，在两条命令之间锁过期、B 加锁，A 随后的 DEL 仍然会删掉 B。

检查与删除需要作为一个不可被其他客户端命令插入的操作。可以把两步放进 Redis 执行的短 Lua 脚本：

```lua
-- KEYS[1]：锁键
-- ARGV[1]：本次获取保存的持有者标识
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

Redis 执行脚本期间，不会穿插其他客户端对这个键的命令，所以能够把比较与删除放在一起。[Redis Lua 脚本执行说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

返回 1 表示删掉了自己仍持有的锁；返回 0 表示键不存在或当前属于别人，不能再删除。结果为 0 不代表业务一定没执行，只表示释放时不再拥有这把锁。

![旧持有者恢复后，比较持有者标识，避免删除新持有者的锁](/images/posts/redis-lock-expired-owner-release.svg)

注意，这段脚本只修复误删锁的问题。它没有撤销 A 刚刚写回的缓存，也没有阻止 A 在锁过期后继续操作数据库。释放安全与业务写入安全，要分别处理。

释放通常放进 finally，确保正常返回和抛异常时都尝试执行。finally 无法覆盖机器断电、进程强制退出，所以过期时间仍然需要存在；两种机制解决的是不同的退出路径。

## 五、任务可能超过有效期，续期怎样工作

固定三十秒的锁，在任务耗时不好预测时比较难用。可以让持有者定期向 Redis 申请延长有效期：任务仍然在运行、仍然是自己持有，就再续一段时间。

续期也要检查持有者标识。如果锁已经到期并被 B 拿走，A 不能对同名键直接延长时间，否则延长的是 B 的锁。

一个简化脚本如下：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0
```

例如，给锁设置三十秒有效期，安排后台每隔一段时间续到三十秒，留出网络与调度的余量。这里描述机制，不要求所有库都使用相同的周期。

正常执行期间，续期把到期时间向后推。持有者进程崩溃后，后台续期也停止，最后一次续期留下的有效期耗尽，其他实例就能接手。

这种自动续期常被称为看门狗。名字听起来像一个安全开关，实际仍然是后台任务定期向 Redis 发请求。它可能被进程暂停、线程调度或网络故障耽误。

如果续期没有在期限内完成，锁仍然会过期。网络请求超时，也可能让客户端无法确认续期是否成功。此时不能一直假定“看门狗开着，所以我必然还持有锁”。

业务应当把失去持有资格当作异常路径：尽量停止尚未开始的步骤，不再发起新的受保护操作，并记录失去锁的原因。已经发出的外部操作，不能仅靠停止本地线程撤回。

还有一个时间空隙需要理解。A 检查自己持有锁，随后被暂停；等它恢复时，锁已经过期。之前的检查结果不能永久有效。因此“每次写入前查一下锁”能减少风险，却无法单独提供严格的过期写入隔离。

对于允许偶尔重复计算的缓存重建，续期加上合理的超时可能已经满足需求。对于不能接受旧任务写入的资源，就要让资源本身检查写入资格或业务条件，不能只依赖续期成功率。

## 六、Java 里用 Redisson，需要读懂哪些参数

生产代码一般会选用成熟的客户端库，避免每个项目重复编写加锁、等待、持有者检查和续期逻辑。Redisson 的普通 RLock 是 Java 里常见的一种选择。

需要先分清两个时间：最多等多久才放弃获取，以及获取以后多久自动过期。它们分别影响等待者与持有者。

```java
RLock lock = redisson.getLock("lock:product:S42");

// 最多等待 1 秒；成功获取后，固定持有期限为 30 秒
boolean acquired = lock.tryLock(1, 30, TimeUnit.SECONDS);
```

这两个数字都使用最后一个参数指定的单位。若写成 tryLock(200, 30, TimeUnit.MILLISECONDS)，意思是最多等二百毫秒，持有期限只有三十毫秒，不是三十秒。参数看错会让正常任务很快失去锁。

显式指定固定持有期限时，不要同时假定看门狗会无限续期。如果希望使用看门狗续期，使用不指定固定 leaseTime 的获取方式，并检查项目实际采用的版本与配置。

下面用这种方式表达缓存重建的主要控制流。readProductCache、loadFromDatabase 等是业务方法，示例不包含完整的缓存降级和异常策略：

```java
RLock lock = redisson.getLock("lock:product:" + productId);
boolean acquired = lock.tryLock(1, TimeUnit.SECONDS);

if (!acquired) {
    // 不进入重建；再次读取缓存，或执行约定的降级
    return readCacheOrFallback(productId);
}

try {
    Product cached = readProductCache(productId);
    if (cached != null) {
        return cached;
    }

    Product product = loadFromDatabase(productId);
    writeProductCache(productId, product);
    return product;
} finally {
    try {
        lock.unlock();
    } catch (IllegalMonitorStateException lostOwnership) {
        // 本线程已经不再持有锁，记录异常；不能强行删除别人的锁
        recordLostLock(productId, lostOwnership);
    }
}
```

这里 tryLock 可能抛出 InterruptedException，外层方法需要声明它，或者按应用的取消规则处理并保留中断信号。不能捕获所有异常后继续执行重建逻辑。

普通 RLock 支持同一持有线程重复获取，也就是可重入。例如外层方法拿到锁后，内层方法再次获取同一把锁，库会记录重入次数；释放次数与获取次数相匹配，最后才真正释放。前面的简单 SET NX 字符串锁没有自动提供这种能力。

Redisson 的锁结构也不是直接照搬本文的 owner 字符串。库要维护线程持有关系、重入计数等信息，所以不要拿前面的 GET/DEL 脚本去操作 Redisson 创建的锁键。

使用普通同步调用时，应由持有线程释放锁。不要随意把解锁丢给另一个线程；异步接口需要遵循对应的持有者参数约定。单看“业务执行完成”不能证明当前线程仍有解锁资格。

Redisson 文档给出的看门狗默认超时是三十秒，可通过配置调整。项目应以实际版本为准，明确自己使用固定期限还是自动续期。[Redisson 锁与同步器说明](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)

finally 里的异常记录也有边界。它只能告诉我们释放时持有资格丢失，不能证明此前写回的缓存安全。如果场景不允许失去锁后继续写，要在真正的数据写入位置加保护。释放时才发现问题，通常已经太晚。

另外，Redis 通信错误可能出现在获取、续期或释放任一步。获取抛异常时不能进入临界区；释放遇到网络问题时要记录并依赖后续确认或到期恢复，不能改成无条件删除来“补救”。

## 七、Redis 故障切换时，为什么可能同时出现两个持有者

前面主要分析同一个 Redis 实例正常运行时的竞争。实际部署可能有主节点和副本，主节点故障后由副本接管。

假设 A 在主节点加锁成功，主节点向 A 返回成功。但这条锁记录还没复制到副本，主节点就崩溃了。副本接管以后，看不到这把锁。

B 向新主节点加锁，新主发现键不存在，于是也返回成功。A 并不知道自己的锁记录在切换中消失，继续干活；B 也开始干活。

这个问题来自锁记录的复制与确认边界。NX 保证的是处理该命令时的条件写入，并没有自动承诺“任何故障切换后，这份记录都不会丢”。Redis 官方分布式锁说明也明确讨论了异步复制下的这个窗口。[Redis 分布式锁与故障切换](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

有些客户端会等待副本同步、检查同步数量。这类措施能降低特定窗口的风险，但需要结合客户端版本、Redis 拓扑和故障条件判断，不能概括成“用了某个库，任何故障下都不会双持有”。

Redis 的内存淘汰策略也要注意。如果锁键像普通缓存一样被提前淘汰，等待者就可能看到键不存在。锁所在的实例是否允许淘汰、内存不足时如何处理，应当纳入运维配置。不能把协调记录与可随时丢弃的缓存完全同等对待。

为什么有时依然会用 Redis 锁？因为业务的损失可能主要是偶尔多做一次缓存重建，而 Redis 已经在系统里，访问成本也比较低。这个选择需要说明“允许什么程度的重复”，而不是宣称没有重复可能。

如果重复操作会直接破坏资金或库存事实，就应把数据库约束、条件更新或更严格的协调机制一起设计。业务最终防线不能只是一把在故障下可能丢失的锁。

Redlock 是另一种尝试，要求向多个独立 Redis 节点获取锁，并结合成功数量与耗时判断有效期。它不是“Redis Cluster 节点多，所以自然就是 Redlock”。这涉及额外的时间与故障假设，先理解单 Redis 锁的边界，再按需要单独研究，不在这里把它展开成另一个主线。

## 八、锁住代码以后，为什么还需要数据库保护

现在换一个例子：库存只剩一件，A 和 B 都想卖出。最重要的要求是，可用库存不能减成负数。

即使外面有分布式锁，也应该让数据库执行带条件的原子更新：

```sql
UPDATE inventory
SET available = available - 1
WHERE sku_id = 'S42' AND available >= 1;
```

检查实际更新行数。如果成功更新一行，说明这次扣减满足条件；更新零行，需要区分库存不足或商品不存在等情况。不能先在 Java 里读到一件，再无条件把库存改成零，让并发请求都认为自己扣减成功。

这条语句可以挡住超卖，但不能阻止同一订单重复扣减。如果库存本来有十件，同一个订单扣两次，仍然满足 available >= 1。还需要以订单编号建立唯一的预占记录，并与扣库存放进一个本地事务。

可以看到，锁、条件更新和幂等约束关注的问题不同。锁让遵守协议的参与者尽量轮流进入；条件更新保护库存数值；订单编号约束防止同一订单重复扣减。某些业务只靠后两者就够了，不一定还要额外加 Redis 锁。

锁也不会把几个服务的操作自动变成一个事务。订单服务拿着锁，先扣库存，再扣款，如果扣款失败，库存仍然需要释放。锁并没有替你完成回滚或补偿。

回到缓存重建，锁同样不能保证读到的是数据库最新版本。A 拿到锁以后，商品可能由另一条业务路径修改；A 最后写回一个较早的版本。若不能接受旧数据覆盖新数据，需要给缓存写入设计版本检查，或者调整更新流程。

版本检查应在资源端原子完成。例如缓存已有版本 12，写入者带版本 11，资源拒绝覆盖。但如果缓存里的版本记录被删除，这种“与当前缓存比较”的保护也可能失效，不能宣称它解决所有数据新旧问题。

分布式锁能帮我们减少并发冲突，实际数据的合法条件仍然要放在最接近数据的位置。这样锁失效时，错误也不至于直接进入业务记录。

## 九、ZooKeeper 与 Fencing Token 补上什么

到这里，Redis 锁的主线已经讲完。最后补充两个经常与它一起被提到的机制，分别回答不同的问题。

### 先看树上的节点，再看锁

ZooKeeper 可以让多个进程共同读写一棵小型数据树。路径从根节点 / 开始，每一个数据节点叫 znode。例如，给商品 S42 建一个锁目录：

```text
/
└── locks
    └── product-S42                  ← 这把锁的固定父节点
        ├── contender-0000000001     ← A 的排队节点
        ├── contender-0000000002     ← B 的排队节点
        └── contender-0000000003     ← C 的排队节点
```

这里的“节点”是数据树上的条目，不是一台服务器。树形路径有点像目录，但 znode 还可以保存少量数据，比如参与者信息。ZooKeeper 适合保存协调记录，不适合存放商品详情和大量业务数据。[ZooKeeper 数据模型](https://zookeeper.apache.org/doc/r3.8.4/zookeeperOver.html#Data+model+and+the+hierarchical+namespace)

### 临时与顺序，是两个可以组合的属性

先看节点活多久。持久节点在创建它的客户端断开后仍然存在，除非被显式删除。上面的 /locks/product-S42 可以用持久节点，作为大家共同排队的固定位置。

临时节点则与创建者的会话绑定。客户端与 ZooKeeper 建立会话，通过通信保持会话有效；会话关闭或被服务端判定过期后，对应临时节点会被删除。临时节点不能再带子节点。

短暂断网不等于会话立刻过期。客户端可能重新连接并继续原会话，所以临时节点不是“TCP 连接一断就马上消失”。

再看节点怎样命名。创建顺序节点时，客户端提供路径前缀，ZooKeeper 在后面添加递增编号，并返回实际创建的路径。例如，A 创建 contender-，得到 contender-0000000001；B 的下一次创建得到 contender-0000000002。

编号由 ZooKeeper 生成，在同一个父节点范围内建立顺序；不是客户端读取当前最大值再自己加一，也不是所有目录共用的一个无限编号。编号反映服务端接受创建的顺序，不保证等于用户按按钮的先后。

因此，“临时顺序节点”就是同时选择两种属性：会话失效后清理节点，创建时自动附加编号。普通持久、普通临时、持久顺序、临时顺序都可以组合使用。这把锁用持久父节点和临时顺序子节点。[临时与顺序节点说明](https://zookeeper.apache.org/doc/r3.8.4/zookeeperProgrammers.html#Ephemeral+Nodes)

### A、B、C 怎样排队拿锁

A、B、C 都在同一个父路径下创建自己的临时顺序节点，保存返回的完整路径，再读取子节点列表并按编号排序。getChildren 返回的列表不能被默认当成已经排好序。

A 的编号最小，于是进入缓存重建。B 关注紧挨着它的前一个节点 A；C 关注 B。这个关注机制叫 Watch：客户端请求“这个节点发生指定变化时通知我”，等待者不用一直循环查询。

A 完成以后删除自己的节点，B 收到前驱消失的通知。B 重新读取并排序，确认自己仍在队列里、已经最小，才进入业务。C 此时继续等待 B。A 若崩溃且会话最终过期，它的节点被清理，也能触发 B 重新检查。

通知本身不是“你已拿到锁”的凭证。排序检查与注册 Watch 之间，前驱可能已经删除；若带 Watch 的 exists 检查发现节点不存在，应立即重新检查队列，不能继续等一个已经消失的节点。使用普通一次性 Watch 时，通知触发后若仍需等待，要重新注册。

只关注前驱，可以让一次释放主要唤醒下一位，避免所有等待者同时抢着重查。但客户端等待超时或取消时，也要删除自己的排队节点，不能留下已经放弃的排队者占住位置。

创建请求超时还有结果未知的问题：服务端可能已经创建节点，客户端却没拿到路径。实际实现可以在节点名前缀中携带本次申请的唯一标识，重连后查找原节点，避免盲目重复创建。这也是使用成熟锁库的原因。[ZooKeeper 锁配方](https://zookeeper.apache.org/doc/r3.8.4/recipes.html#sc_recipes_Locks)

### 多台 ZooKeeper 服务器怎样维护这份顺序

这棵树不是每台应用各自保存的独立数据。ZooKeeper 集群会复制它的状态；修改请求交给负责排序的领导节点，由它安排顺序，并经过多数投票节点确认后提交。

例如三个投票节点中，至少两个需要能够参与确认。只剩一台时，它不能自作主张继续确认新的加锁请求。这份复制与恢复规则让多个客户端共享同一条已提交的变化顺序，而不是各台机器各自分配一套排队编号。[ZooKeeper 写请求与复制](https://zookeeper.apache.org/doc/r3.8.4/zookeeperInternals.html#Atomic+Broadcast)

这里先理解到“共同数据树、会话清理、自动编号、变化通知”即可。完整选主和恢复协议不是这篇锁文章的重点，也不能从“多数确认”推导普通读取永远是最新值。

ZooKeeper 仍然不能强制杀掉旧客户端的业务线程。客户端长时间暂停，会话已经过期，B 已接手；A 恢复时仍可能继续业务。连接状态不明时应暂停新的受保护操作，会话过期后更不能沿用原持有资格。这就需要下面的资源端检查。

### 递增资格编号怎样挡住旧写入

这就引出 Fencing Token，可以理解成“资源端用来挡住旧持有者的递增资格编号”。随机 owner 标识只用来判断“是不是我这一次持有”，不能判断谁更新；递增编号则能区分哪次持有资格更晚。

假设 A 获得编号 41，后来失去锁；B 获得编号 42。B 向资源写入时携带 42，资源在接受写入的同一个原子步骤里记住“已经接受到 42”。

A 迟到的写入带着 41。资源发现 41 比已接受的 42 小，就拒绝它。这样，新持有者的写入已经生效后，旧持有者不能再覆盖它。

关键在资源端检查，而不是把编号打印进日志。数据库、存储服务或其他接收写入的组件需要维护这个上限，并与写入一起原子检查；所有写入路径都要遵守。资源不支持这类检查，应用自己生成一个编号也不会自动获得保护。

还要注意顺序：如果 A 的 41 先到，资源尚未看到 42，只靠“最高已见编号”不一定能拒绝 41。它不意味着资源随时知道锁是否到期。若要让 B 接手时立刻排除旧写入，需要让资源确认新的编号，并把这个确认纳入接手流程。

Redisson 也提供带递增令牌的锁接口，但普通 RLock 不会让所有外部资源自动检查令牌。是否需要使用这类机制，要看能否通过现有数据库条件、版本号和唯一约束保护业务。[Redisson Fenced Lock](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/#fenced-lock)

它们不是三种并列的“锁产品”：Redis 和 ZooKeeper 负责协调资格，Fencing Token 需要被写入的资源配合，阻止较旧资格的操作。理解这个分工，比记住三个名称更重要。

对于本文的 S42 缓存重建，可以先采用 Redis 锁、有限等待、持有者校验释放和适当续期，并明确偶尔重复重建的可接受范围。对于资金、库存或严格禁止旧写入的业务，再把保护要求落实到真实的数据操作上。选型应当从业务允许的失败结果出发，而不是看到“分布式”就先加一把锁。
