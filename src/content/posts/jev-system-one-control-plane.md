一个 Agent 完成任务时，会做大量很小的判断：该调用哪个工具，这条记忆要不要写入，检索是否足够，当前结果能不能通过验收，下一步继续执行还是向用户确认。

我们习惯把这些判断全部交给 LLM。系统把状态写成 Prompt，让模型生成一段文字或 JSON，再解析成程序动作。这个方案通用，却有一处不协调：为了在几个有限选项之间做选择，我们启动了一个擅长生成任意字符串的大模型。

Jev 尝试提供另一种计算原语。它接收非结构化状态和类型化问题，直接返回允许答案上的概率，不生成解释文本。TypeSafe AI 把它称作 System One Model：快、便宜，适合软件内部反复发生的有界决策。这篇文章想回答一个具体问题，就是什么时候可以用这种类型化决策模型替换一次生成式调用，什么时候不能。

证据来自 TypeSafe 的官方介绍，以及三项围绕 Jev 的研究：REFLEX 的选择性控制、Jev-Mem 的 Agentic Memory、以及 Jev 作为评测 Judge 的对比。Pi、DSH 那两篇讲的是运行时怎么搭，这一篇讲的是运行时内部的一种新模型接口。所有实验数字都来自各自论文的设定，不能直接外推到任意业务。

![Jev 在 Agent 中承担高频决策，大模型处理复杂推理与生成](/images/posts/jev-control-plane.svg?v=20261001)

## 先看结论

Jev 的价值不在于"更小更快"，而在于它把一类决策从"生成"改成了"选择"。

| 问题 | 传统 LLM 调用 | Jev |
| --- | --- | --- |
| 输出是什么 | 逐 token 生成的字符串 | 固定答案集上的概率 |
| 会不会生成非法格式 | 需要 schema 约束 | 输出空间在调用前已封闭 |
| 主要成本 | 生成 token | 一次前向分类 |
| 适合什么 | 开放式推理、解释、生成 | 路由、分类、打分、继续或停止 |

它仍然会选错。"不生成自由文本"只保证不会返回答案集之外的字符串，不保证选对。理解这层区别，是判断 Jev 能不能进生产的起点。

后面会先解释为什么"为有界决策启动生成模型"是一种浪费，再讲 Jev 的类型化决策原语、System One 与 System Two 的边界，然后用 REFLEX、Jev-Mem 和评测 Judge 三个场景说明它在真实系统里怎么用、在哪里失效，最后给出一个端到端例子和落地判断。

## 一、为有界决策启动生成模型，问题出在哪

把 Agent 的每个小判断都交给 LLM，最直接的问题是成本结构。一次调用要加载 Prompt、执行前缀、逐 token 生成、再解析。哪怕答案只是三个候选项里的一个，这套流程也照走一遍。

成本只是表层。更深的问题在于"输出空间没有被约束"。模型可能返回 `refund`，也可能返回 `"refund"`、`refund.`、`我建议退款`、或一段带解释的 JSON。JSON mode 能收紧格式，却没有改变"模型在开放词汇表上生成"这个事实。运行时必须准备解析器、容错和重试，才能把输出接回程序。

### 一个具体的重复成本

设想一个客服 Agent。用户每条消息进来，系统都要判断下一步动作：退款、换货、澄清、转人工。假设一天十万条对话，每条平均触发两次这种判断。这就是二十万次调用，而其中绝大多数答案只落在四个选项里。

如果这四个选项在执行前就已知，那么运行时真正需要的是一个"带语义理解能力的四分类器"，而不是一个万能生成器。分类器不需要写句子，只需要给出每个选项的概率和置信度。

### 生成不是免费的抽象

生成式接口的通用性有代价。它把"格式正确"和"语义正确"两件事捆在一次调用里，运行时必须同时处理两者。Jev 把两者拆开：格式正确由输出空间的封闭性保证，语义正确由模型能力与阈值共同保证。

这个拆分改变了工程的落点。运行时的解析器变简单了，但阈值、校准和升级逻辑变得更重。换句话说，Jev 把复杂度从"解析自由文本"转移到"管理有限决策"，后者更容易测量，也更容易做确定性检查。

### 一次判断的真实成本结构

一次有界决策的 LLM 调用，成本不只在生成的 token 上。它还包括：系统提示词和工具定义的前缀、上下文历史的重复加载、输出解析与容错、重试与超时的尾延迟。当同一个决策每天重复几十万次，这些固定成本会被放大。

Jev 改变的正是这部分固定成本。它不需要生成长文本，也不太需要复杂的解析兜底，单次成本和延迟都能显著下降。REFLEX 论文报告的强模型调用减少，就是这种成本结构变化的直接体现。

值得注意的是，成本下降不等于总收益上升。节省的调用必须能覆盖多出来的阈值管理、校准和监控开销，多模型系统才真正划算。这一点后面还会展开。

### 一个对照：同一个决策，两种接口

拿"这条检索结果是否相关"举例。LLM 接口可能是：请判断下面这段检索结果和用户问题是否相关，输出相关或不相关，并说明理由。Jev 接口是：给定用户问题和检索结果，在 `[relevant, irrelevant]` 上返回概率。

LLM 接口多出一个"说明理由"，这段理由不参与后续程序决策，却要花生成成本。Jev 接口没有理由，只有概率，程序直接用它做过滤。两种接口的差别不在能力，而在是否把"解释"当成必需输出。

### 什么时候这种不协调最明显

这种不协调在决策频率高、答案空间小的时候最明显。频率高意味着成本会被放大，答案空间小意味着生成能力大部分被浪费。

反过来，低频、开放的任务即使交给强模型，浪费也不明显。判断是否值得改成类型化决策，先看这两个维度。

## 二、Jev 到底是什么

[TypeSafe AI 对 Jev 的介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)给出一个很准确的描述：unstructured state in, typed probabilistic decisions out。非结构化状态输入，类型化概率决策输出。

假设 Agent 要根据工单内容选择动作，传统 LLM 调用可能长这样：

```text
阅读下面的用户请求，从 refund、replace、clarify 中选择一个动作。
只输出 JSON，不要解释……
```

模型仍然在做自回归生成。JSON mode 能约束输出格式，却没有改变"逐 token 生成字符串"这件事。

Jev 的调用更接近一个带语义理解能力的分类函数：

```ts
const decision = await jev.choose({
  state: ticket,
  question: "下一步应采取什么动作？",
  choices: ["refund", "replace", "clarify"],
});

// {
//   choice: "clarify",
//   probabilities: {
//     refund: 0.08,
//     replace: 0.17,
//     clarify: 0.75
//   }
// }
```

关键在于输出空间在调用前已经确定。软件得到一个类型化选择及其概率，可以直接设置阈值、比较候选或决定是否升级到强模型。

Jev 仍然会出错。"不生成自由文本"只意味着它不会返回类型之外的字符串，不代表它不会选择错误选项。把格式错误和语义错误分开，是理解 Jev 的第一步。

### 它用什么训练出来的

TypeSafe 把 Jev 的训练方法称作 RLCD，即 Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习。官方把它和两种常见的 LLM 训练路线并列比较：RLHF 优化人类偏好，让回答更像人喜欢的文字；RLVR 优化可验证奖励，让答案能被程序判对错；RLCD 优化的是"在有界问题上给出诚实的概率"。

这个区别决定了 Jev 的目标不是写出最讨喜的答案，而是让概率尽量反映真实的不确定性。对一个要接入阈值和升级逻辑的决策层，校准比文采重要得多。

### 名字和定位

TypeSafe 把这类模型称为 System One Model，灵感来自"快思考与慢思考"的划分，命名则来自 William Stanley Jevons。官方借用 Jevons 悖论的直觉：当某种智能的单位成本下降一个数量级，使用量往往增长更多。Jev 的定位就是让"每次判断都调用强模型"这种昂贵做法，变成可以大规模使用的便宜操作。

官方还强调 Jev 是"不能幻觉"的，因为它不做字符串生成。这句话需要准确理解。Jev 不会凭空写出一个不存在的工具名或一段编造的引用，因为它的输出被限制在给定的答案集里。但它可能把相关误判为不相关，把澄清误判为退款。不会幻觉格式，和不会判断错误，是两件事。

### 和 JSON mode、小模型、分类器的区别

Jev 常被归到三个已有概念里，但都不完全一样。

和 JSON mode 的区别在于输出空间。JSON mode 约束的是语法结构，Jev 约束的是答案集合。前者仍可能生成任意字段值，后者只能从给定选项里选。

和小模型的区别在于优化目标。一个通用小模型还是要完成生成任务，它的概率未必校准。Jev 专门为有界决策训练，重点是概率的可靠性，而不是语言能力。

和传统分类器的区别在于输入。传统分类器通常需要结构化特征，Jev 直接吃非结构化状态，例如一段用户消息或一份工单，并返回概率。这让它可以放进原本只接受自然语言的链路。

### 校准到底校准什么

概率校准指的是：当模型说 0.8 时，在大量同类样本里，它是否真的对了大约 80%。一个模型可以很准却校准很差，也可以校准不错但区分度不高。Jev 的目标是让概率可信，因为控制层要用概率做决策。

校准差会直接造成阈值失效。如果模型把 0.5 和 0.9 都混在一起说成高置信，运行时就无法用阈值区分"能自动执行"和"必须升级"。RLCD 针对的就是这个问题，它优化的是概率与实际正确率之间的关系，而不只是答案对错。

### 输出空间怎么定义

Jev 的答案集由调用方在请求时给出，所以它的能力边界由"问题怎么写"决定。同一个状态，写成"选一个动作"和写成"这段内容属于哪一类"是两个不同的决策。

这带来一个设计要点：控制层的决策要拆得足够细。把太多语义塞进一个问题，会让答案集变得模糊；把一个问题拆成两个更清楚的问题，往往能同时提高准确率和可校准性。问题设计本身就是控制层工程的一部分。

### 概率怎么用

得到一个概率分布后，程序可以按几种方式使用它。取最大值是最简单的方式；按阈值过滤是控制层常用的方式；把概率作为权重传给下游是更复杂的方式。

大多数控制场景只需要前两种。取最大值对应"自动执行"，按阈值过滤对应"自动或升级"。理解这一点，就能明白为什么 Jev 强调概率而不是只给一个标签。标签丢失了不确定性，而控制层恰恰需要不确定性来做升级决策。

### Jev 不能做什么

Jev 不能生成解释、不能引用原文、不能做多步推理。它不回答"为什么"，只回答"是哪个、有多大把握"。需要理由、需要引用、需要链式推理的场景，仍然要交给生成模型。

把它放错位置，最常见的错误是让它承担本属于生成模型的职责，例如要求它总结一段对话或解释一个判断。它的接口决定了它只能给出有界决策。

## 三、System One 与 System Two 的边界

命名来自"快思考与慢思考"的区分：

| 层 | 擅长的任务 | 在 Agent 中的例子 |
| --- | --- | --- |
| System One | 高频、有界、可类型化的快速判断 | 路由、分类、打分、继续或停止 |
| System Two | 开放式推理、规划、解释与生成 | 分析故障、编写代码、总结证据 |

这不是一条绝对边界。同一个问题可以写成有界选择，也可以要求开放推理。真正需要判断的是：动作集合是否清楚，决策错误是否可检测，输入是否包含足够信息，以及不确定时能否安全升级。

例如"从三个只读检索工具中选择一个"适合快速控制层。"是否删除生产数据库中的一批记录"即使只有 yes 或 no 两个答案，也不该因为输出空间小就自动执行。决策的风险不会随着选项数量一起缩小。

### 快不等于简单

把决策交给快层，不等于这个决策可以草率处理。恰恰相反，快层的价值在于它值得被认真优化：因为调用量大，哪怕准确率提升一个百分点，绝对收益也很可观；因为结构固定，可以积累带标签数据来校准；因为错误可被监控，可以按动作风险分别设置阈值。

把快层当成"廉价的近似"会浪费它的潜力。它应该是一等公民，有自己的评测集、自己的校准曲线、自己的升级策略，而不是强模型的一个降级替身。

### 什么任务不该写进快层

三类判断不适合交给类型化快层。第一类是答案空间本身开放，例如"总结这段对话"或"这段代码哪里有问题"，选项无法在执行前穷举。第二类是决策依赖大量隐式语境，例如"用户是不是真的想退款"，需要结合多轮对话和业务规则推理。第三类是错误不可回退，例如删除、扣款、对外发送，超时或误判的代价无法承受。

这三类不是永久排除，而是当前不适合自动执行。它们可以由 Jev 做初筛，再把结果交给强模型或人工，而不是让 Jev 直接决定。

### 快层和慢层怎么协作

快层和慢层不是替代关系，而是流水线上的两级。快层处理大量简单样本，把不确定的挑出来；慢层处理被挑出来的困难样本，并把结果作为反馈，用于更新快层的阈值和训练数据。

这个协作模式要求慢层的结果可回收。如果慢层的决策不记录标签，快层就永远学不到"哪些我判断错了"。可回收的反馈是快层持续改进的前提。没有反馈闭环，Jev 只是一个更便宜的分类器，而不是一个会随数据变好的控制层。

### 决策粒度怎么选

粒度太粗，一个决策里塞进多种语义，答案集模糊；粒度太细，决策数量爆炸，反而更贵。合适的粒度是：每个决策只回答一个可清楚陈述的问题。

一个实用的检验方法是，试着给每个选项写一句"选它就意味着什么"。如果两句话互相重叠，说明粒度太粗；如果两个选项几乎不可能同时出现，说明可以考虑合并。

### 快层的能力来自约束

有人会担心，把问题限制成有界选择，会损失模型的智能。实际相反：约束让模型把注意力集中在判别上，而不是同时处理判别和表达。

这类似于人类专家做快速判断：经验丰富的人在熟悉的问题上能迅速给出分类，是因为他不需要重新组织语言。Jev 的设计正是把这种"判别归判别、表达归表达"的分工固定下来。

## 四、REFLEX：让 Jev 管 routine decisions

[REFLEX 论文](https://arxiv.org/abs/2609.26532)把 Jev 放进一个选择性控制架构：

```text
当前状态
   ↓
Jev 返回 choice + confidence
   ├── 高置信且允许自动执行 → 直接采取动作
   └── 低置信 / 需要生成 / 高风险 → Strong LLM
```

论文在冻结的 100 个任务上报告，REFLEX 取得 95% 成功率，同时比只用强模型减少 72.7% 的强模型调用，成功率在 2 个百分点的非劣性边界内。这个结果说明很多工具选择和流程判断确实不需要每次调用最强模型。

更值得关注的是细分结果。论文观察到，替代率在工具选择上达到 99%，完成判断为 77%，检索判断为 56%，澄清判断只有 28%。常规工具路由容易下放，涉及用户授权和信息是否充分的问题更难。

### 门控不依赖下游模型

论文里有一个容易被忽略的细节：这个高置信门不随下游强模型的身份而变化。在同一个固定阈值下，无论后面接的是哪个强模型，Jev 都会把同样 66 个任务判为"可以自主完成"，而且这 66 个任务每次都成功。

剩下的 34 个任务才是强模型真正起作用的地方。不同强模型在这 34 个任务上的表现不同，但 Jev 的门控判断保持一致。这说明门控学的是"任务本身适不适合下放"，而不是"去模仿某个特定强模型"。

这个性质对工程很有价值。它意味着升级策略可以和模型选择解耦：先判断任务该不该升级，再决定升级到哪个模型。

### 实验是怎么设计的

REFLEX 的实验分两层。一层是冻结的 100 个任务，用来测整体成功率与调用减少；另一层是受控干预，用来测决策结构对可靠性的影响。冻结任务集保证所有对照组面对同样的输入，受控干预则单独改变动作集大小和候选相似度。

这种设计值得借鉴：整体收益用端到端任务测，机制解释用受控变量测。只报端到端分数，无法知道收益来自哪里；只报受控实验，又无法证明真实任务上有效。两类实验一起看，结论才站得住。

### 可靠性取决于决策结构

论文的另一组实验（RF-5C）研究了两个变量：动作集大小，以及候选动作在结构上有多接近正确答案。结果显示，动作集越大、候选越接近正确项，可靠性越低。论文特别指出，在授权边界附近的"近似有效"候选最容易出错。

这个发现直接指向工程做法：不要用一个统一的置信阈值。动作集大小不同、错误代价不同、候选相似度不同，阈值都应该不同。把授权边界附近的决策单独拎出来处理，比整体调阈值更有效。

### 论文自己承认的局限

REFLEX 没有把结论写成"Jev 全面替代 LLM"。在外部任务上，一个便宜的生成模型级联已经能把普通路由做得很好，Jev 的优势会缩小。论文在 BFCL 和 τ 类评测上看到，当普通路由本身准确率已经很高时，Jev 带来的额外收益有限。

论文还记录了大量错误集中在控制类决策上，包括风险错误和澄清错误，而检索、普通工具选择和流程决策几乎没有错误。这说明"高频"不等于"容易"，不同决策类型的难度差异很大。

所以 REFLEX 的正确读法不是"以后不用大模型做 Agent"，而是：

> 先识别 Agent Loop 中重复、类型固定的控制决策，再用置信门把困难样本送回强模型。

### 替换率为什么差异这么大

工具选择 99%、完成判断 77%、检索 56%、澄清 28%，这组数字反映的是决策的信息完备程度。工具选择通常有明确的候选和清楚的输入，模型容易判对；澄清判断要求模型评估"我掌握的信息够不够"，这是一个关于自身知识的判断，难度更高。

这个差异对落地有直接指导：先下放信息完备的决策，把关于"我知不知道"的元认知判断留到后面。替换率高不等于值得下放，还要看错误代价。

### 论文结果怎么读

读到"95% 成功率、减少 72.7% 调用"时，先看它的分母。这是在一个冻结的 100 任务基准上的结果，任务是受控构造的，不能直接等同于真实业务。再看它比较的对象，是"只用强模型"的基线，而不是某种已优化的便宜级联。

论文自己也记录了外部基准上的有限优势。把这两部分一起读，才能得到准确结论：在受控条件下，Jev 能大幅减少强模型调用；在真实且已优化的路由上，收益可能缩小。

### 一个可以立刻验证的小实验

如果想快速判断 Jev 是否适合你的场景，可以做一个小实验：选一个已有的、带标签的决策，把它的输入同时喂给 Jev 和现有 LLM 调用，比较两者的选择和成本。

不需要改生产流程，只需要一个离线脚本。如果 Jev 在多数样本上与现有判断一致，并且成本明显更低，就值得进一步做校准；如果分歧很大，先分析分歧落在哪些样本上。

## 五、置信门不能只看一个数字

最简单的升级规则是：

```ts
if (decision.confidence >= 0.85) {
  return execute(decision.choice);
}
return strongModel.decide(state);
```

真实系统至少还要加入风险与决策类型：

```ts
const shouldEscalate =
  decision.confidence < thresholdByAction[decision.choice] ||
  actionRisk[decision.choice] === "high" ||
  requiresFreeFormGeneration(state) ||
  isOutOfDistribution(state);
```

统一阈值通常不够。误选一个只读搜索工具，最多损失一次调用；误选"退款"或"删除"，代价完全不同。阈值应该按动作风险、错误方向和线上数据校准。

### 置信度不是承诺

模型给出的 0.9 不天然等于"100 次里对 90 次"。上线前需要画可靠性图，检查置信区间是否真的对应准确率。输入分布变化后还要重新监控，否则阈值只是一个看起来精确的常量。

校准要分层做。整体校准好，不代表每一个动作类型的校准都好。工具路由、记忆写入、验收判断可能各有各的偏差。按动作类型分别画可靠性图，才能定位哪一类的阈值不可信。

### 一个最小校准流程

最小可用流程包括四步：收集一批带真实标签的样本；按动作类型分组；对每组画置信度与准确率的关系；为每组选一个满足目标错误率的阈值。

这条流程不需要复杂工具，一个脚本加一份标注数据就能跑。它的价值在于把"阈值"从拍脑袋变成一个可验证的量。上线后再用线上数据周期性重跑，跟踪校准是否漂移。

### 校准数据从哪来

校准需要带标签的样本，数据可以来自三处：历史人工决策记录、升级后强模型的决定、以及线上真实结果的回流。

三者质量不同。人工决策最可信但量少；强模型决定量多但可能与 Jev 有相关错误；真实结果最直接但获取慢。混合使用，并对来源加权，比只用一种更稳。用强模型决定做标签时尤其要小心，因为相关错误会被当成正确答案固化下来。

### 相关错误会毁掉级联

级联架构隐含一个假设：第一个模型的错误，会被第二个更大的模型纠正。Jev 作为 Judge 的研究正面挑战了这个假设。

研究发现，LLM Judge 经常重复 Jev 最有信心的那些错误。也就是说，"Jev 低置信就交给 LLM"能省钱，却不一定能提高准确率，因为真正难的错误可能同时难住了两个模型，它们的错误是相关的。

这一点对设计升级策略很关键。升级不是万能的纠错机制。要判断升级是否有效，必须看两个模型的错误是否独立，而不是默认"更大的模型更对"。

### 阈值之外还要看什么

阈值只回答"这一条要不要升级"。工程上还要看升级的成本和收益是否匹配。如果某类动作的升级率高达 90%，说明阈值或者模型在这类动作上失效，继续升级只是把成本转嫁给强模型，控制层没有产生价值。

一个健康的控制层应该呈现这样的分布：大部分动作在低升级率下保持低错误，少数困难切片有较高升级率。如果升级率在全球面均匀偏高，问题往往出在问题设计或输入表示，而不是阈值本身。

### 升级不是免费的

每次升级都消耗一次强模型调用。升级率高到一定程度，控制层的成本优势就被抵消。设计时要给升级设置预算，并定期检查"哪些被升级的样本其实不需要升级"。

一个常见的浪费是把大量"模型其实判对了但置信度偏低"的样本升级掉。改进校准通常比提高模型能力更能降低这种浪费，因为它让正确的判断重新变得可信。

### 阈值应该由谁定

阈值不该由模型决定，也不该由工程师拍脑袋。它应该由业务能接受的错误率反推。先确定"这类动作最多允许多少错误"，再根据校准曲线找到对应阈值。

把阈值和业务风险挂钩，让阈值有了可解释的依据。当业务风险变化时，阈值也随之调整，而不是变成一组没人记得为什么的数字。

## 六、Jev-Mem：控制记忆，而不是生成记忆

Agentic Memory 常把写入、分类、关联、检索和停止都交给 LLM。一次用户对话可能触发多轮模型调用：提取事实、生成摘要、判断关系、改写查询，再判断检索结果够不够。

[Jev-Mem](https://arxiv.org/abs/2609.23986)把记忆系统拆成三层：

![Jev-Mem 的控制面、结构化记忆面与推理面](/images/posts/jev-memory-planes.svg?v=20261001)

控制层处理频繁的有界决策，强模型只在需要推理和生成时出现。具体来说，控制层负责记忆类型判断、关系组织、查询路由、检索预算分配、图遍历、候选打分和自适应停止。

### 论文报告的数字

论文在 LoCoMo 上报告了 0.777 的 LLM-as-a-Judge 总分，相对最强基线提升 11%；记忆构建时间为 158 秒，比最快对照快 6.6 倍；平均查询延迟降到 0.93 秒，下降 36.7%。这些数字来自论文实验，数据集和对照都有限定，不能直接外推到任意业务。

值得注意的不是绝对值，而是改进的分布：效果、构建时间、查询延迟同时改善。这说明瓶颈未必在"记忆本身的表示"，而在"每个阶段都插入一次生成式判断"这件事上。

### 对 Memory 设计的启示

Jev-Mem 改变了一个默认设计：把记忆系统看成一串生成式调用。如果写入、分类、检索、判断都走 LLM，系统必然慢且贵，而且每一步的概率都难以校准。

把控制决策类型化后，系统更容易测量每一步的准确率、延迟和升级比例。哪一步经常升级、哪一类决策最不准、哪个阈值最贵，都能被单独观测。可观测性本身就是优化的前提。

### 控制层到底替代了哪些调用

在没有控制面的记忆系统里，一次写入可能触发多次模型调用：判断这条信息是不是值得记、判断它属于事实还是偏好、判断它和哪条旧记忆冲突、生成摘要、决定检索预算。每一个都是生成式调用。

Jev-Mem 把这些高频判断集中到控制面，用类型化决策替代。强模型只留两件事：需要跨记忆推理时，以及综合最终答案时。替换的不是"记忆能力"，而是"记忆过程中的重复判断"。

### 记忆控制的三个决策点

记忆系统里最适合类型化的三个判断是：写不写、算哪类、够不够。写不写决定是否占用存储和检索；算哪类决定节点类型和关系；够不够决定检索是否继续。

三个判断都是高频、有界、错误可回退的。把它们交给控制面，强模型只在需要跨记忆推理时出现，这就是 Jev-Mem 能在效果和延迟上同时改善的原因。

## 七、Jev 作为 Judge：便宜，但错误相关

评测是另一个高频判断场景。传统 LLM Judge 会针对每条样本和每项 rubric 生成评价，成本会随样本量快速上升。

[JEV vs. LLMs as Rubric Judges](https://arxiv.org/abs/2609.29769)比较了 Jev 与三种 flash 级 LLM Judge。在七个基准构成的九组面板、五千多条评测对上，27 组两两比较只有 8 组出现显著准确率差异，多数比较在统计上不显著。

### 二元标准与分级标准的差异

Jev 在二元标准上表现更好。例如在 RiceChem 面板上，Jev 的准确率高于三种 LLM Judge。但在分级标准上，它落后于最好的 LLM Judge。例如在 ELLIPSE 作文面板上，Jev 明显低于 Gemini。

论文没有回避这一点，反而指出：在分级标准上，所有四个 Judge 互相之间的一致度都高于它们与人工标注的一致度，而且普遍给出比人工更低的等级。这说明问题不只出在 Jev 身上，分级标准本身的解释空间也很大。

### 为什么二元比分级更适合

二元判断的答案空间只有两个元素，错误方向明确，校准相对简单。分级判断要求模型在一个连续或半连续的尺度上定位，标准本身的解释空间更大，人工标注的一致性也往往更低。

这条差异有实用价值：可以先在二元标准上引入 Jev，把分级判断保留给 LLM Judge。等二元场景验证充分后，再评估分级场景是否值得下放。

### 成本与错误的分布

三种 LLM Judge 的成本是 Jev 的 29 到 325 倍，用时是 30 到 220 倍。这个量级差异是 Jev 的主要优势。

但论文标题里的后半句更重要：wrong in the same places。研究发现，LLM Judge 经常重复 Jev 最有信心的错误。于是"Jev 低置信就交给 LLM"虽然节省成本，却没有带来预想中的准确率提升，级联最多只改善约 1.5 到 2 个百分点。

这揭示了级联系统的一个陷阱：第二个模型更大，不代表它的错误与第一个模型独立。两者可能都误解了同一条 rubric，或者共同缺少某个背景知识。多个 AI Judge 的一致意见不能替代独立证据。

### 对评测设计的启示

Jev 适合做大规模初筛和已验证的二元标准。它能以极低成本把海量样本过一遍，把不确定的样本挑出来。但高风险验收仍需要确定性检查、真实环境结果或人工抽样。

评测体系应该是分层的：确定性断言负责硬约束，Jev 负责低成本的二元初筛，LLM Judge 负责开放质量，人工负责最终仲裁。把 Jev 放在最前面，是为了让后面的昂贵判断只处理真正需要它的样本。

### 级联在评测里为什么容易高估

级联的收益在评测里容易被高估，因为评测常常默认"升级后的判断更准"。但如果两个模型的错误相关，升级带来的净提升会远小于预期。

要避免这个陷阱，评测时要单独报告三组数字：第一层单独的正确率、升级后整体的正确率、以及两者错误的交叠。只看整体正确率，会把相关错误当成独立错误计分。

### 三类 Judge 的分工

把评测拆开看，三类判断共用一套信号：确定性断言判硬约束，Jev 判二元标准，LLM Judge 判开放质量。三者不是替代关系，组合起来价格和可靠性更平衡。

用 Jev 处理二元标准，能把大部分样本在低成本下判完，剩下的交给 LLM Judge 或人工。这个分层的关键是每一层只处理自己擅长的部分，而不是让最贵的一层处理全部样本。

## 八、把 Jev 放在 Agent 哪一层

它最适合进入 Harness 的 Control Plane，而不是替代主模型：

| 运行环节 | Jev 的角色 | 强模型的角色 |
| --- | --- | --- |
| 工具调用前 | 工具族路由、风险分类 | 生成复杂参数、处理例外 |
| 记忆写入 | 类型、保留与关系判断 | 总结和跨记忆推理 |
| 检索过程 | 预算、候选评分、停止 | 查询改写和答案综合 |
| 输出验收 | 二元 rubric 初筛 | 复杂分级与解释 |
| 模型路由 | 判断任务是否需要升级 | 完成困难样本 |

这层设计会让 Agent 的成本结构发生变化。强模型调用次数不再等于 Agent 决策次数，大量 routine control 可以被单独观测、训练和优化。

### 控制平面不是"更小的模型"

把 Jev 理解成"更小的 LLM"会错过它的定位。它接管的是一层职责：决定下一步交给谁。这层职责在传统设计里分散在各个 if 和 Prompt 里，现在被集中成一个可测量、可校准的组件。

控制平面出现后，系统多了一个新的观测点。可以问"这一步为什么升级""哪类决策最贵""阈值是否漂移"。这些问题在纯 LLM 架构里很难回答，因为没有独立的控制层可观测。

### 一个多模型分工的形状

未来的 Agent Harness 很可能同时拥有几类模型：强模型负责推理和生成，小模型负责路由与提取，Embedding 模型负责相似性，Jev 这样的决策模型负责类型化选择。系统根据风险和置信度在它们之间调度。

这个分工下的 Harness 需要新增一类组件：决策编排器。它不生成内容，只决定"这一步交给哪层模型、用哪个阈值、是否升级"。这一层的好坏，直接决定多模型系统是否比单模型更划算。

### 成本模型：什么时候多模型更划算

多模型系统不天然更便宜。引入 Jev 意味着多一层调用、多一套阈值、多一份运维。只有当被下放的决策量足够大，节省的强模型调用能覆盖这层开销时，多模型才划算。

一个粗略的判断：如果一个决策每天调用次数很高、结构固定、错误可回退，下放大概率划算；如果调用次数低、每次都不同、错误代价高，保留强模型更合适。控制平面的收益来自规模。

### 编排器的最小状态

决策编排器至少要维护三类状态：每个动作的当前阈值、每类决策的近期校准、以及升级预算。阈值决定自动化比例，校准决定阈值是否需要调整，预算防止升级失控。

把这三类状态集中管理，而不是散落在各处，是多模型系统可维护的关键。否则调一个阈值要翻五个文件，排查一次异常要对三个日志。

### 从单模型到多模型的迁移

迁移不要一次到多模型。先保留现有强模型决策，同时并行跑 Jev，只记录不执行。积累一段时间后，比较两者的选择，找出 Jev 稳定可靠的决策类型。

找到之后，只对这几类放开自动执行，其余继续走强模型。逐步扩大范围，每一步都用数据支撑。多模型的价值来自规模化的可靠下放，而不是把所有决策一次交出去。

## 九、哪些决策适合交给 Jev

我会从四个条件筛选：

1. 输出集合能在执行前完整列出；
2. 大量调用具有相同的决策结构；
3. 错误可以被后续检查发现，或能够安全回退；
4. 系统能积累带标签的数据来校准阈值。

适合的例子包括：

- 从有限工具集中路由一个只读查询；
- 判断某条内容属于事实、偏好还是临时状态；
- 给检索候选打相关或不相关标签；
- 判断测试是否满足一条二元 rubric；
- 在预算耗尽前选择继续、停止或升级。

不适合直接自动执行的例子包括：

- 涉及资金、删除和外发的不可逆动作；
- 候选动作随上下文临时生成；
- 需要引用证据和解释推理链的判断；
- 标签标准本身含糊或持续变化；
- 系统无法观察真实结果，只能用另一个模型打分。

### 从候选清单到上线阈值

选好决策之后，落地要经过几步：先固定一份离线评测集，覆盖每个动作类型；再用它画可靠性图，确定每类的初始阈值；然后线上用灰色流程并行跑 Jev 与现有逻辑，比较它们的选择；最后按错误代价逐步放开自动化比例。

这四步的顺序不能乱。跳过离线评测直接上线，会把校准问题带进生产；跳过灰度直接全量，会把相关错误放大到不可控。

### 评测集怎么建

评测集要覆盖四类样本：典型的简单样本、边界样本、历史失败样本、以及分布上少见但风险高的样本。只收集简单样本，会让离线指标虚高，上线后遇到边界样本就暴露问题。

每条样本要标注正确的动作，以及错误的代价等级。代价等级决定了阈值：同样是不确定，低代价动作可以放宽，高代价动作必须升级。

### 衡量控制层好坏的指标

衡量控制层不只看准确率。更完整的指标包括：自动化比例、升级率、升级后的净准确率、每千次决策的成本、以及错误在切片上的分布。

这些指标一起看，才能判断控制层是否真的产生了价值。一个自动化比例很高、但错误集中落在高风险切片的控制层，比一个自动化比例中等、错误均匀分散的更危险。

## 十、端到端：一个客服工单的决策链

把前面的机制串成一个具体场景。用户发来消息："我上周买的耳机右边不响了，我想退掉。"

### 第一步：意图与动作路由

控制层先判断用户意图属于哪一类，以及下一步动作候选。Jev 返回的候选可能是 `refund`、`replace`、`clarify`。它给出概率，例如 refund 0.62、replace 0.21、clarify 0.17。

### 第二步：置信门与风险判定

运行时检查这类动作的阈值。退款属于中等风险，阈值设得较高。0.62 低于阈值，或者命中"需要确认商品状态"的规则，于是升级到强模型或人工确认，而不是直接发起退款。

### 第三步：记忆写入判断

无论最终动作是什么，系统都要判断这条对话里有没有值得写入长期记忆的信息。一条只读的分类决策决定了"用户偏好退款而非换货"是否写入，以及归到哪一类记忆。这个判断高频、结构固定，适合 Jev。

### 第四步：验收判断

动作执行后，系统要判断"是否满足验收条件"。对于二元标准，例如"是否已向用户说明处理方式"，Jev 可以做低成本初筛。对于更复杂的分级判断，交给 LLM Judge 或人工。

### 第五步：失败后的升级路径

如果 Jev 在某个动作上持续低置信，或者线上监控发现某类动作的错误率上升，运行时会提高该动作的升级比例，或者把这类动作暂时移出自动执行范围。升级策略是动态的，不是一次配置就固定。

这个例子里，Jev 没有替代强模型，它承担了链路前端的高频筛选，让强模型和人工只处理真正需要它们的样本。

### 这个例子里 Jev 做对了什么

这个例子里，Jev 做对的关键不是"猜对了动作"，而是"承认自己不确定"。候选里 clarify 和 refund 概率接近时，控制层选择升级，把决定权交给更强的判断。

控制层的成熟标志，是它在不确定时愿意说"我不确定"。一个永远高置信的快层比一个会犹豫的快层更危险，因为它会在没有把握的时候也直接执行。

## 十一、失败模式与局限

Jev 的可靠性有清晰的边界，下面几类是论文和官方资料都指出过的。

| 失败模式 | 触发条件 | 缓解方式 |
| --- | --- | --- |
| 授权边界误判 | 候选动作在权限边缘、彼此相近 | 单独设阈值，高风险动作强制升级 |
| 分级标准落后 | rubric 需要细粒度分级 | 分级判断交给 LLM 或人工 |
| 分布漂移 | 输入分布与训练时不同 | 持续监控校准与升级率 |
| 相关错误 | 升级后的模型犯同类错误 | 用独立证据交叉验证 |
| 动作集过大 | 候选数量多、区分度低 | 分层路由或缩小候选集 |
| 假精确 | 概率未校准，阈值看似精确 | 画可靠性图，按类型校准 |

这些失败模式有一个共同点：它们不是"模型不够聪明"，而是"决策结构和验证方式"的问题。换一个更大的模型未必能解决，因为它们常常是相关错误或结构性问题。

### 一个容易被忽略的风险

把 Jev 放在控制层，会改变系统的失败形态。原来强模型偶尔判断错误，是低频事件；现在 Jev 高频决策，错误可能更规律、更集中。如果某个阈值设错，错误会在短时间内大批出现。

因此控制层必须自带熔断和监控。升级率突然上升、某类动作错误率突破阈值、置信度分布整体偏移，都应该触发告警或自动降级。高频决策的收益和风险是成比例的。

### 上线后的监控清单

上线后至少监控四类指标：各动作的升级率、各动作的错误率、置信度分布的偏移、以及级联的净收益。升级率突然上升往往意味着分布变了或阈值失效；错误率上升则可能意味着模型能力在特定切片上退化。

把监控和阈值联动，才能让控制层自我调整。静态阈值只能应对上线那一刻的分布，动态监控才能跟上真实世界的变化。

### 什么时候应该关掉控制层

控制层不是必须一直开着。如果监控显示某类动作的升级率长期偏高、错误率没有改善、维护成本又持续存在，就该考虑把这部分交回强模型或人工。

退出的判断和进入一样重要。控制层的目标是降低总成本、提高可测性，如果它反过来增加了风险和维护负担，就该承认这个场景不适合下放。

### 与普通分类器相比的额外风险

Jev 比普通分类器多了语义理解能力，也多了对应的风险：它可能对训练分布之外的语言给出看起来合理但错误的概率，而且这种错误不容易通过规则拦截。

普通分类器的输入是固定特征，异常可以被检测；Jev 的输入是自由文本，异常分布在语义空间里。监控要覆盖语义分布，而不是只看特征范围。这也是高频决策需要持续校准的原因。

## 十二、现阶段该怎么用

Jev 最有意思的地方不是速度数字，而是它挑战了一个默认假设：智能软件中的每个语义判断都必须通过文本生成完成。

LLM 很适合开放问题，却不是所有控制决策的天然接口。把有界决策单独抽象出来，可以让系统更便宜、更可测、更容易校准。这是它真正的价值。

但要克制。Jev 刚刚进入公开使用，独立研究还不多；官方关于速度和能力的说法需要更多外部复现；已有论文显示，它在复杂分级、授权边界和相近候选上会遇到限制。它适合成为新的控制层候选，而不是一夜之间替换全部 LLM 调用。

### 一个务实的起步方式

如果要尝试，我会从一个最窄的场景开始：选一个高频、二元、错误可回退的判断，例如"这条检索结果是否相关"，先用 Jev 做初筛，把不确定样本送回现有逻辑。跑一段时间，拿到校准数据和升级率，再决定是否扩大范围。

从窄场景起步的好处是，既能验证 Jev 在真实分布上的表现，又不会把高风险决策直接交给它。控制层的信任是积累出来的，不是配置出来的。

### 一个 30 天的试点计划

第一周确定一个高频、二元、可回退的决策，收集并标注一批线上样本。第二周做离线评测和校准，确定初始阈值。第三周并行跑，Jev 只记录、不执行，对比它与现有逻辑。第四周对表现稳定的类别放开自动执行，其余保持升级。

这个节奏的好处是每一步都有明确的验收点：第一周要能建成评测集，第二周要能画出校准曲线，第三周要能量化分歧，第四周要能看到成本或延迟的改善。任何一步达不到，就停下来重新界定场景。
