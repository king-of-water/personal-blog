一个 Agent 完成任务时，会做大量很小的判断：该调用哪个工具，这条记忆要不要写入，检索是否足够，当前结果能不能通过验收，下一步继续执行还是向用户确认。

我们习惯把这些判断全部交给 LLM。系统把状态写成提示，让模型生成一段文字或 JSON，再解析成程序动作。这个方案通用，却有一处不协调：为了在几个有限选项之间做选择，我们启动了一个擅长生成任意字符串的大模型。

Jev 尝试提供另一种计算原语。它接收非结构化状态和类型化问题，直接返回允许答案上的概率，不生成解释文本。TypeSafe AI 把它称作 System One Model：快、便宜，适合软件内部反复发生的有界决策。这篇文章想回答一个具体问题，就是什么时候可以用这种类型化决策模型替换一次生成式调用，什么时候不能。

证据来自 TypeSafe 的官方介绍，以及三项围绕 Jev 的研究：REFLEX 的选择性控制、Jev-Mem 的 Agentic Memory、以及 Jev 作为评测 Judge 的对比。所有实验数字都来自各自论文的设定，不能直接外推到任意业务。

## 一、为什么有界决策不该交给生成模型

把 Agent 的每个小判断都交给 LLM，最直接的问题是成本结构。一次调用要加载提示、执行前缀、逐 token 生成、再解析。哪怕答案只是三个候选项里的一个，这套流程也照走一遍。当同一个决策每天重复几十万次，这些固定成本会被放大。

成本只是表层，更深的问题在于输出空间没有被约束。模型可能返回 `refund`，也可能返回带引号的 `"refund"`、带句号的 `refund.`、或者一段带解释的 JSON。JSON 模式能收紧格式，却没有改变"模型在开放词汇表上生成"这个事实。运行时必须准备解析器、容错和重试，才能把输出接回程序。

如果这几个选项在执行前就已知，那么运行时真正需要的是一个"带语义理解能力的分类器"，而不是一个万能生成器。分类器不需要写句子，只需要给出每个选项的概率和置信度。Jev 的定位就在这里。

生成式接口的通用性有代价：它把"格式正确"和"语义正确"两件事捆在一次调用里，运行时必须同时处理两者。Jev 把它们拆开：格式正确由输出空间的封闭性保证，语义正确由模型能力与阈值共同保证。这个拆分改变了工程的落点，解析器变简单了，但阈值、校准和升级逻辑变得更重。复杂度从"解析自由文本"转移到"管理有限决策"，后者更容易测量，也更容易做确定性检查。

还有一个更根本的观察：并不是每个语义判断都值得用生成来完成。判断"这条日志属于哪一类""这个工具有没有权限""检索结果够不够"这类问题，输出的可能空间是有限的，而生成模型 99% 的算力花在了我们不关心的表达自由度上。把这类判断独立出来，本质上是把算力从"怎么说"转回"怎么选"。

从系统设计角度看，这种拆分还有一个好处：它让控制逻辑变得可实现、可测试。一个返回概率的组件可以被单元测试，可以用一批带标签的样本反复验证；一段"让模型输出 JSON 再解析"的逻辑，测试起来要困难得多。

### 它和 JSON 模式、小模型、分类器的区别

Jev 常被归到三个已有概念里，但都不完全一样。和 JSON 模式的区别在于输出空间：JSON 模式约束的是语法结构，Jev 约束的是答案集合，前者仍可能生成任意字段值，后者只能从给定选项里选。和小模型的区别在于优化目标：通用小模型还是要完成生成任务，它的概率未必校准，Jev 专门为有界决策训练，重点是概率的可靠性。和传统分类器的区别在于输入：传统分类器通常需要结构化特征，Jev 直接吃非结构化状态，这让它可以放进原本只接受自然语言的链路。

### 一次判断的真实成本结构

一次有界决策的 LLM 调用，成本不只在生成的 token 上，还包括系统提示和工具定义的前缀、上下文历史的重复加载、输出解析与容错、重试与超时的尾延迟。Jev 改变的正是这部分固定成本。它不需要生成长文本，也不太需要复杂的解析兜底，单次成本和延迟都能显著下降。

值得注意的是，成本下降不等于总收益上升。节省的调用必须能覆盖多出来的阈值管理、校准和监控开销，多模型系统才真正划算。

一个常见的误解是"既然便宜，就都交给他"。实际相反：越便宜的控制层，越容易被滥用，因为它看起来没有代价。但没有代价的是调用费，有代价的是错误。一个低成本的错误判断，如果发生在高风险动作上，代价可能远高于一次昂贵但正确的强模型调用。所以控制层的价值不在"什么都做"，而在"做那些做对了收益明显、做错了代价可控的判断"。

还有一个对照能说明问题。拿"这条检索结果是否相关"举例：LLM 接口可能是"请判断这两段内容是否相关，输出相关或不相关，并说明理由"；Jev 接口是"给定问题和检索结果，在相关、不相关上返回概率"。LLM 接口多出的"说明理由"不参与后续程序决策，却要花生成成本；Jev 接口没有理由，只有概率，程序直接用它做过滤。差别不在能力，而在是否把"解释"当成必需输出。

这种不协调在决策频率高、答案空间小的时候最明显。频率高意味着成本会被放大，答案空间小意味着生成能力大部分被浪费。反过来，低频、开放的任务即使交给强模型，浪费也不明显。判断是否值得改成类型化决策，先看这两个维度。

## 二、Jev 到底是什么

TypeSafe 对 Jev 的描述很准确：unstructured state in, typed probabilistic decisions out，非结构化状态输入，类型化概率决策输出。一个典型调用像这样，给定工单和候选动作，返回每个动作的概率。

```ts
const decision = await jev.choose({
  state: ticket,
  question: "下一步应采取什么动作？",
  choices: ["refund", "replace", "clarify"],
});

// { choice: "clarify",
//   probabilities: { refund: 0.08, replace: 0.17, clarify: 0.75 } }
```

关键在输出空间在调用前已经确定。软件得到一个类型化选择及其概率，可以直接设置阈值、比较候选，或决定是否升级到强模型。Jev 仍然会出错，"不生成自由文本"只意味着它不会返回类型之外的字符串，不代表它不会选择错误选项；把格式错误和语义错误分开，是理解 Jev 的第一步。

输出空间的具体形状，会直接影响它的表现。同一个状态，写成"选一个动作"和写成"这段内容属于哪一类"是两个不同的决策。这带来一个设计要点：控制层的决策要拆得足够细。把太多语义塞进一个问题，会让答案集变得模糊；把一个问题拆成两个更清楚的问题，往往能同时提高准确率和可校准性。问题设计本身就是控制层工程的一部分。

它用一个面向校准决策的训练方法，官方称作 RLCD。它的目标不是写出最讨喜的答案，而是让概率尽量反映真实的不确定性。对一个要接入阈值和升级逻辑的决策层，校准比文采重要得多。概率校准指的是：当模型说 0.8 时，在大量同类样本里，它是否真的对了大约 80%。一个模型可以很准却校准很差，也可以校准不错但区分度不高；Jev 的目标是让概率可信，因为控制层要用概率做决策。

官方还强调 Jev 是"不能幻觉"的，因为它不做字符串生成。这句话需要准确理解：Jev 不会凭空写出一个不存在的工具名或一段编造的引用，因为它的输出被限制在给定的答案集里；但它可能把相关误判为不相关，把澄清误判为退款。不会幻觉格式，和不会判断错误，是两件事。

它也有明确的能力边界：不能生成解释、不能引用原文、不能做多步推理。它不回答"为什么"，只回答"是哪个、有多大把握"。需要理由、需要引用、需要链式推理的场景，仍然要交给生成模型。把它放错位置，最常见的错误是让它承担本属于生成模型的职责，例如要求它总结一段对话或解释一个判断。

得到概率之后，程序通常只有两种用法：取最大值，对应"自动执行"；按阈值过滤，对应"自动或升级"。标签丢失了不确定性，而控制层恰恰需要不确定性来做升级决策，所以要尽量保留概率，而不是过早把它压成一个标签。

Jev 的答案集由调用方在请求时给出，所以它的能力边界由"问题怎么写"决定。这既是灵活，也是负担：写得好，它就是一个趁手的判别器；写得含糊，它也会给出一组含糊的概率。控制层的工程质量，很大一部分体现在问题的设计上。

## 三、System One 与 System Two 的边界

命名来自"快思考与慢思考"的区分。快层擅长高频、有界、可类型化的快速判断，例如路由、分类、打分、继续或停止；慢层擅长开放式推理、规划、解释与生成，例如分析故障、编写代码、总结证据。

| 层 | 擅长的任务 | 在 Agent 中的例子 |
| --- | --- | --- |
| System One | 高频、有界、可类型化的快速判断 | 路由、分类、打分、继续或停止 |
| System Two | 开放式推理、规划、解释与生成 | 分析故障、编写代码、总结证据 |

这不是一条绝对边界。同一个问题可以写成有界选择，也可以要求开放推理。真正需要判断的是：动作集合是否清楚，决策错误是否可检测，输入是否包含足够信息，以及不确定时能否安全升级。

一个关键点是，决策的风险不会随着选项数量一起缩小。"从三个只读检索工具中选择一个"适合快速控制层；"是否删除生产数据库中的一批记录"即使只有 yes 或 no 两个答案，也不该因为输出空间小就自动执行。快不等于简单，把快层当成"廉价的近似"会浪费它的潜力；它应该是一等公民，有自己的评测集、校准曲线和升级策略。

把决策交给快层，不等于这个决策可以草率处理。恰恰相反，快层的价值在于它值得被认真优化：因为调用量大，哪怕准确率提升一个百分点，绝对收益也很可观；因为结构固定，可以积累带标签数据来校准；因为错误可被监控，可以按动作风险分别设置阈值。把快层当成"廉价的近似"，会浪费它真正的潜力。

什么任务不该写进快层，大致有三类：答案空间本身开放，例如"总结这段对话"；决策依赖大量隐式语境，例如"用户是不是真的想退款"；错误不可回退，例如删除、扣款、对外发送。这三类不是永久排除，而是当前不适合自动执行，可以由 Jev 做初筛，再把结果交给强模型或人工。

快层和慢层是流水线上的两级，不是替代关系。快层处理大量简单样本，把不确定的挑出来；慢层处理被挑出来的困难样本，并把结果作为反馈，用于更新快层的阈值和训练数据。这个协作模式要求慢层的结果可回收：如果慢层的决策不记录标签，快层就永远学不到自己哪些判断错了。没有反馈闭环，Jev 只是一个更便宜的分类器，而不是一个会随数据变好的控制层。

快层的能力其实来自约束。有人担心把问题限制成有界选择会损失模型的智能，实际相反：约束让模型把注意力集中在判别上，而不是同时处理判别和表达。这类似于人类专家做快速判断，经验丰富的人在熟悉的问题上能迅速给出分类，是因为他不需要重新组织语言。

判断快层粒度也有一个简单方法：试着给每个选项写一句"选它就意味着什么"。如果两句话互相重叠，说明粒度太粗；如果两个选项几乎不可能同时出现，说明可以考虑合并。粒度合适时，每个选项都对应一个清晰、互斥的动作。

## 四、REFLEX：选择性控制

REFLEX 把 Jev 放进一个选择性控制架构：当前状态先交给 Jev，Jev 返回选择和置信度；高置信且允许自动执行的直接采取动作，低置信、需要生成或高风险的则交给强模型。论文在冻结的 100 个任务上报告，这个架构取得 95% 成功率，同时比只用强模型减少 72.7% 的强模型调用，成功率在 2 个百分点的非劣性边界内。

更值得关注的是细分结果。论文观察到，替代率在工具选择上达到 99%，完成判断为 77%，检索判断为 56%，澄清判断只有 28%。这组数字反映的是决策的信息完备程度：工具选择通常有明确的候选和清楚的输入，模型容易判对；澄清判断要求模型评估"我掌握的信息够不够"，这是一个关于自身知识的判断，难度更高。替换率高不等于值得下放，还要看错误代价。

论文里还有一个容易被忽略的细节：这个高置信门不随下游强模型的身份而变化。在同一个固定阈值下，无论后面接哪个强模型，Jev 都会把同样 66 个任务判为可以自主完成，而且这 66 个任务每次都成功。剩下的 34 个任务才是强模型真正起作用的地方。这说明门控学的是"任务本身适不适合下放"，而不是去模仿某个特定强模型；这个性质让升级策略可以和模型选择解耦。

REFLEX 没有把结论写成"Jev 全面替代 LLM"。在外部任务上，一个便宜的生成模型级联已经能把普通路由做得很好，Jev 的优势会缩小。论文也记录了错误集中在控制类决策上，包括风险错误和澄清错误，而检索、普通工具选择和流程决策几乎没有错误。所以它的正确读法不是"以后不用大模型做 Agent"，而是：先识别 Loop 中重复、类型固定的控制决策，再用置信门把困难样本送回强模型。

读这类结果时，先看分母。95% 成功率是在一个冻结的 100 任务基准上的结果，任务是受控构造的，不能直接等同于真实业务；比较的对象是"只用强模型"的基线，而不是某种已优化的便宜级联。论文自己也记录了外部基准上的有限优势，两部分一起读，才能得到准确结论：在受控条件下它能大幅减少强模型调用，在真实且已优化的路由上收益可能缩小。

实验设计也值得借鉴：整体收益用端到端任务测，机制解释用受控变量测。冻结任务集保证所有对照组面对同样的输入，受控干预则单独改变动作集大小和候选相似度。只报端到端分数，无法知道收益来自哪里；只报受控实验，又无法证明真实任务上有效。

一个可以立刻做的小实验是：选一个已有的、带标签的决策，把输入同时喂给 Jev 和现有 LLM 调用，比较两者的选择和成本。不需要改生产流程，一个离线脚本就够。如果 Jev 在多数样本上与现有判断一致、成本又明显更低，就值得进一步做校准；如果分歧很大，先分析分歧落在哪些样本上。

控制层还有一个组织上的好处：它把"判断"从"生成"里拆出来之后，团队可以分别优化。懂模型的调模型，懂业务的定义动作集和阈值，懂运维的盯监控。过去这些工作混在一段提示里，谁也说不清自己负责哪一块；拆开之后，责任边界清楚了，迭代速度也更快。

## 五、置信门与校准

最简单的升级规则是一个阈值：置信度高于阈值就执行，低于就升级。真实系统至少还要加入风险与决策类型，把动作风险、是否需要自由生成、是否属于分布外样本都考虑进去。

```ts
const shouldEscalate =
  decision.confidence < thresholdByAction[decision.choice] ||
  actionRisk[decision.choice] === "high" ||
  requiresFreeFormGeneration(state) ||
  isOutOfDistribution(state);
```

统一阈值通常不够。误选一个只读搜索工具，最多损失一次调用；误选"退款"或"删除"，代价完全不同。阈值应该按动作风险、错误方向和线上数据校准。

### 校准为什么重要

模型给出的 0.9 不天然等于"100 次里对 90 次"。上线前需要画可靠性图，检查置信区间是否对应准确率；输入分布变化后还要重新监控，否则阈值只是一个看起来精确的常量。校准要分层做：整体校准好，不代表每个动作类型都好，工具路由、记忆写入、验收判断可能各有各的偏差。

一个最小的校准流程是：收集一批带真实标签的样本；按动作类型分组；对每组画置信度与准确率的关系；为每组选一个满足目标错误率的阈值。数据可以来自历史人工决策、升级后强模型的决定，以及线上真实结果的回流；三者质量不同，混合使用比只用一种更稳。用强模型决定做标签时要特别小心，因为相关错误会被当成正确答案固化下来。

校准流程不需要复杂工具，一个脚本加一份标注数据就能跑，价值在于把"阈值"从拍脑袋变成一个可验证的量。上线后再用线上数据周期性重跑，跟踪校准是否漂移。校准不是一次性任务，而是一个持续的过程，因为输入分布会变，模型行为也会随版本变化。

### 相关错误会毁掉级联

级联架构隐含一个假设：第一个模型的错误会被第二个更大的模型纠正。Jev 作为 Judge 的研究正面挑战了这个假设：LLM Judge 经常重复 Jev 最有信心的那些错误。也就是说，"低置信就交给 LLM"能省钱，却不一定能提高准确率，因为真正难的错误可能同时难住了两个模型，它们的错误是相关的。

判断两个模型的错误是否独立，可以用同一批样本分别看它们的错误列表，算重叠比例。重叠高，说明级联的纠错空间小；重叠低，级联才有意义。凭感觉假设"更大的模型更对"，是最容易出错的地方。

升级本身也不是免费的。每次升级都消耗一次强模型调用，升级率高到一定程度，控制层的成本优势就被抵消。一个常见的浪费是把大量"模型其实判对了但置信度偏低"的样本升级掉。改进校准通常比提高模型能力更能降低这种浪费，因为它让正确的判断重新变得可信。

阈值也不该由工程师拍脑袋定，而应该由业务能接受的错误率反推：先确定"这类动作最多允许多少错误"，再根据校准曲线找到对应阈值。把阈值和业务风险挂钩，它就有了可解释的依据；业务风险变化时，阈值也随之调整。

一个健康的控制层应该呈现这样的分布：大部分动作在低升级率下保持低错误，少数困难切片有较高升级率。如果升级率在全球面均匀偏高，问题往往出在问题设计或输入表示，而不是阈值本身。

校准数据也要注意来源质量。三种来源里，人工决策最可信但量少，强模型决定量多但可能与 Jev 有相关错误，线上真实结果最直接但获取慢。用强模型决定做标签时尤其要小心：如果两者的错误相关，错误就会被当成正确答案固化下来，越校准越偏。

阈值之外还要看一件事：升级的成本和收益是否匹配。如果某类动作的升级率高到九成，说明要么阈值或模型在这类动作上失效，要么问题设计有问题，继续升级只是把成本转嫁给强模型，控制层没有产生价值。

从评测的角度看，控制层还提供了一个额外的好处：它让系统里"决策"这件事变得可度量。一个纯 LLM 系统里，"这一步为什么这么选"往往不可解释；引入控制层之后，每一步选择都有概率、有阈值、有升级记录，可以回溯、可以统计、可以改进。可观测性本身就是一种能力。

## 六、Jev-Mem：控制记忆

Agentic Memory 常把写入、分类、关联、检索和停止都交给 LLM。一次用户对话可能触发多轮模型调用：提取事实、生成摘要、判断关系、改写查询，再判断检索结果够不够。Jev-Mem 把这些高频判断集中到控制面，用类型化决策替代。

![Jev-Mem 的控制面、结构化记忆面与推理面](/images/posts/jev-memory-planes.svg?v=20261001)

它把记忆系统拆成三层：控制层处理记忆类型判断、关系组织、查询路由、检索预算分配、图遍历、候选打分和自适应停止；结构化记忆层存储多类型节点与关系；推理层只在需要跨记忆推理和答案生成时被调用。强模型只留两件事：需要跨记忆推理时，以及综合最终答案时。

论文在 LoCoMo 上报告了 0.777 的 Judge 总分，相对最强基线提升 11%；记忆构建时间为 158 秒，比最快对照快 6.6 倍；平均查询延迟降到 0.93 秒，下降 36.7%。这些数字来自论文实验，数据集和对照都有限定，不能直接外推。值得注意的不是绝对值，而是改进的分布：效果、构建时间、查询延迟同时改善，说明瓶颈未必在记忆本身的表示，而在"每个阶段都插入一次生成式判断"。

记忆系统里最适合类型化的三个判断是：写不写、算哪类、够不够。写不写决定是否占用存储和检索，算哪类决定节点类型和关系，够不够决定检索是否继续。三者都是高频、有界、错误可回退的。把它们交给控制面，强模型只在需要跨记忆推理时出现，这就是 Jev-Mem 能在效果和延迟上同时改善的原因。

它改变了一个默认设计：把记忆系统看成一串生成式调用。如果写入、分类、检索、判断都走 LLM，系统必然慢且贵，而且每一步的概率都难以校准。把控制决策类型化后，系统更容易测量每一步的准确率、延迟和升级比例：哪一步经常升级、哪一类决策最不准、哪个阈值最贵，都能被单独观测。可观测性本身就是优化的前提。

这个思路可以推广到很多"看似需要生成"的环节。只要一个环节的输出是有限的、判断是重复的，它就有被类型化的可能。转成类型化决策之后，成本下降只是第一层收益，更重要的收益是可测量、可校准、可优化。

记忆内容还可以粗分三类：事实、偏好、过程经验。事实是"用户是谁、项目处于什么状态"，偏好是"用户喜欢怎样的输出"，过程经验是"这类任务怎么做更好"。三类内容的写入条件、寿命和检索方式不同，把偏好当事实存储会污染检索，把一次过程经验当成普遍规则会误导后续任务。控制层的第一步，就是区分这三类。

记忆的另一个风险是错误积累。一次判断失误若被写进长期记忆，后续会不断引用它，形成自我强化。这要求控制层的写入判断不仅考虑"这条信息有没有用"，还要考虑"它有没有来源、有没有时效、错了能不能撤回"。类型化决策让这个判断更便宜，但不代表可以省略校验。

还有一个决策：控制层应该由谁维护。如果它只是一个实验性组件，可以让研究同学维护；一旦进入生产，它就成了基础设施，需要有人长期负责阈值、监控和升级策略。没有明确维护者的控制层，阈值会慢慢过时，监控会慢慢失效，最后沦为摆设。

## 七、Jev 作为 Judge

评测是另一个高频判断场景。传统 Judge 会针对每条样本和每项标准生成评价，成本会随样本量快速上升。Jev 作为 Judge 的研究比较了它与三种 flash 级 LLM Judge：在七个基准构成的九组面板、五千多条评测对上，27 组两两比较只有 8 组出现显著准确率差异，多数比较在统计上不显著。

Jev 在二元标准上表现更好，例如在一个化学推理面板上准确率高于三种 LLM Judge；但在分级标准上落后于最好的 LLM Judge，例如在一个作文面板上明显低于 Gemini。论文没有回避这一点，反而指出：在分级标准上，所有四个 Judge 互相之间的一致度都高于它们与人工标注的一致度，而且普遍给出比人工更低的等级。这说明问题不只出在 Jev 身上，分级标准本身的解释空间也很大。

三种 LLM Judge 的成本是 Jev 的 29 到 325 倍，用时是 30 到 220 倍，这个量级差异是 Jev 的主要优势。但论文标题里的后半句更重要：wrong in the same places。研究发现 LLM Judge 经常重复 Jev 最有信心的错误，于是"低置信交给 LLM"虽然节省成本，却没有带来预想的准确率提升，级联最多只改善约 1.5 到 2 个百分点。

这说明"多一个模型"不等于"更可靠"。级联的价值取决于两层模型的错误是否独立，而这一点往往被默认忽略。判断独立性的方法并不复杂：用同一批样本分别看两层的错误列表，算重叠比例即可；重叠高，级联的纠错空间就有限。

对评测设计的启示是分层的：确定性断言负责硬约束，Jev 负责低成本的二元初筛，LLM Judge 负责开放质量，人工负责最终仲裁。Jev 适合做大规模初筛和已验证的二元标准，但高风险验收仍需要确定性检查、真实环境结果或人工抽样。多个 Judge 的一致意见不能替代独立证据，因为相关的错误会在多个 Judge 之间一起出现。

级联的收益在评测里容易被高估，因为评测常常默认"升级后的判断更准"。要避免这个陷阱，评测时要单独报告三组数字：第一层单独的正确率、升级后整体的正确率、以及两者错误的交叠。只看整体正确率，会把相关错误当成独立错误计分。

对二元和分级的差异也要有预期。二元判断的答案空间只有两个元素，错误方向明确，校准相对简单；分级判断要求模型在连续尺度上定位，标准本身的解释空间更大，人工标注的一致性也往往更低。这条差异有实用价值：可以先在二元标准上引入 Jev，把分级判断保留给 LLM Judge，等二元场景验证充分后再评估分级场景。

还有一个细节值得记录：在被当作评分器的场景里，判断的"稳定性"和"准确性"同样重要。同一份回答今天判通过、明天判不通过，会让整套评测失去可比性。所以 Judge 要有稳定的版本，并定期用固定样本检查它的判断是否漂移。

对评测的另一个启示是，要让被评者表达不确定性。一个在证据不足时敢说"我不确定"的判断层，比一个永远高置信的判断层更可靠；同样，一个在证据不足时敢说"不知道"的 RAG 系统，比一个硬答的系统更值得信任。把不确定性写进输出，是让判断可用的前提。

从成本结构看，控制层真正的价值在于"把昂贵判断的次数和数据量脱钩"。纯 LLM 系统里，判断次数越多，强模型调用越多，成本线性上升；引入控制层之后，大部分判断由便宜层完成，强模型调用只和"困难样本的比例"相关。数据量涨十倍，成本可能只涨一两倍。这种非线性，才是控制层在大规模场景下最实际的意义。

## 八、把 Jev 放进 Agent 的哪一层

它最适合进入 Harness 的控制平面，而不是替代主模型。在工具调用前，它做工具族路由和风险分类；在记忆写入时，它判断类型、保留和关系；在检索过程中，它管预算、候选评分和停止；在输出验收时，它做二元标准初筛；在模型路由上，它判断任务是否需要升级。

这层设计会让 Agent 的成本结构发生变化。强模型调用次数不再等于 Agent 决策次数，大量 routine control 可以被单独观测、训练和优化。系统也因此多了一个新的观测点：可以问"这一步为什么升级""哪类决策最贵""阈值是否漂移"，这些问题在纯 LLM 架构里很难回答。

把 Jev 理解成"更小的 LLM"会错过它的定位。它接管的是一层职责：决定下一步交给谁。这层职责在传统设计里分散在各个条件分支和提示里，现在被集中成一个可测量、可校准的组件。控制平面出现后，系统多了一个可以单独优化的对象，而不是又多了一个模型。

控制平面也改变了团队的分工。过去"路由逻辑"往往散落在业务代码里，谁也说不清全貌；现在它成为一个独立组件，有清晰的输入、输出和指标，可以单独评测、单独迭代。这种"把散落的判断集中起来"的过程，本身就是一次架构上的整理。

未来的 Harness 很可能同时拥有几类模型：强模型负责推理和生成，小模型负责路由与提取，Embedding 模型负责相似性，决策模型负责类型化选择，系统根据风险和置信度在它们之间调度。这要求新增一类组件：决策编排器。它不生成内容，只决定"这一步交给哪层模型、用哪个阈值、是否升级"。

不过多模型系统不天然更便宜。引入 Jev 意味着多一层调用、多一套阈值、多一份运维，只有当被下放的决策量足够大、节省的强模型调用能覆盖这层开销时，它才划算。一个粗略的判断是：如果一个决策每天调用次数很高、结构固定、错误可回退，下放大概率划算；如果调用次数低、每次都不同、错误代价高，保留强模型更合适。

决策编排器至少要维护三类状态：每个动作的当前阈值、每类决策的近期校准、以及升级预算。阈值决定自动化比例，校准决定阈值是否需要调整，预算防止升级失控。把这三类状态集中管理，而不是散落在各处，是多模型系统可维护的关键；否则调一个阈值要翻五个文件，排查一次异常要对三个日志。

从单模型迁移到多模型也不要一步到位。先保留现有强模型决策，同时并行跑 Jev、只记录不执行；积累一段时间后比较两者的选择，找出 Jev 稳定可靠的决策类型；再只对这几类放开自动执行，其余继续走强模型，逐步扩大范围。多模型的价值来自规模化的可靠下放，而不是把所有决策一次交出去。

缓存和批处理也值得考虑。同一类决策往往在短时间内大量重复，缓存判断结果能显著降低成本；多个决策如果可以合并成一次调用（例如一次给一批候选打分），也比逐个调用更省。这些都属于控制层的工程优化，和模型本身无关，但收益常常很可观。

它还有一个隐含前提：上下文足够干净。如果输入里混进了无关内容或错误格式，判别质量会明显下降。所以控制层通常要配一层输入整理，把状态裁成判别需要的形状，而不是把原始上下文整段塞进去。输入的质量，和模型的能力同样重要。

## 九、哪些决策适合交给 Jev

我会从四个条件筛选：输出集合能在执行前完整列出；大量调用具有相同的决策结构；错误可以被后续检查发现或能够安全回退；系统能积累带标签的数据来校准阈值。

适合的例子包括：从有限工具集中路由一个只读查询；判断某条内容属于事实、偏好还是临时状态；给检索候选打相关或不相关标签；判断测试是否满足一条二元标准；在预算耗尽前选择继续、停止或升级。

不适合直接自动执行的例子包括：涉及资金、删除和外发的不可逆动作；候选动作随上下文临时生成；需要引用证据和解释推理链的判断；标签标准本身含糊或持续变化；系统无法观察真实结果、只能用另一个模型打分。这些场景可能仍然可以用 Jev 做初筛，但不能由它直接决定。

选好决策之后，落地要经过几步：先固定一份离线评测集，覆盖每个动作类型；再用它画可靠性图，确定每类的初始阈值；然后线上用灰度流程并行跑 Jev 与现有逻辑，比较它们的选择；最后按错误代价逐步放开自动化比例。这四步的顺序不能乱：跳过离线评测直接上线，会把校准问题带进生产；跳过灰度直接全量，会把相关错误放大到不可控。

评测集要覆盖四类样本：典型的简单样本、边界样本、历史失败样本，以及分布上少见但风险高的样本。只收集简单样本，会让离线指标虚高，上线后遇到边界样本就暴露问题。每条样本要标注正确的动作，以及错误的代价等级；代价等级决定了阈值，同样是不确定，低代价动作可以放宽，高代价动作必须升级。

衡量控制层好坏，也不只看准确率。更完整的指标包括自动化比例、升级率、升级后的净准确率、每千次决策的成本，以及错误在切片上的分布。这些指标一起看，才能判断它是否真的产生了价值：一个自动化比例很高、错误却集中落在高风险切片的控制层，比一个自动化比例中等、错误均匀分散的更危险。

这也提示了一个衡量标准：控制层做得好不好，可以看"强模型调用占全部决策的比例"是否在一个合理区间。比例太高，说明它没起作用；比例太低，说明它可能冒险下放了不该下放的决策。这个比例本身，就是一个值得持续盯的指标。

## 十、端到端案例

用一个具体场景把前面的机制串起来。用户发来消息："我上周买的耳机右边不响了，我想退掉。"

控制层先判断意图和下一步动作候选，Jev 返回的概率可能是退款 0.62、换货 0.21、澄清 0.17。运行时检查这类动作的阈值，退款属于中等风险，阈值设得较高，0.62 低于阈值或命中"需要确认商品状态"的规则，于是升级到强模型或人工确认，而不是直接发起退款。无论最终动作是什么，系统都还要判断这条对话里有没有值得写入长期记忆的信息，这个高频、结构固定的判断适合 Jev。动作执行后，系统再用 Jev 对二元标准做低成本初筛，更复杂的分级判断交给 LLM Judge 或人工。

这个例子里，Jev 做对的关键不是"猜对了动作"，而是"承认自己不确定"。候选里澄清和退款概率接近时，控制层选择升级，把决定权交给更强的判断。控制层的成熟标志，是它在不确定时愿意说"我不确定"；一个永远高置信的快层，比一个会犹豫的快层更危险。

失败模式主要有几类。授权边界误判，通常发生在候选动作在权限边缘、彼此相近时，缓解方式是单独设阈值、高风险动作强制升级；分级标准落后，通常发生在需要细粒度分级时，缓解方式是交给 LLM 或人工；分布漂移，靠持续监控校准和升级率；动作集过大、候选区分度低，靠分层路由或缩小候选集。这些问题有一个共同点：它们不是"模型不够聪明"，而是决策结构和验证方式的问题，换一个更大的模型未必能解决。

把 Jev 放在控制层，还会改变系统的失败形态。原来强模型偶尔判断错误是低频事件，现在 Jev 高频决策，错误可能更规律、更集中；如果某个阈值设错，错误会在短时间内大批出现。所以控制层必须自带熔断和监控：升级率突然上升、某类动作错误率突破阈值、置信度分布整体偏移，都应该触发告警或自动降级。高频决策的收益和风险是成比例的。

上线后至少监控四类指标：各动作的升级率、各动作的错误率、置信度分布的偏移，以及级联的净收益。把监控和阈值联动，才能让控制层自我调整；静态阈值只能应对上线那一刻的分布，动态监控才能跟上真实世界的变化。

还有一类风险要单独提：与普通分类器相比，Jev 多了语义理解能力，也多了对应的风险。它可能对训练分布之外的语言给出看起来合理但错误的概率，而这种错误不容易通过规则拦截。普通分类器的输入是固定特征，异常可以被检测；Jev 的输入是自由文本，异常分布在语义空间里，监控要覆盖语义分布，而不是只看特征范围。

控制层也不是必须一直开着。如果监控显示某类动作的升级率长期偏高、错误率没有改善、维护成本又持续存在，就该考虑把这部分交回强模型或人工。退出的判断和进入一样重要。

从长远看，控制层可能会成为 Agent 架构里一个标准组件。就像今天每个 Web 系统都有鉴权层和日志层一样，未来的 Agent 可能会有一个统一的"决策层"，负责路由、打分、阈值和升级。这个判断不一定对，但它提供了一个有用的视角：把高频的小决策集中管理，比散落在各处更容易做对。

这两个例子合起来说明，控制层的价值不在某一次判断，而在把成百上千次同类判断变成可管理、可度量的对象。单看一次，它只是选了一个动作；看全局，它决定了系统在多大比例上依赖强模型、在哪些地方必须升级、成本结构是否健康。这才是它真正的意义。

一个常见的反对意见是："既然大模型能力在涨、价格在降，等到它足够便宜，控制层就没必要了。"这个判断一半对、一半错。对的部分是，模型确实会越来越便宜、越来越快；错的部分是，判断次数也在同步增长，Agent 越强，能处理的任务越复杂，需要做的决策越多。成本下降和使用量上升会同时发生，控制层的价值不会因为单价下降而消失，就像缓存和索引没有因为内存变便宜而消失一样。

换个角度看，控制层做的事情，是把"智能"按成本重新分配：能便宜做对的事，就用便宜的方式做；只有在真正需要深度时，才动用昂贵的能力。这不是在替代强模型，而是在给它减负，让它把算力用在只有它才能做对的地方。

## 十一、现阶段该怎么用

Jev 最有意思的地方不是速度数字，而是它挑战了一个默认假设：智能软件中的每个语义判断都必须通过文本生成完成。LLM 很适合开放问题，却不是所有控制决策的天然接口；把有界决策单独抽象出来，可以让系统更便宜、更可测、更容易校准。

但要克制。Jev 刚进入公开使用，独立研究还不多，官方关于速度和能力的说法需要更多外部复现，已有论文也显示它在复杂分级、授权边界和相近候选上会遇到限制。它适合成为新的控制层候选，而不是一夜之间替换全部 LLM 调用，也不该被当成包治百病的方案。

如果只给一条建议，我会说：从一个最窄的场景开始，选一个高频、二元、错误可回退的判断，例如"这条检索结果是否相关"，先用 Jev 做初筛，把不确定样本送回现有逻辑。跑一段时间，拿到校准数据和升级率，再决定是否扩大范围。控制层的信任是积累出来的，不是配置出来的，也不是一次调参能得到的。

一个可以按周推进的试点节奏是：第一周确定决策、收集并标注一批线上样本；第二周做离线评测和校准，确定初始阈值；第三周并行跑、只记录不执行，对比它与现有逻辑；第四周对表现稳定的类别放开自动执行，其余保持升级。每一步都有明确的验收点，任何一步达不到，就停下来重新界定场景。

判断一个场景值不值得引入控制层，可以问三个问题：这个判断一天发生多少次？它的输出集合是不是稳定的？做错了会不会造成难以挽回的后果？次数高、集合稳定、后果可控，是三个都指向"值得试"的信号；任一条不满足，就该先解决那条，而不是硬上 Jev。

最后想强调一点：控制层不是越多越好。把每个小判断都抽成一个独立组件，会增加调试和运维的负担。真正值得抽取的，是那些"高频、有界、错误可回退"的判断；其余的判断留在原来的地方，反而更简单。控制层的价值来自集中管理少数关键决策，而不是把系统切得越碎越好。
