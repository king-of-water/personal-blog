Coding Agent 处理陌生仓库时，大量成本花在找代码上。用户问"修改用户角色字段会影响哪些鉴权逻辑"，Agent 需要找到模型定义、权限加载、缓存键、会话序列化、迁移脚本和测试。任何一处遗漏，都可能让最后的修改计划看起来完整，实际却留下回归。

常见 Agent 会边搜边读：列目录，搜索关键词，打开文件，根据正文继续搜索。每次读取都把更多代码送进上下文。读错的文件不会立刻消失，后续调用还会反复处理这些历史。仓库越大，探索的成本越容易超过回答本身。

FastCode 在 2026 年 3 月提出 scouting-first，也就是"先侦察"的代码推理方式。它把 repository exploration 与 content consumption 拆成两个阶段：模型先在轻量的语义结构地图上缩小范围，确认目标后再读取完整实现。研究问题可以压缩成一句话：**如果模型先用符号、签名和关系边寻找证据，最后一次性读取候选正文，能否同时降低上下文成本和漏检率？**

本文的实现描述以 [FastCode 论文 v2](https://arxiv.org/html/2603.01012v2) 和 [官方开源仓库](https://github.com/HKUDS/FastCode) 为主；Aider 与 Sourcegraph 只用于比较相邻方案。论文里的准确率、成本和 Token 节省都是作者在指定数据集、模型与计价方式下的实验结果，不代表任何仓库都能复现。没有公开证据支持的产品内部机制，本文不作推断。

FastCode 改变了上下文的获取顺序：先把探索限制在低成本表示上，再把正文预算留给已经有充分理由的候选。它没有用代码图替代模型，也不只是增加一个向量库。这个设计适合仓库问答、代码定位和影响分析，也适合作为 Coding Agent 的上下文服务。它不能独立证明运行时行为，更不能替代编辑、测试、回滚与权限控制。

## 一、仓库级推理的成本从哪里来

一个仓库级任务通常有三类不确定性：入口在哪，关系怎么扩展，证据是否足够。"登录为什么绕过缓存"没有告诉系统入口函数名；找到登录接口之后，还要追到缓存读取、特性开关和回源条件；最后还要判断当前代码是否足以支持结论。普通文本问答只需要解决最后一步，仓库推理要连续解决三步。

假设用户问：

> 把 `User.role_id` 改成多角色列表，会影响哪些鉴权逻辑？

一个通用 Coding Agent 可能执行下面的路径：

```text
列出目录
  -> 搜索 User / role / permission
  -> 打开模型与几个命中文件
  -> 搜索调用方、序列化和迁移
  -> 打开中间件、缓存与测试
  -> 整理影响范围
```

这条路径能工作，代价来自三个地方。

第一个代价是重复输入。Agent 在第 1 轮读过 `models/user.py`，第 4 轮调用模型时，这段内容通常仍在历史中。一次错误读取会影响后面的每一轮成本。工具结果可以截断，压缩也能减少历史，可它们只能缓解累积，无法让最初的选择更准。

第二个代价是关系缺失。文本相似度容易找到包含 `role` 的文件，却不一定找到 `PermissionCache.make_key()`。后者可能只接收用户 ID 和权限版本，文件里根本没有"角色"这个词。跨文件影响分析依赖调用、导入、继承和状态读写，文本相似只是其中一个信号。

第三个代价是停止困难。在线 Agent 每发现一条新边，都可以继续搜索。继续可能补到关键证据，也可能进入工具类、生成代码或旧实现。没有预算和停止条件时，系统通常在两种错误间摇摆：读得太少，结论缺证据；读得太多，延迟与成本失控。

长上下文也没有消除选择问题。窗口能放下一百万 Token，只说明输入上限变大，不说明整个仓库都值得输入。论文在 LongCodeQA 上观察到，整库输入的成本随上下文规模增长，选择性构造的上下文则保持在更小范围。更重要的是，噪声会与关键代码竞争注意力。"能放下"和"该放什么"仍是两个问题。

因此，仓库推理可以拆成四项工作：

1. 把自然语言问题翻译成代码中的可能入口；
2. 沿程序结构补齐非文本相关的邻居；
3. 在预算内选择足够的正文；
4. 用正文回答、修改并验证。

FastCode 主要重做前三项。第四项仍交给推理模型或上层 Coding Agent。

## 二、最小模型：地图、侦察与正文

理解 FastCode 不需要先记住所有模块。最小模型只有三种对象。

第一种是代码单元。文件、类、函数和文档都可以成为单元。每个单元保存两份信息：用于侦察的轻量元数据，以及用于最终推理的完整正文。轻量信息包括路径、符号名、签名、文档字符串、类型提示和行范围。

第二种是关系边。FastCode 把依赖、继承和调用分别建图。一个候选函数可以沿调用边找到上下游，沿依赖边找到模块关系，沿继承边找到接口实现。图负责补回文本切块丢失的结构。

第三种是侦察状态。系统记录问题复杂度、仓库结构复杂度、已经选择的代码量、当前轮次和模型对证据充分性的自评。策略根据这些状态决定继续搜索、扩展关系、保留候选或停止。

可以把一次查询写成下面的简化过程：

```python
def answer(query, repository, budget):
    map = repository.semantic_structural_map
    intent = augment(query)
    candidates = hybrid_retrieve(map, intent)

    state = init_state(query, repository, candidates, budget)
    while not should_stop(state):
        candidates |= run_structural_tools(map, state)
        candidates |= expand_graph(map, candidates)
        state = assess(candidates, state)

    selected = select_by_priority(candidates, budget)
    context = load_full_bodies(selected)
    return reason(query, context)
```

这段伪代码省略了索引、去重、缓存和异常处理，但保留了设计边界。检索只产生候选，图扩展也不直接加载所有邻居。正文读取发生在候选已经被筛选之后。

论文把最终上下文写成一个带成本惩罚的选择问题：在候选代码集合中，最大化与问题的相关性，同时惩罚计算和 Token 开销。工程系统无法准确知道一段代码的真实证据价值，只能用检索分数、来源、图距离、粒度和模型判断近似。公式的价值在于明确目标：系统追求最小充分上下文，而不是尽可能多地搬运代码。

## 三、FastCode 和普通 Code RAG 的分界

从宽泛定义看，FastCode 属于 Code RAG，因为它从模型外部取回代码，再把代码交给生成模型。只把它叫作"向量检索"会漏掉结构导航和成本策略。

普通 Code RAG 常用以下流程：

```text
代码切块 -> Embedding -> 向量索引 -> Top K -> LLM
```

它处理局部问答很合适。用户知道错误码、函数名或业务术语时，前几条结果往往已经够用。困难发生在答案跨越多个不相似文件时。调用方和被调用方可能没有相同词汇，接口定义与实现的自然语言描述也可能完全不同。固定 Top K 还会强迫不同问题使用相同的上下文规模。

FastCode 加入三种变化。它先按文件、类、函数和文档保留层级，不让固定长度切块破坏符号边界；它组合稀疏与稠密检索，让精确标识符和抽象意图同时参与召回；它在初始候选上沿程序关系扩展，而不是把相似度排序当成最终答案。

| 维度 | 普通 Code RAG | FastCode |
| --- | --- | --- |
| 基本单元 | 固定 Token 块或函数块 | 文件、类、函数、文档的层级单元 |
| 召回信号 | 向量或关键词 | BM25、向量、工具命中、图邻居 |
| 跨文件关系 | 依赖文本共现或二次检索 | 显式调用、依赖、继承图 |
| 上下文规模 | 固定 Top K 居多 | 根据问题和仓库动态分配 |
| 停止条件 | 取完 Top K | 置信度、信息增益、轮次与预算 |
| 适合任务 | 局部查找、快速问答 | 跨文件问答、定位、影响分析 |

这并不表示所有 Code RAG 都是扁平的。很多生产系统已经加入 AST 切块、混合检索、重排和调用图。FastCode 的可辨识特征是把这些组件组织成 scouting-first 流程，并让 Agent 在轻量表示上进行多轮选择。组件本身并不新，新的部分是它们在上下文获取阶段的分工。

## 四、离线阶段：把仓库变成可导航地图

FastCode 查询前要先建立 semantic-structural map。论文把仓库表示为有向图，节点是层级代码单元，边是依赖、继承和调用关系。每个节点既有轻量元数据，也能回到完整代码体。这个双重表示是先侦察后读取的前提。

### 层级代码单元保留程序边界

固定长度切块对散文通常可用，对代码容易切断语义。函数签名在一个块，异常处理落到下一个块；类字段与使用字段的方法被分开；装饰器和被装饰函数也可能不在一起。FastCode 用 AST 抽取 File、Class、Function 与 Documentation 四级单元，并保存行范围，最终可以精确回读对应正文。

层级还允许查询按粒度变化。"支付模块由哪些部分组成"需要文件或类级轮廓；"为什么这里会吞掉异常"需要函数级实现。系统如果只有函数块，架构问题会返回大量碎片；如果只有整文件，定位问题又会浪费预算。

一个索引节点至少要保存下面这些字段：

```json
{
  "unit_id": "auth/middleware.py::AuthorizationMiddleware.resolve_authorities",
  "kind": "function",
  "path": "auth/middleware.py",
  "parent": "AuthorizationMiddleware",
  "signature": "resolve_authorities(user_id, tenant_id) -> list[str]",
  "docstring": "Load effective authorities for a user in one tenant.",
  "line_start": 41,
  "line_end": 88,
  "content_hash": "...",
  "index_commit": "..."
}
```

`content_hash` 和 `index_commit` 虽然不是论文公式的中心，却是生产系统需要的字段。没有版本绑定，系统无法判断回答依据的是当前代码还是旧索引。重命名、移动和删除也必须更新节点与边，否则地图会把 Agent 导向不存在的位置。

### 稀疏与稠密索引负责不同入口

代码查询同时包含标识符和意图。BM25 擅长 `ROLE_ADMIN`、`resolveAuthorities`、错误码与配置键；Embedding 擅长"权限继承"与 `mergeGrantedAuthorities()` 之间的语义对应。FastCode 为层级单元建立稀疏与稠密索引，让两类信号共同产生初始候选。

混合检索需要先处理两套不可直接比较的分数。BM25 分数依赖词频，向量分数依赖距离度量。实际系统需要归一化、Reciprocal Rank Fusion 或训练过的重排器。论文把重点放在整体框架，没有把某一种融合公式描述成普遍最优。落地时应该分别测量召回率、噪声比例和延迟，避免只调整一个综合分数。

### 三层关系图补回非文本邻居

FastCode 用 AST 分析建立三类有向关系：

- 依赖图记录文件或模块的 import 关系；
- 继承图连接基类、接口和具体实现；
- 调用图把函数调用位置连接到定义。

三类边不应混成一种"相关"。依赖边只说明模块可见，调用边更接近执行路径，继承边说明可能的替换关系。影响分析通常更关心反向调用者，理解实现则可能沿正向调用继续读取。边类型、方向与查询意图共同决定扩展顺序。

AST 的优势是轻量，可以覆盖多种语言而不需要完整编译环境。代价是精度有限。重载解析、宏、反射、依赖注入、运行时注册和字符串构造的符号名都可能让静态边缺失。论文明确选择了高效率的 AST 分析，因此不应把生成的图等同于编译器级精确调用图。

地图构建还要过滤噪声。依赖目录、构建产物、压缩文件、生成代码和测试快照可能比业务代码更大。它们进入索引后会占用检索与图扩展预算。忽略规则应当版本化，并允许按任务临时覆盖。例如调查代码生成器时，生成文件通常是噪声；调查序列化兼容性时，它们又可能是证据。

## 五、查询增强：把人话拆成检索线索

Query augmentation 负责衔接业务描述与代码符号。FastCode 先判断查询意图，然后产生两条互补的检索线索。

第一条是语义重写与关键词扩展。系统保留原始问题，同时补充可能的领域术语、类名和 API 候选。"修改角色字段影响鉴权"可以扩展出 `permission`、`authority`、`principal`、`session claims`、`cache invalidation` 等检索词。语义重写服务向量检索，关键词服务 BM25 与正则工具。

第二条是伪代码提示。论文让 LLM 生成可能的骨架实现，包括库调用、控制流或类层次。伪代码只用于暴露潜在结构锚点，不构成答案，也不要求仓库按它实现。例如：

```python
def update_user_roles(user_id, roles):
    user_repo.save_roles(user_id, roles)
    permission_cache.invalidate(user_id)
    session_store.revoke_or_refresh(user_id)
    audit_log.record_role_change(user_id, roles)
```

仓库未必有这些函数名，但骨架提示了四类可能关系：持久化、缓存失效、会话传播和审计。检索器可以寻找相似 API 或调用结构，弥补用户问题没有给出代码词汇的缺陷。

这一招也有风险。模型生成的伪代码会带入常见架构先验，可能把仓库并不存在的 Redis、JWT 或审计模块当成方向。系统必须把它标记为查询假设，只用于扩大召回，不能当成证据。最终答案只允许引用实际代码正文。评测时也要检查查询增强是否制造了稳定偏差，例如总把 Spring 项目解释成某一种权限框架。

## 六、在线阶段：结构侦察怎样推进

初始检索结束后，FastCode 不会立刻把 Top K 正文交给回答模型。它把候选的来源、签名、关系和代码行数整理成轻量列表，让 Agent 决定下一步。

### 工具搜索与检索互相补位

论文描述了两类探索工具：目录遍历，以及返回路径和匹配次数的正则搜索。目录遍历帮助 Agent 识别模块组织，正则搜索处理精确模式。工具结果以路径、符号和计数为主，避免读取整文件。

检索适合"意思相近但名字未知"，工具适合"我要找这个符号所有出现位置"。例如初始向量检索发现 `AuthorizationMiddleware`，Agent 可以随后正则搜索 `role_id` 的读取位置；如果用户直接给出错误码，工具搜索可能比向量召回更可靠。FastCode 把两路候选去重后再进入图扩展。

### 图扩展补齐结构链路

初始命中通常只是入口。系统查询调用、依赖和继承图，把没有文本相似度却有程序关系的节点加入候选。扩展需要限制方向与跳数，否则公共工具函数会迅速把子图扩散到整个仓库。官方 README 把"following code connections"描述为有限深度导航，并给出最多两步的说明；这是一项工程默认值，不是所有仓库的最优深度。

一跳关系适合局部影响，二跳可以看到中间适配层。超过两跳后，候选数量通常快速增长，关系含义也变弱。更稳妥的做法是让任务类型决定方向：

| 任务 | 优先扩展 |
| --- | --- |
| 找实现 | 定义、继承实现、正向调用 |
| 找影响范围 | 反向调用、依赖者、读写相同字段的节点 |
| 查异常来源 | 正向调用、异常转换、外部边界 |
| 理解架构 | 文件依赖、入口模块、公共抽象 |

图扩展还要根据来源筛选候选。下一轮需要知道候选来自 BM25、向量、工具命中还是图邻居，它和已有候选是什么关系，预计要读取多少行。来源会影响可信度，关系会解释为什么保留，代码量则进入成本判断。

### Agent 在元数据上做保留与停止决策

每轮侦察后，模型看到的是候选概况，而不是实现正文。一个候选记录可以长这样：

```json
{
  "unit": "AuthorizationMiddleware.resolve_authorities",
  "provenance": ["dense", "call_graph"],
  "lexical_rank": 8,
  "semantic_rank": 2,
  "relation": "reads User.role_id",
  "signature": "resolve_authorities(user_id, tenant_id) -> list[str]",
  "line_count": 47
}
```

Agent 根据这些概况保留候选、发起新工具调用或结束侦察。元数据如果过薄，模型无法判断相关性；如果塞入长摘要，侦察本身又会变贵。签名、文档字符串、类型、路径、关系和行数构成一个实用起点。具体项目还可以加入所有者、测试覆盖、最近修改时间和运行时热度，但这些字段都要说明来源。

## 七、成本感知策略：何时继续，何时停

FastCode 没有把"少读代码"停留在口号。论文把每轮状态写成五个维度：查询复杂度、仓库熵、累计代码量、迭代深度与认知置信度。它们共同控制预算和停止。

查询复杂度描述任务需要多深的推理。查一个函数定义很简单，重构跨模块权限模型更难。仓库熵是结构复杂度的近似，论文给出的因素包括文件数量与代码深度。两者共同决定初始行数预算，概念上可以写成 `B ∝ query_complexity * repository_entropy`。

累计代码量是硬成本，迭代深度防止无限探索。认知置信度由 Agent 自评当前证据是否足以回答。模型可能对错误候选很自信，所以置信度只能是停止信号之一，不能代替可验证条件。

FastCode 还定义了信息增益率：新增代码量带来了多少置信度提升。如果连续扩展只增加上下文，没有明显提高证据充分性，策略停止；如果预计下一轮会超过剩余预算，也停止。论文允许单轮置信度下降，因为新证据可能推翻旧假设，只有连续低收益才触发终止。

停止条件可以整理成三类：

```text
充分：confidence >= threshold
低效：连续多轮信息增益过低
耗尽：预计新增内容超过剩余预算，或达到最大轮次
```

候选最终按优先级装箱。论文的评分综合相关性、是否由工具显式找到，以及信息密度。工具命中通常比纯模型猜测更可追溯；函数单元比巨大文件密度高。系统按优先级贪心选择，直到达到行数预算，然后才回读完整正文。

这套策略有两个现实问题。第一，代码行数只是 Token 的粗略代理。一行生成代码和一行简单字段的成本不同，不同语言的 Token 密度也不同。生产实现应在行数之外估计实际 Token。第二，自评置信度可能校准不良。可以加入确定性覆盖条件，例如影响分析必须同时找到定义、直接读取者、缓存或序列化路径以及相关测试；缺一项时，即使模型自信也继续搜索或明确声明缺口。

## 八、端到端例子：把单角色改成多角色

继续使用同一个任务，目标是评估把 `User.role_id` 改成 `role_ids` 的影响。仓库假设包含模型、权限中间件、缓存、会话服务、迁移和测试。完成条件是一份可验证的影响清单，说明每个相关文件为什么受影响，以及哪些结论仍需运行时验证。

第一轮做查询增强。语义问题被重写为"用户角色字段从标量变为集合后，权限解析、缓存键、会话声明、持久化迁移与测试如何变化"。关键词加入 `role_id`、`authority`、`permission`、`claims`、`invalidate`、`migration`。伪代码提示产生保存角色、刷新权限和更新会话等结构假设。

第二轮进行混合召回。BM25 精确命中 `models/user.py`、`migration/backfill_user_role.py` 和 `tests/test_user_create.py`；向量召回命中 `AuthorizationMiddleware.resolve_authorities()` 与 `UserSerializer.to_session_claims()`。候选仍然不完整，因为缓存实现可能只出现 `permission_version`。

第三轮做工具与图扩展。正则工具搜索 `role_id` 的读写；反向调用边从权限解析函数找到路由鉴权；依赖边找到会话序列化模块；调用边从角色更新服务追到 `PermissionCache.bump_version()`。候选关系变成：

```text
User.role_id
  |-- RoleRepository.load_role
  |     `-- AuthorizationMiddleware.resolve_authorities
  |            `-- check_route_permission
  |-- UserSerializer.to_session_claims
  |-- AdminUserService.change_role
  |     `-- PermissionCache.bump_version
  `-- migration/backfill_user_role.py
```

第四轮评估缺口。模型已经找到读取、更新、缓存和迁移，但测试候选只覆盖用户创建，没有权限回归。它发起一次面向 `resolve_authorities`、`session claims` 和 `bump_version` 的测试搜索。新增候选提高了覆盖，下一轮预计只会进入通用缓存库，信息增益很低，于是停止。

第五轮按预算加载正文。最终上下文包含模型定义、角色仓储、权限中间件、缓存版本更新、会话序列化、迁移脚本和三组相关测试。系统不加载头像、用户偏好和管理后台列表页，即使它们也引用 `User`。

最后的答案应按影响类型组织，而不是只给文件列表：

- 数据模型与持久化：字段类型、关联表或数组存储、迁移与回填；
- 权限计算：单角色查询改为角色集合合并，重复权限需要去重；
- 缓存：缓存值与失效事件是否包含角色版本；
- 会话：旧 Token 里的单值声明如何兼容，新角色何时生效；
- 测试：多角色并集、撤销角色、缓存失效和旧会话兼容。

这时 FastCode 的工作仍未结束任务。上层 Coding Agent 需要读取完整配置，实施修改，运行测试，并观察是否存在静态图看不到的运行时注册。如果会话服务通过消息队列异步刷新，仓库内调用图可能找不到跨服务消费者，答案必须把它列为待验证项。

## 九、论文结果应该怎样读

FastCode 在 SWE-QA、LongCodeQA、LOC-BENCH 和 GitTaskBench 上分别评估仓库问答、长代码理解、文件定位与端到端仓库任务。四组任务覆盖面较广，但指标、模型和对手不同，不能把它们合成一个"准确率提升"数字。

在 SWE-QA 的三仓库子集上，FastCode 使用 Gemini-3-Flash 得到总分 43.28；Cursor 为 43.17，Claude Code 为 42.08。分项并非全面领先：FastCode 的正确性和推理分数较高，Cursor 的完整性更高，SWEQA-Agent 的清晰度与相关性也不低。这组结果支持"scouting-first 可以竞争"，不支持"所有维度都优于商业工具"。

LongCodeQA 的结果更能说明选择性上下文的作用。论文报告 Claude 3.5 Sonnet 在 256K 子集上，直接输入为 66.6，FastCode 为 78.5；在 64K 上两者都是 69.7。不同长度的收益不稳定，说明结构侦察不是每个问题都必然提高准确率。论文成本表中，可比长度的平均成本下降 83.01%，但这依赖作者的模型价格、调用流程和计费口径。

LOC-BENCH 上，Gemini-3-Flash 版本的 FastCode 报告 Acc@1 86.13%，Qwen3-Coder-30B 为 75.55%，Claude 3.5 Sonnet 为 76.28%。论文声称 Qwen 版本以很低成本保留了接近最佳基线的定位能力。这里测的是文件级定位，不等于能生成正确补丁。

GitTaskBench 才接近完整任务。论文报告 FastCode 使用 Claude 3.7 Sonnet 时 ECR 为 74.07%、TPR 为 57.41%；使用 Gemini-3-Flash 时分别为 68.52% 和 53.70%。同表中的 OpenHands Claude 3.7 为 72.22% 与 48.15%。成本差异很大，但框架能力、工具配置与模型调用方式也不同。商业工具使用默认模式，社区基线与 FastCode 的模型设置并不完全对称，比较时应保留这一边界。

消融实验比"节省十倍 Token"更有设计价值。在 SWE-QA 三仓库子集、Qwen3-Coder-30B-A3B 上，移除混合检索、图扩展或成本管理分别带来约 0.60%、0.83% 和 0.92% 的下降；同时移除导航与成本管理下降 5.06%，保留查询增强但移除工具侦察与成本管理下降 4.31%。单个索引或单张图不是主要来源，完整导航流程的组合更重要。

README 的"最高准确率"、"最多节省 90% Token"和相对产品的速度数字属于项目方陈述。采用前应回到论文表格，确认比较对象、模型、任务和成本口径，再在自己的仓库复测。

## 十、与 Repo Map、代码图和在线 Agent 搜索比较

FastCode 附近有几条容易混淆的技术路线。它们都在帮助模型选择代码，但产物和使用时机不同。

![普通代码 RAG、Repo Map、FastCode 与在线 Agent 搜索的差异](/images/posts/fastcode-strategy-comparison.svg)

| 方案 | 主要产物 | 选择发生在哪里 | 适合的任务 |
| --- | --- | --- | --- |
| 普通 Code RAG | Top K 代码块 | 检索器排序 | 局部问答、明确关键词查找 |
| Aider Repo Map | 预算内的仓库符号地图 | 图排名与渲染阶段 | 给编辑模型持续提供全局轮廓 |
| Sourcegraph Code Graph | 定义、引用、符号与精确导航数据 | 搜索和代码导航查询 | 企业代码搜索、多仓库导航 |
| 在线 Coding Agent | 工具调用历史与已读文件 | Agent 每轮决策 | 编辑、执行、测试、修复闭环 |
| FastCode | 针对问题的最小充分上下文 | 轻量侦察与成本策略 | 仓库问答、定位、影响分析 |

Aider 的 [Repo Map 实现](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py) 用 Tree-sitter 抽取定义与引用，通过图排序选择重要符号，再在 Token 预算内渲染。它倾向于提供一份持续可见的全局轮廓。FastCode 会针对当前问题主动检索、调用工具和扩展关系，最后生成专用上下文。二者可以组合：Repo Map 给初始方向，scouting 针对问题继续缩小范围。

Sourcegraph 的 [Code Graph](https://sourcegraph.com/docs/cody/core-concepts/code-graph) 依赖索引器产生定义、引用、符号和文档注释等代码智能数据，强项是精确导航与多仓库基础设施。FastCode 采用更轻的 AST 路线，并把查询增强与成本管理放在框架中心。组织已经有 Sourcegraph 时，没有必要为了 scouting-first 重建所有索引；可以复用精确代码图，把 FastCode 式策略放到上层选择器。

在线 Coding Agent 能根据新证据随时改方向，还能编辑文件、运行测试和处理失败。FastCode 把昂贵的全文读取推迟，先完成一次集中侦察。二者可以放在同一套架构里：FastCode 充当上下文工具，上层 Agent 负责执行闭环；当预构建地图置信度不足时，再退回在线搜索。

## 十一、怎样接入 Coding Agent

官方仓库提供 Web、CLI、REST API 和 MCP Server。MCP 暴露加载仓库、查询、列出仓库、查看状态和管理会话等工具，因此 Cursor、Claude Code 或其他支持 MCP 的宿主可以把 FastCode 当作外部代码理解服务。

一个最小接入不应只返回自然语言答案。为了让上层 Agent 验证，工具结果最好包含证据清单与索引版本：

```json
{
  "answer": "权限在登录后由 AuthorizationMiddleware 解析……",
  "index_commit": "a19f0d2",
  "evidence": [
    {
      "path": "auth/middleware.py",
      "symbol": "AuthorizationMiddleware.resolve_authorities",
      "lines": [41, 88],
      "reason": "reads User.role_id"
    }
  ],
  "coverage_gaps": [
    "cross-service session refresh is not represented in this repository"
  ],
  "token_usage": {
    "scouting": 3120,
    "content": 6840,
    "answer": 910
  }
}
```

官方 API 当前返回答案与总 Token 等信息；上面的结构是面向生产接入的建议，不是对现有接口的逐字段复述。证据、版本和缺口让上层 Agent 能决定是否继续读取，也让审计人员知道结论从哪里来。

接入链路可以分成四层：

1. 仓库同步层负责 clone、分支与 commit 固定；
2. FastCode 负责索引、侦察和候选上下文；
3. Coding Agent 负责计划、编辑和工具调用；
4. 测试、静态检查与人工审查负责验收。

多仓库场景还需要仓库路由。FastCode 支持同时加载与查询多个仓库，但跨仓库调用通常没有统一符号边。服务 A 发布事件，服务 B 用字符串主题订阅，静态图很难自动连接。可以从 API schema、消息主题、构建依赖和服务目录补充跨仓库边，同时把每条边的来源与可信度保留下来。

权限过滤必须在候选产生前执行。不能先让全局索引召回私有仓库，再在最终答案里删掉文件名。向量库、BM25、关系图、缓存、会话历史和日志都要继承同一套访问控制。对企业代码而言，索引本身就是敏感资产。

## 十二、失败模式与适用边界

### 静态结构看不到完整运行时

Spring 依赖注入、Python 插件注册、前端事件总线、反射、宏、配置路由与消息队列都会让真实调用关系偏离 AST 图。静态图可以缩小范围，无法证明一条路径在线上必然发生。涉及性能、故障和真实流量时，应结合 Trace、日志、覆盖率或可重复测试。

### 查询增强会制造先验偏差

伪代码提示来自模型的常见模式。它可能把不存在的缓存层或会话系统带入检索，导致候选围绕错误架构聚集。缓解办法是保留原始查询、限制扩展词权重、记录每个候选的来源，并对"只有伪代码相似、没有实际结构关系"的结果降权。

### 图扩展会经过高连接枢纽

日志、配置、序列化、基础异常和通用工具常被大量模块引用。无约束地扩展这些节点，会让两跳搜索接近整仓库。系统需要按边类型、方向、节点度数和任务意图裁剪。高连接节点可以保留摘要，但不应自动把所有邻居装入候选。

### 索引过期会产生很像真的错误

旧索引比没有索引更危险。Agent 会引用已经删除的函数，沿旧调用边解释当前行为。增量更新必须处理新增、修改、移动和删除；回答返回 commit；索引与工作树不一致时应拒绝给出确定结论，或者先刷新受影响文件。

### 成本策略可能过早停止

自评置信度高不代表证据完整。简单命中一个权限中间件后，模型可能忽略异步缓存失效和旧会话兼容。对高风险任务要使用覆盖模板和最小证据集合，而不是只看模型分数。安全、支付、权限与数据迁移尤其需要强制读取测试和配置。

### 小仓库与明确查找未必需要它

几十个文件的小项目，`rg` 加两次文件读取可能比建立向量、图与策略更快。用户已经给出精确路径和符号时，直接读取也更简单。FastCode 的收益随仓库规模、跨文件关系和问题模糊度增长。离线索引、存储与更新成本必须计入总账。

## 十三、怎样在自己的仓库验证

采用 FastCode 前，先从真实开发记录抽取一批任务。不要只挑"鉴权在哪里"这种容易问答，还要包含影响分析、跨模块链路、答案不存在、动态调用和索引刚变更等样本。每条任务记录参考文件、关键符号、必要关系和允许的不确定项。

评测至少分四层。

第一层测入口召回：参考文件和符号是否进入初始候选。它能诊断查询增强、BM25 与向量索引。第二层测结构覆盖：沿图扩展后，必要调用方、实现类和依赖是否齐全。第三层测上下文选择：最终正文是否覆盖证据，无关内容占比多少。第四层测任务结果：问答是否有依据，定位是否准确，补丁是否通过测试。

可以记录下面的指标：

| 层级 | 指标 | 失败说明 |
| --- | --- | --- |
| 初始召回 | File/Symbol Recall@K | 查询翻译或索引漏掉入口 |
| 图扩展 | 必要关系覆盖率 | 边缺失、方向或跳数错误 |
| 上下文 | 证据覆盖率、噪声率、正文 Token | 选择策略失衡 |
| 回答 | 引用准确率、支持率、拒答正确率 | 生成未受证据约束 |
| 修改 | 定位准确率、测试通过率、人工接受率 | 上下文未转化成正确行动 |
| 成本 | 预处理时间、查询延迟、总 Token、模型费用 | 节省只发生在某一阶段 |

对比实验要固定模型、温度、最大轮次和价格版本。至少比较四个基线：直接长上下文、BM25 或向量 RAG、通用 Agent 在线搜索、FastCode 式侦察。把离线索引摊销到预计查询量；一次性仓库若只问一个问题，索引成本不能假装为零。

还要专门做消融。关闭图扩展，可以看结构边的实际贡献；关闭查询增强，可以看伪代码与扩展词是否有效；固定上下文预算，可以看动态策略是否比固定 Top K 更好；把自评置信度换成覆盖规则，可以检查模型校准。生产环境只需要保留在当前仓库上有效的层次。

一次评测的失败应能归因到具体阶段：入口没召回，图没连上，预算裁错，正文理解错，还是验证不足。只有端到端通过率无法回答该修哪里。把探索过程表示为候选、关系与成本决策后，这些阶段才能分别观察。

## 十四、从原型到生产的采纳顺序

第一阶段只做层级切块与混合检索，返回文件、符号和行范围。先确认查询集与基础召回质量，避免一开始就把图、Agent 和多仓库权限同时引入。

第二阶段加入一类最可靠的关系。静态语言可以先做调用与定义引用，动态语言可以先做 import 和继承。用影响分析任务验证关系扩展确实补到了纯检索漏掉的文件。

第三阶段把正文选择显式化。为每个候选记录来源、关系、预计 Token 与保留理由，设置硬预算和最大轮次。此时即使不用 LLM 自评置信度，也能先靠覆盖规则与增益阈值获得稳定行为。

第四阶段接入上层 Coding Agent。上下文服务只负责提供证据，上层负责读当前工作树、编辑、运行测试和报告差异。把索引 commit、工具执行 commit 与最终补丁基线对齐，避免在变化中的分支上混用证据。

第五阶段再处理多仓库、权限、缓存与增量更新。这些能力改变系统的信任边界，应该在单仓库正确性和可观测性已经稳定之后加入。每扩一层，都要补相应的越权、过期和删除测试。

团队可以用一张决策表判断是否值得建设：

| 条件 | 建议 |
| --- | --- |
| 小仓库、查询少、路径明确 | 直接搜索与读取 |
| 中型仓库、局部问答为主 | AST 切块加混合 RAG |
| 大仓库、跨文件定位频繁 | 加入关系图与 scouting |
| 需要编辑、执行和测试 | 将 scouting 作为 Coding Agent 的上下文层 |
| 动态调用占比很高 | 静态地图结合 Trace、日志与测试 |
| 多仓库且权限复杂 | 先解决版本与 ACL，再扩大检索范围 |

## 十五、我对 scouting-first 的判断

FastCode 提出了一个可操作的分层：结构信息用来选择，完整正文用来推理，运行结果用来验证。三层信息的成本和可信度不同，不应一起塞进同一段工具历史。它也没有保证"用更少 Token 获得更高准确率"，地图质量和停止策略仍会决定结果。

这个分层也解释了它与 Repo Map、Code Graph 和 Coding Agent 的关系。Repo Map 提供压缩轮廓，Code Graph 提供精确关系，FastCode 式策略负责针对问题选择，上层 Agent 负责行动。一个成熟系统可以同时使用它们，没有必要让某个组件承担全部职责。

论文把上下文获取变成了可观察的决策过程。候选从哪里来，为什么沿这条边扩展，正文预算花在哪，什么条件触发停止，都可以记录和评测。任务失败时，团队能定位是搜索、结构、预算还是生成出了问题。

scouting-first 也有清楚的边界。地图过期、动态关系缺失或模型过早自信时，它会高效地走向错误答案。让最终结论回到源码、测试和运行证据，才能把"少读代码"变成可靠的工程收益。
