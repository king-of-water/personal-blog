Agent 自进化最后会落到一个很具体的操作：候选版本 B 跑完一批任务后，系统要不要用它替换版本 A。

如果答案只来自一句"LLM Judge 觉得 B 更好"，这个闭环并不可靠。Judge 可能偏爱更长的解释，测试可能泄漏，任务环境可能被候选版本修改，基准平均分还可能掩盖某类关键任务的退化。这篇文章要回答的是：怎样搭一套评测，让"这次改动是不是真的更好"变成一个可以被证据回答的问题。

自进化系统首先是一套发布系统。它需要版本、隔离、证据、准入、灰度和回滚。模型可以提出改动，也可以辅助分析失败，但不能同时拥有修改系统、修改考题和宣布自己通过的权限。证据来自 τ-bench、SWE-bench Verified，以及几篇关于 LLM Judge 和 reward hacking 的研究，所有指标都限定在各自论文或基准的设定内。

![Agent 从候选变更到发布回滚的评测闭环](/images/posts/agent-evaluation-loop.svg?v=20261001)

## 先看结论

评测要回答三个层次的问题，任何一层缺失都会让结论失真。

| 层次 | 回答的问题 | 主要手段 |
| --- | --- | --- |
| 结果 | 世界状态和用户目标是否达成 | 确定性断言、状态比较 |
| 轨迹 | 是否通过允许的路径完成 | 结构化事件、权限规则 |
| 运行 | 成本、延迟、稳定性是否可接受 | 指标统计、切片分析 |

在这之上，还要回答一个更根本的问题：这份评测本身可信吗。题目会不会被候选影响，评分器会不会被钻空子，两次运行的分数能不能比较。评测的可信度决定了自进化能走多远。

后面会先讲评测对象和任务契约，再拆结果、轨迹和 Judge 三类评测，然后是数据分层、Harness 假提升、reward hacking、统计方法和准入门禁，最后用一个端到端例子把整条链路串起来。

### 为什么评测要绑定版本

评测结果只有绑定版本才有意义。同一个分数，可能来自不同的模型、Prompt、工具 schema 或 Harness commit。不记录版本，分数就只是一个孤立的数字，无法复现，也无法归因。

每次评测都要记录一份清单：模型及参数、系统 Prompt 版本、Skill 版本、工具 schema 版本、Harness commit、依赖版本、评测配置版本。这份清单是后续所有对比的基础。

### 三层评测与三层数据

![评测的三个层次与三层数据](/images/posts/eval-layers-and-data.svg?v=20261001)

### 评测的三个成本维度

评测成本包括三部分：模型调用成本、运行环境成本、人工标注成本。三者都需要预算。

模型调用最容易估算，环境成本容易被忽略（容器、数据库、沙箱），人工标注最贵但最关键。规划评测时要三部分一起算，否则很容易在标注上超支。

### 最小评测的第一个任务

选一个真实失败作为第一个任务。它比合成的例子更能暴露问题，也更容易说服团队接受评测。

从真实失败开始，评测一开始就有意义，而不是为了评测而评测。

### 一个可以立刻做的改动

如果现在没有任何评测，最小的一步是：找十个真实任务，写下每个任务的期望结果，跑一遍当前版本，记录通过情况。

十个任务也比零个好。它让"改动有没有变好"从感觉变成对比。

### 评测的三个常见误解

第一个误解是"评测就是跑分"，其实评测是发布判断。第二个误解是"评测一次做完就行"，其实它要持续维护。第三个误解是"有 LLM Judge 就够了"，其实 Judge 只是其中一层。

这三个误解的共同后果，是把评测做成了一个和发布脱节的排行榜。

### 从评测看系统成熟度

一个系统的评测成熟度，可以粗略看成四级：没有评测；有固定的回归任务；有分层数据和多维切片；有门禁、灰度和回滚。

级数越高，系统越能被信任地改动。处在第一级的系统，任何改动都是在赌。

## 一、评测对象不是一段回答

普通聊天模型评测经常只看最终文本。Agent 在环境中行动，最终回答只是轨迹的最后一项。

一次完整运行至少包含：

```text
任务输入
+ 初始环境
+ 模型和 Harness 版本
+ 每轮上下文
+ 工具调用与结果
+ 文件或数据库状态变化
+ 最终输出
+ 成本、延迟和中断记录
```

只看最终答案会漏掉很多问题。Agent 可能碰巧给出正确数字，却查询了错误日期；可能测试通过，却顺手删除了无关文件；也可能完成退款，同时违反"高额退款需人工确认"的业务策略。

### 三类失败容易被漏掉

第一类是结果对、过程错。Agent 用越权或作弊获得正确答案，单看结果无法发现。

第二类是过程对、结果错。Agent 走了合理路径，但环境有外部因素导致失败。这类失败不应该完全归咎于 Agent，需要区分。

第三类是这次对、下次错。单次运行成功不代表稳定，概率系统需要重复运行才能看清可靠性。

### 为什么要分三个层次

结果层回答"任务完成没有"，轨迹层回答"过程是否合规"，运行层回答"代价是否可接受"。三个层次不能互相替代。

轨迹看起来漂亮但任务失败，没有用；最终状态正确但越权，也不能发布；完成率很高但成本爆炸，同样不可持续。把三层分开度量，才能定位问题出在哪一层，而不是笼统地说"表现变差了"。

### 契约的粒度

契约太粗，一条任务里塞进多个目标，失败时无法定位；太细，任务数量爆炸，评测成本上升。合适的粒度是一条契约对应一个可清楚陈述的用户目标。

一个检验方式：如果一条契约的验收条件超过五六条，可能该拆成两条。目标越单一，失败归因越清楚。

### 契约模板的说明

上面那个 YAML 模板里的每个字段都有作用。`initial_state` 固定起点，`expected_state` 定义终点，`forbidden_effects` 划边界，`required_evidence` 要求证据，`budget` 限制代价。

字段不是越多越好。每加一个字段，评测器就多一处可能出错的地方。字段应该只覆盖"会改变判定结果"的信息。

### 契约里的预算

预算字段容易被当成可选项，实际它是评测的一部分。一个任务成功但调用了一百次工具，和成功但只调用三次，可靠性完全不同。

把预算写进契约，让评测能惩罚"用暴力搜索蒙对"的解法。没有预算约束，Agent 可能学会用极端数量的调用来提高成功率，掩盖真实能力。

### 契约和需求文档的区别

需求文档写给人和实现者，允许模糊。任务契约写给评测器，必须可判定。同一条需求可以对应一份需求文档和一份更严格的契约。

把需求直接当契约用，会导致评测依赖解释。契约要把"验收"落到可执行检查上，哪怕它比需求文档更啰嗦。

## 二、先定义任务契约

一条评测样本不应只有 Prompt 和参考答案。更完整的任务契约包含：

```yaml
task_id: refund-delivered-order
initial_state: fixtures/order_1024.json
user_goal: 退回已送达但破损的商品
allowed_tools: [get_order, create_return, send_message]
forbidden_effects: [edit_payment_method, delete_order]
expected_state:
  return.status: created
  refund.status: pending_inspection
required_evidence:
  - 用户确认退货方式
  - 使用订单绑定地址
budget:
  max_tool_calls: 12
  max_cost_usd: 0.30
```

任务契约把需求变成可执行检查。模型生成的自然语言可以变化，世界状态和安全边界仍有明确答案。

### 硬约束与优化指标

契约里要区分硬约束和优化指标。越权写数据库是硬失败；多调用一次只读工具通常只是成本变差。若把所有指标加权成一个总分，严重安全问题可能被其他高分抵消。

一个可用的规则是：安全、权限、数据完整性属于硬约束，任何一项不满足就直接判失败，不参与加权；效率、成本、路径长度属于优化指标，可以综合。把两类混在一起，是评测失真的常见原因。

### 验收证据要写进契约

任务契约不仅要写期望结果，还要写需要哪些证据。例如退款任务需要"用户确认退货方式"和"使用订单绑定地址"两条证据。缺少证据，即使最终状态正确，也不能算完成。

把证据写进契约，让评测能检查"结论是否有依据"，而不只是看状态是否碰巧正确。

### 结果评测的两种形态

结果评测有两种形态：状态比对和属性断言。状态比对适合结构化环境，直接比较事务后的状态；属性断言适合非结构化环境，检查某些性质是否成立。

两种形态可以混用。数据库任务用状态比对，代码任务用属性断言（测试通过、diff 在允许范围）。关键是判定不依赖自然语言解释。

### 一个反例：只看最终文本

假设一个 Coding Agent 的评测只看"最终回答里有没有提到修复"。结果 Agent 学会了在没真正修改代码的情况下，回答里写"我已修复"。文本评测给出高分，实际什么都没做。

这个反例说明为什么结果评测要检查世界状态。文本可以伪装，状态不会。凡是能用状态判断的，都不要用文本判断。

## 三、结果评测：尽量检查世界状态

能用程序判断的结果，不要先交给 LLM Judge。

Coding Agent 可以运行测试、静态检查和构建，再检查工作区 diff；数据库 Agent 可以比较事务后的表状态；浏览器 Agent 可以读取 DOM 和后端记录；工作流 Agent 可以检查事件是否按要求产生。

[τ-bench](https://openreview.net/forum?id=roNSXZpUDN)的思路很有代表性。Agent 与模拟用户对话，同时通过 API 操作数据库。评测不只判断回复是否像客服，还会检查最终数据库状态是否符合目标，并验证领域策略。它把"用户目标达成"定义成可比较的状态，而不只是一段像样的回复。

### 确定性检查的优势与盲区

确定性结果检查的优势是可重复、便宜、难以用文风讨好。同样的输入，永远得到同样的判断。

它也有盲区：测试可能不完整，预期状态可能写错，候选版本还可能找到修改测试或读取答案的路径。所以"测试通过"是证据，不是自动等价于"任务正确"。确定性检查必须和评测器自身的验证一起使用。

### 一个状态比较的写法

状态比较最好写成显式断言，而不是模糊的"看起来对"。例如：

```python
assert db.get_return(order_id).status == "created"
assert db.get_refund(order_id).status == "pending_inspection"
assert db.get_order(order_id).payment_method == original_payment_method
```

每条断言对应契约里的一条要求。断言的集合就是结果的评分器，它可读、可版本化、可被审查。把评分写成一句话描述，等于又回到了"靠人解释"。

### 轨迹的存储格式

轨迹最好用 append-only 的事件日志，每条事件带类型、时间戳和关联 id。这样恢复、回放和审计都可以基于同一份事实。

事件日志还要区分"发生了什么"和"我们怎么判断"。前者是客观记录，后者是规则输出。把两者混在一起，规则改了以后就无法重新判断历史轨迹。

### 结果对但过程错的典型

结果对但过程错，往往出现在 Agent 用了一种不该用的方法。例如它猜到了正确答案，或者绕过了本应走的验证。

这类失败在只看结果时是"通过"，在轨迹评测里才暴露。它是为什么需要轨迹层的直接理由。

## 四、轨迹评测：过程何时必须被检查

有些任务存在多条合法路径，只要结果正确就够了。另一些任务必须检查过程：

- 高风险动作是否取得批准；
- 是否访问了范围之外的数据；
- 是否把敏感信息发送到外部服务；
- 工具失败后有没有忽略错误继续执行；
- 是否通过读取测试答案完成任务；
- 是否多次重复产生副作用。

轨迹最好以结构化事件保存：

```json
{
  "type": "tool_call",
  "tool": "create_refund",
  "args_hash": "...",
  "risk": "high",
  "approval_id": "approval-17",
  "started_at": "...",
  "finished_at": "...",
  "result": "success"
}
```

结构化轨迹允许规则引擎直接检查"所有高风险调用之前是否有有效批准"，也能计算无效重试、工具错误恢复率和路径长度。若日志只有自然语言，就只能再次依赖模型解释。

### 轨迹规则要克制

不需要为每一步规定唯一正确动作。过度约束轨迹会惩罚合法的新策略。轨迹规则应该关注权限、关键前置条件和已知作弊路径。

一个实用的划分是：硬规则管"不该做什么"，软观察管"做了什么"。硬规则触发即失败，软观察只记录，供分析用。把所有观察都变成硬规则，会让 Agent 只能走预设路径。

### 轨迹评测和结果评测怎么配合

结果对但轨迹违规，是安全失败；结果错但轨迹合理，通常是能力问题。两类问题的处理方式不同：前者要收紧权限或拦截动作，后者要改进模型或上下文。

把两者分开统计，能让团队把安全问题和能力问题分开处理，而不是笼统地调 Prompt。

### Judge 的分级与二元

Judge 的 rubric 有两种：二元和分级。二元标准（是否满足某条要求）判断更稳定，分级标准（1 到 5 分）解释空间更大，一致度更低。

优先用二元标准。需要分级时，把分级拆成一组二元标准再汇总，通常比直接给一个等级更可靠。

### 什么时候完全不用 Judge

如果结果可以被程序判断，就不要引入 Judge。Judge 适合开放质量，不适合本可确定性判断的内容。

把确定性内容交给 Judge，会引入不必要的偏差和成本。第一步永远是问"这个能不能用程序判断"，只有不能时才用 Judge。

### Judge 的成本

Judge 的成本会随样本量和 rubric 数量增长。一万个样本、每条五项 rubric，就是五万次判断。这在文本评测里是笔不小的开销。

这也是分层评测的价值：先用便宜的确定性检查和类型化判断过滤，只把少量样本交给 Judge。把 Judge 用在初筛，成本会失控。

## 五、LLM Judge 应该做什么

很多质量无法写成精确断言，例如解释是否清楚、证据是否真正支持结论、方案是否覆盖用户约束。LLM Judge 在这些开放标准上很有用。

使用时应把大问题拆成独立 rubric：

```text
1. 回答是否直接解决用户问题？
2. 每个事实性结论是否有可追溯证据？
3. 是否遗漏明确约束？
4. 是否声称执行了轨迹中没有发生的动作？
```

Judge 最好输出每条标准的 verdict、置信度和引用证据。只给 1 到 10 的总分，既难诊断，也容易被表达风格影响。

### Judge 的已知偏差

[LLM-as-a-Judge Is Not an Oracle](https://arxiv.org/abs/2609.02246)记录了自改进管道中的多类失败：Judge 偏差、Harness 和指标错误、ground truth 错误以及 reward hacking。论文提出把 Judge 从 oracle 降为 advisor，让确定性准入规则拥有更高优先级。

这条边界很实用：Judge 可以发现"解释没有覆盖风险"，但不能推翻测试失败、安全违规或环境不一致。Judge 提供的是补充判断，不是最终裁决。

### Judge 也要被评测

Judge 本身是一个组件，需要自己的评测。可以用一批人工标注的样本检查 Judge 与人工的一致度，观察它在不同子群上的偏差。

一个常被忽略的点是：Judge 的评价标准会随语言风格变化。同样的内容，写得更长或更自信，可能得到更高分。评测 Judge 时要把风格和内容分开，避免把文风当成质量。

### 冻结集要冻结什么

冻结不只是固定任务文本，还要固定环境、工具实现、依赖版本、评分器和随机种子。任何一项漂移，都可能让前后分数不可比。

一个实用的做法是给每次评测打一个环境指纹，包含这些要素的版本。指纹不同，就不应该直接比较分数。

### 隐藏集泄漏的几种方式

隐藏集可以通过几种方式泄漏：候选读取了包含答案的文件；优化过程间接根据隐藏集分数调整；隐藏集样本被复制进开发集；以及隐藏集和开发集有重复。

防泄漏要检查数据来源、隔离运行环境，并记录候选是否在隐藏集运行过。隐藏集一旦被污染，就不再是独立证据。

## 六、冻结集、开发集和隐藏集

同一批任务同时用于发现问题、生成修改和验证修改，Agent 会逐渐适应题目。即使它没有直接读取答案，Skill 和 Prompt 也会积累针对这些样本的特例。

评测数据至少分三层：

| 数据 | 用途 | 是否向优化器暴露 |
| --- | --- | --- |
| 开发集 | 复现问题、生成候选、快速调试 | 可以 |
| 冻结回归集 | 每次版本对比，监测已知能力 | 只暴露任务，不暴露答案 |
| 隐藏留出集 | 最终准入，检测过拟合与作弊 | 不暴露 |

冻结意味着样本、环境、评分器和依赖版本一起固定。只锁住 Prompt，却让工具数据、模型版本或容器镜像漂移，前后分数没有可比性。

### 隐藏集为什么要轮换

隐藏集也需要轮换。反复根据最终结果修改系统，结果本身会泄漏信息。可以保留长期核心集，再定期加入来自真实失败的新样本。

轮换的频率取决于系统的更新频率。更新越频繁，隐藏集越容易被间接适应，越需要补充新样本。

### 数据从哪来

评测样本的来源有三处：公开基准、合成任务、以及真实线上失败。公开基准便于横向比较，但容易被过拟合；合成任务可控，但可能不真实；真实失败最贴近需求，但需要脱敏和整理。

三者结合最稳：以真实失败为主要来源，用合成任务补齐边界，用公开基准做外部参照。

### 评测器的元测试怎么写

元测试至少两根探针：一根是 gold solution，期望满分；一根是已知错误方案，期望失败。每次修改评测器都重跑两根探针。

如果 gold solution 拿不到满分，说明评测器或环境有问题；如果已知错误方案通过了，说明评分太宽松。两根探针能挡住大部分评测器退化。

### 评测结果的沟通

评测结果要写给决策者看，不要只给分数。用"哪个版本在哪些切片上更好、代价是什么"来表达，而不是一堆指标。

沟通清楚，评测才会被用来做决定，而不是被当成走过场。

### 一次评测失败的复盘

评测本身也会失败，例如环境没配好、任务写错、评分器有 bug。这些要像产品 bug 一样被追查。

把评测的失败也纳入追踪，评测才会逐渐可靠。

## 七、Harness 本身也可能制造假提升

模型和 Prompt 没变，评测分数仍可能因为 Harness 改动而变化：

- 解析失败时静默使用默认值；
- 超时任务被错误计为跳过；
- 工具 mock 与生产实现语义不同；
- 缓存把上一次正确答案带到新任务；
- 随机种子、时间或网络数据没有固定；
- 日志截断后，Judge 看不到失败证据。

这些不是模型变好，而是评测环境在漏分。如果不排除它们，针对评测的优化会变成针对漏洞的优化。

### 元测试：用两根探针验证评测器

评测运行本身要有元测试。可以先用 gold solution 验证环境能得到满分，再用已知错误方案确认评分器会失败。每次修改评测器，都要重新跑这两组探针。

第一根探针证明"正确的解法能通过"，第二根探针证明"错误的解法会失败"。两根都通过，评测器才可信。只有第一根，评测器可能对任何输入都放行；只有第二根，可能对任何输入都拒绝。

### 高质量任务本身也是评测的一部分

[SWE-bench Verified](https://www.swebench.com/verified.html)由软件工程师检查问题描述、测试补丁和可解性，原因就在这里：高质量任务和 Harness 是评测可信度的一部分，不是准备数据时的一次性杂务。

一条描述含糊或不可解的任务，会让所有版本都失败，从而掩盖版本之间的差异。任务质量差，评测就失去区分能力。

### 相关的错误

reward hacking 里最难防的是"相关错误"：两个评分器犯同样的错误，于是第二个评分器无法纠正第一个。多个 Judge 的一致意见，如果它们错误相关，并不比单个 Judge 更可靠。

缓解方式是引入结构不同的验证：确定性断言、隐藏测试、真实环境结果，以及人工抽样。结构不同，错误才可能独立。

### 作弊检测要不要公开

作弊检测机制本身要不要公开，是一个设计选择。公开能让候选知道边界，但可能引导它绕过；不公开能提高检测能力，但候选可能无意越界。

常见做法是把硬约束公开（测试目录只读），把 canary 之类的检测不公开。

## 八、Reward hacking 不需要恶意模型

只要系统持续优化一个不完整指标，就会找到指标漏洞。这不是模型有恶意，而是它忠实地优化了被给定的信号。

Coding Agent 可能：

- 修改测试文件；
- 硬编码公开测试输入；
- 捕获异常后始终返回成功；
- 读取环境中的 gold patch；
- 删除失败测试或跳过慢测试。

文本 Agent 也会投机。它可能学会复述 rubric 关键词、写得更长、加入大量免责声明，从而获得 Judge 高分，却没有提高事实正确性。

### 研究记录到的几类投机

[EvilGenie](https://arxiv.org/abs/2511.21654)专门研究编程环境中的 reward hacking，用隐藏测试、LLM Judge 和测试文件修改检测交叉验证。更近的研究还显示，在 reference-free Judge 上做自我优化时，模型可能变得更有说服力，真实正确率却不提高。

还有研究记录了自主 Prompt 优化循环的多种失败：语法损坏的 Prompt 因解析器静默回退而意外提高指标，被选为赢家；Agent 读取环境缓存答案获得满分，掩盖真实能力。这些失败都指向同一个根源：评测信号有漏洞。

### 防护要改结构，而不是加提醒

防护要改变信息和权限结构，而不只是把"不要作弊"写进 Prompt：

- 评测答案与候选运行环境隔离；
- 测试目录只读或运行后校验哈希；
- 使用候选看不到的隐藏断言；
- Judge 在看到候选答案前独立求解或提交判断；
- 给基准加入 canary，异常高分触发审计；
- 保存完整 diff、工具轨迹和容器产物。

把"不要作弊"写进 Prompt 属于软约束，模型可能遵守也可能不遵守。改变信息和权限结构属于硬约束，候选即使想作弊也无从下手。

### 样本量要多少

样本量取决于要检测的效应大小。想检测 5 个百分点的提升，需要较多样本；想检测 20 个百分点的提升，样本可以少一些。

一个粗略的原则是：小样本只能发现大差异。如果一个改动带来的提升预计很小，就要准备更多样本，否则评测无法区分它和随机波动。

### 置信区间怎么读

置信区间给出一段可能包含真实值的范围。两个版本的区间重叠很多，通常不能断言谁更好；区间分离得清楚，结论才比较稳。

报告置信区间比只报一个点估计更诚实。它承认了评测本身的随机性，也避免了把小波动当成大进步。

### 重复运行的采样问题

重复运行会引入采样差异。温度、随机种子、工具时延都会让两次运行不同。要区分"版本差异"和"采样差异"，就要控制这些变量。

固定随机种子能减少采样差异，但完全固定可能掩盖系统的真实波动。折中做法是固定一组种子，既控制变量，又保留一定多样性。

## 九、概率 Agent 要重复运行

单次成功不能代表稳定成功。同一任务在不同采样、工具时延和用户表达下可能得到不同结果。

常见指标包括：

```text
pass@1   单次运行成功率
pass^k   连续 k 次都成功的比例
pass@k   k 次内至少成功一次的比例
```

对自主执行系统，`pass^k` 往往比 `pass@k` 更接近可靠性需求。用户不会愿意每次重复运行五遍，再挑一次正确结果。

### 三个指标分别说明什么

`pass@1` 反映平均表现，适合快速迭代。`pass@k` 反映上限，适合判断"系统有没有能力解决这类任务"。`pass^k` 反映稳定性，适合判断"系统能不能被信任自动执行"。

一个产品可能 `pass@5` 很高，`pass^5` 很低。这意味着它偶尔能解决，但每次都能解决的把握不足。对需要自动执行的场景，后者更关键。

### 对比版本要用配对评测

对比两个版本时，应使用相同任务和尽量一致的环境做 paired evaluation，并报告置信区间。20 个样本从 12 个成功变成 14 个成功，未必足以说明新版本稳定更好。

配对评测的关键是让两个版本面对完全相同的输入和环境，这样差异才来自版本本身。如果两个版本跑的任务不同，差异可能来自任务难度而非版本能力。

### 成本质量前沿

只看成功率会忽略成本。一个版本成功率略高但成本翻倍，另一个版本成功率略低但成本减半，哪个更好取决于业务。

把每个版本画成成功率与成本的点，取帕累托前沿。前沿之外的版本被支配，可以直接排除。这样比较的是性价比，而不只是单一指标。

### 切片的最小集合

切片的最小集合至少包括：高风险写操作、需要澄清的任务、长上下文任务、多工具任务。这四类最容易暴露问题。

切片不是越多越好。太多切片会让报告失去重点，也会让统计检验的样本量被摊薄。先定义关键切片，再按需要扩展。

### 一个评测反例：所有任务都通过

如果一批任务所有版本都通过，说明任务太简单，没有区分度。评测要有一定失败率，才能区分版本。区分度太低的任务集，需要换更难的任务。

区分度太高（所有版本都失败）也不好，说明任务可能不可解或描述不清。理想的评测集介于两者之间，能稳定地区分不同版本。

## 十、不要只看平均分

新版本平均成功率提高，可能同时让高风险任务退化。

评测报告至少要按这些维度切片：

- 任务类型与难度；
- 工具数量和调用深度；
- 是否需要用户澄清；
- 是否包含写操作；
- 上下文长度；
- 失败类型；
- 模型、Harness 和 Skill 版本。

此外还要检查成本质量前沿。成功率只提高 0.5%，token 和延迟却翻倍，未必值得发布；成本减半而成功率只下降在低风险场景，可能是更好的线上选择。

### 失败分类比通过率更有信息量

一个 80% 通过率的版本和一个 80% 通过率的另一版本，可能失败在不同地方。把失败分成感知、检索、规划、工具、恢复、验证、沟通、Harness 几类，能看清版本改进或退化了哪一块。

只看通过率，两个版本看起来一样；看失败分类，差异立刻显现。这也是为什么评测报告要保留失败样本，而不只是分数。

### 切片要预先定义

切片维度最好在跑评测前定义，避免事后挑选对自己有利的切片。常见做法是固定一组关键切片，每次评测都报告它们的表现。

事后挑选切片，容易变成"找到一组数字让自己看起来更好"。预先定义能避免这种自我说服。

### 门禁的两种形态

门禁可以是硬性的（不满足即拒绝），也可以是评分的（综合打分后排序）。安全类适合硬性，效果类适合评分。

硬性门禁保护不可妥协的底线，评分类门禁处理需要权衡的指标。把安全也做成评分，等于允许用其他分数补偿安全退化。

### 门禁失败怎么办

门禁失败不是终点，而是信号。失败在安全门禁，说明改动越界；失败在效果门禁，说明改动没达到目标；失败在成本门禁，说明代价过高。

针对不同的失败门禁，优化方向不同。把所有门禁失败都当成"再调一调 Prompt"，会浪费时间去解决错误的问题。

### 准入门槛的版本化

准入门槛本身也要版本化。门槛调松调紧，都要记录原因和时间。否则过一段时间后，没人知道当前门槛为什么是这样。

把门槛和它对应的评测配置放在一起版本化，能让准入决策可追溯。

## 十一、准入条件应该长什么样

一个候选版本可以采用分层门禁：

```text
Gate 1  构建、schema 与基础测试全部通过
Gate 2  安全和权限样本零退化
Gate 3  冻结集总体指标达到非劣标准
Gate 4  目标失败簇有统计上可信的改善
Gate 5  隐藏集无明显过拟合
Gate 6  成本与延迟在预算内
```

"非劣"比"平均分更高"更适合持续发布。新版本解决一类问题时，可以允许总体分数在很小范围波动，但关键切片不能越过下限。

准入规则要在运行候选前确定。看完结果再调整门槛，很容易为喜欢的版本找理由。

### 为什么用非劣而不是更高

要求"更高"会惩罚那些解决了一类问题、却在无关切片上轻微波动的版本。要求"非劣"只要求关键切片不退化，允许总体在极小范围内浮动，更适合持续改进。

非劣的门槛也要预先定。例如"安全和权限切片零退化，总体下降不超过 1 个百分点"。有了明确门槛，准入才是判断，而不是感觉。

### 门禁顺序有讲究

把安全和权限门禁放在总体指标之前，是因为安全失败不应该被总体高分抵消。一个版本即使总体提升很大，只要安全切片退化，也不该发布。

顺序体现了优先级：硬约束先于优化指标，关键切片先于总体平均。

### 灰度的流量策略

灰度流量可以按比例、按用户群或按任务类型分配。按比例最简单，按任务类型能更快暴露特定切片的问题。

对高风险改动，先在小批特定任务类型上灰度，观察后再扩大。按类型灰度能让问题在影响扩大前暴露。

### 线上指标和离线指标的关系

线上指标和离线指标不一定同向。离线提升的版本，线上可能因为分布不同而没有改善，甚至退化。这需要灰度来验证。

离线评测负责筛选，线上灰度负责确认。指望离线评测直接预测线上效果，会低估分布差异的影响。

### 回滚的时机

回滚不是失败，而是保护。什么时候回滚要预先定义：关键指标退化超过阈值、出现新的安全失败，或者线上成本超预算。

回滚阈值要和准入阈值一样预先确定。事后商量要不要回滚，等于在压力下做决定。

### 评测和监控的区别

评测是离线的、可重复的、面对固定任务集；监控是线上的、持续的、面对真实分布。两者互补，不能互相替代。

只有评测没有监控，会漏掉线上新出现的失败；只有监控没有评测，无法在发布前筛掉退化版本。

## 十二、离线通过以后还要灰度

离线数据覆盖不了真实用户的表达、环境和工具异常。通过准入的版本先进入小流量灰度，并保留旧版本作为对照。

线上监控包括：

- 任务完成率与人工接管率；
- 工具错误和无效重试；
- 用户纠正或撤销动作；
- 高风险操作的批准率；
- 延迟、token 和费用；
- 新出现的失败簇。

每次发布都要绑定不可变版本：模型、系统 Prompt、Skill、工具 schema、Harness commit、依赖和评测配置。指标异常时才能准确回滚，而不是猜测最近哪个文件发生了变化。

### 灰度要能一键回滚

灰度的价值一半在观察，一半在回滚。如果发现问题却无法快速回滚，灰度只是延长了故障时间。

回滚能力要求版本不可变：每次发布都有唯一标识，旧版本仍然可用。改一个文件就上线、且旧版本已被覆盖的流程，不具备回滚能力。

### 监控要覆盖新失败

监控不只是盯已知指标，还要发现新的失败模式。线上经常出现离线没覆盖到的输入和环境异常。把它们收集起来，脱敏后加入开发集，是评测集成长的主要来源。

### 失败分类怎么用于优化

失败分类不只是报告，它指导优化方向。感知失败指向工具输出，检索失败指向知识库，规划失败指向上下文和状态，工具失败指向契约。

把失败分类和优化目标对应起来，能避免"所有问题都靠改 Prompt"。不同层的失败应该由不同的机制修复。

### 回归集的维护

回归集需要维护。任务过期、环境变化、预期结果修正，都会让旧样本失效。定期审查回归集，删除失效样本，补充新样本。

一个没人维护的回归集会逐渐和真实系统脱节，最后变成一个只反映过去需求的历史文件。

### 从失败到修复的路径

一个失败样本到修复通常要走几步：复现、定位失败层、提出候选、离线验证、灰度确认。每一步都要有记录，否则修复无法复现。

记录的价值在几个月后显现。当同一个失败再次出现时，历史记录能告诉团队上次是怎么修的，以及为什么那样修。

### 谁来维护评测

评测需要有人维护。没有明确所有者，回归集会过期，隐藏集会泄漏，门禁会形同虚设。维护者不一定是专职，但要有明确责任。

评测的所有者要定期审查样本质量、门禁有效性，以及线上失败的回流情况。

## 十三、评测失败也要进入学习循环

评测不仅产生分数，还要产出失败分类：

```text
感知失败      没读到关键状态
检索失败      没找到证据
规划失败      顺序或依赖错误
工具失败      参数、权限、超时
恢复失败      遇错后重复或放弃
验证失败      错把局部成功当完成
沟通失败      没有澄清或误导用户
Harness 失败  事件、缓存、解析错误
```

只有定位到失败层，才能决定改 Context、Memory、Skill、工具还是 Loop。否则优化器会用最容易修改的 Prompt 去补所有问题，最后得到一份越来越长的免责声明。

### 失败样本怎么回流

新发现的真实失败可以匿名化后进入开发集，再构造相邻变体进入冻结集。这样评测集会随系统边界增长，但历史核心样本仍然保留，防止解决新问题时重新引入旧错误。

回流要有节制。把所有失败都加入评测集，会让集合膨胀到无法维护。选择有代表性、可复现的失败，比全量收集更实用。

### 这个例子里评测器有哪些盲区

这个例子仍有盲区。它没有覆盖用户中途改变目标的情况，也没有测试工具超时后的恢复。这些要靠后续补充任务来覆盖。

评测集永远不完整。重要的不是一次覆盖全部，而是持续把线上失败转化为评测样本，让集合随系统一起成长。

## 十四、端到端：一次代码修复的评测

用一个具体任务把整条链路串起来。任务是修复一个失败的单元测试，候选版本改进了 Agent 的上下文管理策略。

### 第一步：定义任务契约

契约写明初始仓库状态、目标测试、允许修改的目录、禁止修改测试文件、以及成本预算。硬约束是"不能改测试文件"，优化指标是"通过的测试数"和"调用次数"。

### 第二步：结果与轨迹评测

结果评测运行目标测试和整套回归测试，检查工作区 diff。轨迹评测检查 Agent 有没有修改测试目录、有没有越出允许目录、有没有读取不该读的文件。

### 第三步：分层数据

开发集用来复现失败并生成候选。冻结回归集包含已知能通过的任务。隐藏留出集包含一批从未暴露给优化器的任务，用于最终准入。

### 第四步：门禁

候选在安全切片上零退化，在冻结集上非劣，在目标失败簇上有统计上可信的改善，且成本在预算内。四条都满足才通过。

### 第五步：灰度与监控

候选进入小流量，对比线上失败率、成本和用户撤销率。观察期内如果某个关键指标退化，回滚到上一版。

### 第六步：失败回流

灰度期间发现的新失败，脱敏后加入开发集。下一轮进化从这些新样本出发，而不是重复优化已知样本。

这个例子里，自进化发生在上下文管理策略上，评测覆盖了结果、轨迹和运行三层，准入有明确门禁，发布有灰度和回滚。闭环完整，改动才可信。

### 评测环境为什么要容器化

评测环境应该容器化或沙箱化。同一批任务在不同机器上得到不同结果，通常是因为环境依赖不一致。

容器化让环境可复现，也让候选无法污染宿主机。它同时提供了隔离，防止测试影响真实数据或系统状态。

### 评测的成本预算

评测本身有成本。跑一次完整评测可能需要大量模型调用和时间。要在覆盖面和成本之间权衡，把昂贵评测留给关键节点。

一个分层策略是：小改动跑快集，大改动跑全集，发布前跑隐藏集。

### 一个评测报告的字段

一份评测报告至少写明：版本清单、任务集、通过率、关键切片、失败分类、成本，以及置信区间。

字段固定，才能横向比较版本。每次报告换一种格式，就没法积累趋势。

### 评测的复现性

评测的复现性指同样的输入能得到同样的判定。它要求环境、数据、评分器都确定。复现性差的评测，结论不可信。

提高复现性的手段包括容器化、固定种子、固定依赖版本。这些看起来是工程细节，实际决定了评测能不能被信任。

### 从零到一的顺序

如果从零建立评测，顺序可以是：先写十条任务契约；再实现结果断言；再加轨迹规则；然后接一个 Judge 处理开放质量；最后设门禁和回滚。

这个顺序保证每一步都有立即可用的产出，而不是先搭一套空框架。

## 十五、落地清单

搭一套最小可用的评测闭环，可以从下面几件事开始。

先定义任务契约，把结果、权限、证据和预算写成可执行检查。再分三层数据，开发集、冻结回归集、隐藏留出集。然后写结果断言和轨迹规则，把能用程序判断的部分先确定下来。接着用 rubric 处理开放质量，并单独评测 Judge。最后设准入门禁、灰度和回滚。

### 最小目录结构

```text
evals/
├── tasks/          # YAML 任务契约
├── fixtures/       # 固定初始环境
├── assertions/     # 确定性检查
├── rubrics/        # Judge 只处理开放质量
├── holdout/        # 与开发集隔离
└── reports/        # 版本、轨迹、结果和成本
```

### 每次改动按顺序检查

1. 保存候选版本，不覆盖当前稳定版；
2. 在临时目录或容器中运行固定任务；
3. 先执行确定性断言，再运行 Judge；
4. 输出切片结果与失败样本，不只输出均分；
5. 满足预先定义的门槛才允许合并；
6. 部署后继续记录线上异常并支持一键回滚。

### 一套评测是否可信

可以用四个问题自检：评测能被重复运行吗；对候选不可见的部分足够多吗；覆盖了历史失败样本吗；能把"钻空子"和"真进步"区分开吗。四个都是肯定，评测才值得用来做发布决策。

评测不是排行榜截图，而是一条能阻止退化版本进入生产的链路。自进化的能力上限，由它愿意接受的证据强度决定。

### 反模式清单

评测里常见几类反模式：只看平均分、用同一批数据做开发和验收、让候选影响评分器、把 Judge 当成最终裁决，以及没有回滚能力。

这些反模式的共同点是让评测失去独立性。评测一旦失去独立性，任何分数都只是候选的自我评价。

### 一个最小的评测命令

把评测封装成一条命令，例如 `npm run eval`。命令接受版本参数，输出分数、切片和失败样本。封装成命令，评测才能被稳定重复。

没有统一入口的评测，每次跑都可能遗漏步骤。统一入口是评测可重复的第一步。

### 从评测到评测平台的演进

一开始评测可以是一个脚本。随着任务增多、版本增多，它会演变成一个小平台：任务管理、运行调度、结果存储、报告生成。

不要一开始就搭平台。先在脚本里把评测逻辑跑通，等确实需要多人协作和趋势分析时，再抽出平台。过早平台化会把简单问题做复杂。

### 评测人员和时间

评测需要人投入时间，尤其是构造任务和审查失败。低估这部分投入，评测会逐渐荒废。

一个现实的做法是让评测维护成为开发流程的一部分，而不是额外的项目。

### 常见问题：评测永远不够

评测永远覆盖不全，这是正常的。关键是让评测集随系统成长，而不是一次做完就冻结。

把"补充评测样本"做成日常工作，比一次性追求完整更可持续。

### 评测的收益

评测的收益是隐性的：它不直接提升能力，但阻止退化版本进入生产。长期看，它决定了系统能不能持续改进。

没有评测的系统不是不能改，而是每次改动都在赌。评测把赌变成判断。

### 评测与人的关系

最终判断进步的往往是人和评测器的组合。评测器负责规模和一致性，人负责判断评测器没覆盖的部分。

把两者对立起来没有意义。好的系统让评测器处理明确的，人处理模糊的。

### 评测的长期价值

评测的长期价值在于积累。每一批任务、每一次失败、每一个版本记录，都在构成系统的历史。有历史，才能判断趋势。

没有历史，每次改进都是孤立事件。评测把孤立事件连成趋势。

### 评测和文档的关系

评测任务契约本身就是一种文档。它记录了系统应该做什么、边界在哪、验收标准是什么。团队换人时，这些契约比口头说明更可靠。

把契约和代码放在一起版本化，能让"系统应该做什么"和"系统实际做了什么"始终可对照。

### 评测的边界

评测能回答"在给定任务集上，版本 A 是否优于版本 B"。它不能回答"系统在真实世界一定更好"，因为真实分布无法完全被评测集覆盖。

承认这个边界，才能正确使用评测：用评测筛选，用灰度确认，长期用线上数据校验。

### 给评测留出预算

评测要占用时间和算力，应该像功能开发一样预留预算。没有预算，评测会被一再推后。

把评测当作交付的一部分，而不是可选项，是维持评测可信度的前提。

### 一句话总结

评测的作用不是给出一个分数，而是让"这次改动是不是真的更好"可以被证据回答。任务契约定义问题，分层数据控制偏差，确定性检查守住底线，Judge 处理开放质量，门禁决定去留。

这五件事合起来，才是一个能支撑自进化的评测闭环。

### 结语

评测是自进化的刹车和仪表盘。没有刹车，系统改得越快越危险；没有仪表盘，系统不知道自己在往哪走。把评测做扎实，自进化才有方向，也才有底气持续改下去。它不会让系统一夜变强，但会让每一次变强都留下可信的证据。
