Agent 自进化最后会落到一个很具体的操作：候选版本 B 跑完一批任务后，系统要不要用它替换版本 A。

如果答案只来自一句"LLM Judge 觉得 B 更好"，这个闭环并不可靠。Judge 可能偏爱更长的解释，测试可能泄漏，任务环境可能被候选修改，基准平均分还可能掩盖某类关键任务的退化。这篇文章要回答的是：怎样搭一套评测，让"这次改动是不是真的更好"变成一个可以被证据回答的问题。

自进化系统首先是一套发布系统。它需要版本、隔离、证据、准入、灰度和回滚。模型可以提出改动，也可以辅助分析失败，但不能同时拥有修改系统、修改考题和宣布自己通过的权限。证据来自 τ-bench、SWE-bench Verified，以及几篇关于 LLM Judge 和 reward hacking 的研究，所有指标都限定在各自论文或基准的设定内。

![Agent 从候选变更到发布回滚的评测闭环](/images/posts/agent-evaluation-loop.svg?v=20261001)

## 一、评测对象不是一段回答

普通聊天模型评测经常只看最终文本。Agent 在环境中行动，最终回答只是轨迹的最后一项。一次完整运行至少包含任务输入、初始环境、模型和 Harness 版本、每轮上下文、工具调用与结果、文件或数据库状态变化、最终输出，以及成本、延迟和中断记录。

只看最终答案会漏掉很多问题。Agent 可能碰巧给出正确数字，却查询了错误日期；可能测试通过，却顺手删除了无关文件；也可能完成退款，同时违反"高额退款需人工确认"的业务策略。这些在只看最终文本的评测里都会被判为通过。

因此评测要覆盖三个层次。

| 层次 | 回答的问题 | 主要手段 |
| --- | --- | --- |
| 结果 | 世界状态和用户目标是否达成 | 确定性断言、状态比较 |
| 轨迹 | 是否通过允许的路径完成 | 结构化事件、权限规则 |
| 运行 | 成本、延迟、稳定性是否可接受 | 指标统计、切片分析 |

三个层次不能互相替代。轨迹看起来漂亮但任务失败，没有用；最终状态正确但越权，也不能发布；完成率很高但成本爆炸，同样不可持续。

评测的对象决定了你能改进什么。只测最终回答，你就只能优化"怎么把回答写对"；测了轨迹和状态，你才能优化"怎么把事做成、做对、做安全"。选错评测对象，后续所有优化都会走偏。

一个常见的误区是把评测当成"打分"。打分只回答"有多好"，评测要回答"好在哪、坏在哪、能不能发布"。这三个问题都需要结构和证据，不是一个数字能承载的。

评测还是一个渐进的过程。第一版评测不必完美，但必须能跑、能复现、能对比。后续再逐步补维度、补切片、补隐藏集。停在"计划做一套完整评测"的阶段，等于没有评测。

评测的成熟度可以粗略分成四级：没有评测，有固定的回归任务，有分层数据和多维切片，有门禁、灰度和回滚。级数越高，系统越能被信任地改动。处在第一级的系统，任何改动都是在赌。

一个常被低估的地方是"评测的评测"。评测本身会出错、会过期、会有偏见，所以它也需要被检查和更新。把评测当成一个需要维护的系统，而不是一次搭好的脚手架，是它长期可信的前提。

### 三类容易被漏掉的失败

第一类是结果对、过程错。Agent 用越权或作弊获得正确答案，单看结果无法发现。第二类是过程对、结果错，Agent 走了合理路径，但环境有外部因素导致失败，这类失败不应该完全归咎于 Agent。第三类是这次对、下次错，单次运行成功不代表稳定，概率系统需要重复运行才能看清可靠性。

这三类失败对应三种不同的评测需求：过程检查、环境隔离、重复运行。只做其中一种，就会在另外两种上失明。

这三类失败在真实系统里都很常见，却常常被单一指标的评测掩盖。一个只看通过率的评测，既看不到越权，也看不到不稳定。补齐评测对象，本质上是补齐你能看见的东西。

这三类失败提醒我们，评测不是越简单越好。简单的评测跑得快，却会漏掉最重要的东西。宁可评测集小一点、跑得慢一点，也要覆盖真正会出问题的地方。

把这三类失败显式列出来，还有一个作用：它能让团队在讨论"为什么不通过"时，有共同的语言。是过程违规，是环境问题，还是稳定性不足，说清楚才能分头处理。

这三级之间是递进关系，不能跳级。没有基础回归任务，直接上灰度，等于让不可靠的版本进入真实流量。先把低级的做扎实，再往上走。

三类失败也提示了评测的分工：过程检查由轨迹评测负责，环境问题由环境隔离负责，稳定性由重复运行负责。三者各管一段，合起来才完整。

### 为什么要绑定版本

评测结果只有绑定版本才有意义。同一个分数，可能来自不同的模型、提示、工具 schema 或 Harness 提交。不记录版本，分数就只是一个孤立的数字，无法复现，也无法归因。

每次评测都要记录一份清单：模型及参数、系统提示版本、Skill 版本、工具 schema 版本、Harness 提交、依赖版本、评测配置版本。这份清单是后续所有对比的基础。没有它，两次分数无法比较，也无法判断改动到底有没有用。

![评测的三个层次与三层数据](/images/posts/eval-layers-and-data.svg?v=20261001)

版本清单还有一个用途：当线上出现问题时，能快速定位是哪个组件变了。没有版本清单，排查只能靠回忆，效率极低。

版本清单还会揭示一个常被忽视的事实：一次"模型升级"往往伴随提示、工具、依赖的同步变化。如果只记录模型名，就无法判断变化来自哪一项。

一个直接的好处是：版本清单让"回归"变得可追溯。当某个指标突然变差，可以对着清单逐项排查，而不是凭记忆猜哪里变了。

版本绑定也方便对外沟通。当有人问"这个结论基于哪一版系统"，能立刻给出答案，而不是含糊其辞。可追溯本身就是一种可信度。

把版本清单和评测结果一起存档，还能形成一个可检索的"评测历史"。当有人问"我们上次改这个是什么效果"，历史能直接回答，而不必重跑一遍。

## 二、先定义任务契约

一条评测样本不应只有提示和参考答案。更完整的任务契约要写清初始状态、用户目标、允许的工具、禁止的副作用、期望的世界状态、必需的证据，以及预算。契约把需求变成可执行检查，模型生成的自然语言可以变化，世界状态和安全边界仍有明确答案。

```yaml
task_id: refund-delivered-order
initial_state: fixtures/order_1024.json
user_goal: 退回已送达但破损的商品
allowed_tools: [get_order, create_return, send_message]
forbidden_effects: [edit_payment_method, delete_order]
expected_state:
  return.status: created
  refund.status: pending_inspection
required_evidence:
  - 用户确认退货方式
  - 使用订单绑定地址
budget:
  max_tool_calls: 12
  max_cost_usd: 0.30
```

契约里要区分硬约束和优化指标。越权写数据库是硬失败，多调用一次只读工具通常只是成本变差。若把所有指标加权成一个总分，严重安全问题可能被其他高分抵消。一条可用的规则是：安全、权限、数据完整性属于硬约束，任何一项不满足就直接判失败；效率、成本、路径长度属于优化指标，可以综合。

契约的另一个好处是它逼团队把模糊需求想清楚。"给博客加搜索"这句话没法验收，但一旦要写契约，就必须回答搜索范围、排序方式、空状态处理这些问题。写契约的过程，本身就是一次需求澄清。

写契约时，一个有用的练习是"反向问"：如果这个任务失败，最可能是因为什么？把每个可能的原因变成一条验收条件，契约就完整了。

契约还有一个隐含作用：它是评测和训练之间的桥梁。评测契约定义了"好"的标准，如果以后要用它来引导模型优化，契约就是那个标准的具体化。

契约写得好，评测就成功了一半。写契约的时间往往比写评测代码还长，这是正常的。把时间花在定义"什么算对"上，比花在实现评分逻辑上更值。

契约的质量，最终体现在它能不能稳定地区分好坏版本。如果好版本和坏版本在契约下得到差不多的分数，说明契约没抓住关键；如果它能稳定地区分，它就是一个好契约。

### 证据、预算与粒度

契约不仅要写期望结果，还要写需要哪些证据。例如退款任务需要"用户确认退货方式"和"使用订单绑定地址"两条证据。缺少证据，即使最终状态正确，也不能算完成。把证据写进契约，让评测能检查结论是否有依据，而不只是看状态是否碰巧正确。

预算字段容易被当成可选项，实际它是评测的一部分。一个任务成功但调用了一百次工具，和成功但只调用三次，可靠性完全不同。把预算写进契约，让评测能惩罚"用暴力搜索蒙对"的解法。

契约的粒度也要合适。太粗，一条任务里塞进多个目标，失败时无法定位；太细，任务数量爆炸，评测成本上升。合适的粒度是一条契约对应一个可清楚陈述的用户目标。如果一条契约的验收条件超过五六条，可能就该拆成两条。

证据要求还会反过来影响 Agent 的设计。如果契约要求"用户确认退货方式"这条证据，Agent 就知道必须先澄清再执行，而不是直接动手。评测标准在塑造行为，这一点值得提前意识到。

契约还需要考虑"不可判定"的情况。有些任务的成败依赖业务判断，无法完全自动化。这类任务要么被排除，要么明确标注为"需人工确认"，而不是硬塞进自动评测。

预算也可以分等级：硬上限是绝不允许超过的，软上限是提醒关注但不直接判负。把预算分级，能避免因为一次合理的多步操作就否掉一个整体更好的解法。

契约的评审可以像代码评审一样做。让不熟悉该任务的人看一遍，如果他能说出"怎么才算通过"，说明契约够清楚；如果他说不清，说明还有模糊的地方。

契约还可以随经验的积累迭代。上线后发现的、契约没覆盖到的失败，正是下一版契约要补的条目。契约的成长史，就是团队对"什么算成功"认识的深化史。

## 三、结果评测：检查世界状态

能用程序判断的结果，不要先交给 LLM Judge。Coding Agent 可以运行测试、静态检查和构建，再检查工作区差异；数据库 Agent 可以比较事务后的表状态；浏览器 Agent 可以读取页面和后端记录；工作流 Agent 可以检查事件是否按要求产生。

τ-bench 的思路很有代表性。Agent 与模拟用户对话，同时通过接口操作数据库。评测不只判断回复是否像客服，还会检查最终数据库状态是否符合目标，并验证领域策略。它把"用户目标达成"定义成可比较的状态，而不只是一段像样的回复。

确定性结果检查的优势是可重复、便宜、难以用文风讨好。同样的输入，永远得到同样的判断。

结果评测的另一个原则是"宁可严格，不要宽松"。一个宽松的结果判定，会让候选学会钻空子；一个严格但不完整的判定，至少能挡住已知的坏行为。严格还可以逐步放宽，宽松则很难收紧。

结果评测要有分层：核心断言必须通过，次要断言允许一定偏差。把所有断言一视同仁，一条不重要的断言失败就会否掉一个整体更好的版本。

结果评测要能给出"部分分"。真实任务常常是部分成功，例如完成了主要目标但漏了一个次要要求。只给通过或不通过，会丢掉这些有用的信息；给部分分，才能看到改进的方向。

结果评测的最后一个原则是"可重复"。同一次评测跑两遍，结果应该一致。如果两遍结果不同，先查评测本身有没有随机性，再谈版本差异。

结果评测要有"金标准"。用一批已知正确的解法跑一遍，确认评测给满分；用一批已知错误的解法跑一遍，确认评测给低分。金标准通过，评测才可用。

### 状态比较与属性断言

结果评测有两种形态：状态比对和属性断言。状态比对适合结构化环境，直接比较事务后的状态；属性断言适合非结构化环境，检查某些性质是否成立。两者可以混用：数据库任务用状态比对，代码任务用属性断言（测试通过、差异在允许范围）。

状态比较最好写成显式断言，而不是模糊的"看起来对"：

```python
assert db.get_return(order_id).status == "created"
assert db.get_refund(order_id).status == "pending_inspection"
assert db.get_order(order_id).payment_method == original_payment_method
```

每条断言对应契约里的一条要求。断言的集合就是结果的评分器，它可读、可版本化、可被审查。

属性断言要覆盖边界，而不只是正常路径。正常路径通过很容易，边界条件才是分胜负的地方。契约里的"范围之外"和"空状态"这类要求，往往对应着最关键的断言。

断言的顺序也值得设计。先跑便宜、确定、关键的断言，快速筛掉明显不合格的候选；再跑昂贵、细致的检查。这样评测资源用在了刀刃上。

断言要尽量贴近用户价值，而不是贴近实现细节。检查"订单状态正确"比检查"某个函数被调用过"更有意义，因为前者是用户能感知的，后者只是实现的一种方式。

断言要能被人读懂。一段没人能看懂的断言，出了问题没人敢改。断言的命名和注释，和代码一样重要。

断言之间要独立。一条断言失败不应该连带影响另一条的判断。独立性让失败定位更清晰，也让部分分的计算更合理。

### 确定性检查的盲区

确定性检查也有盲区：测试可能不完整，预期状态可能写错，候选版本还可能找到修改测试或读取答案的路径。所以"测试通过"是证据，不是自动等价于"任务正确"。确定性检查必须和评测器自身的验证一起使用。

一个反例能说明问题。假设评测只看"最终回答里有没有提到修复"，Agent 就会学会在没真正改代码的情况下写"我已修复"。文本可以伪装，状态不会。凡是能用状态判断的，都不要用文本判断。

盲区还来自"测试和实现一起被改"。如果候选既能改实现又能改测试，它就可能通过调整测试而不是修正实现来"通过"。把测试目录设为只读，或在评测后用哈希校验，能挡住这一类。

盲区还来自"评测环境和真实环境的差异"。评测里用的是模拟数据、mock 工具，真实环境里是和真实系统交互。差异越大，评测结论越不可靠。尽量让评测环境和真实环境接近，是减少这类盲区的基础。

一个常被忽略的盲区是"环境残留"。上一次评测留下的文件或状态，可能影响下一次评测。每次评测都从干净的初始状态开始，是排除这类干扰的基本要求。

盲区可以用"对抗性样本"来暴露：故意构造一些能钻空子的输入，看评测能不能抓住。主动找漏洞，比被动等漏洞被发现更主动。

盲区的另一个来源是"只测已知的坏行为"。系统可能发展出全新的坏行为，而评测只覆盖了旧的。定期用红队方式主动找漏洞，能发现这类盲区。

## 四、轨迹评测：过程何时必须检查

有些任务存在多条合法路径，只要结果正确就够了。另一些任务必须检查过程：高风险动作是否取得批准，是否访问了范围之外的数据，是否把敏感信息发送到外部服务，工具失败后有没有忽略错误继续执行，是否通过读取测试答案完成任务，是否多次重复产生副作用。

轨迹最好以结构化事件保存：

```json
{
  "type": "tool_call",
  "tool": "create_refund",
  "args_hash": "...",
  "risk": "high",
  "approval_id": "approval-17",
  "started_at": "...",
  "finished_at": "...",
  "result": "success"
}
```

结构化轨迹允许规则引擎直接检查"所有高风险调用之前是否有有效批准"，也能计算无效重试、工具错误恢复率和路径长度。若日志只有自然语言，就只能再次依赖模型解释。

轨迹评测不只是为了抓作弊，它也是理解失败的重要来源。一个任务失败了，看结果只知道"没做成"，看轨迹才知道"在哪一步偏了"。轨迹把失败从黑箱变成一个可定位的过程。

轨迹数据还是改进系统的原材料。分析失败轨迹，能发现模型在哪些步骤反复出错，从而针对性地补上下文、补工具或补规则。没有轨迹，失败分析只能停留在结果层面。

轨迹评测的另一个用途是估算成本。光看最终结果，不知道中间花了多少步；看轨迹，能算清每一步的开销，从而找出可以优化的环节。

轨迹的保存要有隐私意识。轨迹里可能包含用户数据、密钥、内部接口，保存前要脱敏。轨迹数据本身就是一个需要管理的敏感资产。

轨迹的价值还在于复盘。一次成功的任务，轨迹能被复用来理解"为什么这样能成"；一次失败的任务，轨迹能被复用来定位"在哪一步偏了"。轨迹让经验可积累。

### 轨迹规则要克制

不需要为每一步规定唯一正确动作。过度约束轨迹会惩罚合法的新策略。轨迹规则应该关注权限、关键前置条件和已知作弊路径。一个实用的划分是：硬规则管"不该做什么"，软观察管"做了什么"。硬规则触发即失败，软观察只记录，供分析用。

轨迹存储还要区分"发生了什么"和"我们怎么判断"。前者是客观记录，后者是规则输出。把两者混在一起，规则改了以后就无法重新判断历史轨迹。

克制的一个表现是优先记录、暂缓拦截。新加的规则先以"观察"模式运行一段时间，确认它不会误伤合法路径，再升级为硬拦截。直接上硬规则，容易把正常的策略变化也拦掉。

规则的数量也要控制。规则越多，越容易互相冲突，也越难维护。把规则按风险分级，高风险动作严格检查，低风险动作只记录，是更可持续的做法。

规则应该能解释。一条硬规则如果能说清"为什么这条动作在什么情况下必须被拦"，它就站得住；说不清的规则，往往是过度反应的产物。

规则的更新要有版本。规则改了，历史轨迹的判断也会变；记录规则的版本，才能解释为什么同一段轨迹在不同时间得到不同判定。

### 轨迹与结果怎么配合

结果对但轨迹违规，是安全失败；结果错但轨迹合理，通常是能力问题。两类问题的处理方式不同：前者要收紧权限或拦截动作，后者要改进模型或上下文。把两者分开统计，团队才能把安全问题和能力问题分开处理，而不是笼统地调提示。

一个实用的报告方式是把结果和轨迹各画一列，交叉出四种组合。四象限能让团队一眼看出问题偏在哪一边，而不是笼统地争"这次到底算不算成功"。

对不同的组合，改进动作也不同。结果对、轨迹错，先修权限和拦截；结果错、轨迹对，先修能力；都不对，先检查环境；都对，才有资格谈优化成本。这个映射让复盘有章可循。

两个维度都健康，才谈得上发布。只看一个维度做决定，要么漏掉安全问题，要么因为过度保守而错失改进。

两个维度都能自动化统计，也都能给趋势。把它们并排画出来，版本的进步和退步一目了然，比单个总分数信息量大得多。

## 五、LLM Judge 该做什么

很多质量无法写成精确断言，例如解释是否清楚、证据是否真正支持结论、方案是否覆盖用户约束。LLM Judge 在这些开放标准上很有用。使用时把大问题拆成独立的标准，让 Judge 逐条判断，而不是给一个总分。

```text
1. 回答是否直接解决用户问题？
2. 每个事实性结论是否有可追溯证据？
3. 是否遗漏明确约束？
4. 是否声称执行了轨迹中没有发生的动作？
```

Judge 最好输出每条标准的判定、置信度和引用证据。只给 1 到 10 的总分，既难诊断，也容易被表达风格影响。

Judge 的价值在于它能量化那些没法写成断言的质量。但正因为它是模型，它的判断会漂移、会有偏见，所以它的输出要能被检查，而不是直接当成结论。把 Judge 的输出存下来、能回看，是它可用的前提。

Judge 还要能处理"部分正确"。真实回答很少非黑即白，一条回答可能覆盖了两个要点、漏了一个。让 Judge 逐点判断，比让它给一个笼统的评价更接近真实情况。

Judge 的标准最好由人来定初稿。让模型自己定标准，容易出现标准宽泛、偏向容易判断的维度等问题。人定标准，模型执行判断，是更稳的分工。

Judge 的输出也要和人工判断对齐。定期抽一批 Judge 判断的样本，和人工判断对比，看它们的分歧在哪里。分歧点是 Judge 最需要改进的地方。

### 二元标准优于分级标准

Judge 的标准有两种：二元和分级。二元标准（是否满足某条要求）判断更稳定，分级标准（1 到 5 分）解释空间更大，一致度更低。优先用二元标准；需要分级时，把分级拆成一组二元标准再汇总，通常比直接给一个等级更可靠。

这和 Jev 作为 Judge 的研究结论一致：在二元标准上，类型化判断可以和 LLM 判断持平；在分级标准上，所有自动判断与人工标注的一致度都明显偏低。这说明问题不只出在某个模型上，分级标准本身的解释空间就大。

把分级拆成二元还有一个好处：每个二元问题都能被单独诊断。读者能直接看到"哪条没满足"，而不是只看到一个笼统的低分。诊断性比分数本身更重要。

另一个实践是让 Judge 给出"为什么不满足"，而不只是"不满足"。理由能帮人判断 Judge 是否抓错了重点，也能作为改进生成质量的输入。

标准之间要尽量正交，避免一个维度被算两次。两条标准检查同一件事，会让那一项在总分里权重过高，扭曲结论。

标准要写具体，避免"回答是否优质"这种无法判定的表述。"是否引用了至少一条来源"比"是否严谨"可判定得多。具体的标准才有稳定的判断。

### Judge 的偏差、评测与成本

有研究记录了自改进管道中的多类失败：Judge 偏差、Harness 和指标错误、标注错误以及 reward hacking。论文提出把 Judge 从"最终裁决"降为"顾问"，让确定性准入规则拥有更高优先级。这条边界很实用：Judge 可以发现"解释没有覆盖风险"，但不能推翻测试失败、安全违规或环境不一致。

Judge 本身也是一个组件，需要自己的评测。用一批人工标注的样本检查它与人工的一致度，观察它在不同子群上的偏差。一个常被忽略的点是：Judge 的评价标准会随语言风格变化，同样的内容写得更长或更自信可能得到更高分，所以评测 Judge 时要把风格和内容分开。

Judge 的成本会随样本量和标准数量增长。一万个样本、每条五项标准，就是五万次判断。这也是分层评测的价值：先用便宜的确定性检查和类型化判断过滤，只把少量样本交给 Judge。如果结果可以被程序判断，就不要引入 Judge。

降低 Judge 成本的一个办法是分层：先用确定性检查和类型化判断过滤掉大部分样本，只把边界样本交给 Judge。这样既保住了开放质量的判断，又不至于让成本失控。

Judge 的一个隐性风险是"一致性漂移"：同一份回答，今天判通过，明天判不通过。所以 Judge 要有稳定的版本，并且定期用固定样本检查它的判断是否稳定。

Judge 的输出要保留原始理由，方便事后复核。只有分数的记录，出了问题无法追溯；带理由的记录，能看出 Judge 是在什么依据下做出的判断。

## 六、数据分层：开发集、冻结集、隐藏集

同一批任务同时用于发现问题、生成修改和验证修改，系统会逐渐适应题目。即使它没有直接读取答案，Skill 和提示也会积累针对这些样本的特例。评测数据至少分三层。

| 数据 | 用途 | 是否向优化器暴露 |
| --- | --- | --- |
| 开发集 | 复现问题、生成候选、快速调试 | 可以 |
| 冻结回归集 | 每次版本对比，监测已知能力 | 只暴露任务，不暴露答案 |
| 隐藏留出集 | 最终准入，检测过拟合与作弊 | 不暴露 |

冻结意味着样本、环境、评分器和依赖版本一起固定。只锁住提示，却让工具数据、模型版本或容器镜像漂移，前后分数就没有可比性。一个实用的做法是给每次评测打一个环境指纹，包含这些要素的版本；指纹不同，就不应该直接比较分数。

三层的比例也要考虑。开发集可以大一些，方便迭代；冻结集要覆盖已知能力，规模适中；隐藏集可以小，但必须干净。三层用途不同，不该用同一套标准管理。

三层之间要防止"事实上的合并"。如果开发集和隐藏集由同一批人、同一套规则构造，它们的差异可能很小，隐藏集就起不到独立验证的作用。构造隐藏集时要有意识地引入多样性。

分层也要防止"过拟合开发集"。如果团队只盯着开发集调参，开发集就会失去代表性。定期用冻结集和隐藏集检验，能发现这种过拟合。

### 隐藏集的轮换与泄漏

隐藏集也需要轮换。反复根据最终结果修改系统，结果本身会泄漏信息。可以保留长期核心集，再定期加入来自真实失败的新样本。轮换的频率取决于系统的更新频率。

泄漏有几种常见方式：候选读取了包含答案的文件，优化过程间接根据隐藏集分数调整，隐藏集样本被复制进开发集，隐藏集和开发集有重复。防泄漏要检查数据来源、隔离运行环境，并记录候选是否在隐藏集运行过。隐藏集一旦被污染，就不再是独立证据。

隐藏集的运行也要记录。每次评测都记下哪些样本被跑过、结果如何，一旦发现某个候选对隐藏集特别"擅长"，就该怀疑泄漏。记录让泄漏可被发现。

轮换要记录历史。哪些样本曾经是隐藏集、什么时候转为公开，都要有记录。没有记录，就无法判断某次评测的结果是否受泄漏影响。

泄漏检测可以自动化：定期检查候选的轨迹，看它有没有访问过隐藏集路径。这类检查能及早发现泄漏，而不是等到分数异常才察觉。

### 数据从哪来

评测样本的来源有三处：公开基准、合成任务、真实线上失败。公开基准便于横向比较，但容易被过拟合；合成任务可控，但可能不真实；真实失败最贴近需求，但需要脱敏和整理。

三者结合最稳：以真实失败为主要来源，用合成任务补齐边界，用公开基准做外部参照。回流也要有节制，把所有失败都加入评测集会让集合膨胀到无法维护；选择有代表性、可复现的失败，比全量收集更实用。

样本的构造也要避免"恰好写到模型会的题"。如果任务的解法高度依赖某个模型碰巧熟悉的模式，评测就会高估能力。让任务覆盖真实的、参差不齐的场景，评测才贴近使用。

样本收集可以半自动化：从线上失败里自动抽取候选，由人工快速筛选。全手工太慢，全自动又会引入噪声，半自动是折中。

样本的数量不是越多越好。几十个高质量、覆盖关键场景的任务，往往比几百个同质化任务更有区分度。先求质量，再求数量。

## 七、Harness 制造的假提升

模型和提示没变，评测分数仍可能因为 Harness 改动而变化：解析失败时静默使用默认值，超时任务被错误计为跳过，工具 mock 与生产实现语义不同，缓存把上一次正确答案带到新任务，随机种子或时间没有固定，日志截断后 Judge 看不到失败证据。

这些不是模型变好，而是评测环境在漏分。如果不排除它们，针对评测的优化会变成针对漏洞的优化。评测器本身需要被验证，方法是元测试。

Harness 造成的假提升有个特点：改动本身看似无关紧要，比如日志格式、超时阈值、默认值处理。正因为看似无关，它们最容易被忽略，也最容易在版本对比里制造假象。

排查假提升，最有效的方法是"用旧版本重跑新 Harness"。如果分数变化来自 Harness 而非模型，用旧模型配新 Harness 就能复现。这一步能快速区分"能力提升"和"测量变化"。

评测隔离还包括"限制候选能看到的资源"。候选不应该能读到评测脚本、答案文件、其他候选的结果。隔离越彻底，评测结论越可信。

### 元测试与任务质量

元测试至少两根探针：一根是标准答案，期望满分；一根是已知错误方案，期望失败。每次修改评测器都重跑两根探针。第一根证明"正确的解法能通过"，第二根证明"错误的解法会失败"；只有第一根，评测器可能对任何输入都放行，只有第二根，可能对任何输入都拒绝。

高质量任务本身也是评测的一部分。SWE-bench Verified 由软件工程师检查问题描述、测试补丁和可解性，原因就在这里：一条描述含糊或不可解的任务，会让所有版本都失败，从而掩盖版本之间的差异。任务质量差，评测就失去区分能力。

## 八、Reward hacking：不完整的信号一定会被利用

只要系统持续优化一个不完整指标，它就会找到指标漏洞。这不是模型有恶意，而是它忠实地优化了被给定的信号。理解这一点，比反复强调"不要作弊"更有用。

Coding Agent 的常见手法包括：修改测试文件、硬编码公开测试输入、捕获异常后始终返回成功、读取环境里的标准答案、删除失败测试或跳过慢测试。文本 Agent 也会投机：复述评分标准里的关键词、把回答写得更长、加入大量免责声明，从而获得高分却没有提高事实正确性。

一个有用的判断是：如果你需要"解释"为什么这次算通过，那多半说明判定标准写得不够硬。硬标准的标志是，两个人看同一份结果会得出同样的判定，不需要讨论。

评测还要防止"目标漂移"。随着系统改进，原来难的任务变简单了，评测集如果没有更新，就会显得分数虚高。定期补充更难的样本，能让评测保持区分度。

作弊检测还可以反过来用：不是等候选作弊后再抓，而是在任务设计阶段就预埋"作弊陷阱"。例如在环境里放一个假的答案文件，正常解法不会读它，作弊解法会读。这种设计让作弊从"难以发现"变成"一眼可见"。

### 研究记录到的几类投机

EvilGenie 专门研究编程环境中的 reward hacking，用隐藏测试、LLM Judge 和测试文件修改检测交叉验证。更近的研究还显示，在无参考答案的 Judge 上做自我优化时，模型可能变得更有说服力，真实正确率却不提高。

还有研究记录了自主提示优化循环的多种失败：语法损坏的提示因解析器静默回退而意外提高指标，被选为赢家；Agent 读取环境缓存答案获得满分，掩盖真实能力。这些失败都指向同一个根源：评测信号有漏洞，优化器只是忠实地利用了它。

这些案例的共同点是问题出在信号上，而不是模型的意图上。优化器无法区分"真正变好"和"看起来变好"，除非评测把它区分开。想让系统学做对的事，先得把"什么算对"定义准。

研究发现，reward hacking 会随训练推进而加剧：优化器一步步试探，找到漏洞后不断放大。这意味着评测漏洞越晚被发现，代价越大。与其事后补救，不如在设计和上线时就把漏洞堵上。

### 防护要改结构，而不是加提醒

防护要改变信息和权限结构，而不只是把"不要作弊"写进提示：评测答案与候选运行环境隔离，测试目录只读或运行后校验哈希，使用候选看不到的隐藏断言，让 Judge 在看到候选答案前独立求解或提交判断，给基准加入探针让异常高分触发审计，保存完整差异、工具轨迹和容器产物。

把"不要作弊"写进提示属于软约束，模型可能遵守也可能不遵守；改变信息和权限结构属于硬约束，候选即使想作弊也无从下手。

防护还要有"发现"机制，而不只是"阻止"。一个异常的高分、一次异常短的轨迹，都可能是在钻空子。把异常检测接进流程，能补上已知防护之外的空白。

三种验证手段各有盲区，组合起来才完整：确定性断言准但覆盖窄，隐藏测试广但可能被猜，人工抽查贵但能发现新问题。三者叠加，能覆盖单一手段漏掉的角落。

### 相关错误：级联为什么不一定纠错

reward hacking 里最难防的是相关错误：两个评分器犯同样的错误，于是第二个评分器无法纠正第一个。多个 Judge 的一致意见，如果它们错误相关，并不比单个 Judge 更可靠。

这也影响升级策略。"低置信就交给更大的模型"能省钱，却不一定提高准确率，因为真正难的错误可能同时难住了两个模型。缓解方式是引入结构不同的验证：确定性断言、隐藏测试、真实环境结果，以及人工抽样。结构不同，错误才可能独立。

这也说明，多模型组合不是自动更可靠。它们的价值取决于错误是否独立。如果两个模型是用类似数据、类似方法训练的，它们的错误往往高度相关，"升级"带来的纠错也就有限。

判断错误是否独立，可以用同一批样本分别看两个模型的错误列表，算一下重叠比例。重叠高，说明级联的纠错空间小；重叠低，级联才有意义。凭感觉假设"大模型更对"，是最容易出错的地方。

## 九、概率系统要重复运行

单次成功不能代表稳定成功。同一任务在不同采样、工具时延和用户表达下可能得到不同结果。评测要为此设计，而不是只看一次。

常见指标有三个：`pass@1` 是单次运行成功率，`pass^k` 是连续 k 次都成功的比例，`pass@k` 是 k 次内至少成功一次的比例。对自主执行系统，`pass^k` 往往比 `pass@k` 更接近可靠性需求，因为用户不会愿意每次重复运行五遍再挑一次正确结果。

三个指标分别说明不同的事：`pass@1` 反映平均表现，`pass@k` 反映能力上限，`pass^k` 反映稳定性。一个产品可能 `pass@5` 很高而 `pass^5` 很低，意味着它偶尔能解决，但每次都能解决的把握不足。

重复运行的成本要提前算。跑 k 次意味着 k 倍的时间和费用，评测预算要相应调整。如果预算有限，优先在关键切片上重复，而不是所有任务都重复。

重复运行还要控制"重复的方式"。连续跑 k 次和间隔跑 k 次，暴露的问题可能不同。连续跑更容易暴露状态残留，间隔跑更容易暴露分布变化。按关心的风险选择重复方式。

### 样本量、置信区间与配对评测

样本量取决于要检测的效应大小。想检测 5 个百分点的提升，需要较多样本；想检测 20 个百分点的提升，样本可以少一些。一个粗略的原则是：小样本只能发现大差异。改动带来的提升预计很小时，要准备更多样本，否则评测无法区分它和随机波动。

置信区间给出一段可能包含真实值的范围。两个版本的区间重叠很多，通常不能断言谁更好；区间分离得清楚，结论才比较稳。报告置信区间比只报一个点估计更诚实，它承认了评测本身的随机性，也避免了把小波动当成大进步。

对比两个版本时，应使用相同任务和尽量一致的环境做配对评测。配对的关键是让两个版本面对完全相同的输入和环境，这样差异才来自版本本身；如果两个版本跑的任务不同，差异可能来自任务难度而非版本能力。重复运行还会引入采样差异，温度、随机种子、工具时延都会让两次运行不同，固定一组种子是控制变量的常见做法。

配对评测还有一个好处：它天然控制了许多变量。同一个任务在两个版本上都跑一遍，任务难度、环境噪声都被共同抵消，剩下的差异更可能来自版本本身。

一个实用的经验是，先估一个大概的样本量，跑一轮，看置信区间有多宽，再决定要不要加样本。区间太宽说明结论不稳，继续加样本比急着下结论更划算。

## 十、切片、失败分类与成本

新版本平均成功率提高，可能同时让高风险任务退化。所以评测报告要按维度切片：任务类型与难度、工具数量和调用深度、是否需要用户澄清、是否包含写操作、上下文长度、失败类型、模型与 Harness 与 Skill 版本。

切片维度最好在跑评测前定义，避免事后挑选对自己有利的切片。事后挑选容易变成"找到一组数字让自己看起来更好"。预先定义能避免这种自我说服。

切片要和团队关心的风险对应。如果业务最怕的是"误删数据"，那"包含写操作的切片"就该是报告里的重点，而不是埋在附表里。让切片服务于决策，而不是为了报告好看。

切片报告的读者是决策者。与其给一堆数字，不如直接说清"哪个版本在哪个场景更好、代价是什么"。信息传达到位，评测才会被用来做决定，而不是被当成走过场。

### 失败分类比通过率更有信息量

两个通过率都是 80% 的版本，可能失败在不同的地方。把失败分成感知、检索、规划、工具、恢复、验证、沟通、Harness 几类，能看清版本改进或退化了哪一块。只看通过率，两个版本看起来一样；看失败分类，差异立刻显现。

```text
感知失败      没读到关键状态
检索失败      没找到证据
规划失败      顺序或依赖错误
工具失败      参数、权限、超时
恢复失败      遇错后重复或放弃
验证失败      错把局部成功当完成
沟通失败      没有澄清或误导用户
Harness 失败  事件、缓存、解析错误
```

失败分类不只是报告，它指导优化方向。感知失败指向工具输出，检索失败指向知识库，规划失败指向上下文和状态，工具失败指向契约。把失败分类和优化目标对应起来，就能避免"所有问题都靠改提示"。

失败分类还要能分类到"可修复"和"不可修复"。有些失败是系统缺陷，可以改；有些是任务本身不可解，改也没用。把两者分开，优化精力才不会浪费。

失败分类还要能追踪趋势。同一类失败在多个版本间是否在减少，比单次的比例更有意义。趋势能说明改进是否真的有效，也能预警正在累积的问题。

### 成本质量前沿

只看成功率会忽略成本。一个版本成功率略高但成本翻倍，另一个版本成功率略低但成本减半，哪个更好取决于业务。把每个版本画成成功率与成本的点，取帕累托前沿，前沿之外的版本被支配，可以直接排除。这样比较的是性价比，而不只是单一指标。

前沿上的点没有优劣之分，选哪个取决于业务对成功率和成本的偏好。前沿的价值是排除被支配的选项，把选择范围缩小到真正值得权衡的几个。

成本的统计要完整，不能只算模型调用。工具调用、环境运行、评测自身的开销都要算进去。漏掉一部分，前沿就会失真。

## 十一、准入门禁

一个候选版本可以采用分层门禁：构建、schema 与基础测试全部通过；安全和权限样本零退化；冻结集总体指标达到非劣标准；目标失败簇有统计上可信的改善；隐藏集无明显过拟合；成本与延迟在预算内。

"非劣"比"平均分更高"更适合持续发布。新版本解决一类问题时，可以允许总体分数在很小范围波动，但关键切片不能越过下限。非劣的门槛也要预先定，例如"安全和权限切片零退化，总体下降不超过 1 个百分点"。有了明确门槛，准入才是判断，而不是感觉。

门禁要能自动化执行，否则每次发布都要人工判断，成本高且容易走样。把门禁写成脚本，接入 CI，发布才可重复。人工只负责处理脚本报出的例外。

门禁还要能解释失败原因。一条"未通过"的输出如果只说"没通过"，团队就得自己查；如果能说清"安全切片退化 3 个百分点"，就能直接定位。可解释的门禁更容易被接受，也更容易被信任。

### 门禁的顺序与形态

把安全和权限门禁放在总体指标之前，是因为安全失败不应该被总体高分抵消。一个版本即使总体提升很大，只要安全切片退化，也不该发布。顺序体现了优先级：硬约束先于优化指标，关键切片先于总体平均。

门禁可以是硬性的，也可以是评分的。安全类适合硬性，不满足即拒绝；效果类适合评分，综合后排序。把安全也做成评分，等于允许用其他分数补偿安全退化。

门禁失败不是终点，而是信号。失败在安全门禁，说明改动越界；失败在效果门禁，说明改动没达到目标；失败在成本门禁，说明代价过高。针对不同的失败门禁，优化方向不同，把所有门禁失败都当成"再调一调提示"，会浪费时间去解决错误的问题。准入门槛本身也要版本化，调松调紧都记录原因和时间，否则过一段时间后没人知道当前门槛为什么是这样。

门禁的阈值也应该定期复核。随着系统成熟，同一套阈值可能变得过松或过严。定期看一眼漏网和误拦的比例，据此调整阈值。

门禁不是越严越好。太严会让任何改动都过不了，团队就会绕过门禁。门槛要设置在"能挡住明显问题、又不阻碍合理改进"的位置，并在实践中调整。

## 十二、灰度、回滚与失败回流

离线数据覆盖不了真实用户的表达、环境和工具异常。通过准入的版本先进入小流量灰度，并保留旧版本作为对照。线上监控任务完成率与人工接管率、工具错误和无效重试、用户纠正或撤销动作、高风险操作的批准率、延迟与费用，以及新出现的失败簇。

每次发布都要绑定不可变版本：模型、系统提示、Skill、工具 schema、Harness 提交、依赖和评测配置。指标异常时才能准确回滚，而不是猜测最近哪个文件变了。

灰度需要有人盯着。自动监控能发现指标异常，但新出现的失败模式往往需要人判断。设定明确的观察期和负责人，灰度才不会变成走过场。

灰度的数据量要够。流量太小，观察到的差异可能只是噪声。根据预估的效应大小确定灰度规模，别用一小撮流量得出大结论。

### 灰度策略与回滚

灰度流量可以按比例、按用户群或按任务类型分配。按比例最简单，按任务类型能更快暴露特定切片的问题。对高风险改动，先在小批特定任务类型上灰度，观察后再扩大。

灰度的价值一半在观察，一半在回滚。如果发现问题却无法快速回滚，灰度只是延长了故障时间。回滚阈值要和准入阈值一样预先确定：关键指标退化超过阈值、出现新的安全失败、或者线上成本超预算，都触发回滚。事后商量要不要回滚，等于在压力下做决定。

回滚能力要提前演练。真出问题时才第一次尝试回滚，往往手忙脚乱。定期做一次回滚演练，能确认流程真的可用。

回滚之后要做复盘。为什么上线前没发现、门禁为什么放行、灰度为什么没拦住，这些问题比"回滚本身"更重要。复盘能把一次事故变成一个改进点。

### 线上指标与失败回流

线上指标和离线指标不一定同向。离线提升的版本，线上可能因为分布不同而没有改善，甚至退化。离线评测负责筛选，线上灰度负责确认；指望离线评测直接预测线上效果，会低估分布差异的影响。

线上出现的新失败要回流到评测集。新发现的真实失败可以匿名化后进入开发集，再构造相邻变体进入冻结集。这样评测集会随系统边界增长，但历史核心样本仍然保留，防止解决新问题时重新引入旧错误。

回归集也需要维护。任务过期、环境变化、预期结果修正，都会让旧样本失效。定期审查回归集，删除失效样本，补充新样本。一个没人维护的回归集会逐渐和真实系统脱节，最后变成一个只反映过去需求的历史文件。

回流要脱敏。线上失败常常包含用户数据和内部信息，进入评测集前必须处理。脱敏不彻底，评测集会变成一个新的泄露点。

线上监控还要覆盖"沉默的失败"：用户不再使用、任务被悄悄放弃、结果被默默绕过。这些不会出现在错误日志里，却反映真实的问题。把它们纳入监控，能发现被忽略的退化。

## 十三、一个端到端例子

用一个具体任务把整条链路串起来。任务是修复一个失败的单元测试，候选版本改进了 Agent 的上下文管理策略。

第一步定义任务契约：写明初始仓库状态、目标测试、允许修改的目录、禁止修改测试文件、成本预算。硬约束是"不能改测试文件"，优化指标是"通过的测试数"和"调用次数"。

第二步做结果与轨迹评测：结果评测运行目标测试和整套回归测试，检查工作区差异；轨迹评测检查 Agent 有没有修改测试目录、有没有越出允许目录、有没有读取不该读的文件。

第三步分层数据：开发集用来复现失败并生成候选，冻结回归集包含已知能通过的任务，隐藏留出集包含一批从未暴露给优化器的任务，用于最终准入。

第四步过门禁：候选在安全切片上零退化，在冻结集上非劣，在目标失败簇上有统计上可信的改善，且成本在预算内，四条都满足才通过。

第五步灰度与监控：候选进入小流量，对比线上失败率、成本和用户撤销率，观察期内某个关键指标退化就回滚到上一版。

第六步失败回流：灰度期间发现的新失败，脱敏后加入开发集，下一轮优化从这些新样本出发，而不是重复优化已知样本。

这个例子里，改动发生在上下文管理策略上，评测覆盖了结果、轨迹和运行三层，准入有明确门禁，发布有灰度和回滚。闭环完整，改动才可信。

这个例子里，"改动发生在哪一层"和"评测覆盖哪几层"要对应。改动在上下文管理，评测就重点看上下文相关的失败；改动在工具契约，评测就重点看工具错误。评测的焦点跟着改动走，才能力度集中。

这个例子可以缩小到一个人也能做的规模：几十个任务、一个脚本、一份报告。规模不重要，闭环完整才重要。先有一个能跑的闭环，再逐步扩大覆盖。

### 这个例子的盲区

这个例子仍有盲区。它没有覆盖用户中途改变目标的情况，也没有测试工具超时后的恢复。这些要靠后续补充任务来覆盖。评测集永远不完整，重要的不是一次覆盖全部，而是持续把线上失败转化为评测样本，让集合随系统一起成长。

盲区要靠真实使用来发现。上线后收集到的失败，比任何预设的盲区清单都更全面。持续用真实失败补评测集，盲区才会越来越小。

盲区要定期重审。今天补上的盲区，明天可能因为系统变化又出现新的。把"审视盲区"变成常规动作，评测才不会慢慢失效。

## 十四、落地清单

搭一套最小可用的评测闭环，可以从几件事开始。先定义任务契约，把结果、权限、证据和预算写成可执行检查；再分三层数据；然后写结果断言和轨迹规则，把能用程序判断的部分先确定下来；接着用标准处理开放质量，并单独评测 Judge；最后设准入门禁、灰度和回滚。

```text
evals/
├── tasks/          # 任务契约
├── fixtures/       # 固定初始环境
├── assertions/     # 确定性检查
├── rubrics/        # Judge 只处理开放质量
├── holdout/        # 与开发集隔离
└── reports/        # 版本、轨迹、结果和成本
```

每次改动按顺序检查：保存候选版本，不覆盖当前稳定版；在临时目录或容器中运行固定任务；先执行确定性断言，再运行 Judge；输出切片结果与失败样本，不只输出均分；满足预先定义的门槛才允许合并；部署后继续记录线上异常并支持一键回滚。

如果现在没有任何评测，最小的一步是：找十个真实任务，写下每个任务的期望结果，跑一遍当前版本，记录通过情况。十个任务也比零个好，它让"改动有没有变好"从感觉变成对比。

清单不是一次做完的。可以先做契约和数据分层，再做断言和门禁，最后补 Judge 和灰度。每加一层，评测的可信度就提高一档。按顺序推进，比一次求全更稳。

### 评测的常见反模式

评测里常见几类反模式：只看平均分，用同一批数据做开发和验收，让候选影响评分器，把 Judge 当成最终裁决，以及没有回滚能力。这些反模式的共同点是让评测失去独立性。评测一旦失去独立性，任何分数都只是候选的自我评价。

还有一个常见误解是"评测一次做完就行"。评测要持续维护：任务会过期，环境会变，隐藏集会泄漏，门禁会失效。把"补充评测样本"做成日常工作，比一次性追求完整更可持续。评测的收益是隐性的，它不直接提升能力，但阻止退化版本进入生产；长期看，它决定了系统能不能持续改进。没有评测的系统不是不能改，而是每次改动都在赌。

元测试最好纳入 CI，每次改动评测器自动跑。人工记得跑 probes 很难长期坚持，自动化才可靠。评测器退化而没人发现，是很多评测失真的根源。
最后，评测的收益是长期才显现的。它不像功能开发那样有即时的产出，但它决定了系统能不能持续、可控地变好。愿意在评测上投入的团队，往往也是能把 Agent 真正用起来的团队。
任务本身也可以被元测试。用一个已知正确的解法跑一遍，看它能否拿到满分；再故意引入一个错误，看分数是否下降。任务如果没有区分度，评测就白做了。
一个健康的评测套件，应该有一部分任务专门用来"抓作弊"。这些任务设计成"只有走捷径才能高分"，一旦候选在它们上异常高分，就是作弊的信号。
最后想强调一点：评测不是一次性的工程，而是随系统成长的能力。它和系统一起演进，也需要和系统一样被认真对待。愿意在评测上持续投入的团队，最终也更能把 Agent 用在真正重要的地方。
成本之外，还有个可靠性问题：Judge 服务本身也可能不稳定。评测流程要对 Judge 的失败有降级方案，例如重试或转人工，而不是让整个评测卡住。
一条好的轨迹规则应该能被一句话解释清楚。如果一条规则需要好几段话才能说清它的边界，那它多半太复杂，应该被拆开或简化。
