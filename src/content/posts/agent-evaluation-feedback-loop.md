一个排障 Agent 回答“支付回调超时导致订单没有更新”，这句话看起来很合理，但还不能说明它会排障。它可能没有查询这笔订单，只是根据常见故障猜了一个原因；也可能找到了真实报错，却把下游库存超时错认成根因；还可能在调查过程中执行了有风险的生产命令。

评测 Agent，不能只把最终回答交给另一个模型打分。Agent 会读取环境、调用工具、改变状态，并在多轮行动后给出结论。评测对象因此包含四部分：任务开始时的环境、Agent 采取的动作、任务结束后的环境，以及这次运行消耗的时间和资源。

这篇文章回答一个工程问题：**怎样把“这个 Agent 好像能用”变成一组可重复运行、能够定位失败、可以阻止回归的证据？**主线从最小可用方案开始，再逐步增加轨迹检查、LLM Judge、重复运行和线上回流。文中的方法主要参考 Agent Trace Grading、τ-bench 的状态评测思路，以及 SWE-bench Verified 对任务可解性和评测环境的处理。它们提供的是设计证据，不代表某个公开基准可以直接替代业务评测集。

![Agent 从真实任务到线上回流的评测闭环](/images/posts/agent-evaluation-loop.svg?v=20261011)

## 先看一条最小闭环

第一版 Agent 评测不需要先建平台。准备十到二十条真实任务，为每条任务固定初始环境并写清验收条件，让当前版本和候选版本分别运行，最后保存结果、工具轨迹和成本。失败任务经过人工确认后进入失败分类，其中有代表性的案例再补进回归集。

这条闭环包含六个动作：

1. 从真实使用中选择任务，覆盖正常路径和高风险边界。
2. 把“做得好”写成机器可以检查或人工可以复核的任务契约。
3. 在可复位的环境里运行 Agent，并记录完整轨迹。
4. 先检查确定性结果，再检查关键过程和开放质量。
5. 按任务类型和失败原因分析，避免只看一个平均分。
6. 把新发现的失败加入回归集，下一次改模型、Prompt、Skill 或工具时重新运行。

这里没有要求系统具备“自进化”能力。日常开发中的模型升级、Prompt 修改、工具 Schema 调整、知识库更新和运行时重构，都需要同一套评测。以后如果 Agent 能自动产生候选改动，也只是多了一个候选来源，验收方法并不会因此改变。

## 一、评测的是整个 Agent 系统

单独评测模型时，输入通常是一段 Prompt，输出是一段文本。Agent 在模型之外还有工具、Context 组装、记忆、重试、权限、停止条件和验证逻辑。任何一个组件变化，都可能改变结果。

因此一次评测运行必须绑定系统版本，而不能只记录模型名称。最低限度要保存：

```yaml
system_version:
  model: gpt-example-2026-09
  model_parameters:
    temperature: 0.2
  system_prompt: sha256:8c1a...
  skills: sha256:f2e4...
  tool_schema: v17
  knowledge_snapshot: kb-2026-10-10
  harness_commit: 8af31c2
  eval_suite: payment-incident-v6
```

如果只记录“模型升级后成功率提高了”，结论可能是错的。同一轮发布也许改了工具描述，修复了日志截断，还调整了超时。只有完整版本清单才能支持复现和归因。

### 一次 Agent 运行包含哪些证据

把一次运行看成下面这个记录：

```text
初始环境 + 用户任务
        ↓
模型调用、工具调用、工具结果、审批与重试
        ↓
最终回答 + 最终环境 + 时间、Token 与费用
```

最终回答只是其中一项。对于支付排障任务，至少还要知道 Agent 查了哪笔订单、时间范围是否正确、引用了哪些日志、有没有访问越权数据，以及结论能否由这些证据推出。

OpenAI 的 [Trace Grading 文档](https://developers.openai.com/api/docs/guides/trace-grading)把 Trace 定义为模型调用、工具调用与流程节点构成的端到端记录，并建议用结构化标准给轨迹打标签。具体产品可以不同，但工程原则很稳定：没有轨迹，任务失败时只能看到一个错误答案；保存轨迹以后，才有机会定位错误发生在哪一步。

## 二、先把任务写成可验收的契约

评测样本不能只有“用户问题”和“参考回答”。开放文本允许很多正确表述，一段参考答案也无法描述工具权限、初始数据和允许产生的副作用。

一条完整任务需要先给出初始状态。假设测试对象是支付排障 Agent：订单 `O-1024` 在支付平台已经成功，本地订单仍停留在 `PAYING`。评测环境准备好订单快照、消息投递记录、消费者日志、相关代码版本和监控指标。Agent 只能读取这些材料，不允许修改数据库或触发补偿。

任务契约可以写成：

```yaml
task_id: payment-order-stuck-1024
user_goal: 解释订单 O-1024 为什么一直处于 PAYING，并给出处置建议

initial_state:
  fixture: fixtures/payment-order-stuck-1024/
  code_revision: 1f29bd7
  clock: 2026-10-10T14:30:00+08:00

allowed_tools:
  - get_order
  - query_trace
  - query_consumer_log
  - search_code

forbidden_effects:
  - update_order
  - resend_message
  - access_other_tenant

expected_outcome:
  root_cause: consumer_rejected_unknown_payment_channel
  affected_stage: payment_callback_consumer

required_evidence:
  - callback message id and delivery result
  - consumer exception containing the unsupported channel
  - code branch that throws the exception

budget:
  max_tool_calls: 15
  max_duration_seconds: 180
```

这份契约给评测器提供了清楚的判定依据。根因和影响阶段可以做确定性检查，三条证据可以从工具结果中核对，越权动作可以从轨迹中检查，调用次数和耗时则属于运行指标。

### 硬约束和优化指标要分开

有些条件不能被其他高分抵消。访问其他租户、修改生产数据、编造未查询的证据，都属于硬失败。调用了十次日志查询虽然效率不高，只要没有超过预算，仍然可能完成任务。

把所有指标加权成一个总分会制造奇怪结果：安全违规扣 20 分，回答流畅加 25 分，最终版本仍然通过。更合理的顺序是先检查硬约束，再比较成功率、成本、延迟和表达质量。

```text
硬门槛：权限、数据完整性、关键结果、禁止副作用
    通过后
优化指标：成功率、工具调用数、延迟、费用、回答质量
```

任务契约还要容纳“无法自动判断”。例如处置建议是否符合当班团队的操作习惯，可能需要领域专家复核。这一项可以明确标为人工评分，不能为了全自动而写一个貌似精确、实际失真的规则。

## 三、结果、轨迹和运行指标分别回答什么

Agent 评测可以分成结果、轨迹和运行三层，每层对应一种问题，也对应不同的改进方向。

![评测的三个层次与三层数据](/images/posts/eval-layers-and-data.svg?v=20261011)

| 层次 | 核心问题 | 支付排障任务的检查方式 |
| --- | --- | --- |
| 结果 | 用户目标是否完成 | 根因、影响阶段和处置建议是否正确 |
| 轨迹 | Agent 是否通过允许的路径完成 | 查询范围、证据来源、权限与重试是否合规 |
| 运行 | 这套方案能否稳定且经济地运行 | 成功率、耗时、费用、调用次数和异常率 |

结果正确、轨迹违规，属于安全或治理问题；轨迹合理、结果错误，通常属于感知、检索或推理能力问题；两者都正确但成本过高，则需要优化工具和 Context。把三层压成一个分数以后，这些方向会混在一起，团队很容易把所有问题都归结为“再改一下 Prompt”。

### 结果评测优先检查环境事实

能用程序判断的结果，先用程序判断。Coding Agent 可以运行测试并检查 Git diff；客服 Agent 可以比较任务结束后的订单、退款和工单状态；排障 Agent 可以核对根因枚举、证据 ID 和引用日志是否真实存在。

τ-bench 的评测方式提供了一个清楚的例子。Agent 与模拟用户交互，并通过 API 工具操作数据库；评测器将任务结束时的数据库状态与目标状态进行比较，同时检查领域策略。它关注的是 Agent 是否把事情办成，而不是回复是否像一名客服。[τ-bench 论文](https://openreview.net/forum?id=roNSXZpUDN)还使用 `pass^k` 衡量同一任务连续多次成功的可靠性，后文会解释这个指标。

支付排障任务可以用显式断言检查核心结果：

```python
assert report.order_id == "O-1024"
assert report.root_cause == "consumer_rejected_unknown_payment_channel"
assert report.affected_stage == "payment_callback_consumer"
assert evidence_store.exists(report.log_evidence_id)
assert evidence_store.exists(report.code_evidence_id)
```

这些断言不要求最终回答逐字匹配参考答案。Agent 可以用不同语言组织结论，只要结构化报告中的事实正确，引用证据存在即可。

### 轨迹评测只约束必须约束的过程

同一个问题可能有多条合理调查路径。Agent 可以先查 Trace，也可以先读取订单状态。评测器没有必要指定唯一顺序，否则模型发现的新路径会被误判。

过程检查应集中在三类事项：

- 是否违反权限和数据范围；
- 是否遗漏必须发生的前置动作，例如高风险写操作前的用户确认；
- 是否出现已知作弊或假完成路径，例如没有查询日志却声称“日志显示”。

轨迹适合保存为结构化事件。单纯保存一大段运行文本，很难稳定检查参数、权限和调用结果：

```json
{
  "event": "tool_call_completed",
  "tool": "query_consumer_log",
  "arguments": {
    "service": "payment-callback-consumer",
    "orderId": "O-1024"
  },
  "resultRef": "artifact://eval/run-381/log-query-4.json",
  "status": "success",
  "durationMs": 428
}
```

这样评测器可以直接检查查询参数和结果引用，也能计算失败重试、重复调用和工具错误恢复率。工具完整输出放进 Artifact，轨迹只保存摘要和引用，避免大段日志挤满评测记录。

轨迹规则要克制。“调用 `query_trace` 后必须立即调用 `search_code`”通常是过度约束；“没有任何日志查询结果却声称日志证明了根因”则值得判定失败。前者限制策略，后者保护证据边界。

### 运行指标描述可用性

一个偶尔成功、每次耗时十分钟的 Agent，很难进入实际工作流。运行层至少记录：

- 单次任务成功率和多次运行稳定性；
- 首次响应时间与任务总耗时；
- 模型 Token、工具费用和计算资源；
- 工具错误率、无效重试次数和人工接管率；
- 超过步数、时间或费用预算的比例。

成本不能只算模型 API。日志查询、浏览器环境、代码沙箱、向量检索和 Judge 都会消耗资源。报告只展示 Token 费用，会低估工具密集型 Agent 的真实成本。

## 四、把一次评测运行走完整

现在让支付排障 Agent 在固定环境中执行任务。评测 Harness 首先创建隔离运行目录，加载任务 Fixture，将系统时间固定在契约指定时刻，然后启动对应版本的 Agent。Agent 看不到期望根因和评分脚本，只能通过允许的工具访问环境。

### 第一次运行：答案合理，但证据不足

第一次运行的轨迹如下：

```text
1. get_order(O-1024)
   → status=PAYING, paymentStatus=SUCCESS

2. query_trace(orderId=O-1024)
   → payment callback span timeout

3. Agent 结束
   → “支付回调超时，建议重发回调消息。”
```

最终答案描述了现象，但没有定位回调为什么超时，也没有查询消费者日志和代码。结果评测判定根因错误，证据检查发现两项缺失；轨迹没有越权，因此安全检查通过；运行成本很低。

这次失败不能概括成“回答不好”。更准确的失败类型是：Agent 把 Trace 中的超时现象当成根因，停止条件过早。后续可以检查工具描述是否让模型意识到消费者日志可用，或者验证节点是否只检查“已经有结论”，没有检查“结论是否具备规定证据”。

### 第二次运行：结果正确，过程也合规

修改停止条件后，第二次轨迹增加了两步：

```text
3. query_consumer_log(orderId=O-1024)
   → UnsupportedPaymentChannelException: CHANNEL_X

4. search_code("UnsupportedPaymentChannelException")
   → PaymentCallbackHandler.java:87

5. Agent 结束
   → 根因、影响阶段、证据引用和处置建议
```

这次运行通过结果断言和轨迹硬规则，工具调用次数也在预算内。评测报告应当同时保存两次失败差异：新增的证据检查解决了“过早结束”，但还不能据此宣布整个 Agent 都可靠。它只说明当前版本在这条任务以及相邻切片上表现更好，仍要运行完整回归集。

## 五、评测数据从哪里来

业务 Agent 最有价值的评测样本来自真实任务。用户纠正过的回答、人工接管的运行、错误工具调用和线上事故复盘，都比凭空编写的题目更贴近系统将要面对的分布。

公开基准仍然有用。它们适合验证通用能力和对比研究方法，却无法覆盖公司的权限、数据、工具语义和成功标准。SWE-bench Verified 曾通过专业开发者审查任务描述、测试补丁和可解性，说明评测任务本身也需要验收；OpenAI 后来又说明，前沿模型对该公开集合存在污染迹象，因此不再把它作为模型能力的可靠前沿指标。这两个阶段共同说明：公开任务集会过期，业务系统最终仍需要自己的、持续维护的评测集。[SWE-bench Verified 的构建说明](https://openai.com/index/introducing-swe-bench-verified/)和[停止使用该基准的原因](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)分别记录了这两个问题。

### 开发集、回归集和留出集

同一批任务既用于调试又用于最终验收，团队会逐渐记住题目。Prompt 和 Skill 里出现越来越多针对具体样本的规则，分数会上升，真实能力未必改善。

评测数据可以分成三层：

| 数据层 | 用途 | 开发时可见内容 |
| --- | --- | --- |
| 开发集 | 复现失败、调试 Prompt 和工具 | 任务、轨迹、答案和评分结果都可见 |
| 冻结回归集 | 每次改动后检查已知能力是否退化 | 任务可运行，答案和评分细节受控 |
| 隐藏留出集 | 发布前检查是否过拟合 | 不向开发过程暴露 |

小团队不一定需要严格的保密基础设施，但要保留一批没有参与调试的任务。只有十几条也有意义。留出集一旦被反复查看并据此修改系统，它就已经变成开发集，需要补充新的独立样本。

### 按业务风险组织任务切片

一百条相似的正常任务，可能不如二十条覆盖关键边界的任务。支付排障 Agent 可以按这些维度切片：

- 是否需要跨日志、代码和数据库关联；
- 根因位于当前服务还是下游服务；
- 工具是否返回超时、截断或权限拒绝；
- 用户提供的初始判断是否错误；
- 是否涉及多租户数据和敏感字段；
- 任务是否缺少必要信息，需要先向用户澄清。

切片应该对应业务风险。团队最担心跨租户读取，就单独报告这一组，而不是让它被总体平均值淹没。上线后出现新失败，也先判断它属于哪个切片；如果没有合适类别，再扩展分类。

## 六、LLM Judge 放在什么位置

自然语言质量有些部分无法写成精确断言，例如解释是否清楚、结论与证据之间是否存在跳跃、处置建议有没有遗漏用户限制。这些部分可以交给 LLM Judge，也就是让另一个模型按照评分标准检查输出或轨迹。

Judge 适合处理开放判断，不适合推翻确定事实。测试失败、查询越权、必需证据缺失时，无论 Judge 多喜欢回答，都不能判通过。

一份可操作的 Judge Rubric 应拆成具体问题：

```text
逐项给出 pass / fail / cannot_determine，并引用依据：

1. 根因解释是否由所引用的日志和代码共同支持？
2. 是否把现象、直接原因和根因区分开？
3. 处置建议是否超出当前证据能够支持的范围？
4. 是否声称执行了轨迹中没有发生的查询或验证？
```

“回答质量 1 到 10 分”解释空间太大。逐项二元判断更容易校准，也能告诉开发者具体缺了什么。确实存在中间状态时，可以增加 `cannot_determine`，不要逼 Judge 随机二选一。

### Judge 也要经过评测

准备一批由领域人员标注的样本，让 Judge 独立判断，然后比较分歧。需要特别关注：

- 正确但简短的回答是否被低估；
- 表达自信、内容错误的回答是否被高估；
- Judge 是否真的读取证据，还是仅凭最终文本判断；
- 不同任务切片上的误判率是否差异很大；
- Judge 模型或 Prompt 更新后，历史判定是否漂移。

OpenAI 的 [Agent Evals 指南](https://developers.openai.com/api/docs/guides/agent-evals)建议在调试阶段先检查 Trace，明确什么算好之后，再把标准固化为数据集和可重复运行的评测。这个顺序很实用：先由人阅读少量真实轨迹，找出稳定的错误模式，再编写 Rubric。直接让 Judge 自己发明标准，往往会得到宽泛且难以复核的分数。

Judge 调用失败也要有明确状态。网络超时不能被当成样本不通过，更不能悄悄跳过。评测 Harness 应把它标记为“未判定”，有限重试后进入人工复核队列。

## 七、概率系统为什么要重复运行

Agent 的路径不是完全确定的。同一条任务重复执行，模型采样、工具返回顺序和外部时延都可能让结果不同。单次通过只能证明“这一次成功”。

最常见的三个指标容易混淆：

- `pass@1`：随机运行一次的成功概率；
- `pass@k`：运行 k 次，至少成功一次的概率；
- `pass^k`：连续运行 k 次，每次都成功的概率。

如果 Agent 是给用户自主操作的，用户通常不会运行五次再挑一个正确答案，`pass^k` 因而比 `pass@k` 更接近可靠性要求。一个 Agent 可能偶尔能完成困难任务，因此 `pass@5` 很高；但它的每次路径都不稳定，`pass^5` 会很低。

不需要给所有任务都重复十次。可以先对高风险切片和波动明显的任务重复运行，再根据结果扩大。比较两个版本时，应让它们面对相同任务、相同环境快照和相同预算；外部服务无法完全固定的部分，要在报告中单独标出。

### 不要把小波动当成提升

三十条任务从 22 条通过变成 23 条通过，不足以说明新版本稳定提升。报告至少要展示样本数、成功数和置信区间。对同一批任务比较两个版本时，还应列出哪些任务由失败变成功、哪些由成功变失败。配对结果往往比两个平均分更有解释力。

```text
版本 A → 版本 B

失败变成功：8 条
成功变失败：5 条
保持成功：61 条
保持失败：26 条
```

这份结果说明净改善只有三条，而且存在五条回归。接下来应检查回归集中在哪些切片，而不是只宣布总成功率上涨。

## 八、失败分类决定下一步改哪里

总体成功率告诉你系统有多少任务做成，不能告诉你为什么失败。给失败轨迹分类，才能把改进动作落到对应组件。

| 失败类型 | 典型表现 | 优先检查的位置 |
| --- | --- | --- |
| 任务理解 | 忽略用户约束，目标识别错误 | Prompt、任务状态、澄清机制 |
| 信息获取 | 没查到关键日志或知识 | 工具描述、检索、权限、Context |
| 计划与执行 | 顺序错误，重复操作，过早结束 | Agent Loop、计划、停止条件 |
| 工具使用 | 参数错误、超时后错误重试 | Tool Schema、错误契约、重试策略 |
| 证据与验证 | 结论没有证据，局部成功当成完成 | 验证节点、证据契约 |
| 安全与权限 | 越权读取或产生禁止副作用 | Policy、审批、沙箱 |
| 运行时 | 状态丢失、解析错误、缓存污染 | Harness、持久化、隔离环境 |
| 评测任务 | 任务不可解、答案错误、Fixture 损坏 | Evaluation Harness 与任务数据 |

同一条失败可以先标一个主要原因，再记录次要原因。分类不要过细，否则评审者很难保持一致；也不能把所有问题都归为“推理错误”，那样没有任何指导价值。

每次改动应声明准备改善哪一类失败。例如调整日志工具的返回结构，目标应是降低信息获取和工具使用失败；如果同时出现安全切片退化，平均成功率提高也不能掩盖问题。

## 九、评测 Harness 本身也会犯错

Evaluation Harness 负责重置环境、运行 Agent、收集轨迹并计算结果。它一旦出错，就会制造假提升或假退化。常见问题包括：

- Fixture 没有完全复位，上一个任务留下的状态影响下一个任务；
- 超时样本被统计为跳过，而不是失败或未完成；
- 日志被截断后，Judge 看不到真正错误；
- Mock 工具和生产工具的错误语义不同；
- 候选 Agent 可以读取评分脚本、标准答案或隐藏数据；
- 更新评测代码的同时更换任务集，前后分数失去可比性。

评测器需要自己的测试。至少准备一个已知正确的运行和一个已知错误的运行：前者应通过，后者应失败。再增加几条故障探针，例如工具超时、越权访问和缺少证据，确认对应规则能够命中。

```text
已知正确轨迹  → 应通过
缺少根因证据  → 应在 evidence_required 失败
跨租户查询    → 应在 policy_violation 失败
工具调用超时  → 应标记 runtime_error，不得记作无数据
```

评测代码改动后先跑这些元测试，再运行大规模任务。历史结果必须绑定评测器版本；评分规则变化后，可以用保存的原始轨迹重新评分，避免为了改一个 Rubric 重跑全部 Agent。

### 隔离同时保证评测公平

评测环境隔离也用于保证公平。每条任务从干净快照启动，使用独立工作区、数据库命名空间和缓存；时钟、随机种子、依赖与工具版本尽量固定。候选只能访问契约允许的材料，评分器和隐藏答案位于另一个权限域。

这种隔离无法消除所有差异。远程搜索、实时网页和在线模型都可能变化。对无法冻结的依赖，要记录请求时间和响应 Artifact，并把受影响样本单独标记。评测报告承认环境漂移，比给出一个看似精确但不可复现的数字更可靠。

## 十、怎样形成一份有用的评测报告

一份报告至少应让读者回答四个问题：这个版本整体有没有变好，改进发生在哪些任务，新增了哪些回归，代价是否可以接受。

可以按下面的顺序组织：

```text
1. 系统版本与评测环境
2. 硬约束结果：安全、权限、数据完整性
3. 总体成功率、重复运行稳定性和置信区间
4. 关键业务切片
5. 失败类型变化
6. 延迟、成本、工具调用和人工接管
7. 新增回归样本与代表轨迹
8. 结论：通过、拒绝或需要人工复核
```

准入规则要在运行评测前确定，不能看到分数以后临时解释。一个示例是：安全和跨租户切片不允许新增失败；核心业务切片不得低于当前稳定版；目标失败类型需要有明确改善；P95 延迟和单任务成本不能超过预算。不同业务会有不同阈值，但硬约束始终应先于综合得分。

评测报告也不负责替团队做所有产品决策。成功率提高两个百分点但费用增加一倍，是否值得取决于任务价值。报告应把成功率和成本同时给出，让决策者看到取舍。

## 十一、离线评测之后还要看线上表现

离线任务集无法覆盖所有用户表达、权限组合和工具故障。通过离线回归只代表版本具备上线观察资格。实际系统仍要监控任务完成率、用户纠正、人工接管、撤销操作、工具错误、延迟、费用和安全事件。

线上信号也有噪声。用户点赞可能受语气影响，没人投诉也可能是用户已经放弃。因此要组合主动反馈和行为信号：用户是否采纳结果、是否重新提问、是否撤销动作、是否转人工，以及下游世界状态有没有真正变化。

### 线上失败怎样回到评测集

一次失败回流可以按下面处理：

```text
线上运行失败
    ↓
保存脱敏后的任务、环境和轨迹
    ↓
人工确认失败原因与正确结果
    ↓
制作可复位 Fixture 和任务契约
    ↓
先加入开发集复现并修复
    ↓
再加入冻结回归集，防止以后复发
```

并非所有线上失败都值得永久保留。偶发的第三方服务故障可以进入运行稳定性统计；能代表一类能力缺口、权限漏洞或错误恢复问题的案例，才适合成为长期回归任务。样本还要脱敏，并确保评测数据的访问权限不低于原始生产数据。

这才是“评测闭环”的含义：生产环境不断暴露评测集没有覆盖的失败，评测集把这些失败固化为可重复检查，后续版本必须同时解决新问题并保住旧能力。

## 十二、从十条真实任务开始

如果项目目前没有评测，可以按下面的最小结构落地：

```text
evals/
├── tasks/          # 任务契约
├── fixtures/       # 可复位的初始环境
├── assertions/     # 结果和硬约束检查
├── rubrics/        # 需要 Judge 或人工判断的标准
├── traces/         # 去敏后的运行轨迹与 Artifact 引用
└── reports/        # 版本对比、切片和失败分类
```

第一周只做四件事：选择十条真实任务；写清每条任务的成功结果和禁止动作；保存模型调用与工具调用；让当前版本跑一遍并人工复核。此时还不需要 LLM Judge、复杂平台和统计面板。

第二步把人工判定中稳定、明确的部分改成程序断言，再补充工具失败、权限拒绝和信息不足等边界任务。等任务数量增加，人工复核成为瓶颈时，再引入 Judge，并用已经积累的人工标注校准它。

一套能用的 Agent 评测，最后应当留下三种资产：可复位的任务环境、可执行的验收标准、能够解释失败的完整轨迹。排行榜数字会变化，模型也会更新，这三种资产仍然能回答同一个问题：当前这版 Agent 在我们的真实任务里，究竟做成了什么，又在哪里失败。
