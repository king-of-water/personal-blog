一家网店只有一个域名，后面却可以有多个区域、多台入口和多台商品服务器。顾客点开商品 42，到底是谁决定让哪台机器接住请求？先把三个选择连成一条路线，再逐个展开。

## 先看全程：DNS 选入口，NLB 选连接目标，Nginx 选业务实例

假设小店有两个区域，每个区域都有入口，入口后面有两台 Nginx，Nginx 后面有两台商品服务 A、B。顾客只输入一个网址，选择过程分成三步：

![三步主线：DNS 返回区域入口，NLB 选择 Nginx，Nginx 选择商品实例，结果沿请求路径返回](/images/posts/lb-request-mainline.svg)

1. 域名系统 DNS 回答域名对应的入口地址。顾客取得地址后，连接选中的区域入口。
2. NLB，也就是网络负载均衡器，为这条连接选择一台 Nginx，例如 G1。
3. G1 读懂 HTTP 请求，找到商品服务组，再从 A、B 中选择一台处理商品 42。

如果这次选中 A，就是 A 查询商品并返回结果，Nginx 再把响应交回顾客。DNS 只提供地址，商品页面通常不经过 DNS 服务器转发。

先记住三个选择对象：区域入口、连接目标、业务实例。接下来前三节按这条顺序展开，再讲每一层怎样选、故障后怎样改选。它们是部署中的三个环节，不是网络协议的第一、第二、第三层；小网站也不必把三级全部部署齐。

## 一、选择区域入口：DNS 先回答这次连接去哪里

顾客还没建立连接，只知道域名。假设小店有华东和华南两套入口，DNS 根据配置回答其中一套的入口地址；浏览器取得地址以后，才开始向那里连接。

这叫 DNS 调度：通过改变名称查询的回答，影响后续连接的目的地。可以按地域、延迟、权重或主备策略配置；具体能力与健康条件由 DNS 服务提供。它不会解析 `/products/42` 来选商品服务，也不会在浏览器发出每条 HTTP 请求时都重新参与。[Route 53 路由策略](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html)

注意这里有两条路径。第一条是客户端查询域名、解析器取回名称记录；第二条才是浏览器连接返回的入口，传输页面请求。网页数据通常不穿过 DNS 服务器。DNS 是影响连接目的地的控制环节，不是夹在 NLB 前面搬运每个 HTTP 数据包的代理。


![解析器优先使用有效缓存，未命中时询问权威服务；修改记录不会迁移已有连接](/images/posts/lb-dns-cache-choice.svg)

### DNS 权重不等于每百次页面访问精确分配

假设把区域权重设为 80:20。一个递归解析器得到华东地址后，可以把缓存答案提供给大量顾客；某些顾客又会复用已有连接。最终的页面请求比例可能偏离 DNS 查询回答比例。

TTL 指示解析器可缓存记录多久。改权威记录不会主动清掉全部缓存，更不会主动迁移已经建立的连接。因此 DNS 切换通常存在传播窗口，不能承诺改完记录后下一秒所有顾客都改走新入口。[Route 53 的 TTL 与变更传播说明](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-values-basic.html#rrsets-values-basic-ttl)

区域故障时，还需要知道健康检查从哪里执行、检查哪个依赖、什么条件触发返回备用地址。若备用区的商品数据没有准备好，DNS 成功切过去仍然可能给出错误价格。区域选择只改变请求方向，业务数据和写入权限能否接管，是更深一层的容灾问题。

## 二、选择连接目标：NLB 把连接交给一台 Nginx

DNS 已经把顾客带到某个区域，但区域内不只有一台入口代理。假设 Nginx G1、G2 都能处理请求，需要由区域入口决定这条新连接交给谁。

网络负载均衡器 NLB，英文 Network Load Balancer，可以承担这一层。典型四层负载均衡主要依据传输协议、地址和端口处理连接或数据流，将它们交给后端目标。名字里有 Network，不意味着它就是第三层的 IP 路由器；这里“四层”指传输层职责。

以 AWS NLB 的 TCP 流量为具体例子，它使用流哈希等信息选目标，同一条 TCP 连接在存续期间对应一个后端目标。浏览器建立连接 C1 时选到 G1，另一条连接 C2 可以选到 G2。不能把 C1 中后续某个 TCP 段随意交给 G2，否则 G2 不拥有对应的连接状态。[AWS NLB 的目标选择与连接行为](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html)

这里要同时看见选择粒度。NLB 为一条连接选 Nginx；Nginx 解读连接内的 HTTP 请求，再为请求选择应用实例。HTTP/2 的一条客户端连接可以承载许多请求，所以连接数各占一半，不保证 HTTP 请求数也各占一半，更不保证 CPU 消耗各占一半。

四层实现也有不同路径。有的通过地址转换转发，有的采用全代理建立两端连接，还有的支持直接返回等设计。不能看到“四层”就假定所有产品都使用相同回程路径或源地址保留方式。网络访问规则、日志中的源 IP，以及后端如何返回，都要结合实际产品确认。

![NLB 按连接选择 G1 或 G2，Nginx 再把连接内的请求交给商品服务组](/images/posts/lb-dns-nlb-nginx-flow.svg)

图中 DNS 是查询分支，下面才是页面请求路径。连接 C1 选中 G1 后，后续仍经过 G1；G1 可以为不同 HTTP 请求选择不同的应用实例。

### TLS 放在哪里，决定谁能读取请求

一种清楚的部署方式是 NLB 的 TCP 443 监听把加密字节交给 G1 或 G2，TLS 在 Nginx 终止。Nginx 解密后读路径，再通过 HTTP 或 HTTPS 访问应用。另一种方式是在支持 TLS 终止的入口完成握手，再按配置向下游发送。

是否保留客户端 IP 也需要配置与实现支持。如果使用代理提供的额外地址信息，接收方只能信任受控入口，不能无条件相信用户自己填的转发头。否则限流、审计和访问控制都可能使用伪造身份。TLS、源地址和业务路由是三项相关但不同的配置，不能互相替代。

NLB 也必须有自己的可用性设计。云产品的多节点入口、多个可用区，或自建入口的冗余与故障接管，解决的是 NLB 这一层的故障。单独在一台机器上安装一个四层转发程序，并不会因为它叫“负载均衡”就自动高可用。

## 三、选择业务实例：Nginx 读懂请求，再把它交给 A 或 B

现在连接已经交给 G1。假设 TLS 在 G1 终止，G1 解密后拿到 `GET /products/42`，才知道顾客要看商品页。它先按请求找到商品服务组，再从组里的 A、B 选择目标。

这里要区分“路由”和“分配”：路径 `/products/42` 指向商品业务，路径 `/orders/100` 指向订单业务，这是路由；商品业务有 A、B 两个副本，从中选 A，这是负载分配。两个动作发生在相邻位置，但回答的问题不同。

![Nginx 先按 HTTP 路径找到服务组，再在组内选择健康实例，接收结果并响应客户端](/images/posts/lb-nginx-route-select.svg)

### 选中实例以后，请求和响应怎样转交

G1 通过另一条连接向 A 发送请求，A 查询商品 42，返回页面或数据；G1 接收后，再向顾客发送响应。浏览器到 G1、G1 到 A 是两段通信，连接可以分别复用，不必始终一一绑定。

只要 A、B 实现相同业务契约，顾客就不需要知道自己访问了哪台机器。下一个请求可以由 B 完成。HTML、样式和价格查询是不同请求，也可能由不同实例处理。[Nginx HTTP 负载均衡说明](https://nginx.org/en/docs/http/load_balancing.html)

副本要能正确处理同一类请求。若 A、B 各自在内存中维护互不相干的库存，刷新页面就可能看到不同结果；若购物车只保存在 A 的进程内，下一请求交给 B 时可能读不到。负载均衡改变请求目标，不负责合并这些业务状态。

### 为什么这一步叫七层

Nginx 根据 HTTP 的主机名、路径等信息作决定，理解的是应用协议，所以这种工作通常称为七层负载均衡。上一层 NLB 为传输连接选目标，典型职责在四层。只有得到解密后的 HTTP，才能按加密请求里的路径路由。

Nginx 本身也能通过 `stream` 模块代理 TCP/UDP。产品名称不决定它正在做哪一层的工作，实际处理的协议与配置才决定职责。[Nginx stream 模块](https://nginx.org/en/docs/stream/ngx_stream_upstream_module.html)

到这里正常流程已经走完：DNS 给出入口，NLB 选中 G1，G1 选中 A，A 返回商品。下面先放大“从候选中选谁”，再讨论候选失效时怎么办。

## 四、怎样选得合适：轮询、权重、连接与请求

### 请求次数相同，不代表工作量相同

假设十个请求里，九个查普通马克杯，每个很快；另一个需要组合许多优惠信息，耗时明显更长。轮询可以让 A、B 各收到五次请求，但拿到复杂查询的实例仍可能更忙。

权重能表达不同容量。例如 A 是较大规格，给它权重 2，B 权重 1，期望在足够多、条件相近的请求中大致形成 2:1 的分配。它并没有测量每次请求的 CPU 开销；A 的下游数据库变慢以后，固定权重也不会自动理解这个变化。

另一个思路是观察当前负担：新请求优先交给活动连接更少的实例，或交给在途请求更少的实例。Nginx 的 `least_conn` 比较活动连接，并考虑权重；“最少连接”和“最少请求”不能混写，特别是连接内可以并发多个请求时，两者的含义会分开。[Nginx upstream 算法说明](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#least_conn)

| 选择依据 | 在小店里怎样理解 | 仍然可能出什么问题 |
| --- | --- | --- |
| 轮询 | A、B 依次接单 | 订单处理成本不一样 |
| 加权轮询 | 大规格实例多接一些 | 权重过期或实际瓶颈在共享数据库 |
| 最少活动连接 | 优先分给连接较少的实例 | 一条长连接里的工作量可能很大 |
| 最少在途请求 | 优先分给未完成请求较少的实例 | 请求成本不同，统计也可能延迟 |
| 哈希 | 同一个键倾向同一个实例 | 热点键集中，实例变化影响映射 |

实际系统还可能先筛选同区域、同可用区或同版本的候选，再在这些候选中选实例。候选范围缩小以后，即使算法非常公平，也只是在这个范围里公平；如果范围内已经过载，需要另行决定是否跨区域、限流或降级。

### 为什么哈希和会话粘性不能替代状态设计

假设希望同一个顾客总到 A，以复用 A 的本地缓存。可以对用户标识、Cookie 或 IP 做哈希，把同一个键映射到固定目标。它解决的是亲和性，不是保证业务状态永不丢失。

按 IP 分配时，一家公司的许多顾客可能共享出口 IP，流量被集中到一台；按用户分配时，一个超级活跃用户仍可能形成热点。采用一致性哈希可以在节点增减时减少部分键的迁移，但不会让最热的那个键自动拆散到多台。

如果购物车是必须保留的数据，就应由业务选择可靠的共享存储或可恢复设计。粘住 A 只能让正常期间更容易读到 A 的状态，A 宕机后不会凭空把购物车复制给 B。关键状态的生存方式，需要在选择算法之外回答。

## 五、目标失效时：先获得健康证据，再停止选择

把应用 A 关掉，入口还可能在短时间内继续选它。因为配置里存在 A，只说明它是候选，并不证明此刻健康。需要获取新证据，再改变可选集合。

主动健康检查由检查者定期请求目标，例如连端口或访问 `/healthz`。被动检查则从真实请求中观察连接失败、超时等情况。前者可以在没有用户请求时发现故障，后者更接近实际调用路径；两者都有局限。端口能连接，不保证商品数据库可用；一次真实请求失败，也可能是网络抖动或该请求自己的参数问题。

检查还有时间窗口。假设每两秒探测一次，连续三次失败才摘除，在某次探测刚结束后宕机的实例，并不会立即从所有地方消失。门槛低，切换更快但容易误摘；门槛高，判断更稳却可能多让一批请求碰到坏实例。

例如，代理可以在一段时间内累计真实连接失败，达到阈值后暂时避开 A，再经过观察窗口重新允许尝试。哪些状态计入失败取决于代理规则，不能把用户查错商品导致的所有 4xx 都算成机器故障。[Nginx 失败判定参数](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server)

商业版本或其他代理可能提供主动探测等额外能力，需要区分实际启用的是主动探测还是被动观察。云 NLB 的检查和应用层代理的检查也分别针对自己的直接目标：NLB 能连接 Nginx，不说明每一台商品实例都健康。

极端情况下，产品可能采用“全部目标不健康时继续尝试目标”的失败开放策略，而不是统一停止转发。AWS NLB 文档明确描述了相应情形，所以“负载均衡绝不把请求交给不健康目标”不是无条件承诺。[NLB 健康检查与失败开放](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/target-group-health-checks.html)

### 恢复与下线都需要过渡

实例刚启动，可能尚未加载商品规则、建立连接池或预热缓存。应该在可以接业务时再进入候选集合，必要时逐步增加流量。否则新实例虽然端口已经开着，却会被第一批真实请求压垮。

计划下线时也不要先杀进程。先停止给它分配新工作，等待已接收请求完成，在宽限期结束后再关闭。这个过程叫连接或请求排空。不同层的排空对象不同：四层入口面对连接，七层入口还需要处理同一长连接上是否继续接收新请求。

尤其是 HTTP/2、gRPC 和 WebSocket，连接可以存活很久。只把实例从新连接候选中删除，旧连接仍可能产生新工作。需要相应协议的退出信号与期限管理；超过期限的请求如何重试或恢复，也要另行约定。摘除不是把正在执行的业务瞬间搬到另一台。

## 六、失败后改选：先区分读取、写入和结果未知

顾客读取商品失败，入口改向 B 查询，通常容易理解。但如果请求变成 `POST /orders`：A 已经创建订单，只是响应回来的时候断了，入口再把同样内容发给 B，就可能创建第二笔订单。

这时“连接失败”和“结果未知”需要分开。能确认请求还没交给任何业务实例，与发出后没拿到响应，提供的证据不同。即便入口自身知道某次尝试失败，也未必知道上游数据库有没有提交。

Nginx 的 `proxy_next_upstream` 控制哪些情况可以尝试下一个上游；非幂等方法在请求已发送之后，默认有额外限制。启用 `non_idempotent` 等选项会改变重试行为，不能为减少错误页面就直接打开。响应内容已开始发送给客户端后，也不能随意从另一台重新返回一份完整响应。[Nginx 上游重试规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream)

需要安全重试的写操作，应使用同一业务编号，由服务端确认原结果、阻止重复生效。重试还受总等待预算约束。浏览器、网关、RPC 客户端若各自重试三次，底层尝试数可能放大；目标已经过载时，这些额外流量会拖慢恢复。[超时后怎样安全重试](/posts/timeouts-retries-idempotency-exactly-once/)解释了业务幂等键与结果查询。

超时也分不同阶段：建立上游连接的等待、两次读取之间的等待、整项业务的总截止时间，并不是同一个限制。某一层设置最大尝试次数，也不会自动约束所有更深的调用。

![失败后先判断是否已经产生业务效果；只在语义允许且预算足够时重试，实例下线先排空再退出](/images/posts/lb-failure-retry-drain.svg)

图中的判断依赖能够获得的证据。结果未知时，不能把“换一台”当作已经证明前一次没执行；换机器改变目标，不会擦掉数据库里可能已存在的订单。

## 七、回到完整路径：每一级负责什么，什么时候需要它

回到开头那张图，顾客先解析名称，拿到某个区域入口；NLB 为连接选择 G1；G1 接收并解密 HTTP，按路径找到商品组，再选择 A；A 返回商品，响应经 G1 和入口回到顾客。另一请求可以选 B，而已有 TCP 连接仍可能一直经过 G1。

此时每一层都要留下与自己职责相符的证据。DNS 看解析回答和区域分布；NLB 看连接、目标健康和流量；Nginx 看请求、上游地址、各段耗时和重试；应用看请求编号、业务状态和数据库结果。四处都写一个“成功数”，却不知道分母是查询、连接还是请求，数字就无法对齐。

例如所有应用都慢，先查共享数据库、入口容量和重试放大，不能只把 A 的权重减半。只有少数用户慢，则要结合区域入口、长连接、哈希键和网络路径。总连接数很均匀但某台 Nginx CPU 高，可能是连接内请求数量与处理成本不同，需要继续看 HTTP 层。

| 当前规模或需求 | 可以先采用的结构 | 扩展前必须确认 |
| --- | --- | --- |
| 单机学习或很小的网站 | 一个入口与一个应用 | 备份、进程恢复和监控 |
| 应用需要多副本 | 七层入口 + 应用组 | 状态共享、超时和入口单点 |
| 入口也需要冗余 | 四层入口 + 多台七层代理 | 入口高可用、连接排空与地址传递 |
| 多区域部署 | DNS 调度 + 区域入口 | 数据接管、缓存窗口与跨区成本 |
| 已有托管七层产品 | 由托管入口承担相应职责 | 实际功能、配置、限制与故障边界 |

托管应用负载均衡器可以承担 Nginx 的一部分入口职责，四层入口也可以直接把流量交给应用。只有一台应用的小站，不必为了画齐架构而人为加三层。每增加一层，都增加连接、配置、日志与故障边界，收益需要对应真实问题。

负载均衡最终要回答三件具体的事：现在有哪些可用目标，这次按什么粒度和规则选择，失败或变更后怎样停止旧选择并恢复。算法负责其中一部分；连接生命周期、健康证据和业务重试语义接上以后，整个入口才具备可解释的行为。
