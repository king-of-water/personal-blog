打开这个博客时，你会看到首页、栏目、文章目录，以及浏览量和点赞。它们出现在同一个网页上，实现方式却不相同：文章正文在发布前就已经生成，浏览量和点赞要等你打开页面后，再向接口查询或写入。

如果只用“Astro、GitHub、Cloudflare Pages”介绍这个项目，很容易漏掉这些区别。下面沿着一篇文章从本地文件到读者浏览器的过程，解释每一步是谁做的、数据保存在哪里，以及哪一步失败会影响什么。实现细节对应本站代码；平台的构建、绑定和回滚能力则参考各自的官方文档。

## 一、为什么这样搭：文章先生成，互动单独处理

这个网站首先是一个长期写作和阅读的地方。后端知识、Agent、行业理解和项目记录会持续增加，但一篇文章写完以后，并不需要根据不同读者重新生成一遍正文。

例如这篇项目说明，上午十点和下午两点打开，标题和正文通常没有区别。只有我修改文件并重新发布，它才应该变化。因此可以在发布时把 Markdown 转换成 HTML，也就是浏览器直接能显示的网页。读者访问时，托管平台把已经生成的文件交给浏览器，不必再查询文章数据库、运行模板，然后拼出正文。

这里的“静态”说的是正文生成的时机，并不要求页面不能动。鼠标悬停时卡片放大、目录跟随阅读位置、点击按钮点赞，都可以在浏览器里完成。真正需要服务器参与的，是把多个读者产生的数据保存到同一个地方。

如果浏览量只存在我的电脑或某个读者的浏览器里，别人就看不到相同的总数。如果把数字写进文章文件，下一次访问也不会自动改变。因此本站把这部分放进一个小型后端，用 Cloudflare Pages Functions 接收请求，再写入 Cloudflare D1 数据库。

各个工具在项目里的职责可以这样理解：

| 部分 | 实际负责什么 | 不负责什么 |
| --- | --- | --- |
| Markdown 文件 | 保存正文、标题、分类和文章日期 | 不接收读者的点赞 |
| Astro | 读取内容，套用组件，生成文章页和栏目页 | 本站没有用它实时查询数据库生成正文 |
| Git 和 GitHub | 保存源码版本、查看修改、提供部署需要的提交 | 不直接向读者提供本站页面 |
| Cloudflare Pages | 托管构建后的网页、样式和图片 | 不负责判断文章讲得是否清楚 |
| Pages Functions | 处理浏览量与点赞接口 | 不承担正文渲染 |
| Cloudflare D1 | 保存共享的计数和点赞记录 | 不保存本站 Markdown 正文 |

这套结构适合当前的个人博客：文章可以用熟悉的编辑器写，内容修改也能像代码一样看差异、提交和回退。页面主体不用依赖统计数据库的状态。

它也有成本。新增或修改文章需要经过构建，不能像带管理后台的网站那样，在浏览器中点一下保存就立即更新所有页面。多人协作、审核流、登录和付费阅读也没有现成实现。如果将来需要这些功能，就要重新评估内容管理和权限系统，不能只给现有页面多加几个按钮。

## 二、一篇文章在仓库里是什么样的

文章保存在 `src/content/posts/`。比如这篇的文件名是 `how-this-blog-works.md`，正文就在文件里，不需要先把它导入数据库。图片和流程图则放在 `public/images/posts/`，正文通过图片路径引用。

一篇文件开头的两道 `---` 之间，是描述文章的信息，通常叫 frontmatter。它和正文承担不同工作：正文回答技术问题，头部信息决定这篇文章怎么出现在网站里。

下面是一篇后端文章的头部示例，正文内容省略：

```yaml
---
title: 限流算法：窗口、漏桶与令牌桶怎样选择
description: 从请求到达和放行的过程，理解常见限流算法的区别。
category: 后端
subcategory: 系统设计与高并发
articleClass: focused
seriesOrder: 120
publishedAt: 2026-10-10T10:00:00+08:00
tags: [限流, 高并发]
draft: true
---
```

`title` 和 `description` 用于文章标题、摘要以及页面描述。`category` 是“后端、Agent、行业、项目”这样的大栏目；`subcategory` 则用于 Java、Redis、分布式等更具体的专栏。分类会影响栏目归属、面包屑和左侧文章列表，不只是展示一个标签。

`publishedAt` 是首次发布日期，`updatedAt` 用来记录之后的修改。当前首页最近更新和归档列表，实际按 `publishedAt` 倒序排列，所以补写旧文章并不会因为更新了 `updatedAt` 就自动跑到列表最前面。这是当前排序规则，不应该把字段名当成已经实现的功能。

`seriesOrder` 决定专栏中的学习顺序。假设入门篇是 10，进阶篇是 20，后来补一篇基础解释，可以用 15 放进中间，不必把全部编号重写。这个值是排序依据；界面展示的 01、02、03，是排序后按位置生成的序号，并不直接显示 10、15、20。

`articleClass` 是写作和审查时区分文章范围的字段，表示长篇系统说明、单个机制解释或较小的记录。它不会让浏览器采用不同的数据存储方式。`tags` 则用于表达这篇文章涉及哪些主题，和栏目归属可以同时存在。

### 怎么避免分类和日期写错

`src/content.config.ts` 定义了文章集合的规则。集合可以理解成“用同一套规则读取的一组文章”。这里用 `glob()` 找到目录里的内容文件，再用 Zod 校验字段。Zod 在此负责检查数据形状，例如标题应该是字符串，分类必须是预先允许的名字，日期要能被转换为日期对象。

如果把 `category` 写成不存在的栏目，构建会暴露错误，而不是等上线后才发现这篇文章丢在所有列表之外。这比每个页面临时猜测文章属于什么地方更容易维护。[Astro 内容集合文档](https://docs.astro.build/en/guides/content-collections/)

但字段校验只能检查程序能判断的东西。日期格式合法，不代表日期填写正确；正文能转换成 HTML，不代表技术结论没有问题。代码规则和文章内容审查仍然是两件事。

### 草稿隐藏到什么程度

当前文章路由和列表读取内容时，都会过滤 `draft: true`。因此草稿不会生成公开文章页，也不会进入公开栏目、归档和首页精选。仅仅从首页移除一个链接不够，因为原文章地址可能仍然存在；本站是在生成路由这一步就排除草稿。

不过，这不是保密措施。如果源码仓库公开，别人仍然可能在 GitHub 中看到草稿文件，旧提交中的内容也不会因为设置草稿而消失。已经发布过的内容，还可能存在于搜索缓存和历史副本中。

所以“暂时不让网站读者看到”和“内容不能泄露”需要不同处理。待检查的普通技术笔记可以用草稿字段；公司内部材料、访问令牌和私人信息，就不应提交进公开仓库。

## 三、Markdown 怎么变成一个能打开的网页

`src/pages/` 决定网站有哪些页面。比如 `index.astro` 对应首页，`projects.astro` 对应项目页。所有文章则共用 `src/pages/posts/[...id].astro` 这个模板，不是每写一篇文章就复制一个页面组件。

模板文件名里的 `[...id]` 表示地址中这部分由内容决定。本篇文件产生的文章 ID 是 `how-this-blog-works`，对应地址就是 `/posts/how-this-blog-works/`。这里虽然使用动态路由模板，但本站仍在构建时生成具体页面；“路由参数是动态的”并不意味着读者访问时必须运行服务器渲染。

关键代码很短：

```ts
export async function getStaticPaths() {
  const posts = await getCollection('posts', ({ data }) => !data.draft);
  return posts.map((post) => ({
    params: { id: post.id },
    props: { post },
  }));
}
```

`getCollection()` 先取出非草稿文章。随后每篇文章返回一个具体地址参数，以及这张页面需要使用的文章对象。Astro 按这份清单逐张生成网页，不需要读者先访问一次才能出现页面。[Astro 路由文档](https://docs.astro.build/en/guides/routing/)

模板拿到文章后，再执行 `render(post)`。结果中有正文组件 `Content`，也有标题信息 `headings`。模板把 `<Content />` 放进正文区域，把标题、摘要、日期和分类放进文章头部，把符合条件的章节标题放进目录。

![文章文件经过校验、草稿过滤和页面模板，生成可发布的静态文件；校验失败时停止构建](/images/posts/blog-content-build-flow.svg)

整个过程发生在本地构建或部署平台的构建环境里。成功后，输出目录 `dist` 中已经有对应文章的 HTML，以及浏览器需要的样式、脚本和图片。读者拿到的不是一份等着前端程序再解释的 Markdown。

这也说明了为什么发布文章不只是上传一个 `.md` 文件。正文改动以后，文章页要重新生成；标题和摘要变化以后，引用它们的栏目卡片也要更新；新增文章以后，归档和专栏列表也需要重新计算。

### 文件名、栏目和精选不是同一套规则

文件名会影响文章地址，所以文章公开后，修改文件名比修改标题更需要谨慎。标题可以从“缓存基础”改成更具体的问题，原地址仍保持不变；文件名改了，旧链接就可能失效。要迁移地址，应同时考虑旧地址的跳转，不能只检查新页面能否打开。

栏目页面从同一个文章集合筛选内容。比如后端下面的 Java 页，找出大栏目为“后端”、子栏目为“Java”的文章。栏目中文名字与网址片段的对应关系保存在 `src/config/sections.ts`，因此界面上可以显示中文，地址仍采用稳定的英文片段。

这里还做了一个有意保留的兼容：现在栏目叫“工程原理与选型”，它的网址仍然是 `data-structures-storage`。栏目改名并不一定要把已经流通的地址全部换掉。Agent 的一些旧栏目路径，则在 `astro.config.mjs` 中配置了跳转。

首页精选采用另一种方式：`src/pages/index.astro` 显式保存了五篇文章的 ID，按指定顺序读取它们。它不会因为一篇文章写了 `featured: true` 就自动收录。目前精选包括 Harness、分布式 ID、Muse，以及数据结构和缓存局部性两篇。

这样做是为了保持首页的阅读入口稳定，不让每次发布都改变推荐顺序。代价是想换精选时，需要修改首页那份 ID 清单。要是某个 ID 对应草稿或找不到的文章，首页会跳过它，不会把一个无法打开的占位链接展示出来。

## 四、文章越来越多以后，阅读界面怎么组织

页面共用 `BaseLayout.astro`。它负责 HTML 外壳、页面标题和描述、导航、页脚、全局样式，以及全站统计脚本。文章模板负责文章自己的结构，不用再重复实现一份顶部导航。

在 Astro 中，组件开头 `---` 里的代码用于生成页面；写在 `<script>` 中的交互代码才会交给浏览器执行。本站没有因为使用组件，就把整套文章列表和正文渲染逻辑发到浏览器里重新运行。[Astro 组件文档](https://docs.astro.build/en/basics/astro-components/)

桌面文章页有三个阅读区域：左侧看同栏目有哪些文章，中间读正文，右侧看当前文章的章节。左侧解决“接下来读什么”，右侧解决“这一篇读到哪里”。它们虽然都能跳转，内容来源却不同，不能简单复制同一份目录。

左侧专栏列表按 `seriesOrder` 排序，正在阅读的文章会高亮。当前专栏默认展开，页面初始化时还会把当前文章滚到侧栏可见区域内，避免专栏一长就只能看到前面几篇。

右侧目录来自正文中的二级、三级标题。模板取 `headings` 中深度为 2 或 3 的条目；数量至少三个时，才显示目录。作者修改标题以后，下一次构建会生成新的目录，不用手动维护另一份链接。

读者向下滚动时，浏览器脚本根据页面滚动位置和章节位置判断当前章节，更新目录高亮。如果高亮条目已经跑到右侧可见区域之外，侧栏会滚动到能看到它的位置。滚动事件通过 `requestAnimationFrame()` 合并更新，避免每触发一次事件都立即重复修改页面。

脚本还会用 `history.replaceState()` 更新地址里的章节片段，例如网址末尾的 `#某个章节`。它不为每次滚动新增一条浏览历史，因此按浏览器返回键时，不会逐个倒退刚才读过的所有章节。直接打开带章节片段的链接时，页面会在加载后对齐对应位置。

手机上没有足够宽度同时放下三栏，所以布局会收起桌面侧栏，文章内保留可用的目录入口。代码块、表格和图示也必须按正文可用宽度处理；否则桌面看起来整齐，手机却可能被一段 SQL 撑出横向滚动。

文章底部的上一篇、下一篇也分情况：设置了系列顺序、并且属于具体子专栏的文章，沿该专栏的顺序导航；其余文章按发布时间导航。因此一篇 Java 系列文章看完后，可以继续读相邻章节，而不是跳到刚发布的另一篇行业文章。

### 为什么首页会有动效，正文没有一直动

首页的标题、头像、精选卡片等，是进入内容的入口。鼠标悬停时轻微缩放或位移，能让读者知道哪些位置有交互。主要效果由 CSS 的状态选择器、`transform` 和过渡实现，不需要单独引入 React 来驱动整个页面。

阅读正文时，持续移动的背景和大幅弹跳会干扰注意力，所以这些反馈集中在入口和操作控件上。现有样式还考虑 `prefers-reduced-motion`：这是浏览器表达用户希望减少动态效果的设置。相应条件下，入口的弹性效果会减少或停用。

首页浏览量旁边的说明浮层则需要少量 JavaScript。鼠标移入可以打开，键盘聚焦也能打开；点击可以固定展示，点击外部或按 Escape 关闭。手机用户可以通过点击查看，不必模拟桌面悬停。

浮层展示的是计数说明，打开它不会额外查询数据库，也不会再增加一次浏览量。控件用 `aria-expanded` 告诉辅助工具当前是否展开，用明确的按钮让键盘用户也能触发。视觉效果、数据请求和可访问性分别处理，能减少一个小改动牵连整个页面的情况。

## 五、浏览量到底怎么保存和累加

统计数据保存在 D1。可以把 D1 理解成由 Cloudflare 托管、供接口执行 SQL 的数据库。浏览器不直接连接它，而是访问本站 `/api/` 下的地址，接口再通过名为 `DB` 的数据库绑定执行查询。

绑定就是运行环境交给接口的一份访问能力。代码使用 `env.DB`，不需要把数据库访问凭据写进发给浏览器的 JavaScript。绑定可以通过平台配置；配置变更后需要重新部署才能生效。[Pages Functions 的 D1 绑定说明](https://developers.cloudflare.com/pages/functions/bindings/#d1-databases)

仓库中 `migrations/0001_post_stats.sql` 定义了两张表。`post_stats` 按文章 ID 保存累计浏览量和点赞数；`post_likes` 保存某个匿名浏览器对某篇文章的点赞记录。后者以“文章 ID、访客哈希”作为联合主键，避免数据库中出现两条完全相同的点赞记录。

先看一次正常的文章访问。假设这篇文章已有 100 次浏览，这个浏览器今天还没访问过它：

1. 浏览器先收到文章 HTML，显示标题、正文和图示。
2. 文章脚本检查本地存储。如果还没有匿名访客 ID，就生成一个随机 ID，留在这个浏览器里供后续使用。
3. 脚本检查“这篇文章今天是否计数”的标记。没有标记，就向 `/api/stats/how-this-blog-works` 发出 `POST`，请求体包含 `action: view` 和访客 ID。
4. 接口校验参数和数据库绑定，必要时建立这篇文章的统计行，再执行数据库中的加一操作。
5. 接口读出统计结果，返回浏览量、点赞数和当前浏览器的点赞状态。
6. 浏览器更新数字，并在收到成功结果后写入当天的本地标记。此后同一天刷新这篇文章，走查询接口，不主动再次加一。

![正文先显示，统计脚本根据当天标记决定查询还是加一；接口不可用时仍可阅读正文](/images/posts/blog-reading-stats-flow.svg)

计数没有采用“先读出 100，在代码里加成 101，再写回去”的方式。否则两个请求同时读到 100，可能都写回 101，丢掉一次加一。当前接口直接执行：

```sql
UPDATE post_stats
SET views = views + 1, updated_at = CURRENT_TIMESTAMP
WHERE slug = ?;
```

加法由数据库执行，参数通过绑定传入。不过，这只解决多个写请求之间的累加问题，不代表同一个读者的重复请求会被服务器识别。只要合法的加一请求确实到达并执行，它就可能计数。

### 首页总数为什么不只统计首页

文章访问使用 `/api/stats/:slug`。首页、栏目、项目、归档等非文章页面，则由共用布局加载的 `src/scripts/site-stats.ts` 上报到 `/api/site-stats`。

非文章计数集中放进 `post_stats` 的一个保留行 `@site-pages`。这个名字不能作为普通文章接口允许的 ID，便于和文章记录区分。首页总浏览量通过下面的查询得到：

```sql
SELECT COALESCE(SUM(views), 0) AS views FROM post_stats;
```

因此它包含已有文章的浏览量，以及全站非文章统计上线以后记录的访问。以前没有记录过的栏目访问，不能事后从文章数量或 Git 历史推算出来；这个总数也不是从建站第一天开始完整记录的所有请求。

共用脚本会检查页面是否存在文章统计节点。有这个节点，就不再向非文章接口上报；非文章接口也拒绝文章路径。文章打开一次不会同时给文章行和 `@site-pages` 各加一次。

为了复用现有数据库，这个实现只保留非文章访问的合计，没有给每个栏目保存单独的明细。因此可以展示全站累计值，却不能直接回答“Java 栏目昨天来了多少人”“哪篇文章带来了后续阅读”等分析问题。

### 为什么这个数字不能当成真实访客人数

当前去重发生在浏览器本地存储中，规则是同一浏览器、同一页面、同一个世界协调时间（UTC）日期尽量计一次。这个日期从 `toISOString()` 中取出，对应北京时间每天 08:00 换日，不是北京时间零点。

一个人今天打开三篇不同文章，可以贡献三次计数。相反，同一浏览器同一天刷新同一篇很多次，通常只贡献一次。所以它既不是每次刷新都计数的严格页面浏览次数，也不是一天只算一次人的独立访客数。

换浏览器、使用新的浏览器配置或清理本地存储，都会失去旧标记。两个标签页在标记写入前同时打开，也可能同时上报。关闭 JavaScript 的访问不会执行这套脚本，直接调用公开接口则可能绕过前端去重。

还有一种容易忽略的情况：数据库已经成功加一，但响应在网络中丢失。浏览器没收到成功结果，就不会写入本地标记。下次刷新仍可能再次上报，导致重复。这是“数据库已执行”和“浏览器已确认”之间的差异，当前没有服务器端请求幂等键来消除它。

因此这个数适合展示博客的累计阅读活动，不适合拿来证明增长效果、结算费用或防刷。若以后需要可靠的访问分析，要先明确统计口径，再考虑服务端去重、机器人识别和数据保留规则，而不是只把数字显示得更精确。

## 六、点赞、失败和数据库边界

点击“赞一下”时，浏览器向同一个文章接口发送 `action: like`。接口把“文章 ID 加访客 ID”计算成 SHA-256 哈希，在 `post_likes` 中查有没有对应记录。

没有记录，表示这个匿名浏览器尚未点赞：接口写入点赞记录，并给文章点赞数加一。有记录，则删除该记录，并把点赞数减一，表现为取消点赞。返回结果里的 `liked` 决定按钮显示“赞一下”还是“已点赞”。

这里的匿名 ID 用来维持同一浏览器的状态，不是账号，也不能证明两个浏览器背后是否是同一个人。哈希用于保存这个组合标识，不应把它说成完整的身份认证或隐私保护方案。

一条点赞记录和一个点赞总数要同时变化，否则可能出现“已经有点赞记录，总数却没增加”。代码把对应的两条 SQL 放进 D1 的 `batch()` 中执行。这个方法提供批量语句的事务处理，失败时会回滚批次内的修改。[D1 batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

但查“之前有没有点赞”发生在批次外。两个并发请求仍可能同时查到没有记录，之后其中一个插入遇到联合主键冲突；并发取消点赞也不能仅凭这个批次就证明计数永远正确。浏览器在请求期间禁用按钮，减少单个页面连续点击，却挡不住多个标签页或直接接口调用。

请求超时后的自动重试也需要谨慎。因为当前操作是“切换点赞状态”，成功后丢失响应，再重发同一操作，可能变成取消点赞。如果以后希望重试安全，应让请求明确表示目标状态，例如“我要处于已点赞状态”，并把并发条件更新和幂等处理一起设计好。本站当前没有把这些能力包装成已经完成的保证。

### 统计服务坏了，文章还能不能看

可以。文章 HTML 不需要统计接口参与生成。接口不可用时，首页显示“暂不可用”；文章页则保持统计区域隐藏或保留之前的状态，不把读取失败解释成零次浏览，也不阻止读者看正文。

数据库绑定缺失时，接口返回 503；请求体或参数不符合要求时，返回 400。若数据库还没有执行建表迁移，即使绑定名正确，SQL 也可能失败。排查时需要分清“函数拿不到数据库”和“拿到了数据库但表不存在”，不能只反复刷新网页。

浏览器存储也是依赖。非文章统计脚本捕获了存储不可用的情况，退回只读总数、不增加计数。文章统计初始化直接读写本地存储，当前还没有同样完整的异常兜底；严格限制存储的浏览器可能因此无法显示互动部分，但已经生成的正文仍然存在。

接口目前还比较轻量。它检查文章 ID 的格式，但没有逐个验证 ID 一定对应已发布文章；公开接口也没有完善的认证和防刷。因此格式合法的任意 ID 可能产生统计记录，总和也就不能视为严格审计过的阅读数据。这些是当前实现的边界，后续增强时应先补接口约束，而非只调整前端显示。

## 七、从本地修改到网站发布，中间发生什么

本地开发使用 Node.js 和 npm。仓库声明的 Node.js 下限是 `22.12.0`，开发和部署环境都应满足这个约束。安装依赖后，可以按项目约定用后台模式运行开发服务：

```sh
npm install
npx astro dev --background
npx astro dev status
```

结束开发时用 `npx astro dev stop`；需要查看运行情况时用 `npx astro dev logs`。开发服务会让内容和样式改动更快显示出来，但预览正常并不能代替一次正式构建。

本地的 `astro dev` 主要服务 Astro 页面，并不会自动运行根目录下的 Cloudflare Pages Functions。因而本地文章能打开，统计却暂不可用，是两个运行环境的区别。要验证完整接口，需要 Pages 的函数运行环境、相应 D1 绑定和已初始化的数据表，不能在页面里写一个假数字当成验证通过。

假设我要发布一篇后端限流文章，完整操作会是这样：

先在 `src/content/posts/` 建立内容文件，补好标题、描述、分类和日期。还没审完时保留草稿状态。图示放进文章图片目录，正文引用对应路径；这样内容和图示可以在同一个提交里维护，不需要把图上传到另一个后台再拼链接。

随后检查正文和图示，确认文章可公开，再把草稿状态改为 false。文章列表、栏目页和侧栏会在构建时从内容集合重新计算，不需要手工到几个页面各复制一次标题。如果想把它放到首页精选，则要另外修改首页的精选 ID 清单。

提交前先运行文章审查，再执行 `npm run build` 和 `git diff --check`。构建能发现内容字段错误、模板导入问题等；图示还要检查是否能解析，生成的文章也要检查目录、代码块和图片。它们验证的范围不同：构建成功不代表图片里的小字可读，更不代表解释已经准确。

完成检查后用 Git 提交。提交是一份可以追踪的修改记录，推送则把本地提交交给 GitHub。Cloudflare Pages 连接仓库后，可以根据生产分支的更新触发构建；这个项目的构建命令是 `npm run build`，输出目录是 `dist`。[Pages Git 集成说明](https://developers.cloudflare.com/pages/configuration/git-integration/)

平台拿到该提交，安装依赖，执行构建，再发布生成的静态资源，并处理仓库中的 Functions 代码。数据库仍然是单独的资源：接口发布了，不代表 D1 自动建表；源码中有 SQL 文件，也不代表生产数据库已经执行过它。首次接入时，要完成建库、迁移和 `DB` 绑定；日常修改正文不需要改数据库，表结构变化则要单独处理迁移。

读者最后访问新文章时，先拿到这次部署生成的网页；正文显示后，统计脚本走前面介绍的独立请求。文章发布和计数更新因此不在同一个时点，也不必依赖同一条请求完成。

### 提交成功、推送成功、部署成功分别说明什么

提交成功，只说明本地仓库保存了修改。推送成功，只说明 GitHub 收到了提交。平台构建成功并完成部署，才说明新版本可以从对应部署地址访问。生产域名是否已经显示新内容，还应以实际页面和部署记录为准。

如果新的构建失败，它不会因此生成一个能正常上线的新版本；网站可以继续使用已有的成功部署。排查重点是部署日志中的失败步骤，例如依赖、Node.js 版本、字段校验或模板错误。只看到 GitHub 里有新文件就认定上线，会把这个问题藏起来。

若新版本成功部署却有界面问题，可以用平台支持的回滚能力切回之前的成功生产部署，也可以在源码中修正或撤销相应修改后重新发布。[Pages 回滚说明](https://developers.cloudflare.com/pages/configuration/rollbacks/)

不过，回滚网页或函数版本，不会自动把 D1 中的浏览量、点赞和表结构恢复到过去。代码和数据库是两份不同状态。涉及数据库结构变更时，需要考虑旧代码还能否读取新结构，不能把 Git 回退等同于整个系统回到昨天。

## 八、现在维护什么，哪些能力还没有做

这套实现省去了自己管理常驻服务器的工作，但仍需要维护依赖、发布配置、域名、数据库结构和内容。托管服务有套餐额度和限制，统计接口执行次数、数据库读写量也会随访问增加而变化。费用应根据实际用量和当时的平台套餐核对，不能从“静态博客”推出永远没有运行成本。

Markdown 和 Git 对当前写作习惯很合适：修订可以看差异，文章、图片和代码可以一起保存，换托管平台也不必先导出一个专用内容数据库。另一方面，当前流程依赖编辑器和 Git，不熟悉它们的作者会觉得不方便；文章数量继续增加，全量构建和内容检查的时间也需要关注。

界面已经有页面标题、描述、正文 HTML 和语义化导航，但仓库当前还没有输出供搜索引擎识别页面正式网址的规范地址（canonical）、列出页面地址的站点地图，以及让读者订阅文章更新的 RSS。站点配置里的 `url` 仍是占位值，也没有在布局中输出规范地址。后续做搜索收录和分享信息时，应先补齐真实域名和这些输出，不能仅凭有一个描述标签就说搜索优化已经完成。

互动统计的下一步则更具体：校验真实文章资源、限制异常上报、改进请求去重与点赞并发处理，并完善存储受限时的兜底。如果只是想知道博客有没有被阅读，当前累计展示已经能提供一个粗略反馈；如果要分析读者路径，就需要独立设计统计数据，而不是继续往一个总数上堆功能。

日常新增内容时，最常碰到的文件仍然很少：正文改 `src/content/posts/`，图示改 `public/images/posts/`，专栏规则改 `src/config/sections.ts`，精选入口改首页，阅读结构改文章模板，共用视觉样式改 `src/styles/global.css`。统计行为则要同时看浏览器脚本、Functions 接口和数据库表，不能只改其中一处就假定口径已经改变。

这也是我希望这个项目能长期保持的状态：写一篇文章时，不必同时改动整站；调整界面时，不必改正文；统计暂时失效时，读者仍然可以把文章读完。等新的需求确实超出这些边界，再增加对应的实现。
