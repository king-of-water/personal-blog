这个博客用来记录后端知识、Agent、行业理解和自己的项目。我的要求比较简单：文章写起来方便，读起来舒服，后续修改不需要自己维护一台服务器。

目前的实现是：用 Markdown 保存文章，Astro 生成网页，GitHub 保存源码和修改记录，Cloudflare Pages 托管网站。浏览量和点赞会持续变化，由单独的接口和数据库处理。

## 为什么选择 Astro

博客的大部分内容不会因为访问者不同而变化。一篇文章写好以后，无论谁打开，看到的标题和正文通常都一样，直到我修改并重新发布。

因此，我选择在发布时就生成 HTML，也就是浏览器能直接显示的网页。读者访问时，平台把已经生成的页面交给浏览器，不需要临时查文章数据库、拼装正文。

Astro 适合这种内容型网站。它可以把页面拆成导航、文章卡片、正文等组件，再在构建时组合成网页。本站用少量浏览器脚本处理交互，没有为阅读正文引入一整套前端应用。

这里的“静态”只是说正文提前生成了，不代表网页不能动。卡片悬停、目录高亮和点赞按钮，仍然可以各自增加交互。代价是修改正文后需要重新构建、发布，本站也没有浏览器里的文章管理后台。

## 文章怎么管理，又怎么变成网页

所有文章放在 `src/content/posts/`，一篇文章对应一个 Markdown 文件。图片和流程图放在 `public/images/posts/`，正文引用它们的路径。

文件开头填写标题、摘要、发布日期、分类和标签。比如一篇 Java 文章，主分类是“后端”，子分类是“Java”。Astro 读取这些信息后，就知道它应该进入哪个栏目，卡片上显示什么。

这些字段由 `src/content.config.ts` 统一定义和校验，避免分类拼错、必要字段遗漏后悄悄进入网站。[Astro 内容集合说明](https://docs.astro.build/en/guides/content-collections/)

还没检查完的文章设为 `draft: true`，不会生成公开文章页，也不进入栏目和首页精选。不过，草稿隐藏只针对网站；如果源码仓库公开，文件仍可能被看到，所以敏感内容不能靠这个字段保护。

发布时，文章共用一个模板：`src/pages/posts/[...id].astro`。它为每篇非草稿文章列出地址，把 Markdown 正文转换成 HTML，再补上标题、日期、导航和章节目录。本篇对应的地址就是 `/posts/how-this-blog-works/`。

![文章经过字段校验、草稿过滤和模板渲染，生成可发布的网页](/images/posts/blog-content-build-flow.svg)

栏目页也从同一批文章中筛选，不需要新增文章后再手工复制标题。系列文章用 `seriesOrder` 决定阅读顺序，上一篇、下一篇也可以沿着该专栏导航。

首页精选则是手动维护的文章 ID 清单，按指定顺序显示五篇文章。这样入口比较稳定，不会每发一篇新文章就改变推荐内容；需要换精选时，修改首页清单即可。

## 阅读界面和互动怎么做

页面共用 `BaseLayout.astro`，统一管理顶部导航、页脚和全局样式。文章模板主要负责阅读区域，界面样式集中在 `src/styles/global.css`。

桌面文章页分成三栏：左边是同栏目的文章列表，中间是正文，右边是当前文章的目录。目录从正文的二级、三级标题生成，滚动时高亮正在阅读的章节。手机上收起桌面侧栏，保留文章内的目录入口。

视觉上保留浅色背景、衬线大标题和细分隔线。首页标题、头像、精选卡片有轻微缩放或位移反馈，主要通过 CSS 实现；正文不放持续移动的背景，避免阅读时分心。用户开启减少动态效果的设置时，相应动效也会减少或停用。

浏览量和点赞需要共享数据，所以另外用了 Cloudflare Pages Functions 和 D1：前者是接收请求的小型后端，后者是保存统计数据的托管数据库。

打开文章时，浏览器先显示正文，再检查本地的当天访问标记。没有标记，就请求接口给浏览量加一；收到成功结果后显示数字、写入标记。同一天再打开这篇文章，通常只查询数字，不再次累加。

![文章先显示，统计再独立请求；统计失败不影响阅读正文](/images/posts/blog-reading-stats-flow.svg)

首页总浏览量包含已有文章浏览量，以及非文章统计上线后记录的首页、栏目等页面访问。文章只在文章接口计数，不会被全站脚本再加一次。

这个数字不是独立访客人数。去重依靠浏览器本地存储，按 UTC 日期换日，也就是北京时间每天 08:00；换浏览器、清理存储或并发打开标签页，都可能重复计入。它适合展示累计阅读活动，不能当成严格的访问分析。

点赞也通过接口保存，匿名浏览器标识用来判断当前是否点过赞，再次点击可以取消。统计服务不可用时，首页显示“暂不可用”，文章仍然能读，不会把接口失败显示成零次浏览。

## 修改以后怎么发布

日常更新先改本地文件：写文章、调整分类、补图示，或者修改页面组件和样式。预览没有明显问题后，再执行 `npm run build`，检查正式构建是否成功。

构建后的网页、样式和图片输出到 `dist`。我把修改提交并推送到 GitHub，Cloudflare Pages 根据连接的生产分支更新触发构建，成功后发布新版本。[Pages Git 集成说明](https://developers.cloudflare.com/pages/configuration/git-integration/)

因此，推送成功和网站更新成功是两回事。前者说明仓库收到了提交，后者还要看平台构建和部署结果。新构建失败时，网站可以继续使用之前的成功版本。

数据库也单独管理。统计接口需要绑定 D1，并提前建立数据表；日常改文章不需要修改数据库。本地 Astro 开发服务不自动运行 Pages Functions，所以本地正文能打开、统计暂不可用，并不矛盾。

这套流程让我可以把文章、图片和页面改动放在同一个仓库里维护，出了问题也能查修改记录。后续仍需要关注依赖、域名、托管额度和统计接口，但新增一篇文章时，主要工作就是把内容写清楚，检查后发布。
