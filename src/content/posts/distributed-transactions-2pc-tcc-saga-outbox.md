用户花 100 元买一件商品。订单服务创建订单，钱包服务扣款，库存服务扣减库存。正常情况下，最后应该留下一个已支付订单、一次扣款和一份扣减后的库存。

问题出在中途：钱包已经扣钱，库存扣减却失败了。订单服务的数据库可以回滚，钱包里的扣款会跟着回滚吗？不会。它们有各自的数据库、提交点和故障，订单服务没有一个普通的本地事务，能顺便撤销远程系统已经提交的修改。

分布式事务要处理的就是这种跨资源、跨服务的整体结果。有人要求多个资源共同提交或回滚；有人允许短时间处理中，但失败后必须恢复或补偿；还有人首先要解决“本地提交成功，通知下游的消息却没发出”。这些要求对应不同机制，不能只凭“跨了服务”就选框架。

下面围绕购买过程讲清五种常见方案：2PC、TCC、Saga、事务消息和 Outbox。示例中的单号和状态用于说明机制，具体落地仍要结合参与方接口与业务规则。协议说明参考官方文档与原始论文；数据库状态驱动放在后面，作为一种定制恢复流程的补充。

## 一、本地事务管不到哪里，分布式事务就从哪里开始

先把服务数量与事务边界分开。两个应用连接同一个数据库，关键修改确实由同一个数据库事务完成，不一定需要分布式事务。一个应用同时修改两个独立数据库，即使没有微服务，也可能已经跨了本地事务边界。

本地事务能够把一组修改一起提交或回滚。比如库存和订单位于同库：库存足够才扣减，订单插入成功后一起提交。扣减条件不满足或订单写入失败，应用应回滚这次事务。

```sql
START TRANSACTION;

UPDATE inventory
SET available = available - 1
WHERE sku_id = 'S42' AND available >= 1;
-- 应用必须检查影响行数为 1；否则回滚，不再创建订单。

INSERT INTO orders(order_no, sku_id, status)
VALUES ('O1001', 'S42', 'CREATED');

COMMIT;
```

改成远程钱包调用后，情况就变了。本地事务回滚，撤销的是自己的数据库修改。钱包完成扣款后，撤销扣款需要钱包的退款操作或其他协作协议。把 RPC 放在本地事务方法里，不会自动获得这种能力，反而可能让本地锁一直等着远程响应。

第二个问题是结果未知。库存接口超时，可能是请求没到，也可能是库存已经扣减、响应丢失。调用方不能把所有超时都当作“没执行”。分布式事务的恢复必须区分明确失败与暂时无法确认。

第三个问题是事务已经提交，后续工作却没被通知。订单服务把订单改成已支付，准备发消息让仓储发货，却在发送前崩溃。这与钱包扣款和库存扣减共同提交不是同一个边界，但同样会让整条业务只完成一部分。

可以先按要求区分：

| 想要的结果 | 需要解决的具体问题 |
| --- | --- |
| 多个事务资源共同提交或回滚 | 谁收集准备结果，谁作出持久化决议，参与者怎样恢复 |
| 多个业务资源先预留，再确认或释放 | 每个服务怎样冻结、确认、取消，并处理重复与迟到请求 |
| 各步骤分别提交，失败后继续或补偿 | 保存完成进度，确认未知结果，执行可恢复的补偿 |
| 本地业务提交后可靠通知下游 | 业务数据与消息发布之间不能留下不可恢复的缺口 |

2PC 主要处理第一类，TCC 处理第二类，Saga 处理第三类，事务消息和 Outbox 处理第四类。它们可以组合：例如用 Saga 决定何时退款，用 Outbox 可靠通知下一个步骤。

分布式事务也不是每条链路都必须上。能缩进一个本地事务的先缩；独立的短信通知通常不值得阻塞整个支付提交；必须一致的账务结果则不能因为“协议比较重”就不处理。要先明确哪些结果必须共同成立，允许多久的中间状态，以及失败后的合法结果是什么。

## 二、2PC：参与者先准备，协调者再统一决定

假设订单与库存分别位于两个受控数据库，而且都支持参与全局事务。我们希望订单创建和库存扣减共同提交，失败则共同回滚。

这里多了一个协调者。它记录本次全局事务，知道有哪些参与者，负责收集准备结果和发送最终决定。订单数据库、库存数据库是参与者，各自管理本地事务。

### 准备成功，承诺的是以后能按决议提交

两个数据库先执行各自的修改，但还不把分支作为普通事务提交。协调者要求它们准备：把必要的恢复信息可靠保存，检查这次分支是否可以提交，然后回答赞成或拒绝。

订单库准备好，库存库也准备好，协调者才能决定提交。任何一个拒绝，或者准备阶段未能满足完成条件，就走回滚路径。这个“先准备、后决定”的过程叫两阶段提交，英文 Two-Phase Commit，简称 2PC。[MySQL 对 XA 与 2PC 的说明](https://dev.mysql.com/doc/refman/8.4/en/xa.html)

准备后的参与者不能随意改变承诺。它通常要保留事务资源，直到获得最终决定；仅仅回复“SQL 执行成功”，没有保存可恢复的准备状态，不能算参加了这个协议。

![2PC 先收集准备结果，再持久化提交或回滚决议，参与者按同一决议完成](/images/posts/transaction-2pc-decision-flow.svg)

图里的第二阶段有一个很重要的顺序：协调者先可靠保存“提交”决定，再发提交通知。这样即使发送到一半崩溃，恢复后仍然知道应该继续提交剩余分支，不会重新猜一次结果。

MySQL 可以通过 XA 接口参与这种事务。XA 是数据库提供的一套分支事务控制接口，2PC 是协调这些分支的提交过程，两者分别对应参与接口与协调过程。

```sql
-- 在库存库执行一个分支；单独执行它不构成完整全局事务。
XA START 'G1001', 'inventory';
UPDATE inventory
SET available = available - 1
WHERE sku_id = 'S42' AND available >= 1;
-- 应用检查扣减成功，失败则报告该分支不能提交。
XA END 'G1001', 'inventory';
XA PREPARE 'G1001', 'inventory';

-- 等协调者的持久化决议，再执行其中之一：
-- XA COMMIT 'G1001', 'inventory';
-- XA ROLLBACK 'G1001', 'inventory';
```

订单库有属于同一个全局事务的另一分支。协调者必须管理两边的结果，不能在库存准备后就自行提交库存，再看订单能否成功。[MySQL XA 状态与语句](https://dev.mysql.com/doc/refman/8.4/en/xa-states.html)

### 一边已经提交，另一边还没收到消息怎么办

协调者决定提交，订单库完成提交，发往库存库的通知却丢了。库存库仍然处于已准备状态。此时恢复动作是查询决议、继续提交库存，不是因为库存超时就回滚订单。

如果提交通知已经到库存库，只是确认响应丢了，协调者也要确认该分支结果。对已经完成的分支重发可能得到“事务不存在”等结果，恢复程序要结合完成证据处理，不能把它解释成另一个回滚决定。

协调者在决议未知时失联，则更麻烦。参与者知道自己准备成功，却不知道别人是否准备成功、协调者是否已经决定提交。它不能凭本地超时退出，否则另一边可能已经提交。这就是经典 2PC 的阻塞问题。[Gray 与 Lamport：事务提交中的阻塞](https://lamport.azurewebsites.net/video/consensus-on-transaction-commit.pdf)

数据库重启后，已准备事务也需要继续恢复。MySQL 的 XA RECOVER 可以列出准备中的分支，运维与事务管理器据此检查，而不是让这些事务一直占着资源。随意人工回滚一个未知分支，可能打破原来的共同提交保证。

2PC 的原子性说的是各分支遵守同一个提交或回滚决议，不是所有机器同一毫秒完成，也不等于任意独立查询都看不到短暂差异。跨资源读取与隔离仍需要相应事务安排。

适用条件也很具体：参与者支持协议，事务短，数量可控，确实需要共同提交。只提供“扣款、查单、退款”的第三方钱包不能被调用方单方面纳入 XA；长时间等物流、人工审核的流程，也不适合一直保留准备资源。

## 三、TCC：先把钱和库存留住，再确认购买

如果服务没提供数据库的准备接口，但业务资源可以预留，就可以在业务层定义三个操作。

仍然购买一件商品，用户钱包总额 100 元、没有冻结金额，库存剩一件。先不最终扣款或出库，让钱包冻结这 100 元，让库存保留这一件。全部预留成功后，再正式使用这些资源；任何一个预留不了，就释放已经预留的部分。

这叫 Try-Confirm-Cancel，简称 TCC。Try 检查并预留，Confirm 确认使用，Cancel 取消预留。参与方自己实现这些业务接口，协调者负责作出和恢复全局决定。[Apache Seata TCC 机制](https://seata.apache.org/docs/user/mode/tcc/)

| 阶段 | 钱包实际动作 | 库存实际动作 |
| --- | --- | --- |
| Try | 可用金额减少 100，冻结金额增加 100 | 可卖库存减少 1，预留库存增加 1 |
| Confirm | 将这笔冻结转为最终扣款 | 将这笔预留转为订单正式占用 |
| Cancel | 解冻这笔金额，恢复可用金额 | 释放这笔预留，恢复可卖库存 |

用户在 Try 后不能把被冻结的钱再用于别的购买，其他订单也不能买走预留库存。但钱包并没有最终扣款，库存也没有开始发货，释放预留仍有清晰的业务含义。

![TCC 的预留成功后才能选择确认；准备失败时释放已经预留的资源](/images/posts/transaction-tcc-reservation-flow.svg)

Try 里面的可用额度修改与预留记录，应在钱包自己的本地事务里完成。比如以全局事务 G1001 和钱包分支 W1 标识这次冻结，把“冻结 100 元”与对应记录一起提交。否则余额冻了、记录没存，后面 Cancel 就不知道应该解冻什么。

### 确认失败，要继续确认，不能临时换成取消

所有 Try 成功，协调者可靠记录确认决定，然后调用各参与方的 Confirm。钱包确认完成、库存 Confirm 响应丢失，恢复时继续确认库存，不能因为没有收到响应就解冻钱包。

Confirm 重复执行，也不能再扣一次。参与者根据同一分支的控制记录判断：尚在预留则原子地转成已确认；已经确认则返回已有结果。Cancel 同样只释放本次预留一次，不能每收到一次取消就给用户多加 100 元。

Confirm 与 Cancel 是互斥结局。已确认分支不能再按取消逻辑释放资源，已取消分支不能被迟到确认重新激活。协调者的决议记录与参与方的条件状态转换都不可少。

### 取消比预留先到，为什么还要留记录

假设钱包 Try 在网络中延迟，协调者等不到准备结果，决定取消。Cancel 先到钱包，这时还没有冻结记录。它不能从余额凭空加回 100 元，这种“还没做 Try 就要 Cancel”的情况通常叫空回滚。

但直接返回“没有冻结，取消成功”也有漏洞。稍后 Try 到达钱包，第一次冻结 100 元；协调者已经结束，没人再确认或取消，这笔资源就悬在那里。这种取消先执行、迟到 Try 又占用资源的情况，通常叫悬挂。

处理办法是 Cancel 在没有预留记录时也保存“此分支已取消”的记录。迟到 Try 读取同一分支，看到取消结果就拒绝预留。Try 与 Cancel 并发时，需要唯一约束和原子状态转换，让它们不能分别认为自己赢了。[Seata 对重复、空回滚与悬挂的解释](https://seata.apache.org/blog/seata-tcc/)

可以把一个参与方的合法转换写成：

```text
尚无记录 → Try 原子预留 → 已预留 → Confirm → 已确认
                                   └→ Cancel → 已取消

尚无记录 → Cancel 留下取消记录 → 已取消
已取消收到迟到 Try：拒绝，不再预留
已确认再次收到 Confirm：返回已有结果，不重复扣减
```

预留也不能在等待一段时间后偷偷释放，再让协调者继续确认。资源过期必须和全局决议、终止机制协调，否则 Try 时答应留住的商品，Confirm 时已经卖给别人。

TCC 用短本地事务管理较长的业务预留，通常不必把数据库事务锁一直持有到第二阶段，但资源占用仍然存在。未决预留积压，同样会减少可卖库存与可用额度。

它适合库存、余额、额度、名额等能自然预留的资源，代价是参与方都要实现并维护完整接口。把“直接扣款”改名为 Try，再用退款当 Cancel，会失去先预留、再确认的设计前提，不能仅凭方法名就声称已经实现 TCC。

## 四、Saga：每一步先提交，做不成时用新操作补偿

再看不适合长时间预留的流程。订单创建成功，钱包已扣款，接下来还要仓储接单、安排发货。整个过程可能持续很久，一直冻结资源或保留数据库事务都不合适。

Saga 把流程拆成一串本地事务。每一步在自己的服务内提交，后续失败时，要么继续恢复，要么执行前面步骤对应的补偿。这是 Saga 原始论文讨论的长事务拆分思想。[Saga 原始论文](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)

例如先创建订单、再扣款、最后确认库存占用。全部完成就是购买成功；库存明确拒绝且不会再占用时，先退款，再把订单关闭。与 TCC 不同，钱包这时已经真正扣款，失败后需要一笔新的退款，而不是仅仅解冻。

![Saga 中已经完成的本地事务不会自动回滚，后续失败需要可恢复的补偿](/images/posts/transaction-saga-compensation-flow.svg)

图里退款也可能失败。流程需要记录补偿进度，下次继续退款，确认退款成功后才关闭到相应终态。钱包扣款成功后，不能只在异常处理里写一行退款调用，进程重启后就忘记它。

补偿也不等于还原整个数据库。退款会产生新账务记录，订单关闭会保留购买历史。邮件已经被用户阅读、包裹已经发出时，也不存在一个通用撤销函数。业务必须定义还能做什么，比如退货、追回或人工处理。

### 谁决定下一步，是两种组织方式的区别

一种方式是由订单服务或独立流程管理器保存进度，发出扣款、占用库存、退款等命令，并根据结果决定下一步。这叫编排式 Saga。恢复时看它记录的步骤，就能知道现在应该查扣款还是继续退款。

另一种方式是各服务通过事件接力：订单创建事件触发扣款，支付成功事件触发库存处理，库存失败事件触发退款。这叫协同式 Saga。没有一个中心负责所有分支，但每个服务仍然需要保存自己的处理结果和后续通知。

参与者少、分支简单时，事件接力容易理解；服务多了，容易看不清“当前到底卡在哪里”，事件之间还可能形成循环。中心编排更容易集中表达业务规则，但管理器本身也需要持久化、恢复和监控。[Saga 的组织方式与隔离边界](https://microservices.io/patterns/data/saga.html)

无论哪种，失败处理都要区分三类结果。暂时故障可以继续向前重试；明确业务拒绝才选择补偿；调用超时则先查明原操作的结果。库存可能已经扣减时，不能一边退款，一边让迟到请求继续出库。

正向与补偿操作都需要稳定身份。重复执行扣款使用原支付单号；重复退款使用同一退款单号；库存占用与释放针对同一个订单。流程管理器的步骤状态可以落后于服务事实，恢复时查询参与方，不能只相信原来的内存变量。

Saga 不提供普通大事务那样自动的隔离。别人可能看见订单已支付、仓储还没接单的中间状态；并发取消可能与发货交错。服务要限制合法转换，例如已关闭订单不得出库，发货与关闭需要明确仲裁。允许中间状态不代表允许任意相互冲突的动作。

它适合跨外部服务、持续时间长、允许处理中且补偿规则明确的业务。若要求多个资源严格共同提交，不能用“失败后补偿”冒充完全相同的保证；若副作用无法补偿，则要提前调整流程，比如先确认可履约，再执行不可逆动作。

## 五、事务消息：本地提交了，消息就应该被放行

先换一个更小的边界。订单服务已经确认支付结果，现在要在自己的数据库把 O1001 改成已支付，并通知下游准备发货。

这里本地事务只包括订单库修改，不包括远程钱包扣款或仓储执行。要解决的是订单状态与这条通知之间的缺口。

先改订单再发消息，进程可能在两步之间崩溃，已支付订单没有发货通知。先发消息再改订单，下游可能已经收到通知，订单事务却回滚了。把发消息代码放进数据库事务函数里，也不会让普通 MQ 发送跟随数据库回滚。

事务消息通过“先暂存、后决定能否投递”处理发布侧一致性。下面以 RocketMQ 为例讲协议，不混用不同版本 SDK 的接口。

### 半消息不是消息内容发了一半

订单服务先发完整的通知内容和稳定事务编号 T1001。Broker 是负责接收、保存和投递消息的服务端，它先把消息留在消费者不可见的状态。这个状态叫半消息，消费者暂时不能处理它。

生产者检查半消息发送结果，符合所需保存条件后，执行本地事务：把 O1001 改为已支付，并保存 T1001 对应的已提交结果。两份记录在同一个订单数据库事务内提交。

本地提交成功，生产者通知 Broker 提交消息，允许投递；本地明确回滚，通知 Broker 回滚消息，不向消费者放行。这里“提交消息”的意思是改变投递资格，不是让下游业务也一起提交。[RocketMQ 事务消息的正常流程](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/#working-mechanism)

![半消息确认后执行本地事务，二次通知丢失时通过回查恢复消息的投递决定](/images/posts/transaction-mq-check-release-flow.svg)

如果半消息发送超时，应用也不能当作已经可靠准备完毕就继续执行本地事务。实际实现要遵守 SDK 与存储策略的发送结果约定；重新发送仍可能产生重复记录，逻辑事务与消费动作需要稳定业务身份。

半消息保存确认、消息可以投递、消费者处理完成，是三个不同时间点。第一步不代表订单已支付；第二步不代表商品已发货；第三步也取决于消费者确认前实际完成了什么。

### 回查要查原事务结果，不能再执行一次下单

最典型的故障是本地事务已经提交，生产者还没通知 Broker，就崩溃了。Broker 没拿到明确结论，随后要求生产者查询这次本地事务结果。

恢复后的生产者按 T1001 读取持久化证据。确认已提交，返回 Commit，消息放行；确认已回滚且不能再提交，返回 Rollback，消息不放行；仍在执行、查询失败或不能确定，返回 Unknown，暂不作最终判断。

回查不能只看当前订单是不是已支付。这个订单可能后来退款或关闭了，但原来“支付确认”的事务确实提交过。也不能查到某笔同名旧订单，就认定本次事务成功。证据必须对应原来的逻辑事务。

查不到记录也不能马上返回回滚。事务可能尚未提交，读副本可能落后，原执行线程还可能在继续。若要终止，必须通过受控状态或执行互斥确认原事务不会再提交，并留下终止记录，否则回查拒绝投递后，业务又晚到提交，就重新出现缺口。

原实例不在时，回查需要由有相同查询能力的可用生产者处理。只把结果放在原进程内存里无法恢复。不同 SDK 的路由和状态名有区别，版本级代码见站内[事务消息专题](/posts/rocketmq-transactional-message-half-message-check/)；这里先理解半消息与持久化回查的关系。

### 发布一致了，下游仍然可能处理失败

消息放行后，仓储消费者需要完成自己的本地操作。仓储把接单记录与事件 E1001 的已处理记录放进同一个本地事务，提交后再确认消费完成。

仓储已经提交，确认响应丢了，消息会再次到达。消费者看到同一事件已经处理，就返回已有结果，不能重复安排一次出库。反过来，若先确认消费再写仓储数据库，进程崩溃可能让任务永久消失。[RocketMQ 的消费重试与确认边界](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)

如果仓储确定无法履约，消费者可以记录失败，再可靠通知上游，由业务流程判断关闭或退款。事务消息不会自动回滚已支付订单，它也不会保证所有下游一起成功。[RocketMQ 对事务消息使用边界的说明](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/#usage-limits)

Broker 回查、生产者查询、消费重试都存在超时、次数或保留期限。长期未知、没有可用生产者、积压超过保存期限，都需要监控和业务对账。协议减少不可恢复窗口，但不能脱离数据库与 Broker 的持久化条件，承诺任何故障都不丢。

因此事务消息适合“一个明确的本地事务，提交后需要可靠通知下游，允许异步执行”的场景。它是构建分布式业务一致性的一部分，与跨数据库的共同提交不是相同保证。

## 六、Outbox：把待发消息与业务记录一起提交

不使用 RocketMQ 的事务消息能力，也可以在数据库内保存待发事件。Outbox 通常译为本地消息表或发件箱：先把业务变化和要通知的内容放进同一个本地事务，再由发送程序把这些事件送往 MQ。

仍然把 O1001 改为已支付，同时插入事件 E1001。数据库提交成功，两者一起存在；事务回滚，两者一起不存在。待发内容已经持久化，进程重启后仍知道需要通知什么。[Transactional Outbox 模式](https://microservices.io/patterns/data/transactional-outbox.html)

```sql
START TRANSACTION;

UPDATE orders
SET status = 'PAID', version = version + 1
WHERE order_no = 'O1001' AND status = 'PAYING';
-- 只有本次合法状态转换成功，才新增对应事件。

INSERT INTO outbox_event(event_id, order_no, event_type, payload, status)
VALUES ('E1001', 'O1001', 'OrderPaid', '{...}', 'PENDING');

COMMIT;
```

注意必须在同一个实际数据库事务里。业务表和消息表分别位于两个独立数据库时，两个 INSERT 即使写在同一个方法，也不能靠普通本地事务一起提交。

发送程序分批读取待发送事件，发往 Broker，获得符合要求的发送确认后，再记录已发送。发送失败，下次继续发；发送前崩溃，待发送记录仍在；发送成功后、标记已发送前崩溃，会再发一次。

这个最后的窗口无法仅靠调换两步消除。先标记再发，可能丢；先发再标记，可能重复。因此消费者仍要幂等，事件 ID 必须稳定，不能每次补发生成一个新 ID，再指望消费者识别它们是同一事件。

也可以由程序读取数据库的变化日志，把新增事件转给消息队列。这种方式减少轮询需求，但新增了日志读取进度和连接器运维。Debezium 的 Outbox Event Router 提供事件 ID 与路由键等映射，具体配置需按版本接入。[Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

并发发送程序需要受控领取或等价的并发策略，避免互相覆盖发送结果；“已发送”只说明发布阶段完成，不代表下游业务成功。事件还要保留足够时间，不能看到已发送就立刻删掉所有恢复证据。

同一个订单先支付、后退款，两个事件也有顺序要求。按订单号分区，只约束进入同一消息分区后的处理路径；多个发送者若先把退款发出去，再发支付，分区不会替它纠正发布顺序。需要从源头保证同一订单事件顺序，或让消费者用版本检查拒绝倒退、处理缺口。

Outbox 与事务消息都需要可恢复的本地事实。Outbox 把待发布内容留在本地数据库，自己维护转发；事务消息先把内容交给 Broker，再通过本地事务结果决定投递。选择时要比较两套恢复设施的维护成本。

若整个购买采用 Saga，Outbox 可以可靠发布“支付成功”“库存拒绝”“退款完成”等事件，Saga 决定收到这些事件后继续还是补偿。Outbox 自己不定义退款规则，也不使所有消费服务原子提交。

## 七、补充案例：数据库状态驱动怎样落实恢复与补偿

前面这些机制说明整体思路，项目里还会遇到没有通用 Saga 引擎、下游也不支持 XA 或冻结接口的情况。此时可以自己把业务进度持久化，配合重试、查单和补偿实现恢复。

以扣款、发放权益为例。先在购买库建立流水，保存支付单号 P1001，再调用钱包。确认扣款后记为已支付；确认本单权益已发放后记为购买成功；确定权益无法发放、满足退款条件后，记为退款待确认，再调用退款。

这类定制流程采用分步提交与补偿的思路。是否称为编排式 Saga，要看步骤、补偿与恢复是否成立；数据库里增加一个 status 字段本身不提供保证，也不能替代参与方的协议能力。

最需要保留的是稳定单号和下游事实。钱包扣款成功、本地状态没更新，恢复时按 P1001 查单，不能换单号再扣；退款成功、本地状态没更新，按固定退款单号 R-P1001 查退款。钱包是支付事实的权威来源，购买库记录流程进度，两者不能混为一谈。

权益调用超时也不能直接退款。权益可能已经发放，甚至旧请求仍在网络里。参与方需要能确认本单结果，并在退款前关闭对应发放，阻止迟到请求继续生效。已发放就确认成功，确定关闭才退款，未知则继续查、告警或人工对账。

普通 MQ 可以提醒“这条流水该继续处理”。消费者拿流水 ID 查询当前状态，再执行下一步。消息漏发时，数据库扫描找出到期的未完成记录，也调用同一个推进方法。前提是数据库状态完整表达待办，每个非终态都能被重新发现。

```text
同步请求 / 普通 MQ / 数据库扫描
                ↓
        按流水 ID 读取当前进度
                ↓
     查询原单号 / 执行幂等动作 / 保存进度
                ↓
        已结束，或留下下一次待办
```

多个入口仍可能同时执行。条件更新可以防止旧版本覆盖新状态，下游的幂等接口防止重复副作用；购买库的版本号不能替远程钱包防止多扣，也不能替权益服务阻止迟到发放。

扫描还要分批、限速并周期性重新覆盖待办范围，监控未完成记录最老年龄。自动重试达到阈值时，需要降频和升级处理，不能把未知支付随手改成失败。

这种扫描能恢复本系统当前待办，不等于可靠广播每个历史事件。如果支付成功事件需要通知多个下游，后来流水又退款了，仅扫当前状态未必能恢复原事件，仍应保存事件或采用事务消息。

业务允许中间状态，参与方能幂等执行、查询结果并阻止相冲突的迟到动作，才有条件采用这种定制流程。若缺少这些能力，反复扫描数据库也无法安全恢复。

## 八、怎样选：先确定要协调哪一个边界

同一个购买系统不必全站只选一种方案。订单与本库库存可以用本地事务；跨服务冻结库存与额度可以考虑 TCC；物流长流程可以按 Saga 组织；每一步提交后的通知可以使用事务消息或 Outbox。

先确定是否真的需要多个资源共同提交。若关键修改可以收进同库事务，先用本地事务。如果确实需要跨资源原子提交，参与方都支持 XA 且事务足够短，2PC 有适用位置。别仅因为有两次 SQL，就长期占住两个数据库的事务资源。

再看是否能预留。库存、名额、额度存在“先留给这次操作”的明确语义，且参与者能兑现后续确认，TCC 才有基础。只有直接扣款与退款接口时，不能由调用方虚构冻结能力。

允许处理中，并能定义可靠查询、幂等与补偿的长流程，可以按 Saga 处理。但先确认哪些动作不可逆。商品发货后补偿可能是退货，不再只是库存加一；用户已消费的权益也不能简单删除。

如果问题只是“本地事务提交了，消息不能漏”，重点比较事务消息与 Outbox。事务消息依赖 Broker 对暂不可投递消息的管理，以及生产者的事务结果回查；Outbox 依赖本地消息表、发送程序与发布进度。消费者的恢复，两者都不会替你完成。

| 方案 | 主要协调对象 | 已做的事情如何处理 | 必须具备的能力 |
| --- | --- | --- | --- |
| 2PC / XA | 支持协议的事务资源 | 按同一决议提交或回滚准备中的分支 | 准备状态、持久化决议、分支恢复 |
| TCC | 能预留的业务资源 | 确认使用，或释放本次预留 | 预留、幂等确认/取消、防迟到 |
| Saga | 各自提交的业务步骤 | 继续恢复，或新执行补偿 | 保存进度、查明结果、恢复补偿 |
| 事务消息 | 本地事务与消息投递资格 | 回查原事务，决定放行或丢弃 | 可查询的事务结果、半消息恢复 |
| Outbox | 本地业务数据与待发事件 | 转发持久化事件，失败后重发 | 同库事务、发送程序、消费幂等 |

有几个常见误解可以直接对应到选择上。

分布式锁不等于分布式事务。锁可以限制并发执行，却不能在扣款后进程崩溃时自动撤销扣款。消息有序也不等于整体事务成功，顺序送到了，第二步仍可能失败。

事务消息里用了两阶段思想，不代表它把所有下游拉进了 XA。TCC 有准备和确认两个阶段，也不代表它与数据库锁定式准备的成本完全相同。比较时需要说清是哪一种资源、在哪一步承诺了什么。

“最终一致”不能只有一句承诺。未完成记录谁发现，结果未知怎样查询，补偿失败谁继续，超过恢复时限怎样对账，都需要有实际入口。框架能提供调度或记录，但参与方缺少可靠接口时，它也无法猜出真实结果。

业务对外的成功边界也要对应。订单已受理可以在持久记录建立后返回；消息已发布只能表示通知进入投递阶段；购买完成需要确认约定的关键步骤。若产品要求后者，就不能在前者完成时提前显示成功。
