用户花 100 金币买一份权益。钱包扣款成功，权益服务却没有及时返回。用户的钱已经少了，页面还在转圈。这时应该重试发权益，还是把钱退回去？

只看“请求超时”无法决定。权益可能根本没开始，也可能已经发放，只是响应没传回来。直接重试可能重复发放；直接退款又可能让用户同时拿到权益和退款。

这篇围绕这条链路展开。先回答分布式事务是不是一定要用，再讲一种常见做法：把进度写进数据库，允许流程暂时处于处理中，后续根据事实继续执行或补偿。消息队列负责及时唤醒，后台扫描负责找回没完成的记录。最后再介绍事务消息、Outbox、2PC 和 TCC，看看它们在哪一段有用。

下文的表名、状态名和单号都是用于说明的例子，不代表某个公司的内部接口，也不是一套可以直接复制上线的完整支付代码。

## 一、跨了两个服务，就一定要上全局事务吗

不一定。先看这两个动作是否真的必须在同一个提交点一起成功。

如果余额扣减和权益发放都由同一个数据库事务管理，可以在一个本地事务里完成。余额足够才扣减，权益记录写成功后一起提交；中间失败就一起回滚。这里首先要考虑本地事务，没有必要为了“听起来分布式”把流程拆得更复杂。

现在换一种情况：钱包有自己的数据库，权益服务也有自己的数据库。购买服务只能分别调用它们。钱包完成扣款后，购买服务的本地事务即使回滚，也不会让钱包里的钱自动回来。在 Java 方法上加一个普通的本地事务注解，也不能把另一个服务已经提交的修改撤销。

这才出现跨系统的协调问题。但协调有不同要求。

一种要求是多个资源一起提交，不能接受其中一个已经成功、另一个还没完成。实现这类全局原子提交，需要参与方支持相应协议，不能只靠调用方包装一个方法。

另一种要求是允许短时间显示“处理中”，但必须保证不重复扣款、不重复发权益；扣款后发放不了，最终要退款；任何没完成的单子都得有人继续处理。在线购买、订单履约等长流程，经常更适合后一种要求。

这里的“允许处理中”也有代价。用户可能先看到余额扣了、权益还没到账，需要状态查询和客服处理；其他业务不能把中间态当完成态。若产品不允许这种体验，不能用“最终一致”四个字把它省略。

所以，大家口头上说“不用分布式事务”，通常是说不用重型的全局提交协议，并不是不处理跨服务一致性。数据库状态驱动的流程，也可以算广义的分布式事务解决方案；严谨一些，可以称为“可恢复的跨服务业务流程”。它不提供多个数据库瞬间一起提交的保证。

## 二、先把没完成的事情留下来，进程才能换人接着做

购买服务准备调用钱包之前，先把这次购买流水写入自己的数据库。至少保存：买什么、谁购买、金额、支付单号、当前进度，以及下次需要处理的时间。

为什么要先存？假设先扣款，再存流水。钱包扣款成功，购买服务在插入流水前崩溃。进程重启后连“曾经有过这笔调用”都不知道，后台任务也没有记录可以找。这是恢复流程最早需要堵住的缺口。

可以把一条流水想成一张随时能交给另一个工作人员的处理单。上面既记录已确认的步骤，也记录还需要确认什么。这里说的状态机，就是为这些进度规定合法的转换，避免代码随意把“支付未知”改成“购买成功”。

例如使用下面这些状态：

| 数据库里的进度 | 已确认的事实 | 下一次要做什么 |
| --- | --- | --- |
| 待支付 WAIT_PAY | 流水已建立，还没确认扣款 | 用固定支付单号发起或恢复支付 |
| 支付待确认 PAYING | 已进入支付阶段，结果还不确定 | 向钱包查这笔支付 |
| 已支付 PAID | 钱包确认这笔钱已扣 | 发放或确认权益 |
| 退款待确认 REFUNDING | 已确定可以退款，退款还没确认完成 | 用固定退款单号退款或查退款 |
| 购买成功 SUCCESS | 本单权益已发放 | 停止推进 |
| 支付失败 PAY_FAILED | 钱包确认本次支付失败，不会再扣款 | 停止推进 |
| 已退款 REFUNDED | 钱包确认对应退款完成 | 停止推进 |

状态名本身不重要，重要的是不能把“已扣款”和“已发权益”合并成一个成功字段。否则只要扣款成功，系统就无法表达后面仍有事情没做。

还要分清业务目标与一次支付尝试。用户要买的这份权益可以有一个业务编号 B42；这次付款使用支付单号 P1001。付款结果未知时继续确认 P1001，不能随手改成 P1002 再扣一次。只有旧尝试已经明确结束，符合业务重试规则，才建立新尝试。

退款也使用稳定单号，比如 R-P1001。钱包需要保证同一单号、同一请求内容不会重复执行；金额、用户不同却用了同一单号时，应拒绝或返回冲突，不能默默当成合法重复。

用户双击购买也要在创建入口处理。对同一个有效购买目标，可以用数据库唯一约束或带条件更新绑定当前尝试，让并发请求返回已有流水。否则即使每个支付单号都幂等，两次请求各生成一个不同单号，仍然可能扣两次钱。

数据库保存了持久化记录，只说明进程重启后有机会恢复。记录本身丢失、备份无法恢复，同样会破坏这套方案；因此数据库的持久化和灾难恢复仍是前提。

## 三、扣款之后来不及写状态，怎样知道钱到底扣没扣

正常情况下，购买服务先把流水推进到支付待确认，再用 P1001 调用钱包。钱包扣款成功，购买服务将状态改为已支付，然后去发权益。

如果钱包已经扣款，本地状态却还没更新，就需要查单恢复。

钱包已经扣款，购买服务还没把已支付写进数据库，就崩溃了。重启后，本地流水仍然是支付待确认。下一次处理不能看到这个旧状态就认定“还没扣钱”，更不能换一个新单号再扣。

它应该向钱包查询 P1001。钱包确认成功，就补写已支付；钱包确认最终失败，就保存支付失败；钱包还在处理中，继续等待并安排下一次查询。响应超时也按未知处理，不能虚构一个确定结果。

![扣款响应丢失时，使用原支付单号查询，再恢复本地状态](/images/posts/transaction-payment-confirmation-flow.svg)

这里需要钱包提供两种能力：同一支付单号幂等处理，以及按这个单号查询可靠结果。只有“支持重试”却没有说明如何识别重复，是不够的；只有一个可能滞后的列表查询，也不够用来决定退款或重新扣款。

查单返回“没有记录”也要小心。旧扣款请求可能仍在网络中，稍后才到达。若钱包允许按原单号安全重试，可以继续使用 P1001；若要结束这次尝试，则需要钱包有确定终结或关闭该单号的能力。一次查不到不能证明原请求永远不会执行。

这也解释了数据库为什么是流程依据，却不是所有外部事实的唯一来源。购买数据库管理“这条流程接下来做什么”；钱包管理“这笔支付到底有没有扣款”；权益服务管理“本单权益到底有没有发放”。本地进度可能落后，恢复时要向对应的权威服务核对。

客户端看到“支付待确认”时，页面可以显示处理中并提供原单号的查询入口。客户端断网、关闭页面，不应让后台恢复停止。接口返回已受理，只说明请求已留存；返回购买成功，则应该已经确认权益发放。两个响应不能混着用。

如果确认扣款后，本地更新又失败了，也不用冒险往下继续。等数据库恢复，再从相同单号查单并推进。为追求一次请求内完成而绕过持久化步骤，会让下一次恢复不知道已经做到了哪里。

## 四、为什么权益超时不能直接退款

扣款确认后，购买服务用 B42 和 P1001 发放权益。权益服务要把“权益已发放”和“由哪笔支付完成”一起保存，并保证重复请求不会重复发放。

成功时，购买服务根据权益服务的确认，把流水改成购买成功。权益调用超时，下一次先查本单的发放结果：已经发放，就补记成功；暂未确定，就继续确认；明确拒绝且不会再执行，才进入补偿判断。

归属也不能省。假设同一个用户另一次购买 P1002 已经拿到权益，不能仅凭“这个用户现在有权益”，就把 P1001 也认定成功。需要查的是对应业务目标与支付单号的处理结果。

现在考虑更危险的竞态。请求 A 发权益，在网络里延迟；恢复任务 B 看见截止时间到了，发起退款；随后 A 才到权益服务，把权益发放了。单纯增加一个截止时间，并没有阻止迟到的动作。

要安全退款，需要权益服务能够关闭本次发放，让“发放成功”和“关闭发放”争用同一份受控状态。例如权益服务为 B42、P1001 保存一条待处理记录：发放只能从待处理改成已发放；关闭只能从待处理改成已关闭。这两种转换不能同时成功。

关闭接口不应只返回“收到取消请求”。它要返回已经关闭且后续不会发放，或者返回已经发放，并指出归属。关闭后到达的旧请求必须检查关闭状态，拒绝再次发放。

示意更新如下，实际还需与权益写入放在正确的本地事务边界内：

```sql
-- 发生在权益服务的数据库，不是购买服务的流水库
UPDATE entitlement_task
SET status = 'CLOSED'
WHERE business_key = :businessKey
  AND payment_no = :paymentNo
  AND status = 'PENDING';
```

更新一行，表示这次关闭赢得了竞争；更新零行，要重新查询具体状态。可能已经发放，也可能早已关闭，不能把零行简单解释成失败。发放接口则只能在合法的待处理状态下，原子地写入权益并标记已发放。

如果关闭请求先到、发放记录还不存在，关闭操作也要留下对应单号的关闭记录，或用等价的规则拒绝迟到请求。否则“没找到记录，所以关闭成功”仍挡不住稍后第一次创建发放记录。

![先确认或关闭本单权益，再决定是否可以退款](/images/posts/transaction-rights-close-refund-flow.svg)

退款分支确定后，购买服务先持久化退款待确认，再按 R-P1001 调用钱包。钱包退成功而本地更新失败，下次就查 R-P1001，确认后保存已退款。退款本身同样会超时，不是一条永远成功的兜底语句。

如果权益服务不支持可靠查询，也不能阻止迟到发放，就没有安全自动退款所需的证据。应该保持待确认，告警并对账或人工处理，必要时改造参与方接口。为了让每条记录看起来“有终态”，强行退款会把未知结果变成资金损失。

退款是新发生的一笔资金操作，需要审计和幂等，它不会把已经提交的扣款历史从数据库中抹掉。对于已经消费的权益、已经寄出的包裹，补偿又有不同规则，不能假定任何动作都有一个简单反操作。

## 五、普通消息可能丢，为什么这条流程仍然能继续

现在每条未完成流水都明确表达待办：支付待确认就查支付，已支付就确认权益，退款待确认就查退款。后台不需要依靠原进程的内存才能知道下一步。

消息队列可以让后续处理更及时。购买服务处理一步后，若还没结束，就发一条普通延迟消息。消息里带流水 ID，消费者收到后，读取数据库当前状态，再执行下一步。

但是数据库提交与发消息是两次操作。状态写成功后、发消息之前崩溃，消息就可能根本没有发出去。普通消息自己无法消除这个缺口。

这套方案增加数据库扫描任务。它定期找出已经到处理时间、还没结束的流水，并调用同一个推进方法。即使消息没有发出，数据库里的未完成记录仍然会被找回来。

```text
同步接口、消息消费者、数据库扫描
              ↓
         advance(流水 ID)
              ↓
        读取当前持久化状态
              ↓
  查询下游事实 / 执行幂等动作 / 保存新进度
              ↓
  结束，或留下下次处理时间继续等待
```

这个扫描不是一句“定时重试”就完成了。每个需要继续的状态都要包含在查询条件里，记录需要有可索引的下一次处理时间；每轮分批处理，限制并发和下游调用速度，不能把全表一次捞进内存。

用游标分页时，要保证周期性重新覆盖待办范围。游标已经越过的旧记录，后来到了处理时间，仍需被下一轮发现。只维护一个永远向前的最大 ID，会漏掉这些记录。

消息也不应该携带一份由消费者直接执行的旧状态。消息可能晚到一天，本地已经退款了，却还写着“现在发权益”。消费者应重新读当前有效状态；已经结束就退出，不再制造副作用。

消费者何时确认消息已处理，也要说明。在这里，确认可以表示本次推进完成，剩余待办已持久化且扫描会再次发现；它不一定表示整个购买完成。若数据库状态未能持久化，不应伪装成这一步完成，消息可按消费重试机制重投。

这个设计允许消息确认后、下一条消息发送前进程崩溃，因为扫描兜住了后续工作。代价是最坏恢复时间取决于扫描周期、积压量和下游恢复速度，不能承诺消息丢失后仍然秒级完成。

扫描任务停了怎么办？要监控它有没有正常运行，也要看各状态最老记录的年龄。只看错误次数可能一直是零，因为根本没有人在处理。支付长期未知、退款积压等情况要有人工接手入口，而不只是无限重试。

## 六、同时来了三个处理者，状态机能保证不重复吗

同步请求、消息和扫描可能同时处理 P1001。把它们放进同一个推进方法，可以统一规则，但并不会让它们自动排队。

假设 A 和 B 都读到支付待确认，版本号都是 3。A 查到支付成功，先更新成已支付、版本 4；B 随后拿版本 3 更新，应该失败，而不是覆盖 A 的结果。

这可以用带旧状态和版本的条件更新实现。通常叫 CAS，即“只有值还是我刚才看到的那份，才修改”：

```sql
UPDATE purchase_flow
SET status = :newStatus,
    version = version + 1,
    next_retry_time = :nextRetryTime
WHERE id = :id
  AND status = :oldStatus
  AND version = :oldVersion;
```

影响行数为零，说明有人改过了，处理者重新读取，再决定退出还是继续。不能不看当前状态就盲目重发原来的动作；更不能把购买成功改回退款待确认。

但本地条件更新只能保护本库。A 和 B 都可能在更新之前向钱包发出请求；要避免重复扣款，仍要靠钱包对 P1001 幂等。权益发放和关闭的互斥，也必须在权益服务自身的状态转换中保障，不能靠购买服务的版本号隔空实现。

可以加锁减少重复调用、降低下游压力，但锁过期、进程暂停和网络延迟仍会留下并发窗口。前面的分布式锁文章强调的保护边界，在这里同样适用：流程跨多个服务，正确性需要各参与方共同配合。

同库里相关证据则应一起提交。例如购买成功状态与对应权益确认编号，退款完成状态与退款编号，不应拆成两个独立提交。否则重启后只看到一个成功字段，却找不到支持它的证据。

这套流程允许一笔款已经扣了、权益还在处理中，并没有自动获得跨服务隔离。其他接口要按状态限制行为，例如处理中不能再次创建有效支付尝试，退款中的订单不能继续发权益。业务页面也应明确展示中间态，而不是把所有非失败状态统称为成功。

在恢复策略上，临时网络故障可以退避后继续；明确的业务拒绝可以走关闭和补偿；结果未知先查事实。达到重试次数上限，只能表示这一轮自动处理要降频或升级，不代表能把未知支付改成失败。

“最终会一致”还有运行条件：数据库记录可恢复，参与方能提供可靠结果，扫描和消息处理还在运行，下游最终恢复或有人处理。若这些条件不成立，程序不能凭一个状态机保证自动收敛。

## 七、事务消息和 Outbox，什么时候比扫描更合适

上面的消息只负责提醒本系统“这条流水该继续了”。状态已经完整表达待办，因此消息漏发后可以扫描找回。

但假设支付成功后，积分、订单、通知三个独立系统都要收到一次支付事件。只扫描购买表的当前状态，不一定能重建所有需要发布的历史事件。记录可能从已支付变成已退款，中间支付成功的事件仍需要留下。

这时，“保存业务结果”和“留下待发布事件”就需要一起设计。常见选择是事务消息或 Outbox，两者都不是让所有消费者与生产者一起提交数据库。

RocketMQ 事务消息先发送一条暂时不给消费者看的消息，通常称为半消息。Broker 确认收到后，生产者执行本地事务，再告诉 Broker：本地提交了，消息可以发布；本地回滚了，消息不要发布。

若生产者在本地提交后断线，没有把结论告诉 Broker，Broker 会回查生产者。回查逻辑要根据持久化的事务记录判断，不能问原线程“你刚才成功没有”。已经提交返回提交，确定回滚返回回滚；无法确认继续按产品机制处理未知。[RocketMQ 事务消息机制](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)

回查也不是无限期保险。RocketMQ 有事务超时与回查限制，长时间无法确认会影响消息结果。回查服务和数据库要能够恢复，异常未决记录仍要跟踪和对账。

这解决的是生产者本地事务与消息发布的关联。消息变得可消费时，下游可能还没处理，消费者处理也可能失败或重复。消费者需要自己的本地事务、幂等记录和恢复机制。不能因为叫“事务消息”，就声称钱包扣款、权益发放和积分增加同时成功。

Outbox 可以理解为数据库里的待发送事件表。业务状态变化时，在同一个本地事务里新增事件行。数据库提交，两份记录一起存在；数据库回滚，两份一起不存在。随后发送程序读取事件，送往消息队列。[Transactional Outbox 模式](https://microservices.io/patterns/data/transactional-outbox.html)

发送成功后、标记已发送之前崩溃，恢复后可能再发一次。事件需要稳定 ID，消费者按事件 ID 或业务编号处理重复，并把消费记录与业务修改放在自己的本地事务中。需要顺序的业务，还要设计发布顺序、分区和版本检查，不能只加一张表就默认有序。

Outbox 留下的是每一次要通知的事件；扫描流水恢复的是尚未完成的当前工作。前者适合可靠广播业务变化，后者适合可从当前状态重新推导的待办。它们也可以一起使用：扫描继续推进购买，Outbox 把已确认的结果通知别的系统。

没有必要把所有简单任务都改成半消息或事件表，但也不能把扫描当万能替代。如果数据库没有保存足够信息，扫描无法猜出进程崩溃前打算发哪条事件。

## 八、2PC、TCC 和 Saga 再放到这里看，就容易理解了

先看严格共同提交。假设两个受控数据库都支持“先准备，等统一决定再提交”的接口，可以由一个协调者询问：你们是否已经准备好提交？

参与者准备好后，保存恢复信息并保留必要资源；协调者收齐赞成答复，持久化提交决定，再通知所有参与者提交。有人准备失败，就决定回滚。这个先准备、后决定的过程，叫两阶段提交，简称 2PC。MySQL 的 XA 是参与此类跨资源事务的一套接口。[MySQL XA 事务](https://dev.mysql.com/doc/refman/8.4/en/xa.html)

如果协调者发出提交决定后崩溃，已经准备的参与者不能随便当作失败回滚，需要恢复并查明决定。等待期间可能继续占用锁和资源，跨网络协调也进入请求耗时。这是它比普通本地事务重的原因之一。[MySQL XA 状态与恢复](https://dev.mysql.com/doc/refman/8.4/en/xa-states.html)

2PC 的目标是共同提交或回滚，也不代表所有参与者在同一毫秒完成，更不会自动解决所有业务隔离问题。普通钱包 HTTP 接口如果没有参与准备和决议的能力，购买服务不能单方面把它纳入 XA。对参与者有限、事务短、原子提交要求明确的受控资源，可以考虑；不要把它默认套在每次跨服务调用上。

再看能预留资源的场景。钱包先冻结 100 金币，库存先保留一份商品；都预留成功，才真正扣款和扣库存；任一预留失败，释放其他预留。冻结不等于已经最终扣款。

这就是 TCC：Try 预留，Confirm 确认使用，Cancel 释放。各服务需要实现这三类业务操作及其持久化记录。确认或取消响应丢失后会重复调用，所以重复执行要安全；取消先到、预留迟到时，也不能重新占用已经取消的资源。[Apache Seata TCC 模式](https://seata.apache.org/docs/user/mode/tcc/)、[TCC 的空回滚与迟到请求处理](https://seata.apache.org/blog/seata-tcc/)

TCC 适合有明确冻结语义的库存、额度等资源，但不是把已有“扣款、退款”方法改个名字就完成。若钱包根本不支持冻结，为了用它需要改造参与方，成本可能高于本文的恢复流程。

最后是 Saga。这个词描述一串各自提交的本地事务：后一步暂时失败就继续恢复，最终做不成则执行补偿。它不依赖长期持有跨库事务，但需要自己规定补偿与中间状态的行为。[Saga 模式](https://microservices.io/patterns/data/saga.html)

本文的扣款、发权益、失败后退款，就采用了这类本地提交与补偿思路。由购买服务保存进度并决定下一步，可以叫编排式的补偿流程。没有通用 Saga 框架也能实现；有框架则可能少写一些调度代码，但框架无法替你判断权益是否属于本单、迟到请求会不会发放、什么情况下退款安全。

因此选型可以从现有接口反推：同库能完成的先用本地事务；接受处理中、下游有幂等与查单能力的长流程，可以用持久化状态加恢复和补偿；本地提交后必须可靠发布事件，再考虑事务消息或 Outbox；严格共同提交且参与方支持协议，才考虑 XA / 2PC；资源能先冻结再确认时，TCC 才有合适的落点。

对一笔具体购买，最先要回答的仍是：扣没扣钱能查吗，发没发权益能查吗，迟到动作能阻止吗，进程崩溃后谁接着处理？这些答案齐了，才能判断某种协议是否有必要。
