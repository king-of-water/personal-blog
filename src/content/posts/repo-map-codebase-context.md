Coding Agent 面对一个陌生仓库，第一件难事不是写代码，而是决定去读哪些文件。一个中等规模的仓库有几千个文件，把它们全塞进上下文既贵又没用；随手打开几个文件，又大概率错过真正相关的那部分。

Repo Map 解决的就是这一步。它把仓库的结构压缩成一份模型能直接读的索引：有哪些模块、哪些符号、谁引用谁、哪些地方最重要。模型先看地图，再决定读什么。这篇文章想讲清楚它内部怎么工作、和代码检索差在哪、在什么条件下会失灵。

证据主要来自 Aider 的公开实现和文档，以及通用的图排序、代码解析知识。Repo Map 不是一个标准协议，各家的实现在细节上差异很大，下面描述的是这类系统的共同结构和 Aider 的代表性做法。

## 一、Repo Map 到底是什么

Repo Map 是一份从代码仓库自动生成的结构摘要：把文件里的符号（类、函数、方法）抽出来，按层级和关系组织，再按重要性排序，最后渲染成一段文本。它不是文档，不解释业务，只回答"有什么、在哪、和谁有关"。

它和索引、目录树都不同。索引求全，只要能查得到就行；目录树只表达位置，不表达关系；地图求重点，用有限的篇幅表达结构和重要性。地图是索引的有损压缩，损失的是细节，保留的是骨架。

地图通常有三个用途。第一是给模型导航，让它在动手前知道仓库由哪些部分组成；第二是给检索定优先级，告诉后续步骤先看哪里；第三是给人一个快速入口，开发者也能用它熟悉仓库。三个用途对应不同消费者，但共享同一份结构信息。

仓库越大，地图省下的越多。在只有几十个文件的小项目里，地图和目录树的差别不大；到了上千个文件，能不能快速定位到相关模块，直接决定一次任务的成败。地图的价值是随规模放大的。

这也解释了为什么地图最早出现在 Coding Agent 的工具链里。开发者面对陌生仓库会迷路，模型更会。地图不是为了让模型更聪明，而是为了让它在动手前不至于全凭运气。

还有一点值得说清楚：地图是"结构摘要"，不是"代码摘要"。它摘要的是模块和符号之间的关系，而不是某段代码在做什么。想理解一段逻辑，仍然要读代码。地图只是帮你更快找到该读哪一段。

### 地图和目录树差在哪

目录树只有位置，没有关系。它不告诉你哪个文件重要，也不告诉你文件之间怎么引用。一个两百个文件的仓库，目录树列出来同样是一两百行，但读完你仍然不知道从哪开始。

地图在目录树的基础上加了两层信息：重要性和关系。重要性来自图排序，关系来自符号引用。有了这两层，"从哪开始"才有一个可计算的答案。这也是为什么地图看起来像目录树，作用却完全不同。

另一个常见误解是把地图当成"自动生成的架构文档"。架构文档解释设计意图，会告诉你为什么拆成这几个模块；地图只描述结构，告诉你有哪些模块、它们怎么连。把两者混在一起，就会期望地图去回答"为什么"，而它只能回答"是什么"和"在哪"。

地图也不会替代读代码。它是一层筛选：先把范围缩小，再让模型去读真正关键的那几段。跳过地图直接读，等于放弃这层筛选；只读地图不读代码，又会在关键实现上停于表面。

地图的好处还在于它可计算。目录树只能被人"看"，地图能被程序排序、筛选、裁剪。正因为可计算，它才能适配不同的预算和任务，而不是一份固定的清单。

### 为什么用图而不是列表

引用关系天然是图：A 调用 B，边从 A 指向 B；调用可以被看成 A 依赖 B。列表只能表达顺序，图能表达这种双向或多向的关系，还能让重要性沿着边传播。

边是有方向的，方向决定重要性往哪流。如果方向弄反，排序会把被依赖的基础库排在前面，而任务通常从调用方入手。方向是最容易忽略、也最容易搞错的一步。边的类型也重要：调用、继承、导入、读写同一状态，权重不同。Aider 一类的实现会给不同边设不同权重，用权重表达"哪种关系更能说明耦合"。

把地图和"项目结构文档"区分开也很重要。结构文档给人看，会解释模块职责和设计意图；地图给模型看，只描述符号和关系，格式要紧凑到能塞进上下文。两者可以共享同一份抽取结果，分别渲染成给人看的文档和给模型看的地图。混为一谈，就会对地图提出它做不到的要求，比如"解释这段代码为什么这样写"。

还有一点常被忽略：地图是压缩后的产物，压缩必然有损。它保留骨架，丢掉细节。判断一张地图好不好，不是看它多完整，而是看它有没有保留住对任务关键的那部分结构。一张只列文件名、没有关系的地图，信息量接近目录树；一张把每个函数体都复制的"地图"，又退化成代码本身。好坏的分界，在于有没有在有限篇幅里保住结构和重点。
把地图和依赖图放在一起，也能看出粒度差别。依赖图通常停在模块或包的粒度，适合做架构分析；地图细到文件和符号，适合做具体修改。一个回答"系统由哪几块组成"，另一个回答"改这行代码会牵动哪些文件"。

地图还天然支持"传播"这类计算。重要性可以沿边流动，影响可以沿边扩散。列表做不到这些，因为它没有边。这也是地图的实现几乎都建立在图结构上，而不是简单文件清单的原因。

地图的另一个作用是统一团队对仓库的认知。每个人对仓库的理解都略有偏差，地图提供了一份公共的、从代码生成的结构视图。当讨论"改动应该放在哪"时，双方看的是同一张图，而不是各自的印象。这份公共视图也是地图在团队协作里的价值。

## 二、大窗口为什么还需要地图

有人会问，既然模型上下文已经能放下几十万 token，为什么还要费劲做地图。答案是大窗口有两个代价，而地图同时缓解这两个代价。

第一个代价是成本。token 越多越贵，而且成本随长度线性增长。把整个仓库塞进上下文，等于每次都为一个只需要改一行代码的任务付全额费用。第二个代价是注意力。内容越多，关键信息越容易被稀释；模型可能读了几万 token，最后仍抓不住重点。

地图的核心价值就在于用更少的 token 承载结构的重点。它不追求完整，只追求"先看什么"。这个问题不随窗口变大而消失，因为"能放下"和"该先看"是两件事。

有人会反驳说，模型可以在需要时自己搜索文件，为什么还要预先给一张地图。问题在于搜索需要有线索。没有线索时，模型只能靠猜关键词，而关键词往往和代码里的命名对不上。地图提供的是结构线索：它不依赖模型猜对关键词，而是直接给出仓库的骨架。

这也是地图和多轮探索的区别。多轮探索每走一步都要调用一次模型，成本高、延迟长；地图是一次性生成、反复使用的。把结构信息提前算好，通常比让模型每次现猜更划算。

换句话说，地图把"理解仓库"从一次性的手工动作，变成了可以重复使用的基础设施。一次构建，多次受益。

### 地图解决的是选择问题

模型真正要解决的是"这么多文件，先看哪些"。地图不解释代码，它帮模型做选择。选择对了，后面的读取才有意义；选择错了，读再多也只是在错误的地方深挖。

从这个角度看，地图是决策的输入，不是答案本身。它把"读哪些代码"从一个靠运气的过程，变成一个由结构引导的过程。哪怕地图不完美，只要它显著提高了第一次选对文件的概率，就有价值。

换个说法，地图把"读哪些文件"这个决策，从模型的即兴发挥，变成一个可以预先计算、可以检查、可以复用的结果。这一步的确定性，让后面所有步骤都更可控。任务失败时，你至少能区分是"一开始就选错了范围"，还是"选对了范围但没读对"。

这种可归因性是地图的隐藏价值。没有地图时，任务失败往往只能笼统地归为"模型不够好"；有了地图，失败可以被拆成范围选择和内容理解两段，分别排查。

预算分配没有一个放之四海皆准的比例，唯一可靠的判断标准是评测：在多组比例下测任务成功率，选效果最好的那组。

### 上下文预算怎么分

地图要占用一部分上下文预算，但通常只占小头。一个常见的分配是把预算分成三份：地图、相关正文、指令。地图占太多会挤掉正文，占太少起不到导航作用，比例要按仓库规模和任务类型调。

地图还应该跟着预算变。预算充足时多渲染一些节点，预算紧张时只留主干。固定大小的地图，在预算紧张时会挤掉真正需要的正文。

值得一提的是，地图和"检索"解决的不是同一个问题。检索是有了明确线索之后去找内容，地图是在还没有线索时给出方向。很多失败并非因为检索算法不好，而是因为一开始就不知道该检索什么。地图补的正是这一步：先把问题可能涉及的区域圈出来，后续的检索和读取才有落点。

从这个角度讲，地图是小成本的保险。它不保证一定找到正确文件，但能显著降低"完全跑偏"的概率。对一次要花几次工具调用、几十秒等待的任务来说，这点保险很划算。
预算分配还要考虑任务类型。宽泛的探索性任务需要更大的地图，帮助模型建立全局认识；精确的修改任务需要更小的地图，把预算留给具体的实现代码。同一个仓库，不同任务的地图占比可以不同。

一个经验是，地图的预算应该随任务的不确定性增长。任务越不确定，越需要地图来缩小范围；任务越明确，地图越可以精简。

把地图和"让模型自己规划"对比也很有意思。规划回答"分几步做"，地图回答"每步该看哪些代码"。两者互补：没有规划的模型容易在中途迷失目标，没有地图的模型容易在第一步就选错范围。成熟的做法是两个都给：先规划任务，再用地图为每一步定位代码。

## 三、符号抽取：从源码到图

地图的第一步是抽取符号。Aider 用 Tree-sitter 把源码解析成语法树，再用查询语句匹配节点，区分"定义"和"引用"。定义是"这里声明了一个符号"，引用是"这里用到了某个符号"。

定义容易定位，引用需要解析作用域。两者的关系就是图的边：文件里有定义，文件引用了别的文件的定义，边就出现了。抽取的质量决定地图的上限，抽取错了，后面的排序和渲染都是错的。

抽取的准确性可以从两个方向评价：有没有漏，即真实存在的定义和引用是否都被抽到；有没有错，即抽到的关系是否真的成立。漏会带来盲区，错会带来噪声，两者都会影响排序质量。

在动态语言上，抽取更依赖约定。通过字符串拼接出来的函数名、通过配置指定的处理器，静态分析往往抓不到。这类缺失要靠运行时信息或人工标注补，不能指望抽取器凭空推断。承认这一点，才能正确解读地图在动态语言仓库上的覆盖率。

抽取的语言支持也不是越多越好。每支持一种语言，就多一套要维护的查询和一堆要处理的边界。覆盖主要语言、把这几种做扎实，通常比铺开十几种、每种都半破更划算。

### Tree-sitter 与多语言支持

Tree-sitter 的好处是抽取依赖语法结构，而不是依赖正则。同一套查询思路可以覆盖多种语言，跨语言时更稳，也更容易维护。

但不同语言的抽取质量差别很大。静态类型语言可以借助类型信息，抽取最准；动态语言需要处理运行时和动态派发，容易漏；模板、宏、代码生成的文件最难处理。所以多语言支持是有取舍的：先支持主要语言并做准，再逐步扩到其他语言，比一上来支持几十种却处处不准更实用。

```
# 每种语言一套查询：定义、引用分开匹配
queries = {
  "python":   {"def": "(function_definition name: (identifier) @name)", "ref": "(call function: (identifier) @name)"},
  "typescript": {"def": "(function_declaration name: (identifier) @name)", "ref": "(call_expression function: (identifier) @name)"},
}
```

多语言仓库还有一层额外难度：跨语言关系往往不体现在直接的符号引用里，而是通过接口定义文件（例如 IDL、protobuf）连接。只看单一语言的调用边，会把跨语言的链路断开。处理这类仓库，要么先解析接口文件把它当成中间节点，要么在渲染时把跨语言关系显式标出。

抽取器本身的版本也会影响结果。Tree-sitter 的语法和查询会随语言演进更新，一次升级可能改变抽取结果。地图系统要能感知这种变化，至少在结果明显变化时给出提示，而不是默默改变排序。

一个务实的顺序是：先把一种语言抽准，再考虑第二种，而不是一开始就追求全覆盖。多语言的价值只有在单语言已经可靠的前提下才成立。

### 解析失败与边界情况

解析失败不能直接丢弃文件，否则地图会缺一块。更稳妥的做法是回退到文件级节点，只保留文件名和大小，并记录这次失败，方便排查是语言不支持还是语法本身有问题。悄悄丢掉文件，会在地图里留下看不见的空洞。

边界情况要显式列出来：宏展开、条件编译、生成代码、多语言文件、超大文件。生成文件（例如 protobuf、ORM 自动生成的代码）节点多但信息量低，应该降权或排除；超大文件会贡献大量节点，可以按类或函数聚合，避免单个文件独占地图。忽略规则本身也要保守：忽略太激进会漏掉重要文件，过度包含又会引入噪声。

抽取还有一个朴素的优化空间：仓库的规模分布通常是长尾的。少数文件包含大部分符号，多数文件很小。利用这个分布，可以只对大文件做深入解析，小文件粗粒度处理，在不明显损失信息的前提下节省大量计算。冷启动只发生一次，但拖得太久也会影响体验，值得做这类优化。

抽取结果本身也应该被缓存。文件没变就复用上次的解析结果，这是增量的基础。没有缓存，每次更新都要重新解析全部文件，增量也就无从谈起。
失败处理的原则是"宁可粗，不可缺"。解析不了的复杂文件，退化成文件级节点也好过消失。地图的空洞里，模型看不见的东西等于不存在；而一个粗糙的节点，至少还能告诉模型"这里有东西"。

对生成代码的处理值得单独说。很多仓库里，自动生成的文件数量远多于手写代码，但结构高度重复、信息量低。如果把生成代码也纳入图，它们会靠数量挤掉真正的手写核心逻辑。常见做法是在忽略列表里按路径或文件头排除生成文件，只保留手写部分。

抽取还有一个工程上的权衡：解析精度和解析速度。全量精确解析最准但最慢，适合离线构建；增量粗略解析最快，适合边写边看。真实系统往往同时保留两条路径，离线建全量、在线走增量，再定期用全量校准增量。

## 四、排序：PageRank 与个性化

抽取出图之后，需要一个排序，决定哪些节点先进入地图。Aider 用的是带个性化的 PageRank。

PageRank 的直觉是：被很多重要文件引用的文件更重要，而且重要性会沿着引用关系传播。它把"被引用的次数"和"引用者的重要性"结合起来，比单纯统计引用次数更稳，不容易被大量小文件刷高分数。

排序决定了地图的"重点"。同一个仓库，不同的排序会给出完全不同的地图。排序错了，地图会把模型引向错误的方向。

排序的质量很难一眼判断，但它对地图的影响是决定性的。同一张图，换一套排序，地图的重点就从业务逻辑变成基础工具，从核心模块变成边缘文件。排序实际上是在替使用者回答"什么是这个仓库里重要的东西"，这本身带有价值判断。

![静态目录、全局 Repo Map 与任务相关 Repo Map 的差异](/images/posts/repo-map-ranking.svg)

因此排序参数通常需要按仓库校准，而不是一套参数通吃。新接入一个仓库时，先看一版地图，对照自己对这个仓库的了解，判断排序是否符合直觉。不符就调参数，而不是抱怨地图没用。

个性化的输入来源可以按可信度排序：直接提到的文件最可信，正在编辑的次之，最近查看的最弱。把这个顺序反映到权重上，地图的焦点会更贴合任务。

### 个性化向量：让地图跟着任务走

PageRank 有一个个性化向量，决定排序偏向谁。Aider 用当前对话涉及的文件作为个性化起点。没有个性化，地图只有一个全局排序；有了个性化，地图会向任务相关的部分倾斜。这就是"通用地图"和"任务相关地图"的区别。

个性化的输入可以有很多来源：用户提到的文件、正在编辑的文件、最近查看的文件、报错堆栈里的文件。输入越贴近任务，地图越有用。常用做法是把这些来源合起来，给不同的来源不同权重。

个性化还有冷启动和漂移两个问题。任务刚开始时往往还没有明确的焦点文件，个性化向量可以先用最近编辑或报错涉及的文件兜底；随着对话推进，焦点会变化，个性化向量也要跟着更新，否则地图会一直盯着开头那几个文件。

一个稳妥的策略是把个性化向量做成滑动窗口：越近期的焦点权重越高，早期的焦点逐渐衰减。这样地图既能跟上任务的变化，又不会因为一句话就彻底重排。

没有个性化的地图，在大型仓库里常常把大量边缘模块排在前面，因为它只看全局引用。个性化是让地图从"这个仓库里什么重要"，变成"对这个问题什么重要"的关键一步。

### 中心性的偏差与改进方向

中心性容易偏爱基础工具和公共库，因为它们被到处引用。但任务真正关心的，可能是一个边缘的业务文件。个性化能缓解这个偏差，但不能完全消除，因为有些关键文件天然引用少。

几种常见的改进方向。一是语义分组：纯符号图不表达"这几段代码属于同一个业务概念"，把相关符号聚成簇，粒度更接近人的理解。二是历史信号：经常一起被修改的文件之间有隐式关系，提交历史能提供这种关系。三是热度信号：最近改动频繁的文件往往是当前的焦点。把这些信号和引用关系结合，地图会更接近真实的工作单元，而不是只反映静态调用。

权重是排序里另一个需要调的旋钮。定义、引用、调用给不同权重，等于在定义"什么算重要"。权重没有通用最优值，要按评测结果调，而且最好跟着仓库的气质走：有的仓库重测试，有的重配置，有的重接口，同一套参数在不同仓库上效果不同。

排序的绝对值其实不重要，相对顺序才重要。没有人需要知道某个文件的分数是 0.13 还是 0.17，需要的是"这两个文件哪个该先看"。不过排序的稳定性有意义：同一个仓库两次排序差异太大，说明抽取或排序不稳定，需要回头检查。
把重要和热点分开也很有必要。最重要的文件不一定是最常被改的，一个稳定但核心的模块可能很久没动；反之，一个频繁改动的文件也可能只是配置或文案。把两者当成独立维度，排序才不会顾此失彼。

两种信号可以合成一个二维排序：结构上关键的部分优先，同时把近期焦点适当提前。这样的排序更接近资深工程师的判断，也更容易被人接受。

个性化向量还有一个容易忽略的作用：它让同一份图可以在不同任务间复用。图本身是仓库级的，不随任务变化；个性化只在渲染时改变排序。这样就不必为每个任务重新构图，只需换一个个性化的起点。这是性能和灵活性的双赢。

## 五、渲染：把地图压进 token 预算

排序之后是渲染。渲染要回答一个约束问题：在给定的 token 预算下，输出尽可能多的、尽可能重要的结构。Aider 的做法是用二分搜索找到"在预算内能渲染的最大地图"，预算多就多渲染，预算少就只留最重要的节点。

渲染格式要紧凑：用缩进表达层级，只保留签名、省略函数体。紧凑是为了在有限 token 里塞进更多结构，同样一个 token，用来表示层级比用来表示空行更有价值。

```
src/
  order/
    service.py
      class OrderService
        def create_order(...)
        def cancel_order(...)
```
二分搜索的另一个好处是自适应。不同模型有不同的窗口，不同任务有不同的预算，二分让同一套逻辑覆盖这些差异，而不是为每种情况写一个固定大小。预算变了，地图自动跟着变。

渲染还要处理缩进的成本。结构靠缩进表达，但缩进也消耗 token；层级太深时，缩进会吃满预算。所以渲染通常会限制最大缩进深度，超过的部分用折叠标记。用少量符号表达层级，是渲染效率的关键。

省略的取舍最后要落在一个判断上：这段信息，模型在导航阶段用得到吗？用得到就留，用不到就省。这个判断贯穿渲染的每一个决定。

### 省略与保留的取舍

省略函数体、保留签名，牺牲了实现细节，保留了结构。对导航来说，签名比实现更重要，因为它回答的是"这个模块提供什么"。是否保留注释要看注释是否承载关键信息：有些仓库的注释写明了关键约束，这时保留注释比多保留几个签名更有价值。

还有一种取舍是文件级还是符号级。文件级地图简单、便宜，符号级地图精确但更大。多数场景文件级够用，只有需要精确定位符号时才下沉到符号级。从文件级开始，按需升级，比一上来就做最细的粒度更现实。
签名和实现的取舍，本质上是结构信息和行为信息的取舍。导航阶段，结构比行为更重要；等到确定要读某个文件时，才需要行为细节。地图服务的正是导航阶段，所以它偏向签名是合理的。

注释的取舍要更小心。有些仓库把关键约束写在注释里，例如"这个函数必须在事务内调用"；这类注释一旦省略，模型可能做出错误假设。一个折中做法是保留注释首行或带特定标记的注释，其余省略。

组装的质量往往比检索的质量更能决定最终结果。检索把正确的片段找出来，组装决定模型能不能用好它。地图在这里的作用，是帮组装判断每段代码的相对重要性。

### 上下文组装的优先级

地图只是组装的一部分。完整的一次上下文通常包括：地图、关键文件的正文、相关测试、接口定义。优先级大致是，关键实现优先于相关测试，相关测试优先于接口定义，接口定义优先于地图摘要。

预算不够时，宁可少放几个文件，也要保证关键实现完整。截断关键实现，比少读一个次要文件危害更大。地图的作用是帮模型在组装时做出这些取舍。

渲染还有一个容易踩的坑：地图太长反而会被忽略。当地图长到超出模型的注意力分配，模型可能只读了开头，后面的结构等于没放。所以地图要短到能被完整阅读，这比 token 上限更严格。宁可少放几个次要节点，也要让整张地图都在有效阅读范围内。

另外，渲染的结果要能被开发者看懂。地图是给模型的，但人也要能读。人看不懂的结构，往往模型也用不好，因为那通常意味着抽取或排序出了问题。把地图打印出来看一眼，是最快的质量检查。
优先级不是固定的，要看任务。排查线上故障时，日志和错误处理代码可能比接口定义更重要；增加新功能时，扩展点和接口定义更靠前。地图本身不决定优先级，它提供结构，优先级由任务决定。

组装还有一个容易被忽略的问题：同一段代码可能被多个来源引用，例如既在地图的扩展范围里，又在检索结果里。组装时要去重，否则同样的代码会重复占用预算。去重看似细节，却能实实在在省下预算。

渲染的输出最好还带一点元信息：基于哪个提交、覆盖了哪些目录、被省略了多少节点。这些信息不影响模型理解结构，却能让人判断这张地图的时效和完整度。没有元信息，一张过期的地图和一张最新的地图看起来一模一样。

## 六、和相邻工具的关系

Repo Map 不是孤立的技术，它处在一组解决"代码理解"的工具中间。分清各自的边界，才知道什么时候用它。
把这几类工具放在一条链路上看更清楚：地图负责缩小范围，检索负责定位片段，侦察负责按任务读取，知识库负责沉淀解释。它们解决的是同一个问题的不同阶段，配合使用比单独用任何一个都更完整。

如果只记一件事，可以记这个分工：地图给结构，检索给证据，侦察给上下文，知识库给理解。四者都会用到代码的抽取结果，但产出的形态和用途各不相同。

分不清界面的一个常见后果是重复造轮子：把搜索、地图、知识库各做一套，结果三套抽取互相打架。先想清楚每类工具的职责，再决定自建还是复用，能省下很多返工。

### 与 RAG、FastCode、LLM Wiki 的分工

Repo Map 是一张常驻的全局结构，回答"仓库整体长什么样"。RAG 是给定问题即时寻找证据，回答"哪里可能相关"。FastCode 是先在结构上侦察、再读取正文，回答"这个问题该读哪些代码"。LLM Wiki 是把仓库编译成可阅读的知识页，回答"这部分怎么工作、为什么这么设计"。

四者可以叠加使用：用地图选范围，用 RAG 找片段，用 FastCode 做任务级侦察，用 Wiki 看背景和决策。它们不是竞争关系，而是同一份底层结构在不同粒度上的呈现。Aider 的 Repo Map、FastCode 的语义结构地图、LLM Wiki 的知识模型，实际上都在抽取同一类东西，只是渲染方式不同。
值得强调的是，这几类工具可以共享同一份底层结构。Repo Map 用的是符号图，FastCode 的语义结构地图用的是更丰富的多层图，LLM Wiki 用的是知识模型。它们的抽取目标高度相似，差别主要在渲染和使用方式。理想情况下，一个仓库只抽取一次，再按需渲染成地图、上下文或文档。

现实中它们常常各自抽取，因为出自不同的工具和团队。这带来重复计算，也带来不一致：同一个代码实体，在不同工具里可能被描述得不一样。长期看，统一的抽取层会是这类工具发展的方向。

和已有设施的关系，最终取决于团队的技术债和资源。有钱有人的团队倾向自建以获得控制力，资源有限的团队倾向复用现成的。两条路都可行，关键是别两头都做一半。

### 与 Sourcegraph、IDE、LSP 的关系

Sourcegraph 是通用代码搜索和导航，主要给人用；能力很强，但输出是给检索者看的匹配结果，而不是给模型看的紧凑结构。IDE 和 LSP 提供精确的跳转和引用，比 Tree-sitter 更准，但更慢，也更依赖环境。

地图可以复用这些已有的索引。复用 IDE 或 LSP 的数据能省下大量重复解析，代价是依赖它们的格式和可用性。对批量构建地图的场景，速度更重要；对精确分析，精度更重要。

一个容易混淆的点是"地图"和"依赖图"的关系。依赖图关注模块之间的依赖，粒度粗；地图关注文件和符号的关系，粒度细。两者可以互补：依赖图给出模块边界，地图给出文件关系。做架构分析时看依赖图，做具体修改时看地图。

这几类工具还有一个共同趋势：都在从"给人看"转向"给模型看"。传统的搜索和文档是为人的阅读效率设计的，而模型需要的是紧凑、结构化、可直接消化的输入。地图、侦察、知识模型，本质上都是为模型重新设计过的代码表示。

## 七、一次真实任务中的使用

把地图放回工作流，才能看出它值不值。一个典型的修改任务大致是这样：模型先读地图，据此选中几个相关文件，读取正文，做出修改，再运行测试验证。

在地图出现之前，模型对陌生仓库的处理方式通常有两种：要么从入口文件开始顺序读，要么依赖用户点名文件。前者容易在无关代码上消耗大量上下文，后者要求用户已经知道该改哪里。地图填的正是这两者之间的空档。

地图只是这条链路的第一步。但它改变了第一步的性质：从"随便打开一个文件"，变成"从结构上相关的地方开始"。在陌生仓库里，这个差别尤其大，因为错误的第一跳往往会把后面所有步骤带偏。

还有一层不那么明显的作用：地图让模型的每一步都留下可追溯的路径。它为什么读这个文件，是因为地图上这个文件与入口相邻、被多次引用。任务失败时，这条路径能被复盘；任务成功时，这条路径也能被复用。

### 从地图到修改的完整轨迹

假设任务是"修复下单接口在高并发下偶发的超时"。模型读地图，看到 `order` 模块和它依赖的 `payment`、`inventory` 模块，以及这几个模块的被引用情况。它据此先读 `order` 的服务实现，再沿着调用关系读 `payment` 客户端，最后读相关测试。

整个过程里，地图缩小的不只是读取量，还有推理量。模型不需要在几十个无关模块之间纠结，注意力可以集中在少数几个相关文件上。这类收益在预算紧张时尤其明显。

值得注意的是，地图并不保证一次就选对。它可能把某个相关文件排在后面，或因静态分析漏掉一条动态调用。区别在于，即使选错了，地图也提供了一个可解释的起点：是排序把相关文件排低了，还是抽取根本没有这条边。这两种情况对应不同的修复方向。

### 影响分析与代码评审

地图还能支持影响分析：改一个函数签名，沿调用图找所有调用者，再找它们的测试，范围就清楚了。评审时，同一份信息能显示改动的传播范围，回答"改这里会影响什么"。

把影响范围从猜测变成结构推导，是地图在工程上的直接价值。它不保证列全（动态调用会漏），但比凭印象圈范围可靠得多。

评审场景还有一个附带好处：地图让"这段代码为什么在这里"变得可追溯。当评审者看到某个改动的调用范围，就更容易判断改动是否放在正确的地方，而不是只盯着 diff 本身。地图把 diff 放回了它的结构上下文里。

评审场景还有一个附带好处：地图让"这段代码为什么在这里"变得可追溯。当评审者看到某个改动的调用范围，就更容易判断改动是否放在了正确的地方，而不是只盯着 diff 本身。地图把 diff 放回了它的结构上下文里。

地图在多轮任务里的作用会随时间变化。任务初期，地图帮模型建立全局认识；任务中期，地图帮模型确认没有遗漏相关模块；任务后期，地图帮模型检查改动没有破坏依赖关系。同一张地图，在任务的不同阶段回答不同的问题。

## 八、增量更新与维护

地图能不能用，很大程度取决于它更不更新得动。一个每次都要全量重算的地图，在快速迭代的仓库里很快就会落后，落后到不可信。

地图的"新鲜度"和"精确度"是一对矛盾。追求每一处关系都最新最准，就要频繁全量重算，代价高；只做粗略的增量，速度快但会滞后。多数系统在两者之间取一个平衡：日常增量更新，定期全量校准。

增量更新的基本思路是只处理变化的文件，并限制受影响的范围。缓存键可以基于文件哈希、语法树哈希或符号哈希，粒度越细命中越高。一个文件改动通常意味着它里面的符号也变了，所以文件级哈希往往就够用。

增量更新最容易出错的地方是删除和重命名。新增一个文件容易处理，删掉一个文件却常常被忽略，于是地图里残留着已经不存在的节点。重命名更麻烦，因为它同时涉及删除和新增，如果只按文件路径匹配，会丢掉这个文件原来的所有关系。这两类操作必须在更新逻辑里显式处理，而不是指望通用流程自动覆盖。

### 重算范围与刷新频率

一个文件变化，严格来说只影响它一跳邻域内的排序，不一定需要全图重算。把全图重算留给定期任务，把局部重算留给日常更新，能大幅提速。近似做法是只重算受影响的一跳邻域，代价是一部分排序会滞后，滞后在同一批文件反复改动后可能累积。

判断重算是否足够的依据，可以是一个简单的不变量：地图里不应出现已经不存在的文件或符号，也不应缺少新出现的核心模块。前一条靠删除处理保证，后一条靠覆盖率检查保证。两者都满足，地图就足够可信。

刷新频率要和仓库的变化频率匹配。刷新太频繁浪费计算，太稀疏会过期。它应该是一个可调参数，而不是固定值。

刷新还可以按重要性分级。核心模块变化时立即更新，边缘模块可以等到下一次定期更新。全仓库用同一个频率，要么浪费在无关文件上，要么让核心变化延迟反映。

### 分支、版本与持久化

不同分支的代码不同，地图也要分分支，至少要标明它基于哪个分支，避免用错版本。一个简化策略是只维护主干分支的地图，特性分支按需生成。地图本身还可以带版本，和代码版本绑定，这样既能判断它是否过期，也能存进版本控制、和代码一起演进。

持久化让冷启动只发生一次：地图序列化到磁盘，下次直接加载，再增量更新。格式可以是文本、JSON 或二进制，文本便于人检查，二进制便于快速加载。

持久化让冷启动只发生一次：地图序列化到磁盘，下次直接加载，再增量更新。格式可以是文本、JSON 或二进制，文本便于人检查，二进制便于快速加载。

版本绑定还有一个附带用途：当模型输出可疑时，可以核对它当时看到的地图版本，判断问题出在地图本身还是模型理解。没有版本绑定，这种核对无从谈起。

### 谁来维护地图

地图需要有人负责更新抽取规则、忽略列表和排序参数。没人负责，地图会逐渐偏离仓库。把抽取规则当成代码来维护，而不是一次性配置，是地图长期可用的前提。仓库越复杂、语言越多，维护成本越高，这一点要算进是否采用地图的决策里。

一个实用的做法是把地图的生成和校验放进 CI：代码合并后自动更新地图，并运行一组"地图应该包含哪些核心模块"的断言。断言失败时提示有人检查，而不是等到使用者发现地图缺了一块。

维护地图还有一条现实经验：抽取规则的复杂度要和收益匹配。支持十种语言、解析所有边界情况的地图，维护成本很高；只支持主流语言、覆盖常见结构的地图，往往已经能拿到大部分收益。先做够用的版本，再按真实痛点补语言和边界。

## 九、局限与失败模式

地图不是万能的，它有几种稳定的失灵方式，值得提前知道。

这些失灵方式有个共同点：它们都不是"算法不够聪明"，而是"信息本身不完整"。静态分析看不到运行时行为，结构描述不了业务语义，索引追不上代码速度。知道这些边界，才能在地图给出可疑结果时，判断是换个参数能解决，还是要绕开地图找别的证据。

### 静态结构不等于运行时行为

静态引用抓不到反射、动态派发、事件订阅和配置驱动的调用。完全静态的地图，对动态语言的覆盖率会明显偏低。调用图是起点，不是全部；在结果可疑时，需要补充运行时证据或人工判断。

补救的办法之一是引入运行时信号。例如把测试执行时的调用轨迹记录下来，和静态图合并。运行时能看到实际发生的调用，静态图能看到可能发生的调用，两者结合比任何单一来源都完整。代价是需要运行环境，也需要处理轨迹的噪声。

同样，签名说明函数做什么，却不说明为什么这样约束。业务规则要从测试、文档和决策记录里补。地图负责结构，业务约束需要 LLM Wiki 那类产物补充。

这也解释了为什么地图和知识库常常要一起用：地图回答"在哪"，知识库回答"为什么"。只看地图，会知道某段逻辑的调用方很多，却不知道这些调用为什么必须存在；只看知识库，会知道某个约束的理由，却不知道它落在哪些代码上。

### 过期、业务无关与权限

索引会过期，过期的地图会指向已经不存在的文件或关系，比没有地图更危险。结构相关也不等于业务相关：结构上相邻的代码，业务上可能毫无关系，纯结构图会把无关代码拉进来。侦察要结合语义，才能减少这种噪声。

权限是另一个容易被忽略的点。地图暴露文件结构和命名，敏感项目的地图要按权限裁剪，过滤要在侦察阶段就生效，而不是等到放进上下文时才过滤。多仓库场景下，还要合并多个仓库的结构，而跨仓关系通常通过接口而非直接调用，识别更难。

权限是另一个容易被忽略的点。地图暴露文件结构和命名，敏感项目的地图要按权限裁剪，权限过滤要在侦察阶段就生效，而不是等到放进上下文时才过滤。多仓库场景下，还要合并多个仓库的结构，而跨仓关系通常通过接口而非直接调用，识别更难。

多仓库还有一层结构性问题：如果每个仓库各自生成地图，跨仓的调用就会被切断，模型看到的是几张互不相连的图。要解决这个问题，需要在关系层做合并，把跨仓接口识别出来。这项工作通常比单仓地图复杂得多，也是多仓场景下地图效果打折的主要原因。

### 什么时候地图反而有害

如果地图给出了错误的重要排序，模型会集中读错误的文件。错误的地图比没有地图更糟，因为它带着一种可信的外表。所以地图的质量必须能被评测；没法验证质量的地图，宁可不用。

还有一种情况是地图本身没错，但被用错了地方。地图适合"先看什么"，不适合回答"这一段逻辑为什么这样写"或"这个业务规则是什么"。把它当成万能入口，会在它能力之外的维度上得到空泛的结果。清楚它擅长什么，比让它承担所有理解任务更重要。

还有一些场景根本不需要地图：单个已知文件的小改动，直接读就行；只有几十个文件的小仓库，人脑和简单搜索更快。地图的价值随仓库规模和任务复杂度上升，在小规模场景里它只是增加了一层开销。

判断是否引入地图，可以问三个问题：仓库大到人脑装不下吗？任务是否需要先理解结构？团队里有没有人愿意维护抽取规则？三个都"是"，地图值得做；有一个长期是"否"，就该先解决那个问题，而不是硬上地图。

这些局限也提示了地图的正确用法：把它当成"降低盲区"的工具，而不是"保证正确"的工具。它能显著减少"完全找不到相关代码"的情况，却消除不了"找错了相关代码"的可能。使用者要保留对地图结果的怀疑，尤其是当它和常识冲突时。

## 十、自己实现一个最小版本

要理解地图，最好的办法是实现一个最小版本。它不需要 Tree-sitter 的全部能力，也不需要完整的 PageRank，只要把"抽取、构图、排序、渲染"四步走通。

四步里，最容易低估的是抽取，最容易高估的是排序。抽取决定了图里有什么，是地基；排序只是给已有节点排顺序，地基没打好，排序再精妙也无济于事。很多人一上来就琢磨排序参数，结果卡在抽取质量上。

抽取阶段提取定义和引用；构图阶段把文件连成图；排序阶段按重要性排序；渲染阶段在预算内输出。每一步都能单独测试，也都能单独替换。

把每一步都做成纯函数是个好习惯：输入是确定的数据，输出是确定的结果，没有隐藏状态。这样每一步都能单独跑测试，也能在出问题时快速定位是哪一步的输入不对。地图的调试往往就靠这种分步隔离。

```python
def extract_tags(path):
    tree = parser.parse(open(path).read())
    defs, refs = [], []
    for node in walk(tree):
        if is_definition(node): defs.append(symbol(node))
        if is_reference(node): refs.append(symbol(node))
    return defs, refs

def build_graph(files):
    graph = {"nodes": {}, "edges": []}
    for f in files:
        defs, refs = extract_tags(f)
        graph["nodes"][f] = {"defs": defs, "refs": refs}
    for f in files:
        for r in graph["nodes"][f]["refs"]:
            if r.file in graph["nodes"]:
                graph["edges"].append((f, r.file, "ref"))
    return graph
```

### 排序与渲染

有了图，排序和渲染都很短。排序用 PageRank，个性化向量取当前任务涉及的文件；渲染在预算内按重要性输出节点。结构简单，但已经具备地图的核心能力。

这套实现刻意省略了很多细节：没有多语言、没有增量、没有缓存、没有边界处理。它的价值在于把主干跑通，让你能在一百行内看清地图到底在做什么。真实系统是在这个主干上加工程，而不是换一套完全不同的思路。

```python
from networkx import pagerank

def rank(graph, focus_files):
    scores = pagerank(graph, personalization=focus_files)
    return sorted(graph.nodes, key=lambda n: scores[n], reverse=True)

def render(nodes, budget):
    lines = []
    for node in nodes:
        line = f"{'  ' * node.depth}{node.signature}"
        if count_tokens(lines + [line]) > budget: break
        lines.append(line)
    return "\n".join(lines)
```

### 让它可调试、可确定

最小版本要顺手加上两个性质。一是确定性：同样的仓库快照应该产生同样的地图，排序和渲染都不能有随机性，否则无法对比和调试。二是可调试：能 dump 中间结果，包括抽取的符号、构建的边、每个节点的分数。看不到中间结果，地图出问题时只能靠猜。

还有一个常被忽略的性质是幂等：对同一个文件重复抽取，结果应该一致；对同一张图重复渲染，输出应该相同。幂等让增量更新可以放心重试，也让缓存可以安全复用。没有幂等，一次失败的更新可能留下半新半旧的结果，比不更新更糟。

一个低成本的正确性测试是构造一个小仓库，人工写出期望的地图，再和实际输出对比。它能覆盖抽取、排序、渲染的完整链路。

最小版本跑通之后，下一步不是加更多算法，而是加更多测试。为抽取、排序、渲染各写一组针对小仓库的测试，覆盖常见语言和边界情况。有了测试，后续的优化才有安全网；没有测试，每次改动都可能悄悄破坏已有能力。

## 十一、评测与取舍

地图有没有用，要用数据回答，而不是感觉。评测大致分三层：检索层、定位层和任务层。

三层之间是递进关系。检索层没通过，定位层基本不会通过；定位层没通过，任务层更不可能好。所以排查时可以从下往上：先看检索是否命中，再看上下文是否组装完整，最后才看任务是否完成。反过来，只有任务层分数变差时，才需要往上追查是检索还是定位出了问题。

检索层看正确文件是否被找到、排名如何，常用前 k 命中率。定位层看最终组装的上下文是否包含回答问题必需的代码。任务层看端到端成功率和 token 消耗的组合。只看其中一层都会得出片面的结论。

评测样本的选择比指标本身更关键。样本要覆盖三类任务：答案在单文件里的、需要跨文件的、需要理解动态行为的。第三类最容易暴露地图的短板，因为动态行为正是静态图的结构性盲区。样本里全是单文件任务，评测会给出过于乐观的结论。

### 任务成功率与 token 效率

任务成功率是最直接的指标：同样任务，有地图和没地图，成功率差多少。它最贴近使用，但噪声大，需要足够样本，否则会把随机波动当成地图的收益。

对比时要控制变量。模型、提示、仓库快照、任务集都要一致，只让"有没有地图"这一项变化。同时报告置信区间，避免把一两个任务的差别当成系统性收益。

token 效率是另一个维度：同样的结构信息用了多少 token。地图的价值本来就在于用更少 token 表示结构。省了 token 但降低成功率不算赢，信息足但太贵也不算好，指标要成对看。

把两个维度画在一张图上会更清楚：横轴是 token，纵轴是成功率，每个配置是一个点。地图的真正价值，是让曲线向左上移动，即同样成功率用更少 token，或同样 token 换更高成功率。只在一个方向上改善，可能是以另一个方向为代价换来的。

### 一个务实的评测方法

选二十个真实任务，记录每个任务"正确修改涉及哪些文件"，再看地图是否把这些文件排在了前面。这是一种贴近使用的评测，衡量的是地图能不能帮模型选对范围。

这个方法的另一个好处是低成本复现。二十个任务的标注一次做完就能反复使用，每次调整参数都重跑一遍，很快能看出改动是否真的有效，而不是靠零散的主观印象。

还可以做一个更快的检查：让一个熟悉仓库的人看地图，问他"最重要的几个文件在不在，顺序对不对"。人的判断快且可靠，适合在自动评测之前先做一次方向性验证。

人的判断也有盲区：熟悉仓库的人会不自觉地把自己的知识补进地图，觉得"看起来挺对"。所以最好找不完全熟悉该模块的人来看，才能暴露地图本身的信息量是否足够。

评测的结论最好落成一句话：在什么仓库、什么任务、什么预算下，地图把定位成本降低了多少。这样的结论可复用、可比较，也便于判断地图对当前场景是否值得。笼统地说"地图有用"或"地图没用"，都缺少可操作的信息。

## 十二、什么时候值得用

地图的价值和仓库规模、任务复杂度正相关。小仓库、单文件任务，它带来的收益可能还不如开发者自己的记忆；大仓库、跨模块任务，它解决的正是最难的"从哪开始"。

除了规模，还有一个维度是"团队流动性"。新人多、人员轮换快的团队，更依赖把结构显式化，因为记忆留不住。这种情况下，地图的价值不仅对模型成立，对人也成立。

一个实用的判断是：如果任务只需要改一个已知文件，就不需要地图；如果需要先理解结构再动手，地图就有用。判断标准是"是否已经知道要改哪里"。

这个标准可以再具体一点：如果你能直接说出要改的文件名，就不需要地图；如果只能说出"大概在订单相关的部分"，就需要地图帮你把"大概"变成具体文件。

### 从最小可用开始

如果决定引入地图，建议从最小可用版本开始：文件级、单向引用、简单排序。跑通之后再逐步增加粒度、补齐关系类型、加入个性化。

扩展的顺序也有讲究。先补抽取质量，再调排序，最后压渲染。抽取是地基，排序和渲染是上层；顺序颠倒，会在错误的基础上反复优化，收益有限。每次扩展都用那二十个任务复测一遍，确认真的变好再加下一项。

最小可用能快速验证价值，也避免一开始就陷入优化细节。地图的目标是减少无效阅读，不是展示完整结构。如果它让定位更快，就值得保留；如果只是增加了阅读负担，就该缩小范围或调整参数，而不是继续加内容。

还有一点值得提醒：地图是手段，不是目标。有些团队花大力气把地图做到很精细，却发现任务成功率没变，因为瓶颈其实在别处，比如工具调用不稳定或测试不可靠。地图只解决"先看什么"，如果系统卡在别的问题上，地图再精美也换不来收益。先确认瓶颈在哪，再决定要不要投入地图。

还有一个容易被忽略的前提：地图要有人用。如果团队里的 Agent 工作流根本不读地图，做得再好也只是摆设。引入地图的同时，要确认它真的接进了任务流程，而不是停在"可以生成"这一步。

## 十三、我对 Repo Map 的理解

Repo Map 解决的问题很小，也很基础：在动手之前，先知道仓库长什么样。它不解释语义，不做业务判断，只把结构显式化。

但正是这个基础问题，决定了后面所有步骤的效率。模型读得对不对、检索搜得准不准、上下文组装得合不合理，都建立在"先看什么"这个选择上。地图把这个选择从靠运气，变成一个由结构引导的过程。

它更像是理解仓库的放大镜，也是缩小搜索空间的透镜。用很小的 token 代价，换来更好的起点。起点对了，后面很多工作都会顺；起点错了，后面越努力越偏。这就是为什么在一堆代码理解工具里，地图不显眼，却常常是第一个该用的。

### 一句话总结

Repo Map 把"先看什么"这个问题，变成一张可以预先算好、反复使用的结构图。它不解释代码，不判断业务，只负责让起点更准。在代码理解这一长串工具里，它站在最前面，也最容易被忽略。
