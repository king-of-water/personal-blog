让 Coding Agent 修改一个陌生仓库时，我们很容易陷入两个极端。

一种做法是只给它当前文件。模型能看清局部实现，却不知道仓库里已有的接口、工具类和抽象，最后又造出一套重复代码。另一种做法是把大量文件塞进上下文。模型确实看见了更多内容，注意力和 Token 也被无关实现占满。

Repo Map 走的是中间路线：保留少量完整文件，同时提供一份仓库地图。地图不复制所有代码，只列出重要文件、类、方法、函数签名以及它们之间的引用关系。模型先借地图形成全局印象，确定需要深入阅读的文件，再把有限上下文用在实现细节上。

Aider 是 Repo Map 最有代表性的实践之一。它会在每次代码修改请求中附带一份与当前对话相关的仓库地图，并根据 Token 预算裁剪内容。[Aider 的官方文档](https://aider.chat/docs/repomap.html)给出的默认建议预算是 1K Token。这个数字不大，却足以放下一批跨文件符号，帮助模型发现当前文件之外可以复用的模块。

## 一、Repo Map 到底是什么

先看一份简化后的 Java 仓库地图：

```text
src/main/java/com/example/order/OrderController.java:
│class OrderController {
│    OrderResponse create(CreateOrderRequest request)
│    void cancel(Long orderId)

src/main/java/com/example/order/OrderService.java:
│interface OrderService {
│    Order createOrder(CreateOrderCommand command)
│    void cancelOrder(Long orderId)

src/main/java/com/example/order/OrderServiceImpl.java:
│class OrderServiceImpl implements OrderService {
│    Order createOrder(CreateOrderCommand command)
│    void cancelOrder(Long orderId)

src/main/java/com/example/inventory/InventoryClient.java:
│interface InventoryClient {
│    void reserve(ReserveRequest request)
│    void release(ReleaseRequest request)
```

它比目录树多了一层语义。模型不只知道仓库里有四个文件，还知道文件暴露了哪些符号，接口和实现大概是什么形状。它又比完整源码轻得多，没有方法体、日志、异常处理和样板代码。

Repo Map 可以回答三类基础问题：

1. 仓库里有哪些可以使用的模块和接口；
2. 当前任务可能涉及哪些文件；
3. 想继续理解某个行为，下一步应该打开哪里。

这张地图并不尝试直接解释业务。`cancelOrder()` 为什么先改状态再释放库存，仍然需要读取完整实现、测试和设计文档。Repo Map 提供的是导航坐标。

### 地图的三个用途

地图有三个用途：给模型一个全局导航、给检索一个优先级、给人一个快速入口。

导航让模型知道仓库里有哪些部分，优先级告诉它先看哪里，入口让人能快速定位。三个用途对应不同消费者，但共享同一份结构信息。

### 地图和索引的区别

索引求全，地图求重点。索引回答"有没有这个东西"，地图回答"哪些重要、彼此什么关系"。

地图是索引的有损压缩：损失的是细节，保留的是结构和重要性。它不是更小的索引，而是另一种视图。

### 为什么用图而不是列表

列表只能表达顺序，图能表达关系。引用关系天然是图，用图处理更自然。

图还支持传播：重要性可以沿着边流动，一个文件的重要程度受它引用和被引用的对象影响。

### 边的方向

引用是有方向的：A 引用 B，边从 A 指向 B。方向决定重要性往哪流。

如果方向弄反，排序会把被依赖者排在前面，而任务通常从依赖者入手。方向是最容易忽略、也最容易出错的一步。

### 权重的一个例子

```python
EDGE_WEIGHTS = {"def": 1.0, "ref": 0.5, "call": 2.0}
```

权重体现"哪种关系更重要"。调用比普通引用更能说明耦合，所以权重更高。

### 抽取的准确率

抽取准确率决定地图的上限。抽取错了，排序再准也没用。

抽取准确率要单独评测：抽样核对一批符号是否被正确识别、引用是否指向正确目标。

### 语言支持矩阵

不同语言的抽取质量不同。静态类型语言最好，动态语言次之，模板和宏最难。

了解语言支持矩阵，才能知道地图在哪些仓库可靠。在支持差的语言上，地图的可信度要打折扣。

### 大文件怎么处理

一个几千行的文件会贡献大量节点，可能占满整个地图。可以按类或函数聚合，避免单个文件独大。

聚合是压缩的另一种形式。它保留结构，减少噪声。

### 生成文件的处理

自动生成的文件（例如 protobuf、ORM 代码）节点多但信息量低。应该降权或直接排除。

不处理生成文件，地图会被噪声淹没。真正重要的手写代码反而排不上。

### 地图和上下文工程

地图是上下文工程的一部分：它决定模型先看到什么结构。

上下文工程不只是选内容，还包括内容的顺序和粒度。地图处理的是"先看什么"这一层。

## 二、有大上下文窗口，为什么还需要地图

上下文窗口变大以后，把整个仓库交给模型看起来变得可行。问题是窗口容量只说明“能装多少”，没有保证模型能同等重视每一段内容。

大量无关代码会带来几种具体影响：

- 每次请求都要为相同代码支付输入 Token；
- 关键定义可能被埋在长上下文中间；
- 相似类、旧实现和测试夹具会干扰判断；
- 对话继续增长后，系统需要压缩或丢弃旧内容；
- 仓库稍有变化，预先拼好的大上下文就会过期。

Aider 的使用建议明确提醒用户不要把所有文件加入对话。它会自动分析仓库并补充 Repo Map，让完整上下文保留给真正可能修改的文件。官方 FAQ 也提到，过多无关文件可能降低代码结果质量并增加成本。

一个实用的上下文通常分成三层：

```text
完整代码层：当前要编辑或验证的少量文件
仓库地图层：其他文件的重要符号和签名
按需检索层：地图不足时，再搜索并读取新文件
```

完整代码负责细节，仓库地图保持全局感，工具调用负责继续探索。这比单纯追求“把更多代码塞进去”更稳定。

### 大窗口的两个代价

大窗口有两个代价：成本和注意力。成本是线性的，token 越多越贵；注意力是非线性的，内容越多，关键信息越容易被稀释。

地图的核心价值是同时缓解这两个代价：用更少的 token 承载结构的重点，让模型把预算花在真正相关的部分。

### 地图解决的是选择问题

模型真正要解决的是"这么多文件，先看哪些"。地图不解释代码，而是帮模型做选择。

选择对了，后面的读取才有意义；选择错了，读再多也没用。地图是决策的输入，不是答案本身。

### 图的大小

大仓库的图可能有几十万节点。PageRank 要能在这个规模上跑，还要跑得快。

增量更新和缓存，本质上都是为了避免每次全量重算这张大图。

### 采样的必要性

超大仓库不可能把整张图放进一次计算。可以按目录分层，或者只算相关子图。

分层是把大图拆成小图，各自排序，再合并。代价是跨层的关系会被削弱。

### 测试与实现的权重

测试和实现的关系是双向的：测试引用实现，实现不一定引用测试。

权重设置要反映"任务通常从哪一侧入手"。修行为从测试入手，理解结构从实现入手。

### 排名对任务类型的敏感性

不同任务关心的代码不同。修 bug 关心出错路径，加功能关心扩展点。

单一排序难以适配所有任务。个性化是缓解，但还可以按任务类型切换权重。

### 一个任务路由的设想

按任务类型选择不同的排序参数：修 bug 偏向测试和错误处理，加功能偏向扩展点。

这需要任务分类，但能显著提升地图的相关性。类型化决策在这里又派上用场。

### 抽取的边界情况

宏、生成代码、条件编译、多语言文件都是边界情况。处理不好会让地图出现缺口或错误。

边界情况要显式列出来，逐一处理。默默忽略，会在地图里留下看不见的空洞。

### 一个仓库的规模分布

大多数仓库里，少数文件包含大部分符号，多数文件很小。分布是长尾的。

利用这个分布，可以只深入处理大文件，小文件粗粒度处理。这样既省时间，又保住重点。

### 地图和代码库的"气质"

每个仓库有自己的气质：有的重测试，有的重配置，有的重接口。地图要能反映这种气质。

同样的排序参数，在不同气质的仓库上效果不同。参数要跟着仓库调。

## 三、Aider 怎样提取仓库里的符号

Aider 的实现入口在 [`aider/repomap.py`](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py)。生成地图的第一步，是从源文件中提取定义和引用。

### 1. Tree-sitter 负责理解语法结构

Aider 使用 Tree-sitter 解析不同语言的代码。Tree-sitter 会生成语法树，查询文件再从语法树中捕获类名、函数名、方法名等节点。它的查询语言适合匹配具体语法结构，不必为每种语言手写一套完整解析器。

以 Java 为例，概念上可以把查询理解成：

```scheme
(class_declaration
  name: (identifier) @name.definition.class)

(method_declaration
  name: (identifier) @name.definition.method)

(method_invocation
  name: (identifier) @name.reference.call)
```

真实查询会考虑更多语法情况，这里只展示定义和引用的区别。Aider 将捕获结果整理成类似下面的 Tag：

```python
Tag(
    rel_fname="src/order/OrderService.java",
    line=42,
    name="cancelOrder",
    kind="def",
)
```

每条记录至少要回答四个问题：符号叫什么、位于哪个文件、处于哪一行、这是定义还是引用。

Tree-sitter 的优势是速度快、语言覆盖广，也适合增量解析。它的边界同样明显：静态语法不一定能还原反射、依赖注入、运行时注册和字符串形式的调用。Repo Map 看见的是源码中能够被解析的结构，不是运行时世界的完整复制。

### 2. 定义和引用把文件连接起来

假设 `OrderServiceImpl.java` 定义了 `cancelOrder`，`OrderController.java` 和 `OrderJob.java` 引用了它。系统就得到两条跨文件关系：

```text
OrderController.java ──引用 cancelOrder──▶ OrderServiceImpl.java
OrderJob.java        ──引用 cancelOrder──▶ OrderServiceImpl.java
```

文件由此成为图上的节点，符号引用成为边。一个被很多文件引用的定义，往往是公共接口、领域模型或基础设施入口，值得优先进入地图。

这里要保留一份怀疑：引用次数高不一定说明业务重要。`StringUtils` 可能遍布仓库，却和当前“取消订单”任务关系不大。因此 Repo Map 还需要利用当前对话调整排序。

### Tree-sitter 的查询机制

Tree-sitter 把源码解析成语法树，再用查询语句匹配节点。定义和引用各用一套查询。

查询机制让抽取依赖语法结构，而不是依赖具体语言的正则。跨语言时更稳，也更容易维护。

### 定义和引用的抽取差异

定义是"这里声明了一个符号"，引用是"这里用到了某个符号"。定义容易定位，引用需要解析作用域。

两者的关系构成图：文件里有定义，文件引用其他文件的定义，边就出现了。图的质量取决于引用解析的准确度。

### 多语言支持怎么落地

多语言支持要处理不同语言的语法差异。有的语言用 tree-sitter 查询，有的用已有的 tags 工具，有的需要回退到简单的符号提取。

支持的广度和精度是取舍。先支持主要语言并做准，再逐步扩展，比一上来支持几十种语言却处处不准更实用。

### 解析失败怎么办

解析失败的文件不能直接丢弃，否则地图会缺一块。可以回退到文件级节点，只保留文件名和大小。

失败要记录，方便排查是语种不支持还是语法错误。悄悄丢掉文件，会让地图出现看不见的空洞。

### 与符号索引的结合

符号索引提供精确的"定义在哪、引用在哪"。地图用它构图，但不暴露全部符号。

地图是符号索引上的一个视图。索引求全，地图求重点，两者是同一份底层数据的两种呈现。

### 与代码搜索的结合

地图给出范围，代码搜索给出具体位置。两者结合：先用地图像定几个目录，再在目录里搜索。

这比全局搜索更聚焦，也更省 token。地图负责"去哪找"，搜索负责"找到那一行"。

### 与 IDE 索引的关系

IDE 已经维护了符号索引。地图可以复用 IDE 的索引，而不必重新解析整个仓库。

复用能省大量计算。代价是依赖 IDE 的索引格式和可用性。

### 与 Language Server 的关系

LSP 提供精确的跳转和引用。地图可以用 LSP 的数据，比 tree-sitter 更准，但更慢。

精度和速度的取舍。批量构建地图时速度重要，精确分析时精度重要。

### 排名分数的解释

排名的绝对值不重要，相对顺序才重要。用分数解释"为什么这个文件重要"意义不大。

但排序的稳定性有意义。同一个仓库两次排序差异太大，说明抽取或排序不稳定。

### 分数与位置的关系

文件在目录里的位置也是一个信号。核心目录往往比工具目录更重要。

可以把目录权重作为先验，和引用图结合。位置是先验，引用是证据。

### 一个可选的目录权重

```python
DIR_PRIOR = {"src": 2.0, "lib": 1.5, "tests": 0.8, "vendor": 0.2}
```

先验权重让地图更贴近工程的常识，而不是只看纯引用次数。

### 忽略目录

vendor、node_modules、build 等目录应该忽略。它们节点多但和任务无关。

忽略列表是地图可用性的基本配置。没有忽略列表，地图会被依赖库淹没。

### 忽略文件

生成的 .min.js、.pb.go、lock 文件也应该忽略。

忽略规则要可配置，不同仓库忽略的东西不同。写死的忽略列表，迟早会不合时宜。

### 一个常见错误：忽略太激进

忽略太激进会漏掉真正重要的文件。忽略规则要保守，宁可多留一点。

过度忽略和过度包含，都会损害地图。前者漏信息，后者添噪声。

### 与代码覆盖率工具的关系

覆盖率工具知道哪些代码被执行过。测试覆盖率高的模块往往更重要。

覆盖率可以作为排序的一个信号，和引用图结合使用。

### 与变更频率的关系

经常变更的文件可能是热点，也可能是痛点。变更频率是一个独立的排序信号。

### 一个可选的热度信号

```python
heat[path] = commits_in_window(path, days=90)
```

热度反映"大家最近在关心什么"，和静态引用关系是互补的。

## 四、PageRank 怎样挑出重要代码

文件和引用关系组成图以后，Aider 使用图排序寻找重要节点。思路来自 PageRank：一个节点被多个重要节点引用，它的得分也会提高。[NetworkX 的 PageRank 文档](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.link_analysis.pagerank_alg.pagerank.html)将其描述为根据入链结构计算节点排名。

放到代码仓库里，可以这样理解：

```text
很多业务模块都引用 Money
            ↓
Money 的全局重要性较高

当前对话正在修改 OrderController
            ↓
与 OrderController 相连的 OrderService 获得额外权重
```

PageRank 提供仓库级中心性，个性化向量则把当前任务注入排序。Aider 的实现会关注已经加入对话的文件、用户提及的文件名和标识符，让地图随着对话变化。

因此，同一个仓库面对不同任务，地图内容也会不同：

```text
任务 A：修复订单取消
OrderController → OrderService → InventoryClient → OrderEventPublisher

任务 B：调整优惠券过期时间
CouponController → CouponService → CouponPolicy → CouponExpireJob
```

如果地图永远只展示仓库中引用最多的符号，它会退化成一份静态 API 目录。实用的 Repo Map 会同时考虑全局重要性和任务相关性。

![静态目录、全局 Repo Map 与任务相关 Repo Map 的差异](/images/posts/repo-map-ranking.svg)

### PageRank 的直觉

PageRank 的直觉是：被很多重要文件引用的文件更重要。重要性沿着引用关系传播。

它把"被引用的次数"和"引用者的重要性"结合起来，比单纯统计引用次数更稳，不容易被大量小文件刷高。

### 个性化向量怎么定

个性化向量决定排序偏向谁。Aider 用当前对话涉及的文件作为个性化起点。

没有个性化，地图只有一个全局排序；有了个性化，地图会向任务相关部分倾斜。这是"通用地图"和"任务相关地图"的区别。

### 权重怎么调

定义、引用、调用等不同类型的边可以给不同权重。调权重就是调地图的偏好。

权重没有通用最优值，要按评测结果调。调权重的过程，本质上是在定义"什么算重要"。

### 中心性的偏差

中心性容易偏爱基础工具和公共库，因为它们被到处引用。但任务真正关心的，可能是一个边缘的业务文件。

个性化能缓解这个偏差，但不能完全消除。知道偏差存在，才能在结果不理想时想到它。

### 一个真实的失败场景

在一个大型 monorepo 里，没有地图时，模型倾向于读根目录附近的文件，忽略了深处的业务代码。

有了地图和个性化，它会先看和任务相关的模块。这个差别在陌生仓库里尤其明显。

### 地图要不要包含测试

测试是理解行为的重要线索。地图可以包含测试文件，但权重通常低于实现。

是否包含测试取决于任务：修改行为时测试更重要，理解结构时实现更重要。

### 地图要不要包含配置

配置说明了运行时行为。地图可以包含关键配置，但配置文件往往很多很杂。

只保留和任务相关的配置，而不是全部。把所有配置都放进地图，会挤占真正重要的结构。

### 地图的内存占用

图结构可能很大，内存占用是设计要考虑的因素。

可以用紧凑表示或外部存储来减少内存压力。内存不够时，地图要么分片，要么持久化。

### 地图的序列化

地图可以序列化到磁盘，下次直接加载，不必每次重新计算。

序列化让冷启动只发生一次。之后都是加载加增量更新。

### 地图的输入输出契约

地图的输入是仓库快照，输出是结构文本。契约清楚，才能替换实现。

把地图做成一个纯函数，便于测试。同样的输入，同样的输出。

### 地图的确定性

同样的仓库快照应该产生同样的地图。确定性来自固定的排序和渲染。

不确定性会让对比失效。两次结果不同，就无法判断是数据变了还是算法抖了。

### 一个测试地图的方法

构造一个小仓库，人工写出期望的地图，再和实际输出对比。

这是最低成本的正确性测试。小仓库能覆盖抽取、排序和渲染的完整链路。

### 一个常见的优化顺序

先修抽取准确率，再调排序，最后压渲染。

抽取错了，后面全是白搭。顺序错了，会在错误的基础上反复调参。

### 地图的层次化

大仓库可以分层：顶层地图给模块，模块内地图给文件，再往下给符号。逐层下钻。

层次化让地图在任意规模都能用。小图给全景，大图给细节，按需切换。

### 一个层次化示例

```text
src/                   # 顶层：模块
  order/               # 下钻：文件
    service.py         # 再下钻：符号
      class OrderService
```

同一份知识模型，可以渲染成不同层次的视图。

### 地图和子图

任务相关时，可以只渲染相关子图，而不是整张图。

子图更聚焦，也更省 token。整张图用于冷启动，子图用于具体任务。

### 一个子图选择的方法

以任务涉及的文件为起点，取 k 跳邻域。

邻域大小决定子图的广度。k 太大接近全图，k 太小可能漏掉关键依赖。

### 一个上下文预算的分配建议

把预算分成三份：地图、相关正文、指令。地图通常占小头。

地图占太多会挤掉正文，占太少起不到导航作用。比例要按仓库规模和任务调整。

### 地图和模型能力

模型越强，越能用好地图。弱模型可能只看地图的显眼部分。

地图的效果和模型能力相关。同一个地图，在不同模型上的价值不同。

### 一个测试：换模型看地图收益

同样的地图，在不同模型上的收益不同。评测时要固定模型，否则会把模型差异当成地图差异。

### 地图和提示位置

地图放在提示的什么位置也有影响。放在开头做背景，通常比放在末尾更常被读到。

### 地图和语言生态

不同语言生态有不同的工具。地图要适配语言生态，用最合适的工具。

统一用一套工具，会在某些语言上吃亏。分语言选工具，效果更好但实现更复杂。

### 一个跨语言仓库的挑战

跨语言仓库的关系往往通过文件格式（例如 IDL）连接。地图需要理解这些连接。

只看单一语言，看不到跨语言的调用。跨语言仓库对地图的要求更高。

## 五、如何把地图压进 Token 预算

完成排序以后仍不能直接输出全部符号。大型仓库的类和函数签名本身就可能超过上下文窗口。

Aider 会按照排名从高到低选取 Tag，把这些 Tag 渲染成带文件名和必要上下文的代码树，然后估算 Token 数量。它通过搜索合适的截断位置，让输出尽量接近 `--map-tokens` 指定的预算。

可以把算法简化成下面的伪代码：

```python
def build_repo_map(files, chat_files, mentioned_symbols, token_budget):
    tags = extract_definitions_and_references(files)
    graph = build_file_reference_graph(tags)

    scores = personalized_pagerank(
        graph,
        focus_files=chat_files,
        focus_symbols=mentioned_symbols,
    )

    ranked_tags = rank_definitions(tags, scores)

    low, high = 0, len(ranked_tags)
    best = ""

    while low <= high:
        middle = (low + high) // 2
        candidate = render_code_tree(ranked_tags[:middle])

        if count_tokens(candidate) <= token_budget:
            best = candidate
            low = middle + 1
        else:
            high = middle - 1

    return best
```

预算机制比固定选择 Top 100 更合理。不同语言的签名长度差异很大，一个带大量泛型参数的 Java 方法可能占据数行，一个 Python 函数只需要一行。最终约束应该落在模型实际接收的 Token，而不是符号数量。

预算也不该完全固定。刚进入仓库、还没有选择文件时，Agent 更依赖全局地图；已经锁定两三个目标文件以后，地图可以收缩，把空间让给完整代码、测试结果和对话历史。Aider 会根据会话状态动态调整地图大小，并支持 `auto`、`always`、`files` 和 `manual` 等刷新策略。

### 二分搜索怎么适配预算

预算不是固定值，要按模型窗口和当前对话动态算。用二分搜索找到"在预算内能渲染的最大地图"。

二分让地图能自动适配不同预算，而不需要人工指定要放多少文件。预算多就多渲染，预算少就只留最重要的。

### 渲染格式的设计

渲染要紧凑：符号名加缩进表示层级，省略函数体，只保留签名。

紧凑是为了在有限 token 里塞进更多结构信息。同样一个 token，用来表示层级比用来表示空行更有价值。

### 省略与保留的取舍

省略函数体、保留签名，牺牲了实现细节，保留了结构。对导航来说，签名比实现更重要。

是否保留注释，取决于注释是否承载关键信息。有些仓库的注释说明了关键约束，这时保留注释比保留更多签名更有价值。

### 什么时候地图反而有害

如果地图给出了错误的重要排序，模型会集中读错误的文件。错误的地图比没有地图更糟。

所以地图的质量要能被评测。没法验证质量的地图，宁可不用。

### 一个改进方向：语义分组

纯符号图不表达"这几段代码属于同一个业务概念"。语义分组能把相关符号聚成簇。

分组可以用聚类或人工标注，粒度更接近人的理解，也更接近任务的边界。

### 一个改进方向：历史信号

经常一起被修改的文件之间有隐式关系。提交历史可以提供这种关系。

把历史关系和引用关系结合，地图会更接近真实的工作单元，而不是只反映静态调用。

### 地图与依赖图的关系

依赖图关注模块依赖，地图关注文件和符号。地图更细，依赖图更粗。

两者可以互相补充：依赖图给出模块边界，地图给出文件关系。

### 地图的性能预算

地图生成要在可接受时间内完成。大仓库可能几分钟，小仓库应该几秒。

性能预算决定了能做什么。超预算的功能，再有用也用不上。

### 一个性能优化：并行解析

文件解析可以并行。解析是 CPU 密集，适合多核。

并行能显著缩短冷启动时间。冷启动只发生一次，但拖太久会影响使用体验。

### 一个性能优化：缓存解析结果

解析结果可以缓存。未变化的文件直接复用。

缓存是增量的基础。没有缓存，每次更新都要重新解析全部文件。

### 地图的持久化格式

地图可以存成文本、JSON 或二进制。文本便于查看，二进制便于加载。

格式取决于用途。需要人审查时用文本，需要快速加载时用二进制。

### 地图和文档生成

地图可以喂给文档生成器，产出模块说明。

地图是结构，文档是解释。结构稳定，解释可以按需要生成。

### 地图和开发者体验

地图也可以直接服务开发者：一条命令生成当前仓库的结构概览。

它把"仓库长什么样"变成随时可得的输出，而不是需要专门去问人或翻目录。

### 地图和新人问题

新人最常问"这个功能在哪个文件"。地图能直接回答这类问题。

## 六、Repo Map 与普通目录树差在哪里

目录树只保存物理结构：

```text
src/
├── controller/
├── service/
├── repository/
└── model/
```

它适合发现模块，却不能说明每个文件提供什么能力。Repo Map 增加了符号和关键代码行：

```text
service/OrderService.java:
│interface OrderService
│    Order createOrder(CreateOrderCommand command)
│    void cancelOrder(Long orderId)
```

调用图则更进一步，试图描述符号之间的调用：

```text
OrderController.cancel
  → OrderService.cancelOrder
  → InventoryClient.release
  → OrderEventPublisher.publish
```

三者适合不同阶段：

| 结构 | 信息量 | 主要用途 | 主要缺口 |
| --- | --- | --- | --- |
| 目录树 | 低 | 认识模块和文件布局 | 不知道文件内部能力 |
| Repo Map | 中 | 给模型提供跨仓符号全景 | 不包含完整实现和精确运行时链路 |
| 调用图 / Code Graph | 高 | 路径追踪与影响分析 | 建图更贵，动态行为仍可能缺失 |

Repo Map 的价值来自适度。它没有承担所有代码理解任务，而是用很少的上下文回答“仓库里还有什么值得看”。

### 目录树缺的是什么

目录树只有位置，没有关系。它不告诉你哪个文件重要，也不告诉你文件之间怎么引用。

地图在目录树的基础上加了"重要性"和"关系"两层信息。这两层正是模型在陌生仓库里最缺的。

### 地图是否等价于项目结构文档

不完全等价。项目结构文档给人看，地图给模型看，格式和取舍都不同。

但两者可以共享同一份抽取结果。抽取一次，分别渲染成给人看的文档和给模型看的地图。

### 地图的可视化

地图可以可视化成人看的图：节点是文件，边是引用，颜色是重要性。

可视化帮助人理解结构，也是调试地图的工具。看不出结构的图，往往是抽取或排序出了问题。

### 地图的输出格式

地图可以输出成文本、JSON 或图结构。给模型用文本最省 token，给工具用 JSON 更方便。

格式取决于消费者。同一份地图，可以同时渲染成给人看和给模型看的两种形式。

### 地图与提示词的关系

地图是给模型的一种提示，但它不是指令。它提供事实，不规定动作。

把地图当指令写，会让模型失去灵活性。地图只是"仓库长这样"，怎么用由模型决定。

### 地图的 token 计数

token 计数要按实际模型算，不同模型的分词不同。

精确计数能避免超预算。估算偏差大时，地图可能在关键时刻被截断。

### 地图和 CI

地图可以在 CI 里生成并缓存，供开发者和模型使用。

把地图生成放进 CI，能保持地图和代码同步，而不是靠人记得更新。

### 地图的可访问性

地图是给模型的，但也应该能被开发者看懂。

可读的结构对两者都有用。人看不懂的地图，往往模型也用不好。

### 地图和故障排查

排障时，地图能显示相关模块和它们的依赖，帮排查者理解影响范围。

理解影响范围是排障的关键一步。地图把这一步可视化。

### 地图和重构

重构时，地图能显示耦合紧密的部分，提示哪些代码可以一起动。

耦合紧密的代码一起重构，比零散修改更安全。

### 地图和文档

地图可以自动生成"模块关系图"，作为文档的一部分。

自动生成的关系图不会过期，因为它跟着代码走。

### 地图和代码搜索的互补

先用地图像定范围，再用搜索定位。

这个组合在陌生仓库里最有效：地图缩小范围，搜索精确定位。

### 地图的简洁原则

地图的每一条都应该有用。无用的行会稀释有用的行。

简洁不是少放，而是不放没用的。删掉噪声，比增加内容更能提升地图质量。

### 一个最小命令示例

```bash
repo-map --budget 2000 --focus src/order/service.py
```

预算决定输出多少，焦点决定偏向哪里。两个参数就够表达大部分需求。

### 地图和版本控制

地图可以存进版本控制，和代码一起演进。

存进版本控制的地图，能看到结构的变化历史，也能回滚到旧版本。

### 地图和知识沉淀

地图的结构可以沉淀进 LLM Wiki，变成可阅读的模块页。

两者共享抽取，只是渲染方式不同。一份抽取结果，可以同时支撑给模型的地图和给人的文档。

## 七、Repo Map、RAG、FastCode 和 LLM Wiki 的关系

这几个概念最容易混在一起，因为它们都在向模型提供仓库知识。

### Repo Map：常驻的仓库索引页

Repo Map 通常随请求一起进入上下文。它短、稳定、可快速刷新，作用类似书前面的目录和索引。

### RAG：根据问题即时寻找证据

RAG 会把问题转换为关键词或向量查询，从索引中召回相关代码块和文档。它更适合回答具体问题，但一次检索可能漏掉没有文本相似度的结构关系。

### FastCode：先在结构地图上侦察，再读取正文

FastCode 把仓库探索做成一个显式阶段。Agent 可以多步搜索语义结构地图、沿调用和依赖关系移动，收敛后再加载完整代码。Repo Map 更像一次性提供的压缩全景，FastCode 更像一套可以交互探索的侦察工具。

### LLM Wiki：把仓库知识沉淀为可阅读页面

LLM Wiki 面向持续阅读和知识复用。它会把代码事实组织成模块说明、业务流程和架构页面。Repo Map 可以辅助 Wiki 发现核心符号，Wiki 也可以反过来补充地图无法表达的业务解释。

它们可以组合成一套代码知识系统：

```text
Repo Map       提供轻量全局结构
RAG            针对问题召回局部证据
FastCode       在复杂任务中继续结构化探索
LLM Wiki       沉淀稳定、可阅读的解释
Skills         规定找到知识后如何修改和验证
```

Repo Map 不需要替代其中任何一层。它填补的是“完整文件太重，目录树又太薄”之间的空位。

### 四者的组合使用

Repo Map 给全局排序，RAG 按问题找证据，FastCode 在结构上侦察再读正文，LLM Wiki 沉淀成可读页面。

四者可以叠加：用地图选范围，用 RAG 找片段，用 Wiki 看背景。它们不是竞争关系，而是不同粒度上的工具。

### 与代码评审的关系

评审时，地图能显示改动的传播范围：改了 A，哪些文件受影响。

这个功能和"改这里会影响什么"直接对应，是地图在评审场景里的主要价值。

### 一个失败案例：地图太长反而被忽略

地图太长时，模型可能只看开头，后面的结构等于没放。

地图要短到能被完整阅读。长度是地图可用性的一个隐藏约束，比 token 上限更严格。

### 地图和任务规模

小任务不需要地图，大任务需要。地图的价值和任务规模正相关。

任务越大、涉及文件越多，地图的帮助越明显。

### 地图和代码搜索的边界

地图给结构，搜索给位置。地图不替代搜索，搜索也不替代地图。

把两者组合，才知道"去哪找"和"找到哪一行"。

### 地图的一个典型使用流程

生成地图，模型读地图，选中文件，读取正文，修改，验证。地图是这条链路的第一步。

把地图放回工作流，才能看出它值不值。脱离流程评价地图，意义有限。

## 八、一次真实任务中怎样使用 Repo Map

假设任务是：

> 取消订单时增加优惠券返还，并保证重复消费不会重复返还。

Agent 当前只有 `OrderCancelConsumer.java` 的完整内容。Repo Map 还提供：

```text
CouponService.java:
│interface CouponService
│    void returnCoupon(ReturnCouponCommand command)

CouponServiceImpl.java:
│class CouponServiceImpl implements CouponService
│    void returnCoupon(ReturnCouponCommand command)

CouponRecordRepository.java:
│interface CouponRecordRepository
│    Optional<CouponRecord> findByOrderId(Long orderId)

IdempotencyService.java:
│class IdempotencyService
│    boolean tryAcquire(String businessKey)
```

模型因此知道仓库里已有返还接口、订单维度查询和幂等服务。它可以提出读取 `CouponServiceImpl` 与相关测试，而不是直接在消费者里新写一套数据库更新。

接下来仍要验证：

1. `returnCoupon` 是否已经幂等；
2. 事务边界包含哪些操作；
3. 消息重复和数据库回滚怎样处理；
4. 是否有缓存需要同步失效；
5. 现有测试使用什么夹具和断言。

地图帮助 Agent 选对入口，不替它完成这些判断。

### 一次修改的完整轨迹

一次修改从地图开始：模型看到地图，选中相关文件，读取正文，修改，运行测试。

地图只是第一步，但没有它，第一步可能就是盲选。盲选在陌生仓库里尤其昂贵。

### 地图在其中的角色

地图的角色是缩小搜索空间。它不保证找对，但能提高找对的概率。

把地图看成"第一层过滤"，而不是"完整答案"，定位更准确。

### 地图的更新延迟

地图更新如果太慢，会落后于代码。更新延迟要控制在一个可接受范围。

对快速迭代的仓库，更新延迟尤其重要。地图落后一小时，就可能指向已经不存在的文件。

### 地图的稳定性

同样的输入应该得到同样的地图。随机性会让调试困难。

排序和渲染都要确定。每次结果都不一样的地图，无法用来对比和评测。

### 增量更新的正确性

增量更新要处理文件删除和重命名。漏掉会残留旧节点，地图于是指向不存在的文件。

删除和重命名是最容易出错的增量场景。这两类操作要在更新里显式处理。

### 地图的评估频率

地图的质量会随仓库变化而变化。定期评估地图质量，就像定期评估其他组件。

仓库重构后尤其要重新评估，因为结构和重要性都变了。

### 地图的增量重算范围

一个文件变化，影响的是一跳邻域内的排序，不一定是全图。

限制重算范围，能大幅提速。把全图重算留给定期任务，把局部重算留给日常更新。

### 一个近似策略

只重算受影响的一跳邻域，近似更新全图排序。

近似省时，代价是一部分排序会滞后。滞后在同一批文件的多次改动后可能累积。

### 地图和精确性的取舍

精确的全图重算慢，近似的增量快。按刷新频率选择。

频繁刷新的场景适合近似，偶尔刷新的场景适合精确。

### 地图的失败恢复

地图生成失败时，系统应回退到"列出顶层目录"这种最小信息，而不是什么都不给。

回退保证任何情况下都有起点。完全失败，会让模型彻底失去方向。

### 地图的渐进增强

先给最小地图，再按预算增强。渐进增强保证任何预算下都有输出。

预算少时给出主干，预算多时增加细节。这比固定输出更适应不同场景。

### 地图和任务分解

把大任务分解时，地图帮你看清任务的边界和涉及哪些模块。

分解错了，后面每一步都会偏。地图让分解基于结构，而不是猜测。

### 地图和依赖漂移

重构后依赖关系变了，地图要跟着更新，否则会指向已经不存在的关系。

依赖漂移是地图过期的常见原因。定期重算能缓解这个问题。

## 九、增量更新为什么决定可用性

如果每次对话都重新解析整个仓库，Repo Map 很快会变成启动瓶颈。Aider 会按文件修改时间缓存 Tag。文件没有变化时直接复用定义和引用；文件变化后只重新解析对应部分。

一个工程化实现至少需要三层缓存：

```text
解析缓存：文件内容 → 定义与引用 Tag
图缓存：Tag 集合 → 文件关系和基础排名
地图缓存：对话焦点 + Token 预算 → 最终文本
```

三层缓存的失效条件不同。文件内容变化会影响解析与关系图；用户在对话中提到新符号，可能只需重新计算个性化排序；Token 预算变化则只影响最后的选择和渲染。

大型 Monorepo 还要处理范围。Aider 提供 `--subtree-only` 和忽略文件配置，允许用户只分析当前子树。实际系统也应该过滤生成代码、构建产物、第三方依赖和归档目录。地图里的噪声越多，排序算法越难补救。

### 增量缓存的键

缓存键可以基于文件哈希、语法树哈希或符号哈希。粒度越细，命中越高。

文件哈希最简单，符号哈希最精确但计算多。多数情况下文件哈希就够了，因为一个文件改动通常意味着它里面的符号也变了。

### 何时全量重建

当大量文件变化、语言版本升级，或者抽取逻辑本身改变时，要全量重建。

全量重建慢，但能保证一致性。增量更新快，但可能残留过期结果。两者按场景切换。

### 多仓库的地图

多仓库时，每个仓库一张地图，再在关系层合并。

跨仓引用往往通过接口而非直接调用，需要额外识别。只做单仓地图，看不到系统整体的耦合。

### 权限与地图

地图可能暴露文件结构。敏感项目的地图要按权限裁剪。

地图是元信息，但也可能泄露项目结构。多人或多租户环境下，地图也要过权限。

### 地图的刷新频率

刷新太频繁浪费计算，太稀疏会过期。刷新频率要和代码变化频率匹配。

把刷新频率当成一个可调参数，而不是固定值。

### 地图和分支

不同分支的代码不同，地图也要分分支。至少要让地图标明它基于哪个分支。

分支切换时地图可能失效。标注分支能避免用错版本的地图。

### 一个多分支的简化策略

只维护主干分支的地图，特性分支按需生成。

这样避免为每个分支都维护一张地图，代价是特性分支首次使用时要等待生成。

### 地图的版本

地图带版本，才能对应代码版本。没有版本，无法判断地图是否过期。

版本是地图可信度的一部分。过期地图和没有地图一样危险。

### 地图的维护成本

地图需要维护抽取规则、忽略列表和参数。维护成本和仓库复杂度挂钩。

仓库越复杂、语言越多，维护成本越高。要把它算进是否采用地图的决策里。

### 地图和团队规模

团队越大，越需要地图，因为没人能记住整个仓库。

小团队靠记忆就够了，大团队必须靠结构。

### 地图的一个反直觉点

最重要的文件不一定是最常被改的。核心但稳定的文件也很重要。

把"重要"和"热点"分开，是排序的两个维度。只看热点，会漏掉稳定但关键的模块。

### 一个二维排序

结合重要性和热度，可以得到更符合直觉的排序。

重要性回答"结构上关键"，热度回答"最近被关心"。两者一起看，更接近人的判断。

### 地图的一个局限：它不解释语义

地图告诉你文件和符号的关系，但不告诉你业务含义。业务含义要靠文档和 Wiki。

结构能回答"在哪、和谁有关"，语义才能回答"为什么这样做"。地图只是前者。

## 十、Repo Map 的几个局限

### 1. 静态引用会漏掉动态行为

Spring 依赖注入、反射、注解扫描、消息订阅、SPI 和配置路由都可能隐藏真实关系。地图里没有一条边，不代表运行时没有调用。复杂问题仍要结合 Trace、日志、测试和框架元数据。

### 2. 中心性容易偏爱基础工具

被大量文件引用的工具类排名很高，却不一定对当前任务有用。个性化排序、路径过滤、文件角色和问题语义需要共同参与，不能只看 PageRank。

### 3. 签名不足以解释业务约束

方法名可以告诉模型存在 `returnCoupon()`，无法解释它能否重复调用、事务失败后是否重试。业务知识仍来自实现、测试、ADR、故障复盘和 Skills。

### 4. 地图也会给模型制造错觉

模型可能把地图中的省略内容当成完整实现，甚至尝试直接编辑地图片段。Aider 因此会针对模型能力决定是否默认启用 Repo Map。提示中需要明确说明：地图只用于导航，修改前必须读取真实文件。

### 5. 多仓库和权限需要额外设计

微服务调用经常跨仓库。分别生成 Repo Map 很容易，建立版本一致的跨仓关系更难。权限过滤也必须在地图生成前完成，不能先把无权访问的符号放入上下文，再要求模型忽略。

### 动态调用怎么补

静态引用抓不到反射、动态派发和配置驱动的调用。这些要靠在运行时记录，或者靠人工补充。

完全静态的地图，对动态语言的覆盖率会明显偏低。知道这个局限，才能在结果可疑时回头检查。

### 业务约束怎么补

签名说明函数做什么，但不说明为什么这样约束。业务规则要从测试、文档和决策记录里补。

地图负责结构，业务约束需要 LLM Wiki 那类产物补充。两者结合，才能既看到结构又理解约束。

### 一个可选的渲染示例

```text
src/
  order/
    service.py
      class OrderService
        def create_order(...)
        def cancel_order(...)
    repository.py
      class OrderRepository
```

缩进表达层级，签名表达接口。读者一眼就能看出结构和关系。

### 为什么缩进比文字更省

缩进表达层级，不花 token 在连接词上。结构信息用符号表达，比用句子表达更省。

省下来的 token 可以放更多节点。地图的价值就在于把 token 用在结构上。

### 地图要不要带行号

行号帮助定位，但会占 token。可以只对最重要的节点带行号。

行号是成本换精度的取舍。全都带行号会让地图膨胀，都不带又难以定位。

### 地图的调试

地图出问题时，要能 dump 中间结果：抽取的符号、构建的边、排序的分数。

可调试是地图能维护的前提。看不到中间结果，就只能靠猜。

### 一个最小的图结构

```python
graph = {"nodes": {}, "edges": []}
graph["nodes"]["src/a.py"] = {"symbols": [...]}
graph["edges"].append(("src/a.py", "src/b.py", "ref"))
```

节点是文件，边是引用。结构简单，容易检查和调试。

### 一个最小的 PageRank 调用

```python
from networkx import pagerank
scores = pagerank(adjacency, personalization=focus)
```

接口就这么简单。复杂的是先把图建准。

### 一个取舍：文件级还是符号级

文件级地图简单，符号级地图精确但更大。多数场景文件级够用。

符号级在需要精确定位时才有价值。按仓库规模和任务精度要求选择。

### 一个判断：任务是否需要地图

如果任务只需改一个已知文件，不需要地图。如果需要先理解结构，地图有用。

判断标准是"是否已知要改哪里"。已知就不用地图，未知才需要。

### 地图的自动化程度

地图可以全自动生成，也可以人工修正。人工修正能补上静态分析漏掉的关系。

全自动是起点，人工修正提高上限。两者结合，比追求纯自动更实用。

### 一个可选的混合方案

自动生成骨架，人工补充关键模块的说明和关系。

混合方案兼顾覆盖和深度。全自动覆盖广但浅，人工深入但慢。

### 一个判断地图质量的快速方法

让一个熟悉仓库的人看地图，问他"最重要的几个文件在不在，顺序对不对"。

人的判断快且可靠。地图好不好，熟悉仓库的人一眼就能看出来。

## 十一、自己实现一个最小版本

第一版不需要图数据库或向量数据库。选一个语言和一个中等规模仓库，完成下面四步就能验证价值。

### 第一步：提取定义和引用

使用 Tree-sitter 或语言服务器得到：

```text
file, symbol, kind, line, signature
```

先覆盖类、接口、函数和方法。字段、局部变量和匿名函数会迅速放大图规模，可以稍后增加。

### 第二步：建立文件关系

当文件 A 引用了文件 B 定义的符号，就增加一条 A 到 B 的边。可以用引用次数作为初始权重，并降低测试、生成代码和样板文件的权重。

### 第三步：注入任务焦点

从用户问题和已打开文件中提取文件名、类名和方法名，为对应节点增加个性化权重。第一版不必使用复杂语义模型，精确名称和简单分词已经能产生明显差异。

### 第四步：按预算渲染

输出文件路径、符号签名和少量父级上下文。持续加入高分符号，达到 Token 预算时停止。随后让模型回答两个问题：它能否正确选择下一批文件，能否复用仓库已有接口。

第一版的代码骨架可以控制在几百行以内。后续工作主要集中在语言适配、排序特征和评测集。

### 一个最小的符号抽取

```python
def extract_tags(path):
    tree = parser.parse(open(path).read())
    defs, refs = [], []
    for node in walk(tree):
        if is_definition(node): defs.append(symbol(node))
        if is_reference(node): refs.append(symbol(node))
    return defs, refs
```

这段是骨架。真实实现要处理作用域、导入和多语言差异，但结构不出其右。

### 一个最小的渲染

```python
def render(nodes, budget):
    lines = []
    for node in ranked(nodes):
        line = f"{'  ' * node.depth}{node.signature}"
        if count_tokens(lines + [line]) > budget: break
        lines.append(line)
    return "\n".join(lines)
```

渲染只做一件事：在预算内按重要性输出结构。它不解释，只呈现。

### 一个最小的排序

```python
def rank(graph, focus_files):
    scores = pagerank(graph, personalization=focus_files)
    return sorted(graph.nodes, key=lambda n: scores[n], reverse=True)
```

排序把图变成一个有顺序的列表。顺序对了，后面的截断才有意义。

### 一个最小的评测集

选二十个真实任务，记录"正确修改涉及哪些文件"，再看地图是否把这些文件排在了前面。

这是一种更贴近使用的评测方式。它衡量的是地图能不能帮模型选对范围。

### 排序的前 k 命中率

一个常用指标是前 k 命中率：正确文件是否出现在地图的前 k 个里。

k 越大越容易命中，但意义越小。k 应该和实际预算对应。

## 十二、怎样判断地图有没有用

Repo Map 的评测不能只看文本是否整齐。至少要记录下面几项：

| 指标 | 要回答的问题 |
| --- | --- |
| 目标文件召回率 | 最终需要修改的文件是否出现在地图或后续选择中 |
| 关键符号覆盖率 | 完成任务所需的接口、类型和方法是否被保留 |
| 无关符号比例 | Token 有多少花在与任务无关的地图内容上 |
| 下一步选择准确率 | 模型根据地图选择继续读取的文件是否正确 |
| 复用率 | 模型是否发现并复用仓库已有抽象 |
| 任务成功率 | 加入地图后，测试通过和人工验收是否改善 |
| 更新延迟 | 代码变化后多久能反映到地图中 |

评测集最好来自真实提交。对每个历史任务保留用户需求、最终修改文件、关键符号和测试结果，然后比较三组输入：只有目录树、加入 Repo Map、直接提供大批完整文件。

这里还要单独统计成本。Repo Map 节省的是每轮重复输入和盲目探索，生成地图本身也需要解析与排序。仓库小、任务明确、相关文件已经由用户选好时，它带来的收益可能很小。

### 用任务成功率评测

地图有没有用，最终看任务成功率。同样任务，有地图和没地图，成功率差多少。

成功率最直接，但噪声大，需要足够样本。单次对比说明不了问题。

### 用 token 效率评测

另一个指标是 token 效率：同样的结构信息，用了多少 token。

地图的价值就是用更少 token 表示结构。效率高但信息不足，或者信息足但太贵，都不算好。

### 地图和上下文预算的关系

预算多时可以多放地图，预算少时地图要更精简。

地图大小应该跟着预算变，而不是固定。固定大小的地图，在预算紧张时会挤掉真正需要的正文。

### 一个关于精度的实用建议

对大多数任务，文件级地图足够。只有需要精确定位符号时，才用符号级。

从文件级开始，按需升级到符号级。一上来就做符号级，成本高收益未必明显。

## 十三、什么时候值得使用

Repo Map 适合下面这些情况：

- 仓库大于模型能够舒适阅读的范围；
- 任务经常跨文件，但一次只需要修改少量文件；
- 仓库已有稳定的模块和公共抽象；
- Coding Agent 需要主动选择下一步读取内容；
- 团队在意输入 Token、响应时间和上下文噪声。

它不太适合单文件脚本、临时 Demo，以及已经明确指定全部相关文件的简单修改。动态语言和大量运行时注册也会降低静态地图的覆盖率，此时应当把 Repo Map 当成入口，并补充搜索、运行时数据和测试。

### 小仓库和单文件任务

小仓库用不上地图，直接读文件更快。单文件任务也不需要地图。

地图的价值随仓库规模上升。在几十个文件的仓库里，地图的收益可能还不如开发者自己的记忆。

### 大仓库和跨模块任务

大仓库、跨模块任务最需要地图。这时的难点是"从哪开始"，地图正好解决。

仓库越大、越陌生，地图的收益越高。

### 一个常见的误解

有人以为地图是"自动生成的架构文档"。架构文档解释设计意图，地图只描述结构。

把两者混为一谈，会对地图提出它做不到的要求。它不解释为什么，只描述是什么和在哪。

### 与 FastCode 的分工再强调

FastCode 是任务驱动的侦察，按需计算；Repo Map 是常驻的结构视图，持续维护。

两者共享抽取，但用途不同。一个回答"这个任务去哪找"，一个回答"仓库整体长什么样"。

### 一个关于地图的争论

有人认为地图是过渡方案，等上下文足够长就不需要了。但长上下文有成本和注意力代价，地图仍然有价值。

地图解决的不是"能不能放得下"，而是"先看什么"。这个问题不随窗口变大而消失。

### 地图的未来

地图可能和检索、Wiki 融合，成为统一的"仓库理解层"。

目前它们还是分开的工具，各自解决一部分问题。

### 一个关于地图精度的建议

地图不需要绝对精确，够用就好。追求绝对精确会拖慢更新。

精度和时效是一对取舍，地图偏向时效更实用。

### 地图和团队知识

地图是把个人对仓库的理解，变成团队共享的结构。

一个人脑子里的结构，经过地图变成所有人都能看到的东西。

### 地图和任务入口

每个任务都需要一个入口。地图让入口从"随便打开一个文件"，变成"从结构上相关的地方开始"。

入口选得好，后面的每一步都更省。入口选得差，后面会一直在错的地方打转。

### 一个可以立刻验证的检查

选一个你不熟悉的仓库，用地图和不用地图各做一次同样的探索，比较找到目标文件的时间。

这个对比不需要复杂评测，几个人做几次就能感觉到差别。

## 十四、我对 Repo Map 的理解

Repo Map 是一种面向模型的代码压缩。它没有压缩每一行源码，而是保留仓库中最能帮助模型继续行动的坐标：文件、符号、签名、定义位置和引用关系。

这也解释了它为什么适合放进代码知识库系列。RAG 解决按问题召回，FastCode 解决结构化侦察，LLM Wiki 解决长期解释，Skills 解决执行方法。Repo Map 在每轮对话中提供一份轻量全景，让 Agent 不必在完全失去方向和一次读取全仓之间二选一。

树形输出只是一种表现形式。Repo Map 更值得研究的是它对信息预算的处理：哪些信息常驻、哪些按需检索、哪些只有在验证时才读取。

### 与 onboarding 的关系

新人 onboarding 时，地图可以作为"仓库导览"。地图给结构，Wiki 给解释。

把地图放在 onboarding 文档里，能让新人几秒钟看懂仓库的主要部分。

### 结语

Repo Map 不是让模型更聪明，而是让它在动手前先看清地形。它用很小的 token 代价，换来更好的起点选择。

### 地图的三个动作

抽取、排序、渲染。三个动作对应三个可独立优化的环节。

哪个环节差，都会影响最终质量。分环节优化，比整体调参更有效。

### 地图解决的是"看不见"的问题

仓库大到一个程度，没人能把它装进脑子。地图把结构显式化，让模型和人都不必全靠记忆。

### 地图是理解的第一公里

理解一个仓库，最难的是第一步。地图把第一步变简单。

### 地图让"从哪开始"不再是难题

理解一个仓库，最难的是第一步。地图用很小的成本，解决了这个障碍。

### 地图是理解的放大镜

Repo Map 是理解仓库的放大镜，也是缩小搜索空间的透镜。它让模型和人都从更清楚的起点出发。

### 一个关于地图的长期判断

地图不会消失，因为"先看什么"的问题不会消失。它可能会换形式，但需求一直在。

理解一个复杂系统，第一步永远是找到入口。地图解决的就是这一步。

### 谁来更新地图

地图要有人负责更新抽取规则和参数。没人负责，地图会逐渐偏离仓库。

抽取规则和忽略列表需要跟着仓库演进。把它们当成代码来维护，而不是一次性配置。

### 地图是结构的载体

Repo Map 把仓库的结构变成模型和人能直接使用的东西。它不深，但它是很多深度工作的起点。

有了清楚的起点，后面的检索、阅读和修改都更容易走对方向。

### 地图和最小可用原则

从最小可用的地图开始：文件级、单向引用、简单排序。跑通之后再逐步增加复杂度。

最小可用能快速验证价值，也避免一开始就陷入优化细节。

### 一个关于"够用"的判断

地图不需要完美，够用就好。判断标准很简单：用它能不能比不用更快找到起点。

如果地图让定位更快，它就值得保留；如果只是增加了阅读负担，就该缩小范围或调整参数，而不是继续加内容。地图的目标是减少无效阅读，不是展示完整结构。

### 一句话总结

Repo Map 解决的问题很小，也很基础：在动手之前，先知道仓库长什么样。先把这一步做好，后面很多工作都会更顺。它不是终点，而是整条代码理解链条真正的起点。
