2026 年 9 月，Meta 发布了 Muse。它把自己定义为 Personal Agent，也就是个人 Agent：用户交代一个目标，它可以继续读取邮件、检查日历、打开网页、填写表单、购买商品，并在任务发生变化或需要批准时回来找人。

这和聊天机器人有一条清楚的分界。聊天机器人给建议，Personal Agent 代表用户进入其他系统并采取行动。模型决定它会怎样计划，产品能力的上限则取决于它能进入多少服务、拿到什么权限，以及这些服务是否允许一个外部 Agent 代替人操作。

这也是 Muse 值得用来观察中美互联网的原因。在美国的互联网结构里，邮箱、日历、支付、电商、设计、财务和协作通常由不同产品提供，它们之间已经形成 OAuth、API、连接器、网页和信用卡网络等接缝。Muse 可以站在这些产品上面，成为一个新的统一入口。

中国消费互联网的形态不同。微信、支付宝、美团、抖音等大型 App 都在向内部扩展，身份、支付、内容、交易与小程序聚集在各自平台中。每个平台内部能力很完整，平台之间却存在明显边界。一个 Personal Agent 若想横跨它们完成任务，除了需要 API，还要面对平台是否愿意把用户关系和行动权交给外部入口。

本文要回答的问题是：Muse 这样的 Personal Agent 需要哪些生态条件，为什么超级 App 结构会让中国的同类产品走向另一种形态？

文章主要依据 Meta 的产品公告、Google 的授权文档、腾讯公开材料与平台研究。Muse 上线时间很短，当前能力与安全机制大多来自 Meta 自述，还缺少长期用户验证。下面会把公开事实和我的判断分开。

## Muse 与聊天机器人的分界

[Meta 的发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)列出了几类任务：发邮件、预订旅行、购买商品、降低账单、出售汽车，以及随着用户生活变化调整长期计划。Muse 可以在用户关闭应用后继续运行，遇到变化或敏感操作再请求批准。入口既可以是独立 App，也可以是 WhatsApp。

这些例子的共同动作是“代表用户”。系统需要同时具备五种能力：

1. 理解目标，并把它拆成会跨越多个服务的步骤；
2. 记住用户长期偏好、关系与已经发生的事情；
3. 持有邮箱、日历、购物和支付等服务的授权；
4. 在 API 或网页中执行动作，并处理长时间任务；
5. 知道哪些动作可以自动完成，哪些必须由用户确认。

少了第三和第四项，它仍然是一个能给出好建议的助手。拿到这两项以后，它才成为 Agent，同时也开始承担真实风险。一次错误回答可以忽略，一次错误付款、误发邮件或取消预订会立刻造成损失。

Meta 为此给 Muse 配置了专属的 Muse Secure VM。官方说，每位用户的 Agent 在独立云端虚拟机中运行，虚拟机包含浏览器、数据和凭证存储；另一个与 Muse 隔离的 Sentinel 负责检查对外动作。用户可以决定连接哪些 App、授予只读还是写入权限，发送邮件和购买等敏感操作需要确认，并且可以查看行动记录。

![Muse Personal Agent 的执行链](/images/posts/muse-personal-agent-runtime.svg)

这张图展示了 Personal Agent 的产品结构。聊天窗口是入口，后面还有长期状态、身份凭证、浏览器、连接器、权限策略、确认机制和审计记录。Muse Spark 模型负责推理，这套执行环境负责让任务持续、可控地运行。

## Personal Agent 为什么天然需要跨应用

人的目标不会按照软件边界切开。“帮我安排下周出差”可能需要查看邮件里的会议地点，对照日历，搜索航班和酒店，读取公司的差旅规则，完成付款，再把行程同步给同事。任何一个单独 App 都只拥有其中一部分状态。

传统软件让人充当集成层。我们从邮件复制地址，切到地图看距离，再去旅行网站比较价格，最后回日历创建事件。Personal Agent 想替代的正是这段手工拼接，所以它必须横跨多个系统。

这会产生三个基本条件。

### 服务需要暴露可用的行动接口

接口可以是正式 API，也可以是 Agent 操作的网页。正式 API 通常更稳定，能声明明确的读写范围，也更容易做审计；浏览器覆盖面更广，但页面结构变化、验证码、反自动化策略和模糊的操作状态都会增加失败概率。

Muse 同时使用两种方式。Meta 称它拥有自己的浏览器，可以打开网页、填写表单和协商；Muse for Small Business 又提供一批正式连接器。浏览器给它广度，连接器提供稳定性和结构化权限。

### 用户必须能够把权限交给第三方

[Google 的 Gmail API 文档](https://developers.google.com/workspace/gmail/api/auth/web-server)展示了这种授权结构：应用通过 OAuth 取得访问令牌，可以在用户离线时代表用户访问数据；[Calendar API](https://developers.google.com/workspace/calendar/api/auth)又把只看空闲时间、只读日历和完整编辑拆成不同 scope。用户可以授权一组有限能力，无需把账号密码直接交给 Agent。

这套机制并不完美。权限说明可能难懂，scope 仍可能过大，刷新令牌被盗也会造成风险。它至少提供了一种通用语言：第三方是谁，可以做什么，权限何时到期，用户怎样撤销。

### 不同服务要允许同一个入口组合它们

一项服务提供 API，不代表它乐于被 Agent 重新编排。平台可能只开放读取，不开放交易；允许自家客户端调用，不允许通用 Agent 调用；提供接口，却限制第三方展示、排序或替用户选择。

Personal Agent 会改变流量入口。过去用户先打开电商 App，再看平台推荐；现在用户先告诉 Agent 需求，由 Agent 决定访问哪个商家。谁拥有第一句话，谁就可能影响后续选择、广告和交易。跨应用授权同时在重新分配分发权。

## Muse 背后是一片已经模块化的服务市场

Meta 在 9 月底推出 [Muse for Small Business](https://about.fb.com/news/2026/09/introducing-muse-small-business/)，公布的连接对象包括 Asana、Box、Canva、Dropbox、Figma、QuickBooks、Klaviyo、Notion、Shopify、Slack、Stripe 和 Zoom，也包括 Facebook 与 Instagram 商业账号。随后发布的信息又提到 Walmart、Best Buy、PayPal、Expedia 和 Instacart 等合作方。

这份名单比任何一句“美国 SaaS 发达”都更具体。一个小企业可能分别使用 Shopify 做店铺、Stripe 收款、QuickBooks 记账、Klaviyo 做营销、Canva 做素材、Slack 沟通。每家公司只占据一段业务流程，通过账户体系和接口连接。Muse 的机会是把分散状态拉到一个任务里。

这里的“小公司做 SaaS”不应理解为所有供应商都很小。名单中有大量成熟平台。决定生态结构的是模块可以独立采购、独立授权，也可以被另一个产品组合。企业不必先进入某个超级 App，才能同时使用这些服务。

### 独立 SaaS 给 Agent 留出了上层位置

模块化软件长期存在一个使用成本：用户必须理解多个工具，在它们之间同步状态。过去这催生了 Zapier 一类自动化产品，也推动各家提供 API、Webhook 与应用市场。Personal Agent 把固定规则变成了基于目标的动态编排。

举个例子，小店老板说“分析今年销售和营销数据，给出明年的增长计划”。Agent 可以读取 Shopify 订单、Stripe 回款、QuickBooks 成本和 Meta 广告数据，再把结果写入 Notion。单个系统不需要知道整个企业，Agent 负责聚合。

服务边界增加了用户的手工成本，也为 Personal Agent 这样的编排层留下了位置。Agent 能否站稳这一层，取决于接口质量与用户授权。

### 开放 Web 是连接器不足时的兜底

不是每个商家都会为 Muse 开发连接器。只要服务仍提供可访问网页，Agent 就可能像人一样搜索、比较和填写表单。支付网络再提供一次性卡号和购买保护，它就能在没有深度集成的商家完成交易。

Meta 宣布 Muse 通过 Stripe Link 结账，一次性卡号让商家按普通卡交易处理，而不用先理解 Muse 协议。这种兼容方式很关键。一个新入口若要求所有旧服务同时改造，永远无法起步；能沿用网页、邮件和支付网络，覆盖范围会扩大得更快。

网页操作也有明显上限。Agent 可能误读库存、优惠条件或取消规则，页面改版会让自动化失效，商家也可以通过验证码和条款阻止机器操作。Muse 当前的演示说明它希望覆盖这条路径，还不能证明它已经稳定解决了所有长尾网站。

## 超级 App 的生态生长在内部

中国互联网常被描述为“App 彼此隔离”，这句话只说了一半。大型 App 内部往往非常开放。微信通过小程序、公众号、视频号、微信支付和企业微信连接大量第三方；支付宝、美团、抖音也拥有商家与服务生态。

[腾讯对微信小程序的说明](https://www.tencent.com/zh-cn/products/weixin-mini-programs/)强调，用户可以通过搜索或二维码直接使用商家和机构提供的服务。[腾讯 2025 年中期报告](https://static.www.tencent.com/uploads/2025/09/16/5a0b274dacf222d262734936c3508821.pdf)则把聊天、搜索、小程序、小店、视频号和支付描述为相互连接的生态，并披露 2024 年小程序促成的 GMV 超过 8 万亿元。

这是一种 app-in-app 结构。第三方开发者很多，服务也很丰富，但身份、流量、支付和运行时由宿主平台提供。[关于 Mini-App Ecosystems 的研究](https://doi.org/10.1007/s12599-022-00773-9)指出，宿主 App 在操作系统应用商店之上形成了一层新的应用生态。[另一项平台研究](https://doi.org/10.1177/01634437221128937)把微信的演化概括为平台化和基础设施化：第三方能力进入微信边界，微信成为移动流量、数据和收入的重要入口。

对用户和商家来说，这套结构解决了真实问题。停车缴费、餐厅点单、医院挂号等低频服务不值得各装一个 App。小程序复用身份和支付，扫码即可使用。平台内部的 Agent 若能调度这些服务，完成生活任务的效率可能非常高。

问题出在“跨平台”。A 平台对自己的小程序开放接口，不等于它愿意让 B 平台的 Agent 读取用户状态并发起交易。每个平台都有完整账号、推荐、支付与商业化体系，外部 Agent 若拿走入口，可能同时绕开广告、搜索、会员和支付闭环。

![Personal Agent 在两种互联网生态中的不同路径](/images/posts/personal-agent-two-ecosystems.svg)

左边的接口数量可能更多，也更碎；右边每个岛内部的能力更强。Personal Agent 想做的是一条横线：从用户目标出发，同时跨过邮箱、日历、电商、出行和支付。超级 App 的结构则更像几个纵向完整的岛。岛内调度容易，跨岛调度困难。

## 中国为什么更可能先出现“平台 Agent”

中国具备做出 Muse 的技术条件。模型、浏览器自动化、安全容器、记忆和调度都不存在不可逾越的障碍。产品上线后会被生态推向哪里，才决定它最终的形态。

### 第一条路径是超级 App 内部的 Agent

微信里的 Agent 可以理解聊天、调用小程序、完成支付；支付宝里的 Agent 可以围绕金融和生活服务工作；美团里的 Agent 可以处理本地消费；抖音里的 Agent 可以连接内容与电商。这些产品一开始就拥有高频入口和大量可调用能力。

它们的优势是授权关系清楚。用户已经登录，平台认识商家，也控制交易与退款流程。Agent 不必先说服几十个外部服务提供 OAuth。缺点也同样清楚：它对自家生态最有用，跨到竞争平台时能力会迅速下降。

国内最先成熟的形态可能是“我的微信 Agent”“我的购物 Agent”或“我的出行 Agent”。一个对所有 App 保持中立的个人 Agent，需要等待更多跨平台接口。平台 Agent 对用户仍有价值，只是个人状态会继续分散在多个平台中。

### 第二条路径是手机厂商的系统级 Agent

操作系统位于所有 App 之下，看起来天然适合做统一入口。它可以读取通知、理解屏幕、调起应用，并使用无障碍或系统意图完成操作。相比某个互联网平台，手机厂商与各 App 的直接业务竞争可能更少。

但系统级权限不等于业务接口。看见一个按钮和知道订单是否可退，是两件不同的事；模拟点击也无法替代稳定的交易协议。App 可以修改界面、限制后台行为或要求额外验证。系统 Agent 若想可靠执行，最终仍要与服务方建立正式合作。

### 第三条路径是企业内部 Agent

企业场景中的边界更容易被管理。公司可以统一采购办公软件，管理员可以批准连接器，内部系统也能提供专用 API。数据权限、审计和责任人虽然复杂，却有明确组织来协调。

因此，中国市场可能先在客服、销售、财务、研发和运营中出现跨系统 Agent，再逐步走向个人生活。企业 Agent 连接的是公司授权的数据，Personal Agent 连接的是一个人的全部生活。后者的授权面更广，错误后果也更难由单一组织承担。

## Muse 也来自大平台

Muse 是 Meta 的产品，Meta 自己就是全球最大的互联网平台之一。它把 Muse 放进 WhatsApp，并准备连接 AI 眼镜。Muse 依靠 Meta 的社交入口、模型、算力和设备争夺下一代用户界面。

这反而让案例更有价值。美国模块化服务生态给了 Personal Agent 跨产品工作的接口，大平台则拥有构建安全执行环境、谈连接器合作和获取用户的资源。Muse 是这两种力量的组合：底层依赖分散的 SaaS 与开放 Web，上层由 Meta 争夺统一入口。

一旦 Agent 成为入口，它也可能产生新的封闭。连接器排序会不会偏向合作商家？推荐依据能否解释？用户长期记忆能否迁移到另一个 Agent？商家需要向 Agent 平台支付什么费用？这些问题现在还没有稳定答案。

因此，不能把 Muse 简化成“美国生态开放，所以个人 Agent 自然出现”。更准确的说法是：模块化服务为跨应用 Agent 提供了可连接的底座，而 Meta 正试图把这些连接重新收束到自己的 Agent 和设备入口。

## 授权网络比模型更难复制

模型能力会扩散，同一代模型也可以被不同公司采购或训练。Personal Agent 更难复制的部分有四层。

第一层是连接器。每个服务的身份、数据结构、限流、写操作和错误语义都不同。连接数量决定覆盖面，连接质量决定能否稳定交付。

第二层是信任。用户是否愿意让系统读邮件、保存偏好、代表自己沟通和付款。信任来自品牌，也来自细粒度授权、关键动作确认、审计与赔付机制。

第三层是长期记忆。Agent 需要知道用户在意什么，又不能无限保存一切。记忆的来源、可见性、纠错和删除会直接影响产品体验，也可能把用户锁进单一平台。

第四层是责任网络。航班订错、商品损坏、价格变化或邮件误发后，谁退款、谁举证、谁承担损失。Meta 为 Muse 引入 Stripe Link 的购买保护，说明交易责任不能只靠模型置信度解决。

这四层会形成复利。连接器越多，用户越愿意把任务交给 Agent；任务越多，长期上下文越完整；信任越强，Agent 越能获得高风险权限。后来者即使模型一样，也要重新建立授权与责任关系。

## 用一个具体任务比较两种生态

假设用户提出：“下周五帮我组织一次六人的聚餐，避开大家没空的时间，照顾两位朋友的饮食限制，订好餐厅并提醒所有人。”

在模块化服务结构中，Agent 读取通讯录和历史邮件，向参与者收集时间，查询日历空档，在地图或预订网站筛选餐厅，再用支付方式支付订金。每一步属于不同服务，统一的是用户授权给 Agent 的目标和确认规则。

系统要处理的失败很具体：有人没有回复，日历只开放忙闲信息，餐厅网页没有 API，订金不可退，发送邀请前还要用户确认。Agent 的价值来自协调这些不一致，单个步骤未必比原 App 做得更好。

在超级 App 结构中，如果六个人、餐厅、支付和群聊都位于同一平台，内部 Agent 可能完成得更顺。它知道群成员，能调用餐厅小程序，付款后把结果发回群。可是一旦餐厅只在另一平台经营，或某位参与者的日历位于企业办公 App，跨平台边界就会出现。

这个例子说明，超级 App 并不会让 Agent 必然更弱。单个平台覆盖任务闭环时，它甚至更强。难点在于个人生活分布在多个平台。Personal Agent 要跟随用户跨越场景，平台 Agent 则倾向于让场景留在平台内。

## 对中国 Personal Agent 的几个判断

第一，国内不会缺少 Agent 产品，但“个人”需要重新定义。有些产品把个人理解为私人记忆和长期陪伴，有些把它理解为替用户跨服务办事。前者主要依赖模型与数据，后者依赖授权网络。两者的商业难度完全不同。

第二，浏览器或界面自动化可以帮助冷启动，无法长期替代正式接口。涉及支付、隐私和不可逆操作时，服务方最终需要提供可撤销授权、幂等语义、状态查询和争议处理。否则 Agent 只是一个速度更快但责任模糊的代点工具。

第三，平台互联互通会直接影响 Agent 能力。若用户可以携带身份和数据，服务可以暴露标准行动接口，第三方 Agent 就有机会形成；若接口只对平台内部开放，Agent 会沿着超级 App 边界分裂。

第四，支付入口尤其重要。Personal Agent 能比较和推荐，也能决定交易流向。平台不会轻易放弃这部分控制。未来很多“AI 开放平台”争议，表面讨论模型调用，实际争夺的可能是订单、佣金与客户关系。

第五，端侧和系统级 Agent 可能成为平衡力量。它更接近用户，也有机会在数据不离开设备的情况下理解屏幕和通知。但若没有服务方配合，它仍然只能操作界面，可靠性和责任边界有限。

## 技术人员怎样看懂这一轮产品竞争

看到一个 Personal Agent，可以先画五张表，再去比较模型排行榜。

先列入口：用户从独立 App、聊天工具、浏览器还是设备找到它。入口决定获客成本，也决定 Agent 能看到多少上下文。

再列连接：它能读哪些系统，能写哪些系统，依靠官方 API、合作连接器还是网页自动化。连接数量与可执行深度要分开看。

第三列权限：授权是否细分读写，关键动作是否确认，凭证怎样保存，用户能否撤销并查看记录。Personal Agent 的安全设计本身就是产品能力。

第四列责任：任务失败后谁恢复，交易争议谁处理，重复执行怎样避免，长任务中断后能否继续。只展示顺利完成的视频，无法证明系统能承担真实生活。

最后列商业关系：Agent 怎样收费，是否从交易抽佣，连接器是否付费获得推荐位置，平台会不会优先调用自己的服务。这张表往往比技术架构更早暴露产品会走向开放还是封闭。

## 结语：超级 App 之后，谁来代表用户

Muse 正在争夺一种新的互联网位置。过去，用户在多个 App 之间移动，平台各自经营自己的入口；Personal Agent 希望站在这些入口之前，接收目标，再代表用户调度服务。

模块化的 SaaS、OAuth、开放 Web 和支付网络让这件事更容易起步，因为服务之间已经存在可以授权和组合的接缝。中国的超级 App 把大量服务组织得更紧密，平台内部执行很强，跨平台行动却会碰到商业与数据边界。

所以中国并非做不出 Muse。更可能出现的分叉是：美国市场先形成连接多个独立服务的通用 Personal Agent，中国市场先形成多个能力很强的平台 Agent。谁能进一步跨越边界，取决于平台是否愿意开放行动接口，也取决于用户能否真正掌握自己的授权和数据。

下一代入口的竞争，表面上是 Agent 替人做多少事，底层争夺的是谁有资格代表用户。
