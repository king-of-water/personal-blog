服务器连着一万个客户端，当前只有 B、D 发来了数据。程序怎样等到它们，又怎样知道该读谁？

理解 select、poll、epoll，先看三件事：登记要监听谁，记录谁有事件，取回就绪结果。红黑树只参与其中一部分，不能把 epoll 理解成“每次从树里找出有数据的连接”。

## 先看主线：登记、通知、领取

以 epoll 为例，先把全过程走完：

![应用登记连接后，状态变化触发回调，候选项进入就绪队列，epoll_wait 复查并返回事件](/images/posts/io-epoll-mainline.svg)

1. 应用登记这一万个连接，以及关注的可读、可写事件。
2. B、D 的状态变化触发通知，对应监听项进入就绪队列。
3. 应用领取一批事件，再对 B、D 实际执行读取。

这里有两份数据：**监听登记表记录“要关注谁”，就绪队列记录“哪些项现在值得处理”**。Linux 用红黑树管理前者，用链表组织后者。以下按这条路径展开，实现细节限定于 Linux v6.12 的网络 Socket。

## 一、先区分等待事件和读取数据

连接在进程里通过文件描述符访问，简称 FD。它是一个整数编号，程序把它交给 `recv`，才能从对应 Socket 读取数据。

如果线程在没有数据的 A 上阻塞读取，就可能一直等着 A，顾不上已经有数据的 B。为所有连接逐个尝试非阻塞读取，又会反复检查大量空闲连接。

I/O 多路复用把等待集中起来：一次关注多个连接，某些连接可以操作时再通知程序。select、poll、epoll 都能在无事件时让线程睡眠，不需要持续占用 CPU 检查。

“可读”只是可以尝试读取，可能有数据，也可能读到连接结束或错误。它不保证一条完整业务请求已经到齐；事件返回以后，程序仍需检查实际读取结果。[recv 的返回语义](https://man7.org/linux/man-pages/man2/recv.2.html)

## 二、select 和 poll：每次交名单，返回后找标记

先把一万个连接缩成 A、B、C、D，只有 B、D 可读。两种接口都会标明就绪项，但不另外生成一份紧凑的连接数组。

| 接口 | 传入什么 | 结果放在哪里 |
| --- | --- | --- |
| select | 按 FD 编号设置的位集合 | 修改返回位集合，保留就绪位 |
| poll | 每项包含 FD 和关注事件的数组 | 在原数组各项的 `revents` 中标记事件 |

例如 poll 的结果可以读成：

```text
监听数组： A      B      C      D
返回标记： 0     可读    0     可读
```

程序通常仍要检查这些位置，才能找到 B、D。select 则检查返回集合中哪些位被置上，不能把它描述成“把未就绪连接也当成就绪返回”。返回数量与返回结果的存放方式是两回事。[select](https://man7.org/linux/man-pages/man2/select.2.html)、[poll](https://man7.org/linux/man-pages/man2/poll.2.html)

内核同样有工作要做：每次调用接收监听集合，检查各对象状态；没有就绪项时建立等待关系并睡眠，收到唤醒后继续检查。这里的集合检查，与应用返回后寻找非零标记，是两个不同位置的成本。

![poll 每次提交名单并检查集合，epoll 保留登记并围绕就绪候选领取事件](/images/posts/io-poll-epoll-work.svg)

两边都有睡眠和唤醒。区别在于，select、poll 本次调用建立的等待关系结束后会清理；epoll 的监听登记可以跨多次等待保留。[Linux v6.12：集合检查与等待](https://github.com/torvalds/linux/blob/v6.12/fs/select.c)

还要纠正一个常见说法：poll 的用户接口是数组，不是链表；不能用“select 是数组、poll 是链表”来概括机制。select 的常见 `fd_set` 另有 FD 编号必须小于 1024 的限制，poll 不使用这套固定大小的位集合。

## 三、epoll：先保留监听关系，再按通知组织就绪项

应用先创建 epoll 对象，用 `epoll_ctl` 添加、修改、删除监听项。之后调用 `epoll_wait`，交入的是结果数组及其容量，不必每轮重新提交完整连接名单。

登记 B 时，内核已经把 B 对应的监听记录关联到它的等待通知上。B 收到数据，Socket 状态变化触发回调；**回调能取得对应记录，通常不需要先去红黑树里搜索 B**，再把符合条件且尚未入队的记录加入就绪结构。D 同理。

于是，收到事件的路径是“B 状态变化 → B 的通知回调 → 就绪队列”，而不是“扫描一万个连接，检查谁有变化”。登记时也会检查初始状态，避免漏掉注册前已经到达的数据。[Linux v6.12：`ep_poll_callback`](https://github.com/torvalds/linux/blob/v6.12/fs/eventpoll.c)

`epoll_wait` 从就绪候选中复查状态，再把事件紧凑地写入输出数组。候选不一定最终有效，例如其他线程已经读走数据，所以不能把队列当作永不变化的准确快照。

这一次若返回 B、D，应用只需处理这批有效结果。输出容量只限制本次最多返回多少个事件，不限制总监听数量；一万个连接都就绪时，需要分批领取。结果包含事件和应用登记的关联标识，请求正文仍要通过读取 Socket 取得。[epoll 的登记与就绪集合](https://man7.org/linux/man-pages/man7/epoll.7.html)

## 四、红黑树负责什么，数组或链表能不能替代

红黑树管理的是全部监听登记项。应用要求“修改 B 的关注事件”或“取消 B 的监听”时，需要定位对应记录；添加前也要检查是否已登记。树的查找成本为 `O(log N)`，其中 N 是登记项数量。

它没有按“谁收到数据”给连接排序，也不是 `epoll_wait` 每次找就绪连接的必经入口。把三项工作分开就不会混淆：

| 动作 | 主要使用什么 | 做什么 |
| --- | --- | --- |
| 管理监听项 | 红黑树 | 定位登记记录，添加、修改或删除 |
| 处理就绪通知 | 已建立的回调关联、就绪链表 | 取得对应记录，按条件入队 |
| 等待并返回事件 | 就绪候选、输出数组 | 复查并交回一批有效事件 |

数组或链表当然也能保存登记记录，差别是查找和维护成本。普通无序数组、链表定位指定项通常需要 `O(N)`；排序数组可以二分查找，但插入、删除可能移动大量元素；红黑树让查找和结构增删保持对数级。

这不代表整个 `epoll_ctl` 都只做一次树操作，它还可能维护等待关系和同步状态。哈希表或带额外索引的数组也可以设计成替代方案，需重新考虑内存、冲突、扩容和生命周期。红黑树是登记管理的一种实现选择，事件通知与就绪队列才决定等待时怎样避开大量空闲项。

## 五、为什么给 poll 换一棵树，还不能得到 epoll

假设把 poll 的监听集合改成红黑树，却仍然每轮逐项问“你就绪了吗”。一万个对象就要做一万份状态检查，树的对数查找帮不上这件事：它擅长找指定对象，不能自动回答哪些对象刚有事件。

也可以保留 poll 的逐项检查，只把 B、D 压缩到输出数组。这样减少了应用寻找结果的工作，内核仍然检查了整份名单。

要进一步减少这部分检查，就得长期保存监听关系，让状态变化关联到具体记录，持续维护就绪候选。随之需要创建、更新和释放这些状态的接口。这已超出“换一种容器”或“换一下返回格式”的范围。

已有 poll 程序按固定数组位置读取 `revents`，直接压缩原数组还会改变接口约定。因此应把“能不能设计另一个接口”与“能否直接改变旧接口行为”分开；这里解释的是接口约束，并非断言历史选型只有一个原因。

## 六、拿到事件后，还要正确读写

假设 B 已收到 100 字节，应用只读了 40 字节。剩下的 60 字节，是否还会被报告，取决于通知方式。

- **LT，水平触发**：条件仍满足，后续等待仍有机会报告 B。epoll 默认使用这种模式。
- **ET，边缘触发**：依赖状态变化通知，不能指望剩余字节一直没读，就必然再收到通知。常见做法是使用非阻塞 Socket，持续读取到 `EAGAIN`，表示当前暂时没有更多数据。

![可读事件之后，按实际读取结果决定继续读取、等待或收尾](/images/posts/io-nonblocking-read-loop.svg)

读取返回正数就保存字节并按协议解析；`EINTR` 可结合退出条件重试；`EAGAIN` 回到调度；返回 0 表示对端发送方向结束，其他错误按连接策略处理。LT 下也应检查实际返回值，因为通知之后状态仍可能变化。

ET 若因处理预算提前停止，应保留在应用自己的待处理队列中，之后主动续读；否则可能留下数据却一直等不到预期的新通知。ET 也不等于一个网络包通知一次，多次通知可能合并。

发送同样可能只写出一部分，剩余内容要保存偏移继续发送。没有待发送内容时，不应长期关注可写，否则连接持续可写会让线程反复醒来。事件接口不负责协议拼包、业务执行和连接生命周期。

## 七、比较成本时，别只看 O(1) 和 O(N)

一万个连接中只有两个活跃，而且监听集合稳定，epoll 可以复用登记并围绕少量就绪候选工作，这是它适合的场景。

但返回两个事件仍要处理两个事件；几千个连接同时活跃时，大量读写也不会消失。登记变更、事件回调、同步和状态复查同样有成本，因此不能把整个 epoll 称为无条件 `O(1)`。

少量连接时，poll 可能已经足够简单实用。业务代码长时间占住事件循环时，换成 epoll 也不会自动解除阻塞。选择接口要看连接总数、活跃比例和登记变更频率，而不是只比较“树比数组快”。

回到开头的 B、D：监听登记告诉内核关注谁，通知把对应记录送入就绪队列，等待接口交回事件，应用再执行读写。红黑树承担其中的登记查找，不承担逐个发现就绪状态的工作。
