很多 RAG 教程停在同一个流程：文档切块，生成向量，查询时取回最相似的几段，把它们塞进提示。这个流程足以做演示，也容易让人产生一种错觉，以为换一个更强的生成模型，或者把返回条数调大一点，回答质量就会稳定上升。

上线之后更常见的是另一种情况：系统找回了一些相关片段，却不足以回答问题。用户问某项设计为什么调整，系统找回了新方案却漏掉旧方案的约束；用户要比较三个产品，检索结果集中在其中一个。这些失败不在同一层，修法也各不相同。

这篇文章想把 RAG 当成一条流水线来看，而不是一个"接上向量库"的动作。GraphRAG、LightRAG、Self-RAG、Corrective RAG 和 Agentic RAG 之所以同时存在，是因为它们在补不同环节的洞，而不是一代取代一代。

## 一、RAG 在解决什么问题

RAG 面对的是一个很具体的问题：模型的知识是冻结的、有限的，而业务知识更新快、量又大。把全部知识塞进上下文既贵又慢，于是系统改成按需检索，只把相关的一部分交给模型。

这个定位决定了 RAG 的本质：它不是让模型记住更多，而是在需要的时候，把对的材料递到模型面前。所以评价一套 RAG，核心不是生成模型多强，而是"递料"这一步准不准、全不全、能不能核对。递料出了问题，再强的模型也只能用错误或不足的材料作答。

它和微调解决的是两类不同的问题。微调改变模型的内部倾向，适合让模型形成某种风格，或稳定掌握一类能力；RAG 提供外部知识，适合知识频繁变化、需要给出处、量又超出上下文容量的场景。知识每天更新时，重建索引比重新训练便宜得多；需要引用来源时，检索到的原文天然比模型记忆可信。两者不是替代关系，很多系统会同时使用。

把 RAG 当作流水线，还有一个直接的好处：排障有了固定路径。从"文档是否存在"开始，一路查到"生成是否忠实"，每次只问一个环节。没有这条路径，排查会变成四处试探，效率很低。流水线也意味着木桶效应，最弱的一环决定上限：切块做得再好，重排很差，正确片段还是会被挤出上下文；重排再好，切块把关键句子切断了，也救不回来。

### 和搜索的区别

搜索返回的是相关的页面，RAG 要返回的是一个能回答问题的结果。这意味着 RAG 必须在检索之外多做一层判断：证据够不够、有没有互相矛盾、能不能支撑结论。只做检索不做判断，得到的是"一堆看起来相关的东西"，而不是答案。

这层判断也解释了为什么 RAG 比搜索更难做好。搜索的相关性可以是模糊的，用户自己会再挑；RAG 的相关性必须落到"能不能回答问题"上，判断标准更严，出错的代价也更大。

## 二、一条流水线，三种失败

一条完整的 RAG 流水线至少包含这些环节：文档解析、切块、向量化、索引、召回、融合、重排、证据组装、生成、校验。每一段都可能出问题，而它们最终都表现为一句笼统的"回答不对"，让定位变得困难。

![RAG 的离线索引与在线查询流程](/images/posts/rag-offline-online.svg)

### 失败可以分成三层

把失败分层，是修复 RAG 的第一步。第一层是检索失败：正确证据根本没被找到。第二层是理解失败：证据找到了，但被重排挤下去，或组装时被切碎，模型看到的是断章取义。第三层是生成失败：证据齐全，模型却表达错、过度推断，或者编造了证据里没有的内容。

三层对应不同的修复手段。检索层改切块和召回，理解层改重排和组装，生成层改提示和校验。分不清层次，就会把所有问题都归到"模型不行"或"提示不好"，于是反复调提示，却始终碰不到真正的瓶颈。

一个很常见的误判，是把检索失败当成生成失败。模型在没有证据时只能编，或基于错误证据推理，看起来像"模型在胡说"，实际是证据没给对。正确的排查顺序是：先确认正确证据是否进了上下文，再怀疑生成。

### 失败归因流程

具体的排查可以按一个固定顺序进行：核对正确答案所在的文档是否存在，不存在就是知识缺失；存在但没被召回，是检索问题；被召回但没进最终证据，是重排问题；进了证据但答案错，是生成问题。每一步只回答一个问题，命中后就知道该修哪一层。

```text
召回分数低        → 切块 / 召回 / 过滤条件
召回高但答错      → 重排 / 证据组装
引用对不上        → 引用映射
该说不知道却回答  → 召回阈值 / 证据覆盖检查
成本失控          → 路由 / 预算
引用过期内容      → 增量更新 / 版本控制
```

这条流程还有一个副产品：它能指导投入分配。如果失败里检索问题占多数，重点就该放在切块和召回；如果生成问题占多数，重点才在提示和约束。把有限精力按失败分布来分，比平均用力有效得多。失败分布会随系统演进变化，所以要定期重新统计，而不是一次定死。

## 三、基础环节：把料备好

基础环节之所以值得反复讲，是因为绝大多数线上问题出在这里，而不是出在更复杂的框架上。很多团队急着上图检索和 Agent，结果基础的切块和重排没做扎实，问题反而更隐蔽。

### 解析与切块

RAG 的第一道坎常常是文档解析。PDF 的表格、扫描件、多栏排版、页眉页脚，都会让文本抽取变成一堆错乱字符。解析错了，后面全都错。解析要保留结构：标题层级、表格行列、列表、代码块。把 PDF 直接转成一段纯文本，几乎一定会破坏表格和层级。

表格需要特殊处理，例如转成保留表头和行的结构化文本，或者按行切块并带上表头；图片和图表无法直接检索，需要生成描述或提取其中的文字。不同来源的格式千差万别，为每种格式写一套解析逻辑成本很高，务实做法是先支持占比最高的几种并做准，其余的降级处理。

切块没有通用最优解。固定长度最简单，但会切断语义；递归切块按标题和段落分层，保留更多结构；语义切块按内容边界切，效果好但计算贵；结构化切块直接利用文档本身的结构。技术文档适合结构化和递归切块，聊天记录适合按会话和话题切，表格适合按行加表头切，代码适合按函数和类切。用一种切法处理所有文档，几乎一定会有一类切得很差。

一个具体建议是给每个片段带上足够的元信息，包括来自哪个文档、哪个章节、第几段。这些信息在后面的过滤、引用和去重里都会用到。没有元信息的片段，是一块无根的文本，很难被正确使用。

```python
def chunk(doc, max_tokens=400, overlap=60):
    # 先按标题层级切，保留结构
    chunks = []
    for section in split_by_heading(doc):
        if tokens(section) <= max_tokens:
            chunks.append(with_meta(section, doc.id))
        else:
            # 过长再按段落二次切，并保留重叠
            for piece in sliding_window(section, max_tokens, overlap):
                chunks.append(with_meta(piece, doc.id))
    return chunks
```

切块大小也有取舍，而且最好跟着问题类型走。事实型问题需要短而准的片段，归纳型问题需要更大、更完整的片段。一个折中是同时保留两种粒度：细块用于精确定位，粗块用于提供上下文，检索时用细块定位、用粗块补全背景。

### 混合召回与融合

稠密向量擅长语义相似，稀疏检索（例如 BM25）擅长精确词和罕见词。两者混合通常比单用任一种更好：只依赖稠密，会在需要精确匹配时吃亏，比如错误码和专有名词；只依赖稀疏，又会漏掉换了说法的同义表达。

```python
def retrieve(query, k=20):
    dense = vector_index.search(embed(query), k)
    sparse = bm25.search(tokenize(query), k)
    fused = rrf([dense, sparse], k=k)      # 倒数排名融合
    reranked = rerank(query, fused[:k])[:10]
    return [with_citation(hit) for hit in reranked]
```

融合有两种常见方式。把分数归一化后加权，需要处理不同检索器的分数量纲；用倒数排名融合，只依赖排名，跨检索器组合时更省心，是更稳的默认选择。融合之后仍然需要重排，因为两路召回都会带进噪声；去重也不能省，同一份内容可能被两路同时召回，也可能在索引里存在近似副本，不去重会浪费重排算力，也挤占了其他证据的位置。

中文稀疏检索还要注意分词，分词错误会直接影响命中，尤其是专有名词和长词。维护一份领域词汇表能显著改善中文稀疏检索的效果，是低成本、高回报的优化。混合召回的参数（两路权重、各取多少、融合后保留多少）则要按语料分布调，没有一套参数适合所有场景，最好的办法是拿一批真实查询去测。

### 重排与元数据过滤

重排分两类：交叉编码器精读查询和候选，准确但慢；LLM 重排让模型给候选打分，更灵活但更贵。重排的收益和候选数量有关：候选从一百降到二十，重排能明显提升精度；候选本身只有十个，重排收益有限。重排应该作用在召回之后的候选上，而不是替代召回。召回求全、重排求准，目标互补，谁也不能替谁。

重排的收益也不是无限的。当召回质量本身很差时，重排只能"矮子里拔将军"。所以重排要配合召回一起看：先确认召回里有正确证据，再谈重排能不能把它排上来。召回里没有的，重排变不出来。重排的评估可以用"位置改进"衡量，看正确片段在重排前后排名有没有提升；如果没有提升，说明这个重排器对这个语料没有帮助。

元数据过滤有两种位置。召回前过滤先缩小候选范围，快，但可能因为条件过严漏掉相关内容；召回后过滤先召回再筛选，召回全，但可能浪费算力，还可能因为过滤后候选不足而失败。权限过滤尤其要小心：过滤错了，用户会以为"没有相关资料"，而不是"你没有权限看"。过滤规则要单独测试，尤其要测"用户没有权限时，系统是否如实说明，而不是假装没有资料"。

元数据要提前规划。创建时间、更新时间、来源、密级、所属主题，这些字段在过滤和排序里都会用到，事后补的成本很高，因为要重新处理全部文档。

### 引用映射与"不知道"出口

引用可以定位到文档，也可以定位到片段。文档级引用简单，但用户难以核对；片段级引用精确，但需要保存片段到原文的偏移。片段级引用对可信度更重要，用户看到"答案来自这一段"才能自己验证。实现上要保存片段的原文偏移，并在生成时把引用和证据绑定，而不是事后猜。

引用还可能被伪造。模型可能生成一个看起来合理但不存在的引用，所以引用要在程序侧校验：引用的片段必须真的在检索结果里。要求模型引用证据，不只是为了用户核对，也能减少幻觉，因为模型知道自己的每句话都要被追到证据。引用的呈现方式也影响体验，把引用放在句子末尾、可点击、显示来源标题，比在文末列一堆链接更友好。

"给不知道留出口"要落到具体触发条件：召回分数低于阈值、重排后没有高于阈值的候选、证据之间互相矛盾、证据不足以覆盖问题的所有部分。把这些条件写成运行时可判断的规则，而不是靠模型自觉。模型倾向于给出一个答案，即使证据不足；运行时用规则拦截，比在提示里求它诚实更可靠。

阈值本身也需要校准，定得太高，系统动不动说不知道，用户会觉得它没用；定得太低，系统总在证据不足时硬答，用户会被误导。阈值应该按业务对错误的容忍度来定，而不是拍一个数字。"不知道"的措辞也值得设计，一句"现有资料没有覆盖这一点，我可以帮你查 X"，比一句生硬的"没有找到相关信息"更专业。

## 四、查询理解：在检索之前想清楚

基础 RAG 假设用户的问题已经清楚。真实场景里，用户的问题常常口语化、含糊，或者一次问了多件事。查询理解就是为了在检索之前，把问题整理成更适合检索的形式。

### 查询改写的三种手法

查询改写有三种常见手法：改写、扩展、分解。改写是把口语化问题变成检索友好的表述；扩展是生成多个相关查询，提高召回；分解是把多跳问题拆成子问题，逐个检索再综合。

改写适合表述模糊，扩展适合召回不足，分解适合多跳推理。三者可以组合，但每加一步都会增加延迟和成本，应该按实际失败类型选择，而不是全上。多查询会放大召回噪声，分解会产生更多中间结果，两者都要配合重排和去重，否则合并后候选会迅速膨胀。分解还要小心过度，把一个问题拆得太碎，每块都单独检索，最后可能拼不回原来的问题；分解的粒度应该以"每块能独立检索"为标准。

改写和检索的关系是双向的：改写影响检索结果，检索结果也能反过来提示改写是否有效。如果一次改写几乎没召回任何新内容，说明这次改写没有价值，下一次可以跳过。

### 路由与降级

路由决定一个请求走哪条检索路径：不检索、只走稀疏、走混合、走图检索，还是走上层 Agentic。路由本身也可以是一个类型化决策。好的路由按成本排序：能一步答对的就不多查，需要多源的就多路召回。路由错了，要么答案不准，要么成本过高。

路由可以简单到几条规则，也可以复杂到一个分类模型。多数系统不需要太复杂：按问题长度、是否包含专有名词、是否多跳，几条规则就能覆盖大部分情况。路由还可以根据历史成功率动态调整：某个查询类型在检索路径上长期表现好，就默认走它；表现差，就升级到更复杂的路径。

每个检索模块都可能超时或失败，所以要有降级路径。混合召回里稀疏检索挂了，应该退回到只用稠密；重排超时，应该退回按召回分数排序。降级路径要预先定义，没有降级，一个次要模块的故障会让整个问答失败。降级不只是容错，也是成本控制，一个模块临时不可用时退回更简单但可用的路径，比直接报错更符合用户预期。降级要能被记录，事后才能知道哪些请求走了降级。

## 五、进阶结构：它们各自补什么洞

基础 RAG 之上有一组被反复提起的结构：GraphRAG、LightRAG、Self-RAG、Corrective RAG 和 Agentic RAG。它们容易被误读成"越往后越先进"，实际上补的是不同的洞：图结构补关系，Self-RAG 补自我判断，Corrective RAG 补证据质量，Agentic 补多步决策。一个只需要单跳事实的场景，上 Agentic 只是浪费。

| 结构 | 补什么洞 | 主要代价 |
| --- | --- | --- |
| 基础 RAG | 无 | 切块、召回、重排都要自己调 |
| 查询改写与路由 | 表述不一致、路径单一 | 额外延迟 |
| GraphRAG | 关系和全局归纳 | 索引成本高、更新难 |
| LightRAG | 全局视图，成本更低 | 归纳不如完整图细 |
| Self / Corrective RAG | 检索质量不确定 | 更多模型调用 |
| Agentic RAG | 多跳和复杂证据判断 | 状态管理和预算 |

判断要不要上某个结构，可以问一个具体问题：系统现在的失败，是不是集中在它要补的那类问题上。如果是，值得试；如果失败更多是找不到单个事实，问题还在基础召回上。技术要服务于具体的失败，而不是服务于流行度。

### GraphRAG 与 LightRAG：处理关系和全局

GraphRAG 针对的是"关系型"和"全局型"问题。当问题关心实体之间的关系，或者需要"整体讲了什么"的归纳，按片段检索的向量方案会力不从心，因为它只能给出局部描述，拼不出全局结构。GraphRAG 从文档里抽取实体和关系，构建图，为社区生成摘要，检索时既走局部邻居，也走全局主题。

它的代价在索引。抽取和摘要都依赖模型调用，成本随文档量增长，而且更新困难：文档变了，图和社区摘要都要跟着变，重建图的代价很高。这决定了它更适合相对稳定、需要全局归纳的语料，不太适合高频更新的场景。用之前要算清索引成本和更新频率，否则很容易在维护上陷入被动。

LightRAG 用双层检索连接局部和全局：低层检索实体和它们的邻域，回答"某个具体事物"的问题；高层检索主题和社区，回答"整体讲了什么"的问题。它不像完整 GraphRAG 那样为每个社区生成详尽摘要，而是在检索时按需组合局部和全局证据，用更低的索引成本拿到近似全局的视图。对大多数只需要"大致归纳"的场景，它比完整 GraphRAG 更实际。

![GraphRAG 与 LightRAG 在索引、全局知识、查询和更新上的对比](/images/posts/rag-graph-vs-light.svg)

图检索的评测和向量检索不同。它要评的不只是"有没有找到相关节点"，还有"有没有找到连接这些节点的关系"；一个只找到孤立实体的图检索，等于退化成普通的实体检索，没有发挥图的价值。图检索的实现门槛也不低，实体抽取、关系判定、社区发现、摘要生成每一环都要调，所以在决定上图检索之前，最好先确认在向量检索上已经做到极限。很多"需要图"的问题，其实是切块和关系元数据没做好。

### Self-RAG 与 Corrective RAG：检索之后还要判断证据

基础 RAG 隐含一个假设：检索到的是对的。Self-RAG 和 Corrective RAG 把这个假设变成需要检查的环节，因为真实系统里检索质量参差不齐，盲目采信会放大错误。

Self-RAG 让模型在生成过程中判断"要不要检索""证据是否支持""输出是否靠谱"，把反思变成生成过程的一部分，让检索按需发生，而不是固定的一步。它的反思也不是越多越好，每一步都反思会拖慢系统、引入更多不确定；更实际的做法是把反思集中在关键决策点上，比如要不要检索、证据够不够、答案是否忠实。

Corrective RAG 则是在检索之后先评估证据质量，质量差时走修正分支：重写查询、放宽条件，或者改用其他来源。关键在"评估证据质量"这一步，它把检索从一次动作变成带检查的过程。两者都会增加模型调用，所以要控制触发频率：只在小部分不确定的请求上触发，成本可控；每个请求都触发，成本会成倍上升。

### Agentic RAG：把检索变成有状态的决策过程

Agentic RAG 把检索放进一个有状态的过程：模型可以决定是否检索、检索什么、结果够不够、要不要再查。检索变成工具之一，而不是固定的一步。它适合多跳、需要判断证据是否充分、需要组合多个来源的问题。

代价是需要状态管理：已经查过什么、还缺什么、预算还剩多少。没有状态，Agent 会在同一批查询上打转；没有预算，它会无限检索。它最难的部分其实是"停"：什么时候证据够了、该给答案了，什么时候证据注定不够、该放弃了。没有清晰的停止条件，Agent 会一直查下去。

Agentic RAG 的一个好处是它能处理"证据不足"的情况，而不是硬答。当它判断证据不够，可以选择追问用户、换一个来源，或者明确说不知道；这种能力在普通 RAG 里需要额外的规则，在 Agentic 里是自然的一部分。它的调试也比普通 RAG 难，因为行为路径更多样，所以轨迹记录必须足够完整：每一步查了什么、看到了什么、为什么继续或停止。没有轨迹，Agentic 的失败几乎是黑箱。

对单跳事实问题，Agentic 只会增加延迟和成本。一个实用的判断是：如果基础 RAG 加上好的重排就能答对，就不需要 Agentic。几种结构也常常组合使用，例如用 LightRAG 做全局归纳、用基础检索补充细节，或者用 Corrective RAG 判断证据质量、质量差时触发 Agentic 的补充检索。

## 六、生产架构：让它稳得住

把上面的模块拼成一套能上线的系统，需要一些不华丽却决定稳定性的工程约束。这套约束的核心，是让系统的每一步都可观测、可降级、可审计。

生产架构里最容易被忽视的是可观测性。每个请求走了哪条路由、检索了多少候选、重排后保留了什么、最终用了哪几条证据，这些都要被记录。出现问题时，没有记录只能猜；有了记录，能快速还原一次问答的完整决策路径。一个完整的检索请求可能经过七八个环节，每个环节都想做复杂处理，延迟就会累积到超出用户耐心，所以常见取舍是让常见路径短、罕见路径长：普通问题走两三步，疑难问题才走完整链路。

### 统一证据格式与组装

无论证据来自向量、关键词还是图检索，都应统一成同一种结构：内容、来源、位置、版本、相关度。统一格式让下游的重排、组装和引用都只处理一种结构，避免为每种来源写一套逻辑。它的另一个好处是让"证据"这个概念可被检查：既然每条证据都有来源、位置和版本，就可以在生成前做一次校验，确认证据是否齐全、引用是否存在、权限是否匹配。

生成之前的校验，其实是把一部分质量控制前移了。事后发现问题，成本是重新生成一遍；事前发现问题，成本是多查一次证据，前者贵得多。把能前移的检查尽量前移，是控制系统成本的有效手段。

召回和重排之后，候选片段可能仍然超过上下文预算，需要压缩：合并、去重、抽取关键句，只留下回答问题必需的部分。压缩有风险，压得太狠会删掉关键证据，所以压缩后要保留来源和边界标记，让每句话都还能追回出处。组装还要防一种情况：多路证据互相矛盾。一条说政策适用，一条说促销期间除外，正确的做法不是随意选一个，而是把矛盾标出来，让生成阶段明确处理，或者退回补充检索。

证据放进上下文也有顺序讲究：稳定的指令在前，证据在中间，问题和输出要求在后；证据之间按相关度排序，最相关的放在更靠近问题的位置。排序不只是给检索用的，也是给生成用的一个隐性信号。

### 权限、注入与多租户

多租户场景下，检索必须按租户隔离，共享索引要在召回阶段就做权限过滤，而不是召回后过滤。隔离不只是数据安全，也是正确性：一个租户的文档出现在另一个租户的上下文里，既是安全问题，也是答案污染。权限过滤还有一个容易忽略的边界，它应该同时影响检索结果和引用列表；如果被过滤掉的内容仍然出现在引用来源里，就等于通过引用泄露了它的存在。

检索到的文档会被放进模型上下文，因此文档内容本身就是攻击面。一份被注入指令的文档，可以让模型忽略原任务、泄露上下文，或做出越权动作。防护的基本原则是指令和资料分开：系统对模型的指令来自开发者，检索到的内容是被引用的资料，两条通道不能混在同一位置。把资料明确标注为"以下是检索到的资料，供参考"，比不作区分安全得多。完整的防护还包括对高风险动作做独立授权，以及对检索来源做信任分级。

权限和注入最好在架构上分开处理：权限是"能不能看到"，注入是"看到了会怎样"。前者靠过滤，后者靠隔离和怀疑，混在一起处理容易顾此失彼。

### 增量更新与新鲜度

真实文档会更新和删除。全量重建索引简单但慢，增量更新快但复杂，要处理新增、修改和删除。删除尤其容易被忽略，只做新增的索引会残留已删除内容，导致模型引用过期信息。索引更新要做三件事：写入新内容、更新被修改的片段、删除已下线的片段，并记录每段的版本和更新时间。

更新的正确性可以从不变量入手：索引里不应出现已删除的文档，也不应缺少新加入的核心文档。前一条靠删除处理保证，后一条靠覆盖率检查保证；把这两条做成自动检查，更新才敢自动化。多个文档同时更新时，处理顺序也可能影响最终状态，用确定性的顺序处理能避免并发导致的不一致。更新的自动化程度可以逐步提高，先半自动（系统生成候选、人确认后发布），稳定之后再提高自动比例。

新鲜度直接影响信任。用户一旦发现系统引用了已经作废的政策，就会对它整体失去信任，哪怕准确率数字不错，过期内容的负面影响也会远大于那些数字。这也是为什么长上下文模型没有让 RAG 过时：把整个知识库塞进上下文既贵又慢，关键信息还容易被淹没；RAG 的价值是用更小的上下文承载更相关的证据。

### 缓存与成本预算

RAG 系统里大量查询是重复或近似的，缓存能显著降低成本：缓存检索结果、缓存查询改写、缓存最终回答。缓存要处理失效，文档更新后相关缓存必须失效，带版本的缓存键能避免返回过期答案；证据格式统一之后还能支持证据复用，同一条证据被多个问题用到时可以省下重复检索。

成本要分层估算：召回便宜，重排较贵，生成最贵，Agentic 的多次循环最贵。优化的空间主要在"少做无谓的昂贵步骤"，而不是"把每步做得更快"。很多回答其实可以基于检索到的原文直接给出，不需要模型生成一大段，把回答做得更短、更聚焦，既省钱又更符合用户想快速得到答案的需求。

缓存和成本优化都要有边界：缓存无限增长会拖慢系统，成本优化过度会牺牲质量。给缓存设容量上限、给成本优化设质量下限，两者都留出边界，系统才稳。

## 七、评测：把检索和生成拆开

RAG 的评测要分层，否则无法定位问题。检索评测看正确文件或片段是否被找到、排名如何；生成评测看答案是否由证据支持、是否回答了问题。混在一起看端到端分数，两个系统可能分数相同，一个检索强生成弱，另一个相反，而它们的改进方向完全不同。

检索评测常用召回率、倒数排名和排序质量；生成评测常用忠实度和答案相关性。忠实度低有两种表现：答案里有证据不支持的内容，或者答案忽略了关键证据；提高忠实度靠两件事，更好的证据和更强的约束。评测的另一个维度是延迟，用户能接受的等待时间有限，一个准确但很慢的 RAG，和不准一样会流失用户，所以报告里质量要和延迟一起看。

### 评测集怎么建

评测集要覆盖三类问题：答案在单篇文档里的、需要跨文档的、答案不存在的。第三类最容易被忽略，但它决定了系统会不会在没证据时硬答。样本还要平衡，简单的检验基本能力，困难的检验上限，中等的检验稳定性，三类都要有，结论才全面。

一个健康的评测集应该有一定的失败率。所有版本都能通过的任务没有区分度，所有版本都失败的任务也不能指导改进；理想情况下，有相当一部分任务处于"当前版本时好时坏"的状态，它们最能反映真实水平。评测集的构造方式要可复现，用脚本生成、版本化保存，比每次手工临时凑一批问题可靠；它还要随系统成长，每次发现新的失败类型，就补一批对应的任务。

没有评测集时，可以先用一批真实问题做冷启动：人工判断每个问题的答案在哪个文档，再用它检查检索是否命中。冷启动的重点是建立"问题到文档"的对应关系，有了它，后续每次改动都能对比。检索评测还要固定版本，因为结果依赖切块方式、嵌入模型、索引参数、重排模型和提示，任何一项变了，分数都会变。

评测的结果要能落到行动。与其说"检索分数偏低"，不如说"跨文档问题的召回只有三成，需要先解决切块和混合召回"。可行动的结论才有价值，只说分数上升或下降，不能指导下一步做什么。

## 八、端到端案例

用一个具体问题把整条链路串起来。用户问"我们的退款政策在促销期间是否适用"。

系统先做查询改写，识别出"退款政策"和"促销"两个主题；路由判断需要检索；多路召回拿到政策文档和促销规则；重排后选出最相关片段；校验发现两段证据的时间不同，触发一次补充检索；最后生成带片段引用的回答，并标注政策版本和生效时间。

这个案例里，每一步都有明确的输入和输出，失败也能定位到具体环节。它尤其说明了"补一次检索"的价值：校验发现两段证据的时间不同，触发补充检索，最终答案才把新旧规则都覆盖到。如果系统不做这层检查，用户可能只拿到一半的政策，得出错误结论；多出来的那一次检索，换来了答案的完整性。

这条链路还可以扩展到多轮。用户在追问"那我上周买的那单算不算"，系统要结合上一轮的政策结论和新的订单信息。多轮 RAG 的难点在状态：哪些结论可以沿用，哪些需要重新检索。把多轮当作一连串独立问答，会丢掉上一轮的上下文；完全沿用，又可能用过期的结论。所以多轮系统要显式管理"哪些结论在当前轮仍然有效"。

把整条链路写下来，还有一个好处：它让团队对齐。每个人都清楚一次问答要经过哪几步，讨论问题时就能定位到具体环节，而不是笼统地说"系统不准"。一份写清每个环节职责和失败模式的文档，比一堆代码更容易让人建立全局认识，而 RAG 系统尤其需要这种文档，因为它的环节多、耦合隐蔽。

## 九、我对 RAG 的理解

RAG 的成熟度不看用了多少花哨的模块，而看它能不能稳定地回答、诚实地承认不知道、清楚地指向来源。做到这三点，一个朴素但扎实的 RAG 系统，往往比一个堆满组件却无人维护的系统更可靠。技术选型会变，这三条标准不会变。

它也不是万能的。如果知识是固定的、量很小、可以写进提示，直接写进系统提示更简单，不必搭检索；如果任务需要的是推理能力而非知识，RAG 也帮不上忙。RAG 解决的是"模型不知道"，不是"模型不会推"。判断要不要上 RAG，可以看两个信号：知识是否频繁更新，答案是否需要出处。两个都成立，RAG 才真正划算。

推动 RAG 变好的，往往不是某一个亮眼的算法，而是切块、重排、引用这些不起眼的基础环节有没有做扎实，以及系统有没有人持续观测和优化。把 RAG 当成一个需要长期维护的系统，而不是一次搭好的工具，是它能不能持续好用的关键。没有维护者的 RAG，会随着知识库的变化慢慢失准，最后被用户悄悄弃用。
