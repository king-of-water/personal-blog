买东西时，你点了一次“提交订单”，页面转了两秒，提示“请求超时”。现在再点一次，会不会产生两张订单？

这取决于服务端怎样处理重复请求。第一次请求可能根本没到，也可能已经创建好了订单，只是成功消息没有回到你的手机。如果第二次被当成一次新的购买，重复订单就出现了。

我们围绕这个问题来讲。例子先只做一件事：订单服务在自己的数据库里创建一张订单，不包含支付、库存等外部操作。把这一步讲明白，再讨论流程跨服务以后哪些保证会失效。

## 一、超时以后，到底发生了什么

假设用户 42 购买一件商品。手机发出创建订单的请求，订单服务收到后写入数据库，生成订单 O900，再把订单号返回。

正常情况下，页面收到 O900，跳转到订单详情。超时情况下，页面没有收到可用的结果，但服务端可能处于三个完全不同的位置。

第一种，请求没有到达订单服务。手机的网络断了，订单服务什么也没做。第二种，请求到了，服务端正在处理，还没提交数据库。第三种，数据库已经提交，O900 已经存在，但响应在返回途中丢了。

这三种情况在手机上都可能表现为“等了两秒，没有结果”。所以页面不能仅凭超时就说“订单创建失败”，更不能认定“可以放心再创建一张”。

这里说的“结果未知”，是调用方不知道结果。数据库里的订单可能已经明确存在，并不需要给订单表增加一个叫 UNKNOWN 的状态。调用方的认识和业务的实际状态要分开。

![下单超时后，先按原请求查询，再决定是否重试](/images/posts/retry-order-confirmation-flow.svg)

图中的“暂未查到”还不等于第一次一定失败。原请求可能在队列里，也可能正在执行；如果查询读取的是有延迟的副本，刚提交的订单也可能暂时查不到。下一步仍然要围绕同一次购买来确认，不能随手换一个编号重新下单。

有时可以明确知道请求没发出去，例如客户端在本地检查参数时就失败了。但只要请求已经可能离开客户端，或者框架内部可能发过其他尝试，就不能仅凭某个连接错误断言服务端没做事。排障时要找到失败发生的位置。

## 二、为什么还要超时，不能一直等吗

一直等也解决不了这个问题。用户不会无限等待，应用的连接和线程也有限。一次调用长时间卡住，后面的请求会占满更多资源，原本的一次慢请求就可能拖累整个服务。

超时的作用是给等待设置上限。它告诉调用方“我最多等这么久”，没有给服务端发出一份可靠的“你一定没执行”的证明。

比如页面愿意等待两秒。网关接收请求、订单服务排队、校验参数已经用了三百毫秒，那么调用下游时就只剩一千七百毫秒，还要留出返回响应的时间。如果每一层都重新获得两秒，整个链路可能远远超过用户原本愿意等待的时间。

因此，服务之间要传递剩余的时间预算。有些框架用“最晚完成时间”表达，有些用“剩余多少毫秒”表达。理解它时，先记住一件事：下游不能把已经花掉的时间重新算回来。gRPC 的截止时间传播就是这一思路的一种实现。[gRPC 截止时间说明](https://grpc.io/docs/guides/deadlines/)

调用超时后，框架可能通知服务端取消处理。服务端可以停止尚未开始的工作，释放资源。但业务线程需要配合检查取消信号，已经提交的数据库事务也不会因为客户端不等了而自动撤销。

如果服务端正在向支付渠道扣款，取消本地等待同样不代表渠道没有扣款。取消处理和确认业务结果，是两件需要分别实现的事情。

合理的超时不是越短越好。正常请求需要五百毫秒，却设置一百毫秒，会制造大量“服务端成功、客户端超时”的请求。设置得过长又会让故障时的资源迟迟无法释放。需要结合正常耗时、排队情况和业务可接受的等待时间来决定，并分别记录等连接、等服务处理、等响应的耗时。

## 三、安全重试的起点：给这次购买一个固定编号

现在考虑第二次点击。服务端怎样知道“这是刚才那次购买的重试”，而不是“用户又想买一件”？

让客户端在第一次提交前，为这次购买生成一个编号，例如 R100。第一次请求带 R100，发生超时后的重试仍然带 R100。用户明确开始另一笔购买时，才生成 R101。

这个固定编号通常叫幂等键。幂等的意思是，同一个操作执行多次，业务效果与执行一次相同。在这个例子里，无论 R100 到达几次，都只对应同一张订单。

```text
第一次提交：用户 42，购买请求 R100，商品 A，数量 1
超时后重试：用户 42，购买请求 R100，商品 A，数量 1
另一次购买：用户 42，购买请求 R101，商品 A，数量 1
```

不能用“用户 ID + 商品 ID”直接当购买编号。同一个用户当然可以先后买两次同一件商品；这样的键会把两次真实购买错误地合并。

也不能每次发送请求时都重新生成编号。那样网络层每重试一次，服务端就看到一次新购买，编号存在也没有意义。客户端需要在这次提交和结果确认期间保存它；页面刷新后若仍在确认这次购买，也要能找回原编号。

还要检查参数是否相同。如果 R100 第一次购买一件商品，第二次变成两件，服务端不能静默返回旧订单，也不能把旧订单改成两件。应明确拒绝“同一编号对应不同请求”，让用户确认原订单后，再发起新的购买。

幂等并不要求每一次响应都逐字相同。例如第一次删除一个资源成功，第二次发现资源已不存在，两个响应可以不同，但资源最终都不存在。HTTP 对幂等方法的定义也是看预期效果，而非要求响应完全一致。[HTTP 幂等方法语义](https://httpwg.org/specs/rfc9110.html#idempotent.methods)

创建订单为了方便调用方确认，通常还会把同一个订单号返回给重复请求。这是接口额外提供的结果重放能力，不能只靠“幂等”两个字就假定已经有了。

## 四、数据库怎样保证两个并发请求只建一张订单

只有一个编号还不够。假设两个请求同时到达，两边都查询 R100，发现没有订单，然后都插入一张，仍然会重复。

“先查有没有，再决定插入”之间有空隙。第二个请求可以在第一个插入之前完成查询。需要让数据库在写入时强制检查：同一个用户的同一个购买编号，最多只能对应一张订单。

下面是简化的表结构：

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    client_request_id VARCHAR(64) NOT NULL,
    request_digest VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    UNIQUE KEY uk_purchase (user_id, client_request_id)
);
```

唯一约束保护的是 user_id 和 client_request_id 的组合。不同用户的编号可以相同，同一用户不能用同一编号建两张订单。真正的接口还要先校验登录身份，不能相信请求里随便填写的 user_id。

request_digest 用来保存关键参数的摘要，例如商品、数量、所选规格。生成摘要前，需要把等价参数规范成一致的格式；不能因为 JSON 字段顺序变了，就把同一请求判成不同请求。

第一次请求在一个数据库事务里插入订单，完成这一步的本地写入，最后提交。对本文的简单例子，不需要先单独提交一条“正在处理”的记录，再另起事务建订单。

两个请求竞争唯一键时，数据库负责协调冲突。某个事务拿到了写入机会，另一个可能等待它结束。如果第一个提交，重复请求读到已有订单，检查参数后返回同一个订单号。如果第一个回滚，没有留下订单，后续尝试才有机会创建它。

![唯一约束把同时到达的同一购买请求归到同一张订单](/images/posts/idempotency-order-transaction-flow.svg)

这里的“读到已有订单”要建立在事务已经结束、查询能看到已提交结果的基础上。不同数据库和事务配置会影响冲突报错、等待和读取细节，不能捕获所有异常后就无条件当作“已有订单”。

伪代码可以写成：

```text
先校验身份和参数
尝试在本地事务里创建订单，使用固定购买编号
  提交成功：返回订单号
  确认为唯一键重复：结束当前事务，再查询原订单
    参数一致：返回原订单号
    参数不一致：拒绝复用这个编号
  连接中断、提交结果不确定：按原编号查询确认
  其他错误：按实际错误处理，不伪装成成功
```

数据库连接在提交时断开，也会让订单服务自己不知道事务有没有提交。这时订单服务同样要按 R100 查询，而不是换订单号再插入。结果未知并不只发生在手机和服务端之间。

唯一约束和订单写入在同一个数据库里，是这个方案能够成立的重要前提。如果先往 Redis 写“R100 已处理”，再创建订单，进程可能在两步中间崩溃，留下“已经处理但没有订单”。如果先创建订单再写 Redis，崩溃时又可能留下“有订单但没有去重标记”。两次独立写入不能直接替代这里的原子提交。

## 五、超时以后，页面与服务端应该怎样配合

假设第一次已经创建 O900，但手机没有收到响应。手机保留 R100，向服务端查询这次购买的结果。服务端查到 O900，就返回订单号，页面进入订单详情。

如果查询暂时没有结果，页面可以短暂等待后再查询，也可以按接口约定用 R100 重试创建。后一种做法的安全性来自刚才的唯一约束，而不是来自“刚才没查到”。

如果第一次其实没到，重试创建 O900；如果第一次正在提交，两个请求在唯一键处协调；如果第一次已经成功，重试拿到原来的 O900。三条路径最后归到同一张订单。

查询接口最好按购买编号查询，并检查订单属于当前用户。用这个编号查任何人的订单会产生越权问题。查询也应尽量读取权威结果，或明确告知调用方读取副本可能存在延迟。

更长的业务可能先接收任务，再异步创建订单。此时“已接收”只能说明服务端持久化了任务，不能说明订单已经创建。接口需要给出任务编号和查询方式，并有人负责恢复中断的任务。只有内存里的一个任务对象，进程一重启就丢失，不足以支撑“已经接收”的承诺。

页面可以显示“正在确认订单，请稍候”，提供查看订单的入口。不能一边告诉用户失败，一边在后台继续创建订单，又让用户重新购买。前端禁用按钮可以减少误操作，但用户可能刷新页面、换设备，网络层也可能重试，服务端的防重复仍然需要存在。

有时确认需要超过本次页面请求的时间预算。可以结束这次等待，但保留购买编号，稍后继续查询。不要为了让接口看起来有一个明确结果，把未知强行改成失败。

## 六、能重试，也不能无限重试

安全重试解决重复效果，不会消除服务端压力。同一个请求重复一百次，即使只创建一张订单，仍然消耗连接、线程和数据库查询。

哪些错误需要重试，要先看原因。参数不合法、没有权限、商品不允许购买，重复发送相同参数通常没有意义。连接暂时中断、服务暂时不可用，可能在稍后恢复。但“可能恢复”和“没有产生效果”不能混在一起：一个返回错误的写请求，也可能已经完成了部分业务。

因此要同时满足两个条件：错误值得再试，接口允许用原编号安全重试。只看 HTTP 的 500 或 503，不能判断订单是否存在。

重试还要有总次数和总时间限制。比如给一次用户操作最多两次额外尝试，并且仍然受两秒总预算约束。若第一轮已经花完预算，就转入结果查询或稍后确认，不要偷偷再等几秒。

失败后立即一起重试容易加重拥堵。可以第一次等几十毫秒，第二次等更久，并让不同请求的等待时间略有差异。这样刚恢复的服务不会在同一个时刻被所有请求再次打满。具体等待值需要结合业务耗时，不存在适用于所有服务的固定数字。

还有一个常见问题是每一层都重试。页面重试三次，网关每次再尝试三次，服务调用下游时又尝试三次，一次购买就可能变成二十七次调用。要明确由哪一层决定重试，其他层的自动行为也要纳入总预算。

查询同样不能无限轮询。连续查不到时逐步延长间隔，超过确认时限给出明确的后续入口。服务端需要能通过购买编号继续查证，而不是要求用户记住一次已经消失的网络连接。

## 七、Exactly-once：业务只发生一次，消息一定只到一次吗

现在把订单创建后的动作扩展一下：订单服务通知另一个服务给用户发优惠券。

消息系统把消息送到消费者，消费者发完券，再向消息系统确认处理完成。假设券已经发了，但确认消息丢了，消息系统为了避免丢任务，会把原消息再送一次。

这个过程跟下单超时很像：发送方没有得到确认，不知道接收方究竟做了没有。选择“不再发送”，可能丢掉尚未执行的任务；选择“再发一次”，就可能重复送达。

所以“消息只到达一次”“处理代码只运行一次”“最终只发一张券”不能互相替代。接收同一消息两次、进入处理函数两次，只要数据库最终只产生一份合法权益，业务仍然可以得到“只生效一次”的效果。

一个具体办法是，优惠券服务使用“订单号 + 优惠券类型”作为发券编号，在自己的数据库里同时写入去重记录和优惠券。两步在同一个事务里提交。第一次成功后，重复消息再次到达，唯一约束阻止第二张券，消费者确认完成即可。

如果只先写“已消费”，再另一个事务发券，崩溃时可能少发；如果先发券，再独立标记“已消费”，崩溃后可能多发。原子边界仍然是关键，不是多一张去重表就自然安全。

订单服务也有类似问题：订单提交以后、消息发送以前崩溃，会留下订单却没有通知。可以在创建订单的同一个数据库事务里，顺便写一条“待发送通知”；后台程序不断扫描这些通知并发送。消息可能重复发送，接收方仍按业务编号去重。这种把业务记录与待发消息一起提交的做法，通常叫事务发件箱。

它保证的是订单与待发通知一起留下。后台发送、对方处理、最后确认仍然可能失败，需要重试和恢复。不能把“写进待发列表”描述成“整个跨服务流程已经完成”。

Exactly-once 通常翻译成“恰好一次”。听到这个词时，应追问：是哪个范围内的一次？消息系统内部的某个处理步骤，还是最终的发券、扣款、发货？范围没说清楚，就无法判断它对业务有没有帮助。

## 八、接上外部支付以后，保证在哪里停下来

本地数据库能够把唯一键和订单写入放在一起，但数据库事务不能直接把银行或第三方支付渠道也包进去。

假设本地记录了“准备扣款”，调用支付渠道后连接超时。渠道可能已经扣款，本地却还没来得及记录成功。此时只查看本地数据库，无法得出“可以再扣一次”的结论。

如果渠道支持同一个支付请求编号的幂等调用，以及按该编号查询结果，就继续围绕原编号确认。第一次扣款成功但响应丢失时，重复请求应关联原扣款，而非新增一笔。具体保留时间、失败结果是否重放等规则，需要以渠道接口为准。Stripe 的接口就是一个提供幂等请求键的实际例子。[Stripe 幂等请求说明](https://docs.stripe.com/api/idempotent_requests)

如果渠道既不支持幂等，也不能查询原请求，调用方就无法仅靠自己的重试规则保证不重复扣款。可能要暂停自动重试，通过渠道流水、对账或人工确认恢复。事后退款可以补救，但不能把已经发生的重复扣款说成“从未重复”。

幂等键的保留时间也影响保证。若删除了 R100 对应的记录，几天后旧请求又被发送，服务端可能把它当新请求。对订单这类长期业务，可以让订单上的购买编号保留足够长时间，或在超过接口重试窗口后明确拒绝旧请求并引导查询历史结果。

同一个编号是否过期、过期后能否再次创建、失败是否被记住，都需要写进接口约定。不能把某个平台的二十四小时规则抄成所有业务的统一标准。

回到开头的问题：下单超时，再点一次安全吗？如果第二次保留原购买编号，服务端用数据库约束把它归到同一张订单，并且能够查询已提交结果，就有了清晰的处理路径。如果只是再发一次普通创建请求，那么页面上的“重试”在服务端眼里很可能就是一次新购买。
