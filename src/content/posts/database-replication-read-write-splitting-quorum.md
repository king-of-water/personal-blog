用户创建一个短链接，页面提示成功，还给出了短码。马上打开这个链接，却显示“不存在”。过一会儿再刷新，链接又能用了。

如果创建写入主库，跳转查询从库，这种现象就可能来自复制延迟：主库已经有记录，从库还没把这笔变化应用到自己的表里。创建成功和任意副本都能查到，并不是同一个时间点。

这篇先讲常见的一主多从。我们要解决的具体问题是：为什么要增加副本，副本怎样拿到新数据，哪些请求可以读旧一点的数据，哪些必须确认读到了自己的修改。最后再用三台机器的例子简讲 Quorum，不展开另一套数据库的完整架构。

## 一、数据库为什么需要副本

假设短链接所有创建、修改和跳转请求都访问同一台数据库。请求量上升后，跳转查询占用了大量 CPU、磁盘和连接，创建接口也跟着变慢。

可以增加从库，保存同一份数据，让一部分查询在那里执行。主库继续处理写入，将发生的变化复制给从库。这样，一部分读请求不再与主库上的写入竞争资源。

另一个用途是数据冗余。主库发生故障时，从库可以成为恢复候选。不过是否能接管、接管以后有没有丢数据，还取决于从库追到了哪里和切换规则，后面会展开。

副本与分库分表不同。分库分表把不同记录放到不同地方，例如用户甲在库 1、用户乙在库 2；主从复制则把同一批记录复制出多份。两者可以同时存在，每个分片再配自己的副本。

副本也不是免费的。每台从库需要存储、接收日志和执行更新；一个写入很重的系统，不能靠无限增加读副本消除主库的写入瓶颈。慢查询也可能耗尽从库资源，让复制更落后。

还要区别副本与备份。主库误删了记录，删除通常也会复制到从库。从库不是一份天然保留删除前数据的历史副本，恢复误操作仍需要备份与日志。设计时应分别考虑分担读取、故障接管和历史恢复。

## 二、一笔写入怎样出现在从库里

继续用短链接。创建服务在主库插入记录 L100，提交事务，主库把这次变化记入用于复制的日志。从库接收日志，再按照日志修改自己的表。

在 MySQL 中，主库这份变化日志叫 binlog，也就是二进制日志。从库接收以后，先保存到自己的中转日志 relay log，再由应用日志的线程执行。可以把后者理解为“照着收到的变化，把本地数据更新好”。[MySQL 复制过程](https://dev.mysql.com/doc/refman/8.4/en/binlog-replication-configuration-overview.html)

所以从库至少可能处于几种位置：还没收到 L100 的变化；收到了，但还没执行；正在执行；已经提交到自己的表，可以被新的查询看见。

![主库提交后，从库还需要接收日志并应用，才能查到新记录](/images/posts/replication-write-to-visible-flow.svg)

图里创建接口返回时，从库可能还停在前两步。此时访问从库，查不到 L100 完全可能。它没有证明主库写入失败，只说明这台从库当前还没有可见的记录。

为什么应用会慢？可能是日志传输延迟，也可能是从库磁盘慢、执行更新时等锁、前面有大事务，或者复制处理遇到错误停住。只检查“网络连着”，无法知道数据已经追上。

如果主库产生变化的速度长期超过从库处理速度，从库会越落后越多。平均二十毫秒的延迟也不能保证下一次仍是二十毫秒：一次大事务、一次重启或一段网络故障，都可能拉长等待。

“收到日志”和“查询能看见”因此要分别检查。一次查询还可能受自己的事务快照影响：即使从库后来应用了变化，早先开始的快照事务也不一定自动看见新内容。这里讨论的是正常路由发起的新查询。

## 三、读写分离为什么会把这个时间差暴露出来

读写分离最简单的规则是：写入发主库，查询发从库。它改变了请求去向，没有让每个从库在查询之前自动追到最新数据。

用户创建 L100，服务端写主库；用户紧接着打开链接，另一个请求被分配到从库 B。B 尚未执行创建事务，就返回没有记录。如果程序把它解释成“短链接从来不存在”，用户看到的就是 404。

可以把路由简化成：

```text
创建、修改、删除 → 主库
允许延迟的查询 → 健康从库
写后确认、支付状态等关键查询 → 单独选择读取方式
```

第三行不能省略。SQL 看起来都是 SELECT，业务要求却不同。离线报表可以落后几分钟，创建后的结果页通常不能把刚创建的东西说成不存在。

事务中的查询也不能随意换数据源。应用在主库事务里修改一行，随后查询这行，需要使用同一事务连接；从库看不到这个事务尚未提交的修改。SELECT FOR UPDATE 虽然是读语法，也承担锁定任务，不能按普通查询分配给只读从库。

还有一种现象：用户第一次读从库 A，看到标题版本 3；第二次读更落后的从库 B，又看到版本 2。没有新的修改，页面却像倒退了一步。前面的“一致性模型”文章把它叫单调读问题；在这里，具体原因就是请求切换到了更旧的副本。

所以选择读取方式应当考虑这次请求需要什么，而不只是看 SQL 是读还是写。应用扩容、负载均衡和跨设备访问都可能改变路由，不能假定用户下一次仍落到刚才那台机器。

## 四、写完马上要看见，可以怎样处理

最直接的办法，是让创建后的结果查询读主库。L100 已经在主库提交，就到同一个当前有效主库查询，不必等待从库追赶。

对于修改资料后的确认页、支付结果确认、刚创建订单的详情页，这通常比给所有查询引入复杂协议更简单。代价是这些查询占用主库资源，但并不要求所有报表、列表和公共内容都回主库。

第二种办法，是写完后短时间让相关查询走主库。比如两秒内读主库，两秒后恢复读从库。这样可以改善大部分正常延迟下的体验，但两秒不是可靠证据。若复制卡了十秒，保护窗口结束后仍然可能旧读。

这个标记如果只放在当前应用内存里，下一次请求落到另一实例，也可能失效。放在会话上下文里时，跨设备或匿名分享又不一定带得过去。因此应把固定时间方案描述为体验优化，不能承诺任何故障下都能读到新值。

第三种办法，是带着“至少等到这笔事务执行完成”的凭据查询。从库已经执行到这里，就可以读；还没执行到，就在有限预算内等待，超时回主库或明确结束等待。

MySQL 的 GTID 可以标识事务。写入方取得本次提交对应的 GTID，传给读服务；读服务可以用 WAIT_FOR_EXECUTED_GTID_SET 等待目标事务在该副本执行完成。这个等待会返回结果，业务代码必须检查成功还是超时，不能调用完就默认已经追上。[MySQL 复制等待函数](https://dev.mysql.com/doc/refman/8.4/en/replication-functions.html)

```text
带着事务凭据选择从库
  已经执行目标事务：在该副本查询
  尚未执行：在请求预算内短暂等待
    等到：查询
    超时：回当前有效主库，或返回稍后确认
```

真正接入时，还要解决凭据怎样取得、怎样跨接口传播、等待与查询使用哪个副本。不能拿主库全局的最新进度随意当作每个请求自己的提交凭据，也不能先在副本 A 等到，再把查询随机发往副本 B。

![关键查询确认副本已经追到所需事务，否则等待或回主库](/images/posts/replication-fresh-read-routing.svg)

第四种办法，是创建成功后把短码与目标地址写入缓存，让立即打开的请求直接命中。但数据库和缓存是两次写入，进程可能在中间崩溃。缓存未写成功、过期或被淘汰时，查询仍要有正确的数据库回源策略。

不能先写缓存再提交数据库，随后把尚未成功的创建结果展示给用户；也不能以为“用了缓存”就已经消除了旧读。缓存解决部分读取路径，失败路径仍需设计。

短链接还有负缓存问题：程序查询旧从库，看到不存在，把“没有 L100”缓存五分钟。原本几百毫秒的复制延迟，就被扩大成五分钟的访问失败。需要新鲜度的不存在结果应向主库确认，再决定是否缓存；无法确认时也不应伪装成确定不存在。

## 五、“写成功”到底说明了哪些机器有数据

创建接口返回成功，不能只看系统有没有从库。要看事务提交前实际等待了什么。

在通常的异步复制下，主库提交不等从库追上。即使从库暂时失联，主库仍可以提交并向客户端返回。好处是从库变慢不会直接拖住每次写入；风险是刚确认的写入可能还只在主库。

如果原主库永久损坏，只能用尚未追上的从库接管，这部分记录就可能丢失。若原主库能够从自己的持久化数据恢复，情况又不同；“异步”不等于每次主库重启都会丢事务。

MySQL 半同步会在确认时等待副本保存相应日志。它提高了故障时另一台机器拥有这笔变化的机会，但“保存日志”仍不等于“已经执行到表里”。因此半同步成功后，立刻随机读从库，仍可能旧读。[MySQL 半同步复制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)

半同步等待超过配置时限时，还可能退回异步。配置上启用了半同步，不代表每一笔实际写入都处在这个模式，运行状态也要检查。[MySQL 半同步监控](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync-monitoring.html)

可以用四个问题检查写成功的含义：主库是否已经可靠提交？哪个副本收到？那个副本能否恢复收到的日志？它是否已经应用并能查询？确认点越靠后，通常需要等待越多。

等待也会付出成本。副本网络抖动、磁盘慢，都可能拖长写入耗时；足够多的副本不可用时，系统可能只能暂停写入或降低原来的保证。设计中必须明确选择，不能一边不等副本，一边承诺任意切换都不丢已确认数据。

对于“写完能读到”和“主库永久故障后不丢”也要分开。关键查询读主库，可以解决正常运行时的写后确认，却没有让数据自动多存一份。半同步保存到另一个节点，则没有自动让每一个读副本都马上可见。

## 六、主库故障以后，为什么不能随便选一个从库

假设主库已经提交到事务 103，从库 A 应用到 100，从库 B 应用到 98。提升 A 比提升 B 留下更多数据，但 A 仍然缺少 101 到 103。

“选最先进的从库”只能在候选之间比较，不能证明它包含所有已经向用户返回成功的事务。如果原主库还有机会恢复，需要权衡等待恢复与尽快接管，而不是只看哪一种最快恢复连接。

切换也不只是改一个地址。新主必须具备接管所需数据，旧主不能继续接受业务写入，应用连接要转向新主。否则某些应用仍写旧主，另一些写新主，两边会形成不同历史。

网络联系不上旧主，并不等于旧主已经停机。它可能还能被另一部分应用访问。运维系统需要在真正的写入路径上隔离旧主，比如关闭旧主、撤销访问或让代理拒绝旧连接。仅更新服务发现，不一定会断开已经建立的连接。

计划内切换可以先停写，再等候选追上最终位置，最后切换。故障后的紧急接管可能无法等待原主给出最终位置，能保留多少数据就依赖前面的复制确认和现场证据。

调用方也可能在提交或切换期间超时。事务可能已经成功，客户端却没收到。它应该按原创建编号查询或安全重试，而不是换一个短链接编号重新创建；这个问题与前面的 RPC、幂等文章相同。

主库读的保证也有前提：读的是当前唯一有效主库，查询能看到已提交数据。切换混乱、读到旧主，或者使用较早的事务快照时，“走主库”三个字也不能自动保证读新值。

## 七、Quorum 先理解成“等多少份回应”

Quorum 是法定数量的意思。在多副本读写里，它关注的是：一次操作需要多少个副本参与，才满足设定的完成条件。多数派是常见选择，但不能把所有系统的 Quorum 都等同于同一套多数派规则。

先看一个单独的简化例子，不把它套进上面的一主多从路由。某个存储系统把一条数据保存在 A、B、C 三台机器上。原来三台都是版本 6，现在写入版本 7，要求至少两台确认才算写成功。

假设 A、B 保存了版本 7，C 暂时还是版本 6。随后读取也要求取两台的结果：读 A+B 都是新值；读 A+C 或 B+C，则一新一旧。任何两台组合都会遇到至少一台保存版本 7 的机器。

这就是常见的 N、W、R 公式的来历：N 是副本总数，W 是写成功所需的确认数量，R 是读时参与的数量。这里 N=3、W=2、R=2，W+R>N，意味着读写的参与集合不可能完全错开。[Cassandra 多副本读写说明](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo.html#tunable-consistency)

但读到一新一旧以后，系统还要比较版本并决定返回什么。如果收到第一个旧值就立刻返回，根本没有用上两台的结果。并发写入、故障和版本比较也有额外规则，不能只背这个公式就声称系统已经获得最强一致性。

若写只等一台、读也只看一台，写入 A 后读取 C 就可能看到旧值。若写要求三台全部确认，读一台容易看到该次成功写，但任意一台不可用就可能无法完成写入。这是在读取成本、写入成本和故障时能否继续之间做选择。

对主要使用 MySQL 主从复制的研发人员，先知道这个基本思路即可。它不是必须配置的一个 MySQL 读写分离开关，也不能直接替代应用选择主库或等副本追上的逻辑。其他存储产品使用什么数量、怎样比较版本，应按各自协议理解。

## 八、放回业务里，哪些查询应该怎么读

短链接创建结果页，需要看见刚创建的记录，可以直接读当前主库。没有必要为了这个页面立刻更换数据库，或把全部查询改成复杂的多副本读。

公共跳转请求可以先读缓存，再按业务新鲜度要求回源。若从库返回不存在，不能轻率把它当作永久事实。删除、封禁和权限撤销可能带来安全问题，读取旧状态的容忍度应该比旧标题更低。

后台统计和报表通常允许延迟，可以读从库或分析存储，并告诉使用者数据截至什么时候。支付结果确认、库存扣减则需要根据权威状态或带条件的写入判断，不能只相信随机副本上的旧查询结果。

| 业务场景 | 可以先采用的策略 | 要注意的边界 |
| --- | --- | --- |
| 创建或修改后的确认页 | 当前主库查询 | 主库有效性、事务快照 |
| 已有事务凭据的关联查询 | 等指定副本应用后查询 | 等待有上限，查询不能换到旧副本 |
| 普通内容列表与报表 | 健康从库，允许约定延迟 | 展示水位，剔除严重落后副本 |
| 短链接不存在的判断 | 必要时向主库二次确认 | 不把旧从库的空结果长期缓存 |
| 删除、封禁、权限检查 | 读取当前有效状态或独立严格检查 | 不能只按普通列表的旧读容忍度处理 |

发现旧读时，先沿这条链路排查：主库有没有提交，日志有没有送到从库，从库有没有执行完成，这次查询实际去了哪里。不要只看一个平均延迟，几台正常副本也可能掩盖一台严重落后的机器。

从业务要求开始分流，通常能保留读副本带来的收益，又不让关键确认读到旧数据。主从复制负责把变化传过去，读写分离负责选择访问位置；一次请求需要多新的数据，仍然要由业务明确提出。
